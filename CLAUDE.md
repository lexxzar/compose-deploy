# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Test Commands

```bash
go build -o cdeploy .          # Build binary
go test ./...                   # Run all tests
go test ./internal/runner/ -v   # Run tests for a single package
go test ./... -count=1          # Run all tests uncached
go mod tidy                     # After adding/removing imports
```

The root command launches a Bubble Tea TUI requiring a TTY, so `cmd/root_test.go` tests flag registration and subcommand structure rather than executing the root command directly.

## Architecture

cdeploy is a dual-mode tool: interactive TUI (no args) or non-interactive CLI (`deploy`/`restart`/`stop`/`list`/`logs`/`exec` subcommands). Both modes share the same core through a three-layer architecture:

```
cmd/ (Cobra)  →  runner (pipeline orchestrator)  →  compose (docker CLI wrapper)
tui/ (Bubble Tea) ↗
```

**Key abstraction**: `runner.Composer` interface (defined in `internal/runner/runner.go`, implemented by `internal/compose/compose.go` for local, `internal/compose/remote.go` for SSH, and `internal/compose/hostcontainers.go` for the read-only unmanaged-container view). This is the seam between the orchestrator and Docker — the runner is testable with mock implementations. Methods: `Stop`, `Remove`, `Pull`, `Create`, `Start`, `ListServices`, `ContainerStatus`, `ContainerStats`, `CheckUpdates`, `Logs`. When widening this interface, every mock implementation must add a matching no-op — there are mocks in `internal/runner/`, `internal/tui/app_test.go` (`mockComposer`), `cmd/deploy_test.go` (`opMockComposer`), and `cmd/list_test.go` (`mockComposer`, `mockComposerStatusErr`); a fast `grep -rn "func.*Composer.*ListServices" ./...` enumerates them.

**Event system**: `runner.Run()` sends `StepEvent` structs through a channel. The CLI consumer (`cmd/deploy.go:runOperation`) prints colored status lines. The TUI consumer (`internal/tui/app.go`) drives a Bubble Tea model through `tea.Cmd` that reads from the channel.

**TUI state machine**: Seven screens: `screenSelectServer` → `screenSelectProject` → `screenSelectContainers` → `screenProgress` (for operations), `screenLogs` (for log viewing), `screenConfig` (for config viewing/editing), or `screenInspect` (for the read-only container inspect view). The server screen is shown whenever servers are configured in `~/.cdeploy/servers.yml`; selecting "Local" fast-tracks to containers if a local compose file exists. The model is a flat struct with a `screen` field determining which view/update logic runs. Operations are triggered via action keys on the container screen (`r` restart, `d` deploy, `s` stop) which enter a confirmation sub-state (`confirming` bool + `pendingOp`) before proceeding. The `x` key execs into a running container interactively (enters confirmation with `pendingExec = true`, then shells out via `tea.ExecProcess`; shows warning if container is not running). The `l` key opens the log viewer for the cursor service without confirmation (read-only operation). The `c` key opens the config screen without confirmation (read-only by default). The `i` key opens the inspect screen for the cursor service, also without confirmation, and is the one container action key that is NOT gated on `m.readOnly()` — see the "Inspect screen" paragraph below. Back-navigation (`esc`, also aliased to `q` on nested screens — see "Exit confirmation for remote connections" below) resets downstream state; during confirmation, `esc` cancels without navigating back. The project picker is auto-skipped when the current directory contains a compose file and no servers are configured (backward compatible). `Compose.ListProjects()` discovers projects via `docker compose ls -a --format json`; both `ProjectLoader` literals in `cmd/root.go` then run that result through `projectsWithUnmanaged`, which appends the synthetic `(unmanaged)` row when the host has containers with no compose project label — see the three `Unmanaged containers — …` paragraphs below.

**Exit confirmation for remote connections**: `ctrl+c` is the hard-exit shortcut from any screen. When a remote SSH connection is active (`disconnectFunc != nil`), pressing `ctrl+c` shows a confirmation prompt instead of quitting immediately. The `quitting bool` field on Model gates a global intercept at the top of `handleKey()`: `y` quits, `n`/`esc` cancels, all other keys are swallowed. `View()` checks `quitting` first and renders a standalone confirmation screen via `viewQuitConfirm()` (`"Disconnect from {serverName}? (y/n)"`). The `tryQuit()` helper replaces direct `return m, tea.Quit` calls on all screens except `screenSelectServer` (which always quits immediately since no remote connection exists there). `quitting` is reset to `false` in `esc` back-navigation handlers that clear `disconnectFunc` and in the `entryLocal` handler. Local sessions (`disconnectFunc == nil`) bypass the prompt entirely — `tryQuit()` returns `tea.Quit` directly.

**`?` key-reference overlay**: The `?` key opens a full-screen key list for the current screen. It is a flag (`helpOpen bool` on Model, beside `quitting`), not a screen constant of its own — a screen would drag the overlay into the back-navigation chain, the `clearSearch()` departure checklist, and the session-counter discipline. `View()` checks `helpOpen` immediately after the `quitting` check and returns `viewHelp()`, so the overlay replaces the whole screen exactly like `viewQuitConfirm()` and is invisible to `svcVisibleCount()` and the reserved-bar math. The renderer lives in its own file, `internal/tui/help.go`; the `helpOpen` field, the `View()` check, the two `handleKey()` intercepts, the `confirmPromptArmed()`/`typingInInput()` key-dispatch predicates that gate them, and the `connectResultMsg`/`rollbackSnapshotMsg` clears are in `app.go` (`canGoBack()` and the footer helpers live there too, beside `viewSelectContainers`): `helpGroupsFor(s screen, hc helpContext) []helpGroup` is near-pure data (the three context bits travel in a named `helpContext{canGoBack, readOnly, phase}` rather than as adjacent same-typed parameters, which a call site could transpose silently) — a `helpGroup` is a title plus `helpEntry{keys, desc}` rows — and covers all 9 screens; `Model.helpGroups()` is the renderer's entry point and supplies the three context bits from `Model.canGoBack()`, `Model.readOnly()` and `Model.progressPhase()`. **Group ORDER in `helpGroupsFor` is load-bearing**: `splitHelpGroups` cuts the slice sequentially, so LEAVE sits 4th of 6 on `screenSelectContainers`, 3rd of 4 in `readOnlyContainerGroups` and 3rd of 4 on `screenLogs` purely to land it in the left column — reordering a group for readability changes the rendered layout. **The LEAVE group is conditional, not literal**: on `screenSelectProject` (standalone: no config, no servers) and `screenSelectContainers` (`!showPicker`) `q` QUITS and `esc` is a no-op, so `leaveGroup(false)` renders `q quit` instead of `q esc → back`. `Model.canGoBack()` is the single predicate behind both that group AND the footer's `back` label, so the overlay can never contradict the footer rendered a moment earlier (pinned by `TestHelpGroups_LeaveGroupMatchesFooter`). **`screenProgress` is conditional for the same reason, on a THREE-state phase rather than a bool**: `esc` changes MEANING across the operation's life — while the pipeline runs it CANCELS the operation (`q` and `ctrl+c` are no-ops there), during the health gate `q`/`esc` skip the wait, and once finished `q`/`esc` navigate back. `progressGroups(phase)` renders one table per phase and `Model.progressPhase()` resolves it in the SAME order as `viewProgress()`'s footer switch (`waiting` first, because `waiting` implies `done`), so the overlay and the footer cannot disagree. All three tables name the same three keys, so the drift pin holds whichever phase it samples; `helpKeyTokens(s, canGoBack, readOnly)` unions over `allProgressPhases` anyway, and `TestHelpGroups_ProgressPhases` (what the overlay SAYS) plus `TestProgressPhases_BehaviourMatchesLabels` (what the keys DO) pin the two halves against each other. A static progress table advertised `esc skip health wait` and `ctrl+c quit` mid-pipeline — wrong in the riskiest phase, and the finding an external review caught. `screenName(s screen)` labels the title (`cdeploy > keys > services`, the same `>` breadcrumb separator every other screen uses); `splitHelpGroups` balances the groups across two columns by rendered height (`helpGroupLines` = entries + title + separator), `helpColumnRows` aligns descriptions on the widest key, and `layoutHelpColumns(groups, width)` joins the two columns with `lipgloss.JoinHorizontal`, falls back to ONE column when the two-column render exceeds `width`, then clamps every row with `clampToWidth` — the same never-wrap guarantee as `searchBarLine()`/`logBarLine()`. **The overlay is budgeted against `m.height` too**: the single-column fallback stacks the container table to 24 rows, and bubbletea's renderer keeps only the LAST `height` lines, so without a budget the title and the first groups scroll off a 24-line terminal with no way back (the overlay swallows every scroll key). `budgetHelpRows(rows, budget, width)` truncates to `m.height` minus the title/hint chrome and spends the last row on a `▼ N more · resize for the rest` marker; a budget below 1 (a pane too short for the chrome alone) is clamped up to 1 rather than passed through, the same floor `svcVisibleCount()` applies, and the unknown-height case (`m.height == 0`, tests) is handled by `viewHelp()` skipping the helper entirely. Because of that floor the overlay bottoms out at FIVE physical lines (title 2 + one body row + hint 2), so a pane of height 1-4 still over-renders — accepted, and pinned by `TestViewHelp_MinimumHeightFloor` rather than left undefined: the renderer keeps the LAST lines, so what such a pane drops is the title while the close hint (the only way out) survives. **Truncation ORDER is the discoverability contract**: the footer carries six tokens — `space toggle`, the back key and `? keys` on line1, `d deploy`, `r restart` and `l logs` on line2 — so every other key on the container screen exists NOWHERE else: `a all`, `/ search`, `n N`, `R rollback`, `c config`, `x exec`, `i inspect` and `U check updates`. `helpGroup.actions bool` marks the groups whose keys are advertised nowhere else — on the container screen that is FIND, SELECT, OPERATE and INSPECT, leaving only MOVE (arrows) and LEAVE unflagged — and `singleColumnOrder()` (applied ONLY in the single-column fallback, where the budget actually bites) emits the flagged groups first, so what falls off the bottom is the guessable navigation instead. FIND is split out of MOVE for exactly this reason: `/` and `n N` were riding along with the arrow keys in an unflagged group. The fallback also renders through `helpStackedRows()`, which drops the blank line BETWEEN groups (`helpColumnRows()` keeps it for the two-column layout): that takes the container table from 30 rows to 25, and 25 is what makes all 19 action rows fit the 20 a 24-line pane keeps. Truncation table at width < 65 (below the two-column threshold; re-measured when `i inspect` became the 19th action row, and identical at widths 30/40/50/59 and 64 — below the threshold the width does not change the row count): height >= 24 keeps everything, 23 loses `U check updates`, 22 loses `x exec` too, 21 loses `c config` too, 20 loses `i inspect` too, 19 loses `l logs` too. Every threshold moved up by exactly one when `i` landed, so a 20th action row moves them all again — re-measure rather than extrapolate. The read-only variant stacks to 16 rows and still fits every action row at every height >= 19, so it never truncates an action key. Pinned by `TestViewHelp_NarrowTerminalKeepsActionKeys` (widths 30/40/50/59 at height 24, want-list = the full nowhere-else set), by `TestViewHelp_InspectSurvivesTheFirstTruncation` (height 23, the FIRST notch where a key must go: `inspect` survives and `check updates` is the one sacrificed — height 24 fits everything, so the insert position of `{"i", "inspect"}` in `inspectGroup` is unguarded without a test that samples the notch) and by the ordering assertion in `TestLayoutHelpColumns_SingleColumnFallback`, which pins the CONTRACT against the RENDERED fallback (every `actions` group appears above every non-`actions` one, over whatever groups the screen declares) rather than a hard-coded group list. A short-AND-wide pane (e.g. 120x14) still truncates both columns' tails; the `▼ N more` marker names the remedy. **`viewHelp()` must NOT end its string in a newline, and the height test must NOT trim one.** bubbletea v1.3.10 hands `View()` straight to `standardRenderer.write()`, and `flush()` does a bare `strings.Split(r.buf.String(), "\n")` with NO `TrimSuffix` before keeping the last `r.height` elements — so a trailing newline is a whole extra element, the overlay renders at `m.height + 1`, and the renderer drops the title: the exact failure the budget exists to prevent. `viewSelectContainers()` and `viewLogs()` end without one for the same reason. `TestViewHelp_FitsShortTerminal` therefore splits the RAW `m.View()`, and `TestViewHelp_NoTrailingNewline` pins the invariant directly so a regression names the cause rather than the symptom. Deliberately NOT scrollable — the overlay is a flag over the current screen, not a screen with its own viewport state; widening past the two-column threshold or a taller pane brings the rest back. `helpGroupTitleStyle` and `helpKeyStyle` live in `styles.go`. No composer call and no goroutine, so the overlay needs no session counter and no stale-message guard. **Intercept order in `handleKey()` is load-bearing**: (1) the `quitting` intercept, (2) the `helpOpen` swallow block, (3) the `?` open block, (4) the `q`→`esc` rewrite. The swallow block MUST precede the open block — otherwise a `?` pressed while the overlay is open would re-open it and never close it. Close keys are `?`, `esc` and `q`; every other key is swallowed, so `d` cannot arm a deploy from behind the overlay. **`ctrl+c` clears `helpOpen` and FALLS THROUGH** instead of returning: the fall-through makes each screen's existing `ctrl+c` semantics apply unchanged — the plain local quit, the remote disconnect prompt, and the mid-progress no-op on `screenProgress` while `!done && !failed`. The rationale is NOT "`ctrl+c` is a hard exit from any screen"; that rule has the mid-progress exception, and the fall-through is what preserves it. The open block is additionally gated on `!m.confirmPromptArmed()`: `?` at an armed destructive prompt does nothing, because the overlay would hide the prompt and the single `esc` that closes the overlay would leave it armed underneath — a two-stage `esc` nobody expects (the `q` rewrite makes the same call). **`confirmPromptArmed()` is screen-SCOPED and that is load-bearing** (`screenSelectContainers` → `m.confirming`, `screenSettingsList` → `m.settingsDelete`, else false): `confirming` is armed on the container screen and `enterProgress()` does NOT clear it (only the `esc` back-nav out of `screenProgress` does), so a flat `!m.confirming` gate keeps the overlay shut for the ENTIRE life of the progress screen — hiding the phase table above, including the running phase's destructive `esc`. A `Model{screen: screenProgress}` literal cannot catch that regression; `TestHelpOverlay_OpensOnProgress` drives the real `d` → `enter` → `?` sequence instead. **Two message handlers clear `m.helpOpen` themselves.** `connectResultMsg` clears it for BOTH branches (above the `if msg.err != nil`): the SUCCESS branch is the one that reassigns `m.screen` (to `screenSelectProject`), which an open overlay would ride into with a stale key table; the error branch clears alongside `quitting`/`clearSearch`/`clearWaitState` as uniform departure-site cleanup. Neither is reachable with the overlay open today (the connect runs through `tea.ExecProcess`, which suspends key input, and the overlay swallows the `enter` that starts a connect), so this is defence, not a live path. `rollbackSnapshotMsg` IS live: it is the one confirmation armed by a message rather than a key, so the `?` open gate never saw it — press `R`, press `?` while the async `ReadSnapshot`+`ListServices` fetch is in flight (seconds over SSH), and the rollback prompt would arm behind the overlay. It sets `m.helpOpen = false` next to `m.confirming = true`. Any future handler that arms a confirmation must do the same. **`typingInInput()` duplication rule**: the helper reports whether an open text input is capturing raw runes (`screenSelectContainers`: `m.searching`; `screenLogs`: `m.logFiltering || m.logSearching`; `screenSettingsForm`: `m.settingsField < 4` — fields 0-3 are textinputs, 4 is the color picker; the `< 4` form matches the surrounding code and is safe for out-of-range values, unlike `!= 4`). It is load-bearing because `?` is a regex metacharacter: with `ctrl+r` regex mode on, a user who types `(?:web|db)` into the log filter must get a filter, not a help overlay (pinned by `TestHelpOverlay_RegexFilterAcceptsQuestionMark`). The `q`→`esc` rewrite reads the SAME helper (`if key == "q" && !m.typingInInput()`), so **a new screen that opens a text input needs one case in `typingInInput()` and nothing else**. One exception the helper does NOT cover: the `helpOpen` swallow block runs BEFORE it, so while the overlay is up `q` closes the overlay even on a screen where `q` would otherwise be typed into an open input — the input is not visible behind the overlay. `TestHelpGroups_NamesEveryBoundKey` is the drift pin, and it runs BOTH directions: the help table must name every key that screen's `handleKey` case binds (against a hand-maintained expected set), and it must not name a key the screen does not bind — the likelier drift, where a binding is removed or renamed in `app.go` and the table keeps promising it. `TestAllScreens_Complete` pins the `allScreens` list against the contiguous `screen` iota so a new screen cannot silently skip every table test — but only because its bound now anchors to the LAST constant (`int(screenInspect) + 1`). **Recorded residual**: it used to read `int(screenSettingsForm) + 1`, which made that promise false. `screenInspect` was appended AFTER `screenSettingsForm`, so `want` stayed 8 and adding the constant without listing it in `allScreens` left the whole suite green, while the six tests that iterate the slice (`TestHelpGroups_EveryScreen`, `TestHelpGroups_NamesEveryBoundKey`, `TestViewHelp_FitsShortTerminal`, `TestViewHelp_MinimumHeightFloor`, `TestViewHelp_NoTrailingNewline`, `TestViewHelp_NeverExceedsWidth`) silently skipped the new screen. Move the bound to the new last constant with every screen added, or the hole reopens; the screen tax is developer discipline, not a failing test. A static help table that drifts from the dispatch is this feature's standard failure mode — extend the expected set whenever you bind a new key. It runs the standalone (`canGoBack == false`) variant in the names-nothing-unbound direction only: `esc` stays bound on a standalone container screen (it clears a committed search) but `leaveGroup(false)` must not advertise it as a way out. **A key bound only in a sub-state needs a description that NAMES that sub-state.** The pin forces every bound key into the table, but the overlay can only be opened from the idle state (the gate refuses at an armed prompt, and `?` types literally into an open input), so a bare label would advertise a no-op. `enter` on the container screen is bound only inside the `confirming` and `searching` blocks — it therefore reads `enter  confirm the prompt` under OPERATE, not `enter  confirm` under SELECT. Same shape as `enter  commit query` on `screenLogs` and `y n  confirm / cancel delete` on `screenSettingsList`.

**Container footer and the one-line width guard**: two paired methods in `app.go`, beside `viewSelectContainers()`. `Model.containerFooter() string` renders the footer; `Model.containerFooterLines() int` reports how many physical lines it occupies. `viewSelectContainers()` writes the text and `svcVisibleCount()` reserves `2 + containerFooterLines()`, and `containerFooter()` pads every state out to that same count, so the render and the height math cannot drift — a divergence would miscount visible rows and let the list overflow the terminal. `containerHelpLines()` holds the two idle base strings (and the `back` label via `canGoBack()`); both methods read it, so the count is always measured against the footer that is actually drawn. It replaced the old `containerHelpLine2` const, which could no longer be a const once `back` had to be interpolated. `line1` is `space toggle • {back} • ? keys` (36 cells) and `line2` is `d deploy • r restart • l logs` (35 cells). A read-only composer gets a different idle pair — `{back} • ? keys` and `l logs • x exec`, 19 cells each and 41 joined — so both the render and the height math follow the variant through that one helper. `TestContainerFooterReservation`, `TestContainerFooter_AdvertisesOnlyWorkingKeys` and `TestContainerFooter_RendersOneLineAtEighty` all sweep the read-only dimension too. **The footer must advertise only keys the current state actually binds**, which splits the three search states two ways. *Committed* (`searchQuery != "" && !searching`): `line2` is replaced wholesale with `n/N cycle • esc clear`, but `q` and `?` still work — so `back` and `? keys` have to live in `line1` or they would vanish in exactly the state where the overlay matters most, `/ search` having already left the footer. *Typing* (`m.searching`): the search intercept binds ONLY `enter`, `esc` and `ctrl+c`; every other key, `space`, `q` and `?` included, lands in the query as a literal rune (see the container-search paragraph). Keeping `line1` there would name three dead keys, so `containerFooter()` swaps the whole footer for `enter jump • esc cancel` instead — `line1`'s always-visible role is scoped to the committed state, not to all three. **The line COUNT is state-independent**: `containerFooterLines()` decides it from the idle pair alone (the widest of the three on the WRITE path; the read-only variant inverts that, see the clamp below), before any substitution, and the shorter states are padded back out to it — a trailing `\n` for the typing footer, and a trailing `\n` on the confirm prompt in `viewSelectContainers`. Without that, a one-line typing footer under a wrapped two-line idle footer grew the service list by a row below ~76 columns and re-flowed it under the cursor, which is exactly what the reserved-bar design exists to prevent (`TestContainerFooterReservation` now compares the VISIBLE row count across idle/searching/committed/confirming at every width 40-180, not just the total physical height, which `svcVisibleCount` keeps constant by absorbing the delta). `TestContainerFooter_AdvertisesOnlyWorkingKeys` pins both directions (the tokens each state must show, and the ones the typing state must NOT). The full 19-row container key table lives in the `?` overlay. **`i inspect` is deliberately NOT a footer token, and that is a recorded residual, not an oversight**: a seventh token would re-open the 80-column guarantee and the width 40-180 sweep `TestContainerFooterReservation` runs, so `i` lives in the overlay only, exactly like `c`, `x`, `U` and `R` — the accepted cost is that inspect is discoverable through `?` alone. The one-line-versus-two guard measures `m.width >= ansi.StringWidth(oneLine)+2`, NOT `len(oneLine)+2`: each `•` is 3 bytes but ONE display cell, so the byte form over-counts by 2 per separator and split a footer that in fact fits (it split anywhere from 152 to 173 columns). Do not reintroduce `len()`. Because the count is decided from the idle pair, a substitution WIDER than the idle `line2` can overrun a width the idle pair fit — the read-only pair does exactly that (idle `line2` 19 cells against the committed `n/N cycle • esc clear` at 25, overrunning at widths 43-46), so `containerFooter()` clamps every rendered line with `clampToWidth` rather than widening the count, which would re-flow the list (`TestContainerFooter_NeverExceedsWidth`). The one-line footer measures 74 cells when idle, 64 with a committed search and 27 while a search is typing, so it fits an 80-column terminal in every state and the service list keeps the row the second line used to cost (pinned by `TestContainerFooter_RendersOneLineAtEighty` and `TestSvcVisibleCount_GainsRowVersusOldFooter`; `TestContainerFooterReservation` sweeps every width from 40 to 180 asserting rendered rows == `svcVisibleCount()`).

**`q` as back key on nested screens**: A pre-dispatch block at the top of `handleKey()` (after the `quitting` intercept and the two `?`-overlay intercepts) rewrites `q` to `esc` on nested screens, so `q` behaves like a back-nav alias (lazygit/k9s convention). The existing `esc` handlers do the cleanup — no duplication. `q` quits directly only on root screens: (1) `screenSelectServer` always quits; (2) `screenSelectProject` quits when `len(m.servers) == 0 && m.config == nil` (truly standalone — no config file present and no servers; when `m.config != nil`, the user came from `screenSelectServer` via the Local entry and `q` navigates back); (3) `screenSelectContainers` quits when `!m.showPicker && !m.confirming` (standalone-containers root). `screenProgress` while `!done && !failed` is a no-op for `q` (must not cancel an in-flight operation; today both `q` and `ctrl+c` are no-ops mid-progress). The whole rewrite is skipped when `m.typingInInput()` — the container search bar, the log filter/search bars, and the settings-form text fields (`settingsField` 0–3) — so `q` reaches the open input as a literal character and server names like `qa-prod` stay typeable; with the settings-form color picker focused (`settingsField == 4`, no textinput active) the guard is false and `q` is rewritten to `esc`. That one guard replaced three per-screen carve-outs, so `screenLogs` and `screenSettingsForm` now fall into the `default: key = "esc"` case. `ctrl+c` is unchanged — it still goes through `tryQuit()` and triggers the disconnect prompt on remote sessions. Help footers on nested screens show `q back`; root screens show `q quit`. Because `q` is rewritten to `esc` before per-screen dispatch, the cleanup paths in the "Backward-navigation state cleanup" section below cover both keys — do not add parallel `q` handlers.

**Backward-navigation state cleanup**: When navigating backward (`esc`) or handling errors (e.g. `connectResultMsg` failure), all mutable callbacks (`composerFactory`, `projectLoader`, `disconnectFunc`) must be explicitly cleared or restored to their local defaults (`localFactory`, `localComposer`, `localProjectLoader`). Bubble Tea's value-type model means stale closures silently persist across screen transitions. Every new callback field added to Model needs corresponding cleanup in: (1) `esc` from the project screen, (2) `esc` from the container screen, (3) `entryLocal` handler, (4) `connectResultMsg` error path.

**Stale async message guard**: Goroutines spawned by a screen (e.g., `readLogChunk` for `screenLogs`) may deliver messages after the user has navigated away. Message handlers for screen-specific async messages (`logChunkMsg`, `logDoneMsg`) must check `m.screen` and discard stale messages — otherwise they will read nil fields cleared by `esc` cleanup and panic. A monotonic `logsSession` counter provides additional stale-message rejection. This pattern applies to any future screen that spawns background goroutines.

**Service list scrolling**: The container select screen uses `svcOffset` to track the first visible service when the list exceeds terminal height. `svcVisibleCount()` calculates available lines: `m.height - headerLines - footerLines` (min 1), returning `len(m.services)` when `m.height == 0` for backward compat. Line counts account for lipgloss margins: `titleStyle` has `MarginBottom(1)` (adds a space-padded line), `helpStyle` has `MarginTop(1)` (adds a space-padded line), so header=3 (or 4 with column captions) and footer=3+ (not 2). A conditional column captions row ("Created", "Uptime") is rendered above the service list when any service has non-empty `Created` or `Uptime` data; `hasStatusColumns()` checks this and `svcVisibleCount()` adds 1 to `headerLines` accordingly. The captions use `descStyle` and are left-padded to align with data columns (10 + maxName offset). `fixSvcOffset()` ensures cursor visibility after any state change that affects visible count — cursor movement, window resize, confirming/warning state change. Scroll indicators (`▲ N more` / `▼ N more`) replace existing blank-line content between breadcrumb/services and services/help, so they never change the total line count used by `svcVisibleCount()`. `svcOffset` is reset to 0 alongside `svcCursor` in `servicesMsg` and `esc` back-navigation.

**Container search (search & jump)**: The `/` key on the container screen opens an incremental **search-and-jump** — it is **not a filter**. The service list (`m.services`) is never narrowed and the position-keyed multi-select map (`m.selected`) is never touched; only `svcCursor` moves and matching rows are highlighted, so multi-select/deploy/restart/stop semantics stay intact (regression-pinned by `TestSelectedContainersUnaffectedBySearch`). It is fully synchronous — no goroutine, channel, or session counter (unlike stats/status/updates). Five Model fields (`internal/tui/app.go` ~289): `searching bool` (bar open, capturing text), `searchInput textinput.Model`, `searchQuery string`, `searchMatches []int` (indices into `m.services`), `searchReturn int` (`svcCursor` to restore on esc-while-typing). **Two-mode model**: *typing* (`searching == true`) — the bottom bar is an open `textinput`, every keystroke routes to it and then recomputes matches and live-jumps `svcCursor` to `searchMatches[0]`; *committed* (`searchQuery != "" && !searching`) — bar closed, matching rows stay highlighted, `n`/`N` cycle, `j`/`k` move but keep the highlight. Highlighting and `n`/`N` are driven purely by `searchQuery != ""`. `computeMatches(services []string, query string) []int` is a pure case-insensitive substring match on the service name, preserving list order, returning `nil` for an empty query (table-tested). **Ephemeral-on-departure cleanup invariant**: `m.clearSearch()` (resets all five fields, `SetValue("")`/`Blur()` on the input) is called on **every** transition that *leaves* `screenSelectContainers` or *reloads* `m.services` — the 9 sites are `servicesMsg`, `esc` container→project, `esc` project→server, `entryLocal`, `connectResultMsg` error path, `enterLogs()`, `enterConfig()`, `enterProgress()`, `enterExec()`. Because departure always clears, the ~6 **return** paths into the screen (`esc` from logs/config/progress, `execDoneMsg`, init, pre-select) need **no** `clearSearch()` — a committed search never survives a nested-screen peek or an operation, and `searchMatches` can never carry stale indices into a mutated `m.services`. A committed search does not survive; the user re-opens `/` if needed. **Cycle** (`cycleMatch(forward bool)`, no-op when `searchQuery == ""` or no matches): steps through `searchMatches` (kept ascending by `computeMatches`) with **wrap-around**; when the cursor sits *off* all matches after a manual `j`/`k`, `n` jumps to the first match strictly after the cursor and `N` to the first strictly before (wrapping at the ends). The bottom bar shows an `(i/N)` position counter (or `(no match)` while typing with no hits). **Two-stage `esc`** (committed mode): the first `esc` clears the search (guard at the top of `case "esc"`: `if m.searchQuery != "" { clearSearch(); fixSvcOffset(); return }`) and stays on the screen; a second `esc` (no active search) falls through to the normal back-nav. `esc` **while typing** is a separate branch inside the `if m.searching` intercept — it restores `svcCursor` to `searchReturn` and consumes the key without back-nav. **Guards & seams**: `case "/"` early-returns when `len(m.services) == 0` (mirrors the `l`/`x` empty-list guards). `searchInput` is `(re)constructed via textinput.New()` inside the `/` handler — **not** in `NewModel` — because ~18 tests build `Model{}` literals directly, which would otherwise leave a zero-value input that doesn't echo runes (it is only ever rendered while `searching`, so a zero value is never displayed). The bottom-bar line is **always reserved** (blank when idle) so the list height never jumps between search-idle/searching/committed; `svcVisibleCount()` counts this line in **both** the `confirming` early-return branch and the normal branch — search and `confirming` coexist (a committed search stays live when the user presses `d`), and the confirm prompt takes precedence over the bar on that shared reserved line. The `q`→`esc` rewrite block is skipped entirely while `m.searching` (via the shared `typingInInput()` guard, which the `?` intercept also reads), so `q` lands in the `searchInput` as a literal character (`TestQTypedIntoSearchInput`) instead of hitting the `screenSelectContainers` sub-case's `!showPicker && !confirming` quit. Rendering: `searchMatchStyle` (yellow, same as `updateGlyphStyle`) wraps matching names and `searchCurrentStyle` (yellow + `Bold`) wraps the current match (`i == svcCursor`); styling wraps only the raw name so display-width math (`utf8.RuneCountInString`) is unaffected, same rationale as the update glyph/ports column. `/ search` lives in the `?` overlay, not the help footer; while the search input is OPEN the WHOLE footer becomes `enter jump · esc cancel` (`line1` included — `space`, `q` and `?` all type literal runes in that state), and once the search is COMMITTED only `line2` is replaced, by `n/N cycle · esc clear`. **One-physical-line invariant**: because `svcVisibleCount()` reserves exactly ONE row for the bar, `searchBarLine()` MUST always render as exactly one physical line — a long typed query, a long service name, or the committed-mode hint would otherwise wrap at narrow widths and push the footer past its reserved space (list overflows / cursor scrolls off). Two mechanisms enforce this: (1) the typing-mode `textinput.Width` is set to `m.width - len("  / ") - len(counter)` so a long query scrolls *within* the input, and (2) the final bar string (all non-idle modes) is clamped to `m.width` via `clampToWidth()` → `ansi.Truncate` (ANSI-aware: preserves/reset escape sequences, counts by display cell). `clampToWidth` no-ops when `m.width <= 0` (unknown terminal size in tests), mirroring `svcVisibleCount`'s `m.height == 0` fallback. Pinned by `TestSearchBarLineNeverWraps` (asserts `ansi.StringWidth(searchBarLine()) <= m.width` at widths 40/20 with long content). Reopening `/` over a *committed* search calls `clearSearch()` FIRST (before rebuilding the fresh input + setting `searching`/`searchReturn`) so the reopened bar starts empty with no stale highlights/counter and an immediate `enter` can't re-commit the old query (`TestSearchOpenOverCommittedResetsState`). TUI-only — no CLI/runner/compose changes.

**Log follow-aware auto-scroll**: The tail is follow-aware — scrolling up auto-pauses it (read/scroll freely while the stream keeps flowing underneath), scrolling back to the bottom resumes it. **Headline invariant: ZERO new Model fields** — the viewport's `YOffset` *is* the pause state; "following" ≡ `m.logsViewport.AtBottom()`, recomputed wherever needed. The `logChunkMsg` handler captures `following := m.logsViewport.AtBottom()` BEFORE appending the chunk and only calls `GotoBottom()` when `following` (`SetContent` preserves `YOffset`, so a paused view holds while chunks keep landing). There is no new key: `G` (GotoBottom) doubles as "jump to live and resume follow". The three reformat sites — `w` wrap toggle, `p` pretty toggle, and the `WindowSizeMsg` `screenLogs` resize branch — each capture `following` before `fullReformat()` and re-`GotoBottom()` if following, so a live tail stays pinned across a reformat/resize (otherwise a changed line count would read as an accidental pause). The pure helper `logTailStatus(vp viewport.Model, done bool) (label string, below int)` drives a header indicator in `viewLogs()`: green `● following` when at bottom, yellow `⏸ paused ▲ N below` when scrolled up (`N = TotalLineCount − YOffset − Height`, clamped at 0 — the display-row distance to the live bottom, i.e. how far `G` will jump), and nothing (`""`) once the stream is done (`m.logsDone`) — there is nothing left to follow. Styles `logFollowStyle` (green `Color("2")`) / `logPauseStyle` (yellow `Color("3")`, same as `updateGlyphStyle`) live in `styles.go`. The `logDoneMsg` handler is unchanged — its force-`GotoBottom()` on error is deliberate (a terminal error should be pulled into view). TUI-only — no CLI/runner/compose changes.

**Inspect screen**: the `screenInspect` screen shows what the container under the cursor ACTUALLY holds, against `screenConfig`'s what-the-compose-file-DECLARES — the two disagree the moment a compose file is edited and the service is restarted (`r`) rather than deployed (`d`). The wedge is `.State.Health.Log[last].Output`, the failing probe's own output: `docker compose config` cannot show it at all, and the `✗` icon plus `VerdictUnhealthy` already make the user ask about it. `Inspector` (`Inspect(ctx, service) ([]byte, error)`) is declared in `tui` beside `ConfigProvider`/`ExecProvider` and type-asserted on the concrete composer, so a composer without it (a test mock) makes `i` a silent no-op. **All three composers implement it, so `i` is NOT gated on `m.readOnly()`** — the asymmetry against every other recent container key is deliberate: every operation is a compose pipeline and an unmanaged container has no compose file, but inspect is read-only by nature and works identically on both variants. It therefore appears in BOTH help tables through ONE shared append in `inspectGroup()`, whose position is load-bearing (see the truncation table in the `?` paragraph), and `TestHelpGroups_ReadOnlyNamesEveryBoundKey`'s bound set carries `i` too. **`docker inspect` is a top-level docker command, not a compose subcommand**, so all three implementations bypass `command()`/`remoteCommand()` — the rule `docker stats`, `docker image inspect` and `docker buildx imagetools inspect` already follow: `Compose.Inspect` uses `runDockerCmd`, `RemoteCompose.Inspect` uses `runRemoteDockerCmd` (so the `SSHExtraArgs`-before-host splice and `classifySSHError` come for free), and `HostContainers.Inspect` goes through the `dockerRunner` seam's `run`. Resolving the container ID is a SECOND call, so inspect costs two round-trips on a remote hop: the two compose composers list `ps -a --format json` through their own command builder and feed `parsePsEntries` (array AND NDJSON, the same tolerance `parseContainerStatus` applies to the same output) into `pickInspectContainer`; `HostContainers` reuses `unmanagedEntries` + `pickHostInspectContainer`. **`pickInspectContainer` mirrors the Uptime aggregation gate in `parseContainerStatus` exactly** — `entry.State == "running" && uptime != ""` wins, longest duration among running replicas, and a restarting replica only when nothing running has been seen. A naive max-duration picker disagrees with the Uptime column the container screen renders on a running+restarting mix, so `TestPickInspectContainer_MatchesUptimeColumn` drives the SAME entries through both and fails if the two diverge. A service whose replicas are all stopped falls back to the first matching entry (a stopped container stays inspectable); only a service with no entry at all returns `("", false)`, which every caller turns into `no container found for %q` — never a panic and never an arbitrary container. Host containers need no such rule (docker enforces unique names per host), so `pickHostInspectContainer` is a first match on the existing `hostContainerName` helper. **The parse layer lives in `internal/compose/inspect.go`**, beside every other docker-output parser in this repo: `ParseInspect` unwraps the single-element JSON array docker always emits, strips the leading slash off `Name`, and returns the narrow exported `InspectDoc` family — only the fields the five sections render, exported because the renderer lives in `tui` and constructs them directly in its table tests. `Inspect` still returns raw `[]byte`, so raw mode stays byte-identical to `docker inspect`. `State.Health` and `Config.Healthcheck` are POINTERS because docker omits both keys entirely for an image with no healthcheck, and the HEALTH section is dropped on exactly that distinction (`hasHealthcheck` also drops the explicitly-disabled `Test: ["NONE"]` form); the three `Healthcheck` intervals are `time.Duration`, since docker reports them as nanosecond counts that unmarshal directly. **The renderer is `buildInspectSummary(doc, width)` in `internal/tui/inspect.go`** — pure, no Model, no TTY, no Docker, golden-testable against the three real fixtures in `internal/compose/testdata/docker_inspect_{healthy,unhealthy,stopped}.json`. Five sections in order — STATE, HEALTH, IMAGE, MOUNTS, ENV — a section with nothing to say is omitted and STATE always renders. **Probe output soft-wraps and must NEVER truncate**: it is routinely long and multi-line (curl bodies, stack traces) and it is the feature's whole justification, so every line goes through `inspectBuilder`, which wraps with the existing `softWrapLine` and aligns continuation lines under the value column; below `inspectMinValueWidth` the value stacks under its label instead of shredding one rune per line. NETWORKS, PORTS, RESOURCES and LABELS are deliberately deferred — raw mode answers each, and PORTS duplicates a column the container screen already renders. **No secret masking, deliberate**: ENV is rendered verbatim in both modes, matching lazydocker/k9s/Docker Desktop; the accepted consequence (a screen-share leaks credentials the moment `i` is pressed) is STATED in the README rather than left to be discovered. If masking is ever added it must cover BOTH modes — masking only the summary makes `r` a one-key bypass, which protects nothing. **Mechanics follow `screenConfig`, not `screenLogs`**: `enterInspect()` bumps `inspectSession`, resets the seven `inspect*` fields, sizes the viewport at `m.height - 6` (the config sizing — NOT the logs `- 7`, which reserves a row for the log bar), calls `m.clearSearch()` (departure site #10) and returns `fetchInspect(session)`; the `inspectDataMsg` handler is gated on `m.screen != screenInspect || msg.session != m.inspectSession`; `esc` calls `clearInspect()` and returns WITHOUT a `refreshStatus()`, because the screen changes no container state; the `WindowSizeMsg` branch re-renders the summary at the new width without losing `inspectRaw`. Three helpers keep the two buffers honest: `setInspectContent()` is the single `SetContent` chokepoint, so the fetch handler, the `r` toggle and the resize branch cannot disagree about which buffer is on screen; `rebuildInspectSummary()` surfaces a parse failure in `inspectErr` and empties the summary but KEEPS `inspectRaw`, so `r` stays a working escape hatch (`viewInspect()` therefore keeps the viewport on screen BESIDE the error line and reads `Loading...` only when there are neither bytes nor an error); `clearInspect()` is the single departure-cleanup helper and deliberately does NOT bump `inspectSession` — `enterInspect()` bumps on the way in, which is what invalidates an in-flight fetch, and the handler's screen check discards one that lands after departure, the same discipline as `configSession`. The `r` toggle calls `GotoTop()` after the chokepoint: `SetContent` preserves `YOffset`, so a toggle from a scrolled summary into the much longer raw JSON would otherwise land the reader mid-document. The screen opens no text input, so `typingInInput()` needs no case and `q` reaches the existing `default: key = "esc"` rewrite. TUI-only: no CLI subcommand, no `Composer` change (the four mock sets are untouched) and no ID field on `runner.ServiceStatus` — the ID lookup stays inside `compose`, behind `Inspect`.

**Exec into container**: The `x` key on the container screen execs into a running container interactively. Uses an `ExecProvider` interface (defined in `internal/tui/app.go`) with method `ExecCommand(ctx, service, command) (*exec.Cmd, error)`. Both `Compose` and `RemoteCompose` implement it. The TUI type-asserts `composer.(ExecProvider)` when `x` is pressed — if the assertion fails (e.g., test mock), the key is ignored. If the service is not running, a warning is shown. Otherwise, confirmation is requested (`pendingExec = true`); on confirm, the TUI shells out via `tea.ExecProcess` which suspends Bubble Tea and gives full terminal to the exec process. On return, `execDoneMsg` resets `pendingExec` and calls `refreshStatus()`. Default shell command: `[]string{"/bin/sh", "-c", "command -v bash >/dev/null 2>&1 && exec bash || exec sh"}` (checks for bash first, falls back to sh for Alpine/minimal images; uses `command -v` instead of redirecting stderr on `exec` to avoid silencing bash's stderr for the entire session). Local: `docker compose exec <service> <command...>`. Remote: builds SSH command directly (like `EditCommand` pattern) with `-t` for TTY allocation — does NOT use `remoteCommand()`. CLI: `cdeploy exec <service> [-- command...]` with `--server`/`-s` support; follows `cmd/logs.go` pattern. `ExecCommand` returns `(*exec.Cmd, error)` (not executing it) so the caller controls execution. `DefaultExecCommand` is exported from `internal/compose/compose.go`.

**Log formatting**: The log viewer has two independent toggles: `w` for soft-wrap (default: on) and `p` for JSON pretty-print (default: off). These are implemented via `formatLogContent()` and `formatLogLines()` in `internal/tui/format.go` — pure functions that process raw log content through optional pretty-print and soft-wrap stages. `applyLogFormat()` incrementally formats only the not-yet-scanned tail of the raw-line buffer (via `foldNewRawLines`, using `logsScanned` as a resume cursor into `logsRawLines`), appending to the cached `logsFormatted` — see the **Log search & filter** paragraph for the raw-line derivation pipeline that replaced the old flat `logsContent`/`logsRawOff` string. `fullReformat()` resets and reprocesses everything — called when toggles flip or the window resizes. When wrap is off, horizontal scrolling is enabled (`SetHorizontalStep(4)`). Docker compose log lines with format `<service> | <json>` have their JSON body indented with continuation lines padded to align under the body start.

**Log search & filter**: Two coordinated navigation affordances on `screenLogs`, both synchronous/pure (no new goroutine or session counter — the existing `logsSession` + `m.screen == screenLogs` guards suffice). `f` opens a live **filter** (grep that hides non-matching lines while the stream keeps buffering underneath); `/` opens a **search** (highlight-and-jump *within* the possibly-filtered survivors, mirroring the container-screen search-and-jump). They coexist (lnav/less model): filter narrows, search highlights within. Both use `buildMatcher(query, isRegex, allowNegate) (pred, re, valid)` in `internal/tui/logfilter.go` — case-insensitive substring by default, `ctrl+r` toggles Go RE2 `regexp` (compiled **once**, reused per line); filter passes `allowNegate=true` so a leading `!` strips-and-inverts (RE2 has no negative lookahead — search has no `!`). `buildMatcher` returns `valid=false` (nil pred/re) on empty query, lone `!`, or bad regex; a **bad regex mid-type keeps the last-good predicate** (no thrash) and regex-ness is read from the committed `logFilterCommittedRegex`/`logSearchCommittedRegex` bool (NOT the live `IsRegex` flag) in `logFilterPred`/`logSearchPred`, so a `ctrl+r` into a *bad* regex holds the prior matcher instead of dropping the filter. **Raw-line derivation pipeline** (replaces the old flat `logsContent`/`logsRawOff` string): the source of truth is `logsRawLines []string` (complete logical lines, always unfiltered) + `logsPartial` (trailing incomplete line, no newline yet) + `logsScanned` (a RAW-line scan cursor — count of raw lines already folded into `logsFormatted`, **not** a survivor count). `logChunkMsg` splits incoming bytes on `\n` into raw lines + partial; the filter runs at the **raw-line level before pretty-expansion** (`deriveFiltered(raw, pred)`, nil pred = pass-through), so a matched `svc | {json}` line pretty-prints as a whole block. `foldNewRawLines(raw, scanned, …)` folds only `raw[scanned:]` through the pred + formatter and **always advances the cursor to `len(raw)`** — advancing by survivor count would re-scan already-filtered lines and duplicate output (the survivor-cursor trap). `fullReformat()` resets `logsScanned=0`/`logsFormatted=""` and re-scans; `rederiveLogs()` wraps it with the follow-aware `AtBottom()`→`GotoBottom()` capture (the filter-change analogue of the `w`/`p` toggle). Because the raw buffer is never touched by the filter, **clearing the filter reveals lines that streamed in while it was active**. A terminal error (`logDoneMsg`) is stored in a dedicated **filter-exempt** `logsErrLine` slot appended outside the predicate path (always renders regardless of an active filter), not mixed into `logsRawLines`. **`setLogViewportContent()` is the single SetContent chokepoint**: it assembles `derivedLogContent()` (cached unstyled `logsFormatted` + unfiltered `logsPartial` + filter-exempt `logsErrLine`), and when a search is committed, splits it on `\n`, recomputes `logSearchMatches []int` (physical-line indices via `logComputeMatches`) and overlays `highlightMatches` as a **SetContent-time pass** — `logsFormatted` itself stays UNSTYLED. Routing every write (`applyLogFormat`, `rederiveLogs`, `w`/`p`/resize `fullReformat`) through this chokepoint means all of them pick up the highlight + fresh match set for free. Search runs over the filtered survivors (a filter-hidden line is absent from the derived content, so it can never be a match); a filter that hides everything renders a `(no lines match filter)` placeholder. `highlightMatches` wraps the WHOLE physical line (only indices are known, not a substring offset) with `logSearchMatchStyle`/`logSearchCurrentStyle` (yellow / yellow-bold, in `styles.go`); a foreground-only style adds zero-width ANSI so `ansi.StringWidth` is unaffected. `n`/`N` (`cycleLogMatch`) cycle the ascending `logSearchMatches` with wrap-around; typing live-jumps to the first match; `scrollLogMatchIntoView` pins an off-screen match (auto-pausing follow via the `AtBottom` heuristic — `G` resumes). **Per-physical-line match semantics**: an occurrence fully within a wrapped row highlights, but an occurrence split *across* a soft-wrap boundary is not matched (accepted, pinned). **Layered `esc` ladder** (peel inner → outer): (1) typing-search cancel, (2) typing-filter cancel, (3) committed-search clear-only (stay), (4) committed-filter clear-only (stay), (5) leave screen (cancel ctx, `clearLogFilter()`/`clearLogSearch()`, back to `screenSelectContainers`). Rungs 1–2 live in the two **typing intercepts** at the very top of `case screenLogs` — while `m.logFiltering || m.logSearching`, every keystroke routes to the open input and returns (else `w`/`p`/`G`/`f`/`q` would fire actions mid-query); rungs 3–5 in the main-switch `esc` (reached only when no input is open — filter and search bars are mutually exclusive). The `q`→`esc` rewrite block is skipped while an input is open (via the shared `typingInInput()` guard, which reads `m.logFiltering || m.logSearching`), so `q` types literally; with no input open `screenLogs` falls into the block's `default: key = "esc"` case. **Reserved one-line bar**: `logBarLine()` renders exactly ONE physical line below the viewport (blank when idle), precedence typing-search (`/ <q> [mode] (i/N)` / `(no match)`) → typing-filter (`f <q> [mode] · N/M shown` / `(bad regex)`) → committed summary (`filter: <q> [rx] · N/M · search: <q> (i/N)`, `logFilterCounts` counts RAW lines to match where the filter runs) → idle blank; the final `clampToWidth(line, m.width)` (ANSI-aware `ansi.Truncate`, no-op at width ≤ 0) enforces the never-wrap invariant (pinned by `TestLogBarLineNeverWraps`). To reserve that line, viewport height drops `- 6` → `- 7` at **exactly the two log sites** (`enterLogs` and the `WindowSizeMsg` `screenLogs` branch) — the two config sites are untouched, so a blind `- 6` find/replace is wrong. The follow indicator stays on the title line. Inputs are built lazily via `textinput.New()` inside the `f`/`/` open handlers (not `NewModel`) so `Model{}` test literals stay valid; `f` early-returns on an empty raw buffer, `/` on empty derived content. TUI-only — no CLI/runner/compose changes.

**Docker Compose**: All docker interaction goes through `compose.Compose.command()` (local) or `compose.RemoteCompose.remoteCommand()` (SSH) which builds the correct command based on the `Standalone` field — `exec.CommandContext("docker", "compose", ...)` for plugin mode or `exec.CommandContext("docker-compose", ...)` for standalone mode. Both set `CURRENT_UID` env var (format `uid:gid` locally, `$(id -u):$(id -g)` on remote). Auto-detection via `Detect(ctx)` probes `docker compose version` first, then falls back to `docker-compose version`; the result is cached in the `Standalone` and `detected` fields. Detection is explicit — callers must call `Detect()` before first use; `command()`/`remoteCommand()` only read `Standalone`. `SetStandalone(bool)` allows inheriting the detection result into new instances. `SetTestHooks(run, output)` on both `Compose` and `RemoteCompose` injects test doubles. Exact subcommands: `stop`, `rm -f`, `pull`, `up --no-start`, `start`, `config --services`, `ps -a --format json`, `logs`, `exec`, `ls -a --format json`, plus top-level `stats --no-stream --format json` (NOT a compose subcommand — see below). Empty container slice means operate on all services. `parseContainerStatus()` handles both JSON array output (Docker Compose v2.21+) and NDJSON (older versions); it parses `CreatedAt` and `Status` fields from `psEntry` to populate `ServiceStatus.Created` and `ServiceStatus.Uptime`. `formatUptime()` in `internal/compose/uptime.go` converts Docker's Status string (e.g. `"Up 3 hours (healthy)"`) into compact form (`"3h"`): strips health suffixes, compacts time units (`hours` -> `h`, `days` -> `d`, etc.), handles special cases (`"About a minute"` -> `"~1m"`, `"Less than a second"` -> `"<1s"`), returns `"restarting"` for Restarting status, and empty string for non-Up statuses. `parseUptimeDuration()` converts compact uptime strings back to `time.Duration` for comparison (used to pick the longest-running replica among scaled services, which correctly handles restarts where CreatedAt is older but actual uptime is shorter). CLI subcommands reject `-a` combined with explicit container names.

**Remote SSH**: `RemoteCompose` wraps docker compose commands in SSH calls via a ControlMaster persistent socket (`/tmp/cdeploy-ctrl-{hash}-{pid}`). `ConnectCmd()` returns the SSH connect command for TUI's `tea.ExecProcess` (full terminal access for password prompts), `Connect()` runs it directly for CLI use, and `Close()` tears down the socket. All remote args are shell-escaped via `shellEscape()`. `CURRENT_UID` is evaluated on the remote host via `$(id -u):$(id -g)` to get the correct server-side UID/GID. The `Run()` function in `tui/app.go` calls `disconnectFunc` on exit to ensure socket cleanup. CLI uses `--server`/`-s` flag to select a server; TUI shows a server picker when servers are configured.

**Ad-hoc SSH (`-S`/`--ssh`)**: The `--ssh` persistent flag (registered in `cmd/root.go` alongside `--server`) is the ad-hoc complement to config-based `--server`. It accepts `[user@]host[:port]` and lets CLI users (especially CI) connect without a `~/.cdeploy/servers.yml` entry. Mutually exclusive with `--server`; requires `--project-dir`. Implemented via two helpers in `cmd/remote.go`: `checkRemoteMutex(serverName, sshTarget, identityFile)` enforces both the `--server`/`--ssh` mutex and the `--identity` requires `--ssh` rule at the top of each subcommand's `RunE`, and `resolveSSHRemote(ctx, sshTarget, projectDir, identityFile, newRemote)` parses the target via `config.ParseSSHTarget`, calls the injected factory (`opNewRemote`/`execNewRemote`/`logsNewRemote`/`newRemote` — preserving existing test seams), sets `RemoteCompose.SSHExtraArgs`, and runs `Connect()` + `Detect()`. On `Detect` failure the helper internally calls `Close()` before returning the error; on `Connect` failure cleanup is a no-op. The returned cleanup is always non-nil, so callers can `defer cleanup()` immediately after the call without nil-checking. Wired into `deploy`/`restart`/`stop`/`exec`/`logs`/`list` subcommands as a branch above the existing `--server` block — config-based path is unchanged. Parser lives in `internal/config/sshtarget.go`: rejects whitespace and IPv6 (`[`-prefixed); validates port `1..65535`; returns `SSHTarget{User, Host, Port}` with helpers `SSHHost()` (`user@host` or `host`) and `PortArgs()` (`["-p","NNNN"]` or nil). The `SSHExtraArgs []string` field on `RemoteCompose` is spliced **immediately before the host argument** in every SSH argv build site (Connect, Close, Detect plugin/standalone probes, `remoteCommand`, `findRemoteComposeFile`, `ConfigFile`, `EditCommand`, `ExecCommand`); nil = zero-behavior-change default. No TUI changes — `--ssh` is strictly a CLI feature.

**Ad-hoc SSH identity (`-i`/`--identity`)**: The `--identity` persistent flag (registered in `cmd/root.go` immediately after `--ssh`) accepts a path to an SSH private key, intended for CI/automation workflows that write a key from a secret and don't have a `~/.ssh/config` entry. Strict-narrow: only valid alongside `--ssh` (mutually exclusive with `--server` via the `--identity requires --ssh` rule); CLI-only (TUI mode rejects it). Path validation lives in `internal/config/identity.go` (`ParseIdentity`): trims input, rejects empty, expands `~/` paths via `os.UserHomeDir()`, rejects bare `~` and `~user` forms (only `~/...` is supported), requires `os.Stat` to succeed and report a regular file, requires `os.Open` to succeed (readability check beyond mode bits), and returns `filepath.Clean` of the resolved path. Relative paths pass through unchanged — `ssh(1)` resolves them against cwd. `resolveSSHRemote` appends `["-i", cleanPath]` to `SSHExtraArgs` after the port args, so every existing SSH argv splice site absorbs `-i` for free without any changes to `internal/compose/remote.go`.

**Config**: `internal/config` loads `~/.cdeploy/servers.yml` defining remote servers and groups. The `Config` struct has `Groups []Group` and `Servers []Server`. `Group` has `Name` and `Color` fields. `Server` has `name`, `host`, optional `project_dir`, optional `group`, and optional `color` fields. Color resolution: grouped servers inherit color from their `Group` via `Config.GroupColor()`; ungrouped servers use their own `color` field. `color` accepts ANSI color names listed in `config.ValidColors` (exported slice, single source of truth for both validation and the TUI cycle picker): red, green, yellow, blue, magenta, cyan, white, gray; invalid values are rejected by `Validate()`. `Validate()` also checks group name uniqueness, group color validity, and that servers reference existing groups. `Save(path string) error` writes config atomically (temp file + rename) with `MkdirAll` for parent dirs. When color is omitted (resolved or direct), the TUI keeps the old plain-text breadcrumb instead of rendering a badge. Servers with the same `group` are displayed together under a shared header in the TUI. `Load()` returns an empty config (not error) if the file doesn't exist; it also runs `migrate()` to auto-convert old-format configs (per-server colors on grouped servers) to the new format (colors on Group entries, first-server-wins for conflicts). SSH-specific options (keys, jump hosts, tunnels) belong in `~/.ssh/config` — except `-i` for ad-hoc CI/automation use via `--ssh`.

**Settings editor**: Two screens (`screenSettingsList` + `screenSettingsForm`) accessible via `s` key on the server select screen (only when `m.config != nil`). The settings list shows all servers in a table with Name/Host/Group/Color columns; color is resolved from the group for grouped servers (with a "(group)" indicator) or from the server directly. `a` adds, `enter`/`e` edits, `d` deletes (inline y/n confirmation). The form uses 4 `textinput.Model` instances (name, host, project_dir, group) and a cycle picker for color (left/right arrows cycle through `""` + `config.ValidColors`). `settingsField int` tracks focus (0-3 = text inputs, 4 = color picker). When a server has a group, the color picker shows a "(group)" label; cycling the color edits the group's color (affecting all servers in that group). Editing a grouped server loads `settingsColor` from the group; on save, `settingsColor` is applied to the group's color (not the server's). New group names auto-create `Group` entries; orphaned groups (no servers referencing them) are auto-cleaned on both save and delete. `resolveServerColor()` on Model returns group color when available, falling back to server color (nil-guarded for tests without config). Validation reuses `config.Validate()` on a temporary config (including `Groups`) before applying changes. On save: mutate `m.config.Groups` and `m.config.Servers`, call `m.config.Save(m.configPath)`, sync `m.servers = m.config.Servers`, rebuild `m.serverEntries` via `buildServerEntries()`. Config path and config are threaded into the TUI via `WithConfigPath(path)` and `WithConfig(cfg)` functional options — existing `NewModel()` call sites are not affected. State cleanup: `esc` from settings list returns to server select; `esc` from form returns to settings list with no data changes; `settingsErr` is cleared on transitions.

**Operations**: Four operations — `Restart` (stop → rm → create → start), `Deploy` (stop → rm → pull → create → start), `StopOnly` (stop), `Rollback` (stop → rm → create → start — Restart shape, **NO Pull**: registry outages are a classic rollback trigger, so offline rollback from local blobs must work). All share the same `runner.Run()` pipeline; the step list varies by operation type. `Steps()`/`buildSteps()` fold Rollback into the Restart branch (`default:` case, gated only by `op == Deploy` for the Pull step).

**Wait engine (`--wait` health gate)**: `internal/runner/wait.go` holds ONE tested implementation of the health-wait rules, driven two ways. `EvaluateWait(prev WaitState, status map[string]ServiceStatus, opts WaitOptions, elapsed time.Duration) (WaitState, bool)` is a **pure reducer** — no clock reads, no IO; `elapsed` is an input, so it is table-testable without a fake clock and both drivers share identical semantics. `WaitState` is the accumulator (per-service `Verdicts`, plus unexported `everRunning`/`firstRunningAt`/`restartingCount`/`neverRunningCount` bookkeeping); it is copy-safe (the TUI holds it on its Model). Seed via `NewWaitState(services)` before the first call — a zero-value state has no target services and resolves as immediately-done. **Per-service precedence IS the spec, in this exact order** (documented above `EvaluateWait`): (1) `Uptime == "restarting"` bumps a counter, `restartingThreshold`=3 consecutive ⇒ `restarting` — checked FIRST because a restarting container reports `Running==false` AND `Uptime=="restarting"` simultaneously, so the exited rules would otherwise fire and the restart counter would never reach the threshold; (2) `Health=="unhealthy"` ⇒ `unhealthy`; (3) `Running==false` after `everRunning` ⇒ `exited`; (4) `Running==false`, never observed running, `neverRunningThreshold`=5 consecutive ⇒ `exited (never started)` (the ≥2-poll debounce absorbs the first-poll mid-transition race); (5) `Health!=""` ⇒ passes on `healthy`; (6) `Health==""` && `Running` ⇒ grace timer, passes after running continuously ≥ `Grace`. **Firm timeout boundary**: the PASS assignments in rules 5/6 are gated on `elapsed <= Timeout`, so a service that first becomes healthy STRICTLY AFTER the deadline is NOT allowed to flip a would-be-timeout into a success — it stays pending and is swept to `timed out (still starting)`. A pass observed at or before the deadline is terminal and kept; the fail-fast rules (1–4) are NOT gated (a genuine crash/restart at the deadline keeps its true verdict). Any service still pending once `elapsed >= Timeout` is swept to `timed out (still starting)`. The seven `WaitVerdict` strings (`VerdictHealthy`/`VerdictRunningNoHC`/`VerdictUnhealthy`/`VerdictExited`/`VerdictExitedNeverStart`/`VerdictRestarting`/`VerdictTimedOut`, plus `VerdictPending` = zero value) are load-bearing — both the CLI verdict table and the TUI progress screen render them literally; `WaitVerdict.OK()` (healthy or running-no-HC) defines a passing outcome. **Driver 1 (CLI)**: `WaitHealthy(ctx, c Composer, services, opts)` resolves an empty target set via `ListServices()` (the pipeline's "empty means all" convention), fires the first poll immediately then every `opts.Poll` — **capped at `min(Poll, Timeout-elapsed)`** so a poll lands at ~the deadline rather than up to a full `Poll` past it (the reducer's firm-boundary fix depends on the deadline poll landing at ~`Timeout`, not late) — feeds `ContainerStatus()` snapshots to `EvaluateWait`, and returns `(WaitReport, error)`. **The wait-scoped context is created FIRST — before ANY blocking call — and covers BOTH the empty-target-set `ListServices()` resolution AND the polls** (`context.WithDeadline(ctx, start+Timeout)`, a CHILD of the parent ctx), so a HUNG `ListServices` OR `ContainerStatus` (stuck daemon / dead SSH hop) is interrupted AT the deadline rather than blocking past `--wait-timeout`; the error-retry sleep is capped to the remaining budget the same way. **No status/list call in the wait phase can outlive `--wait-timeout`** — this is the invariant (regression pins: `TestWaitHealthy_HungPollInterruptedAtDeadline`, `TestWaitHealthy_HungListServicesInterruptedAtDeadline`). A `ListServices` resolution cut off by the deadline (derived-ctx `DeadlineExceeded`, parent NOT cancelled) returns a `resolve services: wait timeout … exceeded` operational error → exit 2; a parent-cancel during resolution returns `ctx.Err()` raw → exit 1 (classified by checking `ctx.Err()` first, then `waitCtx.Err()`, exactly as the poll loop does). In the poll loop a pure deadline expiry (derived-ctx `DeadlineExceeded`, parent NOT cancelled) sweeps still-pending verdicts to `timed out` via `reportTimedOut` (NOT a nil-status `EvaluateWait`, which would misread a running service as exited) and returns `(report, nil)` → the CLI wraps it → exit 2; a genuine PARENT cancellation (user Ctrl-C) returns `ctx.Err()` raw → exit 1 — the two are distinguished by an `ctx.Err()` check after the `select` (the `waitForHealth` `errors.Is(err, context.Canceled)` guard depends on this). The error is reserved for OPERATIONAL failures only (parent-ctx cancellation → partial report + `ctx.Err()`; `pollErrorThreshold`=3 consecutive `ContainerStatus` errors WHILE INSIDE the deadline → partial report + wrapped error; a non-deadline `ListServices` failure) — a completed wait with a failing verdict OR a pure deadline expiry returns `(report, nil)` with `report.OK==false`. A single transient poll error is skipped, state carried forward. **Driver 2 (TUI)**: `internal/tui/app.go` drives the same reducer from a `waitTickMsg` loop (the `refreshTickMsg` idiom), so the rules can never diverge between surfaces. Each TUI poll (`pollWaitStatus`) is likewise bounded — `context.WithDeadline(m.ctx, m.waitDeadline)`, the same wall clock the countdown uses — so a HUNG `ContainerStatus` still returns a `waitStatusMsg` (with a deadline error) instead of never delivering; without the bound the reducer's timeout sweep would never run and the progress screen would wait indefinitely (regression pin: `TestPollWaitStatus_BoundedByDeadline`). `WaitOptions{Timeout,Grace,Poll}` normalize non-positive fields to `DefaultWaitTimeout`=2m / `DefaultWaitGrace`=10s / `DefaultWaitPoll`=2s; only `--wait-timeout` is user-exposed (Grace/Poll are internal constants in v1). **Widening note: no `Composer` change** — the wait engine consumes the existing `ContainerStatus()`/`ListServices()` primitives, so the 4 mock sets are untouched.

**`WaitError` exit-2 contract**: `cmd.WaitError{Report runner.WaitReport, Err error}` (exported, in `cmd/deploy.go`) signals that a post-operation `--wait` gate failed. `waitForHealth` wraps a non-OK OR errored report in it; `main.go` maps it via `errors.As(err, &waitErr)` → `os.Exit(2)`, letting CI distinguish "deployed but unhealthy" (2) from "pipeline step failed" (1). `Unwrap()` exposes the operational cause (ctx cancel / poll failures / resolution). `Error()` lists the failing services (or the wrapped cause). A **deploy** wait failure also prints the hint `run 'cdeploy rollback' to restore the previous images` (restart/rollback have no earlier snapshot to fall back to). `--wait`+`--wait-timeout` register on deploy, restart, and rollback via `addWaitFlags(cmd)`; `stop` never gets them, and `runOperationWithPrep` guards `op != runner.StopOnly` defensively so a leaked global can't make a stop wait. `formatWaitReport(report)` is a pure verdict-table renderer (sorted, aligned, colored via the shared styles) — golden-testable.

**Deploy snapshots & the state file**: every `Deploy` records the image digest each *running container* actually uses, to a per-project state file **on the docker host**, BEFORE the pipeline stops anything, so `cdeploy rollback` can restore them. Schema and pure helpers live in `internal/compose/snapshot.go`; the capture + state-IO methods hang off `Compose`/`RemoteCompose`. **Ownership rules**: (1) **Deploy-only** — never Restart (a restart after a bad deploy must not overwrite the good snapshot) and never Rollback (rollback is idempotent — running it twice lands on the same state). (2) **Captured pre-Stop**, from the digest the running container is actually using — container ID → `docker inspect --format '{{.Image}}'` (batched) → `docker image inspect` → `RepoDigests` filtered against the compose-config image ref via `parseLocalDigest` — NOT the local tag's current digest (a pulled-but-not-deployed newer image must not poison the snapshot). (3) **Merge-not-replace** (`mergeSnapshot`, fresh entries win, older entries and their per-service `recorded_at` survive) so a partial `deploy web` never destroys the rest of the project's safety net. (4) State lives at `~/.cdeploy/state/<sha256(projectDir)[:12]>.json` on the host — local file for local, over SSH for remote — so a CI deploy and a laptop rollback share one authoritative history. The key hashes a NORMALIZED project dir (`localProjectDir` = `filepath.Abs`+`Clean`; `remoteProjectDir` = `path.Clean`), so `-C ./app` and its absolute spelling collapse to one key. (5) **Warn-and-proceed**: a not-running service, a locally-built image with no registry digest, a capture error, and a write failure are ALL surfaced as warnings and never block the deploy (`cmd/deploy.go:recordSnapshot`, gated on `op == runner.Deploy` and a `snapshotter` type-assert). Schema is version 1; `parseSnapshot` returns the typed `errSnapshotSchema` for any other version so an older binary refuses rather than misreads. `SnapshotServices` returns `SnapshotResult{Snapshot, Warnings}`; `ReadSnapshot` returns `(nil, nil)` for a missing file (normal first deploy, distinguishable from a parse/schema error); `WriteSnapshot` ties read+merge+atomic-write (temp+rename, `config.Save` pattern). **Overwrite protection** (`existingForMerge`): only a MISSING file or a malformed-JSON file (`errSnapshotCorrupt`, wrapped by `parseSnapshot`) is treated as "no existing" and safely overwritten; a future-schema file (`errSnapshotSchema`) or a transient read/SSH failure ABORTS the write instead of clobbering it — otherwise an older binary would silently downgrade a newer-schema file, and one flaky read would wipe the merge history of every service not in the current deploy. The abort surfaces as a `WriteSnapshot` error, which the best-effort `recordSnapshot`/`recordDeploySnapshot` callers warn about and proceed past. **Concurrent-deploy locking**: the local `WriteSnapshot` wraps its read-modify-rename in an advisory `syscall.Flock` on a sidecar `<state>.lock` (`lockStateFile`, unix-only per the SSH/ControlMaster design; separate `os.OpenFile`s give independent open-file-descriptions so it contends even between goroutines of one process), so two concurrent local deploys of the same project can't both read the old file and clobber each other's merged entry. Best-effort: a lock failure proceeds unlocked (the prior single-deploy behavior). The REMOTE `WriteSnapshot` is deliberately NOT locked — a cross-SSH distributed lock is out of v1 scope (the read `cat` and the write are two SSH round-trips with a host-local merge between them), so concurrent same-project deploys to the same remote host from different machines can race; this is a documented v1 caveat (README) rather than a bug.

**Rollback pipeline & `PrepareRollback` prep**: `cmd/rollback.go` (`newRollbackCmd`) reuses `runOperationWithPrep` with an op-specific pre-run hook (`rollbackPrep`) rather than forking `runOperation`. The hook: `ReadSnapshot` → `resolveRollbackTargets` refusal rules (nil snap = no state file; `-a` with an empty snapshot; a named service absent from the snapshot — the error names exactly which) → `filterLiveTargets` intersects the resolved targets with the CURRENT compose services (`c.ListServices()` = `config --services`) so rollback pins images only against the *current* compose file: a snapshot entry for a since-removed service is warned-and-skipped under `-a`, or a hard error naming it when explicitly named (a `ListServices` failure aborts prep — fail closed; an all-stale `-a` set errors "no snapshot services remain") — this prevents the generated override from resurrecting a removed service as a minimal image-only service → print the plan lines (`web  nginx@sha256:ab12… (recorded 2026-07-28 14:03)`) → `PrepareRollback`, whose returned cleanup `runOperationWithPrep` defers (function-scoped, so it runs after the wait phase but BEFORE the remote SSH teardown in LIFO order — a remote `rm -f` of the override still rides the live ControlMaster socket). `PrepareRollback(ctx, entries, services, w)` (on both composers): discovers the main compose file (fails fast if none), writes an advisory `already at snapshot` line for services whose running container already matches the snapshot digest (best-effort, proceeds — a recreate is still meaningful), ensures each target digest's blob is present locally (`docker image inspect <repo>@<digest>` presence check, else `docker pull <repo>@<digest>` streamed to `w` for live progress via the new `runDockerCmdStream`/`runRemoteDockerCmdStream` primitives — the existing `runDockerCmd` runners CAPTURE, these STREAM), then generates a minimal override YAML (`buildOverrideYAML`, `image: <repo>@<digest>` **plus `pull_policy: never`** per service, services emitted in SORTED order — never marshal a map) and sets `ExtraComposeFiles = [main, override]` (main FIRST — see the contract below). The `pull_policy: never` line is load-bearing for offline rollback (AC4): the rollback pipeline has NO Pull step, but its Create step is the shared `docker compose up --no-start`, whose pull is policy-driven — a MAIN-compose `pull_policy: always` would otherwise force a registry pull at Create and FAIL during a registry outage (the classic rollback trigger). As the SECOND `-f` file, the override's `never` wins the compose merge, so Create never pulls; safe because the presence-check/pull above already guarantees the pinned digest blob is on the host at Create time. A pull that fails (blob pruned AND registry down) aborts BEFORE any override file is written or `ExtraComposeFiles` is touched, so a failed prep never leaves the pipeline half-configured. Cleanup removes the temp override and resets `ExtraComposeFiles = nil`. Local delivery writes the override to `os.TempDir()` via `os.CreateTemp` (unique per process — no collision risk); remote pipes it over the ControlMaster socket to `/tmp/cdeploy-rollback-<pid>-<rand>.yml` via `writeRemoteFile` (`mkdir -p && cat > tmp && mv`) and cleans it up with `rm -f` over SSH. The remote path's random hex suffix (`remoteRollbackOverridePath`, `crypto/rand`) is generated ONCE per `PrepareRollback` and reused for both the write and the cleanup `rm -f`; it makes the path unique across CLIENTS (the local PID alone collides when two machines roll back the same project on the same docker host — one would overwrite the other's override, or a cleanup `rm -f` would delete a file the other's pipeline/wait still references in `ExtraComposeFiles`). `rollbackImageRef(entry)` (`stripTag(image)+"@"+digest`, exported as `compose.StripTag` and reused by `cmd/rollback.go`'s plan line so the advertised repo can't diverge from the pinned one) is the single source of truth for the presence check, the pull, and the override, so all three agree on the exact ref. `rollbackPrep` also returns the resolved (snapshot ∩ live-compose) service set, which `runOperationWithPrep` threads into BOTH the pipeline (`runner.Run`) AND the wait phase — for `-a` this is the intersected snapshot services, NOT the raw nil `containers` arg. Threading it into the pipeline is load-bearing: with nil, `runner.Run` would Stop/Remove/Create/Start EVERY compose service — including ones absent from the override — recreating them with their current UNPINNED image; and `WaitHealthy` would resolve every compose service via `ListServices()`, dragging build-only / run-to-completion services that were never rolled back into the `--wait` health gate. deploy/restart/stop pass a nil prep and keep operating on `containers` unchanged.

**`ExtraComposeFiles` contract**: `ExtraComposeFiles []string` on both `Compose` and `RemoteCompose`. When non-nil, `command()`/`remoteCommand()` splice `-f <f0> -f <f1> …` immediately after `docker compose` / `docker-compose` (both plugin and standalone argv shapes), before the subcommand, shell-escaped on remote. `-f` disables compose's file auto-discovery, so the discovered main file MUST be first (rollback sets `[main, override]`). The local `PrepareRollback` absolutizes the discovered main file (`filepath.Abs`) before storing it, because `command()` sets `cmd.Dir = ProjectDir` and docker resolves `-f` relative to that cwd — a relative `-C ./app` would otherwise re-prefix `-f app/compose.yml` into `./app/app/compose.yml` and fail (the remote path uses a bare name + `cd`, so only the local side needs this). **Regression-pinned nil default**: a nil field produces byte-identical argv to the pre-feature behavior — `TestCommand_NilExtraComposeFiles_ByteIdentical` / `TestRemoteCommand_NilExtraComposeFiles_ByteIdentical` guard this; `cmd.Dir`/project-dir handling is unchanged so project-name derivation stays stable. Only rollback prep sets the field today; everything else leaves it nil.

**TUI wait phase & `R` rollback (sessions + cleanup)**: no new screens. The **progress screen** gains a `waiting` sub-state: after a Deploy/Restart/Rollback pipeline reaches `m.done`, it enters `waiting`, seeds `waitState = NewWaitState(targets)`, sets `waitDeadline`, and starts a singleton `waitTickMsg{session}` loop (one `ContainerStatus` tea.Cmd per tick → `EvaluateWait` → re-render → reschedule) gated on `m.screen == screenProgress && m.waiting && msg.session == m.waitSession`; StopOnly never waits. Each poll is deadline-bounded (`context.WithDeadline(m.ctx, m.waitDeadline)`) so a hung `ContainerStatus` returns a deadline error rather than stalling the loop; the `waitStatusMsg` error path then sweeps pending→timed-out once `elapsed >= Timeout` (`sweepWaitTimeout`), guaranteeing the wait resolves even if Docker/SSH never recovers. It renders a live per-service verdict line (reusing the `♥/●/✗/~` icons + `waitVerdictStyle`) with a countdown; footer shows `esc skip`. `esc` while waiting calls `clearWaitState()` (bumps `waitSession` to invalidate in-flight ticks/polls, clears wait fields) and leaves the op "done". A resolved wait KEEPS `waitState` so the final verdicts stay visible; a failed **deploy** wait shows the hint `press R on the services screen to roll back`. The **`R` key** on the services screen type-asserts `m.composer.(RollbackPreparer)` (no-op if unsupported, like the `c`/`x` guards), guards empty list / empty selection (warn), then **captures the selected target set into `rollbackTargets`** at press time and bumps `rollbackFetchSession` and fires an async fetch that reads the snapshot AND the CURRENT compose service set in one goroutine. The capture is load-bearing (C11 fix): the fetch is async, so the live multi-select can change or CLEAR before `rollbackSnapshotMsg` lands; the captured `rollbackTargets` — NEVER the live `selectedContainers()` — drives the snapshot-presence + live-compose validation, the confirm prompt (`rollbackAgeSuffix`), `PrepareRollback`, and the pipeline target (`opContainers`), so a since-cleared selection can never become an unintended all-service rollback (empty `containers` == all services throughout the runner/composer). A somehow-empty captured set when the msg lands REFUSES (warns `warnNoSelection`) rather than falling through. `rollbackFetchSession` protects the captured set from a stale fetch; a fresh `R` press re-captures (`ReadSnapshot` + `ListServices`, `rollbackSnapshotMsg{snap, live, session}`, gated on screen + session; a `ListServices` failure fails closed via the shared `err`). The handler refuses with an inline warning (mirroring the CLI `filterLiveTargets`) when a selected service is absent from the snapshot OR has since been removed from the live compose file (`msg.live`) — a stale target must NOT resurrect a removed service as a minimal image-only override; an absent snapshot warns inline; a present-and-still-live snapshot enters the existing `confirming` flow with `pendingOp = runner.Rollback` (the confirm prompt shows the snapshot age via `rollbackAgeSuffix`). On confirm, prep runs inside the op tea.Cmd before `runner.Run` (prep failure → op failed); the cleanup is stored as `m.rollbackCleanup` and invoked (via `runRollbackCleanup`, which nils the field so it can't double-fire) when **LEAVING** `screenProgress` — NEVER goroutine-deferred, because `runner.Run`'s `defer close(events)` triggers the wait-tick loop whose `ContainerStatus` reads `ExtraComposeFiles` concurrently with a reset (`go test -race` would flag a goroutine-deferred cleanup). A **hard quit** during a rollback wait also runs `runRollbackCleanup` on the main goroutine so the override temp file isn't leaked (esp. the remote `/tmp` file, which has no reaper): local ctrl+c via `tryQuit()` before `tea.Quit`, remote ctrl+c via the `quitting` confirm's `y` branch (while the ControlMaster socket is still live — `Run`'s `disconnectFunc` only closes it after the tea loop exits). **New sessions**: `waitSession` (gates `waitTickMsg`) and `rollbackFetchSession` (gates `rollbackSnapshotMsg`); both are bumped at the same context-change sites as the other counters and cleared, along with `waiting`/`waitState`/`waitDeadline`/`rollbackSnapshot`/`rollbackTargets`/`rollbackCleanup`, at the documented departure sites (esc back-nav chain, `entryLocal`, `connectResultMsg` error path). `rollbackTargets` is cleared together with `rollbackSnapshot` at every one of those sites. The post-op update-cache invalidation on esc-from-progress now includes `runner.Rollback` alongside Deploy/Restart. `Snapshotter` (SnapshotServices + WriteSnapshot) and `RollbackPreparer` (ReadSnapshot + PrepareRollback) are optional interfaces defined in `tui` and type-asserted on the concrete composer, mirroring `ConfigProvider`/`ExecProvider` and the cmd package's `snapshotter`/`rollbackPreparer` seams; the TUI runs the deploy snapshot FIRST inside the Deploy op goroutine (warn-and-proceed).

**Health checks**: `ServiceStatus` has `Running bool`, `Health string` (values: `"healthy"`, `"unhealthy"`, `"starting"`, or `""` for no healthcheck), `Created string` (formatted creation time, e.g. `"2024-01-15 09:30"`), and `Uptime string` (compact uptime, e.g. `"3h"`, `"2d"`, or `""` if not running). For scaled services, `Running` uses OR (any running = running), `Health` uses worst-case priority (`unhealthy` > `starting` > `healthy`), `Created` uses the oldest replica, and `Uptime` uses the longest-running replica. The TUI shows health icons (♥/✗/~) next to status dots and Created/Uptime columns. The CLI `list` command shows the same icons and columns.

**Multi-project discovery**: The `list` subcommand auto-discovers all compose projects when no `-C` is specified (both local and remote). Services are grouped by project with headers. Per-project errors are non-fatal — a warning is printed to stderr and the project is skipped. When `-C` is specified, only that project's services are shown in a flat list. With `--stats`, CPU/Mem columns are populated by joining `docker stats --no-stream --format json` against each project's `ps` container IDs. The host-wide `docker stats` call is shared across every project: `runList` calls `compose.AllContainerStats`/`AllContainerStatsRemote` once before the project loop and passes the result map into `collectMultiProjectStats`. Each project's composer satisfies the `bulkStatsAggregator` interface (`ContainerStatsFromBulk`) and only runs `docker compose ps` per project, joining against the shared bulk map — one ~1.5s cost regardless of project count. Composers that don't implement the bulk interface (test mocks) fall back to per-project `ContainerStats()`; the fallback also runs if the host-wide fetch failed (`bulkStats == nil`), so stats degrade gracefully rather than disappearing.

**Resource stats**: `runner.ServiceStats` (`CPUPercent float64`, `MemoryUsed int64`, `MemoryLimit int64`) is populated from `docker stats --no-stream --format json` — host-wide NDJSON, one line per container, parsed by `parseStatsOutput()` in `internal/compose/stats.go` (tolerant of both NDJSON and JSON-array forms, mirroring `parseContainerStatus`). `ContainerStats()` is the **first method on `Compose`/`RemoteCompose` to bypass `command()`/`remoteCommand()`** because `docker stats` is a top-level Docker CLI command rather than a compose subcommand — calling `c.command(...)` would prepend `compose` and produce a malformed argv. `AllContainerStats()` builds `exec.CommandContext("docker", "stats", ...)` directly; `AllContainerStatsRemote()` builds the SSH argv directly, splicing `SSHExtraArgs` immediately before the host arg (same convention as `EditCommand`/`ExecCommand`, which also bypass `remoteCommand()`). Per-project `ContainerStats()` calls `docker compose ps --format json` for this project's container IDs, calls the bulk helper, joins by short container ID (first 12 chars), and sum-aggregates `CPUPercent`/`MemoryUsed`/`MemoryLimit` across replicas — a 3-replica service maxing each core shows ~300% CPU. Only running containers appear in the result map; stopped services are absent. Helpers `parseSize` (handles `B`/`KiB`/`MiB`/`GiB`/`TiB` binary and `kB`/`MB`/`GB`/`TB` decimal suffixes, case-insensitive), `parseCPUPercent` (strips `%`), and `FormatBytes` (exported; produces compact `124M`/`1.5G`) live in `internal/compose/stats.go` as the single source of truth — both `cmd/list.go` and `internal/tui/app.go` import `FormatBytes` from there. TUI fetches stats in parallel with status via `tea.Batch(refreshStatus(), refreshStats())` on every entry to `screenSelectContainers` and after every operation completes (return from progress / logs / exec). A periodic `refreshTickMsg` (every `statsRefreshInterval` = 5s, defined in `internal/tui/app.go`) keeps the data fresh while the user lingers on the screen: `Init()` kicks off a singleton `tea.Tick`, and the handler always reschedules itself so exactly one tick is in flight at any time regardless of how many transitions in/out of the screen happen. The handler gates fetches on `m.screen == screenSelectContainers && !m.confirming && m.composer != nil && !m.refreshInFlight` — anywhere else, the tick is a pure reschedule with no docker calls (off-screen / mid-confirmation / mid-disconnect / previous fetch still pending).

**Update detection — tri-state and Composer contract**: `runner.ServiceStatus.UpdateAvailable *bool` is a tri-state: `nil` = unknown / not checked / build-only / error (blank cell), `*v == true` = a newer image exists in the registry (yellow `⇧` glyph, U+21E7), `*v == false` = current. `Composer.CheckUpdates(ctx, services) (map[string]bool, error)` returns only services that were *checked* — absent keys preserve the tri-state's nil for build-only services and per-image errors. When a non-nil error is returned, the accompanying map is *untrusted* — implementations may return a partial map (RemoteCompose does, with whichever services completed before the transport-fail abort), but partial verdicts may be inconsistent with unresolved services. Soft-failure consumers (CLI list, TUI) discard the map (`updates = nil`) and render all-blank-plus-warning rather than mixing partial verdicts with unresolved services. Local impl in `internal/compose/updates.go`; remote in `internal/compose/remote.go`; unmanaged-host impl in `internal/compose/hostcontainers.go` (which returns a partial map on a transport abort too, since its remote runner emits the same `errSSHTransport` sentinel). `compareImageDigest` returns `(updated, ok, err)` on both sides (3-tuple, kept symmetric) so empty-digest cases are distinguishable from positive verdicts without polluting the cascade counters with synthetic errors.

**Update detection — digest comparison**: implementation always uses per-image digest comparison: `docker compose config --format json` for service→image mapping on the two compose paths (compose subcommand → goes through `command()`/`remoteCommand()`; `HostContainers` instead reads the `Image` field `docker ps` already returned, since there is no compose file), then `docker image inspect --format '{{range .RepoDigests}}{{println .}}{{end}}'` for the local digest and `docker buildx imagetools inspect` (preferred, default human format) or `docker manifest inspect --verbose` (fallback) for the remote digest. The buildx-first path is the **multi-arch fix**: `image inspect` returns the manifest-LIST digest for multi-arch images (because docker pulled via the list), and `imagetools inspect`'s top-level `Digest:` line is also the manifest-list digest — they match correctly. The legacy `manifest inspect --verbose` array form returns per-platform descriptor digests that never match a manifest-list digest (false positives on popular Docker Hub images like nginx/postgres/alpine/node/redis). `fetchRemoteDigestVia` (package-level, over the `dockerRunner` seam — the two per-composer `fetchRemoteDigest` methods it replaced no longer exist) tries imagetools first and falls back to manifest inspect only when imagetools fails for non-transport reasons (older Docker without the buildx plugin); SSH transport failures propagate immediately to abort the batch instead of retrying the same broken transport against a second endpoint. **IMPORTANT regression pin**: do NOT add `--format '{{.Manifest.Digest}}'` back to `imagetoolsInspectArgs` — empirically verified on Docker 29.1.3 / buildx v0.30.1-desktop.1 the template substitution silently falls through and the command prints the same default human-readable Name:/MediaType:/Digest:/Manifests: block as no format flag. A permissive "first non-empty line" parser would then return `Name:      docker.io/library/nginx:latest` as the "digest" → universal false-positive (every image flagged as updated). `parseImagetoolsDigest` extracts the top-level `Digest:` line (skipping indented per-platform digests under `Manifests:`) and validates against a strict `sha256:<64 hex>` regex (`imagetoolsDigestRE`); anything else returns empty so the manifest-inspect fallback engages. There is no defensive "bare sha256 line" fallback — aborting on the first non-matching line means any wrapper that prints a leading banner (e.g. a `motd`-injecting docker context) silently defeats it; every real buildx output we've observed exposes the digest on the primary `Digest:` line. Test fixture lives at `internal/compose/testdata/buildx_imagetools_default_output.txt` — a real `hello-world` capture exercised by `TestParseImagetoolsDigest_RealFixture` — and the parser's negative cases pin the `Name:` line, short non-hex, and wrong-length-hex rejections so the regression cannot be reintroduced. `parseLocalDigest(out, imageRef)` filters `RepoDigests` to the entry whose repo matches the compose-file image reference (stripping tags via `stripTag`); falls back to the first non-empty digest when no repo matches. `parseManifestDigest` extracts `Descriptor.digest`. All three (`docker image inspect`, `docker buildx imagetools inspect`, `docker manifest inspect`) **bypass `command()`/`remoteCommand()`** because they are top-level docker commands, not compose subcommands. Local Compose uses `runDockerCmd` (captures stderr explicitly via `strings.Builder`, mirroring the SSH path) and `RemoteCompose.runRemoteDockerCmd` builds the SSH argv directly and splices `SSHExtraArgs` immediately before the host arg (matching `AllContainerStatsRemote`/`EditCommand`/`ExecCommand`); image names are `shellEscape`d. The shared rune is `compose.UpdateGlyph` (alongside `FormatBytes`) so the TUI and CLI render the same character from a single source. The `docker compose pull --dry-run` path was explored and rejected: with `--policy=always` every non-build service reports "Pulling" regardless of currency; with `--policy=missing` the signal is "image present locally" rather than "image current in registry". The manifest-inspect/imagetools path is the single authoritative implementation.

**Update detection — SSH transport classification (RemoteCompose only)**: `runRemoteDockerCmd` captures stderr explicitly (so test hooks producing non-`*exec.ExitError` errors still surface diagnostic context, and so classification works uniformly) and runs `classifySSHError(err, stderr)` which checks stderr against `sshTransportStderrPatterns` (case-insensitive substring match on SSH-only signatures: `ssh:`, `ssh_exchange_identification`, `could not resolve hostname`, `kex_exchange_identification`, `permission denied (publickey`, `control socket connect`, `port forwarding failed`, `lost connection`, plus ControlMaster failure modes `mux_client`/`client_loop`/`controlsocket`/`multiplex`/`session open refused`). Generic networking phrases like `connection refused`/`connection reset`/`broken pipe`/`no route to host` are deliberately NOT in this list — they ALSO appear in docker daemon stderr when docker fails to reach the registry, and classifying them as SSH transport would abort the entire CheckUpdates batch even though other images would have succeeded; the registry cascade below handles those instead. Transport matches are wrapped in the `errSSHTransport` sentinel; everything else is treated as a per-image docker failure and just gets the stderr appended for diagnostic context (mirroring `withStderr`). Tests can drive `classifySSHError` with explicit stderr via `RemoteCompose.SetOutputErrHook(func(*exec.Cmd) ([]byte, string, error))` — prefer this over `SetTestHooks` when the test cares about transport-vs-per-image classification; the legacy `outputCmd` path now passes empty stderr to the classifier (was: err.Error()-as-stderr) so production and test paths can't diverge. `CheckUpdates` then asymmetrically handles the two buckets: an `errSSHTransport` from ANY per-image call aborts the batch immediately with `"remote update check transport failure: <err>"` (return early — every subsequent call will fail the same way); a per-image docker failure (image not pulled, manifest auth required, registry 404) is absorbed into the tri-state "absent" cell, matching local Compose behaviour. Fresh-deploy single-service projects do not trigger a false cascade just because the image hasn't been pulled to the remote yet — `No such image` is a normal `docker image inspect` exit-1, not a transport failure.

**Update detection — systemic-failure cascades**: `Compose.CheckUpdates` runs TWO parallel cascades so the soft-failure consumer sees a real diagnostic instead of an empty map. (1) **Registry cascade**: when `networkFailures == remoteAttempts > 0` AND `len(out) == 0`, returns `fmt.Errorf("registry unreachable: %w", firstNetErr)`. `looksLikeNetworkErr` matches `no such host` (canonical net.DNSError tail), `connection refused`, `dial tcp`, `x509:`, `too many requests`, `timeout exceeded`, etc. — patterns specific enough to avoid over-firing on per-image fragments. (2) **Local-docker cascade**: when EVERY local `docker image inspect` fails AND every failure ALSO matches `looksLikeLocalDaemonErr` (daemon not running, socket missing, docker CLI missing) AND `len(out) == 0`, returns `fmt.Errorf("local docker unavailable: %w", firstDaemonErr)`. The daemon-classifier gate prevents the common "fresh deploy with multiple un-pulled images" case (every image returns `No such image`) from misfiring as `local docker unavailable`. `compareImageDigest` wraps local failures in the `errLocalImageInspect` sentinel so CheckUpdates can dispatch via `errors.Is` into the right cascade. Partial failures (one image down, one up) do NOT cascade — the succeeded service gets a verdict, the failed one stays absent. **RemoteCompose mirrors the registry cascade**: when every non-transport failure matches `looksLikeNetworkErr` AND no service got a verdict, returns `"registry unreachable: <err>"`. This is critical because narrowing `sshTransportStderrPatterns` to SSH-only signatures means a Docker Hub outage seen from the remote host no longer trips the SSH-transport bucket — without this cascade, the remote case would silently blank every glyph with no diagnostic. The three classifiers (sshTransportStderrPatterns, looksLikeNetworkErr, looksLikeLocalDaemonErr) live next to their consumers — see the comment block above `looksLikeNetworkErr` in `internal/compose/updates.go` for the precedence overview. **All three `CheckUpdates` implementations share ONE loop**: `scanImageUpdates(ctx, wanted, compare)` in `updates.go`, with the per-image comparison behind `compareImageDigestVia(ctx, d dockerRunner, image, localErrWrap)`. **There is no per-caller cascade flag — the ERROR SHAPE the comparer emits is what selects the cascade**, and all three diagnostics run unconditionally. Only `Compose` passes `wrapLocalImageInspectErr` as `localErrWrap`, so only `Compose` can ever emit `errLocalImageInspect`, which is what routes a failed local `docker image inspect` to the daemon counters instead of the registry ones AND what keeps "local docker unavailable" off the SSH path, where it would name the wrong machine (`TestCompareImageDigest_SentinelBinding` pins the binding on all three composers, each direction independently mutation-sensitive). `errSSHTransport` likewise exists only on the remote runner, via `classifySSHError`. A flag would only re-state what the sentinel already decides — and `fetchRemoteDigestVia` already short-circuits on `errSSHTransport` with no flag one call level below. The transport abort is the one diagnostic that fires MID-scan rather than after it, because a dead SSH hop fails every remaining image the same way; the partial map still comes back with the error, matching the untrusted-partial-map half of the `Composer.CheckUpdates` contract. `scanImageUpdates` also **memoizes by image ref**, so a repeated image costs one comparison and contributes exactly one attempt to the cascade counters.

**Update detection — TUI caching and refresh**: TUI caches results in `updateCache map[string]updateEntry` on Model, keyed `projectDir + "|" + serverName` (empty `serverName` = local; `projDir` is stored on Model because it's not otherwise retained after composer creation). `updateEntry{fetchedAt time.Time, results map[string]bool, err bool, errMsg string}` in `internal/tui/app.go`. **Two TTLs**: successes live for `updatesCacheTTL` = 10 minutes; failures live for `updatesErrorTTL` = 30 seconds. **Errors ARE cached** (with the short TTL): caching failures prevents the 5-second tight retry loop the `statusMsg` self-heal would otherwise produce on a persistent fault (empty cache → queue refresh → fail → empty cache → repeat; ~120 failed CheckUpdates per 10 minutes against a slow remote SSH hop or a Docker Hub outage). The cached failure entry has `results=nil`, `err=true`, and `errMsg` set to the original error text. **`errMsg` is restored on cache hit** in `maybeRefreshUpdatesCmd` and the `servicesMsg`/`statusMsg` cache-replay paths — without this, navigating away (which clears `m.updatesErr`) and re-entering within `updatesErrorTTL` would silently drop the soft warning even though the failure is still known-bad. A new error entry overwrites any prior successful entry for the same key (don't trust stale success once the latest refresh disagreed); a new success overwrites a cached failure. **Off-screen error handling**: the `updatesMsg` handler applies state mutations (set `updatesErr`, clear stale `UpdateAvailable` glyphs in `m.svcStatus`, hydrate fresh verdicts) BEFORE the screen check — `m.svcStatus` is the source of truth the next entry to `screenSelectContainers` renders from, so leaving stale glyphs in it during an off-screen window (e.g. the config screen, which is read-only and does NOT trigger `refreshStatus` on return) would let them resurface alongside no warning. Only `fixSvcOffset` stays screen-coupled (touches scroll offsets that are only meaningful while the container list is rendered). **Post-operation cache invalidation**: the `esc` handler that returns from `screenProgress` to `screenSelectContainers` deletes the cache entry for the current key on a successful Deploy or Restart, so the next `maybeRefreshUpdatesCmd` misses and enqueues a fresh CheckUpdates — without this, the "update available" glyph would persist for up to 10 minutes after a successful deploy, exactly when the user wants confirmation. Invalidation runs BEFORE the `m.done = false` reset (otherwise the check would see done==false and never fire). Skipped on `m.failed` (don't clear user-visible state on failure) and on Stop (stopping doesn't change image freshness). `refreshUpdates(session)` is fired on entry to `screenSelectContainers` only when the cache is missing or stale (`maybeRefreshUpdatesCmd` helper); the uppercase `U` key bypasses TTL for force-refresh AND guards against stacking via `if m.updateInFlight { return m, nil }`. Updates are **NOT** wired into the periodic 5s `refreshTickMsg` — cadence is TTL + explicit user action, because registry round-trips are expensive and the answer changes slowly.

**Update detection — sessions and in-flight discipline**: `updatesMsg{results, err, session uint64}` carries a session captured at fetch time; `updatesSession` is bumped at the **same 7 sites** as `statsSession`/`statusSession` (project pick, esc container→proj, esc proj→server, entryLocal, execDone, return from progress, return from logs) but NOT at the `connectResultMsg` SUCCESS path (`m.composer` hasn't been swapped yet — the bump happens at the project-pick handler downstream; the success path carries a code comment documenting this asymmetry so future contributors don't add a redundant bump). The `connectResultMsg` ERROR path bumps `projectsSession` (the connect attempt swapped the projectLoader) but not the other three counters (composer/composerFactory weren't touched). The dedicated `updateInFlight bool` flag follows the same clear-before-screen-check pattern as `refreshInFlight`, with one strengthening: the flag is cleared BEFORE BOTH the session check AND the screen check, on EVERY `updatesMsg` arrival (current OR stale, on-screen OR off). The previous "stale leaves it alone, context-change handler resets it" semantics had a sticky-flag bug: after `U` (in-flight=true) → navigate away → come back, the original fetch arrived with an OLD session, and the in-flight guard inside `maybeRefreshUpdatesCmd` would silently swallow every subsequent fetch on cache hits. Clearing on stale arrivals as well is safe because the cache write below is still session-gated, so a stale result can't pollute the cache. Companion guard: `maybeRefreshUpdatesCmd` early-returns nil when `m.updateInFlight == true`, preventing fetch stacking — same rationale as `refreshTickMsg`'s `refreshInFlight` gate. Because of this guard, every context-change site that bumps `updatesSession` AND calls `maybeRefreshUpdatesCmd()` (project pick, execDone, esc back from progress/logs, entryLocal fast-track) MUST reset `m.updateInFlight = false` first; the session bump invalidates any in-flight fetch (its response will be discarded as stale), so the guard must not refuse to fire a fresh fetch for the new context. The 2 leave-screen transitions (esc container→proj, esc proj→server) also reset `updateInFlight = false`. The `connectResultMsg` error path also clears `serverName`/`updatesErr`/`updateInFlight` so a failed connect attempt doesn't leak transient state into a subsequent connection. The `entryLocal` handler explicitly clears `projDir`/`projName`/`updatesErr` to prevent stale cache-key components carrying over from a previous remote session.

**Update detection — rendering, CLI, and JSON**: Cache results are re-hydrated onto `m.services` inside `servicesMsg` and `statusMsg` handlers via a `hydrateUpdates` helper, race-safe regardless of arrival ordering of status vs updates. **Phantom guard**: `hydrateUpdates` skips verdicts whose service name is NOT already in `m.svcStatus` — without this guard, a verdict for an unknown service (compose config and ContainerStatus may transiently disagree during a refresh, or a stale verdict may refer to a service that no longer exists after a project switch) would synthesise a zero-valued `ServiceStatus` entry that'd leak across context switches. The renderer iterates `m.services` (not the status map) so phantoms are invisible today, but the guard prevents a latent class of bugs in any future iterator. Rendering: yellow `updateGlyphStyle` in `internal/tui/styles.go` appends `" ⇧"` after the service name; `maxName += 2` unconditionally (always reserve the glyph slot so Created/Uptime/CPU/Mem/Ports don't shift when a verdict arrives or clears mid-poll); glyph is shown on stopped services too. The `U updates` token lives in the `?` overlay, not the footer. Errors render in the soft-warning slot prefixed `updates: `, priority `svcErr > statsErr > updatesErr`. CLI `cmd/list.go` gates `CheckUpdates` behind `--updates` in BOTH single-project (`-C`, `--ssh`) and multi-project modes (same opt-in shape as `--stats`) — each service costs one registry round-trip and 20+ services over SSH adds 10s+, so the default is off in both modes; soft failure prints `cdeploy: updates unavailable: <err>` (or `for "<project>": <err>` in multi-project) to stderr and leaves cells blank without aborting the listing — callers SET `updates = nil` on error in line with the `Composer.CheckUpdates` partial-untrusted contract above; JSON output gains `update_available *bool` with `omitempty` so the wire shape is unchanged when the flag is omitted. `formatDots`/`formatDotsGrouped` extend `maxName` by 2 cells the same way as the TUI — width is measured by `utf8.RuneCountInString` because the U+21E7 glyph is multi-byte but renders in one terminal cell, and styled rendering carries ANSI escapes that don't count toward display width. The glyph rune is owned by `compose.UpdateGlyph` so both surfaces stay in sync; bumping it changes both in one place.

**Session filters for stale responses**: `statsMsg`, `statusMsg`, `servicesMsg`, AND `projectsMsg` all carry a `session uint64` captured at fetch time; their handlers reject messages where the session (and screen) don't match. Three counters live on Model:
- `statsSession` covers `refreshStats` — bumped at every context change that swaps `m.composer` (proj pick, esc proj→server, esc container→proj, entryLocal, execDone, esc from logs/progress).
- `statusSession` covers both `refreshStatus` AND `loadServices` — bumped at the same 7 sites as `statsSession` (the lifecycle is identical: `loadServices` is the initial-load sibling of `refreshStatus`, fetching list + initial status in one shot).
- `projectsSession` covers `loadProjects` — bumped at every site that swaps `m.projectLoader` (entryServer, entryLocal, preselectedConnectMsg, connectResultMsg error path, esc proj→server). Without this, a stale `loadProjects` from server A's loader could overwrite `m.projects` after the user has switched to server B, then feeding B's `composerFactory` an A-discovered path on selection — potentially mounting the wrong directory on deploy.

Missing the session filter on any of the four is the same class of bug — codex's adversarial review caught each one in successive rounds. When adding a NEW async msg type that's tied to a screen context, give it a session and gate the handler on `m.screen != <its-screen> || msg.session != m.<sessionField>`.

**`refreshInFlight` prevents fetch stacking**: the tick fan-out `tea.Batch(refreshStatus, refreshStats, refreshTick)` schedules the next 5s tick *concurrently* with the current refresh — Bubble Tea batches execute concurrently, not sequentially. Without a guard, if `docker stats --no-stream` takes longer than 5s on a slow remote SSH hop, the next tick would stack another pair of fetches on top. The `m.refreshInFlight bool` is set true at every site that fires `refreshStats()` (the tick handler + the 5 transition handlers that fan out the fetch batch) and cleared in the `statsMsg` handler on any *current-session* arrival, *before* the screen check (success or error). Clearing has to happen before the screen check because if the user opens the config / logs / progress screen while a stats fetch is pending, the response arrives off-screen and would otherwise be discarded silently — leaving `refreshInFlight` stuck true and permanently silencing the periodic loop when the user returns to the container screen. The session-match condition makes the unconditional clear safe: stale responses (different session, indicating a context change has happened) don't touch the flag because the context-change handler already reset it. The flag is also explicitly reset to false at the 2 "leave screen" transition handlers (esc back to project picker, esc back to server picker) so the new context starts clean. When the next tick fires while the guard is set, it reschedules without fetching.

**Test seam for the tick**: `Model.tickCmdOverride func() tea.Cmd` is nil in production; tests set it via `installFakeTick(&m)` (in `internal/tui/app_test.go`) to swap the real `tea.Tick` for a non-blocking Cmd that returns a `fakeTickMsg`. Without the override, every test exercising the gated paths (off-screen, in-flight, confirming) would leave a real 5s `tea.Tick` goroutine running until the program exits. With the override installed, tests assert directly on whether `cmd()` returns a `tea.BatchMsg` (positive path: fetch batch) or any other msg (gated path: just the rescheduling tick). NewModel sets `m.refreshInFlight = true` for the local fast-track because `Init()` will fire `refreshStats`; tests that exercise the unblocked tick path must explicitly clear it.

When adding a new screen that should NOT trigger periodic refreshes, no change is needed: the gate already excludes any screen != `screenSelectContainers`. When adding a new screen that DOES need its own periodic refresh, prefer a separate tick (different msg type) rather than overloading `refreshTickMsg`. When adding a new context-change handler (anything that swaps `m.composer`), bump BOTH `statsSession` AND `statusSession`, and set `refreshInFlight` (true if the handler fires a refresh batch, false if it just navigates away). `statsMsg` carries a `session uint64` captured at fetch time from `m.statsSession`; the handler rejects messages where `msg.session != m.statsSession` in addition to the screen check, mirroring the `logsSession`/`configSession` pattern. `statsSession` is bumped on every context change that swaps `m.composer` (project pick, esc back to project picker, esc back to server picker, entryLocal) so an in-flight fetch from project A cannot land in project B's view. Soft failure: on stats fetch error, both CLI (`cdeploy: stats unavailable: <err>` to stderr, exit 0, blank cells) and TUI (`statsErr` rendered as soft warning) keep status — the load-bearing primary view — intact; in the TUI, when both `svcErr` and `statsErr` are set, `svcErr` wins (the more important failure).

**Ports column**: `ServiceStatus.Ports []runner.Port` (with `Host`, `HostPort`, `ContainerPort`, `Protocol` fields) is populated by `parseContainerStatus()` from `docker compose ps --format json`. Primary data source is the `Publishers []` array (Compose v2); when absent or empty, `parsePortsString()` falls back to parsing the `Ports` text field (e.g. `0.0.0.0:8080->80/tcp, :::8080->80/tcp`). Publishers with `PublishedPort == 0` (i.e. `expose:`-only/internal) are skipped. Dedup is keyed on the full tuple `(Host, HostPort, ContainerPort, Protocol)` so distinct bind interfaces on the same port (e.g. `127.0.0.1:8080->80` and `192.168.1.10:8080->80`) both survive. A separate `collapseIPv6Mirrors()` pass collapses only the IPv4/IPv6 *wildcard* mirror pair — when both `0.0.0.0` (IPv4 unspecified) and `::` (IPv6 unspecified) appear on the same `(HostPort, ContainerPort, Protocol)` tuple, the `::` entry is dropped. All other host strings are distinct user-visible binds: IPv6 loopback `::1`, link-local `fe80::1`, or explicit IPv6 addresses like `2001:db8::1` survive intact, even alongside an IPv4 sibling. Multiple non-wildcard IPv6 entries on the same tuple do not collapse against each other (full-tuple dedup in `mergePort` already removes exact repeats). Bracketed IPv6 like `[::]:8080` is normalized (brackets stripped on input). Empty `URL` from Compose is normalized to `0.0.0.0`. Scaled-service ports go through the same dedup + collapse + sort pipeline (sorted ascending by `HostPort`, then `ContainerPort`, `Protocol`, `Host`). Render helpers live in `internal/compose/ports.go`: `FormatPort()` returns `host:hp→cp` for IPv4 and `[host]:hp→cp` for IPv6 (the arrow is U+2192, not `->`; IPv6 hosts — any host containing `:` — are wrapped in brackets to disambiguate the host:port boundary), with `/proto` suffix only when protocol is non-empty and not `tcp` (`/udp` and `/sctp` are shown). Wildcard hosts (`0.0.0.0` and `::`, both meaning "all interfaces") are omitted entirely so the common all-interfaces case renders as a bare `hp→cp`; non-wildcard binds (loopback, explicit address) keep their host so the LAN-vs-loopback distinction stays visible. The wildcard-hiding affects only display — JSON output (`cmd/list.go` serializes the `Port` struct directly) preserves the original `host` field. `FormatPorts()` comma-joins. Both the CLI `list` (`formatDots`/`formatDotsGrouped` width-track `maxPorts` and append the column after Uptime when any service has ports) and the TUI container-select screen (captions row gains `"Ports"` via `hasStatusColumns()`) render the column. Stopped containers and services without published ports show a blank cell (padded whitespace for alignment). CLI JSON output includes a `ports` array (`omitempty`) per service with `host`/`host_port`/`container_port`/`protocol` fields.

**Unmanaged containers — the `HostContainers` composer and the three-method `dockerRunner` seam**: a container with no `com.docker.compose.project` label — a hand-started `docker run` postgres, a watchtower, a monitoring agent — is invisible to every compose command, so it gets its own `runner.Composer`: `compose.HostContainers` (`internal/compose/hostcontainers.go`), read-only, built on host-level `docker ps`/`docker stats`/`docker logs`/`docker exec`. The differentiator is remote reach: the ControlMaster socket is already open, so the view inspects a production host with **nothing installed on that host**. **One type, one seam — not two parallel types.** The ten `runner.Composer` methods split into five writes that `return errReadOnly` and five reads that differ between local and remote only in how the `*exec.Cmd` is built, so the whole local/remote variation collapses into a single unexported `dockerRunner` field. **The seam needs THREE methods, not one `cmd(ctx, args...)` builder**, because the three call shapes are mutually exclusive: `run` CAPTURES and classifies (the remote adapter reuses `runRemoteDockerCmd`, so `classifySSHError`/`errSSHTransport` and explicit stderr capture come for free instead of being written a second time), `stream` writes to an `io.Writer` and must NOT allocate a TTY (a pty would let docker line-buffer and echo, corrupting the chunked reads the TUI log viewer makes) and wires BOTH Stdout and Stderr to `w` because `docker logs` sends the container's stderr to its own stderr, where most application logs land, and `tty` MUST splice `-t` on the remote side (matching `RemoteCompose.ExecCommand`). All three remote forms build the remote command string through one helper, `RemoteCompose.remoteDockerCmdString(args)` (`remote.go`, beside `sshArgs`), so the `docker` + `shellEscape` rule lives in one place instead of three. **Constructors are exported, the interface is not**: `cmd/root.go` has to build these and cannot name an unexported interface, so `NewLocalHostContainers(*Compose)` and `NewRemoteHostContainers(*RemoteCompose)` are exported while `dockerRunner` and both adapters stay package-private. Discovery is `hostPsArgs` = `ps -a --size=false --format {{json .}}` — the **template** form, not the bare `json` keyword, which only exists on Docker CLI >= 23.0 while this repo deliberately supports legacy standalone hosts via `Detect()`. **`--size=false` is load-bearing for latency and must not be dropped**: the CLI cannot tell which fields `{{json .}}` reads, so it conservatively requests container sizes, and `SizeRw`/`SizeRootFs` make the daemon walk every container's read-write layer — a `du`-style traversal per container that costs tens of seconds on a host with many or large containers (measured: `{{json .}}` alone returns `"Size":"0B (virtual 161MB)"`, the bare keyword and `--size=false` both return `"0B"`). `hostPsEntry` has no `Size` field, so that walk is computed, shipped over SSH and discarded. An explicit `false` wins over the format inference; naming the eight fields individually would avoid it too, but an unknown field is a **hard template error**, so `.State` (CLI >= 20.10) would break the legacy hosts this template form exists to serve. This regressed the project picker to ~30s on real hosts before it was caught; `parseHostContainers` reads NDJSON **only** — unlike the sibling `parseContainerStatus`/`parseStatsOutput`, which tolerate an array because the `--format json` flag they read changed shape across Docker versions; a per-container Go template emits one object per line by construction on every version, so there is no array form to tolerate. `isComposeManaged` matches the `com.docker.compose.project=` prefix **only at a token start** (`HasPrefix(labels, k) || Contains(labels, ","+k)`), **not by splitting into `k=v` pairs**: a label VALUE may legally contain a comma, so slicing the comma-joined `Labels` string into pairs can mis-slice — a false verdict would need a value containing the literal `,com.docker.compose.project=` (the trailing `=` is also what keeps the sibling `…project.config_files`/`…project.working_dir` keys from matching). Host-level `ps` has no Health field — it lives in the trailing `(...)` of `Status`, so `parseHealthFromStatus` captures it with `healthSuffixRe`, the SAME regex `formatUptime`/`stripHealthSuffix` uses (`uptime.go`), which grew a capture group rather than being duplicated — one grammar, one place, so the two consumers of the trailing annotation cannot drift. It is **anchored at the end**, which is what makes the reading trailing rather than first-match: without the anchor `Up 2 hours (healthy) (paused)` reports healthy (the `Exited (255) …` cases cannot catch that, since their first group is a numeric code the switch rejects anyway). `Running` reads `State == "running"` but **falls back to `HasPrefix(Status, "Up ")` when `State` is empty**: the `docker ps` JSON keys are reflected from the CLI's own formatter and `.State` only exists on Docker CLI >= 20.10 — exactly the legacy hosts `hostPsArgs` takes the template form for — so without the fallback every row on such a host renders a stopped dot beside a live `Uptime` and `x` exec refuses on a container that is plainly up (`hostContainerRunning`); `Created`, `Uptime` and `Ports` reuse the existing `parseCreatedAt`, `formatUptime` and `parsePortsString`, and there is no replica aggregation because a host container is its own row. `ContainerStats` goes through the seam directly rather than through `AllContainerStats`/`AllContainerStatsRemote`: those take a concrete `*Compose`/`*RemoteCompose`, which a seam-held `HostContainers` cannot supply without a type switch that would defeat the seam — only the two-line argv build is duplicated, `parseStatsOutput` and `aggregateStatsByService` are reused, and a container present in `ps` but absent from `stats` is skipped, not an error. It **early-returns before the stats call when there are no unmanaged entries** — the join would be empty by construction, and `docker stats --no-stream` is a ~1.5s host-wide call (a full SSH round-trip remotely) that the 5s refresh tick would otherwise pay forever. `ContainerStatus` has NO counterpart guard and must not grow one: its loop already yields an empty map for free, so the branch would buy nothing and imply a cost rationale it does not have. `hostStatsArgs` takes the SAME `{{json .}}` template form as `hostPsArgs`, for the same reason — the bare `json` keyword needs Docker CLI >= 23.0, and for `docker stats` the CLI rewrites that keyword to exactly this template, so the output is identical on a modern host and the two argv builders in this file no longer argue opposite positions on the same host-version question. **That equivalence is per-command and does NOT generalise**: it was verified for `stats`, which has no size concept, and assuming it also held for `ps` is what hid the `--size=false` regression above. Verify the two forms against the specific subcommand before reusing this argument a third time. `AllContainerStats` keeps the keyword; that is pre-existing and out of this file's scope. `CheckUpdates` sources the name→image map from the `Image` field `docker ps` already returned (no second call, and no `docker compose config` — there is no compose file to read) and delegates to the shared `scanImageUpdates`, passing a nil `localErrWrap` — which is what keeps the daemon cascade off this path; it could never fire anyway, because a dead local daemon fails the `docker ps` discovery call first, long before any image inspect runs. `hostImageMap` drops entries with no image ref AND entries whose `Image` is a **bare image ID** (`^[0-9a-f]{12}([0-9a-f]{52})?$` — what `docker ps` reports for an untagged image): no registry can be asked about a ref with no repository, so the verdict is the tri-state absent either way, and including it would only buy a wasted round-trip per hand-started container and skew the cascade ratios. The TUI never fires this check automatically — see the read-only UI contract below: `U` is the only trigger. `scanImageUpdates` **memoizes by image ref**, which matters far more here than on a compose project: distinct services usually have distinct images, but host containers repeat one image constantly (three MCP sidecars off one tag), and each comparison costs a local inspect plus up to two registry inspects — every one a separate SSH round-trip. The memo also keeps the cascade counters honest, since each distinct image contributes exactly one attempt. `ContainerStatsFromBulk` is deliberately NOT implemented — its only consumer is `cmd/list.go`'s `bulkStatsAggregator`, and list integration is deferred, so it would be dead code.

**Unmanaged containers — the picker row, the widened `ComposerFactory`, and the cache-key collision**: the view is reached through one synthetic project-picker row, not a new screen. `compose.Project` gains `Unmanaged bool` and `Desc string` (the picker's description-column override, carrying the container count) — `Status` is NOT reused for it, because `Status` means the `docker compose ls` lifecycle string and the picker never renders that, so overloading it would leave the field with two meanings and the rendered one bolted on. The three picker-row symbols (`UnmanagedProjectName`, `CountUnmanaged`, `WithUnmanagedRow`) live in `internal/compose/unmanagedrow.go`, not in `hostcontainers.go`: `WithUnmanagedRow` operates on `[]Project` and is a picker concern, not a composer one. It appends the row under the exported `compose.UnmanagedProjectName` const, which the renderer test, the picker and the factory branch all read so the row name cannot be spelled two ways. The append happens **after** `ListProjects` and deliberately bypasses `sortProjects`: that sorts case-insensitively by name and `(` sorts before every letter, so a sorted `(unmanaged)` would land first instead of last. A `CountUnmanaged` error is **swallowed** in its own explicit branch (not shared with the `n == 0` path) — the picker must still show the compose projects that did load, and a `docker ps` the SSH user cannot run must not cost the user the whole list. The cost is that a permanently-failing discovery is indistinguishable from a tidy host: the row simply never appears, with no diagnostic. That is an accepted trade-off, not an oversight — surfacing it would need a soft-warning channel the picker screen does not have. `viewSelectProject` renders `proj.Desc` when non-empty, falling back to `shortenPath(proj.ConfigDir)`, which on the unmanaged row would be blank. **Every branch `cmd/root.go` contributes lives in a package-level helper, never in the `RunE` closure**, because `cmd/root_test.go` tests flag registration only — the root command needs a TTY and is never executed, so a closure body has no test seam and the whole feature could be deleted with CI green. The three helpers are `projectsWithUnmanaged(ctx, lister, hc)` (both `ProjectLoader` literals), `localComposerFor(proj, detector, detected)` and `remoteComposerFor(proj, rc)` (both `ComposerFactory` literals; `remoteComposerFor` reads the host off `rc.Host` rather than taking a parallel `host` parameter a caller could pass out of step); each is unit-tested in `cmd/root_test.go`. Add a helper, not an inline `if`, for anything new here. The count is a load-time snapshot: `m.projects` is cached across `esc` back-navigation, so it does not refresh inside a session. **`ComposerFactory` is widened to `func(proj compose.Project) runner.Composer`** — the unmanaged row has no config directory, and a sentinel directory string would be a magic value that deepens the cache-key problem below rather than avoiding it; `cmd/list.go` declares its own `func(dir string) runner.Composer` and is unaffected. **`updatesCacheKey()` gains an `"unmanaged|"` prefix from `m.readOnly()`, and this is the subtlest invariant of the feature.** The key is `projDir + "|" + serverName`, and the local-fast-track context (no project picker) keys a bare `"|"` — an unmanaged row's empty `ConfigDir` would key `"|"` too, a direct collision. Two failures follow: a fresh entry from either context suppresses the other's `CheckUpdates` for the full 10-minute TTL, and `hydrateUpdates` writes one context's verdicts onto any colliding service name (the phantom guard drops only *unknown* names, not colliding ones). The prefix is derived from the COMPOSER rather than from a parallel `projUnmanaged bool` field: the composer IS the context the cache describes, it is live at all three `updatesCacheKey()` call sites, and it is assigned or nil'd at exactly the sites such a field would have to be cleared at — so deriving it keeps four entries out of the back-navigation cleanup discipline CLAUDE.md calls the repo's most fragile invariant, where one forgotten site silently mis-keys the cache (pinned end-to-end by `TestUpdatesCacheKey_FollowsComposerAcrossNavigation`, which drives unmanaged-pick → `esc` → `esc` → local fast-track). **The list is a load-time snapshot in BOTH directions**: the picker's row count does not refresh inside a session (`m.projects` is cached across `esc`), and neither does `m.services` on the unmanaged screen — the 5s `refreshTickMsg` re-fetches status and stats but never re-lists, so a container started by hand while the screen is open never appears and a removed one keeps a stopped-dot row. Making the tick re-list is NOT a one-liner: the `servicesMsg` handler resets `svcCursor`/`svcOffset`/`selected` and calls `clearSearch()`, so a 5s tick would reset the cursor and kill a committed search — a correct fix needs a merge that preserves them, or a separate list-diff message. Documented in the README; deferred, not forgotten.

**Unmanaged containers — the read-only UI contract**: `ReadOnlyComposer` is declared in `tui` beside `ConfigProvider`/`ExecProvider` and type-asserted on the concrete composer, with a **named** `ReadOnlyComposer() bool` method — a method-less marker would be `interface{}`, which every composer satisfies, so `m.readOnly()` would be true everywhere. `Model.readOnly()` is nil-safe, so a `Model{}` test literal reads as writable. `d`, `r`, `s`, `R`, `c`, `space` and `a` all early-return, each calling `fixSvcOffset()` first: the container dispatch clears `m.warning` above the switch, and the freed warning line grows `svcVisibleCount()` by one, so a gated key that returned without re-clamping would leave a too-large `svcOffset` and a blank row under the last service of a scrolled list (`TestReadOnly_GatedKeyReclampsOffset`). `c` and `R` would gate themselves for free (`HostContainers` implements neither `ConfigProvider` nor `RollbackPreparer`) but get an **explicit** gate anyway: an inert key that a help table still names is the exact failure the `?` overlay exists to prevent, so the gate and the table have to move together. Because a read-only mock implements neither capability either, `TestReadOnly_GatesWriteKeys` alone would pass on the type assertion rather than on the gate — `TestReadOnly_GatesWriteKeys_WithCapableComposer` drives the same two keys through a double that DOES satisfy both, so the `m.readOnly()` early return is the only thing left standing between the key and its action. **Nothing advertises a no-op, and that extends past the keys to the widgets.** `containerHelpLines()` returns a different idle pair when read-only (`line1` drops `space toggle`, `line2` becomes `l logs • x exec`); because `containerFooterLines()` and `containerFooter()` both read that one helper, the height math and the render follow the variant by construction. **The read-only pair also inverts a width relationship the writable footer relied on.** `containerFooterLines()` is decided from the IDLE pair alone and must stay state-INDEPENDENT — `svcVisibleCount()` reserves rows from it, so reading the substituted footer would grow the list mid-search, the exact re-flow the reserved bar exists to prevent. On the write path the committed-search substitution (`n/N cycle • esc clear`, 25 cells) is SHORTER than the idle `line2` (35), so the one-line branch always held it; the read-only `line2` (`l logs • x exec`) is 19 cells, so at widths 43-46 the substitution overran the width by 1-4 cells of CONTENT. `containerFooter()` therefore clamps every rendered line with `clampToWidth`, the same never-wrap guarantee `searchBarLine()`/`logBarLine()` give — pinned by `TestContainerFooter_NeverExceedsWidth` and by the `readOnly` dimension of `TestContainerView_ExcessLineWidthIsPaddingOnly`. `helpGroupsFor` reads `helpContext.readOnly` (supplied by `Model.helpGroups()` from `m.readOnly()`) and returns `readOnlyContainerGroups(canGoBack)`: SELECT and OPERATE are gone whole and `c` leaves INSPECT, but **`enter` MOVES into INSPECT** as `{"enter", "confirm the exec prompt"}` — the `x` prompt still binds it and OPERATE was its only home, so deleting that group wholesale would break BOTH directions of `TestHelpGroups_NamesEveryBoundKey`. The two groups the variants SHARE come from shared constructors, `findGroup()` and `inspectGroup(readOnly bool)`, the same answer `leaveGroup(canGoBack)` already gives: FIND is byte-identical across variants and INSPECT differs only by `c` and `enter`, and both groups exist on no other screen — so a hand-copied pair would be new duplication a future key had to be added to twice, with no test comparing them. Group ORDER carries the same load as the writable table (LEAVE sits 3rd of 4 so `splitHelpGroups` leaves it in the left column) and the `actions` flags still drive `singleColumnOrder()`'s truncation order. The drift pin runs **per variant, never over a union**: `TestHelpGroups_NamesEveryBoundKey` reads `helpKeyTokens(s, canGoBack, false)` and `TestHelpGroups_ReadOnlyNamesEveryBoundKey` reads the `true` variant, both directions each. A union would weaken the writable half — a key deleted from the writable table but still named by the read-only one would go unnoticed. The selection affordances go too: the title loses its `(n/m selected)` counter and every row loses its `[ ]`/`[x]` checkbox, because multi-select exists only to feed `d`/`r`/`s`/`R` and a checkbox advertises a dead key as loudly as the counter does. That silently couples to the caption row — the left pad is `cursor(2) + checkbox(3) + space(1) + health(1) + space(1) + dot(1) + space(1) = 10`, so the read-only pad must be **7** in lockstep or every caption misaligns against its data column. **No new screen, no new `tea.Msg`, no new goroutine and no new session counter**: the screen runs the existing `loadServices`/`refreshStats`/`maybeRefreshUpdatesCmd` batch, which is already session-gated, so `clearSearch()` gains no tenth departure site, `hasStatusColumns()` is unchanged and `TestAllScreens_Complete` is unaffected. **The update check is the one member of that batch that does NOT fire here.** All THREE automatic entry points — `maybeRefreshUpdatesCmd()`, the `statusMsg` self-heal, and `Init()`'s picker-skipped fast path — consult `autoUpdatesAllowed()` (= `!m.readOnly()`) and skip the fetch, leaving `U` as the only trigger. The fast path is the one that does NOT route through `maybeRefreshUpdatesCmd()` (the cache is empty on launch, so it calls `refreshUpdates()` directly), which is why it needs its own gate; `NewModel` sets `updateInFlight = m.autoUpdatesAllowed()` rather than a flat `true`, so the flag tracks whether a fetch is actually queued — a `true` with no fetch behind it never clears, and `maybeRefreshUpdatesCmd`'s in-flight guard would then refuse every later fetch, including `U`'s. No production caller hands a `HostContainers` straight to `NewModel` today (the unmanaged view is reached through the project picker), but the gate is what keeps the invariant true for one that does. A compose project bounds `CheckUpdates` to one service list the user is actively managing; the unmanaged set comes from `docker ps -a`, so it grows with every container ever left on the host and each distinct image costs a REGISTRY manifest request. An automatic fan-out on screen entry, repeated by every 5s status tick, can exhaust the anonymous Docker Hub manifest quota — which then breaks a real `docker pull` from the same host. The CLI reaches the same conclusion for the same reason (`list --updates` is opt-in), and the `?` overlay already names `U check updates`. Gating only SOME of the three entry points leaves the rest firing (the self-heal is the worst — it repeats forever), so `TestReadOnly_NoAutomaticUpdateFetch` drives the first two and `TestReadOnly_InitFastPathHonoursOptIn` the third, each against a writable control, and `TestReadOnly_UpdateKeyStillFetches` pins the other half of the contract. **The two gated entry points also CLEAR `m.updatesErr` when the cache entry has expired.** A failed `U` caches a failure whose warning both self-heal paths restore while it is fresh; once the entry ages out, nothing here will ever refetch it, so leaving the warning up would keep one failed `U` on screen for the life of the view (`TestReadOnly_StaleUpdateWarningClears`; the `statusMsg` clear sits BEFORE that handler's `fixSvcOffset()` so the freed footer row is re-clamped). The success side has the matching consequence and it is deliberate: the `⇧` glyphs blank when the 10-minute entry expires and return on the next `U` — documented in the README.

## Adding New Operations

1. Add constant to `Operation` enum in `internal/runner/runner.go`
2. Update `String()`, `Steps()`, and `buildSteps()` in the same file
3. Add action key case in `screenSelectContainers` handleKey in `internal/tui/app.go`, AND name the key in the matching group in `helpGroupsFor()` (`internal/tui/help.go`) — the `?` overlay is the only place the full key table is advertised now that the footer carries 6 tokens
4. Gate the new key on `m.readOnly()` with an early return, and leave it OUT of `readOnlyContainerGroups()` (`internal/tui/help.go`). Every operation is a compose pipeline, and an unmanaged container has no compose file, so a new op is by definition inert on the read-only screen — a key the read-only table still named would advertise a no-op, which is the failure that whole variant exists to prevent
5. Add CLI subcommand in `cmd/deploy.go` and register in `cmd/root.go`
6. Tests: runner sequence test, cmd subcommand/flag tests, TUI action key + confirmation tests, plus the expected-key set in `TestHelpGroups_NamesEveryBoundKey` (`internal/tui/help_test.go`), which fails in both directions when the help table drifts from the dispatch. If the operation is a WRITE, add the key to the table in `TestReadOnly_GatesWriteKeys` (`internal/tui/app_test.go`) so the read-only screen is pinned to refuse the gate step 4 added. The read-only help pin needs NO edit for a gated key — it stays out of `TestHelpGroups_ReadOnlyNamesEveryBoundKey`'s hand-maintained bound set, and that test's names-nothing-unbound direction is what catches a table that advertises it anyway.

If the new operation needs an op-specific pre-run step (like Rollback's snapshot read + digest-pin prep), don't fork `runOperation` — route through `runOperationWithPrep(ctx, op, all, containers, prep)`. The `prep func(context.Context, runner.Composer) (func(), error)` runs AFTER the composer is built and BEFORE the pipeline (so it can apply refusal rules and configure the composer, e.g. set `ExtraComposeFiles`); its returned cleanup is deferred function-scoped, so it runs after the wait phase but before the remote SSH teardown (LIFO). deploy/restart/stop pass a nil prep and keep the original path. Rollback lives in its own `cmd/rollback.go` (see "Adding New CLI Subcommands") but is a deliberate reuse of this deploy machinery, not a fresh subcommand skeleton.

## Adding New CLI Subcommands

See `cmd/list.go`, `cmd/logs.go`, and `cmd/exec.go` for the pattern. Each subcommand:
1. Creates a `*cobra.Command` in its own `new*Cmd()` function
2. At the top of the `Run*` function, calls `checkRemoteMutex(serverName, sshTarget, identityFile)` to enforce the `--server`/`--ssh` mutex and the `--identity requires --ssh` rule (it must run before `os.Getwd()` and `signal.NotifyContext` so spurious setup doesn't run when the flags conflict)
3. Branches in this order: `sshTarget != ""` → `resolveSSHRemote(ctx, sshTarget, projectDir, identityFile, <factoryVar>)` (passing the subcommand's own injectable factory); else `serverName != ""` → load config, `FindServer()`, create `RemoteCompose`, `Connect()`, defer `Close()`, `Detect()`; else fall back to local `compose.New(dir)`
4. Is registered in `cmd/root.go` via `rootCmd.AddCommand()`

`cmd/skill.go` (the `skill install|show|uninstall` subcommand, see "Agent Skill distribution" below) is a deliberate exception to this pattern — it operates on local files only and has no `--server`/`--ssh`/`--project-dir`/remote wiring.

`cmd/rollback.go` (the `rollback` subcommand) is a second deliberate exception: rather than reimplementing the composer-branch skeleton, it reuses the deploy machinery via `runOperationWithPrep(ctx, runner.Rollback, …, rollbackPrep(…))` — the shared `runOperationWithPrep` already does the `checkRemoteMutex` → ssh/server/local branching, and `rollbackPrep` is the op-specific pre-run hook (snapshot read + refusal rules + digest-pin prep). See "Adding New Operations" for the prep-hook recipe.

## Agent Skill distribution (`cdeploy skill`)

**`skills/` package**: the repo-root `skills/` directory is BOTH the external-installer convention directory (so `npx skills add lexxzar/compose-deploy` and `gh skill install lexxzar/compose-deploy` find `skills/cdeploy/SKILL.md` on the default branch) AND a Go package holding the `//go:embed cdeploy` directive. `skills.FS` exposes the embedded tree; `skills.CanonicalSkill()` returns the raw, unstamped SKILL.md bytes — the single source of truth for the CLI, external installers, and verification, version-locked to the binary via `go:embed` (panics on a missing embed, since that is a build/packaging fault, not a runtime error to thread).

**`cdeploy skill install|show|uninstall <claude|codex|all>`** (`cmd/skill.go`): installs the embedded skill into agent skill directories. Targets resolve via `skillTargetDirs()`: claude → `~/.claude/skills/cdeploy` (also read by Cursor/OpenCode); codex → `~/.agents/skills/cdeploy` AND `$CODEX_HOME/skills/cdeploy` (default `~/.codex`; an EMPTY `$CODEX_HOME` is treated as unset because `t.Setenv` can set but never unset an env var); all → the deduped union. Dedupe (`resolveDedupeKey`) resolves symlinks on the deepest EXISTING ancestor of each candidate (the target dir usually does not exist yet, and `filepath.EvalSymlinks` errors on missing paths), then re-appends the not-yet-existing suffix, so two candidates pointing at the same physical directory through a symlink collapse to one write. Multi-path install/uninstall aggregate per-path outcomes — one failed destination never aborts the others, and any failure yields a non-zero exit. Per-agent pickup notes are printed to stdout after a successful install. `show` writes the raw unstamped canonical via `cmd.OutOrStdout()` (NOT `os.Stdout` — testable with `cmd.SetOut(&buf)`); it also enables `cdeploy skill show > .claude/skills/cdeploy/SKILL.md` for project-level placement.

**Stamp/hash ownership model**: install never trusts a file it did not write. `renderSkill(canonical, version)` injects a metadata block — `metadata:` header + `cdeploy-version` + `cdeploy-content-hash: sha256(canonical)` — immediately before the frontmatter's CLOSING `---` (the second `---`, found via `frontmatterCloseOffset`; never a bare `---` in the markdown body), so the frontmatter stays the first bytes of the file (Gemini silently skips otherwise). `stripOwned()` removes exactly that block, giving the round-trip invariant `stripOwned(renderSkill(canonical, v)) == canonical` as literal byte-equality; the stamped hash is therefore simply `sha256(canonical)`, no self-reference. `verifySkillFile(onDisk)` answers ONLY "is this file consistent with its OWN stamp?" → `intact` / `modified` / `unstamped` (stripOwned → sha256 → compare to the recorded hash). The install decision needs a SECOND, distinct check — `bytes.Equal(stripOwned(onDisk), canonical)` against THIS binary's canonical bytes — to reach `unchanged` vs stamp-refresh vs updated; without both checks the `unchanged` state is unreachable. Modified or unstamped files (e.g. a copy dropped by `npx skills`) are refused by both install and uninstall without `--force`; uninstall removes only the stamped `SKILL.md`, then the `cdeploy/` dir only when it is empty (never a recursive delete). Dev builds stamp `cdeploy-version: dev` — freshness keys on the content hash, not the version string.

**SKILL.md content test pins** (`skills/skills_test.go`): future edits to `skills/cdeploy/SKILL.md` MUST keep these satisfied — frontmatter is the very first bytes (`---\n` fence with a closing `---`), `name: cdeploy` (matches the directory AND the `^[a-z0-9]+(-[a-z0-9]+)*$` regex), `description` non-empty and ≤1024 chars (and naming both ops and setup triggers: deploy/servers.yml/ssh), under 500 lines, and — load-bearing — NO `metadata:` key in the canonical frontmatter. That last pin is what keeps block insertion/removal trivial: the install-time renderer owns the `metadata:` block and `stripOwned` must round-trip back to exactly the canonical bytes, so a hand-authored `metadata:` key would break the byte-equality invariant.

## Package Coupling

The TUI package depends on `runner.Composer` (interface), not `compose.Compose` or `compose.RemoteCompose` (concrete). For operations that need to create a `Composer` at runtime (e.g., project picker selecting a project), use a `ComposerFactory` callback injected from `cmd/` — this keeps `tui` decoupled from `compose`. The factory takes the whole `compose.Project`, not a directory string, so it can branch on `proj.Unmanaged` and return the read-only `compose.HostContainers` for the synthetic picker row. Similarly, `ProjectLoader` and `ConnectCallback` are injected by `cmd/` for remote server support. The `compose` package has the `HasComposeFile` package-level function for local compose file detection; project discovery (`ListProjects`) is a method on `Compose`/`RemoteCompose` requiring `Detect()` first. The `ConfigProvider` and `ExecProvider` interfaces are defined in `tui` (not `runner`) because they return `*exec.Cmd` and are TUI-only; the TUI type-asserts `composer.(ConfigProvider)` and `composer.(ExecProvider)` at runtime — no separate factory or wiring needed. `ReadOnlyComposer` is the same shape and the same reason: only `compose.HostContainers` implements it, and a composer that omits it renders the normal writable screen. `Inspector` is the same shape with the reach inverted — ALL THREE composers implement it, so the `i` key is live on every container screen and the type assert exists for test mocks rather than for a capability split.
