## Multi-project host view — grouped vs drilled, the entry model, and `svcKey`

the container screen has TWO modes and one row model. GROUPED is the host view: every compose project on the host plus the synthetic unmanaged bucket, each a foldable group. DRILLED is the single-project screen that existed before, reached by pressing `enter` on ANY grouped row (or by the local fast track). **`m.grouped` is an explicit field, never a `len(svcGroups) > 1` inference** — a host can legitimately run exactly one project and the drilled screen is always one group, so the two shapes are indistinguishable by count. **`svcGroup{proj, services, folded}` is the source of truth and `svcEntry{kind, groupIdx, name}` is DERIVED** by `rebuildSvcEntries`: one header per group then its services, a folded group contributing only its header. Never write `svcEntries` by hand — `setSingleGroup`/`setGroups` are the only writers of the pair, `clearSvcGroups` the only wipe. **A single group emits NO header at all — with ONE exception**: a lone group that is FOLDED, or that holds no services, keeps its header, because suppressing it would leave the screen with zero rows, no cursor, and no way to unfold it again (`TestRebuildSvcEntries`). The predicate is exactly `len(groups) == 1 && (folded || no services)`, and BOTH shapes are reachable: a sole project whose containers are all gone, and a folded group that outlived the other groups on the host (fold state survives the 5-second rebuild by project name). A screen with no rows also carries no name saying which project is on it, so the header is the only thing left to identify it. Otherwise the degenerate shape is what makes the drilled screen render byte-identically to what it drew before grouping existed (`TestViewSelectContainers_SingleGroupHasNoHeaderOrIndent`). The predicate behind it, `groupsHaveHeaders(groups)`, feeds BOTH the entry model and the renderer's 2-cell service indent — **not `m.grouped`**: a grouped host that happens to hold one project would otherwise indent its rows under a header that does not exist (`TestViewSelectContainers_GroupedSingleProjectHasNoIndent`). **Folding hides ROWS, never services.** `svcRefs()` walks every service in every group and deliberately ignores fold state, so selection, counting and the column-width pass go through it rather than over `svcEntries` — with ONE deliberate exception, the fold-aware `a` and its `allVisibleSelected()` toggle direction, which are covered in their own paragraphs below — the alternative drops a folded group's selected services out of the operation the user armed (`TestSelectedContainers_IncludesFoldedGroup`) and re-flows every column the moment a group closes. **Nothing may be keyed on a ROW INDEX across a rebuild**: a fold renumbers every row below it, which is exactly why `m.selected` became `map[string]bool` rather than staying `map[int]bool` (`TestSelection_SurvivesFoldRebuild`). The key producer is `svcKey(projName, service)` = `proj + "/" + service`, and `/` is safe because docker compose rejects it in both a project name and a service name, so no pair can produce an ambiguous key (`TestSvcKey_Distinctness`). Two projects on one host each owning a `db` is the common case, not the exotic one, and a bare-name map lets one silently overwrite the other (`TestQualifiedKeys_DuplicateServiceNamesStayDistinct`). **Qualified keys live ONLY inside the tui Model** — `svcStatus`, `stats`, `selected` and the render caches (`portsStr`/`cpuStr`/`memStr`) all use them — and **every message boundary converts**: `qualifyMap(projName, src)` for a drilled bare-name payload, `flattenQualified(host)` for the grouped project → service payload. Nothing qualified travels back out to `runner` or `compose`: `selectedContainers()`, `opContainers`, `rollbackTargets` and the `NewWaitState` seed all carry BARE names, pinned at the boundary by `TestQualifiedKeys_NeverCrossIntoRunner`. `ownerProjName()` names the owner of an incoming bare payload — one installed group means that group's project, with `m.projName` as the fallback for a payload landing before `setSingleGroup` has run — and `hydrateUpdates` keeps its skip-unknown-name rule, now measured in the same key space the map is stored under. The row-model helpers live in `entries.go` beside the types, not in `app.go`: `svcKeyAt(i)` (empty on a header or out of range — the OWNING group decides the prefix, never the Model's current project), `cursorEntry()`, `cursorService()` (false on a header; every "the service under the cursor" key reads it, because indexing `m.services` by `svcCursor` is wrong once headers occupy rows of their own), `cursorGroup()` (the header-accepting twin — a header IS its group, and the keys that act on a whole project are exactly the ones a header should answer), `groupUnmanaged(gi)` and `eachSelectableRef()` (`eachSvcRef` minus the unmanaged bucket). `clampSvcCursor()` is a separate helper from `fixSvcOffset()` because the grouped reload is also the periodic refresh: the row count can shrink under a cursor that was valid a moment ago, and `fixSvcOffset` only moves the WINDOW (`TestGroupedServicesMsg_ShrinkClampsCursor`). **A clamp alone is not enough, because an index is not an identity.** The grouped rows come from a live `docker ps`, so a container started or removed ANYWHERE on the host — or a project whose last container disappeared — inserts or deletes a row and slides every index below it, every 5 seconds, without a keystroke; the cursor addresses drill-in, `l`/`i`/`c`/`U` and, through the empty-selection rule, the whole-project `d`/`r`/`s`. So the grouped branch captures `svcRowID{proj, service, header}` BEFORE `setGroups` and `restoreCursorRow` looks it up after, falling back to the clamp when the row is genuinely gone — the same identity rule the fold state (project name) and the selection (`svcKey`) already use. The kind is part of the match: a single-project host emits no header at all, so a header ID must not silently land on that project's first service (`TestGroupedReload_CursorSurvivesByIdentity`, `TestRowIDAt_HeaderAndServiceAreDifferentRows`, `TestRestoreCursorRow_FallsBackToClamp`). `searchReturnID` is the same helper applied to the search bar's return cursor, which typing can move by UNFOLDING a group (`TestSearch_EscWhileTypingRestoresTheRowAfterAnUnfold`). **Every project and service name is SANITISED at ingestion — in `buildSvcGroups` and `setSingleGroup`, through `sanitizeName` (`internal/tui/entries.go`) — never at the render sites.** Both come from container LABELS (`com.docker.compose.project` / `.service`), and any `docker run --label` can set those to arbitrary bytes; the grouped screen redraws itself every 5 seconds without a keystroke, so an OSC 52 clipboard write or a CSI sequence hidden in a label would replay into the terminal on its own, and `ansi.StringWidth` counts an escape as zero cells so the clamps and the column padding pass it straight through. `sanitizeName` IS `sanitizeInspectLine` — one implementation, so the two screens cannot disagree about what is safe to draw — and applying it to the NAME rather than to the rendered line keeps the width math honest, since every consumer (header, row, breadcrumb, confirm prompt, progress title, warnings, search bar) then measures the same already-safe string. It is a no-op on anything compose itself could have produced: compose rejects every byte it strips. `m.projName`'s ONLY non-empty assignment is `drillIntoGroup`, from an already-sanitised group, which is what lets the breadcrumb, the confirm prompt and the progress title draw it without re-checking. `svcKey` sanitises BOTH halves and is idempotent, which is what keeps the `host[raw]` lookup, `qualifyMap`/`flattenQualified`, `groupCounts` and `hydrateUpdatesFor` all landing on the same key (`TestBuildSvcGroups_SanitizesLabelDerivedNames`, `TestGroupedView_NeverEmitsLabelControlSequences`). **The dedupe that follows resolves a collision in favour of the name that needed NO sanitising.** Ordering comes from the loader, which sorts RAW names, so a label crafted to sanitise onto a real project's name can sort BEFORE it: a plain first-wins dedupe dropped the real project and left the forged row — carrying an attacker-chosen `ConfigDir` — occupying the real project's display name, which is exactly what `bindProjComposer` / `drillIntoGroup` hand to the composer factory. `raw == sanitized` holds for anything compose could produce, so the authentic row always wins and only two forged rows can still race each other; the leftover pass pre-filters nothing and lets `add()` apply the same rule, so a real project the loader missed still displaces a forged claim on its name. Service names inside a group are deduped on the sanitised value for the same reason — the slice was sorted but never deduped, so one `svcKey` addressed two rows (`TestBuildSvcGroups_AuthenticNameWinsACollision`, `TestBuildSvcGroups_DedupesCollidingServiceNames`, `TestBuildSvcGroups_LeftoverRealProjectDisplacesAForgedRow`). **There is no flat `m.services` field**: `svcGroups` is the ONE representation, and its nil-versus-empty distinction carries the loading state — nil means "still loading", an EMPTY but non-nil slice is a real host with nothing on it (`TestSetGroups_NilIsLoadingEmptyIsAHost`, `TestGroupedScreen_EmptyHostLeavesLoadingState`). `hasServices()` answers the empty-list guards on the action keys and `drilledServices()` the wait fallback. `computeMatches(entries, query)` matches SERVICE entries only and returns ascending ENTRY indices (`TestComputeMatches_SkipsGroupHeaders`), so `/`, `n`, `N` and the two-stage `esc` are unchanged; **every fold and every grouped reload must re-derive `searchMatches`**, since the rebuild renumbered the rows the cached indices point at (`TestGroupedSpace_FoldRecomputesSearchMatches`).

## Multi-project host view — `HostGrouper`, the grouped loader, and the refresh dispatch

the grouped screen needs host-wide status, and asking each project for its own would cost one SSH round-trip per project on exactly the host where that hurts most. `HostGrouper` (TWO methods over ONE listing: `GroupHostStatus(ctx) (compose.GroupedHostSnapshot, error)`, whose snapshot carries a `map[project]map[service]` status map plus the opaque `compose.HostEntries` handle for the listing it was folded from, and `GroupHostStats(ctx, compose.HostEntries)`, which joins CPU/memory against that same handle and owns its own error) is declared in `tui` and type-asserted on the concrete composer, the same shape as `Inspector`/`UpdateDetailer`/`ReadOnlyComposer`. It is reached through `composerFactory(compose.Project{Unmanaged: true})` — the synthetic project the unmanaged row already used, which both `cmd/root.go` factories already branch on to build a `*compose.HostContainers` — so **no existing signature changes**: `ProjectLoader`, `ConnectCallback` and `ComposerFactory` are untouched and `cmd/root.go` needed no edit, only the pin in `cmd/root_test.go`. A factory that yields no `HostGrouper` (a test mock) is **not an error**: the loader's projects still render, with no status and no stats (`TestLoadGroups_NoGrouperIsEmptyNotAnError`). **The two halves share ONE listing but must NOT share one call.** Two self-listing methods issued the same `docker ps` twice per 5-second refresh over the same SSH hop for a byte-identical answer; folding them into one call fixed that and introduced a worse one, because `GroupHost` ran the stats leg synchronously before returning and `loadGroups` emitted a single message, so the ROW LIST was blocked behind `docker stats --no-stream`. **The one measurement, cited from here and nowhere repeated** — on a 7-container daemon: `docker compose ls -a` 0.056s, `docker ps -a` 0.033s, `docker stats --no-stream` **2.084s** — a ~0.09s first paint became ~2.2s, on every screen entry and every 5-second tick. The opaque `compose.HostEntries` handle is what buys both properties at once: `GroupHostStatus` lists and folds, `GroupHostStats` consumes the handle, so the pair is still exactly ps-then-stats (`TestHostContainers_GroupHostStats_ReusesTheListing`) while the status half makes NO stats call (`TestHostContainers_GroupHostStatus_MakesNoStatsCall`). **The handle is opaque AND STAMPED, and the stamp is the load-bearing half.** Its `entries` are unexported, so nothing outside `compose` can read, filter or re-order a listing between the two calls — but any package can write `compose.HostEntries{}`, so opacity alone was never a guarantee: the ZERO handle joined against nothing and `GroupHostStats` answered it `(nil, nil)`, which is byte-for-byte the answer a genuinely EMPTY host gives. A dropped listing and a quiet host were one blank CPU/Mem column apart with nothing red anywhere. `GroupHostStatus` therefore sets an unexported `listed` flag that only it can set, `HostEntries.Listed()` exposes it, and `GroupHostStats` REFUSES an unstamped handle with `errUnlistedHostEntries` (`TestHostContainers_GroupHostStats_ZeroHandleIsRefused`). An empty HOST still gets a stamped handle, is still accepted, and still reaches docker not at all (`TestHostContainers_GroupHostStats_EmptyStampedHandleMakesNoCall`). `GroupHostStats` owning its error is what lets the stats half fail softly on its own. The whole screen therefore costs a CONSTANT number of calls regardless of project count — `docker compose ls -a` (the `ProjectLoader`) plus one `hostPsArgs` `docker ps -a --format '{{json .}}'`, and one further `docker stats --no-stream` for the stats half. `GroupHostStatus` extracts the `com.docker.compose.project=` / `com.docker.compose.service=` label VALUES through `labelValue`, which matches **only at a token start** (the `isComposeManaged` rule) and reads the value to the next comma; **that truncation is safe for these two keys only**, because both compose names are constrained to `[a-z0-9][a-z0-9_-]*` and cannot carry a comma — do not reuse the helper for an arbitrary label key (`TestLabelValue`, `TestHostContainers_GroupedStatus_LabelValueWithComma`). Containers with no project label form the `UnmanagedProjectName` bucket; a managed container missing the SERVICE label falls back to its container name so the row stays addressable (`TestHostContainers_GroupedStatus_NameFallbacks`). Replica aggregation reuses `parseHealthFromStatus`, `formatUptime`, `parsePortsString` and mirrors `parseContainerStatus` exactly — Running is an OR, Health takes the worst case, Created the oldest replica, Uptime the longest-running one — so a scaled service reads the same in the host view as in the per-project one (`TestHostContainers_GroupedStatus_ScaledReplicas`, `TestHostContainers_GroupedStatus_RestartingReplica`). Both local and remote get it through the existing three-method `dockerRunner` seam, so there is **no new SSH plumbing** and the `SSHExtraArgs`-before-host splice is inherited (`TestHostContainers_GroupedRead_RemoteSplice`). The stats half early-returns before the stats call when the ps pass found no addressable container, mirroring `ContainerStats` for the same reason: the join would be empty by construction and `docker stats --no-stream` is the expensive half measured above, which the 5s tick would otherwise pay forever (`TestHostContainers_GroupedStats_EmptyHostSkipsStatsCall`). **The accepted gap is never-created services**: a service declared in a compose file but with no container has no row in the host view, because `docker ps` is the source. Drilling in goes through `ListServices` and shows it, and a WHOLE-GROUP operation does not inherit the gap either — an empty batch slice means "all services", resolved by compose itself. `loadGroups()` merges the loader's project list (which supplies the ORDER) with the snapshot into a `servicesMsg` carrying the ROWS plus the `hostEntries` handle — never the stats. `statsRefreshCmd()` is still nil in grouped mode, but for a new reason: the stats half needs a listing that does not exist until the status half returns, so it is CHAINED off the arrival by `groupedStatsCmd(hg, entries)` (riding `statsSession`, the counter the drilled `refreshStats` uses — the two are the same fetch in the two modes, and every context change bumps both counters together through the ONE helper `bumpFetchSessions()`) instead of batched beside `loadGroups`. **The chain takes BOTH the seam and the listing from the ARRIVAL, captured at DISPATCH — the same rule `updatesMsg.forKey` follows, never a second `m.hostGrouper()` resolution in the handler.** `m.composerFactory` is a mutable Model field and nothing forces the two resolutions to agree; the direction that disagrees (nil at dispatch, non-nil at arrival) called `GroupHostStats` on a freshly built grouper with the zero handle, i.e. exactly the confusable answer the stamp now refuses. The gate is `entries.Listed()` — every `loadGroups` failure path and every no-grouper path carries an unstamped handle, which is what makes "the cycle ends here" a property of the payload rather than of a re-resolution (`TestGroupedStatsChain_UsesTheArrivalsSeam`, `TestGroupedStatsChain_RefusesAnUnstampedListing`, `TestGroupedStatsChain_ConsumesTheArrivalsListing`). **`refreshInFlight` is therefore settled in TWO steps, under ONE rule: the arrival that ENDS the cycle clears it.** The grouped `servicesMsg` branch clears it unconditionally BEFORE its screen check, exactly as `statsMsg` does; the ONE branch that accepts the payload and chains the stats half RE-ARMS it, returning the `tea.Cmd` whose `statsMsg` clears it again. That pairing is the entire safety argument — the re-arm is the only site in the model that sets the guard outside a fetch dispatch, it is inseparable from a Cmd whose message arrives, and every other path out of the handler (stale session, off-screen, the `m.confirming` drop, `msg.err`, a factory with no `HostGrouper`) leaves the clear standing (`TestGroupedArrivals_ClearRefreshInFlight`, `TestGroupedArrival_StaleSessionLeavesTheGuardAlone`, `TestGroupedStatsChain_RidesStatsSession`, `TestGroupedFirstPaint_DoesNotWaitOnStats`). **"Arrives" is ENFORCED, not assumed: `groupedStatsCmd` runs under `context.WithTimeout(m.ctx, groupedStatsTimeout)`.** `m.ctx` is a plain `WithCancel(context.Background())` that lives for the whole program and no `dockerRunner` adds a deadline of its own, so an unbounded call left the re-arm resting on the transport: an SSH ControlMaster that wedges after `docker ps` returns but before `docker stats` does never produces a `statsMsg`, `refreshInFlight` latches true, and every later `refreshTickMsg` becomes a pure reschedule — frozen rows, no error line, no spinner, no self-heal short of a context change. Same bound, same reason, as `updateDetailsTimeout` and `pollWaitStatus`. An expiry DEGRADES to an ordinary `statsErr`: soft warning, blank cells, guard cleared, loop alive (`TestGroupedStatsChain_IsDeadlineBounded`, `TestGroupedStatsChain_TimeoutClearsTheGuard`). **The window between the two messages is also where the guard earns its keep** — the 5-second tick keeps firing while the stats half is still out, and an unguarded one would put a second host-wide `docker ps` on the wire per chain in flight (`TestGroupedChainWindow_TickMakesNoSecondFetch`). **EVERY `loadGroups` return carries `groupedPayload`, the failures included** — the flag is the message's SHAPE, not its success. On a FAILURE that message is the LAST arrival of the cycle, since there is no listing to chain off, so an error return without the flag never reached the clear: it latched `refreshInFlight` true and turned every later `refreshTickMsg` into a pure reschedule, freezing the host view on its error line for the rest of the visit with no self-heal path (`TestGroupedFetchError_ClearsRefreshInFlightAndKeepsTicking`, `TestLoadGroups_ErrorPaths`); `buildSvcGroups(projects, host, prev)` is the pure fold. **`groupedPayload bool` discriminates the two shapes rather than a nil check on either field**: a host with no projects and no containers is a legitimate grouped result whose payload fields are both empty, and it must clear the screen rather than be mistaken for a drilled load. `buildSvcGroups` takes project order from the LOADER (a map has none), keeps a project the loader reported but the host has no containers for as an EMPTY group rendering a bare header (`TestBuildSvcGroups_EmptyProjectKeepsItsGroup`), and appends the reverse case — a project in the status map the loader did not report, since `docker compose ls` and `docker ps` are two calls that can disagree — after the loader's, name-ordered with the unmanaged bucket last, so a running container is never silently invisible (`TestBuildSvcGroups_HostOnlyProjectsAppendedLast`). It carries fold state forward from `prev` by project NAME, because the group slice is rebuilt wholesale and folding is UI state the user set (`TestBuildSvcGroups_PreservesFoldState`). **A group from that leftover path carries NO `ConfigDir`**, and every write path refuses it: `operableProject(proj)` is false for a grouped, non-unmanaged project with an empty directory, `bindProjComposer` is the single refusal point (it also names `warnNoComposeDir` in the warning slot rather than going silently inert), and `armOperation` and `drillIntoGroup` check it too so the refusal lands before a prompt is armed. Without that, `compose.New("")` leaves `cmd.Dir` unset and the pipeline stops, removes and recreates whatever project cdeploy's OWN working directory resolves to — a silent wrong-target deploy on a destructive key (`TestGroupedScreen_RefusesAProjectWithNoComposeDir`, `TestOperableProject_DrilledEmptyDirIsFine`). The refusal is GROUPED-only: the drilled local fast track legitimately runs with an empty `ConfigDir`, because compose finds the file in the directory the user launched cdeploy in. `loadGroups` reuses `statusSession`: it is `loadServices`' grouped counterpart with the same lifecycle, the same context changes and the same staleness rule (`TestGroupedServicesMsg_RejectsStaleSession`). **The grouped `servicesMsg` branch is BOTH the initial load and the 5-second refresh, so — unlike the drilled branch — it PRESERVES what the user set**: cursor, selection, fold state and an active search all survive, because resetting them here would fight the user every tick; the landing sites clear that state once, on entry (`TestGroupedServicesMsg_ReloadPreservesUserState`). **A `servicesMsg` arriving while `m.confirming` is DROPPED WHOLE** — after the `refreshInFlight` clear, so the guard cannot latch. An armed prompt names a target set that the confirming `enter` resolves AGAIN, and in grouped mode this message IS the periodic refresh: a reload that pruned the selection made `partitionSelection` fall through to "the cursor's whole group", so a prompt reading `web (nginx)` deployed the entire project; a clamped cursor moved that whole-project op into a group the prompt never named; and a batch the reload introduced skipped `armOperation`'s up-front `operableProject` sweep. The tick already refuses to FETCH under a prompt (`!m.confirming`), so this only drops the fetch that was already in flight when it armed, and the next tick after the prompt closes refetches (`TestGroupedReload_IsDroppedWhileAPromptIsArmed`). **The DRILLED payload is dropped for the same reason but is REMEMBERED**, in `svcReloadPending`: nothing else reloads a drilled screen — `containerFetchBatch(false)` resolves to `refreshStatus`, and `drillIntoGroup` installs the group's rows first and dispatches `loadServices` behind them, so a `space` + `d` inside that window armed a prompt the payload then landed under — and a plain drop stranded the screen on the host-`ps`-derived subset (no never-created services, and a swallowed `loadServices` error) for the WHOLE visit. Two consumers settle it: `takeSvcReload()` at the prompt's two on-screen exits, and `containerFetchBatch`, which covers the prompt closed by CONFIRMING (that one leaves for the progress or exec screen instead of reloading, so the return from it is where the debt is paid). Grouped mode never sets the flag — its 5-second tick refetches on its own (`TestDrilledServicesMsg_ConfirmingReloadIsRedispatched`, `TestGroupedServicesMsg_ConfirmingDropIsNotRemembered`, `TestSvcReloadPending_SettledByTheReturnFromProgress`). It then re-derives `searchMatches`, prunes the selection, clamps the cursor, fixes the offset and replays the cached update verdicts — the fresh status map carries none, and nothing in grouped mode would fetch them back. Errors split by severity: a loader failure AND a host-ps failure both land in `svcErr`, since neither leaves a usable screen, while the stats half fails independently into `statsErr` on its own chained message (`TestLoadGroups_ErrorPaths`, `TestGroupedStatsMsg_FailureIsSoft`). The grouped `servicesMsg` branch deliberately does NOT touch `m.stats`/`m.statsErr`: the chained `statsMsg` owns both, and the previous cycle's cells — and its soft warning — are what the rows carry until it lands. **Do not re-add a clear.** That branch is the 5-second reload as well as the first load, so clearing either would blank the CPU/Mem column, or drop the "stats unavailable" warning, for the length of every stats call, on every tick (`TestGroupedStatusArrival_KeepsTheStatsCells`). The mode-aware dispatch is `statusRefreshCmd()`/`statsRefreshCmd()` behind ONE fan-out helper, `containerFetchBatch(initial bool)`, and **every container-screen entry goes through it** (six hand-built copies of the same five lines is how a new mode ends up wired at five of them), so the drilled path keeps the exact per-project calls it always made and no site has to remember the branch. The `refreshTickMsg` gate's `m.composer != nil` liveness check gains a grouped branch: grouped mode holds no composer BY DESIGN, so testing for one would silence the periodic refresh on exactly the screen that most needs it — what it needs instead is a FACTORY to reach the host-wide seam through (`TestRefreshTick_GroupedDispatchesHostWideFetches`, `TestRefreshTick_GroupedWithoutFactoryIsRescheduleOnly`, `TestRefreshTick_DrilledStillUsesTheComposer`).

## Multi-project host view — landing, drill-in/out, and action-time composer binding

`NewModel`'s start-screen table has three branches: servers or a config file → the server picker; no composer (no cwd compose file) → the GROUPED container screen; otherwise the drilled local fast track. `Init()` dispatches `loadGroups()` alone in grouped mode (its arrival chains the stats half) and the drilled pair otherwise (`TestNewModel_LandsOnGroupedWhenNoComposer`, `TestInit_LoadsGroupsWhenNoComposer`, `TestInit_GroupedDispatchesGroupedLoad`). **The `connectResultMsg` SUCCESS path now bumps `statsSession`/`statusSession`/`updatesSession` and resets `updateInFlight`/`refreshInFlight`, which INVERTS the rule that held while the next screen was the static project picker.** The reason the old rule existed was that the success path landed on a list that fetched nothing; it now lands on LIVE data, and the site that starts fetching a resource is the site that must invalidate whatever a previous server left in flight (`TestConnectSuccess_BumpsTheThreeCountersAndLandsGrouped`). The error path is otherwise unchanged and additionally drops the grouped rows a previous server populated (`TestConnectError_ClearsGroupedState`). **`enterGroupedContainers()` is the ONE landing body** — the connect success path, `entryLocal` with no local composer, and drill-out all call it — so the one-time reset lives in exactly one place: composer to nil, project identity cleared, rows/selection/cursor/search/wait/rollback state cleared, the four session counters bumped, `statsRequested`/`refreshInFlight` set and `updateInFlight`/`updatesErr` cleared before the load batch (`TestEnterGroupedContainers_ResetsAndBumpsSessions`). That single owner is what lets the grouped `servicesMsg` branch preserve the same state on every reload. **Grouped mode holds `m.composer == nil` deliberately**: every capability assert (`Inspector`, `ExecProvider`, `ConfigProvider`, `RollbackPreparer`, `Snapshotter`) reads nil as "not available", which is precisely the inert behaviour wanted until an action key binds one. The binding is action-time and three-part: `bindCursorComposer()` binds the CURSOR ROW's group (two projects on one screen have two composers, and the Model's own project identity is empty here), `bindProjComposer(proj)` is its addressed twin for the operation keys (a batch is decided by the SELECTION, which may sit in a group the cursor has since left), and `unbindGroupedComposer()` drops it again. Both binders are pure pass-throughs in drilled mode, so every caller can call them unconditionally and the drilled path stays byte-identical. **Every path that binds and then stays on — or returns to — the grouped screen must unbind**: the `l`/`x`/`i`/`c` early returns, the config assert failure, the confirm prompt's `esc`, all three `R` probe failures, and the progress departure. Otherwise grouped mode keeps serving one project's composer to the next row's action key (`TestGroupedScreen_ReadKeysBindTheCursorGroupComposer`, `TestGroupedScreen_RollbackNonPreparerUnbinds`). **`x` is the ONE key that keeps its binding ACROSS the confirmation prompt** (`enterExec` runs on the confirming `enter`), and that is why `readOnly()` in grouped mode reads the GROUP LIST (`allGroupsUnmanaged()`) rather than the composer: an exec prompt over an unmanaged row would otherwise flip the entire screen to the read-only variant — no checkboxes, a 7-cell caption pad instead of 10, a different footer pair and therefore a different `svcVisibleCount` — for the length of the prompt (`TestGroupedScreen_ExecBindsAcrossThePromptAndUnbinds`, `TestGroupedScreen_BoundReadOnlyComposerDoesNotFlipTheScreen`). This is the plan's "grouped mode is not globally read-only" rule made load-bearing. The predicate is not a flat `false`, though: a host whose ONLY group is the unmanaged bucket has no write key that can do anything, so it DOES get the read-only help table and footer pair — advertising `d deploy` there is the no-op the read-only variant exists to prevent, and no action-time bind can change a group list (`TestGroupedScreen_UnmanagedOnlyHostIsReadOnly`). `enter` drills in from ANY grouped row — a header IS its group, and a service row names the same group just as unambiguously (`TestGroupedScreen_EnterDrillsFromAServiceRow`, `TestGroupedScreen_SingleProjectHostCanDrillIn`, `TestDrilledScreen_EnterIsInert` — on the drilled screen `enter` belongs to the confirmation prompt). **Header-only was a bug**: a single group emits no header at all, so the very common host that runs exactly ONE compose project could not reach the drilled screen, and with it lost the never-created service rows, the automatic update scan and the project breadcrumb: `drillIntoGroup` installs the group's composer, its project identity and its EXISTING rows first, so the screen paints the project the user just picked instead of a "Loading services..." frame, then reloads through `loadServices` for full fidelity — including the never-created services the host-wide `ps` cannot see. `svcStatus` and `stats` are KEPT across the drill because their keys are qualified by project, so the drilled group's entries are already correct and the intervening frame carries live data (`TestGroupedScreen_EnterDrillsIntoProject`, `TestGroupedScreen_DrillInReloadsThroughTheGroupComposer`). `esc` drilled → grouped reuses `enterGroupedContainers()` WHOLE rather than growing a second cleanup body, because it already owns the composer, the project identity, the rows, the selection, the search, the wait state and the four counters — exactly what the site owes (`TestSelectContainers_EscDrillsOutToGroupedView`, ## Multi-project host view — fold, header aggregates, footer, and grouped rendering

`space` carries TWO meanings on the grouped screen, decided by the ROW under the cursor: a header folds its group, a service row selects, and an unmanaged row is a no-op. **Each branch calls `fixSvcOffset()` before returning** — the container dispatch clears `m.warning` above the switch, and the freed warning line grows `svcVisibleCount()` by one, so a gated key that returned without re-clamping leaves a too-large `svcOffset` and a blank row under the last service of a scrolled list. The fold branch delegates to `settleFold` — five steps now, not four: rebuild the entries, re-derive `searchMatches`, aim the cursor at the folded group's own header, clamp it, fix the offset (see the fold-keys paragraphs below) (`TestGroupedSpace_OnHeaderFoldsAndUnfolds`, `TestGroupedSpace_OnServiceSelects`, `TestGroupedSpace_OnUnmanagedRowIsNoOp`, `TestGroupedSpace_OnUnmanagedHeaderFolds`). `groupHeaderLine(gi)` draws `▼ name   ● n up  ✗ n  ⇧ n  [x] n/m`, with `▶` when folded — the aggregates are what make a FOLDED group still worth looking at. **A group that owns no services renders a BARE header**: "0 up" for a project with nothing to run reads as a fault it is not (`TestGroupHeaderLine_EmptyGroupIsBare`). `✗` and `⇧` appear only when non-zero, and the aggregates survive folding (`TestGroupHeaderLine_Aggregates`, `TestGroupHeaderLine_FoldedKeepsAggregates`, `TestGroupHeaderLine_OutOfRange`). **The `[x] n/m` selection cell is LAST on the line and draws under three conditions**: only when `n > 0`, never on the unmanaged bucket, and never on an empty group — the bare-header rule stands. Last and conditional together are what keep the cell free: a group with nothing ticked renders byte-identically to the header that existed before the cell did, so pressing `space` never shifts the aggregates left of it (`TestGroupHeaderLine_SelectionCount`, `TestGroupHeaderLine_NoSelectionRendersUnchanged`, `TestGroupHeaderLine_UnmanagedNeverShowsSelection`). The count comes from `groupSelected(g, selected)`, a SIBLING of `groupCounts` rather than a fifth return value on it: the two read different things — `groupCounts` summarises live docker state off `svcStatus`, `groupSelected` reads the UI selection the user built — and only `groupSelected` needs the unmanaged gate, which answers `(0, 0)` by the same rule `eachSelectableRef` skips those rows, since a row with no checkbox can hold no selection and a count there would advertise state that cannot exist. **The header is the ONE place a folded group's selection can be seen**, which is the whole reason the cell exists: folding hides the ROWS and never the services, so without it a selection made before a fold has no representation on screen at all (`TestViewSelectContainers_FoldedGroupShowsItsHiddenSelection` measures the SCREEN rather than the helper's return value — every other pin calls `groupHeaderLine` directly, and the rightmost thing on a row is the first casualty of anything that shortens it). The cell must not cost the list a row: the header goes through `clampToWidth` like every other line, and `TestGroupHeaderLine_SelectionCellKeepsTheRowBudget` compares the RENDER's line count with and without a selection at width 40 — comparing `svcVisibleCount()` would be vacuous, since that helper reads `m.height`, the captions, the footer and the warning slots and nothing of `m.selected`. `groupCounts` reads `svcStatus` through the qualified key and counts a service with no status entry as none of the three: the host-wide fetch reports only containers that EXIST, so a project whose containers were all removed must read "0 up" rather than inflate the total. Service rows indent 2 cells from their header off `groupsHaveHeaders(m.svcGroups)`, the caption pad adds the same `indentW` on top of its base (10 writable, 7 read-only) so the `Service` caption keeps sitting exactly above the names, and both scroll indicators carry the offset too (`TestViewSelectContainers_GroupedIndent`, `TestViewSelectContainers_GroupedScrollIndicatorsIndent`, `TestViewSelectContainers_RendersGroupHeaders`). **`svcVisibleCount` math is UNCHANGED** — a header is an ordinary row, and the count has always been in rows. Column widths are computed over `svcRefs()`, folded groups included, so folding never shifts the columns of the groups that stayed open. **Unmanaged rows render NO checkbox but KEEP its 3 cells**, so the columns stay aligned with the compose groups above and below them; every selection question goes through `eachSelectableRef()`, and the title's `(n/m selected)` denominator counts selectable rows only — counting the unmanaged containers would make `a` look like it left rows behind (`TestGroupedSelectAll_SkipsUnmanagedRows`, `TestAllSelected_UnmanagedOnlyHostIsFalse`, `TestGroupedScreen_UnmanagedOnlyHost`; that second name is unchanged, but the function it drives is now `allVisibleSelected()`). `a` alone narrows further, to the UNFOLDED groups — see the fold-aware select-all paragraph below. The footer gets a THIRD idle pair from `containerHelpLines()`: `space fold/select • <back> • ? keys` over `enter drill in • d deploy • r restart`. `space` names both meanings because it has both; `enter drill in` earns the slot `l logs` holds on the drilled screen, since a group header is the row only grouped mode has, and `l` keeps its home in the `?` overlay. **The line COUNT stays state-independent** (decided from the idle pair alone, before any search substitution) and **every rendered line is clamped with `clampToWidth` and measured with `ansi.StringWidth`**, never `len()` (`TestContainerFooter_GroupedIdlePair`, `TestContainerFooter_GroupedLineCountIsStateIndependent`, `TestContainerFooter_GroupedClampsToWidth`). In the `?` overlay, `helpContext` gained a `grouped` bit and `selectGroup(grouped)` supplies the SELECT table: `space  toggle a service · fold a group` and `enter  drill into the project · confirm the prompt`. **`enter` gets ONE row, in SELECT, and `helpGroupsFor` drops OPERATE's own `enter` row while grouped** — the drill-in is grouped-only and the confirmation is not, but one key cannot occupy two rows of one table, so the row names the pair the way `space` names its two meanings and the way `inspectGroup`'s read-only `enter` already folds the same drill-in into `confirm the exec prompt` (`TestHelpGroups_ContainerNoKeyIsNamedTwice`). The drill-in half answers on EVERY grouped row, header and service alike, so the description names no sub-state for it: restricting it to headers stranded the single-project host, which emits none (`TestGroupedScreen_SingleProjectHostCanDrillIn`). Group ORDER is unchanged (LEAVE stays 4th of 6, so `splitHelpGroups` still cuts it into the left column). The drift pin is `TestHelpGroups_GroupedNamesTheSameKeys`, which compares the grouped token set against the already-pinned writable one — **no longer a plain two-way equality**, because the fold keys below are the first grouped-only bindings on this screen; see the last paragraph of this section.

**The grouped host view lands FOLDED, and exactly once.** Three projects of eight services is 27 rows before the first keystroke, and the header aggregates — `● n up  ✗ n  ⇧ n` — ARE the host summary this screen exists to give; buried under ninety service rows they summarise nothing. `Model.groupFoldPending` is the one-shot that does it, and **it is armed at exactly TWO sites, neither of which implies the other**: `enterGroupedContainers()`, the landing body every transition goes through (connect success, `entryLocal` with no local composer, drill-out), and **`NewModel`'s own grouped branch**, which sets `m.screen`/`m.grouped` by plain assignment and runs no helper at all. Missing the second arm shipped as a review blocker rather than a cosmetic gap: a bare `cdeploy` in a directory with no compose file and no `~/.cdeploy/servers.yml` reaches the host view straight out of `NewModel`, which is precisely the launch this feature targets, and it landed fully open while every remote and drill-out path folded. `TestGroupedLanding_NewModelLandsFolded` drives `Init()`'s OWN batch rather than calling `loadGroups()` directly, because the arm is worth nothing unless the payload that consumes it is the one `Init` dispatches. **Ordering at the arm site is load-bearing**: `enterGroupedContainers()` calls `clearContainerScreen()` FIRST and arms AFTER, because the flag is row-derived state like `svcReloadPending` and that helper drops it together with the rows it names — arming above the clear is a silent no-op whose symptom (the host view lands open) is indistinguishable from never having written the feature. `drillIntoGroup()` is the one departure site that does not call the helper, so it disarms by hand. `TestGroupedOneShots_SettledAtEveryNavigationSite` pins all six sites as a table, ONE row per site covering BOTH row-derived one-shots — drill-in, `backToServerScreen()`, the `connectResultMsg` error path and the `entryLocal` fast track disarm; both drill-outs arm the fold, and the one carrying a project name also arms `groupCursorPending` (its own paragraph is in the landing section above) — so a seventh site that settles only one of the two fails here rather than in whichever of two parallel tables nobody remembered to edit, deliberately as state settled LOCALLY at each site rather than emergent from whatever `svcGroups` happens to hold, which is the same discipline the backward-navigation cleanup rule imposes on every other mutable field.

`applyPendingGroupFold()` spends the flag inside the grouped `servicesMsg` branch, positioned **between `setGroups` and everything below it that re-derives from the rows**. `setGroups` builds the entries from the unfolded state, so the fold rebuilds them again; `searchMatches` holds ROW INDICES, which a fold renumbers, and the landing payload is async, so the user can have opened the search bar while it was still in flight (`TestGroupedLanding_FoldsBeforeTheRowDerivedStateSettles`). **The one-shot is the whole point**: that branch is also the 5-second reload, so a flat "fold whenever a grouped payload arrives" re-folds every group the user opened, on every tick (`TestGroupedLanding_FoldFiresOnceNotOnEveryReload`). **A payload carrying ONE group and a payload carrying ZERO groups get DIFFERENT answers, and the split is not an optimisation.** One group spends the flag WITHOUT folding: folding a lone group leaves a single header and no rows at all, hiding the whole host to summarise one project — and spending it is what stops a host that later gains a second project from folding under an ordinary reload (`TestGroupedLanding_SingleGroupArrivesOpen`, `TestGroupedLanding_SingleGroupHostDoesNotFoldWhenItGrows`). Zero groups leaves the flag ARMED: `buildSvcGroups` always returns a non-nil slice, so an empty one is a real answer — a docker host with nothing up, or a remote box whose containers start a few seconds after the connect — and the user saw no rows, so the landing has not happened yet; the first payload that brings rows is the landing and still folds them (`TestGroupedLanding_EmptyPayloadKeepsTheOneShot`). Drill-out re-folds because it lands through `enterGroupedContainers()` like every other entry, which is the intent and not a side effect (`TestGroupedLanding_DrillOutRefolds`, `TestGroupedLanding_MultipleGroupsArriveFolded`). The fixtures carry the flag's shape too: `groupedTestModel` and `drillTestModel` clear `groupFoldPending` by hand, because they fake a screen the user has ALREADY landed on and every test built on them reads rows by index.

**Three fold keys, all grouped-only and all write-only** (`!m.readOnly() && m.grouped`, each refusal calling `fixSvcOffset()` before it returns, exactly like every other gated container key): `←` folds the cursor's group, `→` unfolds it, and `z` folds every group while any is still open and unfolds every group otherwise — the same "is anything left?" shape `a` already uses for the selection. **The arrows act on the cursor's GROUP from a SERVICE row as well as from its header**, which is the whole reason they exist: `space` folds only from the header, so closing a project the user has scrolled twenty rows into meant scrolling back up to reach it. **The arrows are DIRECTIONAL, never a toggle** — `←` only ever folds, `→` only ever unfolds — so a held key settles instead of oscillating (`TestGroupedFold_ArrowsAreDirectional`, `TestGroupedFold_LeftFoldsFromAServiceRow`, `TestGroupedFold_FoldAllTogglesEveryGroup`). They are grouped-only for the same reason `space`'s second meaning is: the drilled screen is one group and draws no header to fold. **Fold-all is `z`, not `Z`, and the case is deliberate**: uppercase on this screen marks a key that either has a lowercase sibling (`R`/`r`, `N`/`n`) or costs something (`U`, one registry round trip per image), and a fold is neither — it is free, local, and display-only, touching no container. It is NOT self-inverse, so do not justify it that way: `z` folds every group while any is open and unfolds every group otherwise, so a second press opens the host rather than restoring which groups were folded (`TestGroupedFold_FoldAllTogglesEveryGroup`). The rule is SCREEN-scoped — `screenLogs`' `G` is free and local and has no `g` sibling, so it does not follow this convention and nothing here should be generalised to it. **Uppercase `Z` must stay unbound**, and `TestGroupedFold_UppercaseZIsNotBound` asserts BOTH directions, because a `Z` re-added to the arrow case label inherits whichever branch the directional expression falls into — pinning only one of them leaves the other rebindable in silence. Its unfold-direction fixture folds EVERY group first: `foldAllGroups(anyGroupUnfolded())` reads one open group as "fold everything", so against a partly-open host a still-bound `Z` would fold, leave the already-folded group folded, and pass the assertion it exists to fail.

`settleFold` is the shared tail every fold goes through, `space` on a header included, and it is **FIVE steps rather than the four that branch used to run inline**: rebuild the entries, re-derive `searchMatches`, **aim the cursor at the folded group's own header** (`aimCursorAtGroupHeader`), clamp it, fix the offset. The aim is the new one and it is not cosmetic — closing a group from one of its service rows deletes the row the cursor was sitting on, and the bare clamp that used to follow only keeps the INDEX in range, so it silently re-aims at whichever row slid into that slot, while aiming at the FIRST header instead would jump to the top of the host every time the user closed the second project (`TestGroupedFold_AimsAtTheCursorsOwnGroupHeader` folds group two from group two's rows and asserts the cursor lands on group two's header, for `←` and `z` alike). A miss is a real state and not a bug — a lone unfolded group emits no header (`groupsHaveHeaders`) — so the clamp behind it settles the cursor instead. **A fold that changes nothing settles nothing**: `foldGroupAt` early-returns when the group already holds the requested state, because the directional keys land on an already-folded (already-open) group routinely and re-aiming the cursor at a header there would move it for a keypress that changed no row. The rest of the routing exists for narrow reasons worth keeping: `toggleGroupFold` so no caller reads `svcGroups[gi].folded` to hand back its negation, which would put an unguarded index in front of `foldGroupAt`'s own bounds check; `setAllFolded` writes the flag and rebuilds NOTHING, because its two callers settle the rows differently; `foldAllGroups` captures the cursor's group before writing; `anyGroupUnfolded` is `z`'s predicate; and `cursorGroupIdx` is `cursorGroup` by INDEX, because the fold keys WRITE the group while `cursorGroup` hands back a copy of the struct. The fold still hides ROWS and never services, so the selection survives it untouched (`TestGroupedFold_LeftFoldsFromAServiceRow`), the shrunken row list owes the same window re-clamp every cursor move does (`TestGroupedFold_ReclampsTheScrollWindow`), and `searchMatches` owes the re-derive the `space` path already ran (`TestGroupedFold_KeysRecomputeSearchMatches`).

**Every sub-state intercept the container dispatch already has applies to the fold keys, and each one is pinned rather than assumed** — a fold is not a cheap no-op, it hides rows AND re-aims the cursor. Inert on the drilled screen and on a read-only host (`TestGroupedFold_KeysAreInertDrilledAndReadOnly`, which puts each key's group into the state that makes the press a REAL change — `→` needs a folded group, `←` and `z` an open one — since a fixture already in the state the key moves it to cannot fail, gate or no gate). Literal while the search bar is open: the typing intercept sits ABOVE the key switch, so `z` stays typable into a query naming zabbix and the arrows reach the text input (`TestGroupedFold_KeysAreLiteralWhileSearching`). Swallowed behind the `?` overlay, for which `TestHelpOverlay_SwallowsEveryActionKey` grew a grouped variant that asserts the fold flags and the row count on top of the cursor and selection it already checked. Inert behind an `svcErr`, which replaces the whole list with the error screen: reshaping a list that is not on screen leaves the user unable to see what changed (`TestGroupedFold_KeysInertOnTheErrorScreen`). And inert while a confirmation is armed (`TestGroupedFold_KeysInertWhileAConfirmationIsArmed`) — the prompt names a batch that `enter` resolves AGAIN from the cursor, and a fold re-aims the cursor, so folding behind the prompt edits its target.

**An `svcErr` makes EVERY row key inert, not only the fold keys.** `viewSelectContainers` early-returns an error screen that HIDES the rows, while the groups and the selection behind it are kept ON PURPOSE: the grouped reload is also the 5-second refresh, so a transient failure must not discard fold state or a selection the user built. The dispatch therefore swallows every key but `esc` and `ctrl+c` while `m.svcErr != nil`, immediately after the `m.warning = ""` line at the top of the container case. Without it, `d`/`r`/`s` armed a confirmation the error screen has no slot to draw — the prompt is rendered by the branch the early return skipped — and the `enter` that followed ran the operation against an invisible, stale selection, on a screen whose last known state was "the host list could not be read".

**`a` is scoped to the UNFOLDED groups, and every other selection read stays host-wide. The split is the whole design.** The grouped view LANDS folded, so before this change the first `a` on a freshly connected host ticked every service on the box while the only thing that moved on screen was one digit of the title counter — a folded header renders byte-identically whether its services are selected or not, so a `d` pressed afterwards armed a plan the user had never seen. `eachUnfoldedSelectableRef` is the fix: `eachSelectableRef` minus the rows a fold hides, with **exactly two callers** — the `a` handler, through `toggleSelectAll()`, and `allVisibleSelected()`, the renamed `allSelected()`. Those two are one thing, not two: `allVisibleSelected()` is the toggle DIRECTION for `a`, so it must walk exactly what the key writes. Leaving it host-wide is not a cosmetic mismatch but a dead key — a folded group holding one UNSELECTED service makes a host-wide direction read "not all selected" forever, so every press re-ticks rows that are already ticked and nothing short of unfolding that group can clear the selection again (`TestGroupedSelectAll_SecondPressClearsDespiteAnUnselectedFoldedGroup`, whose fixture unticks a service and folds its group from that same row; `TestGroupedSelectAll_ToggleRoundTripKeepsAFoldedSelection` covers the ordinary select/clear round trip). Fold every group and the walk is empty, so `allVisibleSelected()` returns false — which costs nothing, because the `a` handler runs the same empty walk and refuses before the direction is used.

**`selectedContainers()`, `selectedCount()`, `selectableCount()` and `partitionSelection()` are deliberately NOT fold-aware, and that half is the safety guard.** A service the user selected before folding its group is still selected — a fold hides ROWS, never state (the rule `svcRefs()` has carried since grouping landed) — so scoping the reads would let an operation touch fewer services than the confirmation prompt just named, silently, with the difference sitting behind a fold (`TestGroupedSelectAll_FoldedSelectionStillReachesTheRunner`, `TestGroupedSelectAll_ConfirmPromptNamesTheFoldedSelection`, `TestSelectedContainers_IncludesFoldedGroup`). The title's denominator stays host-wide for the same reason, which makes `(2/6 selected)` after an `a` on a partly-folded host the CORRECT reading rather than an off-by-something: the numerator reports what will run, the denominator reports the host, and the gap between them is the signal that a selection reaches past the fold. The group header's `[x] n/m` cell then names which group it is in — the two changes are one feature, and neither is complete alone.

**An `a` whose fold-aware walk writes nothing REFUSES rather than going quiet**, with `warnAllSelectableFolded` — "No selectable service is visible — unfold a group to select one" — and `fixSvcOffset()` before the return, exactly like every other gated container key (`TestGroupedSelectAll_EverySelectableFoldedWarns`, `TestGroupedSelectAll_FoldedRefusalFixesTheOffset`). Silence there would only move the original invisible-selection surprise one keystroke along: the landing state folds every group, so `a` as the first key on a fresh host is the common case, not the corner. **The refusal is gated on `selectableCount() > 0`** so a host that is still loading, or genuinely empty, stays silent — it has no fold to blame — and so the DRILLED screen stays byte-identical, since `setSingleGroup` always builds an UNFOLDED group and the fold keys are gated on `m.grouped` — it can only reach an empty walk when it has no selectable row at all, which is the same condition the guard already covers (`TestGroupedSelectAll_NothingSelectableStaysSilent`, `TestSelectContainers_SelectAllDrilledIgnoresTheFoldRule`). The warning says SELECTABLE rather than visible on purpose: an unfolded `(unmanaged)` bucket can be drawing rows while every compose group is shut, so "visible" would contradict the screen, and those rows carry no checkbox anyway.

In the `?` overlay the grouped SELECT group gains two rows, `← →  fold, unfold` and `z  fold or unfold every group`, and the keys are named there and in NO footer: the grouped idle pair already carries six tokens, so a fold key could only enter it by evicting one that has no other home. `← →` reads `fold, unfold` rather than `fold · unfold` because everywhere else in these tables `·` joins two MEANINGS of ONE key (`space`, `enter`) and here two keys have one meaning each. **`TestHelpGroups_GroupedNamesTheSameKeys` is no longer a two-way equality**, and its old comment — that it existed so grouped mode needed no second hand-maintained key list — no longer holds: `← →` and `z` are the first grouped-only bindings on this screen, so the pin is now `drilled ∪ {z, left, right}` checked three ways (grouped names everything drilled names; grouped names nothing outside the union; the drilled table names none of the three). That three-name `groupedOnly` map is the only hand-maintained list left, and a grouped-only key added to the table without a binding — or bound without a row — still fails. **The two extra action rows move every truncation threshold in grouped mode**: `selectGroup` carries the `actions` flag and `singleColumnOrder` emits SELECT before INSPECT, so the grouped table stacks to 28 rows with 21 action rows against the drilled 31/26/19, and its single-column HEIGHT thresholds sit exactly two notches higher — full fit at 26, `U check updates` lost at 25, then `x`, `c`, `i`, `l`. `TestViewHelp_InspectSurvivesTheFirstTruncation` now measures BOTH variants and pins the notch from both sides (the full-fit height keeps every action row; one line below it loses exactly `check updates`), so a moved threshold fails instead of drifting. The grouped column was UNMEASURED and UNPINNED before this change — do not extrapolate one variant's numbers from the other's. **The grouped WIDTH threshold is the one that bites**: the container `pgup pgdown` row later took it from 77 to 87 columns (drilled only went 65 → 70), so at 77-86 columns and height 24 — 80x24 included — the grouped overlay stacks and drops its last two action rows, `x exec` and `U check updates`, which no footer carries. That gap is accepted and recorded in full in `docs/architecture/tui-help-overlay.md`; it also moved the grouped column cut, so LEAVE now renders at the top of the RIGHT column here while the drilled table keeps it left. **The grouped SELECT row for `a` reads `all visible` rather than `all`** — grouped `a` is scoped to the unfolded groups, and the drilled table keeps the bare word because that screen has no fold and the qualifier would name a distinction it cannot make (see the fold-aware select-all paragraphs above). It is a DESCRIPTION-only change, so `TestHelpGroups_GroupedNamesTheSameKeys` — a TOKEN-set pin — cannot see it, and it moved none of the numbers in this paragraph: rows are clamped and never wrapped, so no row count moved, and at 11 cells `all visible` is nowhere near the left column's widest description (`drill into the project · confirm the prompt`), so none of the four two-column thresholds and none of the truncation heights moved either.

## Multi-project host view — batch partitioning and the sequential progress pipeline

`opBatch{proj compose.Project, services []string}` is one project's share of an operation, and **an EMPTY services slice is not "nothing"** — the runner reads it as ALL services, resolved by compose itself, which is the only way a whole-project batch can reach a service that was never created. `partitionSelection()` walks `svcGroups` in SCREEN order, so the batches run top to bottom, which is the order the confirmation prompt names them in (`TestPartitionSelection_OrderedByScreenPosition`). The unmanaged bucket never enters a batch: its rows have no compose project behind them, and its keys cannot reach `m.selected` anyway (the space handler refuses them), so the skip is the second half of one rule rather than a duplicate check (`TestPartitionSelection_UnmanagedNeverEntersABatch`). An empty selection resolves to ONE batch — the cursor's group with an empty slice — and a cursor on the unmanaged bucket or on no row at all yields NO batch, which callers report as "nothing selected" (`TestPartitionSelection_EmptySelectionIsTheCursorGroup`, `TestPartitionSelection_WholeGroupBatchCarriesNoServices`, `TestGroupedScreen_UnmanagedCursorHasNoOperation`). **The empty-selection rule applies in GROUPED mode only.** `partitionSelection` implements it unconditionally because it is a pure row-model rule, but `armOperation` keeps the drilled screen's long-standing `warnNoSelection` guard: a project's whole service set is one keystroke away there (`a`), so an unselected `d` has always meant a mistake rather than "deploy everything", and reinterpreting a destructive key is a semantic change no requirement asked for (`TestWarning_ShownWhenNoSelection`). **The composer binds at the confirming `enter`, not at the `d`/`r`/`s` press** — unlike `x`, which must keep it across the prompt. Nothing that changes the partition can happen while the prompt is armed, so the prompt RECOMPUTES rather than captures, which is what keeps `opBatch` off the Model and out of the departure-site cleanup list (`TestGroupedScreen_ConfirmBindsTheBatchComposer`). **That invariant covers KEYS, and messages had to be made to obey it too**: every key but `enter`/`esc`/`ctrl+c` is swallowed, but the grouped `servicesMsg` is the 5-second refresh and arrived on its own schedule — so the handler now DROPS any `servicesMsg` that lands while `m.confirming` (see the loader section above). The prompt names the batches through `formatBatchTargets` — `deploy web (nginx, api) → db (all)?` — and spells a whole-group batch `(all)`, which is what keeps it honest about how much the operation touches; it is clamped to one physical line, because a batch list grows with the number of projects it names and a wrapped prompt would overflow the row `containerFooterLines` reserved (`TestGroupedScreen_ConfirmPromptNamesTheBatch`, `TestGroupedScreen_ConfirmPromptClampsToWidth`, `TestFormatBatchTargets`). `enterProgress(batches)` builds the step rows for EVERY batch up front, so the screen shows the whole plan from the start instead of growing a project at a time. **`stepState` gained `label`, not a renamed `name`**: `name` stays the RUNNER step name that a `StepEvent` is matched against, `label` is what the screen draws and carries the `"web: "` prefix only when `len(batches) > 1`. `enterProgress` always sets BOTH; a hand-built fixture goes through the `progressStep(name, status)` helper rather than relying on a fallback in production code. **Each batch gets its OWN events channel**, because `runner.Run` defer-closes the channel it is given: a shared one would close after the first batch and report the whole sequence done. **`handleStepEvent` resolves an event inside the CURRENT batch's step range**, `currentStepRange()` = `[batchIdx*batchStepCount, +batchStepCount)`, never by a global name scan — `runner.Steps` returns the same five names for every batch, so a scan would land on batch 0's `Pulling` forever (`TestBatchSequence_TwoBatchesRunInOrder` uses SHARED step names precisely to pin this). `enterProgress` is the only producer and always sets `batchStepCount` to `len(runner.Steps(op))`, which is never zero, so there is no zero-count fallback to carry: a hand-built fixture sets it too, through `progressStep()` (`TestBatchSequence_SingleBatchEquivalence`). `markBatchesSkipped(from)` starts at batch `from`, so **a single-batch failure skips NOTHING** — the failed batch's own unreached steps stay `○`, byte-identical to today's rendering; only the batches BEHIND the failure are marked, because they are the rows a reader would otherwise take for "still to come" (`TestBatchSequence_FailureStopsSequence`). `stepEventMsg`, `pipelineDoneMsg` and `batchDoneMsg` ALL carry `batchIdx` + `batchSession`, captured at DISPATCH time (in `waitForEvent` and `batchDone`), and each handler applies THREE gates: screen, session, index (`TestBatchSequence_RejectsStaleBatchIndex`, `TestBatchWait_StaleBatchDoneRejected`, `TestStepEvent_StaleEventNeverLatchesFailed`). **`stepEventMsg` needs the identity as much as the other two.** Its channel read BLOCKS, and the esc-cancel below marks the screen terminal immediately — so the second `esc` navigates away while the cancelled step's `StatusFailed` is still in flight. Ungated, `handleStepEvent` latched `m.failed` on whatever screen that straggler landed on, and the NEXT operation started from there inherited it: `viewProgress` drew "q back" over a live pipeline, the spinner froze, and `pipelineDoneMsg` returned early on `m.failed`, so the health gate never opened and no batch past the first ever ran. `enterProgress` resets `done`/`failed` as defence in depth (`TestEnterProgress_ResetsTheVerdict`). **`batchSession` is bumped at INVALIDATION sites only — never in `enterProgress`.** It starts at 0, so a zero-valued `pipelineDoneMsg{}` still resolves against a fresh sequence, which is what keeps the existing hand-driven `Update(pipelineDoneMsg{})` pins driving the handler instead of being dropped by their own gate. The two bump sites are the `esc`-cancel and `clearBatchSequence()` at every progress departure (`TestBatchSequence_DepartureClearsSequence`). `esc` mid-sequence cancels the current batch's context, bumps the session — the cancelled batch is still going to close its channel, so its `pipelineDoneMsg` is already on the way — and marks the rest skipped (`TestBatchSequence_EscDoesNotAdvance`). **It also sets `m.failed`.** Resolving the screen and stopping the sequence are two different decisions: the session bump invalidates the very `pipelineDoneMsg` that used to set `m.done`, so a cancel landing after the last step succeeded left `done` and `failed` both false — `esc` re-cancelled, `q` was a no-op and `ctrl+c` fell through to the viewport, and only an external kill recovered (`TestEscCancel_LeavesATerminalState`). The mid-op `q`/`ctrl+c` no-op rules hold while a PIPELINE runs (`TestProgressRunning_QAndCtrlCStayInert`), but **not during an open health gate**: a mid-sequence gate opens with `done` and `failed` both false, so both guards read `m.waiting` as terminal-enough — `q` rewrites to `esc`, which STOPS a mid-sequence gate (and is the plain skip on the last batch), `enter` skips the wait, and `ctrl+c` goes through `tryQuit()`. Otherwise the `?` overlay's WAIT group advertised two dead keys for up to one wait timeout per batch (`TestProgressWait_QAndCtrlCAreLiveMidSequence`). The Deploy snapshot is PER BATCH, taken inside the batch goroutine before `runner.Run` touches anything (pre-Stop ordering, best effort, `Snapshotter` type-asserted), so a two-project deploy records two state files. **`R` captures the batch's PROJECT alongside `rollbackTargets` at press time (`m.rollbackProj`), and the confirming `enter` builds its batch from it.** `m.currentProject()` is the ZERO project in grouped mode, so the batch carried no name for the progress breadcrumb and the post-success invalidation deleted `"|<server>"` instead of the rolled-back project's key (`TestGroupedRollback_BatchCarriesTheCapturedProject`); it clears at every site that clears `rollbackTargets`. **`startBatch` does NOT rebind the composer for `Rollback`**: `R` bound it at press time (the snapshot fetch already needed one) and the prep validated the captured targets against it, so rebinding from the batch's project would risk swapping it under a capture the selection has since drifted from — **unless the composer is nil**, which is a state `U` and every `l`/`x`/`i` refusal can produce by calling `unbindGroupedComposer()` while the snapshot read is still out. The batch's project IS `m.rollbackProj`, captured at R-press, so a rebind from it can drift nowhere; without it the prep failed with "rollback is not supported for this connection", which names the wrong cause entirely (`TestGroupedRollback_StartBatchRebindsALostComposer`). Update-cache invalidation after a Deploy/Restart/Rollback walks `projUpdatesCacheKey(b.proj)` for every batch that FINISHED — a sequence touches projects the container screen has since left, and the batch at `m.batchIdx` counts when its OWN PIPELINE ran to the end, not when the operation succeeded. `currentBatchPipelineRan()` reads every step of `currentStepRange()` for `StatusDone`: a mid-sequence batch that passed every step and then failed its HEALTH GATE pulled its images all the same, so keying the test off `m.done` — which only the last batch sets — left its `⇧` glyphs stale for the full 10-minute TTL. A batch with an unreached, running or failed step did not pull, and keeps its cache, which is the "a failed deploy must not clear user-visible state" rule (`TestEscFromProgress_InvalidatesTheBatchesThatFinished`, `TestEscFromProgress_InvalidatesABatchWhoseGateFailed`). Keying the whole thing off `m.done`, which only the LAST batch sets, left an earlier successful batch's glyphs stale for the full 10-minute TTL (`TestBatchSequence_InvalidatesEveryBatchCacheKey`, `TestEscFromProgress_InvalidatesTheBatchesThatFinished`). `viewProgress` WINDOWS its step list: the plan is built for every batch up front, so a five-project deploy emits 25 rows and bubbletea keeps only the LAST `m.height` lines — an unwindowed render dropped the title and the running batch off the top. `progressStepWindow(total, rows, hi)` keeps `currentStepRange()` on screen and shows as much finished work above it as fits, with `▲ N more`/`▼ N more` markers. **It anchors on `hi`, the running batch's LAST row, never on its first**: pulling `start` back to the batch's head showed a too-tall batch's opening steps while the step actually running scrolled off the bottom of a short terminal (`TestProgressWindow_TallBatchKeepsTheRunningStep`); `m.height == 0` means unbounded, the same backward-compatible rule `svcVisibleCount` keeps (`TestProgressWindow_KeepsTheRunningBatchOnScreen`, `TestProgressStepWindow`). Its title stopped reading `selectedContainers()` unconditionally: that is empty for a whole-group op, so grouped mode reads `m.opContainers` with an `all services` fallback and a multi-batch sequence repeats `formatBatchTargets(m.batches)`; the drilled title is untouched (`TestGroupedScreen_ProgressTitleNamesTheTarget`, `TestBatchSequence_ProgressTitleNamesEveryBatch`). **That title is clamped to `m.width`**: `formatBatchTargets` grows with every project and service a sequence names, and the row budget is computed from `strings.Count(head, "\n")` — a title the TERMINAL wrapped adds physical rows the count cannot see, so the window it just sized overflowed the screen (`TestViewProgress_TitleIsClampedToWidth`).

## Multi-project host view — the per-batch health gate

every batch runs its OWN `--wait` gate against its OWN composer, which is what makes a two-project deploy stop at the project that came up broken instead of dragging the next one down with it. **`pipelineDoneMsg` OPENS the gate; `batchDoneMsg` — not `pipelineDoneMsg` — RELEASES the next batch.** That split is the whole point of the second message: a batch's pipeline closing its channel no longer means the batch is over. The test harness follows it — `drainBatch` is now `drainPipeline` + `resolveWaitPhase` — so every sequence test drives the gate as well as the pipeline. The target set is the batch's own service slice in BARE form (qualified keys never reach the reducer). An EMPTY slice is the runner's "all services", which the reducer cannot evaluate, so it is resolved per mode: **drilled mode falls back to `m.services`, grouped mode must NOT** — `m.services` is host-wide there, so seeding one project's composer with another project's services is a guaranteed timeout. Grouped mode asks the batch's composer through `ListServices` instead. **`waitTargetsMsg` is a SECOND message, not a widened `waitStatusMsg`**, because the reducer needs the names seeded BEFORE the first poll is evaluated; `m.waitState` stays empty (the header renders with no rows) for the one frame in between (`TestBatchWait_WholeProjectBatchResolvesTargetsViaListServices`, `TestBatchWait_EachBatchWaitsOnItsOwnServices`, `TestBatchWait_StaleTargetsRejected`). **An unresolvable target set SKIPS the gate rather than failing it**: a `ListServices` error names no health verdict, so it is not a health failure — the gate closes and the sequence continues (`TestBatchWait_UnresolvableTargetsSkipTheGate`). In the TUI the wait is advisory for the same reason `esc` can skip it by hand. `waitPhaseResolved()` decides what a finished gate means: a passing gate releases the next batch, a failing one stops the sequence exactly as a failed pipeline step does (`m.failed` + `markBatchesSkipped`), and **the LAST batch takes NEITHER branch** — today's single-project screen renders a failed wait as red verdicts plus the rollback hint over a `done` operation, not as a failed op, and that is preserved (`TestBatchWait_FailureStopsSequence`, `TestBatchWait_LastBatchFailureKeepsDoneState`). **`esc` on a MID-SEQUENCE gate STOPS the sequence; `enter` RELEASES the next batch.** The gate is where a multi-project deploy spends most of its wall clock (one `DefaultWaitTimeout` per batch), so it is where a user who wants to abort is sitting — and `esc` is the abort key everywhere else on this screen, so releasing the next batch from it meant the universal abort key launched a whole project's stop → rm → pull → create → start under a footer that called it "skip health wait". `esc` there spells the stop exactly the way a FAILING gate does — `m.failed`, `markBatchesSkipped(m.batchIdx+1)` and a `batchSession` bump to discard a `batchDoneMsg` already on its way — so the batches behind it read `(skipped)` and the next `esc` navigates back (`TestBatchWait_EscStopsTheSequence`). `enter` carries the old meaning, and on the LAST batch there is nothing to release so both keys are the plain skip that leaves the op "done" (`TestBatchWait_EnterReleasesTheNextBatch`, `TestBatchWait_EscSkipOnLastBatchReleasesNothing`). `midSequence()` is the ONE predicate behind the footer's two-outcome line and the `?` overlay's two-row WAIT table (`TestViewProgress_MidSequenceGateNamesBothOutcomes`, `TestHelpGroups_ProgressWaitingMidSequence`). A stop must not strand the sequence with no terminal state and no way out; `batchFinished()` remains the shared release path for every no-gate case — `StopOnly`, an unresolvable target set, and `enter` (`TestBatchWait_EscSkipOnLastBatchReleasesNothing`, `TestBatchWait_StopOnlyAdvancesWithoutAGate`). `progressPhase()` still resolves `waiting` FIRST and must keep mirroring `viewProgress`'s footer switch, but **the REASON changed**: "waiting implies done" stopped being true when a mid-sequence gate opened with `done` false, so the rule now reads — a gate can be open with `done` set (the last batch), with `failed` set, or with neither, and only the waiting-first order names `esc` correctly in all three. The `batchDoneMsg` handler cancels the finished batch's context before the next batch takes over `m.cancel` (which `esc` reads), then calls `clearWaitState()` — **which also nils `opContainers`, so its order against `startBatch` re-setting it is load-bearing** — then advances `batchIdx` and starts the next batch. `batchSession` still bumps at invalidation sites only, so a zero-valued `batchDoneMsg{}` resolves against a fresh sequence exactly as `pipelineDoneMsg{}` does. `runRollbackCleanup` and the departure cleanup (`clearWaitState`, `waiting`, `waitDeadline`, `clearBatchSequence`) run when LEAVING `screenProgress`, on the main goroutine — **never goroutine-deferred**, per the rollback cleanup timing rule (`TestBatchWait_DepartureRunsCleanupAndClearsWait`, `TestEscFromProgress_InvokesRollbackCleanupOnce`, `TestEscSkipDuringWait_DefersRollbackCleanup`).

## Multi-project host view — updates in grouped mode

**No automatic update scan fires in grouped mode.** `autoUpdatesAllowed()` is `!m.readOnly() && !m.grouped`, and `maybeRefreshUpdatesCmd` ALSO early-returns on `m.grouped` before the cache lookup — and **before the `updateInFlight` guard**, because the grouped branch schedules nothing, so the guard has nothing to protect there while the one thing the branch does do was being skipped for the whole life of a `U` scan (`TestMaybeRefreshUpdates_GroupedExpiresErrWhileAScanIsInFlight`). Its one job there is `syncGroupedUpdatesErr()`, which RE-DERIVES the soft warning from the visible groups' cache entries — dropping one whose failure entry has expired AND restoring one the current group list still justifies. **The restore half is not symmetry**: `U` is the only trigger in grouped mode and the three landing sites (`enterGroupedContainers`, `drillIntoGroup`, `backToServerScreen`) all blank `m.updatesErr` on the way through, so an expire-ONLY form — which early-returned on an already-empty field — left a failed `U`'s warning gone for good after an ordinary drill-in and `esc`, with that group's glyph column blank and nothing on screen explaining why for the full 30-second error TTL (`TestGroupedUpdatesErr_ExpiresWithItsCacheEntry`, `TestGroupedUpdatesErr_RestoredOnTheGroupedPayload`). The grouped reload calls it too, which is what makes it both the age-out and the restore. **A SUCCESSFUL scan clears the warning the same way, not flat**: a scan covers ONE group, so `updatesErr = ""` erased a still-unexpired failure belonging to a different one, and grouped mode would never put it back. Both sites read one derivation, `groupedUpdatesErr()` (`TestUpdatesMsg_GroupedSuccessKeepsAnotherGroupsWarning`) — grouped mode owns neither the single cache key that helper looks up nor the single composer a detail refill would fetch through, so `updatesCacheKey()` there would resolve to whichever project was drilled last. All THREE automatic entry points refuse (`maybeRefreshUpdatesCmd`, the `statusMsg` self-heal, `Init()`'s fast path), and `NewModel` seeds `updateInFlight` from the same predicate rather than a flat `true` — a `true` with no fetch behind it never clears, and the guard would then refuse every later fetch including `U`'s (`TestGroupedMode_AllAutoScanEntryPointsRefuse`, `TestGroupedInit_FiresNoUpdateScan`, `TestGroupedMode_NoAutomaticUpdateScan`). The cost rationale is the unmanaged one squared: a compose project bounds `CheckUpdates` to one service list the user is actively managing, while a host view fans out across EVERY project at once, each distinct image costing a local inspect plus up to two registry manifest requests — enough to exhaust the anonymous Docker Hub quota and break a real `docker pull` from the same host. **`U` is the only trigger, and it scans the CURSOR row's group only.** The composer is bound, read out and unbound in the SAME keystroke, so grouped mode never holds one project's composer while the cursor sits on another's row; the in-flight guard is checked BEFORE the bind, so a refusal leaves the composer exactly as it found it (`TestGroupedU_ScansCursorGroupOnly`, `TestGroupedU_InFlightGuardBindsNothing`). **`updatesMsg` gained `forKey`, captured at DISPATCH, and the handler must NEVER re-derive it.** The cursor is free to move — or fold a group — while a scan runs, so a handler-time re-derive files one project's verdicts under another project's key: the wrong glyphs paint and the scanned project looks unchecked (`TestGroupedU_ForKeySurvivesCursorMove`). The key itself comes from `projUpdatesCacheKey(proj)` = `proj.ConfigDir + "\x00" + proj.Name + "|" + serverName`, carrying the `unmanaged|` prefix off `proj.Unmanaged`. **BOTH project halves are in it and neither alone would do**: the directory does not identify a project — `docker compose -p a` and `-p b` in one tree are two projects with two container sets, and on `ConfigDir` alone they shared one entry, so one project's verdicts painted onto the other's rows and its own scan was suppressed for the whole 10m TTL — while the name does not identify one either, because a group `buildSvcGroups` synthesised from the host status map has no `ConfigDir` at all and two hosts can run the same project name from different trees (`TestProjUpdatesCacheKey_DirlessProjectsStayDistinct`, `TestUpdatesCacheKey_NamedProjectsInOneDirStayDistinct`). NUL is the separator because no filesystem path and no docker project name can contain it, so no (dir, name) pair can spell another pair's key; `updatesCacheKey()` is now literally `projUpdatesCacheKey(m.currentProject())`, so the two producers cannot drift — **the same string `updatesCacheKey()` produces once drilled into that project**, so one cache entry is shared between the two modes and a scan started from the host view still counts after drill-in (`TestGroupedUpdates_DrillInReplaysCachedEntry`, `TestGroupedU_UnmanagedGroupKeepsCachePrefix`). **`reapplyUpdateVerdicts(results)` replaces the two clear-then-hydrate blocks in the `updatesMsg` handler.** The drilled rule is "the message is the whole truth" — clear every verdict, then hydrate from the message — but a grouped scan covers ONE group, so that would blank every group the scan did not cover, on the success path AND on the error path, where the untrusted-map contract binds only the failed project (`TestGroupedU_SecondScanKeepsFirstGroupsVerdicts`, `TestGroupedU_FailureBlanksOnlyItsOwnGroup`). Grouped mode therefore re-reads the verdicts from the CACHE, per group, through `hydrateGroupedUpdates()`. **Those cache reads are RAW — deliberately not the TTL-checked `updatesCacheLookup`.** Grouped mode never refetches on its own, so a TTL-gated replay would blank the glyph column ten minutes after a scan with nothing queued to bring it back; the age of the check is reported on the inspect screen instead. Error entries are skipped (their results map is nil and their verdicts are untrusted by contract). The replay runs on every grouped reload, i.e. every 5 seconds, which is what keeps a `U` scan's glyphs alive across the periodic refresh (`TestGroupedUpdates_SurviveAPeriodicReload`). `groupCounts` gained the header's `⇧ n` as a THIRD return value rather than a second helper: the header reads the same tri-state the row glyph draws, so a nil verdict counts as zero and nothing on the header path can trigger a scan (`TestGroupedHeader_ShowsUpdateCount`). **Grouped mode fetches NO inspect detail rows, and the gate is the MODE, not the nil composer**: `updateDetailsCmd` reads `m.composer`, which an armed `x` prompt may have left bound to a DIFFERENT project than the scan covered, so a batch built from it would spend registry round-trips resolving the wrong project's images. The entry keeps `details == nil`, which is exactly the state `refillUpdateDetailsCmd` fills the moment the user drills into that project — the rows are deferred, not lost (`TestGroupedU_FetchesNoDetailBatch`). `inspectUpdateKey()` resolves the cursor row's group key so `i` from a grouped row reads the right entry; **it is read at RENDER time, not captured on entry**, because the cursor cannot move while the inspect screen is up — equivalent to a captured field, without adding one more field to the departure-site cleanup list (`TestGroupedInspect_ReadsCursorGroupEntry`). **`redrawInspectFromCache()` is gated on `inspectUpdateKey()`, NOT on `updatesCacheKey()`** — grouped mode holds no project identity, so `updatesCacheKey()` resolves to the degenerate `"\x00|<server>"` and never equals the batch's key: a detail batch landing while the inspect screen was open repainted nothing, and the rows appeared only after `esc` and a second `i` (`TestUpdateDetailsMsg_RepaintsTheGroupedInspectScreen`). **`refillUpdateDetailsCmd` carries its own `m.grouped` refusal**, rather than relying on its call sites: the `updateDetailsMsg` arrival tail runs on EVERY screen and cannot check, so without the guard a refill in grouped mode resolved the degenerate key and — whenever any composer happened to be bound (open inspect/config, armed `x` prompt) — fetched one project's details into another project's entry and raised `detailsInFlight` for it (`TestRefillUpdateDetails_RefusesInGroupedMode`).
