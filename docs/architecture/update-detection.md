## Update detection — tri-state and Composer contract

`runner.ServiceStatus.UpdateAvailable *bool` is a tri-state: `nil` = unknown / not checked / build-only / error (blank cell), `*v == true` = a newer image exists in the registry (yellow `⇧` glyph, U+21E7), `*v == false` = current. `Composer.CheckUpdates(ctx, services) (map[string]bool, error)` returns only services that were *checked* — absent keys preserve the tri-state's nil for build-only services and per-image errors. When a non-nil error is returned, the accompanying map is *untrusted* — implementations may return a partial map (RemoteCompose does, with whichever services completed before the transport-fail abort), but partial verdicts may be inconsistent with unresolved services. Soft-failure consumers (CLI list, TUI) discard the map (`updates = nil`) and render all-blank-plus-warning rather than mixing partial verdicts with unresolved services. Local impl in `internal/compose/updates.go`; remote in `internal/compose/remote.go`; unmanaged-host impl in `internal/compose/hostcontainers.go` (which returns a partial map on a transport abort too, since its remote runner emits the same `errSSHTransport` sentinel). `compareImageDigest` returns `(updated, ok, err)` on both sides (3-tuple, kept symmetric) so empty-digest cases are distinguishable from positive verdicts without polluting the cascade counters with synthetic errors.

## Update detection — digest comparison

implementation always uses per-image digest comparison: `docker compose config --format json` for service→image mapping on the two compose paths (compose subcommand → goes through `command()`/`remoteCommand()`; `HostContainers` instead reads the `Image` field `docker ps` already returned, since there is no compose file), then `docker image inspect --format '{{range .RepoDigests}}{{println .}}{{end}}'` for the local digest and `docker buildx imagetools inspect` (preferred, default human format) or `docker manifest inspect --verbose` (fallback) for the remote digest. The buildx-first path is the **multi-arch fix**: `image inspect` returns the manifest-LIST digest for multi-arch images (because docker pulled via the list), and `imagetools inspect`'s top-level `Digest:` line is also the manifest-list digest — they match correctly. The legacy `manifest inspect --verbose` array form returns per-platform descriptor digests that never match a manifest-list digest (false positives on popular Docker Hub images like nginx/postgres/alpine/node/redis). `fetchRemoteDigestVia` (package-level, over the `dockerRunner` seam — the two per-composer `fetchRemoteDigest` methods it replaced no longer exist) tries imagetools first and falls back to manifest inspect whenever imagetools yields no valid digest — either a non-transport FAILURE (older Docker without the buildx plugin) or a call that SUCCEEDED whose output the strict parser rejects; SSH transport failures propagate immediately to abort the batch instead of retrying the same broken transport against a second endpoint. **IMPORTANT regression pin**: do NOT add `--format '{{.Manifest.Digest}}'` back to `imagetoolsInspectArgs` — empirically verified on Docker 29.1.3 / buildx v0.30.1-desktop.1 the template substitution silently falls through and the command prints the same default human-readable Name:/MediaType:/Digest:/Manifests: block as no format flag. A permissive "first non-empty line" parser would then return `Name:      docker.io/library/nginx:latest` as the "digest" → universal false-positive (every image flagged as updated). `parseImagetoolsDigest` extracts the top-level `Digest:` line (skipping indented per-platform digests under `Manifests:`) and validates against a strict `sha256:<64 hex>` regex (`imagetoolsDigestRE`); anything else returns empty so the manifest-inspect fallback engages. There is no defensive "bare sha256 line" fallback — aborting on the first non-matching line means any wrapper that prints a leading banner (e.g. a `motd`-injecting docker context) silently defeats it; every real buildx output we've observed exposes the digest on the primary `Digest:` line. Test fixture lives at `internal/compose/testdata/buildx_imagetools_default_output.txt` — a real `hello-world` capture exercised by `TestParseImagetoolsDigest_RealFixture` — and the parser's negative cases pin the `Name:` line, short non-hex, and wrong-length-hex rejections so the regression cannot be reintroduced. `parseLocalDigest(out, imageRef)` filters `RepoDigests` to the entry whose repo matches the compose-file image reference (stripping tags via `stripTag`); falls back to the first non-empty digest when no repo matches. `parseManifestDigest` extracts `Descriptor.digest`. All three (`docker image inspect`, `docker buildx imagetools inspect`, `docker manifest inspect`) **bypass `command()`/`remoteCommand()`** because they are top-level docker commands, not compose subcommands. Local Compose uses `runDockerCmd` (captures stderr explicitly via `strings.Builder`, mirroring the SSH path) and `RemoteCompose.runRemoteDockerCmd` builds the SSH argv directly and splices `SSHExtraArgs` immediately before the host arg (matching `AllContainerStatsRemote`/`EditCommand`/`ExecCommand`); image names are `shellEscape`d. The shared rune is `compose.UpdateGlyph` (alongside `FormatBytes`) so the TUI and CLI render the same character from a single source. The `docker compose pull --dry-run` path was explored and rejected: with `--policy=always` every non-build service reports "Pulling" regardless of currency; with `--policy=missing` the signal is "image present locally" rather than "image current in registry". The manifest-inspect/imagetools path is the single authoritative implementation.

## Update detection — SSH transport classification (RemoteCompose only)

`runRemoteDockerCmd` captures stderr explicitly (so test hooks producing non-`*exec.ExitError` errors still surface diagnostic context, and so classification works uniformly) and runs `classifySSHError(err, stderr)` which checks stderr against `sshTransportStderrPatterns` (case-insensitive substring match on SSH-only signatures: `ssh:`, `ssh_exchange_identification`, `could not resolve hostname`, `kex_exchange_identification`, `permission denied (publickey`, `control socket connect`, `port forwarding failed`, `lost connection`, plus ControlMaster failure modes `mux_client`/`client_loop`/`controlsocket`/`multiplex`/`session open refused`). Generic networking phrases like `connection refused`/`connection reset`/`broken pipe`/`no route to host` are deliberately NOT in this list — they ALSO appear in docker daemon stderr when docker fails to reach the registry, and classifying them as SSH transport would abort the entire CheckUpdates batch even though other images would have succeeded; the registry cascade below handles those instead. Transport matches are wrapped in the `errSSHTransport` sentinel; everything else is treated as a per-image docker failure and just gets the stderr appended for diagnostic context (mirroring `withStderr`). Tests can drive `classifySSHError` with explicit stderr via `RemoteCompose.SetOutputErrHook(func(*exec.Cmd) ([]byte, string, error))` — prefer this over `SetTestHooks` when the test cares about transport-vs-per-image classification; the legacy `outputCmd` path now passes empty stderr to the classifier (was: err.Error()-as-stderr) so production and test paths can't diverge. `CheckUpdates` then asymmetrically handles the two buckets: an `errSSHTransport` from ANY per-image call aborts the batch immediately with `"remote update check transport failure: <err>"` (return early — every subsequent call will fail the same way); a per-image docker failure (image not pulled, manifest auth required, registry 404) is absorbed into the tri-state "absent" cell, matching local Compose behaviour. Fresh-deploy single-service projects do not trigger a false cascade just because the image hasn't been pulled to the remote yet — `No such image` is a normal `docker image inspect` exit-1, not a transport failure.

## Update detection — systemic-failure cascades

`Compose.CheckUpdates` runs TWO parallel cascades so the soft-failure consumer sees a real diagnostic instead of an empty map. (1) **Registry cascade**: when `networkFailures == remoteAttempts > 0` AND `len(out) == 0`, returns `fmt.Errorf("registry unreachable: %w", firstNetErr)`. `looksLikeNetworkErr` matches `no such host` (canonical net.DNSError tail), `connection refused`, `dial tcp`, `x509:`, `too many requests`, `timeout exceeded`, etc. — patterns specific enough to avoid over-firing on per-image fragments. (2) **Local-docker cascade**: when EVERY local `docker image inspect` fails AND every failure ALSO matches `looksLikeLocalDaemonErr` (daemon not running, socket missing, docker CLI missing) AND `len(out) == 0`, returns `fmt.Errorf("local docker unavailable: %w", firstDaemonErr)`. The daemon-classifier gate prevents the common "fresh deploy with multiple un-pulled images" case (every image returns `No such image`) from misfiring as `local docker unavailable`. `compareImageDigest` wraps local failures in the `errLocalImageInspect` sentinel so CheckUpdates can dispatch via `errors.Is` into the right cascade. Partial failures (one image down, one up) do NOT cascade — the succeeded service gets a verdict, the failed one stays absent. **RemoteCompose mirrors the registry cascade**: when every non-transport failure matches `looksLikeNetworkErr` AND no service got a verdict, returns `"registry unreachable: <err>"`. This is critical because narrowing `sshTransportStderrPatterns` to SSH-only signatures means a Docker Hub outage seen from the remote host no longer trips the SSH-transport bucket — without this cascade, the remote case would silently blank every glyph with no diagnostic. The three classifiers (sshTransportStderrPatterns, looksLikeNetworkErr, looksLikeLocalDaemonErr) live next to their consumers — see the comment block above `looksLikeNetworkErr` in `internal/compose/updates.go` for the precedence overview. **All three `CheckUpdates` implementations share ONE loop**: `scanImageUpdates(ctx, wanted, compare)` in `updates.go`, with the per-image comparison behind `compareImageDigestVia(ctx, d dockerRunner, image, localErrWrap)`. **There is no per-caller cascade flag — the ERROR SHAPE the comparer emits is what selects the cascade**, and all three diagnostics run unconditionally. Only `Compose` passes `wrapLocalImageInspectErr` as `localErrWrap`, so only `Compose` can ever emit `errLocalImageInspect`, which is what routes a failed local `docker image inspect` to the daemon counters instead of the registry ones AND what keeps "local docker unavailable" off the SSH path, where it would name the wrong machine (`TestCompareImageDigest_SentinelBinding` pins the binding on all three composers, each direction independently mutation-sensitive). `errSSHTransport` likewise exists only on the remote runner, via `classifySSHError`. A flag would only re-state what the sentinel already decides — and `fetchRemoteDigestVia` already short-circuits on `errSSHTransport` with no flag one call level below. The transport abort is the one diagnostic that fires MID-scan rather than after it, because a dead SSH hop fails every remaining image the same way; the partial map still comes back with the error, matching the untrusted-partial-map half of the `Composer.CheckUpdates` contract. `scanImageUpdates` also **memoizes by image ref**, so a repeated image costs one comparison and contributes exactly one attempt to the cascade counters.

## Update detection — TUI caching and refresh

TUI caches results in `updateCache map[string]updateEntry` on Model, keyed by `projUpdatesCacheKey` = `proj.ConfigDir + "\x00" + proj.Name + "|" + serverName`, with an `unmanaged|` prefix off `proj.Unmanaged` (empty `serverName` = local; `projDir`/`projName` are stored on Model because they are not otherwise retained after composer creation). **BOTH project halves are in the key and neither alone would do** — see the grouped-mode section below for the two failure modes. `updateEntry{fetchedAt time.Time, results map[string]bool, details map[string]compose.UpdateDetail, err bool, errMsg string}` in `internal/tui/app.go`. **Two TTLs**: successes live for `updatesCacheTTL` = 10 minutes; failures live for `updatesErrorTTL` = 30 seconds. **Errors ARE cached** (with the short TTL): caching failures prevents the 5-second tight retry loop the `statusMsg` self-heal would otherwise produce on a persistent fault (empty cache → queue refresh → fail → empty cache → repeat; ~120 failed CheckUpdates per 10 minutes against a slow remote SSH hop or a Docker Hub outage). The cached failure entry has `results=nil`, `err=true`, and `errMsg` set to the original error text. **`errMsg` is restored on cache hit** in `maybeRefreshUpdatesCmd` and the `servicesMsg`/`statusMsg` cache-replay paths — without this, navigating away (which clears `m.updatesErr`) and re-entering within `updatesErrorTTL` would silently drop the soft warning even though the failure is still known-bad. A new error entry overwrites any prior successful entry for the same key (don't trust stale success once the latest refresh disagreed); a new success overwrites a cached failure. The key travels WITH the message (`updatesMsg.forKey`) and is never re-derived in the handler; `projUpdatesCacheKey(proj)` is the sibling that composes the SAME string for a project the Model is not currently pointed at — a batch sequence, or a grouped `U` scan — see the grouped-updates section below. **Off-screen error handling**: the `updatesMsg` handler applies state mutations (set `updatesErr`, rewrite the whole `UpdateAvailable` column through `reapplyUpdateVerdicts`) BEFORE the screen check — `m.svcStatus` is the source of truth the next entry to `screenSelectContainers` renders from, so leaving stale glyphs in it during an off-screen window (e.g. the config screen, which is read-only and does NOT trigger `refreshStatus` on return) would let them resurface alongside no warning. Only `fixSvcOffset` stays screen-coupled (touches scroll offsets that are only meaningful while the container list is rendered). **Post-operation cache invalidation**: the `esc` handler that returns from `screenProgress` to `screenSelectContainers` deletes the cache entry for the current key on a successful Deploy, Restart or Rollback, so the next `maybeRefreshUpdatesCmd` misses and enqueues a fresh CheckUpdates — without this, the "update available" glyph would persist for up to 10 minutes after a successful deploy, exactly when the user wants confirmation. Invalidation runs BEFORE the `m.done = false` reset (otherwise the check would see done==false and never fire). Skipped on `m.failed` (don't clear user-visible state on failure) and on Stop (stopping doesn't change image freshness). `refreshUpdates(session)` is fired on entry to `screenSelectContainers` only when the cache is missing or stale (`maybeRefreshUpdatesCmd` helper); the uppercase `U` key bypasses TTL for force-refresh AND guards against stacking via `if m.updateInFlight { return m, nil }`. Updates are **NOT** wired into the periodic 5s `refreshTickMsg` — cadence is TTL + explicit user action, because registry round-trips are expensive and the answer changes slowly.

## Update detection — sessions and in-flight discipline

`updatesMsg{results, err, session uint64, forKey string}` carries a session captured at fetch time AND the cache key the fetch was dispatched under — the handler must never re-derive that key, for the reasons in the grouped-updates section below (the inspect detail rows arrive on a SECOND message, `updateDetailsMsg{details, forKey, forEntry}`, which deliberately carries NO session and instead carries its own dispatch-time identity — see the detail-rows section below). `updatesSession` is bumped at the **same 7 sites** as `statsSession`/`statusSession` — `entryLocal`, `execDone`, return from progress, return from logs, and the three navigation helpers `enterGroupedContainers()`, `drillIntoGroup()` and `backToServerScreen()` — **plus one more ENTRY into that set: the `connectResultMsg` SUCCESS path, which reaches `enterGroupedContainers()` and therefore bumps all three.** **That success-path bump is the INVERSE of the rule that used to hold here.** The old rule ("bump everywhere BUT the success path") existed because the success path landed on the static project picker, a screen that fetched nothing, and the downstream project-pick handler owned the bump. The picker is gone; the success path now lands on LIVE data, so the site that starts fetching a resource is the site that must invalidate whatever a previous server left in flight. `projectsSession` and `projectsMsg` are DELETED with that screen — the loader they guarded now feeds `loadGroups`, which is already gated on `statusSession` at the same swap sites — so the `connectResultMsg` ERROR path bumps only `rollbackFetchSession` and leaves `statsSession`/`statusSession`/`updatesSession` alone (it fetches nothing; it clears the grouped rows a previous server populated instead). The dedicated `updateInFlight bool` flag follows the same clear-before-screen-check pattern as `refreshInFlight`, with one strengthening: the flag is cleared BEFORE BOTH the session check AND the screen check, on EVERY `updatesMsg` arrival (current OR stale, on-screen OR off). The previous "stale leaves it alone, context-change handler resets it" semantics had a sticky-flag bug: after `U` (in-flight=true) → navigate away → come back, the original fetch arrived with an OLD session, and the in-flight guard inside `maybeRefreshUpdatesCmd` would silently swallow every subsequent fetch on cache hits. Clearing on stale arrivals as well is safe because the cache write below is still session-gated, so a stale result can't pollute the cache. Companion guard: `maybeRefreshUpdatesCmd` early-returns nil when `m.updateInFlight == true`, preventing fetch stacking — same rationale as `refreshTickMsg`'s `refreshInFlight` gate. Because of this guard, every context-change site that bumps `updatesSession` AND calls `maybeRefreshUpdatesCmd()` (execDone, esc back from progress/logs, entryLocal fast-track, drill-in) MUST reset `m.updateInFlight = false` first; the session bump invalidates any in-flight fetch (its response will be discarded as stale), so the guard must not refuse to fire a fresh fetch for the new context. The 2 leave-screen transitions — `esc` drilling OUT to the grouped host view (`enterGroupedContainers()`) and `esc` from the grouped view back to the server picker (`backToServerScreen()`) — also reset `updateInFlight = false`. **None of those sites touches `detailsInFlight`**, deliberately — see the detail-rows section below: that flag is a GLOBAL one-batch bound whose only clear is the unconditional one on message arrival, and a context-change reset would both let two scans overlap and make the arrival clear a lie. The `connectResultMsg` error path also clears `serverName`/`updatesErr`/`updateInFlight` so a failed connect attempt doesn't leak transient state into a subsequent connection. The `entryLocal` handler explicitly clears `projDir`/`projName`/`updatesErr` to prevent stale cache-key components carrying over from a previous remote session.

## Update detection — grouped mode (the host view)

**No automatic scan fires in grouped mode.** `autoUpdatesAllowed()` is `!m.readOnly() && !m.grouped`, and `maybeRefreshUpdatesCmd` ALSO early-returns on `m.grouped` before the cache lookup — grouped mode owns neither the single cache key that helper reads nor the single composer a detail refill would fetch through, so `updatesCacheKey()` there would resolve to whichever project was drilled last. All THREE automatic entry points refuse (`maybeRefreshUpdatesCmd`, the `statusMsg` self-heal, `Init()`'s fast path) and `NewModel` seeds `updateInFlight` from the same predicate rather than a flat `true`. The cost rationale is the unmanaged one squared: a compose project bounds `CheckUpdates` to one service list the user is actively managing, while a host view fans out across EVERY project at once, each distinct image costing a local inspect plus up to two registry manifest requests.

**`U` is the only trigger, and it scans the CURSOR row's group only.** The composer is bound, read out and unbound in the SAME keystroke, so grouped mode never holds one project's composer while the cursor sits on another's row; the in-flight guard is checked BEFORE the bind, so a refusal leaves the composer exactly as it found it. The scan is dispatched through `refreshUpdatesFor(composer, key)` — `refreshUpdates()` is the wrapper that reads both off the Model, which grouped mode cannot do.

**The key is captured at DISPATCH and travels on `updatesMsg.forKey`; the handler must NEVER re-derive it.** The cursor is free to move — or fold a group — while a scan runs, so a handler-time re-derive files one project's verdicts under another project's key: the wrong glyphs paint and the scanned project reads as unchecked. The key itself is `projUpdatesCacheKey(proj)` = `proj.ConfigDir + "\x00" + proj.Name + "|" + serverName`, carrying the `unmanaged|` prefix off `proj.Unmanaged` — **the same string `updatesCacheKey()` produces once drilled into that project**, so one cache entry is shared between the two modes and a scan started from the host view still counts after drill-in. The two must keep producing identical keys, or a grouped scan and a drilled one file the same project under two entries. **BOTH project halves are in the key and neither alone would do.** The directory does not identify a project: `docker compose -p a` and `-p b` in one tree are two projects with two container sets, shown as two groups, and on `ConfigDir` alone they shared one entry — one project's verdicts painted onto the other's rows, and its own scan suppressed for the whole 10m TTL. The name does not identify one either: a group `buildSvcGroups` synthesised from the host status map has no `ConfigDir` at all (one `docker ps` reported it and `docker compose ls` did not — drill-in is refused for it), and two hosts can run the same project name from different trees. NUL is the separator because no filesystem path and no docker project name can contain it, so no `(dir, name)` pair can spell another pair's key.

**Replay, not overwrite**: `reapplyUpdateVerdicts` routes grouped mode to `hydrateGroupedUpdates()`, which re-reads every visible group's verdicts from the cache (see the rendering section for why the drilled "whole truth" rule cannot apply here). **Those cache reads are RAW — deliberately not the TTL-checked `updatesCacheLookup`.** Grouped mode never refetches on its own, so a TTL-gated replay would blank the glyph column ten minutes after a scan with nothing queued to bring it back; the age of the check is reported on the inspect screen instead. Error entries are skipped (their results map is nil and their verdicts are untrusted by contract). The replay runs on every grouped reload — every 5 seconds — which is what keeps a `U` scan's glyphs alive across the periodic refresh.

**Group headers show `⇧ n` from cached verdicts only.** `groupCounts` returns the update total as a THIRD value beside `up` and `unhealthy`, read off the same tri-state the row glyph draws: a nil verdict counts as zero, exactly like a false one, so nothing on the header path can trigger a scan.

**Grouped mode fetches NO inspect detail rows, and the gate is the MODE, not the nil composer**: `updateDetailsCmd` reads `m.composer`, which an armed `x` prompt may have left bound to a DIFFERENT project than the scan covered, so a batch built from it would spend registry round-trips resolving the wrong project's images. The entry keeps `details == nil`, which is exactly the state `refillUpdateDetailsCmd` fills the moment the user drills into that project — the rows are deferred, not lost. `inspectUpdateKey()` resolves the cursor row's group key so `i` from a grouped row reads the right entry; it is read at RENDER time rather than captured on entry, because the cursor cannot move while the inspect screen is up.

Full rationale and test pins: `docs/architecture/tui-multi-project.md`.

## Update detection — rendering, CLI, and JSON

Cache results are re-hydrated onto `m.svcStatus` inside `servicesMsg` and `statusMsg` handlers via a `hydrateUpdates` helper, race-safe regardless of arrival ordering of status vs updates. Those replay paths stay purely ADDITIVE (they introduce no new data, they only preserve existing verdicts across a status-map overwrite); the destructive rewrite belongs to the `updatesMsg` handler alone, through `reapplyUpdateVerdicts(results)`. **`reapplyUpdateVerdicts` replaced the two clear-then-hydrate blocks, and the "the message is the whole truth" rule it implemented is now DRILLED-ONLY.** Drilled mode has one project and one scan, so clearing every verdict and hydrating from the message is correct: a verdict the newest scan no longer reports (build-only this time, a failed lookup, a service dropped from compose) loses its stale glyph. Grouped mode holds several projects at once and `U` scans exactly ONE of them, so applying the message alone would blank every group the scan did not cover — on the success path AND on the error path, where the untrusted-map contract binds only the failed project. Grouped mode therefore re-reads the verdicts per group from the cache, through `hydrateGroupedUpdates()`. `hydrateUpdatesFor(projName, results)` is the underlying writer — `hydrateUpdates` is the wrapper that infers the owner via `ownerProjName()` — because a bare-name `CheckUpdates` map has to be qualified with the OWNING project before the lookup, and in grouped mode that owner is the group being replayed rather than the Model's single project identity. **Phantom guard**: `hydrateUpdatesFor` skips verdicts whose (qualified) service key is NOT already in `m.svcStatus` — without this guard, a verdict for an unknown service (compose config and ContainerStatus may transiently disagree during a refresh, or a stale verdict may refer to a service that no longer exists after a project switch) would synthesise a zero-valued `ServiceStatus` entry that'd leak across context switches. The renderer iterates `m.services` (not the status map) so phantoms are invisible today, but the guard prevents a latent class of bugs in any future iterator. Rendering: yellow `updateGlyphStyle` in `internal/tui/styles.go` appends `" ⇧"` after the service name; `maxName += 2` unconditionally (always reserve the glyph slot so Created/Uptime/CPU/Mem/Ports don't shift when a verdict arrives or clears mid-poll); glyph is shown on stopped services too. The `U updates` token lives in the `?` overlay, not the footer. Errors render in the soft-warning slot prefixed `updates: `, priority `svcErr > statsErr > updatesErr`. CLI `cmd/list.go` gates `CheckUpdates` behind `--updates` in BOTH single-project (`-C`, `--ssh`) and multi-project modes (same opt-in shape as `--stats`) — each service costs one registry round-trip and 20+ services over SSH adds 10s+, so the default is off in both modes; soft failure prints `cdeploy: updates unavailable: <err>` (or `for "<project>": <err>` in multi-project) to stderr and leaves cells blank without aborting the listing — callers SET `updates = nil` on error in line with the `Composer.CheckUpdates` partial-untrusted contract above; JSON output gains `update_available *bool` with `omitempty` so the wire shape is unchanged when the flag is omitted. `formatDots`/`formatDotsGrouped` extend `maxName` by 2 cells the same way as the TUI — width is measured by `utf8.RuneCountInString` because the U+21E7 glyph is multi-byte but renders in one terminal cell, and styled rendering carries ANSI escapes that don't count toward display width. The glyph rune is owned by `compose.UpdateGlyph` so both surfaces stay in sync; bumping it changes both in one place.

## Update detection — the inspect screen's detail rows (`UpdateDetailer`)

Once the `⇧` verdict is `true` the glyph raises two questions it cannot answer: WHICH image is waiting, and WHEN each side was built. The inspect screen's IMAGE section answers both with four rows — `built`, `update`, `update id`, `update built` — drawn from `compose.UpdateDetail{LocalCreated, NewID, NewCreated}` (`internal/compose/updatedetails.go`), a three-field struct carrying exactly what a row draws and nothing more (`Platform` and `LocalID` were in an earlier draft and were dropped: `docs/architecture/tui-inspect-screen.md` states the rule directly — a parsed-but-unrendered field is a promise the screen does not keep). **`NewID` is the registry image's CONFIG digest, and that is the whole reason it is comparable with the `image id` row above it**: measured on Docker 29.1.3 / buildx v0.30.1-desktop.1, resolving the config digest at an image's own RepoDigest returned the same `sha256:7e7dbab8…` that `docker image inspect --format '{{.Id}}'` reports locally. The manifest-LIST digest `CheckUpdates` compares is a different thing entirely, which is why the same change relabelled the summary's `digest` row to `image id` — an `update id` row sitting beside a row labelled `digest` invites exactly the false comparison this feature must avoid.

**`UpdateDetailer` is a TUI-declared interface, not a `Composer` change.** It is declared in `internal/tui/app.go` beside `Inspector`/`ConfigProvider`/`ExecProvider` and type-asserted on the concrete composer, so `runner.Composer` and its five mock sets (`internal/runner/`, `internal/tui/app_test.go`, `cmd/deploy_test.go`, `cmd/list_test.go`) are untouched and `cdeploy list --updates` keeps its current cost — the CLI has no detail view, so it would pay up to three extra registry round-trips per updated image for data it cannot show. All three composers implement it (`Compose.UpdateDetails` over `localDockerRunner`, `RemoteCompose.UpdateDetails` over `remoteDockerRunner`, `HostContainers.UpdateDetails` over its own `dockerRunner` field), which is why **the three `var _ UpdateDetailer = …` compile-time pins sit beside the `Inspector` triple in `app_test.go`**, plus the runtime assertion in `TestHostContainers_CapabilityInterfaces`: the whole path runs through a runtime type assertion and every TUI test drives a double that satisfies it by construction, so without the pins a rename or a signature drift leaves all 7 packages green while the rows silently vanish. A composer that does NOT implement it produces verdicts with no detail rows — the same outcome a detail-fetch failure produces, which is the point.

**The fetch rides the `refreshUpdates` schedule, but NOT its message.** The explicit requirement was that the detail rows follow the same rules and timings as the `⇧` glyph, and every trigger, cache key, TTL and post-Deploy/Restart/Rollback invalidation is shared — the verdicts' session check gates the enqueue, so the schedule is shared by construction — but the two halves are TWO messages, and that boundary is load-bearing. One `tea.Cmd` returns one message, so folding `UpdateDetails` into `refreshUpdates`' own goroutine would hold the verdicts (already in hand) behind up to three registry round-trips per updated image: the whole `⇧` column stays blank for that window, `updateInFlight` stays `true` so `U` is swallowed and the `statusMsg` self-heal is gated off, and nothing on this path carries a timeout. That inverts the priority stated two paragraphs down — the bonus would gate the signal. So `refreshUpdates` returns the moment `CheckUpdates` does, and the `updatesMsg` handler enqueues `m.updateDetailsCmd(entry, key)` AFTER the cache write — the WHOLE entry, so `results` and `fetchedAt` can never be paired from two different ones; its `updateDetailsMsg` merges `details` onto the entry the verdicts just created. Because that enqueue sits after the session check, a scan **already superseded when its verdicts arrive** spends no detail calls at all. A scan superseded LATER cannot be stopped — `m.ctx` is never cancelled per fetch — so the cost is bounded by an in-flight guard instead: **`m.detailsInFlight`**, `updateInFlight`'s twin for the second phase. `updateInFlight` is cleared the moment the verdicts land (that is what keeps `U` alive during the detail window), so without it the expensive half is unguarded and one `U` press mid-scan stacks a SECOND batch of up to three registry round-trips per updated image on top of the running one, repeated presses stacking without bound — the exact 429 the true-only filter and the per-image memoisation exist to avoid, and two concurrent batches memoise separately so the mitigation does not span them. `updateDetailsCmd` returns nil while the flag is set and the handler clears it on EVERY arrival, before the identity gates. **Nothing else clears it — no context-change site resets it**, so the bound is GLOBAL rather than per context: with at most one batch outstanding there is exactly one arrival per raise, which is what makes the unconditional clear exact and keeps the flag from latching or from being cleared out from under a batch that is still running. **The guard must NOT be a gate on `U` or a delayed `updateInFlight` clear** — either one reinstates the dead-`U` window the message split exists to remove.

**A lost batch heals from the ENTRY's own state, not from a record of the loss.** This is the rule four review rounds converged on, and it replaced three earlier attempts. The failure it prevents is always the same: a detail batch goes missing, the entry the verdicts wrote keeps `details == nil`, and because that entry is a fresh SUCCESS both `maybeRefreshUpdatesCmd` and the `statusMsg` self-heal skip it and the inspect screen — a pure consumer — draws `update available` with no `built` / `update id` / `update built` for the whole 10-minute TTL, with nothing on screen explaining why. Rounds 2, 3 and 4 each found a DIFFERENT mechanism that lost one (a session gate on the message; a cache key re-derived at merge time; a departure-site reset of the park that held it), each patch closed that one door, and the bug walked through the next.

`refillUpdateDetailsCmd` closes the class instead of the doors. It reads the CURRENT context's entry and re-dispatches when — and only when — that entry is fresh, non-errored and no batch has ever reported for it. It is called from exactly two places: the tail of the `updateDetailsMsg` handler (so a batch refused while another was running is retried the moment that one reports, with no further keystroke) and `maybeRefreshUpdatesCmd`'s fresh-SUCCESS branch (so every screen entry heals one too). **NEITHER site is behind `autoUpdatesAllowed()`, and that is deliberate.** The screen-entry one was, for one review round, on the reasoning that the read-only unmanaged view would otherwise fan out to the registry automatically after all — but a refill can only fire for an entry that ALREADY EXISTS under the current key, and no automatic path can create one under a read-only key (the stale branch of `maybeRefreshUpdatesCmd` refuses, and so do the `statusMsg` self-heal and `Init()`). Only `U` can. So a refill there completes that `U`, restricted to the services it already reported `true`, rather than starting a fetch of its own; gating it stranded exactly the rows `U` asked for, for the entry's whole 10-minute TTL, whenever the batch was refused while another was running and the arrival landed under another key. However a batch goes missing, present or future, the entry still says "no batch reported" and the next trigger refills it. **Do not add a fourth guard.** Each of the three that came before it patched one door and the bug walked through the next; the retry must stay keyed off the entry's own state, which is the only formulation that does not have to enumerate the ways a batch can be lost.

**`entry.details == nil` versus an EMPTY map is therefore load-bearing.** nil means no batch has REPORTED; the merge normalises a nil map to an empty one, so a batch that came back with nothing (a 429, a transport abort before the first row) is recorded and NOT retried — without that, a failed detail phase would re-scan the registry on every screen entry for the entry's full 10-minute TTL, the exact amplification the error-swallowing at the fetch site exists to prevent. An entry can also stay nil forever without being a fault (no verdict was true, or the composer does not implement `UpdateDetailer`), and that is safe because both make `updateDetailsCmd` return nil: the refill is a no-op, not a loop. **The refill cannot loop** — a dispatch fills the entry it names, so the same entry is never fetched twice, and a mismatched arrival only re-dispatches for an entry a KEYSTROKE created in the meantime. Three refusals therefore collapse into one retry against the newest verdict set, which is what the park used to buy with a slot of its own.

**Call it in its own statement.** `refillUpdateDetailsCmd` has a pointer receiver and mutates the same `m` the handler returns; Go leaves the evaluation order of a bare operand against a call operand unspecified, so `return m, m.refillUpdateDetailsCmd()` would risk returning a model without the `detailsInFlight` the call raised — and that is precisely the mutation standing between this and an unbounded registry loop. Every other pointer-receiver Cmd builder in the file is already hoisted; keep this one hoisted too.

The merge end: **`updateDetailsMsg` carries NO session — it carries its OWN identity**, `forKey` and `forEntry`, and BOTH are captured at DISPATCH time and travel WITH the message. `forKey` is the `updatesCacheKey()` the batch was fetched under and `forEntry` the `fetchedAt` of the entry it annotates; together they name exactly one verdict set, which is strictly stronger than the session counter. A session gate here was actively HARMFUL, and so was re-deriving the key in the handler — the same bug one step further out. `updatesSession` is bumped by ordinary navigation that does not change the context (esc back from logs or progress, `execDone`), and the CURRENT key changes on navigation that does (`esc` drilling out to the grouped host view, drilling into another project, another server); a detail scan runs for tens of seconds, so both are routine mid-scan. Either gate dropped the only message that could fill the entry, and because those sites find the entry fresh they enqueue no replacement, so it kept `details == nil` for its whole 10-minute TTL while the inspect screen drew `update available` with no `built` / `update id` / `update built` — recoverable only by a manual `U` (`TestUpdateDetailsMsg_LandsAfterASessionBump`, `TestUpdateDetailsMsg_LandsAfterNavigatingAway`, `TestUpdateDetailsMsg_ForeignContextIsNotTouched`, `TestUpdateDetailsMsg_SupersededEntryIsDropped`). The handler only ever MERGES onto an existing non-errored entry — it never creates one — and `redrawInspectFromCache()` runs only when `forKey` IS the current key, because that helper is a render path reading the current context and its `setInspectContent` would otherwise reset a sideways-scrolled pane for data that did not change. `detailsInFlight` is the ONE new Model field, a transient guard rather than view state: `clearInspect()`, the `esc` chain, `entryLocal` and the `connectResultMsg` error path need no cleanup for it (see above) nor for `details` itself, which lives only on the context-keyed cache entry and on the message. It also follows that the read-only unmanaged screen never fetches details on its own: `autoUpdatesAllowed()` gates the three entry points to `refreshUpdates`, so `U` remains the only thing that can create an entry there — which is in turn what makes both refill sites safe to leave ungated (see above).

**A superseded scan is not cancelled, only discarded.** `m.ctx` is assigned once in `NewModel` and every context-change site fires a replacement fetch without stopping the previous one, so two `CheckUpdates` scans can overlap — pre-existing. A detail scan already dispatched when the context changes runs to completion too — its result is no longer dropped (it merges onto the entry it names, under its own `forKey`), but the round-trips are spent whether or not the user ever returns. **`detailsInFlight` bounds the phase to one batch GLOBALLY**: no context-change site resets it, so the new context's `updatesMsg` cannot dispatch a second batch on top of the running one — it is refused, and `refillUpdateDetailsCmd` dispatches it from the old batch's arrival instead. The new context therefore waits out the remainder of a scan it does not care about, which is the deliberate trade in the other direction: bounding the registry cost strictly beats starting the new context's rows a few seconds sooner, and the earlier per-context bound made the unconditional arrival clear unsound (two outstanding batches, one clear). **The arrival is guaranteed by a DEADLINE, not by hope.** `updateDetailsCmd` wraps the fetch in `context.WithTimeout(m.ctx, updateDetailsTimeout)` (3 minutes). `m.ctx` lives for the whole program and neither `dockerRunner` adds a deadline of its own, so without this bound a single stalled registry call would latch `detailsInFlight` for the rest of the session — no departure site resets it and `U` cannot force it, leaving restarting cdeploy as the only escape. An expiry DEGRADES rather than errors: `scanUpdateDetails` checks `ctx.Err()` at the top of each image and returns the PARTIAL map, so the rows resolved before it still land and the loop stops rather than spawning a doomed process per remaining image. The value trades two failure modes against each other — too short records a partial set that the entry then keeps for its whole 10-minute TTL (the merge normalises a partial map to "reported", so `refillUpdateDetailsCmd` will not retry it), too long re-opens the stall. Pinned by `TestUpdateDetails_FetchCarriesADeadline`, which asserts the ctx handed to `UpdateDetails` carries a deadline no further out than the constant. A per-fetch `context.WithCancel` on top would additionally stop a scan the user has already navigated away from; that stays a deferred refinement, since the deadline already bounds the cost. **One discovery call is duplicated per refresh, and the two calls can disagree.** `UpdateDetails` re-runs the `docker compose config --format json` (or `docker ps -a`) that `CheckUpdates` ran moments earlier — a second full SSH round-trip on the remote path. Since the message split the two no longer share a goroutine either: the verdicts return first and the detail batch is dispatched from their arrival, so a compose file edited in between attaches image B's details to a verdict computed for image A. Both halves are conscious deferrals, recorded in the plan's Residuals, and the second one is a judgement rather than an oversight. The cost half is cheap — a LOCAL command, not a registry one, so it spends latency and not quota. The correctness half is bounded by a window the design already accepts: the entry is displayed from cache for up to `updatesCacheTTL` (10 minutes), so ANY compose edit inside that window already makes the shown verdict describe an image the file no longer names, and closing the seconds-wide gap between the two calls would shrink a hole inside an already-accepted one rather than remove the class. The common trigger is self-limiting too — an edit naming an image the host has not pulled fails step 1 (`docker image inspect`) and the whole entry is omitted rather than drawn wrong, and a service that disappears from the file is dropped by `filterServices`. Removing the duplication means passing the resolved image map down, which widens the interface this design deliberately kept narrow; it would also pin the rows to the verdict's map rather than to the truth, trading a stale-verdict mismatch for a stale-image one.

**A detail failure is discarded and must never reach `updatesMsg.err`.** `updateDetailsCmd`'s closure (`app.go`) drops the `UpdateDetails` error on the floor. That is load-bearing, not laziness: a Docker Hub rate limit reads as `429 Too Many Requests`, `looksLikeNetworkErr` matches `too many requests`, and a detail-phase failure promoted to `updatesMsg.err` would trip the registry cascade, blank the ENTIRE `⇧` column and shorten the cache entry to the 30-second error TTL — a rate limit hit while annotating the signal would degrade the signal it was annotating. The glyph is the load-bearing view and these rows are a bonus, the same asymmetry the `svcErr > statsErr > updatesErr` soft-warning priority already encodes. The detail phase is also **skipped entirely when `CheckUpdates` itself errored**: a non-nil error makes the whole verdict map untrusted per the `Composer` contract above, so no verdict is worth following up and the round-trips would be spent on a path that is already broken.

**The cost is real and was measured.** Each updated image costs UP TO FOUR round-trips (one local, up to three registry) on top of the one `CheckUpdates` already makes. It is three (one local, two registry) whenever step 3 is skipped — see the single-manifest rule below, which is what decides it. During research ~15 anonymous manifest requests inside ten minutes was enough to earn `429 Too Many Requests` from `registry-1.docker.io` on a HEAD to `/v2/library/postgres/manifests/16-alpine`. Three mitigations are built in and **all three are load-bearing, not defence in depth**: (1) details are fetched ONLY for services whose verdict is `true`, usually a small minority — `servicesWithUpdate` filters, and the empty-slice guard in `updateDetailsCmd` (which is also what makes the Cmd nil, so the handler enqueues nothing at all in the common case) is required because `filterServices` reads an empty services slice as **ALL** services, so calling through with no true verdicts would spend those round-trips on every service in the project; (2) `scanUpdateDetails` memoises by image reference exactly as `scanImageUpdates` does, and memoises FAILURES alongside successes so a repeated unresolvable image costs one call set rather than one per service; (3) the `autoUpdatesAllowed()` inheritance above. The recommended operator-side mitigation is `docker login` on the docker host, which raises the anonymous quota.

**Considered and rejected — reusing the index `CheckUpdates` already fetched.** `fetchRemoteDigestVia` runs `imagetools inspect <ref>` moments earlier and its human output carries a `Manifests:` block with a `Name:` and `Platform:` per entry; harvesting per-platform digests from it would remove step 2 and cut the cost by a quarter. Rejected on two grounds: parsing per-platform digests out of that human block is exactly the fragile text parse that produced the `--format` regression this subsystem already carries a pin against, and plumbing the raw bytes out of `scanImageUpdates` would change a loop all three composers share. Revisit only if the quota proves binding in practice.

**The four-step sequence** (`fetchUpdateDetail`), per image, all four bypassing `command()`/`remoteCommand()` through the `dockerRunner` seam because every one of them is a top-level docker command:

| # | Command | Yields |
|---|---|---|
| 1 | `localProbeArgs` → `docker image inspect --format '{{json .}}'` (the format constant is `localProbeFormat`) | `LocalCreated` + the platform TRIPLE (`Os`, `Architecture`, `Variant`). **Local only.** |
| 2 | `manifestIndexArgs` → `docker buildx imagetools inspect --format '{{json .Manifest}}'` | the index; select the entry matching the normalised platform triple |
| 3 | `rawManifestArgs` → `docker buildx imagetools inspect --raw <pinnedRef>` | `config.digest` → `NewID` |
| 4 | `imageConfigArgs` → `docker buildx imagetools inspect --format '{{json .Image}}' <pinnedRef>` | `created` → `NewCreated` |

`<pinnedRef>` is `stripTag(ref) + "@" + platformDigest`, reusing the same in-package helper `rollbackImageRef` uses rather than re-deriving the repo portion, so a registry port (`localhost:5000/foo:1`) survives the rewrite. **On the single-manifest path step 3 is SKIPPED**: step 2's own output IS the manifest, so `parseConfigDigest(indexOut)` already has `config.digest` and re-fetching it would be a third of the registry traffic for nothing. `pinnedImageRef` returns `pinned bool` to say which path was taken, and the `--raw` call still runs as a fallback when that parse yields nothing, so a buildx whose `{{json .Manifest}}` omits the config descriptor keeps the `update id` row. Steps 2-4 are registry calls, so `fetchUpdateDetail` returns at the FIRST failure rather than pressing on — the caller omits the whole entry either way and a wasted round-trip is a step closer to the rate limit. **A step that SUCCEEDS but whose parser returns "absent" is NOT a failure**: only its own field stays zero and the rows the other steps filled still render. Going through the seam is what makes the remote path free: `remoteDockerRunner` already carries the `SSHExtraArgs`-before-host splice, `shellEscape`, and `classifySSHError`, so an `errSSHTransport` short-circuits `scanUpdateDetails` and returns the partial map alongside the error, matching the untrusted-partial-map contract. **Services are visited in SORTED order** for the same reason `servicesWithUpdate` sorts: each image costs two or three registry calls and a transport abort truncates the batch, so which images are reached must not depend on Go's map iteration order — otherwise the abort test is flaky and the quota cost is nondeterministic.

**Step 1 asks for `{{json .}}`, and NAMES no field.** The first draft used `{{.Created}}|{{.Os}}|{{.Architecture}}` and forbade `{{.Variant}}` beside it, on the grounds that a template referencing a field the CLI's struct lacks is a hard execution error rather than an empty string. That half is true, and worse than it looks: the CLI retries a failed template against the raw JSON with `missingkey=error`, and `Variant` is `omitempty`, so an image with no variant carries no such key and the retry fails too — one unknown field would kill step 1 for EVERY image and silently disable the whole feature. The conclusion drawn from it was wrong, though. Discarding the variant is not free: it made the index match guess (see below), and the fix is not to name one more field but to stop naming fields at all. `{{json .}}` cannot fail that way — a field an older CLI does not know simply never appears, and an absent variant parses as the empty string the matcher then canonicalises (`arm` ⇒ `v7`, `arm64` ⇒ unqualified) rather than treating as a wildcard — which is exactly the rule `hostPsArgs` documents for `docker ps`. The document is ~2 KB; `parseLocalProbe` decodes four keys out of it (`Created`, `Os`, `Architecture`, `Variant`) and ignores the rest. `Id` is among the ignored, for the "only what a row draws" reason: the `image id` row already comes from the container's own inspect document.

**`parseIndexPlatformDigest` is three-state, and conflating two of the states is the silent failure mode.** `hasIndex=false` means there is no `manifests` key at all — a single-manifest ref, so steps 3 and 4 address the ORIGINAL ref. `hasIndex=true, found=false` means an index exists but the host's platform is absent from it, and the caller must **abort this image**. `hasIndex=true, found=true` pins and continues. A `(string, bool)` return would collapse the middle state onto the first, and then step 3 would run `--raw` against the index (which has no `config.digest`, so `NewID` comes back empty) while step 4 would return the platform-keyed map from which the code could pick a platform that is not the host's — a wrong `update id` and a wrong `update built`, drawn confidently. **Every doubt therefore returns the ABORT state**: malformed JSON, a `manifests` value that is not a list, an empty os/arch argument, and an EMPTY document all fail closed rather than being read as "single manifest". The empty document is the subtle one: `null` unmarshals into a nil map, so `len(doc) == 0` must ABORT rather than fall through to the `hasIndex=false` branch, which would send steps 3 and 4 at the original ref on the strength of a document that said nothing. A real multi-arch index also interleaves **attestation manifests** carrying `platform.architecture == "unknown"` — 8 of nginx's 16 entries — whose digests address provenance/SBOM blobs rather than runnable images, so any entry with an `unknown` os or architecture is skipped. **The variant is MATCHED, not guessed — after both sides are CANONICALISED**, and the road to that rule ran through three wrong ones. Step 1 reports the local image's own variant, and `normalizePlatformVariant` folds the descriptor's and the probe's spelling to one canonical form before they are compared; the entry whose normalised variant equals the probe's wins. **One fallback survives**: a lone entry whose normalised variant is EMPTY serves the whole architecture and is taken whatever the local image says (portainer and qdrant publish `linux/arm64` unqualified, and a host reporting a newer variant still runs the baseline image). **Everything else aborts** — in particular a KNOWN local variant with no entry of its own.

**The default-variant rule is containerd's, and it was verified rather than assumed.** The OCI image-spec makes `variant` an OPTIONAL descriptor property and standardises exactly four values (`image-index.md`, "Platform Variants": `arm`/`v6`, `arm`/`v7`, `arm`/`v8`, `arm64`/`v8`) — it never says what an ABSENT variant means. containerd answers that, and docker and buildx inherit the answer through it (`platforms/database.go`, `normalizeArch`, unchanged from containerd 1.4 to the current `containerd/platforms` module): `arm` with no variant — or with `7` — is **`v7`**, `arm` with `5`/`6`/`8` is `v5`/`v6`/`v8`, and `arm64` with `v8` (or `8`) is the SAME platform as an unqualified `arm64`. Two consequences, and both are load-bearing: an unqualified `linux/arm` descriptor is ARMv7 rather than a wildcard over 32-bit ARM, and library/nginx's single `linux/arm64/v8` entry is an EXACT match for an arm64 image config that records no variant. Only that arm/arm64 pair is folded — the architecture ALIASES containerd also normalises (`aarch64`, `x86_64`, `i386`) cannot appear on either side, because both sides come from docker's own JSON, which spells the architecture as a Go GOARCH value.

The three rejected rules are worth keeping written down, because each looked safe:

- *First in index order wins.* Both real captures carry `linux/arm` twice (nginx as `v5`+`v7`, postgres as `v6`+`v7`), so a 32-bit ARM host was pinned to a variant it never runs and drew a confident `update id` and `update built` for another image, directly under the `image id` row that invites the comparison.
- *Any lone variant-qualified entry wins.* The repair for the first rule, and it stopped one case short: with the host variant discarded, an image published for `linux/arm/v7` alone is a lone entry, so an ARMv6 host still accepted it. Capturing the variant is what closes that, and it is the reason step 1 changed shape.
- *An unqualified entry is a wildcard over its architecture.* The repair for the second, and it stopped one case short in the other direction: `linux/arm` with no variant IS `v7`, so a lone unqualified entry was still handed to an ARMv5 or ARMv6 host — the same wrong `update id` and `update built`, one variant further out. Normalising both sides closes it, and it also retires the mirror leniency: a lone variant-qualified entry is no longer accepted for a probe that names no variant, because such a probe is now a concrete platform (`arm` ⇒ `v7`, `arm64` ⇒ `v8`) rather than "unknown", so taking an `arm64/v9` or `amd64/v3` entry for it would be the identical bug.

**Failing closed on the arm64 spelling was measured and rejected**, not argued: `linux/arm64` is spelled `arm64/v8` in BOTH committed captures, so a rule of "abort whenever no unqualified entry matches" would silently drop the rows on every ARM64 host — Apple Silicon, Graviton, a 64-bit Pi. `TestPinnedImageRef` and `TestParseIndexPlatformDigest_Fixtures` both fail under that mutation, which is the evidence that decided it; the `arm64`/`arm64/v8` fold is what makes the leniency unnecessary — those hosts now match EXACTLY. Pins: `TestNormalizePlatformVariant` (the containerd table, both directions), `TestParseIndexPlatformDigest_VariantMatching` (the whole rule as a table, including the lone-mismatched-entry abort, the v5/v6-versus-unqualified pair and the `arm64/v9` refusal), `_RealCaptureArmVariants` (both real captures, every arm variant they carry and the two they do not) and `TestScanUpdateDetails_HostVariantReachesTheMatch` (the variant — including an ABSENT one — surviving step 1's parse all the way into the pinned ref).

**Step 4 reads the BARE OBJECT shape only, and the platform-keyed map cannot reach it.** `imagetools inspect --format '{{json .Image}}'` returns a platform-keyed map for a bare MULTI-PLATFORM tag (and costs ~4.3 s against ~1.2 s, which is why callers pin whenever step 2 gave them a digest). But step 4 only ever addresses a ref `pinnedImageRef` produced: either a platform-pinned `repo@digest`, or the original ref when step 2 reported `hasIndex=false` — which by definition means no `manifests` key, i.e. a single manifest. A multi-platform tag always carries an index, so it is pinned before step 4 or aborted at step 2. An earlier draft carried a `pickImageConfig`/`platformKeyMatches` branch for the map shape (about 100 production lines and a 50-iteration map-order test) on the premise that "a single-arch ref reaches step 4 unpinned" — the premise is true, but an unpinned SINGLE-ARCH ref returns the bare object, not the map, so the conclusion did not follow and the branch was unreachable. It was deleted. `parseImageCreated(data)` now decodes straight into `imageConfigDoc`; a map document decodes cleanly with no top-level `created`, so it omits the row — the designed behaviour for doubt. **The bare object is trusted WITHOUT a platform cross-check** — it is only reached for a ref that resolves to exactly one manifest, so its config is the only one there is, and rejecting it on a platform mismatch would drop the row for every legitimate single-arch image.

**`validImagetoolsDigest` is a WHOLE-STRING check, shared by steps 2 and 3.** It reuses `imagetoolsDigestRE` and normalises to lower case, and it is whole-string rather than a substring search for exactly the reason `parseImagetoolsDigest` is: the `--format` flag on `imagetools inspect` is only SELECTIVELY usable — `{{json .Manifest}}` and `{{json .Image}}` substitute correctly on buildx v0.30.1 while the documented `{{.Manifest.Digest}}` silently falls through and prints the human block — so a permissive parser would one day accept a fallen-through `Name:` line as a digest. Every parser here validates strictly and returns "absent" on doubt, so a future buildx regression drops rows rather than drawing wrong ones.

**The epoch sentinel.** `created` is `1970-01-01T00:00:00Z` for reproducible builds — verified on `gcr.io/distroless/static`, and true of ko, Bazel and nix images too. It is a placeholder, not data, so `parseImageTimestamp` treats any `Unix() <= 0` as the zero time and the TUI's `formatInspectTimeValue` applies the same guard on the render side; the `built` / `update built` row is then omitted. There is no upstream fix, so those images show no build date at all. An unparseable timestamp takes the same path rather than erroring: the platform pair beside it is still usable, so the scan continues and only the one row drops. Unparseable output, or an EMPTY os/arch, IS an error, though — without an os and an architecture the index match can only fail, so erroring in `parseLocalProbe` saves the two or three registry round-trips that would follow. (The field COUNT stopped being a failure mode when step 1 moved to `{{json .}}`: an absent key parses as the empty string, and only the variant is allowed to be one.)

**Rendering: one lookup site, and the inspect screen never fetches.** `buildInspectSummary(doc, width, upd inspectUpdateInfo)` stays pure — the clock arrives inside `upd` rather than through a `time.Now()` call in the renderer — and **the zero value of `inspectUpdateInfo` draws no new row**, which is what made the signature widening mechanical and every pre-existing assertion hold. `rebuildInspectSummary()` is the SINGLE place the cache is read (via `m.currentUpdateInfo()`), so the fetch path, the resize branch and the `updatesMsg` arrival cannot drift into three copies. That lookup deliberately reads the raw map rather than the TTL-checked `updatesCacheLookup`: the glyph itself is drawn from `m.svcStatus`, which keeps the last verdict until a refresh replaces it, so an entry aging past its TTL must not blank these rows either — the `(checked 3m ago)` suffix is what tells the user how old the answer is, and it is dropped rather than reported as "moments ago" when the entry carries no fetch time. An errored entry yields the zero value. `inspectUpdateInfo.detail` is a VALUE and only `verdict` is a pointer — the verdict needs the tri-state, the detail rows key off their own fields, so a missing detail is the zero struct rather than a nil check. **Both handlers call `redrawInspectFromCache()`**, the one screen-coupled mutation in either: without it, pressing `i` while the first fetch is still in flight — a cold cache is exactly when that happens — would leave the rows permanently absent until the user backed out and re-entered. In the `updatesMsg` handler it sits directly AFTER the cache write, and that order is load-bearing in two ways: a rebuild before the write renders the PREVIOUS entry (the exact bug it exists to prevent), and it runs on the FAILURE path too — the entry that just landed carries no verdicts and no details, so a summary drawn from a previous one must stop showing them, or the blanked glyph column and the inspect screen contradict each other. The helper **rebuilds the summary unconditionally but writes the viewport only when NOT in raw mode**: the raw buffer is untouched by update details, so `setInspectContent()` there changes nothing except its own `SetXOffset(0)` — snapping a user who scrolled sideways through the long JSON lines back to column 0 at an arbitrary moment. The summary is still rebuilt, so a later `r` shows the new rows. Raw mode is untouched — `m.inspectRaw` never sees these values, so `r` stays byte-identical to `docker inspect`.
