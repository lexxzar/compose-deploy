# TUI: the provider-backed screens — inspect (`i`), config (`c`), exec (`x`)

> Extracted verbatim from `CLAUDE.md`, which is auto-loaded and has a size limit.
> `CLAUDE.md` carries the rule digest; this file carries the full rationale, the
> failure modes it prevents, and the tests that pin them. Read it before you touch `internal/tui/inspect.go`, `internal/compose/inspect.go`, or the `ConfigProvider`/`ExecProvider` implementations in `internal/compose/compose.go` and `internal/compose/remote.go`.

`Inspector`, `ConfigProvider` and `ExecProvider` are one family, which is why one file holds all three. Each is declared in `tui` (`internal/tui/app.go`) rather than in `runner` (they return `*exec.Cmd`, or exist only to draw a screen), each is type-asserted on the concrete composer at the moment its key is pressed, and a composer that omits one simply makes that key inert — no capability flag, no factory, no widening of `runner.Composer` and no edit to its five mocks. What differs is REACH, and the reach is what each screen's rules follow from: `Inspector` and `ExecProvider` are implemented by all three composers, so `i` and `x` are live on the read-only unmanaged screen too and are NOT gated on `m.readOnly()`; `ConfigProvider` is implemented by the two compose composers only, so `c` would gate itself for free and gets an explicit gate anyway (`docs/architecture/unmanaged-containers.md` — an inert key a help table still names is the failure the `?` overlay exists to prevent).

## Inspect screen

the `screenInspect` screen shows what the container under the cursor ACTUALLY holds, against `screenConfig`'s what-the-compose-file-DECLARES — the two disagree the moment a compose file is edited and the service is restarted (`r`) rather than deployed (`d`). The wedge is `.State.Health.Log[last].Output`, the failing probe's own output: `docker compose config` cannot show it at all, and the `✗` icon plus `VerdictUnhealthy` already make the user ask about it. `Inspector` (`Inspect(ctx, service) ([]byte, error)`) is declared in `tui` beside `ConfigProvider`/`ExecProvider` and type-asserted on the concrete composer, so a composer without it (a test mock) makes `i` a silent no-op. **Three compile-time assertions in `app_test.go` pin the real types to the interface** (`var _ Inspector = (*compose.Compose)(nil)` and the same for `*compose.RemoteCompose` and `*compose.HostContainers`, beside the older `ExecProvider` one, plus a runtime check in `TestHostContainers_CapabilityInterfaces`): the key works entirely through a runtime type assertion and every TUI test drives a double that satisfies it by construction, so without them a rename or a signature drift leaves all 7 packages green while `i` becomes a silent no-op in production. `Inspector` needs this more than its siblings — it is the one capability ALL THREE composers must implement, and it has no `readOnly` gate to make its absence visible. **All three composers implement it, so `i` is NOT gated on `m.readOnly()`** — the asymmetry against every other recent container key is deliberate: every operation is a compose pipeline and an unmanaged container has no compose file, but inspect is read-only by nature and works identically on both variants. It therefore appears in BOTH help tables through ONE shared append in `inspectGroup(readOnly, grouped bool)`, whose position is load-bearing (see the truncation table in `docs/architecture/tui-help-overlay.md`), and `TestHelpGroups_ReadOnlyNamesEveryBoundKey`'s bound set carries `i` too. **`docker inspect` is a top-level docker command, not a compose subcommand**, so all three implementations bypass `command()`/`remoteCommand()` — the rule `docker stats`, `docker image inspect` and `docker buildx imagetools inspect` already follow: `Compose.Inspect` uses `runDockerCmd`, `RemoteCompose.Inspect` uses `runRemoteDockerCmd` (so the `SSHExtraArgs`-before-host splice and `classifySSHError` come for free), and `HostContainers.Inspect` goes through the `dockerRunner` seam's `run`. Resolving the container ID is a SECOND call, so inspect costs two round-trips on a remote hop: the two compose composers list `ps -a --format json` through their own command builder and hand the bytes to `resolveInspectID(psOut, service)` — `parsePsEntries` (array AND NDJSON, the same tolerance `parseContainerStatus` applies to the same output) then `pickInspectContainer`, one home for the middle half both transports share; `HostContainers` reuses `unmanagedEntries` + `pickHostInspectContainer`. The `no container found for %q` text two test suites pin has ONE producer, `errNoContainer(name)` in `inspect.go`, which `resolveInspectID` and `HostContainers.Inspect` both call — the host path builds no string of its own. **`pickInspectContainer` mirrors the Uptime aggregation gate in `parseContainerStatus` exactly** — `entry.State == "running" && uptime != ""` wins, longest duration among running replicas, and a restarting replica only when nothing running has been seen. A naive max-duration picker disagrees with the Uptime column the container screen renders on a running+restarting mix, so `TestPickInspectContainer_MatchesUptimeColumn` drives the SAME entries through both and fails if the two diverge. A service whose replicas are all stopped falls back to the first matching entry (a stopped container stays inspectable); only a service with no entry at all returns `("", false)`, which every caller turns into `no container found for %q` — never a panic and never an arbitrary container. Host containers need no such rule (docker enforces unique names per host), so `pickHostInspectContainer` is a first match on the existing `hostContainerName` helper. **The parse layer lives in `internal/compose/inspect.go`**, beside every other docker-output parser in this repo: `ParseInspect` unwraps the single-element JSON array docker always emits, strips the leading slash off `Name`, and returns the narrow exported `InspectDoc` family — only the fields the five sections render, exported because the renderer lives in `tui` and constructs them directly in its table tests. **That narrowness claim is literal and must stay so**: a parsed-but-unrendered field is a promise the screen does not keep, so `State.Paused/Restarting/Dead/FinishedAt`, `InspectMount.Mode` and `InspectHealthLog.Start` were dropped rather than carried, and `State.Error`, `Name` and `Healthcheck.StartPeriod` earned rows instead — `State.Error` is docker's own reason a container failed to start (`exec: "foo": executable file not found in $PATH`), which the exit code alone cannot give, and `Name` is the only place the summary says WHICH replica the Uptime rule picked, since the breadcrumb names the service. Add a field only together with the row that draws it. `Inspect` still returns raw `[]byte`, so raw mode stays byte-identical to `docker inspect`. `State.Health` and `Config.Healthcheck` are POINTERS because docker omits both keys entirely for an image with no healthcheck, and the HEALTH section is dropped on exactly that distinction (`hasHealthcheck` also drops the explicitly-disabled `Test: ["NONE"]` form); the three `Healthcheck` intervals are `time.Duration`, since docker reports them as nanosecond counts that unmarshal directly. **The renderer is `buildInspectSummary(doc, width, upd inspectUpdateInfo)` in `internal/tui/inspect.go`** (the third parameter arrived with the IMAGE update rows — see the section below; its ZERO VALUE draws no extra row, so everything in this paragraph reads as it did before) — pure, no Model, no TTY, no Docker, golden-testable against the three real fixtures in `internal/compose/testdata/docker_inspect_{healthy,unhealthy,stopped}.json`. Five sections in order — STATE, HEALTH, IMAGE, MOUNTS, ENV — a section with nothing to say is omitted and STATE always renders. **HEALTH enforces that by building its rows into a scratch `inspectBuilder` first** and writing the header only when at least one row exists: `hasHealthcheck` answers "is there a healthcheck", which a zero-valued `&InspectHealthcheck{}` with no runtime state satisfies while having nothing at all to say, so a straight-line render emits a bare header. **Probe output soft-wraps and must NEVER truncate**: it is routinely long and multi-line (curl bodies, stack traces) and it is the feature's whole justification, so every line goes through `inspectBuilder`, which wraps with `wrapCells` and aligns continuation lines under the value column; below `inspectMinValueWidth` the value stacks under its label instead of shredding one rune per line. **`wrapCells` is cell-aware, and that is load-bearing**: it lives in `internal/tui/format.go` beside its sibling `softWrapLine` (the log viewer's), which chunks by RUNE, so a probe output, env value or mount path carrying CJK or an emoji renders at up to 2x the pane width — and an ASCII-only width sweep can never catch it, because runes and cells agree there. It wraps through `ansi.Hardwrap(line, width, true)` (preserving leading whitespace, so stack-trace indentation survives) and `inspectBuilder.kv` measures its label column with `ansi.StringWidth` for the same reason. `TestBuildInspectSummary_NeverExceedsWidth` carries a wide-rune doc and sweeps widths 1-120; a single wide grapheme is 2 cells and cannot be split, so that one doc starts at width 2. **Every line the builder emits is sanitised at ONE chokepoint, `inspectBuilder.push`.** docker's JSON escapes a control byte into printable text, but only the C0 block — Go's `encoding/json` emits DEL and the C1 code points as RAW bytes, so raw mode needs a filter of its own (`sanitizeInspectRaw`, below) — and `ParseInspect` decodes even the escaped C0 back, and an ENV value, a probe output, an image ref and a mount path are all attacker-influenceable: a third-party image can carry an OSC 52 clipboard write, a title set or a report sequence straight onto the operator's terminal the moment `i` is pressed, and `ansi.StringWidth` counts an escape sequence as ZERO cells so neither the wrap nor the viewport stops it. `sanitizeInspectLine` runs `ansi.Strip` and then drops what it leaves behind (BEL, CR, DEL and the 8-bit C1 controls a terminal reads as escape introducers). `section()` is the ONE deliberate bypass — its title carries our own lipgloss style, which IS an escape sequence — so a future section renderer must not be routed back through `push`. **Tabs are expanded BEFORE the measurement, in `wrapCells`** (`expandTabs`, `tabStopWidth` = 8-column stops, cell-aware, also in `format.go` — both helpers are screen-agnostic text utilities, not inspect ones): `ansi.StringWidth` counts a tab as zero cells while a terminal advances to the next stop, so a tab-bearing stack trace in a probe output wraps late and renders past the pane edge — which pushes `viewInspect` past `m.height` and scrolls the title off, the same failure the clamped error line exists to prevent. Expanding also KEEPS the indentation the sanitiser would otherwise delete (a tab is a C0 control), which is why the order is expand-then-strip and why `TestBuildInspectSummary_ExpandsTabs` pins the rendered indent rather than only the width. **Raw mode carries a NARROWER pass of its own, and the difference is the point**: `setInspectContent()` writes `sanitizeInspectRaw(m.inspectRaw)`, which filters the same rune set through the shared `unsafeTerminalRune` predicate but keeps newlines (they are the raw view's line structure) and does NOT run `ansi.Strip` — the ESC bytes arrive already escaped as the six printable characters `\u001b`, so there is no escape sequence to strip and stripping would only corrupt a payload that is safe as it stands. `m.inspectRaw` itself stays verbatim: it is what `ParseInspect` reads, and the filter runs at the render chokepoint. Without it an ENV value or a probe output could carry U+009B (CSI) or U+009D (OSC 52 clipboard write) onto the operator's terminal through `i` then `r` (`TestSanitizeInspectRaw`, `TestInspectDataMsg_RawModeFiltersControlBytes`). NETWORKS, PORTS, RESOURCES and LABELS are deliberately deferred — raw mode answers each, and PORTS duplicates a column the container screen already renders. **No secret masking, deliberate**: ENV is rendered verbatim in both modes, matching lazydocker/k9s/Docker Desktop; the accepted consequence (a screen-share leaks credentials the moment `i` is pressed) is STATED in the README rather than left to be discovered. If masking is ever added it must cover BOTH modes — masking only the summary makes `r` a one-key bypass, which protects nothing. **Mechanics follow `screenConfig`, not `screenLogs`**: `enterInspect()` bumps `inspectSession`, resets the eight `inspect*` fields, sizes the viewport through `inspectViewportSize(m.width, m.height)` — ONE home for the chrome budget, so `enterInspect` and the `WindowSizeMsg` branch cannot drift: `m.height - 6` (the config sizing — NOT the logs `- 7`, which reserves a row for the log bar) with a 3-row floor, and `m.width - 4` with a `< 10 → 40` floor — calls `m.clearSearch()` (one of the eleven departure sites enumerated in `docs/architecture/tui-logs-and-search.md`) and returns `fetchInspect()`, which reads `inspectSession` off the Model exactly as its seven sibling fetch commands do; the `inspectDataMsg` handler is gated on `m.screen != screenInspect || msg.session != m.inspectSession`, and treats a fetch that SUCCEEDED with zero bytes as an error — `rebuildInspectSummary()` early-returns on empty bytes, so `ParseInspect`'s own empty-output error never fires and `viewInspect()` would read `Loading...` for ever with nothing to retry; `esc` calls `clearInspect()` and returns WITHOUT a `refreshStatus()`, because the screen changes no container state — **with ONE exception, which is the only cleanup this screen owes anything to**: in GROUPED mode `i` binds `m.composer` from the CURSOR ROW's group at action time (`bindCursorComposer()`, since the host view holds no composer of its own), so the `esc` return path must call `unbindGroupedComposer()` and dispatch `loadGroups()` — without the unbind the host view keeps serving one project's composer to the next row's action key, and without the reload it repaints from rows that stopped refreshing the moment the inspect screen took the 5-second tick's screen gate away; the `WindowSizeMsg` branch re-renders the summary at the new width without losing `inspectRaw`. Three helpers keep the two buffers honest: `setInspectContent()` is the single `SetContent` chokepoint, so the fetch handler, the `r` toggle and the resize branch cannot disagree about which buffer is on screen; `rebuildInspectSummary()` surfaces a parse failure in `inspectErr`, empties the summary and KEEPS `inspectRaw`, while the switch to `inspectShowRaw` is made by the `inspectDataMsg` handler — the raw bytes are the only content that exists at that point, so leaving the summary selected would show an error line above an empty pane and make the user guess that `r` is the way to the payload, but the switch has to be made ONCE on the transition into the error state and NOT inside `rebuildInspectSummary()`, which also runs on every resize and would then silently undo a later `r` back to the summary (`TestInspectScreen_ResizeKeepsTheChosenModeAfterAParseFailure`) (`viewInspect()` therefore keeps the viewport on screen BESIDE the error line and reads `Loading...` only when there are neither bytes nor an error); `clearInspect()` is the single departure-cleanup helper and deliberately does NOT bump `inspectSession` — `enterInspect()` bumps on the way in, which is what invalidates an in-flight fetch, and the handler's screen check discards one that lands after departure, the same discipline as `configSession`. The `r` toggle calls `GotoTop()` after the chokepoint: `SetContent` preserves `YOffset`, so a toggle from a scrolled summary into the much longer raw JSON would otherwise land the reader mid-document. **`enterInspect()` also calls `SetHorizontalStep(4)`** (the value `enterLogs` uses when wrap is off): raw mode does not wrap and the viewport hard-cuts every line at its width, so with the default step of 0 `left`/`right` are inert and real `docker inspect` output — a `LowerDir` list, a JSON-escaped probe `Output`, lines hundreds of columns wide — is unreachable past the pane edge, in exactly the mode that exists as the escape hatch. **The step is what makes a stale `xOffset` reachable, so `setInspectContent()` resets it on every buffer change** (`SetXOffset(0)` after the `SetContent`, covering the fetch handler, the `r` toggle and the resize branch at once): `SetContent` KEEPS the horizontal offset and `GotoTop()` moves only `YOffset`, so a sideways scroll through the raw JSON survives the toggle back — and because the summary is wrapped to the pane its `longestLineWidth` never exceeds the width, so `visibleLines()` cuts EVERY line at `[xOffset, xOffset+width]` and renders a BLANK pane under a correct title and footer, recoverable only by an undocumented `left`. The raw path resets for the same reason on a resize that widens the pane past the longest line. Pinned by `TestInspectScreen_RToggleAfterSidewaysScrollKeepsSummaryOnScreen` and `TestInspectScreen_ResizeClearsStaleHorizontalOffset`; `← →` is named in the `screenInspect` MOVE group and `left`/`right` are in that screen's `bound` row. **The footer drops its `r` token whenever the buffer the toggle would switch TO is empty** — a failed FETCH leaves neither buffer, a failed PARSE leaves the raw bytes but no summary, and in both states the toggle could only relabel itself over an empty pane. The `r` case and the footer read ONE predicate, `inspectToggleAvailable()`, so the key and its advertisement cannot disagree; testing `len(inspectRaw) == 0` instead covers only the fetch half and leaves `r summary` on screen after a parse failure (`TestViewInspect_FooterDropsRWithoutBuffers`, `TestInspectScreen_RIsInertWithoutBuffers`, `TestViewInspect_ParseErrorShowsTheRawBytes`). **The footer is clamped for the same budget**: it measures 42 cells, so below 42 columns both its line and the `helpStyle` margin line wrap, add two physical rows the renderer does not know about, and cost the title — `clampToWidth` holds it the way `containerFooter()` does, and `TestViewInspect_ErrorIsOneClampedLine` plus `TestViewInspect_FooterNeverExceedsWidth` sweep widths 40-120 rather than sampling one. The HEIGHT half is `TestViewInspect_FitsShortTerminal` (heights 9-30 at three widths, with and without the error line — the sibling of `TestViewHelp_FitsShortTerminal`) and `TestViewInspect_NoTrailingNewline`, which pins the invariant it rests on: bubbletea splits `View()` on `\n` with no `TrimSuffix` and keeps the LAST `m.height` elements, so a trailing newline renders one line too tall and costs the title. `viewConfig` and `viewLogs` carry the same unclamped footer (and unclamped title) — pre-existing and out of this feature's scope, recorded as a residual. **The error slot is collapsed and clamped**: `viewInspect()` budgets exactly ONE line for it, but the compose layer feeds raw stderr in (`withStderr`, an SSH banner, a multi-line docker failure), so the message runs through `strings.Fields`+`clampToWidth` — the same never-wrap discipline `searchBarLine`/`logBarLine`/`containerFooter` follow. Without it the renderer keeps only the last `m.height` lines and the title, plus the head of the error that names what failed, scrolls off. **The `WindowSizeMsg` branch calls the same `inspectViewportSize` helper**, so the floors cannot be a hand-maintained mirror: unguarded, a 3-column pane sets a negative width and `buildInspectSummary` falls back to its 80-column default for a viewport that renders nothing. `screenConfig` and `screenLogs` still carry that asymmetry between their `enter*` helper and their resize branch — inherited, and out of this feature's scope. The screen opens no text input, so `typingInInput()` needs no case and `q` reaches the existing `default: key = "esc"` rewrite. **The view is a one-shot snapshot, with ONE exception.** `fetchInspect` is called from exactly one place (`enterInspect`), the 5s `refreshTickMsg` is gated on `screenSelectContainers`, and `r` only swaps two buffers already in hand — so health status, failing streak and the probe output are frozen at the instant `i` was pressed, and `esc` then `i` is the only refresh. The exception is the update rows: an `updatesMsg`, an `updateDetailsMsg` whose `forKey` is the context on screen, or the screen's own `inspectDetailMsg`, calls `redrawInspectFromCache()`, which rebuilds the summary so the IMAGE update rows can arrive (or leave) on their own. Nothing `docker inspect` returned is re-FETCHED — the one fetch the screen makes for itself resolves those rows and touches no part of the container document — so the snapshot property still holds for everything in it. `screenConfig` behaves the same way; a refresh key is a recorded follow-up, and the README states the behaviour rather than leaving it to be discovered. TUI-only: no CLI subcommand, no `Composer` change (the four mock sets are untouched) and no ID field on `runner.ServiceStatus` — the ID lookup stays inside `compose`, behind `Inspect`.

## Inspect screen — the IMAGE section's update rows

The IMAGE section grew four rows: `built`, `update`, `update id` and `update built`. Three of them draw only when the `⇧` update check has something to say about the service; `built` was in that set at first and is no longer — it is drawn from the inspect fetch's own image probe and reads nothing out of the update cache (see the section below it). They sit BETWEEN `image id` and `command`, so the two ids and the two build dates read as one block — `image id` against `update id`, `built` against `update built`:

```
IMAGE
  image         postgres:16-alpine
  image id      sha256:7e7dbab8…
  built         2026-07-07 17:47:22  (47d ago)
  update        available  (checked 3m ago)
  update id     sha256:c05eced0…
  update built  2026-08-19 19:14:43  (4d ago)
  command       postgres
  entrypoint    docker-entrypoint.sh
```

The full row order is therefore `image`, `image id`, `built`, `update`, `update id`, `update built`, `command`, `entrypoint`.

`TestBuildInspectSummary_UpdateRowOrder` pins that order, because the pairing is the row block's whole argument — an `update id` two rows away from the `image id` it is meant to be compared with is just another digest on screen.

**The `digest` row was relabelled `image id` in the same change.** It has always been the local image ID docker resolved the tag to, and an `update id` row beside a row still labelled `digest` invites exactly the false comparison the feature must avoid: `update id` is the registry image's CONFIG digest (which equals the image ID the daemon will assign after a pull), NOT the manifest-list digest `CheckUpdates` compares. The rename is user-visible and had four assertions pinning the old label, which is why it landed as an isolated commit.

**Each row keys off its OWN input, and the renderer never infers one from the other.** `built` needs a non-zero `doc.ImageCreated` — the image probe's own answer, and its only source (see below); `update` needs a non-nil verdict (`available` on `true`, `up to date` on `false`, nothing at all on `nil`); `update id` needs a non-empty `NewID`; `update built` needs a non-zero `NewCreated`. So a detail with no verdict still draws the three detail rows, and a verdict with no detail still draws `update` — a future caller that fills only half the struct cannot make the section claim something it was not told. The `(checked 3m ago)` suffix comes from the cache entry's `fetchedAt` and is dropped when that is zero, rather than reported as "moments ago": a missing timestamp is not a fresh one.

**The section's presence gate is UNCHANGED.** A doc with no image, no command and no entrypoint stays silent even when a verdict is in hand. An update verdict describes the image, so a section opened by the verdict alone would carry one row with nothing to compare it against.

**`buildInspectSummary(doc, width int, upd inspectUpdateInfo)` — the signature widened, and the zero value is what made that mechanical.** `inspectUpdateInfo{now, detail, verdict, checkedAt}` carries the clock as a FIELD rather than a `time.Now()` call inside the renderer. `verdict` is a `*bool` because it is a genuine tri-state; `detail` is a VALUE (`compose.UpdateDetail`), not a pointer, because every field of it is already checked on its own, so a zero struct and an absent one draw the same nothing — the pointer bought no state and only split the renderer into two nil-checked blocks around the verdict row, so the function stays pure and the relative ages are testable against a fixed `now` (`TestBuildInspectSummary_UpdateRows`, `_UpdateRowsEpochSentinel`, `_UpdateRowsWrapNarrow`). **Its zero value must keep drawing no new row** — that property is what let the 25 existing call sites migrate by appending `inspectUpdateInfo{}` with every pre-existing assertion intact, and `TestBuildInspectSummary_ZeroUpdateInfoIsByteIdentical` pins it. There is exactly ONE production call site, inside `rebuildInspectSummary()`; the `WindowSizeMsg` branch and the `inspectDataMsg` handler both go through that helper, so they inherited the change untouched. `rebuildInspectSummary` builds the struct itself from `m.currentUpdateInfo()` — one lookup, one site, no chance of three copies drifting.

**The BATCH's rows are read, never asked for; the screen fetches only the ONE service it renders, and only when no batch has reported** (the section below owns that rule). The batch rides the `refreshUpdates` schedule (on a follow-up `updateDetailsMsg`, not the verdict message) and lands on the same `updateEntry`, which is why entering `i` on a cold cache needs `redrawInspectFromCache()` — called by all three handlers — to rebuild the summary. That helper skips the viewport write while `inspectShowRaw` is on, because the raw buffer is unaffected by update details and rewriting it would only reset the horizontal offset out from under a sideways scroll — see the `UpdateDetailer` section of `docs/architecture/update-detection.md` for the fetch sequence, the rate-limit mitigations, the three-state index result and the epoch sentinel that omits the two build-date rows. Two consequences land here: **no departure site owes this machinery a reset**, so `clearInspect()`, the `esc` chain, `entryLocal` and the `connectResultMsg` error path leave both of its fields alone — `inspectMemo` expires with the cache entry its identity names rather than with the visit (below), and the update subsystem's own `detailsInFlight` guard is a global one-batch bound cleared only on message arrival; and **`inspectViewportSize()` is unchanged**, because the new rows live inside the viewport rather than in the chrome budget. (That is about the UPDATE-DETAIL machinery specifically — the screen still owes the grouped-mode composer unbind and reload named above.) The longest new label is `update built` — `"  update built"` is 14 cells against `inspectValueCol = 18` — so no layout constant moves either, and the rows soft-wrap through `inspectBuilder.push` like every other content line rather than truncating. **Raw mode stays byte-identical**: `m.inspectRaw` never sees these values, pinned by `TestInspectScreen_RawModeIgnoresUpdateDetails`, which compares raw output with and without a populated cache and uses the differing summary as its control.

## Inspect screen — the screen's own detail fetch (`inspectMemo`)

**The screen fetches the ONE service it renders, because GROUPED mode dispatches no batch at all.** The host view holds no composer of its own, and one an armed `x` prompt left bound belongs to whichever row the cursor was on, so a batch built from it would resolve the wrong project's images (`docs/architecture/tui-multi-project.md`) — `update id` and `update built` were therefore absent on every grouped row, on every visit. A batch is the wrong shape here anyway: `compose.UpdateDetail` has exactly ONE render site and that site draws ONE service, so a batch resolves N to draw 1. `detailsCmdFor(entry, key)` holds that whole decision beside `updateDetailsCmd` — drilled gets the batch, grouped gets this fetch when the inspect screen is up on a matching key, nothing otherwise. `TestGroupedU_FetchesNoDetailBatch` is the pin recording that the batch approach was NOT taken; `TestGroupedInspect_FetchesItsOwnDetailRows` pins the symptom end to end.

**It is a SECOND message, chained off the document's arrival.** Registry round-trips must not hold the container document — the same boundary `updateDetailsCmd` draws between the verdicts and their rows, for the same reason. The local image probe behind `built` goes the other way and rides the inspect fetch itself (next section), because it is ONE LOCAL call: the split follows the COST, not the subsystem.

**It NEVER writes `entry.details`, and never touches `detailsInFlight` — the most important rule here.** `refillUpdateDetailsCmd` reads a non-nil `details` map as "a batch has reported", so filling it with this one service would tell it one had, and strand every OTHER updated service of that entry for its full 10-minute TTL: a display gap traded for a data gap, on a later drill-in with no way left to ask. `detailsInFlight` is left alone for the same reason — it bounds the BATCH phase, and one service is not a batch, so a batch running elsewhere must neither blank these rows nor be blocked by them. Pins: `TestInspectDetail_LeavesTheCacheAndTheGuardAlone`, and `TestInspectDetail_LeavesTheRefillToTheBatch`, which asserts the refill still asks for every updated service after the screen has asked for one.

**`inspectDetailMemo` is a ONE-SLOT memo whose identity is `(key, service, entry.fetchedAt)`**, and each third of that earns its place. Because nothing is written back, the entry keeps `details == nil` for its whole TTL, so without the memo every `i` on a grouped row re-spent one local probe and up to three registry calls, unbounded (`TestGroupedInspect_RepeatVisitSpendsNoSecondFetch`). The cache entry's own `fetchedAt` is what makes the memo die with the entry it describes: a fresh `U` writes a new stamp and the next `i` pays once more, so no departure site owes it a reset — and the zero memo answers nothing, since every cache key carries the NUL separator an empty key cannot match. The SERVICE is in the identity because two updated services share ONE entry, so a `(key, fetchedAt)` memo would answer `db` with `web`'s `update id`, drawn confidently under a row block whose whole purpose is to invite that comparison (`TestInspectDetail_MemoIsPerService`). One slot rather than a map: the screen shows one service, the repeat this exists to stop is `i` on the SAME row, and a slot cannot grow across a session. `currentUpdateInfo()` reads it through `answers()` and only when `entry.details` yields the zero struct, so a batch always wins whole.

**The identity travels WITH the message, and the handler's trust is SPLIT.** `inspectDetailMsg` carries `forKey`/`forEntry` captured at DISPATCH and the handler never re-derives them: an `updatesMsg` can replace the entry while the screen is up and under the SAME session, so a handler-time read would file one entry's rows under another's stamp — and thereby suppress the fetch that entry is owed. The SERVICE comes from the Model instead, because the session gate pins the visit and one visit inspects one service. **A superseded reply therefore draws NOTHING**: `answers()` refuses it, so rows tied to a scan the screen has moved past never paint, and the `updatesMsg` that superseded the entry is what dispatches the fetch that fills them (`TestGroupedInspect_SupersededReplyDrawsNoRows`).

**The verdicts' own arrival is the SECOND trigger, and it is not redundant.** The fetch chained off the document finds no entry at all while `U`'s scan is still in flight, and the document almost always wins that race — it costs three LOCAL docker calls against `CheckUpdates`' registry round-trip per image. Nothing on `screenInspect` binds `U`, so without the second trigger the rows stay absent for the whole visit. It fires from the `updatesMsg` SUCCESS branch, grouped, on `screenInspect`, and only for `key == m.inspectUpdateKey()`.

**The refusal set is what keeps this off the registry.** The verdict must be `true`, the entry present and non-errored, and `entry.details` still nil — the chained fetch is NOT mode-gated, so in DRILLED mode it fires only in the window before the batch reports and refuses for ever after. The screen therefore never spends a round-trip the `⇧` column would not have spent, which is also what makes it safe without `autoUpdatesAllowed()`: it can only fire for an entry that already exists, and under a read-only key only `U` creates one (`docs/architecture/update-detection.md`). The empty-service guard saves the discovery call `UpdateDetails` makes BEFORE it filters — one SSH round-trip on the remote path, for a name that matches nothing; **it is NOT a 429 guard**, because `[]string{svc}` is never the empty slice `filterServices` reads as ALL SERVICES. A parse failure returns ahead of all of it: no summary is built and every redraw re-parses the same bytes and fails again, so the rows have nowhere to land and the fetch would spend one local probe and up to three registry calls on a result nothing could render (`TestInspectDetail_ParseFailureSpendsNoFetch`). `TestInspectDetail_ReportedBatchCostsNoSecondFetch` pins the drilled half — an entry a batch already filled costs the screen nothing.

**The key is `inspectUpdateKey()`'s, the same resolution `currentUpdateInfo` makes.** In grouped mode the entry belongs to the CURSOR row's group; `updatesCacheKey()` resolves there to the degenerate `"\x00|<server>"`, which names no entry at all, so the fetch would refuse on every grouped row — in exactly the mode it exists for. `TestGroupedInspect_DetailFetchAsksOneServiceOfTheCursorGroup` pins both halves: the cursor row's group is asked, for exactly `[[api]]`, and no other group is asked at all.

## Inspect screen — the `built` row is NOT an update row

`built` describes the image the container is running RIGHT NOW, so it must not depend on an update verdict. It did, for one release: its only source was `compose.UpdateDetail.LocalCreated`, filled by step 1 of the four-step detail fetch — and that batch is dispatched only for services whose verdict came back `true`, only in DRILLED mode, and only once the update cache is warm. An up-to-date container therefore showed `image`, `image id`, `update up to date` and no build date at all, and so did every container in the grouped host view, on the read-only unmanaged screen, and on a cold cache.

**Widening the detail fetch was rejected.** Making `UpdateDetails` resolve the local half for all services fixes none of the three contexts above — no detail batch is dispatched in grouped mode at all — and it pushes on the `servicesWithUpdate` filter, which is one of the three load-bearing mitigations against Docker Hub's anonymous rate limit (`docs/architecture/update-detection.md`).

**The build date is instead part of the inspect fetch itself.** `compose.InspectDoc` carries `ImageCreated time.Time`, tagged `json:"-"`: the container document's own top-level `Created` key is when the CONTAINER was created, not when its image was built, so an untagged field would unmarshal a confidently wrong date straight into the row (`TestParseInspect_NeverFillsImageCreated`). `tui.ImageInspector` — `ImageCreated(ctx, image) (time.Time, error)`, declared beside `Inspector` and type-asserted the same way — is implemented by all three composers over `fetchImageCreated`, which is step 1 of the detail fetch reused verbatim: `localProbeArgs` + `parseLocalProbe`, a TOP-LEVEL `docker image inspect` through the `dockerRunner` seam, purely LOCAL, no registry traffic and nothing that can trip a 429. Reuse rather than a second parser is the point: `localProbeFormat` is `{{json .}}` and NAMES NO FIELD, because a template naming a field the CLI's struct lacks is a hard execution error — a second, hand-written `--format` is the regression that rule exists to prevent.

**It rides the SAME Cmd and the SAME message.** `fetchInspect` type-asserts `ImageInspector` beside `Inspector`, and after `Inspect` returns it parses the document (a pure call), reads `doc.ImageRef()` and probes. One message keeps the screen the one-shot snapshot it is documented to be, and keeps `inspectSession` the only gate. The cost is one extra local docker call — one more SSH round-trip on a remote hop, against the two the screen already makes. This is deliberately NOT the message split `UpdateDetailer` needed: that one holds verdicts behind up to three REGISTRY round-trips per image, this is one local inspect.

**Every probe failure is DISCARDED and yields the zero time**: a composer that is not an `ImageInspector`, a document the narrow parser cannot read, a document naming no image, and the probe itself. The row is omitted and the rest of the container document renders untouched — the same asymmetry the update rows follow, where the container view is load-bearing and the image annotation is a bonus. A probe failure must never reach `inspectErr` (`TestFetchInspect_ProbeFailureIsDiscarded`, `TestInspectScreen_ProbeFailureKeepsTheDocument`).

**`doc.ImageRef()` prefers the resolved ID over the config's tag.** `docker inspect`'s `.Image` is the image ID the daemon resolved the tag to, so it addresses exactly what the container runs even after the tag has been moved to a newer image; `.Config.Image` is the fallback for a document carrying no ID at all (`TestInspectDoc_ImageRef`).

**The merge happens on every re-parse, not once.** `Inspect` still returns raw `[]byte` — raw mode stays byte-identical to `docker inspect`, which is why the probe result has nowhere to ride inside the payload — and `rebuildInspectSummary()` re-parses those bytes on every resize and every cache redraw. So the probed date lives on the Model as `inspectImageCreated` (the eighth `inspect*` field, reset by `enterInspect()` and `clearInspect()` like the other seven) and is assigned onto the freshly parsed doc each time. Drop that one line and the row never draws AT ALL: entry goes through the same `rebuildInspectSummary()`, and `ParseInspect` cannot fill a `json:"-"` field, so every parse yields the zero time — `TestInspectScreen_ResizeKeepsTheBuiltRow` then fails at its PRECONDITION rather than at its resize assertion. The appear-on-entry-then-vanish failure is a DIFFERENT mutation, and the one the resize half of that test actually guards: merging `msg.imageCreated` into the summary inside the `inspectDataMsg` handler and never keeping it on the Model.

**`built` has ONE source, `doc.ImageCreated` read inline by `inspectImageSection`, and a failed probe draws NO row.** `compose.UpdateDetail.LocalCreated` looks like a free fallback for the two cases the probe cannot cover — a composer that is not an `ImageInspector`, and a probe that failed while the detail batch had already resolved a date — and it was one for one commit. It is wrong, because **the two values address DIFFERENT image references**: `doc.ImageCreated` is probed against `doc.ImageRef()`, the container's RESOLVED image ID, while `LocalCreated` comes from `fetchServiceImages`, which reads the TAG `docker compose config` declares. A local `docker pull nginx:1.27` moves that tag while the container keeps running the old image, so the fallback would label a `built` date belonging to an image the container is not running — silently, in the one row whose entire purpose is to say when THIS image was built. A wrong date is worse than no date, and the failure has no tell on screen. The arm was removed rather than made conditional: all three production composers implement `ImageInspector`, so the only way to reach it is a probe FAILURE, which the paragraph above already contracts as "no row, discarded silently". `update id` and `update built` keep `upd.detail` as their ONLY source — those genuinely describe the registry image. Pins: `TestBuildInspectSummary_BuiltRowSource` (the one source, the drawn-once count and the epoch guard), `TestBuildInspectSummary_UpdateRows` (the row's own conditions), `TestInspectScreen_BuiltRowNeedsTheProbe` (the whole path on a composer that is not an `ImageInspector`, with a `LocalCreated` in the cache that must not be borrowed), `TestInspectScreen_BuiltRowIgnoresTheVerdict` (the whole path, with a FALSE verdict in the cache), `TestInspectScreen_UpdateRowsFollowTheVerdict` (which counts `built` neither among the verdict-following rows nor among the cache's), `TestInspectKey_EntersOnReadOnlyComposer` (the row on the unmanaged screen), and the three `var _ ImageInspector` compile-time pins plus the runtime check in `TestHostContainers_CapabilityInterfaces`.

## Config screen (`c`)

`screenConfig` is the inspect screen's counterpart — what the compose file DECLARES, against what the container HOLDS — and unlike inspect it can also WRITE, through `$EDITOR`. `c` opens it from the container screen with no confirmation, because reading a file changes nothing; the edit that follows is guarded by the editor itself rather than by a `y/n` prompt. `ConfigProvider` (`ConfigFile`, `ConfigResolved`, `EditCommand`, `ValidateConfig`) is type-asserted when the key is pressed, so a test mock makes `c` a silent no-op (`TestConfigScreen_CKeyIgnoredWithoutConfigProvider`), and the three fetch helpers repeat the assertion rather than trusting the entry check — each returns a nil `tea.Cmd` on failure, so a composer swapped out from under the screen produces no message instead of a panic (`TestFetchConfigHelpers_RequireConfigProvider`).

**`c` is the one provider key in this file that IS gated on `m.readOnly()`, and the gate is deliberate rather than free.** `*compose.HostContainers` implements neither `ConfigProvider` nor `RollbackPreparer` (pinned as a NEGATIVE assertion in `TestHostContainers_CapabilityInterfaces` — the compile-time `var _` form can only pin the positive direction), so the type assert would already refuse. The explicit gate exists so the key and the read-only help table move together; the full argument is in `docs/architecture/unmanaged-containers.md`. In GROUPED mode there is a SECOND refusal ahead of it: a cursor sitting in the `(unmanaged)` bucket is rejected BEFORE `bindCursorComposer()` runs, because binding it could only produce a composer the assertion below then rejects (`TestGroupedScreen_ConfigRefusedOnUnmanagedGroup`). Every refusal path calls `unbindGroupedComposer()` and `fixSvcOffset()`, and the `esc` return does the same plus a `loadGroups()` dispatch — for exactly the reason the inspect screen's `esc` does: this screen fires no status refresh of its own, so grouped mode has to ask for the host view explicitly, and the composer it bound at press time was the only thing that could have answered a per-project one.

**`r` toggles raw against resolved, and the resolved half is lazily fetched ONCE and cached** (`configResolved`, `docker compose config`): entering the screen costs a file read, and the interpolation round-trip is only paid by a user who asks for it. **A resolved fetch that FAILS does not become `configErr` while raw content is in hand** — it flips `configShowRes` back to false, re-renders the raw buffer and reports the failure through the VALIDATION slot instead (`configValid = false`, `configValidMsg = "resolved config failed: …"`), so the user keeps a readable pane and the error names itself under it. Only when there is no raw buffer to fall back to does it become `configErr` and take the pane. `TestConfigScreen_ResolvedErrorResetsToggle` pins the toggle reset; without it the screen shows an error line above a pane still labelled `r raw`, and pressing `r` refetches the same failure.

**`e` runs the editor where the FILE is, not where cdeploy is.** Local `EditCommand` resolves `$EDITOR`, then `$VISUAL`, then falls back to `vi`, and splits a multi-word value into executable plus args (`code --wait` works); remote `EditCommand` builds its own SSH argv with `-t`, `cd`s into the project directory and runs `${EDITOR:-vi}` **on the docker host**, so it is the host's editor and the host's `$EDITOR` that apply — the laptop's are irrelevant. Both go out through `tea.ExecProcess`, which suspends Bubble Tea and hands over the terminal. On return, `configEditDoneMsg` invalidates the resolved cache (`configResolved = nil`, `configShowRes = false` — the file just changed, so a cached interpolation of the old bytes would be a lie) and returns `tea.Batch(fetchConfigFile, fetchConfigValidate)`: re-read and re-validate concurrently, which is what turns a syntax error introduced in the editor into a visible `Config error: …` line rather than a surprise at the next deploy (`TestConfigScreen_EditDoneTriggersFetchAndValidate`, `TestConfigScreen_EditDoneError`). `ValidateConfig` is `config --quiet` run through `CombinedOutput`, so compose's own reason reaches the user instead of a bare exit status.

**Which file the screen shows follows the picker row, not a probe.** `Compose.findComposeFile` returns `ComposeFiles[0]` whenever docker reported the project's own file set, and only falls back to probing the four canonical names in `composeFiles` for a composer built from a bare directory (the local fast track, every CLI verb). The probe alone would show and edit a SIBLING project's `docker-compose.yml`, and would report "no compose file found" for a project whose only file is `stack.yml`. `RemoteCompose.findRemoteComposeFile` short-circuits the same way and its probe is ONE SSH command — a `for f in …; do test -f … && echo $f && break; done` loop — rather than four round-trips. The two spellings then diverge: the probe returns a BARE name to be joined onto `ProjectDir`, while a `ComposeFiles` entry is already ABSOLUTE (docker reports it that way), so `ConfigFile` prefixes only when the name does not start with `/` — without that check the `cat` runs against `/srv/app//srv/app/prod.yml`.

**Stale-message discipline is `logsSession`'s, applied to `configSession`**: `enterConfig()` bumps it, every fetch captures it, and all four handlers (`configFileMsg`, `configResolvedMsg`, `configEditDoneMsg`, `configValidateMsg`) gate on `m.screen != screenConfig || msg.session != m.configSession` (`TestConfigScreen_StaleMessageDiscarded`, `TestConfigScreen_StaleMessageDiscardedWhenNotOnScreen`). `esc` clears every `config*` field including the viewport itself (`TestConfigScreen_EscCleansUp`) and does NOT bump the session — the entry bumps, the screen check discards, exactly as `clearInspect()` does.

**The two sizing sites are a hand-maintained mirror, and they do not agree.** `enterConfig()` sizes the viewport `m.height - 6` with a 3-row floor and `m.width - 4` with a `< 10 → 40` floor; the `WindowSizeMsg` branch repeats the height and its floor but carries **no width floor at all**, so a resize below 5 columns sets a negative width where the entry path would have used 40. That asymmetry is pre-existing (`screenLogs` carries the same one) and is what `inspectViewportSize()` was extracted to avoid for the third screen — a config-side fix belongs with a helper of its own, not with a second copy of the floors. The `- 6` is also NOT the logs `- 7`: the log viewport reserves one row for the log bar this screen has no equivalent of, and the code carries an inline `do NOT unify these` for the find-and-replace that would otherwise cost the config title a row.

`enterConfig()` is one of the eleven `clearSearch()` departure sites (the list is in `docs/architecture/tui-logs-and-search.md`). The `?` overlay's VIEW group names `r raw / resolved` and `e edit in $EDITOR`; the footer relabels itself `r resolved` / `r raw` from `configShowRes` so the token always names the DESTINATION. Neither `viewConfig`'s title nor its footer is width-clamped — the same residual `viewLogs` carries, recorded in the inspect section above rather than fixed here.

## Exec into container (`x`)

`x` drops the user into a shell inside the container under the cursor. `ExecProvider` has one method — `ExecCommand(ctx, service, command) (*exec.Cmd, error)` — and **it RETURNS the command rather than running it**, so the caller owns execution: the TUI hands it to `tea.ExecProcess` (which suspends Bubble Tea and gives the process the whole terminal), `cmd/exec.go` hands it to the injectable `execRunCmd`. A capability that ran the command itself could not be driven by either without a second seam.

**All three composers implement it, so `x` is NOT gated on `m.readOnly()`** — the same reach `Inspector` has, and the same consequence: the key is named in the read-only help table and in the read-only footer pair. `var _ ExecProvider = (*compose.HostContainers)(nil)` in `app_test.go` pins it at compile time and `TestHostContainers_CapabilityInterfaces` re-checks it at runtime, because every TUI test drives a double that satisfies the interface by construction — without the pins a signature drift leaves the package green while `x` silently dies on the one screen that has no other way in. The three argv shapes differ and each has its own reason: local goes through `command()`, so it is a plain `docker compose exec <service> <command…>`; remote BYPASSES `remoteCommand()` to build its own SSH argv with `-t` for TTY allocation, which is why it has to splice the `-p` flag itself through `composeFlags()` (`docs/architecture/compose-command-and-status.md`); and `HostContainers` emits `docker exec -it <container> <command…>` through the `dockerRunner` seam's `tty` method, with `-it` explicit because plain `docker exec` allocates nothing of its own (`docs/architecture/unmanaged-containers.md`).

**`DefaultExecCommand` (exported from `internal/compose/compose.go`, so all three implementations and the CLI share one default) is `[]string{"/bin/sh", "-c", "command -v bash >/dev/null 2>&1 && exec bash || exec sh"}`, and the shape of the bash probe is a failure record.** `/bin/sh` is the outer binary because it is the one thing an Alpine or distroless-adjacent image can be relied on to have; bash is tried first because it is the better interactive shell. The probe is a SEPARATE `command -v` rather than a redirect on the exec itself: writing `exec bash 2>/dev/null || exec sh` silences bash's stderr **for the entire session**, which breaks the prompt and tab completion in a way that looks like a broken container rather than a broken command. Redirect the probe, never the exec.

**The press-time gate order is cursor → bind → assert → RUNNING → arm.** A cursor on no service, a bind failure and a failed `ExecProvider` assertion each return early; then `m.svcStatus[m.svcKeyAt(m.svcCursor)]` must report `Running`, or the screen shows `Container is not running` and stops (`TestExec_XKeyOnStoppedServiceShowsWarning`, `TestExec_XKeyOnServiceWithNoStatus` — an absent status entry counts as not running). Only then does it set `confirming` + `pendingExec`. Every early return calls `unbindGroupedComposer()` and `fixSvcOffset()`, the second because the dispatch cleared `m.warning` above the switch and the freed footer row changes `svcVisibleCount()`. **`x` is the one action key that KEEPS its grouped binding across the prompt** — the reason, and its consequence for `readOnly()` in grouped mode, are in `docs/architecture/tui-multi-project.md`.

**`enterExec()` runs on the confirming `enter`, and its refusal path owes more than a plain cancel.** A refusal — no `ExecProvider`, no cursor service, or an `ExecCommand` that errored — closes the prompt while STAYING on the container screen, so it cannot rely on `containerFetchBatch` (only reached by LEAVING) to settle anything. The shared `refuse()` closure therefore clears both flags, unbinds, calls `takeSvcReload()` to settle a drilled reload the armed prompt dropped, and re-clamps: without the first the flag sits set until some later prompt happens to close (`TestEnterExec_RefusalSettlesThePendingReload`), without the second the freed footer row leaves a blank line under a scrolled list (`TestEnterExec_RefusalReclampsOffset`). `clearSearch()` is called on the SUCCESS path only — a refusal keeps the user on the screen, and the search is only ephemeral across a departure. The exec always requests the DEFAULT command (`ExecCommand(ctx, service, nil)`); the TUI has no way to type one, which is what `cdeploy exec <service> -- …` is for.

**`execDoneMsg` carries NO session and is gated on the screen alone** — the exec suspends the whole program, so nothing else can be in flight to confuse it, and its own arrival is what re-establishes the context. It resets `pendingExec`/`confirming`, turns a non-nil error into `m.warning` (`exec failed: …` — never a screen of its own), unbinds the composer `x` held across the prompt, then treats its own return as a context change: `bumpFetchSessions()`, `statsRequested = true`, `refreshInFlight = true`, `updateInFlight = false` (the session bump just invalidated any pending `updatesMsg`, so the in-flight guard must not refuse the replacement) and `containerFetchBatch(false)`. **It is a full refresh batch, not a `refreshStatus()`** — a shell session can start, stop or kill anything, so status, stats and updates all have to be re-asked (`TestExec_ExecDoneMsgRefreshesStatus`, `TestExec_ExecDoneMsgWithErrorStillResetsState`, `TestExec_ExecDoneMsgStaleMessageGuard`, `TestExecDone_bumpsStatsSession`).

The CLI half is `cdeploy exec <service> [-- command...]`, built on the `cmd/logs.go` skeleton — `checkRemoteMutex` first, then the `--ssh` / `--server` / local branch described under "Adding New CLI Subcommands" in `CLAUDE.md`. The `--` is optional: `ArgsLenAtDash()` is preferred when present, and everything after the service name is otherwise taken as the command, so `cdeploy exec db psql -U postgres` and `cdeploy exec db -- psql -U postgres` are the same call.
