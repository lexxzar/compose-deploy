## Multi-project host view — grouped vs drilled, the entry model, and `svcKey`

the container screen has TWO modes and one row model. GROUPED is the host view: every compose project on the host plus the synthetic unmanaged bucket, each a foldable group. DRILLED is the single-project screen that existed before, reached by pressing `enter` on a group header (or by the local fast track). **`m.grouped` is an explicit field, never a `len(svcGroups) > 1` inference** — a host can legitimately run exactly one project and the drilled screen is always one group, so the two shapes are indistinguishable by count. **`svcGroup{proj, services, folded}` is the source of truth and `svcEntry{kind, groupIdx, name}` is DERIVED** by `rebuildSvcEntries`: one header per group then its services, a folded group contributing only its header. Never write `svcEntries` by hand — `setSingleGroup`/`setGroups` are the only writers of the pair, `clearSvcGroups` the only wipe. **A single group emits NO header at all**, and that degenerate shape is what makes the drilled screen render byte-identically to what it drew before grouping existed (`TestViewSelectContainers_SingleGroupHasNoHeaderOrIndent`). The predicate behind it, `groupsHaveHeaders(groups)` / `Model.hasGroupHeaders()`, feeds BOTH the entry model and the renderer's 2-cell service indent — **not `m.grouped`**: a grouped host that happens to hold one project would otherwise indent its rows under a header that does not exist (`TestViewSelectContainers_GroupedSingleProjectHasNoIndent`). **Folding hides ROWS, never services.** `svcRefs()` walks every service in every group and deliberately ignores fold state, so selection, counting and the column-width pass go through it rather than over `svcEntries` — the alternative drops a folded group's selected services out of the operation the user armed (`TestSelectedContainers_IncludesFoldedGroup`) and re-flows every column the moment a group closes. **Nothing may be keyed on a ROW INDEX across a rebuild**: a fold renumbers every row below it, which is exactly why `m.selected` became `map[string]bool` rather than staying `map[int]bool` (`TestSelection_SurvivesFoldRebuild`). The key producer is `svcKey(projName, service)` = `proj + "/" + service`, and `/` is safe because docker compose rejects it in both a project name and a service name, so no pair can produce an ambiguous key (`TestSvcKey_Distinctness`). Two projects on one host each owning a `db` is the common case, not the exotic one, and a bare-name map lets one silently overwrite the other (`TestQualifiedKeys_DuplicateServiceNamesStayDistinct`). **Qualified keys live ONLY inside the tui Model** — `svcStatus`, `stats`, `selected` and the render caches (`portsStr`/`cpuStr`/`memStr`) all use them — and **every message boundary converts**: `qualifyMap(projName, src)` for a drilled bare-name payload, `flattenQualified(host)` for the grouped project → service payload. Nothing qualified travels back out to `runner` or `compose`: `selectedContainers()`, `opContainers`, `rollbackTargets` and the `NewWaitState` seed all carry BARE names, pinned at the boundary by `TestQualifiedKeys_NeverCrossIntoRunner`. `ownerProjName()` names the owner of an incoming bare payload — one installed group means that group's project, with `m.projName` as the fallback for a payload landing before `setSingleGroup` has run — and `hydrateUpdates` keeps its skip-unknown-name rule, now measured in the same key space the map is stored under. The row-model helpers live in `entries.go` beside the types, not in `app.go`: `svcKeyAt(i)` (empty on a header or out of range — the OWNING group decides the prefix, never the Model's current project), `cursorEntry()`, `cursorService()` (false on a header; every "the service under the cursor" key reads it, because indexing `m.services` by `svcCursor` is wrong once headers occupy rows of their own), `cursorGroup()` (the header-accepting twin — a header IS its group, and the keys that act on a whole project are exactly the ones a header should answer), `groupUnmanaged(gi)` and `selectableRefs()` (`svcRefs` minus the unmanaged bucket). `clampSvcCursor()` is a separate helper from `fixSvcOffset()` because the grouped reload is also the periodic refresh: the row count can shrink under a cursor that was valid a moment ago, and `fixSvcOffset` only moves the WINDOW (`TestGroupedServicesMsg_ShrinkClampsCursor`). `m.services` survives as the flat name list of every service in every group — the screen still reads it for the "have we loaded anything yet" test, the empty-list guards on the action keys and the search-counter width budget — so a nil slice means "loading" while an EMPTY but non-nil one is a real host with nothing on it (`TestGroupedScreen_EmptyHostLeavesLoadingState`). `computeMatches(entries, query)` matches SERVICE entries only and returns ascending ENTRY indices (`TestComputeMatches_SkipsGroupHeaders`), so `/`, `n`, `N` and the two-stage `esc` are unchanged; **every fold and every grouped reload must re-derive `searchMatches`**, since the rebuild renumbered the rows the cached indices point at (`TestGroupedSpace_FoldRecomputesSearchMatches`).

## Multi-project host view — `HostGrouper`, the grouped loader, and the refresh dispatch

the grouped screen needs host-wide status, and asking each project for its own would cost one SSH round-trip per project on exactly the host where that hurts most. `HostGrouper` (`GroupedStatus` + `GroupedStats`, both `map[project]map[service]…`) is declared in `tui` and type-asserted on the concrete composer, the same shape as `Inspector`/`UpdateDetailer`/`ReadOnlyComposer`. It is reached through `composerFactory(compose.Project{Unmanaged: true})` — the synthetic project the unmanaged row already used, which both `cmd/root.go` factories already branch on to build a `*compose.HostContainers` — so **no existing signature changes**: `ProjectLoader`, `ConnectCallback` and `ComposerFactory` are untouched and `cmd/root.go` needed no edit, only the pin in `cmd/root_test.go`. A factory that yields no `HostGrouper` (a test mock) is **not an error**: the loader's projects still render, with no status and no stats (`TestRefreshGroupedStats_NoGrouperIsEmptyNotAnError`). The whole screen therefore costs a CONSTANT number of calls regardless of project count — `docker compose ls -a` (the `ProjectLoader`) plus one `hostPsArgs` `docker ps -a --format '{{json .}}'`, and one further `docker stats --no-stream` for the stats half. `GroupedStatus` extracts the `com.docker.compose.project=` / `com.docker.compose.service=` label VALUES through `labelValue`, which matches **only at a token start** (the `isComposeManaged` rule) and reads the value to the next comma; **that truncation is safe for these two keys only**, because both compose names are constrained to `[a-z0-9][a-z0-9_-]*` and cannot carry a comma — do not reuse the helper for an arbitrary label key (`TestLabelValue`, `TestHostContainers_GroupedStatus_LabelValueWithComma`). Containers with no project label form the `UnmanagedProjectName` bucket; a managed container missing the SERVICE label falls back to its container name so the row stays addressable (`TestHostContainers_GroupedStatus_NameFallbacks`). Replica aggregation reuses `parseHealthFromStatus`, `formatUptime`, `parsePortsString` and mirrors `parseContainerStatus` exactly — Running is an OR, Health takes the worst case, Created the oldest replica, Uptime the longest-running one — so a scaled service reads the same in the host view as in the per-project one (`TestHostContainers_GroupedStatus_ScaledReplicas`, `TestHostContainers_GroupedStatus_RestartingReplica`). Both local and remote get it through the existing three-method `dockerRunner` seam, so there is **no new SSH plumbing** and the `SSHExtraArgs`-before-host splice is inherited (`TestHostContainers_GroupedStatus_RemoteSplice`, `TestHostContainers_GroupedStats_RemoteSplice`). `GroupedStats` early-returns before the stats call when the ps pass found no addressable container, mirroring `ContainerStats` for the same reason: the join would be empty by construction and `docker stats --no-stream` is a ~1.5s host-wide call the 5s tick would otherwise pay forever (`TestHostContainers_GroupedStats_EmptyHostSkipsStatsCall`). **The accepted gap is never-created services**: a service declared in a compose file but with no container has no row in the host view, because `docker ps` is the source. Drilling in goes through `ListServices` and shows it, and a WHOLE-GROUP operation does not inherit the gap either — an empty batch slice means "all services", resolved by compose itself. `loadGroups()` merges the loader's project list (which supplies the ORDER, including the synthetic unmanaged row appended last) with `GroupedStatus` into a WIDENED `servicesMsg`; `buildSvcGroups(projects, host, prev)` is the pure fold. **`groupedPayload bool` discriminates the two shapes rather than a nil check on either field**: a host with no projects and no containers is a legitimate grouped result whose payload fields are both empty, and it must clear the screen rather than be mistaken for a drilled load. `buildSvcGroups` takes project order from the LOADER (a map has none), keeps a project the loader reported but the host has no containers for as an EMPTY group rendering a bare header (`TestBuildSvcGroups_EmptyProjectKeepsItsGroup`), and appends the reverse case — a project in the status map the loader did not report, since `docker compose ls` and `docker ps` are two calls that can disagree — after the loader's, name-ordered with the unmanaged bucket last, so a running container is never silently invisible (`TestBuildSvcGroups_HostOnlyProjectsAppendedLast`). It carries fold state forward from `prev` by project NAME, because the group slice is rebuilt wholesale and folding is UI state the user set (`TestBuildSvcGroups_PreservesFoldState`). `loadGroups` reuses `statusSession`: it is `loadServices`' grouped counterpart with the same lifecycle, the same context changes and the same staleness rule (`TestGroupedServicesMsg_RejectsStaleSession`). **The grouped `servicesMsg` branch is BOTH the initial load and the 5-second refresh, so — unlike the drilled branch — it PRESERVES what the user set**: cursor, selection, fold state and an active search all survive, because resetting them here would fight the user every tick; the landing sites clear that state once, on entry (`TestGroupedServicesMsg_ReloadPreservesUserState`). It then re-derives `searchMatches`, prunes the selection, clamps the cursor, fixes the offset and replays the cached update verdicts — the fresh status map carries none, and nothing in grouped mode would fetch them back. Errors split by severity: a loader failure AND a host-ps failure both land in `svcErr`, since neither leaves a usable screen, while the stats half fails independently into `statsErr` (`TestLoadGroups_ErrorPaths`, `TestGroupedStatsMsg_FailureIsSoft`). The mode-aware dispatch is three helpers — `statusRefreshCmd()`, `statsRefreshCmd()` and `loadContainerScreenCmd()` — and **every refresh call site goes through them**, so the drilled path keeps the exact per-project calls it always made and no site has to remember the branch. The `refreshTickMsg` gate's `m.composer != nil` liveness check gains a grouped branch: grouped mode holds no composer BY DESIGN, so testing for one would silence the periodic refresh on exactly the screen that most needs it — what it needs instead is a FACTORY to reach the host-wide seam through (`TestRefreshTick_GroupedDispatchesHostWideFetches`, `TestRefreshTick_GroupedWithoutFactoryIsRescheduleOnly`, `TestRefreshTick_DrilledStillUsesTheComposer`).

## Multi-project host view — landing, drill-in/out, and action-time composer binding

`NewModel`'s start-screen table has three branches: servers or a config file → the server picker; no composer (no cwd compose file) → the GROUPED container screen; otherwise the drilled local fast track. `Init()` dispatches `loadGroups()` + `refreshGroupedStats()` in grouped mode and the drilled pair otherwise (`TestNewModel_LandsOnGroupedWhenNoComposer`, `TestInit_LoadsGroupsWhenNoComposer`, `TestInit_GroupedDispatchesGroupedLoad`). **The `connectResultMsg` SUCCESS path now bumps `statsSession`/`statusSession`/`updatesSession` and resets `updateInFlight`/`refreshInFlight`, which INVERTS the rule that held while the next screen was the static project picker.** The reason the old rule existed was that the success path landed on a list that fetched nothing; it now lands on LIVE data, and the site that starts fetching a resource is the site that must invalidate whatever a previous server left in flight (`TestConnectSuccess_BumpsTheThreeCountersAndLandsGrouped`). The error path is otherwise unchanged and additionally drops the grouped rows a previous server populated (`TestConnectError_ClearsGroupedState`). **`enterGroupedContainers()` is the ONE landing body** — the connect success path, `entryLocal` with no local composer, and drill-out all call it — so the one-time reset lives in exactly one place: composer to nil, project identity cleared, rows/selection/cursor/search/wait/rollback state cleared, the four session counters bumped, `statsRequested`/`refreshInFlight` set and `updateInFlight`/`updatesErr` cleared before the load batch (`TestEnterGroupedContainers_ResetsAndBumpsSessions`). That single owner is what lets the grouped `servicesMsg` branch preserve the same state on every reload. **Grouped mode holds `m.composer == nil` deliberately**: every capability assert (`Inspector`, `ExecProvider`, `ConfigProvider`, `RollbackPreparer`, `Snapshotter`) reads nil as "not available", which is precisely the inert behaviour wanted until an action key binds one. The binding is action-time and three-part: `bindCursorComposer()` binds the CURSOR ROW's group (two projects on one screen have two composers, and the Model's own project identity is empty here), `bindProjComposer(proj)` is its addressed twin for the operation keys (a batch is decided by the SELECTION, which may sit in a group the cursor has since left), and `unbindGroupedComposer()` drops it again. Both binders are pure pass-throughs in drilled mode, so every caller can call them unconditionally and the drilled path stays byte-identical. **Every path that binds and then stays on — or returns to — the grouped screen must unbind**: the `l`/`x`/`i`/`c` early returns, the config assert failure, the confirm prompt's `esc`, all three `R` probe failures, and the progress departure. Otherwise grouped mode keeps serving one project's composer to the next row's action key (`TestGroupedScreen_ReadKeysBindTheCursorGroupComposer`, `TestGroupedScreen_RollbackNonPreparerUnbinds`). **`x` is the ONE key that keeps its binding ACROSS the confirmation prompt** (`enterExec` runs on the confirming `enter`), and that is why `readOnly()` short-circuits on `m.grouped`: an exec prompt over an unmanaged row would otherwise flip the entire screen to the read-only variant — no checkboxes, a 7-cell caption pad instead of 10, a different footer pair and therefore a different `svcVisibleCount` — for the length of the prompt (`TestGroupedScreen_ExecBindsAcrossThePromptAndUnbinds`, `TestGroupedScreen_BoundReadOnlyComposerDoesNotFlipTheScreen`). This is the plan's "grouped mode is not globally read-only" rule made load-bearing. `enter` drills in from a group HEADER only (`TestGroupedScreen_EnterIsInertOffAHeader`, `TestDrilledScreen_EnterIsInert` — on the drilled screen `enter` belongs to the confirmation prompt): `drillIntoGroup` installs the group's composer, its project identity and its EXISTING rows first, so the screen paints the project the user just picked instead of a "Loading services..." frame, then reloads through `loadServices` for full fidelity — including the never-created services the host-wide `ps` cannot see. `svcStatus` and `stats` are KEPT across the drill because their keys are qualified by project, so the drilled group's entries are already correct and the intervening frame carries live data (`TestGroupedScreen_EnterDrillsIntoProject`, `TestGroupedScreen_DrillInReloadsThroughTheGroupComposer`). `esc` drilled → grouped reuses `enterGroupedContainers()` WHOLE rather than growing a second cleanup body, because it already owns the composer, the project identity, the rows, the selection, the search, the wait state and the four counters — exactly what the site owes (`TestSelectContainers_EscDrillsOutToGroupedView`, `TestSelectContainers_EscDrillOutBumpsSessions`, `TestGroupedScreen_DrillRoundTrip`). `esc` grouped → server goes through `backToServerScreen()`, which restores the local callbacks, drops the SSH connection and clears every downstream field per the backward-navigation cleanup discipline (`TestGroupedScreen_EscGoesBackToServerScreen`, `TestEscChain_DrilledToGroupedToServer`, `TestBackToServerScreen_RestoresLocalCallbacks`). **`drilledFromHost` is the RENAMED `showPicker`, not a deleted one**, and the rename is the point: it is the drilled screen's `canGoBack()` rule, and no predicate derivable from the composer, the factory or the group list separates the two drilled shapes — one reached by drill-in (parent = the host view) and one launched standalone in a directory holding a compose file, which is a ROOT where `q` quits and `esc` does nothing. Deriving it from `len(servers) > 0 || config != nil` breaks drill-in on a standalone host; making the root non-root turns `q` from "quit" into "drill out" on the primary local flow (`TestRootScreenQ_ContainerModes`, `TestSelectContainers_EscDoesNothingWhenStandalone`, `TestQQuitsAtRoot_ContainerScreenStandalone`). The grouped screen carries the position under the server picker instead: `canGoBack()` is `len(m.servers) > 0 || m.config != nil` there (`TestGroupedScreen_IsRootWithoutServers`). **`screenSelectProject` is gone**, together with `projectsMsg`, `projectsSession`, `viewSelectProject` and the `projects`/`projCursor`/`projErr` fields — the grouped screen IS the "which project?" screen now, and picking one is a drill-in rather than a screen change; the screen iota is 8 constants. `projectsSession` went with the message it guarded: the loader it tracked now feeds `loadGroups`, which is already gated on `statusSession` at the same swap sites. `compose.Project.Desc` was deleted with its only reader, but **`WithUnmanagedRow` STAYS** — `projectsWithUnmanaged` still calls it, because the grouped loader takes the synthetic `(unmanaged)` row and its ORDER from the `ProjectLoader`. The ephemeral-on-departure list for `clearSearch()` is now ELEVEN sites: `servicesMsg` (drilled branch), the `connectResultMsg` error path, `entryLocal`, `enterProgress`, `enterConfig`, `enterInspect`, `enterExec`, `enterLogs`, `enterGroupedContainers`, `drillIntoGroup` and `backToServerScreen`.

## Multi-project host view — fold, header aggregates, footer, and grouped rendering

`space` carries TWO meanings on the grouped screen, decided by the ROW under the cursor: a header folds its group, a service row selects, and an unmanaged row is a no-op. **Each branch calls `fixSvcOffset()` before returning** — the container dispatch clears `m.warning` above the switch, and the freed warning line grows `svcVisibleCount()` by one, so a gated key that returned without re-clamping leaves a too-large `svcOffset` and a blank row under the last service of a scrolled list. The fold branch rebuilds the entries, re-derives `searchMatches`, clamps the cursor and fixes the offset, in that order (`TestGroupedSpace_OnHeaderFoldsAndUnfolds`, `TestGroupedSpace_OnServiceSelects`, `TestGroupedSpace_OnUnmanagedRowIsNoOp`, `TestGroupedSpace_OnUnmanagedHeaderFolds`). `groupHeaderLine(gi)` draws `▼ name   ● n up  ✗ n  ⇧ n`, with `▶` when folded — the aggregates are what make a FOLDED group still worth looking at. **A group that owns no services renders a BARE header**: "0 up" for a project with nothing to run reads as a fault it is not (`TestGroupHeaderLine_EmptyGroupIsBare`). `✗` and `⇧` appear only when non-zero, and the aggregates survive folding (`TestGroupHeaderLine_Aggregates`, `TestGroupHeaderLine_FoldedKeepsAggregates`, `TestGroupHeaderLine_OutOfRange`). `groupCounts` reads `svcStatus` through the qualified key and counts a service with no status entry as none of the three: the host-wide fetch reports only containers that EXIST, so a project whose containers were all removed must read "0 up" rather than inflate the total. Service rows indent 2 cells from their header off `hasGroupHeaders()`, the caption pad adds the same `indentW` on top of its base (10 writable, 7 read-only) so the `Service` caption keeps sitting exactly above the names, and both scroll indicators carry the offset too (`TestViewSelectContainers_GroupedIndent`, `TestViewSelectContainers_GroupedScrollIndicatorsIndent`, `TestViewSelectContainers_RendersGroupHeaders`). **`svcVisibleCount` math is UNCHANGED** — a header is an ordinary row, and the count has always been in rows. Column widths are computed over `svcRefs()`, folded groups included, so folding never shifts the columns of the groups that stayed open. **Unmanaged rows render NO checkbox but KEEP its 3 cells**, so the columns stay aligned with the compose groups above and below them; `a` and `allSelected()` read `selectableRefs()`, and the title's `(n/m selected)` denominator counts selectable rows only — counting the unmanaged containers would make `a` look like it left rows behind (`TestGroupedSelectAll_SkipsUnmanagedRows`, `TestAllSelected_UnmanagedOnlyHostIsFalse`, `TestGroupedScreen_UnmanagedOnlyHost`). The footer gets a THIRD idle pair from `containerHelpLines()`: `space fold/select • <back> • ? keys` over `enter drill in • d deploy • r restart`. `space` names both meanings because it has both; `enter drill in` earns the slot `l logs` holds on the drilled screen, since a group header is the row only grouped mode has, and `l` keeps its home in the `?` overlay. **The line COUNT stays state-independent** (decided from the idle pair alone, before any search substitution) and **every rendered line is clamped with `clampToWidth` and measured with `ansi.StringWidth`**, never `len()` (`TestContainerFooter_GroupedIdlePair`, `TestContainerFooter_GroupedLineCountIsStateIndependent`, `TestContainerFooter_GroupedClampsToWidth`). In the `?` overlay, `helpContext` gained a `grouped` bit and `selectGroup(grouped)` supplies the SELECT table: `space  toggle a service · fold a group` and `enter  drill into the project on a group header`. **`enter` belongs to SELECT, NOT a second row in OPERATE** — OPERATE already names `enter` as the confirmation key, and one key cannot carry two descriptions in one table; the row-kind sub-state it is bound in is named in the description, the convention every sub-state binding follows. Group ORDER is unchanged (LEAVE stays 4th of 6, so `splitHelpGroups` still cuts it into the left column). The drift pin is `TestHelpGroups_GroupedNamesTheSameKeys`, which compares the grouped token set against the already-pinned writable one **in both directions** — so there is no second hand-maintained key list to drift out of step with the dispatch.

## Multi-project host view — batch partitioning and the sequential progress pipeline

`opBatch{proj compose.Project, services []string}` is one project's share of an operation, and **an EMPTY services slice is not "nothing"** — the runner reads it as ALL services, resolved by compose itself, which is the only way a whole-project batch can reach a service that was never created. `partitionSelection()` walks `svcGroups` in SCREEN order, so the batches run top to bottom, which is the order the confirmation prompt names them in (`TestPartitionSelection_OrderedByScreenPosition`). The unmanaged bucket never enters a batch: its rows have no compose project behind them, and its keys cannot reach `m.selected` anyway (the space handler refuses them), so the skip is the second half of one rule rather than a duplicate check (`TestPartitionSelection_UnmanagedNeverEntersABatch`). An empty selection resolves to ONE batch — the cursor's group with an empty slice — and a cursor on the unmanaged bucket or on no row at all yields NO batch, which callers report as "nothing selected" (`TestPartitionSelection_EmptySelectionIsTheCursorGroup`, `TestPartitionSelection_WholeGroupBatchCarriesNoServices`, `TestGroupedScreen_UnmanagedCursorHasNoOperation`). **The empty-selection rule applies in GROUPED mode only.** `partitionSelection` implements it unconditionally because it is a pure row-model rule, but `armOperation` keeps the drilled screen's long-standing `warnNoSelection` guard: a project's whole service set is one keystroke away there (`a`), so an unselected `d` has always meant a mistake rather than "deploy everything", and reinterpreting a destructive key is a semantic change no requirement asked for (`TestWarning_ShownWhenNoSelection`). **The composer binds at the confirming `enter`, not at the `d`/`r`/`s` press** — unlike `x`, which must keep it across the prompt. Nothing that changes the partition can happen while the prompt is armed (every key but `enter`/`esc`/`ctrl+c` is swallowed), so the prompt RECOMPUTES rather than captures, which is what keeps `opBatch` off the Model and out of the departure-site cleanup list (`TestGroupedScreen_ConfirmBindsTheBatchComposer`). The prompt names the batches through `formatBatchTargets` — `deploy web (nginx, api) → db (all)?` — and spells a whole-group batch `(all)`, which is what keeps it honest about how much the operation touches; it is clamped to one physical line, because a batch list grows with the number of projects it names and a wrapped prompt would overflow the row `containerFooterLines` reserved (`TestGroupedScreen_ConfirmPromptNamesTheBatch`, `TestGroupedScreen_ConfirmPromptClampsToWidth`, `TestFormatBatchTargets`). `enterProgress(batches)` builds the step rows for EVERY batch up front, so the screen shows the whole plan from the start instead of growing a project at a time. **`stepState` gained `label`, not a renamed `name`**: `name` stays the RUNNER step name that a `StepEvent` is matched against, `label` is what the screen draws and carries the `"web: "` prefix only when `len(batches) > 1` — so a hand-built `stepState{name: …}` still renders and matches exactly as before. **Each batch gets its OWN events channel**, because `runner.Run` defer-closes the channel it is given: a shared one would close after the first batch and report the whole sequence done. **`handleStepEvent` resolves an event inside the CURRENT batch's step range**, `currentStepRange()` = `[batchIdx*batchStepCount, +batchStepCount)`, never by a global name scan — `runner.Steps` returns the same five names for every batch, so a scan would land on batch 0's `Pulling` forever (`TestBatchSequence_TwoBatchesRunInOrder` uses SHARED step names precisely to pin this). A ZERO `batchStepCount` means one range covering every step, which is the single-pipeline shape every hand-built Model literal in the tests carries (`TestBatchSequence_SingleBatchEquivalence`). `markBatchesSkipped(from)` starts at batch `from`, so **a single-batch failure skips NOTHING** — the failed batch's own unreached steps stay `○`, byte-identical to today's rendering; only the batches BEHIND the failure are marked, because they are the rows a reader would otherwise take for "still to come" (`TestBatchSequence_FailureStopsSequence`). `pipelineDoneMsg` and `batchDoneMsg` both carry `batchIdx` + `batchSession`, captured at DISPATCH time (in `waitForEvent` and `batchDone`), and each handler applies THREE gates: screen, session, index (`TestBatchSequence_RejectsStaleBatchIndex`, `TestBatchWait_StaleBatchDoneRejected`). **`batchSession` is bumped at INVALIDATION sites only — never in `enterProgress`.** It starts at 0, so a zero-valued `pipelineDoneMsg{}` still resolves against a fresh sequence, which is what keeps the existing hand-driven `Update(pipelineDoneMsg{})` pins driving the handler instead of being dropped by their own gate. The two bump sites are the `esc`-cancel and `clearBatchSequence()` at every progress departure (`TestBatchSequence_DepartureClearsSequence`). `esc` mid-sequence cancels the current batch's context, bumps the session — the cancelled batch is still going to close its channel, so its `pipelineDoneMsg` is already on the way — and marks the rest skipped (`TestBatchSequence_EscDoesNotAdvance`); the mid-op `q`/`ctrl+c` no-op rules are unchanged. The Deploy snapshot is PER BATCH, taken inside the batch goroutine before `runner.Run` touches anything (pre-Stop ordering, best effort, `Snapshotter` type-asserted), so a two-project deploy records two state files. **`startBatch` does NOT rebind the composer for `Rollback`**: `R` bound it at press time (the snapshot fetch already needed one) and the prep validated the captured targets against it, so rebinding from the batch's project would risk swapping it under a capture the selection has since drifted from. Update-cache invalidation after a successful Deploy/Restart/Rollback deletes the current key AND `projUpdatesCacheKey(b.proj)` for EVERY batch — a sequence touches projects the container screen has since left (`TestBatchSequence_InvalidatesEveryBatchCacheKey`). `viewProgress`'s title stopped reading `selectedContainers()` unconditionally: that is empty for a whole-group op, so grouped mode reads `m.opContainers` with an `all services` fallback and a multi-batch sequence repeats `formatBatchTargets(m.batches)`; the drilled title is untouched (`TestGroupedScreen_ProgressTitleNamesTheTarget`, `TestBatchSequence_ProgressTitleNamesEveryBatch`).

## Multi-project host view — the per-batch health gate

every batch runs its OWN `--wait` gate against its OWN composer, which is what makes a two-project deploy stop at the project that came up broken instead of dragging the next one down with it. **`pipelineDoneMsg` OPENS the gate; `batchDoneMsg` — not `pipelineDoneMsg` — RELEASES the next batch.** That split is the whole point of the second message: a batch's pipeline closing its channel no longer means the batch is over. The test harness follows it — `drainBatch` is now `drainPipeline` + `resolveWaitPhase` — so every sequence test drives the gate as well as the pipeline. The target set is the batch's own service slice in BARE form (qualified keys never reach the reducer). An EMPTY slice is the runner's "all services", which the reducer cannot evaluate, so it is resolved per mode: **drilled mode falls back to `m.services`, grouped mode must NOT** — `m.services` is host-wide there, so seeding one project's composer with another project's services is a guaranteed timeout. Grouped mode asks the batch's composer through `ListServices` instead. **`waitTargetsMsg` is a SECOND message, not a widened `waitStatusMsg`**, because the reducer needs the names seeded BEFORE the first poll is evaluated; `m.waitState` stays empty (the header renders with no rows) for the one frame in between (`TestBatchWait_WholeProjectBatchResolvesTargetsViaListServices`, `TestBatchWait_EachBatchWaitsOnItsOwnServices`, `TestBatchWait_StaleTargetsRejected`). **An unresolvable target set SKIPS the gate rather than failing it**: a `ListServices` error names no health verdict, so it is not a health failure — the gate closes and the sequence continues (`TestBatchWait_UnresolvableTargetsSkipTheGate`). In the TUI the wait is advisory for the same reason `esc` can skip it by hand. `waitPhaseResolved()` decides what a finished gate means: a passing gate releases the next batch, a failing one stops the sequence exactly as a failed pipeline step does (`m.failed` + `markBatchesSkipped`), and **the LAST batch takes NEITHER branch** — today's single-project screen renders a failed wait as red verdicts plus the rollback hint over a `done` operation, not as a failed op, and that is preserved (`TestBatchWait_FailureStopsSequence`, `TestBatchWait_LastBatchFailureKeepsDoneState`). **`esc` on a MID-SEQUENCE gate RELEASES the next batch.** The three-phase `esc` contract already says the gate's `esc` means "skip the wait" while the pipeline's `esc` means "cancel", so a skip must not strand the sequence with no terminal state and no way out; `batchFinished()` is the shared release path for every no-gate case — `StopOnly`, an unresolvable target set, and the skip (`TestBatchWait_EscSkipReleasesTheNextBatch`, `TestBatchWait_EscSkipOnLastBatchReleasesNothing`, `TestBatchWait_StopOnlyAdvancesWithoutAGate`). `progressPhase()` still resolves `waiting` FIRST and must keep mirroring `viewProgress`'s footer switch, but **the REASON changed**: "waiting implies done" stopped being true when a mid-sequence gate opened with `done` false, so the rule now reads — a gate can be open with `done` set (the last batch), with `failed` set, or with neither, and only the waiting-first order names `esc` correctly in all three. The `batchDoneMsg` handler cancels the finished batch's context before the next batch takes over `m.cancel` (which `esc` reads), then calls `clearWaitState()` — **which also nils `opContainers`, so its order against `startBatch` re-setting it is load-bearing** — then advances `batchIdx` and starts the next batch. `batchSession` still bumps at invalidation sites only, so a zero-valued `batchDoneMsg{}` resolves against a fresh sequence exactly as `pipelineDoneMsg{}` does. `runRollbackCleanup` and the departure cleanup (`clearWaitState`, `waiting`, `waitDeadline`, `clearBatchSequence`) run when LEAVING `screenProgress`, on the main goroutine — **never goroutine-deferred**, per the rollback cleanup timing rule (`TestBatchWait_DepartureRunsCleanupAndClearsWait`, `TestEscFromProgress_InvokesRollbackCleanupOnce`, `TestEscSkipDuringWait_DefersRollbackCleanup`).

## Multi-project host view — updates in grouped mode

**No automatic update scan fires in grouped mode.** `autoUpdatesAllowed()` is `!m.readOnly() && !m.grouped`, and `maybeRefreshUpdatesCmd` ALSO early-returns on `m.grouped` before the cache lookup — grouped mode owns neither the single cache key that helper looks up nor the single composer a detail refill would fetch through, so `updatesCacheKey()` there would resolve to whichever project was drilled last. All THREE automatic entry points refuse (`maybeRefreshUpdatesCmd`, the `statusMsg` self-heal, `Init()`'s fast path), and `NewModel` seeds `updateInFlight` from the same predicate rather than a flat `true` — a `true` with no fetch behind it never clears, and the guard would then refuse every later fetch including `U`'s (`TestGroupedMode_AllAutoScanEntryPointsRefuse`, `TestGroupedInit_FiresNoUpdateScan`, `TestGroupedMode_NoAutomaticUpdateScan`). The cost rationale is the unmanaged one squared: a compose project bounds `CheckUpdates` to one service list the user is actively managing, while a host view fans out across EVERY project at once, each distinct image costing a local inspect plus up to two registry manifest requests — enough to exhaust the anonymous Docker Hub quota and break a real `docker pull` from the same host. **`U` is the only trigger, and it scans the CURSOR row's group only.** The composer is bound, read out and unbound in the SAME keystroke, so grouped mode never holds one project's composer while the cursor sits on another's row; the in-flight guard is checked BEFORE the bind, so a refusal leaves the composer exactly as it found it (`TestGroupedU_ScansCursorGroupOnly`, `TestGroupedU_InFlightGuardBindsNothing`). **`updatesMsg` gained `forKey`, captured at DISPATCH, and the handler must NEVER re-derive it.** The cursor is free to move — or fold a group — while a scan runs, so a handler-time re-derive files one project's verdicts under another project's key: the wrong glyphs paint and the scanned project looks unchecked (`TestGroupedU_ForKeySurvivesCursorMove`). The key itself comes from `projUpdatesCacheKey(proj)` = `proj.ConfigDir + "|" + serverName`, carrying the `unmanaged|` prefix off `proj.Unmanaged` — **the same string `updatesCacheKey()` produces once drilled into that project**, so one cache entry is shared between the two modes and a scan started from the host view still counts after drill-in (`TestGroupedUpdates_DrillInReplaysCachedEntry`, `TestGroupedU_UnmanagedGroupKeepsCachePrefix`). **`reapplyUpdateVerdicts(results)` replaces the two clear-then-hydrate blocks in the `updatesMsg` handler.** The drilled rule is "the message is the whole truth" — clear every verdict, then hydrate from the message — but a grouped scan covers ONE group, so that would blank every group the scan did not cover, on the success path AND on the error path, where the untrusted-map contract binds only the failed project (`TestGroupedU_SecondScanKeepsFirstGroupsVerdicts`, `TestGroupedU_FailureBlanksOnlyItsOwnGroup`). Grouped mode therefore re-reads the verdicts from the CACHE, per group, through `hydrateGroupedUpdates()`. **Those cache reads are RAW — deliberately not the TTL-checked `updatesCacheLookup`.** Grouped mode never refetches on its own, so a TTL-gated replay would blank the glyph column ten minutes after a scan with nothing queued to bring it back; the age of the check is reported on the inspect screen instead. Error entries are skipped (their results map is nil and their verdicts are untrusted by contract). The replay runs on every grouped reload, i.e. every 5 seconds, which is what keeps a `U` scan's glyphs alive across the periodic refresh (`TestGroupedUpdates_SurviveAPeriodicReload`). `groupCounts` gained the header's `⇧ n` as a THIRD return value rather than a second helper: the header reads the same tri-state the row glyph draws, so a nil verdict counts as zero and nothing on the header path can trigger a scan (`TestGroupedHeader_ShowsUpdateCount`). **Grouped mode fetches NO inspect detail rows, and the gate is the MODE, not the nil composer**: `updateDetailsCmd` reads `m.composer`, which an armed `x` prompt may have left bound to a DIFFERENT project than the scan covered, so a batch built from it would spend registry round-trips resolving the wrong project's images. The entry keeps `details == nil`, which is exactly the state `refillUpdateDetailsCmd` fills the moment the user drills into that project — the rows are deferred, not lost (`TestGroupedU_FetchesNoDetailBatch`). `inspectUpdateKey()` resolves the cursor row's group key so `i` from a grouped row reads the right entry; **it is read at RENDER time, not captured on entry**, because the cursor cannot move while the inspect screen is up — equivalent to a captured field, without adding one more field to the departure-site cleanup list (`TestGroupedInspect_ReadsCursorGroupEntry`). `redrawInspectFromCache()` gating is unchanged.
