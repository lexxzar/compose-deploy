# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Test Commands

```bash
go build -o cdeploy .          # Build binary
go test ./...                   # Run all tests
go test ./internal/runner/ -v   # Run tests for a single package
go test ./... -count=1          # Run all tests uncached
go mod tidy                     # After adding/removing imports
```

The root command launches a Bubble Tea TUI requiring a TTY, so `cmd/root_test.go` tests flag registration and subcommand structure rather than executing the root command directly.

## Architecture

cdeploy is a dual-mode tool: interactive TUI (no args) or non-interactive CLI (`deploy`/`restart`/`stop`/`list`/`logs`/`exec` subcommands). Both modes share the same core through a three-layer architecture:

```
cmd/ (Cobra)  →  runner (pipeline orchestrator)  →  compose (docker CLI wrapper)
tui/ (Bubble Tea) ↗
```

**Key abstraction**: `runner.Composer` interface (defined in `internal/runner/runner.go`, implemented by `internal/compose/compose.go` for local, `internal/compose/remote.go` for SSH, and `internal/compose/hostcontainers.go` for the read-only unmanaged-container view). This is the seam between the orchestrator and Docker — the runner is testable with mock implementations. Methods: `Stop`, `Remove`, `Pull`, `Create`, `Start`, `ListServices`, `ContainerStatus`, `ContainerStats`, `CheckUpdates`, `Logs`. When widening this interface, every mock implementation must add a matching no-op — there are mocks in `internal/runner/`, `internal/tui/app_test.go` (`mockComposer`), `cmd/deploy_test.go` (`opMockComposer`), and `cmd/list_test.go` (`mockComposer`, `mockComposerStatusErr`); a fast `grep -rn "func.*Composer.*ListServices" ./...` enumerates them.

**Event system**: `runner.Run()` sends `StepEvent` structs through a channel. The CLI consumer (`cmd/deploy.go:runOperation`) prints colored status lines. The TUI consumer (`internal/tui/app.go`) drives a Bubble Tea model through `tea.Cmd` that reads from the channel.

**TUI state machine**: eight screens — `screenSelectServer`, `screenSelectContainers`, `screenProgress`, `screenLogs`, `screenConfig`, `screenInspect`, `screenSettingsList`, `screenSettingsForm` — selected by a `screen` field on ONE flat Model. **GROUPED is a MODE on `screenSelectContainers` (`m.grouped`), never a screen**, and **there is NO project-select screen**: picking a project is a drill-in on the same screen. Container action keys: `r`/`d`/`s`/`R` arm a confirmation (`confirming` + `pendingOp`), `x` arms one too (`pendingExec`, then `tea.ExecProcess`), `l`/`c`/`i` open their screens with none. **`l`/`i`/`x`/`U` are NOT gated on `m.readOnly()`; every write key is.** `esc` — and `q`, rewritten to it on nested screens — resets downstream state; while confirming it cancels without navigating. Entry model, landing sites and the back-navigation cleanup discipline: `docs/architecture/tui-multi-project.md`.

**Exit confirmation for remote connections**: `ctrl+c` quits, **except mid-pipeline on `screenProgress`, where it is a NO-OP**; with a live remote connection (`disconnectFunc != nil`) it PROMPTS instead. `quitting` gates a global intercept at the TOP of `handleKey()` — `y` quits, `n`/`esc` cancels, every other key is SWALLOWED — and `View()` checks it FIRST. **`tryQuit()` is the ONE quit path, never a direct `tea.Quit`**, outside `screenSelectServer` and the `q`-at-root rewrite. Local sessions bypass it entirely. Full rationale, failure modes and test pins: `docs/architecture/tui-help-overlay.md`.

**`?` key-reference overlay**: `?` opens the screen's key list; a flag (`helpOpen bool`), **never a screen constant**. `helpGroupsFor(s, hc helpContext)` builds it; **group ORDER is load-bearing** (`splitHelpGroups` cuts sequentially). **A key or row added moves that variant's width/height thresholds and needs its drift pin extended**; `layoutHelpColumns`/`budgetHelpRows` clamp; **`viewHelp()` must NOT end in a newline**. **Intercept order is load-bearing**: `quitting`, `helpOpen` swallow, `?` open, `q`→`esc`; swallow BEFORE open; `ctrl+c` clears it and FALLS THROUGH. Open gated on `!m.typingInInput() && !m.confirmPromptArmed()` (screen-SCOPED; flat `!m.confirming` is WRONG), and a handler arming a confirmation must clear `helpOpen`. Full rationale, failure modes and test pins: `docs/architecture/tui-help-overlay.md`.

**Container footer and the one-line width guard**: `containerFooter()` and `containerFooterLines()` read `containerHelpLines()`; `svcVisibleCount()` reserves `2 + containerFooterLines()`, and the footer pads every state to the reserved count, advertising ONLY keys the state binds while **the line COUNT stays state-independent**. Guard with `ansi.StringWidth`, **never `len()`**; clamp with `clampToWidth`, never grow the count. Full rationale, failure modes and test pins: `docs/architecture/tui-help-overlay.md`.

**`q` as back key on nested screens**: the 4th `handleKey()` intercept rewrites `q` to `esc` on nested screens — **never add parallel `q` handlers**. `q` quits only on roots: `screenSelectServer`, and containers when `!m.canGoBack() && !m.confirming` (drilled `canGoBack()` IS `m.drilledFromHost`, so `q` quits when it is FALSE). `screenProgress` no-ops `q`/`ctrl+c` while `!done && !failed && !m.waiting`; skipped under `m.typingInInput()`. Full rationale, failure modes and test pins: `docs/architecture/tui-help-overlay.md`.

**Stale async message guard**: a goroutine a screen spawned (e.g. `readLogChunk` for `screenLogs`) can deliver after the user navigated away, so its handler MUST check `m.screen` and discard — otherwise it reads nil fields `esc` cleanup already cleared and panics. Pair the screen check with a monotonic session counter (`logsSession` is the worked example) for every new screen that spawns background goroutines — the counters, their bump sites and the gate recipe are in `docs/architecture/tui-refresh-loop.md`.

**Service list scrolling**: `svcOffset` = the first visible ROW of `m.svcEntries` (a group header costs one, like a service). `svcVisibleCount()` = `m.height - headerLines - footerLines`, **floored at 1 and THEN capped to the row count** (empty list ⇒ 0); **`m.height == 0` returns every row**. **header 3, 4 with captions; footer `2 + containerFooterLines()` +1 per warning row — never 2**: `titleStyle` `MarginBottom(1)` and `helpStyle` `MarginTop(1)` each cost a REAL row, the reserved search-bar line costs NONE. **Indicators REPLACE blank-line content, never add a row.** **`fixSvcOffset()` moves only the WINDOW, `clampSvcCursor()` only the CURSOR**; every gated container key calls `fixSvcOffset()` before its early return (the dispatch clears `m.warning` above the switch, freeing a footer row). **`svcVisibleCount()` IS the `pgup`/`pgdown` step**, read at PRESS TIME ⇒ overshoot by design; `clampSvcCursor()` BEFORE `fixSvcOffset()`; degenerates to end/home when the list fits. **`svcOffset` resets to 0 with `svcCursor` in the DRILLED `servicesMsg` branch and at every landing/drill site, NEVER in the grouped one** (the 5s reload — `restoreCursorRow(cursorRowID())` + `fixSvcOffset()` instead). **Cursor survives by IDENTITY (`svcRowID`), not index** — `docs/architecture/tui-multi-project.md`. Full rationale, failure modes and test pins: `docs/architecture/tui-refresh-loop.md`.

**Container search (search & jump)**: `/` jumps, **never filters**. **Every fold and reload MUST re-derive `searchMatches`** (`computeMatches`); **every departure from `screenSelectContainers` — and the DRILLED `servicesMsg` RELOAD — calls `clearSearch()`**. Two-stage `esc`: clear, then back-nav; typing-`esc` restores by `searchReturnID`. **`searchBarLine()` MUST be ONE physical line** (`clampToWidth`). Full rationale, failure modes and test pins: `docs/architecture/tui-logs-and-search.md`.

**Multi-project host view — grouped vs drilled, the entry model, and `svcKey`**: GROUPED (`m.grouped`, every project plus `(unmanaged)`) and DRILLED share ONE row model, `svcEntry` DERIVED from `svcGroup`. **`m.grouped` is explicit, never inferred from `len(svcGroups)`.** **Folding hides ROWS, never services — read `svcRefs()`.** **Never key state on a ROW INDEX across a rebuild**: selection by `svcKey(proj, svc)`, cursor by `svcRowID`, fold by NAME. **Qualified keys never leave the Model.** Full rationale, failure modes and test pins: `docs/architecture/tui-multi-project.md`.

**Multi-project host view — `HostGrouper`, the grouped loader, and the refresh dispatch**: `HostGrouper` = `GroupHostStatus` + `GroupHostStats`: **ONE listing, TWO calls**, joined by the STAMPED `HostEntries` handle. **Every `loadGroups` return carries `groupedPayload`, failures included**; `groupedStatsCmd` CHAINS off the arrival, seam and listing taken from IT at DISPATCH. **The arrival ENDING the cycle clears `refreshInFlight` UNCONDITIONALLY** before the screen check (never `if !chaining { clear }`); only the chaining branch re-arms. As the 5s reload it leaves cursor, selection, fold and search ALONE and DROPS payloads under `m.confirming`. **A host-only group has no `ConfigDir` — `bindProjComposer` refuses it.** Full rationale, failure modes and test pins: `docs/architecture/tui-multi-project.md`.

**Multi-project host view — landing, drill-in/out, and action-time composer binding**: **`enterGroupedContainers()` is the ONE landing body** and owns the reset. **Grouped mode holds `m.composer == nil`**; binding is action-time (`bindCursorComposer`/`bindProjComposer`) and **every binder must unbind before staying on or returning to the grouped screen**. **`x` alone keeps its binding across the prompt**, so grouped `readOnly()` reads `allGroupsUnmanaged()`. **The drill-out `esc` arms the third one-shot, `groupCursorPending`**: the visited project's HEADER, only when `projName != ""`, written AFTER `enterGroupedContainers()`; the next payload WITH ROWS spends it. Full rationale, failure modes and test pins: `docs/architecture/tui-multi-project.md`.

**Multi-project host view — fold, header aggregates, and grouped rendering**: **Every fold goes through `settleFold`: re-derive `searchMatches`, aim the cursor at the folded group's OWN header.** **`a` alone is FOLD-AWARE** (`eachUnfoldedSelectableRef()`); **every other selection read stays HOST-WIDE — that split IS the safety rule**. **Fold keys (`←`/`→`, `z`) are grouped-only, write-only, DIRECTIONAL; `Z` stays UNBOUND.** **The view LANDS FOLDED once, via the one-shot `groupFoldPending`**: armed in `enterGroupedContainers()` (after `clearContainerScreen()`) and `NewModel`'s grouped branch, spent by `applyPendingGroupFold()` before the re-derives. Full rationale, failure modes and test pins: `docs/architecture/tui-multi-project.md`.

**Multi-project host view — batch partitioning and the sequential progress pipeline**: `opBatch{proj, services}`: **an EMPTY slice means ALL services**. `partitionSelection()` walks SCREEN order, skips unmanaged, falls back to the cursor's group when nothing is selected — **GROUPED-only; drilled keeps `warnNoSelection`**. **Each batch owns its events channel**; `handleStepEvent` resolves inside `currentStepRange()`. **Every batch message carries `batchIdx` + `batchSession` captured at DISPATCH**; `batchSession` bumps at INVALIDATION sites only. Full rationale, failure modes and test pins: `docs/architecture/tui-multi-project.md`.

**Multi-project host view — updates in grouped mode**: **no automatic scan fires here**: `autoUpdatesAllowed()` = `!readOnly() && !grouped`, `maybeRefreshUpdatesCmd` returns before the cache lookup AND the in-flight guard. **`U` is the only trigger and scans the CURSOR row's group only.** **`updatesMsg` carries `forKey` captured at DISPATCH — never re-derive it.** **`reapplyUpdateVerdicts(results)` replaces the drilled clear-then-hydrate**: one group's scan blanks no other. Full rationale, failure modes and test pins: `docs/architecture/tui-multi-project.md`.

**Log streaming / Log follow-aware auto-scroll**: `screenLogs` pipes `Composer.Logs()` via `io.Pipe`. **ZERO new Model fields**: `YOffset` IS the pause state, following ≡ `AtBottom()`: capture BEFORE every content change, `GotoBottom()` only if it held (`logChunkMsg`, `fullReformat()`, `rederiveLogs()`). Full rationale, failure modes and test pins: `docs/architecture/tui-logs-and-search.md`.

**Log formatting**: `w` wrap/`p` pretty-print are independent; `applyLogFormat()` folds only the unscanned tail (`foldNewRawLines`) into `logsFormatted`; toggles/resizes call `fullReformat()`. Full rationale, failure modes and test pins: `docs/architecture/tui-logs-and-search.md`.

**Log search & filter**: `buildMatcher` builds both preds; `logFilterPred`/`logSearchPred` read the COMMITTED regex flag. `logsRawLines` unfiltered, `logsPartial` the tail, **`logsScanned` a RAW-line cursor, NOT a survivor count** — `foldNewRawLines` MUST advance to `len(raw)`. **`setLogViewportContent()` is the sole `SetContent` chokepoint.** **`esc` peels in order**: typing-search → typing-filter → committed-search → committed-filter → leave. `logBarLine()` is ONE clamped line; viewport height `- 7` at the **two log sites**, `- 6` at config — **no blind find/replace**. Full rationale, failure modes and test pins: `docs/architecture/tui-logs-and-search.md`.

**Status refresh**: every return to the container screen re-fetches `ContainerStatus()` via a `statusMsg` so the running/stopped dots reflect what the operation did — follow this whenever an operation changes container state. `statusMsg.err`/`servicesMsg.err` land in `svcErr`, and a successful refresh clears it. Full rationale, failure modes and test pins: `docs/architecture/tui-refresh-loop.md`.

**Server badge**: `serverBadge()` draws a colored inline badge ONLY when `resolveServerColor()` (group color, else own; **nil-guarded on `m.config`**) is non-empty; empty = the plain breadcrumb. **Inline: no extra line, no viewport budget.** **`serverHost`/`serverColor` are set AND cleared alongside `serverName`**, which also keys `projUpdatesCacheKey`. Full rationale, failure modes and test pins: `docs/architecture/remote-and-servers-config.md`.

**Config screen**: The `screenConfig` screen lets users view and edit docker-compose configuration files. Accessible via `c` key on the container screen (no confirmation). Uses a `ConfigProvider` interface (defined in `internal/tui/app.go`) with methods: `ConfigFile`, `ConfigResolved`, `EditCommand`, `ValidateConfig`. Both `Compose` and `RemoteCompose` implement it. The TUI type-asserts `composer.(ConfigProvider)` when entering — if the assertion fails (e.g., test mock), the `c` key is ignored. Key `r` toggles between raw file content and resolved output (`docker compose config`); resolved content is lazy-fetched on first toggle and cached. Key `e` shells out to `$EDITOR` via `tea.ExecProcess`; on return, re-fetches content and validates. Uses `configSession` (monotonic counter) for stale message rejection, matching the `logsSession` pattern. `esc` clears all `config*` fields and returns to the container screen. Local `findComposeFile()` probes `composeFiles` candidates; remote `findRemoteComposeFile()` uses a single SSH command to avoid multiple round-trips.

**Inspect screen**: `Inspector` is `tui`-declared and type-asserted; **`i` is NOT gated on `m.readOnly()`**. **`docker inspect` is TOP-LEVEL**: bypass `command()`/`remoteCommand()`. **`buildInspectSummary` is pure; its ZERO VALUE draws no update row**; renders STATE/HEALTH/IMAGE/MOUNTS/ENV, empty omitted, HEALTH off POINTER `State.Health`/`Config.Healthcheck`. **Never truncate**: wrap via `inspectBuilder`/`wrapCells`, not `softWrapLine`. **`push` is the ONE sanitise chokepoint**; raw's `sanitizeInspectRaw` must NOT `ansi.Strip`. `inspectViewportSize()` = `m.height - 6` (NOT logs `- 7`); `setInspectContent()` is the ONE `SetContent` site + `SetXOffset(0)`; **`viewInspect()` must NOT end in a newline**. Full rationale, failure modes and test pins: `docs/architecture/tui-inspect-screen.md`.

**Exec into container**: The `x` key on the container screen execs into a running container interactively. Uses an `ExecProvider` interface (defined in `internal/tui/app.go`) with method `ExecCommand(ctx, service, command) (*exec.Cmd, error)`. Both `Compose` and `RemoteCompose` implement it. The TUI type-asserts `composer.(ExecProvider)` when `x` is pressed — if the assertion fails (e.g., test mock), the key is ignored. If the service is not running, a warning is shown. Otherwise, confirmation is requested (`pendingExec = true`); on confirm, the TUI shells out via `tea.ExecProcess` which suspends Bubble Tea and gives full terminal to the exec process. On return, `execDoneMsg` resets `pendingExec` and calls `refreshStatus()`. Default shell command: `[]string{"/bin/sh", "-c", "command -v bash >/dev/null 2>&1 && exec bash || exec sh"}` (checks for bash first, falls back to sh for Alpine/minimal images; uses `command -v` instead of redirecting stderr on `exec` to avoid silencing bash's stderr for the entire session). Local: `docker compose exec <service> <command...>`. Remote: builds SSH command directly (like `EditCommand` pattern) with `-t` for TTY allocation — does NOT use `remoteCommand()`. CLI: `cdeploy exec <service> [-- command...]` with `--server`/`-s` support; follows `cmd/logs.go` pattern. `ExecCommand` returns `(*exec.Cmd, error)` (not executing it) so the caller controls execution. `DefaultExecCommand` is exported from `internal/compose/compose.go`.

**Docker Compose**: all docker interaction goes through `Compose.command()` / `RemoteCompose.remoteCommand()` — binary from `Standalone`, `CURRENT_UID` set (`uid:gid` local, `$(id -u):$(id -g)` remote) — **EXCEPT the top-level docker commands** (`stats`, `inspect`, `image inspect`, `buildx imagetools inspect`, `manifest inspect`, `pull`, host `ps`), which build their own argv. **`Detect()` must run before first use; `command()` only READS `Standalone`** — `SetStandalone` inherits the verdict, `SetTestHooks` injects doubles. **An empty container slice means ALL services**; the CLI rejects `-a` combined with explicit names. **`ls` goes through `hostCommand`/`remoteHostCommand`: NO `-f`, NO `-p`.** Every `--format json` parser tolerates BOTH the array and NDJSON forms. Full rationale, failure modes and test pins: `docs/architecture/compose-command-and-status.md`.

**Project identity — caller-supplied, never looked up**: a composer's identity is what its CALLER supplied — the `--project-name`/`-p` flag, or the `Name` on the picker row the TUI drilled into. It is **NEVER re-derived from `docker compose ls`**. That command enumerates projects by scanning CONTAINER LABELS, so a project whose containers are gone is not reported — and the deploy pipeline itself removes them (`stop → rm -f → pull → create → start`). A round that keyed the snapshot from that lookup made a failed deploy unrollbackable: `pull` fails after `rm -f`, `ls` reports nothing, and the rollback keys a different file. **THE STORAGE KEY MUST NOT DEPEND ON STATE THE OPERATION BEING SNAPSHOTTED CAN DESTROY.** Convergence instead comes from `canonicalStateName(dir, name)` (`internal/compose/projectidentity.go`), which needs no host state at all: an UNNAMED compose invocation is not identity-free — it addresses the project compose derives from the directory — so a composer naming that DEFAULT project and a composer naming nothing fold onto ONE key, the dir-only hash every release has written. `composeDefaultProjectName` reproduces compose-go's `NormalizeProjectName` on `path.Base(dir)` (lower-case, keep `[a-z0-9_-]`, trim leading `_-`); it is not a guess, it is the definition of the project compose would use. A project that is NOT the directory default (`-p blue`) keys its own file, so two `-p` projects sharing one directory never read each other's digests. **`Compose.stateName()`/`RemoteCompose.stateName()` are the ONE producer** of both the key and the `project_name` stamp, so `checkSnapshotProject` can never disagree with the file it guards. `COMPOSE_PROJECT_NAME`, a `name:` key and `.env` are deliberately NOT consulted — the environment is invisible over SSH (honoring it locally would split the local and remote key for one project) and the rest means replicating compose's interpolation; when one of them names a project the derivation does not predict, the two spellings key two files and a rollback says "no snapshot" — a safe failure for a `-p`-addressed project, which is the case this design targets. **It is NOT safe in one narrower shape**: two DIFFERENT projects sharing one directory and BOTH addressed with an EMPTY name (each selected by its own `name:` key, `.env` or `COMPOSE_PROJECT_NAME`) fold onto the same dir-only file, and `mergeSnapshot` merges by SERVICE name, so one can pin the other's digest. That is not a regression — before the name entered the key EVERY project in a directory shared one file — so the rule NARROWS the hazard rather than introducing it. `TestProjectIdentity_EveryPathKeysOneStateFile` (fast track + drill-in + `runOperation` ⇒ ONE state file) and `TestProjectIdentity_TwoNamedProjectsInOneDirStayApart` are the two halves of the contract; `TestRollbackFindsTheSnapshotAfterEveryContainerIsRemoved` and its remote twin pin it against an empty `ls`. **`ListProjects` must carry NO `-f` and NO `-p`** (`hostCommand`/`remoteHostCommand`): `ls` is host-wide discovery, neither flag selects anything there, and `-f` would point compose at a file it must parse — `cdeploy list` and the TUI project loader call it on a composer that may already carry both. **Documented limitation**: the CLI reproduces `docker compose -p <name>` run in `-C <dir>` exactly, so it auto-discovers compose files; a project whose files are not auto-discoverable there must be driven from the TUI, whose picker row carries the set.

**Remote SSH**: `RemoteCompose` over a ControlMaster socket (`/tmp/cdeploy-ctrl-{host hash}-{pid}`). `ConnectCmd()` feeds the TUI's `tea.ExecProcess`; `Close()` tears down. **Every remote arg is `shellEscape`d**; **`CURRENT_UID` is evaluated ON THE REMOTE**. `Detect` builds its OWN argv — no `CURRENT_UID`, no `cd`. `tui.Run()` calls `disconnectFunc` on exit. Full rationale, failure modes and test pins: `docs/architecture/remote-and-servers-config.md`.

**Ad-hoc SSH (`-S`/`--ssh`)**: `[user@]host[:port]`, **CLI-ONLY** (root `RunE` and `skill` reject it). **`--server`/`--ssh` are mutually exclusive; `--identity` requires `--ssh`** — `checkRemoteMutex` at the TOP of every `RunE`, before `os.Getwd()`. **`--ssh` requires `--project-dir`**, enforced inside `resolveSSHRemote`, whose **cleanup is ALWAYS non-nil — `defer` it unconditionally**. **Every ssh argv MUST go through `r.sshArgs()`** = `prefix + SSHExtraArgs + "--" + Host + suffix`: **extras immediately BEFORE the host**, never hand-assembled, nil adds nothing, a derived composer COPIES the field. Full rationale, failure modes and test pins: `docs/architecture/remote-and-servers-config.md`.

**Ad-hoc SSH identity (`-i`/`--identity`)**: **only valid alongside `--ssh`; CLI-only.** `config.ParseIdentity` expands `~/` ONLY and requires a REGULAR file `os.Open` also opens; **no mode/0600 check** — `ssh(1)` does that. `resolveSSHRemote` appends `["-i", cleanPath]` AFTER the port args, so every splice site absorbs it with NO change to `internal/compose/remote.go`. Full rationale, failure modes and test pins: `docs/architecture/remote-and-servers-config.md`.

**Config**: `~/.cdeploy/servers.yml` → `Config{Groups, Servers}`. **`Load()` returns an EMPTY config, not an error, when the file is absent**, then runs the idempotent `migrate()` (per-server colors fold onto `Group.Color`, first-server-wins; auto-create ONLY when `len(Groups) == 0`). **`config.ValidColors` is the ONE source of truth** for `Validate()` and the TUI picker; a new color ALSO needs a `colorMap` entry (`internal/tui/styles.go`), or it renders gray. `Validate()` covers groups and group refs too. **`Save()` is atomic** (temp + rename). **SSH options belong in `~/.ssh/config`, except `-i` via `--ssh`.** Full rationale, failure modes and test pins: `docs/architecture/remote-and-servers-config.md`.

**Settings editor**: `screenSettingsList`/`screenSettingsForm`, `s` on the server screen, **only when `m.config != nil`**. `settingsField` 0-3 = the 4 inputs, 4 = the color picker (`typingInInput()`; `confirmPromptArmed()` = `settingsDelete`). **SAVE FIRST, MUTATE ON SUCCESS**: temp `Config` → `Validate()` → `Save()` → only THEN assign `m.config`/`m.servers` and rebuild `m.serverEntries`. **A grouped server's color lives on the GROUP**; `cleanOrphanedGroups` runs on save AND delete. Full rationale, failure modes and test pins: `docs/architecture/remote-and-servers-config.md`.

**Operations**: Four operations — `Restart` (stop → rm → create → start), `Deploy` (stop → rm → pull → create → start), `StopOnly` (stop), `Rollback` (stop → rm → create → start — Restart shape, **NO Pull**: registry outages are a classic rollback trigger, so offline rollback from local blobs must work). All share the same `runner.Run()` pipeline; the step list varies by operation type. `Steps()`/`buildSteps()` fold Rollback into the Restart branch (`default:` case, gated only by `op == Deploy` for the Pull step).

**Wait engine (`--wait` health gate)**: `EvaluateWait` is a **pure reducer** seeded by `NewWaitState`. **Precedence IS the spec**: (1) `Uptime=="restarting"` x3 **FIRST**; (2) unhealthy; (3) `Running==false` after `everRunning`; (4) never-ran x5; (5) `Health!=""` ⇒ ONLY `healthy`; (6) no healthcheck+running ⇒ after `Grace`. **Firm boundary**: 5/6 PASS needs `elapsed <= Timeout`, 1-4 do NOT; pending at `>= Timeout` ⇒ timed out. **`WaitHealthy`'s `WithDeadline(ctx, start+Timeout)` MUST precede ANY blocking call, `ListServices()` included.** Expiry = exit 2, parent cancel = exit 1 (`ctx.Err()` FIRST). Full rationale, failure modes and test pins: `docs/architecture/wait-snapshots-rollback.md`.

**`WaitError` exit-2 contract**: non-OK/errored ⇒ `errors.As` = **exit 2**; keep `Unwrap()`; `stop` never waits. Full rationale, failure modes and test pins: `docs/architecture/wait-snapshots-rollback.md`.

**Deploy snapshots & the state file**: **Deploy-only**, pre-Stop, from the RUNNING container; `mergeSnapshot`/`existingForMerge` guard writes. **The `canonicalStateName` key must never depend on state the operation destroys**; EMPTY name = dir-only hash. Full rationale, failure modes and test pins: `docs/architecture/wait-snapshots-rollback.md`.

**Rollback pipeline & `PrepareRollback` prep / `ExtraComposeFiles` contract**: `runOperationWithPrep`+`rollbackPrep`; a failed pull aborts BEFORE the override; `pull_policy: never`; `ExtraComposeFiles = [main, override]`, main FIRST, cleanup FUNCTION-scoped; **nil = byte-identical argv**. ## Adding New Operations

1. Add constant to `Operation` enum in `internal/runner/runner.go`
2. Update `String()`, `Steps()`, and `buildSteps()` in the same file
3. Add action key case in `screenSelectContainers` handleKey in `internal/tui/app.go`, AND name the key in the matching group in `helpGroupsFor()` (`internal/tui/help.go`) — the `?` overlay is the only place the full key table is advertised now that the footer carries 6 tokens
4. Gate the new key on `m.readOnly()` with an early return, and leave it OUT of `readOnlyContainerGroups()` (`internal/tui/help.go`). Every operation is a compose pipeline, and an unmanaged container has no compose file, so a new op is by definition inert on the read-only screen — a key the read-only table still named would advertise a no-op, which is the failure that whole variant exists to prevent
4b. **Route the key through the GROUPED path, or it writes a nil deref.** Grouped mode holds `m.composer == nil` BY DESIGN (see the multi-project paragraphs), so a new op key must not touch the composer at press time: arm through `armOperation` / `partitionSelection()`, bind with `bindProjComposer(batches[0].proj)` at the confirming `enter`, and call `unbindGroupedComposer()` on EVERY early return between the two. A key bound in BOTH modes needs no second key list — `TestHelpGroups_GroupedNamesTheSameKeys` (`internal/tui/help_test.go`) checks `grouped == drilled ∪ groupedOnly` three ways and fails the moment they drift. **A GROUPED-ONLY key must be added to that test's hand-maintained `groupedOnly` list**, the last one left. Add the grouped dispatch test alongside the drilled one; a key that works drilled and panics grouped is the shape this step exists to prevent
5. Add CLI subcommand in `cmd/deploy.go` and register in `cmd/root.go`
6. Tests: runner sequence test, cmd subcommand/flag tests, TUI action key + confirmation tests, plus the expected-key set in `TestHelpGroups_NamesEveryBoundKey` (`internal/tui/help_test.go`), which fails in both directions when the help table drifts from the dispatch. If the operation is a WRITE, add the key to the table in `TestReadOnly_GatesWriteKeys` (`internal/tui/app_test.go`) so the read-only screen is pinned to refuse the gate step 4 added. The read-only help pin needs NO edit for a gated key — it stays out of `TestHelpGroups_ReadOnlyNamesEveryBoundKey`'s hand-maintained bound set, and that test's names-nothing-unbound direction is what catches a table that advertises it anyway.

If the new operation needs an op-specific pre-run step (like Rollback's snapshot read + digest-pin prep), don't fork `runOperation` — route through `runOperationWithPrep(ctx, op, all, containers, prep)`. The `prep func(context.Context, runner.Composer) (func(), error)` runs AFTER the composer is built and BEFORE the pipeline (so it can apply refusal rules and configure the composer, e.g. set `ExtraComposeFiles`); its returned cleanup is deferred function-scoped, so it runs after the wait phase but before the remote SSH teardown (LIFO). deploy/restart/stop pass a nil prep and keep the original path. Rollback lives in its own `cmd/rollback.go` (see "Adding New CLI Subcommands") but is a deliberate reuse of this deploy machinery, not a fresh subcommand skeleton.

## Adding New CLI Subcommands

See `cmd/list.go`, `cmd/logs.go`, and `cmd/exec.go` for the pattern. Each subcommand:
1. Creates a `*cobra.Command` in its own `new*Cmd()` function
2. At the top of the `Run*` function, calls `checkRemoteMutex(serverName, sshTarget, identityFile)` to enforce the `--server`/`--ssh` mutex and the `--identity requires --ssh` rule (it must run before `os.Getwd()` and `signal.NotifyContext` so spurious setup doesn't run when the flags conflict)
3. Branches in this order: `sshTarget != ""` → `resolveSSHRemote(ctx, sshTarget, projectDir, projectName, identityFile, <factoryVar>)` (passing the subcommand's own injectable factory); else `serverName != ""` → `resolveServerRemote(ctx, serverName, projectDir, projectName, <factoryVar>)`, or the inline equivalent (load config, `FindServer()`, create `RemoteCompose`, `Connect()`, defer `Close()`, `Detect()`); else fall back to local `compose.New(dir)` handed to **`prepareLocalComposer(ctx, lc, projectName)`** (stamps the name, `Detect()`s — and looks NOTHING up) — the two remote helpers take the name as a parameter and stamp it themselves, precisely so a new subcommand cannot silently address the directory's default project instead
4. Is registered in `cmd/root.go` via `rootCmd.AddCommand()`

`cmd/skill.go` (the `skill install|show|uninstall` subcommand, see "Agent Skill distribution" below) is a deliberate exception to this pattern — it operates on local files only and has no `--server`/`--ssh`/`--project-dir`/remote wiring.

`cmd/rollback.go` (the `rollback` subcommand) is a second deliberate exception: rather than reimplementing the composer-branch skeleton, it reuses the deploy machinery via `runOperationWithPrep(ctx, runner.Rollback, …, rollbackPrep(…))` — the shared `runOperationWithPrep` already does the `checkRemoteMutex` → ssh/server/local branching, and `rollbackPrep` is the op-specific pre-run hook (snapshot read + refusal rules + digest-pin prep). See "Adding New Operations" for the prep-hook recipe.

## Agent Skill distribution (`cdeploy skill`)

**`skills/` package**: the repo-root `skills/` directory is BOTH the external-installer convention directory (so `npx skills add lexxzar/compose-deploy` and `gh skill install lexxzar/compose-deploy` find `skills/cdeploy/SKILL.md` on the default branch) AND a Go package holding the `//go:embed cdeploy` directive. `skills.FS` exposes the embedded tree; `skills.CanonicalSkill()` returns the raw, unstamped SKILL.md bytes — the single source of truth for the CLI, external installers, and verification, version-locked to the binary via `go:embed` (panics on a missing embed, since that is a build/packaging fault, not a runtime error to thread).

**`cdeploy skill install|show|uninstall <claude|codex|all>`** (`cmd/skill.go`): installs the embedded skill into agent skill directories. Targets resolve via `skillTargetDirs()`: claude → `~/.claude/skills/cdeploy` (also read by Cursor/OpenCode); codex → `~/.agents/skills/cdeploy` AND `$CODEX_HOME/skills/cdeploy` (default `~/.codex`; an EMPTY `$CODEX_HOME` is treated as unset because `t.Setenv` can set but never unset an env var); all → the deduped union. Dedupe (`resolveDedupeKey`) resolves symlinks on the deepest EXISTING ancestor of each candidate (the target dir usually does not exist yet, and `filepath.EvalSymlinks` errors on missing paths), then re-appends the not-yet-existing suffix, so two candidates pointing at the same physical directory through a symlink collapse to one write. Multi-path install/uninstall aggregate per-path outcomes — one failed destination never aborts the others, and any failure yields a non-zero exit. Per-agent pickup notes are printed to stdout after a successful install. `show` writes the raw unstamped canonical via `cmd.OutOrStdout()` (NOT `os.Stdout` — testable with `cmd.SetOut(&buf)`); it also enables `cdeploy skill show > .claude/skills/cdeploy/SKILL.md` for project-level placement.

**Stamp/hash ownership model**: install never trusts a file it did not write. `renderSkill(canonical, version)` injects a metadata block — `metadata:` header + `cdeploy-version` + `cdeploy-content-hash: sha256(canonical)` — immediately before the frontmatter's CLOSING `---` (the second `---`, found via `frontmatterCloseOffset`; never a bare `---` in the markdown body), so the frontmatter stays the first bytes of the file (Gemini silently skips otherwise). `stripOwned()` removes exactly that block, giving the round-trip invariant `stripOwned(renderSkill(canonical, v)) == canonical` as literal byte-equality; the stamped hash is therefore simply `sha256(canonical)`, no self-reference. `verifySkillFile(onDisk)` answers ONLY "is this file consistent with its OWN stamp?" → `intact` / `modified` / `unstamped` (stripOwned → sha256 → compare to the recorded hash). The install decision needs a SECOND, distinct check — `bytes.Equal(stripOwned(onDisk), canonical)` against THIS binary's canonical bytes — to reach `unchanged` vs stamp-refresh vs updated; without both checks the `unchanged` state is unreachable. Modified or unstamped files (e.g. a copy dropped by `npx skills`) are refused by both install and uninstall without `--force`; uninstall removes only the stamped `SKILL.md`, then the `cdeploy/` dir only when it is empty (never a recursive delete). Dev builds stamp `cdeploy-version: dev` — freshness keys on the content hash, not the version string.

**SKILL.md content test pins** (`skills/skills_test.go`): future edits to `skills/cdeploy/SKILL.md` MUST keep these satisfied — frontmatter is the very first bytes (`---\n` fence with a closing `---`), `name: cdeploy` (matches the directory AND the `^[a-z0-9]+(-[a-z0-9]+)*$` regex), `description` non-empty and ≤1024 chars (and naming both ops and setup triggers: deploy/servers.yml/ssh), under 500 lines, and — load-bearing — NO `metadata:` key in the canonical frontmatter. That last pin is what keeps block insertion/removal trivial: the install-time renderer owns the `metadata:` block and `stripOwned` must round-trip back to exactly the canonical bytes, so a hand-authored `metadata:` key would break the byte-equality invariant.

## Package Coupling

The TUI package depends on `runner.Composer` (interface), not `compose.Compose` or `compose.RemoteCompose` (concrete). For operations that need to create a `Composer` at runtime (drilling into a group, or an action key binding the cursor row's project), use a `ComposerFactory` callback injected from `cmd/` — this keeps `tui` decoupled from `compose`. The factory takes the whole `compose.Project`, not a directory string, so it can branch on `proj.Unmanaged` and return the read-only `compose.HostContainers` for the synthetic `(unmanaged)` group. That same branch is how the grouped host view reaches its host-wide seam: `composerFactory(compose.Project{Unmanaged: true})` type-asserted to `HostGrouper`, so no signature had to widen. Similarly, `ProjectLoader` and `ConnectCallback` are injected by `cmd/` for remote server support. The `compose` package has the `HasComposeFile` package-level function for local compose file detection; project discovery (`ListProjects`) is a method on `Compose`/`RemoteCompose` requiring `Detect()` first. The `ConfigProvider` and `ExecProvider` interfaces are defined in `tui` (not `runner`) because they return `*exec.Cmd` and are TUI-only; the TUI type-asserts `composer.(ConfigProvider)` and `composer.(ExecProvider)` at runtime — no separate factory or wiring needed. `ReadOnlyComposer` is the same shape and the same reason: only `compose.HostContainers` implements it, and a composer that omits it renders the normal writable screen. `Inspector` is the same shape with the reach inverted — ALL THREE composers implement it, so the `i` key is live on every container screen and the type assert exists for test mocks rather than for a capability split. `UpdateDetailer` is `Inspector`'s twin: all three composers implement it, it is asserted the same way, and a composer that omits it simply renders no update rows. `HostGrouper` (two methods over one listing, `GroupHostStatus`/`GroupHostStats`) is the same shape with the narrowest reach: only `compose.HostContainers` implements it, and a factory that cannot produce one yields a grouped screen with projects but no status — not an error.

- `internal/compose/`: Test command construction (args, env vars, flags) without executing commands; `parseProjects()`, `parseContainerStatus()`, `parseStatsOutput()`, `parseSize()`, `parseCPUPercent()`, and `FormatBytes()` extracted for testability; `RemoteCompose` tests verify SSH arg construction and shell escaping; `inspect_test.go` drives `pickInspectContainer`/`pickHostInspectContainer`, `parsePsEntries` and `ParseInspect` against three real `docker inspect` fixtures, and asserts the inspect argv carries no `compose`; `hostcontainers_test.go` drives `HostContainers` through a fake `dockerRunner` (the same seam production uses), so every read method is testable without Docker and the remote adapter's `SSHExtraArgs`-before-host splice is pinned directly; `updatedetails_test.go` drives the four-step detail fetch through that same seam, against real registry captures in `testdata/imagetools_*.json` plus a real `docker image inspect` document in `testdata/image_inspect_nginx.json` (the one thing a hand-authored fixture cannot pin is docker's KEY SPELLING) — **no test may hit a registry**, since a suite that did would reproduce the 429 in CI
- `internal/config/`: Test YAML parsing, validation, and lookup with temp files
- `internal/tui/`: Test model state transitions by calling `Update()` with `tea.KeyMsg` directly — no TTY needed; `entries_test.go` drives the pure row model (`rebuildSvcEntries`, `svcKey`, `buildSvcGroups`, `partitionSelection`, `groupCounts`, `groupSelected`, `eachSelectableRef`, `eachUnfoldedSelectableRef`, `cursorGroup`, `flattenQualified`) with no Model machinery at all. **There is no `services` field on Model at all** — rows come from `svcGroups` → `svcEntries`, so a test that wants a flat name list uses the `modelServices(m)` helper. The grouped host view has its own file, `grouped_test.go` (the row model over several projects, the grouped loader and reload, fold/select, the header line, drill-in/out, action-time binding, the grouped `U` scan), and the multi-batch progress sequence it feeds has `batch_test.go` — put a new test for either subsystem there rather than growing `app_test.go` again. Every container-screen test must go through the fixture helpers — `singleGroupModel(services)` (`app_test.go`) for the degenerate one-group (drilled) shape, `groupedModel(groups…)` + `svcGroupOf(name, services…)` (`grouped_test.go`) for the multi-group host view, `selectedIdx(m, i…)` to build a selection from ROW indices, `qStatus(m, status)` / `qStats(m, stats)` / `qk(m, service)` to qualify a bare-name map or name the way the message handlers do, and `progressStep(name, status)` to build a progress row (`enterProgress` always sets `label` AND `batchStepCount`, so a fixture must too); `format_test.go` tests `formatLogContent()`, `softWrapLine()`, and `prettyPrintLine()` as pure functions; `inspect_test.go` tests `buildInspectSummary()` the same way, against the compose package's fixtures; `help_test.go` pins the `?` overlay (the two-directional drift pin — run PER VARIANT, `TestHelpGroups_NamesEveryBoundKey` for the writable table and `TestHelpGroups_ReadOnlyNamesEveryBoundKey` for the read-only one, plus `TestHelpGroups_ReadOnlyDropsGatedKeys` — the `allScreens` completeness check, the typing/confirmation exceptions, and the never-exceeds-width/height clamps)
- `internal/logging/`: Use `t.TempDir()` for file creation tests
- `skills/`: Content pins on the embedded `cdeploy/SKILL.md` (frontmatter first, `name` matches dir + regex, description ≤1024 chars, <500 lines, no `metadata:` key) — see "Agent Skill distribution" above
- `cmd/`: Test flag registration, subcommand existence, and validation via `NewRootCmd()`; `cmd/skill_test.go` uses `t.Setenv` HOME/CODEX_HOME (never `t.Parallel`) for the path matrix, symlink dedupe, and the install/uninstall decision matrix in a temp HOME (render/verify round-trip is pure)
