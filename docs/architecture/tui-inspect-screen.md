## Inspect screen

the `screenInspect` screen shows what the container under the cursor ACTUALLY holds, against `screenConfig`'s what-the-compose-file-DECLARES — the two disagree the moment a compose file is edited and the service is restarted (`r`) rather than deployed (`d`). The wedge is `.State.Health.Log[last].Output`, the failing probe's own output: `docker compose config` cannot show it at all, and the `✗` icon plus `VerdictUnhealthy` already make the user ask about it. `Inspector` (`Inspect(ctx, service) ([]byte, error)`) is declared in `tui` beside `ConfigProvider`/`ExecProvider` and type-asserted on the concrete composer, so a composer without it (a test mock) makes `i` a silent no-op. **Three compile-time assertions in `app_test.go` pin the real types to the interface** (`var _ Inspector = (*compose.Compose)(nil)` and the same for `*compose.RemoteCompose` and `*compose.HostContainers`, beside the older `ExecProvider` one, plus a runtime check in `TestHostContainers_CapabilityInterfaces`): the key works entirely through a runtime type assertion and every TUI test drives a double that satisfies it by construction, so without them a rename or a signature drift leaves all 7 packages green while `i` becomes a silent no-op in production. `Inspector` needs this more than its siblings — it is the one capability ALL THREE composers must implement, and it has no `readOnly` gate to make its absence visible. **All three composers implement it, so `i` is NOT gated on `m.readOnly()`** — the asymmetry against every other recent container key is deliberate: every operation is a compose pipeline and an unmanaged container has no compose file, but inspect is read-only by nature and works identically on both variants. It therefore appears in BOTH help tables through ONE shared append in `inspectGroup(readOnly, grouped bool)`, whose position is load-bearing (see the truncation table in `docs/architecture/tui-help-overlay.md`), and `TestHelpGroups_ReadOnlyNamesEveryBoundKey`'s bound set carries `i` too. **`docker inspect` is a top-level docker command, not a compose subcommand**, so all three implementations bypass `command()`/`remoteCommand()` — the rule `docker stats`, `docker image inspect` and `docker buildx imagetools inspect` already follow: `Compose.Inspect` uses `runDockerCmd`, `RemoteCompose.Inspect` uses `runRemoteDockerCmd` (so the `SSHExtraArgs`-before-host splice and `classifySSHError` come for free), and `HostContainers.Inspect` goes through the `dockerRunner` seam's `run`. Resolving the container ID is a SECOND call, so inspect costs two round-trips on a remote hop: the two compose composers list `ps -a --format json` through their own command builder and hand the bytes to `resolveInspectID(psOut, service)` — `parsePsEntries` (array AND NDJSON, the same tolerance `parseContainerStatus` applies to the same output) then `pickInspectContainer`, one home for the middle half both transports share; `HostContainers` reuses `unmanagedEntries` + `pickHostInspectContainer`. The `no container found for %q` text two test suites pin has ONE producer, `errNoContainer(name)` in `inspect.go`, which `resolveInspectID` and `HostContainers.Inspect` both call — the host path builds no string of its own. **`pickInspectContainer` mirrors the Uptime aggregation gate in `parseContainerStatus` exactly** — `entry.State == "running" && uptime != ""` wins, longest duration among running replicas, and a restarting replica only when nothing running has been seen. A naive max-duration picker disagrees with the Uptime column the container screen renders on a running+restarting mix, so `TestPickInspectContainer_MatchesUptimeColumn` drives the SAME entries through both and fails if the two diverge. A service whose replicas are all stopped falls back to the first matching entry (a stopped container stays inspectable); only a service with no entry at all returns `("", false)`, which every caller turns into `no container found for %q` — never a panic and never an arbitrary container. Host containers need no such rule (docker enforces unique names per host), so `pickHostInspectContainer` is a first match on the existing `hostContainerName` helper. **The parse layer lives in `internal/compose/inspect.go`**, beside every other docker-output parser in this repo: `ParseInspect` unwraps the single-element JSON array docker always emits, strips the leading slash off `Name`, and returns the narrow exported `InspectDoc` family — only the fields the five sections render, exported because the renderer lives in `tui` and constructs them directly in its table tests. **That narrowness claim is literal and must stay so**: a parsed-but-unrendered field is a promise the screen does not keep, so `State.Paused/Restarting/Dead/FinishedAt`, `InspectMount.Mode` and `InspectHealthLog.Start` were dropped rather than carried, and `State.Error`, `Name` and `Healthcheck.StartPeriod` earned rows instead — `State.Error` is docker's own reason a container failed to start (`exec: "foo": executable file not found in $PATH`), which the exit code alone cannot give, and `Name` is the only place the summary says WHICH replica the Uptime rule picked, since the breadcrumb names the service. Add a field only together with the row that draws it. `Inspect` still returns raw `[]byte`, so raw mode stays byte-identical to `docker inspect`. `State.Health` and `Config.Healthcheck` are POINTERS because docker omits both keys entirely for an image with no healthcheck, and the HEALTH section is dropped on exactly that distinction (`hasHealthcheck` also drops the explicitly-disabled `Test: ["NONE"]` form); the three `Healthcheck` intervals are `time.Duration`, since docker reports them as nanosecond counts that unmarshal directly. **The renderer is `buildInspectSummary(doc, width, upd inspectUpdateInfo)` in `internal/tui/inspect.go`** (the third parameter arrived with the IMAGE update rows — see the section below; its ZERO VALUE draws no extra row, so everything in this paragraph reads as it did before) — pure, no Model, no TTY, no Docker, golden-testable against the three real fixtures in `internal/compose/testdata/docker_inspect_{healthy,unhealthy,stopped}.json`. Five sections in order — STATE, HEALTH, IMAGE, MOUNTS, ENV — a section with nothing to say is omitted and STATE always renders. **HEALTH enforces that by building its rows into a scratch `inspectBuilder` first** and writing the header only when at least one row exists: `hasHealthcheck` answers "is there a healthcheck", which a zero-valued `&InspectHealthcheck{}` with no runtime state satisfies while having nothing at all to say, so a straight-line render emits a bare header. **Probe output soft-wraps and must NEVER truncate**: it is routinely long and multi-line (curl bodies, stack traces) and it is the feature's whole justification, so every line goes through `inspectBuilder`, which wraps with `wrapCells` and aligns continuation lines under the value column; below `inspectMinValueWidth` the value stacks under its label instead of shredding one rune per line. **`wrapCells` is cell-aware, and that is load-bearing**: it lives in `internal/tui/format.go` beside its sibling `softWrapLine` (the log viewer's), which chunks by RUNE, so a probe output, env value or mount path carrying CJK or an emoji renders at up to 2x the pane width — and an ASCII-only width sweep can never catch it, because runes and cells agree there. It wraps through `ansi.Hardwrap(line, width, true)` (preserving leading whitespace, so stack-trace indentation survives) and `inspectBuilder.kv` measures its label column with `ansi.StringWidth` for the same reason. `TestBuildInspectSummary_NeverExceedsWidth` carries a wide-rune doc and sweeps widths 1-120; a single wide grapheme is 2 cells and cannot be split, so that one doc starts at width 2. **Every line the builder emits is sanitised at ONE chokepoint, `inspectBuilder.push`.** docker's JSON escapes a control byte into printable text, but only the C0 block — Go's `encoding/json` emits DEL and the C1 code points as RAW bytes, so raw mode needs a filter of its own (`sanitizeInspectRaw`, below) — and `ParseInspect` decodes even the escaped C0 back, and an ENV value, a probe output, an image ref and a mount path are all attacker-influenceable: a third-party image can carry an OSC 52 clipboard write, a title set or a report sequence straight onto the operator's terminal the moment `i` is pressed, and `ansi.StringWidth` counts an escape sequence as ZERO cells so neither the wrap nor the viewport stops it. `sanitizeInspectLine` runs `ansi.Strip` and then drops what it leaves behind (BEL, CR, DEL and the 8-bit C1 controls a terminal reads as escape introducers). `section()` is the ONE deliberate bypass — its title carries our own lipgloss style, which IS an escape sequence — so a future section renderer must not be routed back through `push`. **Tabs are expanded BEFORE the measurement, in `wrapCells`** (`expandTabs`, `tabStopWidth` = 8-column stops, cell-aware, also in `format.go` — both helpers are screen-agnostic text utilities, not inspect ones): `ansi.StringWidth` counts a tab as zero cells while a terminal advances to the next stop, so a tab-bearing stack trace in a probe output wraps late and renders past the pane edge — which pushes `viewInspect` past `m.height` and scrolls the title off, the same failure the clamped error line exists to prevent. Expanding also KEEPS the indentation the sanitiser would otherwise delete (a tab is a C0 control), which is why the order is expand-then-strip and why `TestBuildInspectSummary_ExpandsTabs` pins the rendered indent rather than only the width. **Raw mode carries a NARROWER pass of its own, and the difference is the point**: `setInspectContent()` writes `sanitizeInspectRaw(m.inspectRaw)`, which filters the same rune set through the shared `unsafeTerminalRune` predicate but keeps newlines (they are the raw view's line structure) and does NOT run `ansi.Strip` — the ESC bytes arrive already escaped as the six printable characters `\u001b`, so there is no escape sequence to strip and stripping would only corrupt a payload that is safe as it stands. `m.inspectRaw` itself stays verbatim: it is what `ParseInspect` reads, and the filter runs at the render chokepoint. Without it an ENV value or a probe output could carry U+009B (CSI) or U+009D (OSC 52 clipboard write) onto the operator's terminal through `i` then `r` (`TestSanitizeInspectRaw`, `TestInspectDataMsg_RawModeFiltersControlBytes`). NETWORKS, PORTS, RESOURCES and LABELS are deliberately deferred — raw mode answers each, and PORTS duplicates a column the container screen already renders. **No secret masking, deliberate**: ENV is rendered verbatim in both modes, matching lazydocker/k9s/Docker Desktop; the accepted consequence (a screen-share leaks credentials the moment `i` is pressed) is STATED in the README rather than left to be discovered. If masking is ever added it must cover BOTH modes — masking only the summary makes `r` a one-key bypass, which protects nothing. **Mechanics follow `screenConfig`, not `screenLogs`**: `enterInspect()` bumps `inspectSession`, resets the seven `inspect*` fields, sizes the viewport through `inspectViewportSize(m.width, m.height)` — ONE home for the chrome budget, so `enterInspect` and the `WindowSizeMsg` branch cannot drift: `m.height - 6` (the config sizing — NOT the logs `- 7`, which reserves a row for the log bar) with a 3-row floor, and `m.width - 4` with a `< 10 → 40` floor — calls `m.clearSearch()` (one of the eleven departure sites enumerated in `docs/architecture/tui-logs-and-search.md`) and returns `fetchInspect()`, which reads `inspectSession` off the Model exactly as its seven sibling fetch commands do; the `inspectDataMsg` handler is gated on `m.screen != screenInspect || msg.session != m.inspectSession`, and treats a fetch that SUCCEEDED with zero bytes as an error — `rebuildInspectSummary()` early-returns on empty bytes, so `ParseInspect`'s own empty-output error never fires and `viewInspect()` would read `Loading...` for ever with nothing to retry; `esc` calls `clearInspect()` and returns WITHOUT a `refreshStatus()`, because the screen changes no container state — **with ONE exception, which is the only cleanup this screen owes anything to**: in GROUPED mode `i` binds `m.composer` from the CURSOR ROW's group at action time (`bindCursorComposer()`, since the host view holds no composer of its own), so the `esc` return path must call `unbindGroupedComposer()` and dispatch `loadGroups()` — without the unbind the host view keeps serving one project's composer to the next row's action key, and without the reload it repaints from rows that stopped refreshing the moment the inspect screen took the 5-second tick's screen gate away; the `WindowSizeMsg` branch re-renders the summary at the new width without losing `inspectRaw`. Three helpers keep the two buffers honest: `setInspectContent()` is the single `SetContent` chokepoint, so the fetch handler, the `r` toggle and the resize branch cannot disagree about which buffer is on screen; `rebuildInspectSummary()` surfaces a parse failure in `inspectErr`, empties the summary and KEEPS `inspectRaw`, while the switch to `inspectShowRaw` is made by the `inspectDataMsg` handler — the raw bytes are the only content that exists at that point, so leaving the summary selected would show an error line above an empty pane and make the user guess that `r` is the way to the payload, but the switch has to be made ONCE on the transition into the error state and NOT inside `rebuildInspectSummary()`, which also runs on every resize and would then silently undo a later `r` back to the summary (`TestInspectScreen_ResizeKeepsTheChosenModeAfterAParseFailure`) (`viewInspect()` therefore keeps the viewport on screen BESIDE the error line and reads `Loading...` only when there are neither bytes nor an error); `clearInspect()` is the single departure-cleanup helper and deliberately does NOT bump `inspectSession` — `enterInspect()` bumps on the way in, which is what invalidates an in-flight fetch, and the handler's screen check discards one that lands after departure, the same discipline as `configSession`. The `r` toggle calls `GotoTop()` after the chokepoint: `SetContent` preserves `YOffset`, so a toggle from a scrolled summary into the much longer raw JSON would otherwise land the reader mid-document. **`enterInspect()` also calls `SetHorizontalStep(4)`** (the value `enterLogs` uses when wrap is off): raw mode does not wrap and the viewport hard-cuts every line at its width, so with the default step of 0 `left`/`right` are inert and real `docker inspect` output — a `LowerDir` list, a JSON-escaped probe `Output`, lines hundreds of columns wide — is unreachable past the pane edge, in exactly the mode that exists as the escape hatch. **The step is what makes a stale `xOffset` reachable, so `setInspectContent()` resets it on every buffer change** (`SetXOffset(0)` after the `SetContent`, covering the fetch handler, the `r` toggle and the resize branch at once): `SetContent` KEEPS the horizontal offset and `GotoTop()` moves only `YOffset`, so a sideways scroll through the raw JSON survives the toggle back — and because the summary is wrapped to the pane its `longestLineWidth` never exceeds the width, so `visibleLines()` cuts EVERY line at `[xOffset, xOffset+width]` and renders a BLANK pane under a correct title and footer, recoverable only by an undocumented `left`. The raw path resets for the same reason on a resize that widens the pane past the longest line. Pinned by `TestInspectScreen_RToggleAfterSidewaysScrollKeepsSummaryOnScreen` and `TestInspectScreen_ResizeClearsStaleHorizontalOffset`; `← →` is named in the `screenInspect` MOVE group and `left`/`right` are in that screen's `bound` row. **The footer drops its `r` token whenever the buffer the toggle would switch TO is empty** — a failed FETCH leaves neither buffer, a failed PARSE leaves the raw bytes but no summary, and in both states the toggle could only relabel itself over an empty pane. The `r` case and the footer read ONE predicate, `inspectToggleAvailable()`, so the key and its advertisement cannot disagree; testing `len(inspectRaw) == 0` instead covers only the fetch half and leaves `r summary` on screen after a parse failure (`TestViewInspect_FooterDropsRWithoutBuffers`, `TestInspectScreen_RIsInertWithoutBuffers`, `TestViewInspect_ParseErrorShowsTheRawBytes`). **The footer is clamped for the same budget**: it measures 42 cells, so below 42 columns both its line and the `helpStyle` margin line wrap, add two physical rows the renderer does not know about, and cost the title — `clampToWidth` holds it the way `containerFooter()` does, and `TestViewInspect_ErrorIsOneClampedLine` plus `TestViewInspect_FooterNeverExceedsWidth` sweep widths 40-120 rather than sampling one. The HEIGHT half is `TestViewInspect_FitsShortTerminal` (heights 9-30 at three widths, with and without the error line — the sibling of `TestViewHelp_FitsShortTerminal`) and `TestViewInspect_NoTrailingNewline`, which pins the invariant it rests on: bubbletea splits `View()` on `\n` with no `TrimSuffix` and keeps the LAST `m.height` elements, so a trailing newline renders one line too tall and costs the title. `viewConfig` and `viewLogs` carry the same unclamped footer (and unclamped title) — pre-existing and out of this feature's scope, recorded as a residual. **The error slot is collapsed and clamped**: `viewInspect()` budgets exactly ONE line for it, but the compose layer feeds raw stderr in (`withStderr`, an SSH banner, a multi-line docker failure), so the message runs through `strings.Fields`+`clampToWidth` — the same never-wrap discipline `searchBarLine`/`logBarLine`/`containerFooter` follow. Without it the renderer keeps only the last `m.height` lines and the title, plus the head of the error that names what failed, scrolls off. **The `WindowSizeMsg` branch calls the same `inspectViewportSize` helper**, so the floors cannot be a hand-maintained mirror: unguarded, a 3-column pane sets a negative width and `buildInspectSummary` falls back to its 80-column default for a viewport that renders nothing. `screenConfig` and `screenLogs` still carry that asymmetry between their `enter*` helper and their resize branch — inherited, and out of this feature's scope. The screen opens no text input, so `typingInInput()` needs no case and `q` reaches the existing `default: key = "esc"` rewrite. **The view is a one-shot snapshot, with ONE exception.** `fetchInspect` is called from exactly one place (`enterInspect`), the 5s `refreshTickMsg` is gated on `screenSelectContainers`, and `r` only swaps two buffers already in hand — so health status, failing streak and the probe output are frozen at the instant `i` was pressed, and `esc` then `i` is the only refresh. The exception is the update rows: an `updatesMsg`, or an `updateDetailsMsg` whose `forKey` is the context on screen, calls `redrawInspectFromCache()`, which rebuilds the summary so the IMAGE update rows can arrive (or leave) on their own. Nothing is FETCHED for the screen — the rows are read out of the update cache — so the snapshot property still holds for everything `docker inspect` returned. `screenConfig` behaves the same way; a refresh key is a recorded follow-up, and the README states the behaviour rather than leaving it to be discovered. TUI-only: no CLI subcommand, no `Composer` change (the four mock sets are untouched) and no ID field on `runner.ServiceStatus` — the ID lookup stays inside `compose`, behind `Inspect`.

## Inspect screen — the IMAGE section's update rows

The IMAGE section grew four rows that draw only when the `⇧` update check has something to say about the service: `built`, `update`, `update id` and `update built`. They sit BETWEEN `image id` and `command`, so the two ids and the two build dates read as one block — `image id` against `update id`, `built` against `update built`:

```
IMAGE
  image         postgres:16-alpine
  image id      sha256:7e7dbab8…
  built         2026-07-07 17:47:22  (47d ago)
  update        available  (checked 3m ago)
  update id     sha256:c05eced0…
  update built  2026-08-19 19:14:43  (4d ago)
  command       postgres
  entrypoint    docker-entrypoint.sh
```

The full row order is therefore `image`, `image id`, `built`, `update`, `update id`, `update built`, `command`, `entrypoint`.

`TestBuildInspectSummary_UpdateRowOrder` pins that order, because the pairing is the row block's whole argument — an `update id` two rows away from the `image id` it is meant to be compared with is just another digest on screen.

**The `digest` row was relabelled `image id` in the same change.** It has always been the local image ID docker resolved the tag to, and an `update id` row beside a row still labelled `digest` invites exactly the false comparison the feature must avoid: `update id` is the registry image's CONFIG digest (which equals the image ID the daemon will assign after a pull), NOT the manifest-list digest `CheckUpdates` compares. The rename is user-visible and had four assertions pinning the old label, which is why it landed as an isolated commit.

**Each row keys off its OWN input, and the renderer never infers one from the other.** `built` needs a detail with a non-zero `LocalCreated`; `update` needs a non-nil verdict (`available` on `true`, `up to date` on `false`, nothing at all on `nil`); `update id` needs a non-empty `NewID`; `update built` needs a non-zero `NewCreated`. So a detail with no verdict still draws the three detail rows, and a verdict with no detail still draws `update` — a future caller that fills only half the struct cannot make the section claim something it was not told. The `(checked 3m ago)` suffix comes from the cache entry's `fetchedAt` and is dropped when that is zero, rather than reported as "moments ago": a missing timestamp is not a fresh one.

**The section's presence gate is UNCHANGED.** A doc with no image, no command and no entrypoint stays silent even when a verdict is in hand. An update verdict describes the image, so a section opened by the verdict alone would carry one row with nothing to compare it against.

**`buildInspectSummary(doc, width int, upd inspectUpdateInfo)` — the signature widened, and the zero value is what made that mechanical.** `inspectUpdateInfo{now, detail, verdict, checkedAt}` carries the clock as a FIELD rather than a `time.Now()` call inside the renderer. `verdict` is a `*bool` because it is a genuine tri-state; `detail` is a VALUE (`compose.UpdateDetail`), not a pointer, because every field of it is already checked on its own, so a zero struct and an absent one draw the same nothing — the pointer bought no state and only split the renderer into two nil-checked blocks around the verdict row, so the function stays pure and the relative ages are testable against a fixed `now` (`TestBuildInspectSummary_UpdateRows`, `_UpdateRowsEpochSentinel`, `_UpdateRowsWrapNarrow`). **Its zero value must keep drawing no new row** — that property is what let the 25 existing call sites migrate by appending `inspectUpdateInfo{}` with every pre-existing assertion intact, and `TestBuildInspectSummary_ZeroUpdateInfoIsByteIdentical` pins it. There is exactly ONE production call site, inside `rebuildInspectSummary()`; the `WindowSizeMsg` branch and the `inspectDataMsg` handler both go through that helper, so they inherited the change untouched. `rebuildInspectSummary` builds the struct itself from `m.currentUpdateInfo()` — one lookup, one site, no chance of three copies drifting.

**The screen is a pure CONSUMER of the `⇧` cache; it never fetches.** The details ride the `refreshUpdates` schedule (on a follow-up `updateDetailsMsg`, not the verdict message) and land on the same `updateEntry`, which is why entering `i` on a cold cache needs `redrawInspectFromCache()` — called by BOTH handlers — to rebuild the summary. That helper skips the viewport write while `inspectShowRaw` is on, because the raw buffer is unaffected by update details and rewriting it would only reset the horizontal offset out from under a sideways scroll — see the `UpdateDetailer` section of `docs/architecture/update-detection.md` for the fetch sequence, the rate-limit mitigations, the three-state index result and the epoch sentinel that omits the two build-date rows. Two consequences land here: **no screen state of its own exists**, so `clearInspect()`, the `esc` chain, `entryLocal` and the `connectResultMsg` error path need no cleanup at all (the update subsystem's own `detailsInFlight` guard is a global one-batch bound cleared only on message arrival, so no departure site anywhere touches it); and **`inspectViewportSize()` is unchanged**, because the new rows live inside the viewport rather than in the chrome budget. ("No screen state" is about the UPDATE-DETAIL machinery specifically — the screen still owes the grouped-mode composer unbind and reload named above.) The longest new label is `update built` — `"  update built"` is 14 cells against `inspectValueCol = 18` — so no layout constant moves either, and the rows soft-wrap through `inspectBuilder.push` like every other content line rather than truncating. **Raw mode stays byte-identical**: `m.inspectRaw` never sees these values, pinned by `TestInspectScreen_RawModeIgnoresUpdateDetails`, which compares raw output with and without a populated cache and uses the differing summary as its control.
