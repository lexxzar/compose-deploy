# Remote SSH transport, `servers.yml`, and the settings editor

> Extracted verbatim from `CLAUDE.md`, which is auto-loaded and has a size limit.
> `CLAUDE.md` carries the rule digest; this file carries the full rationale, the
> failure modes it prevents, and the tests that pin them. Read it before you touch `internal/compose/remote.go`, `internal/config/`, `cmd/remote.go`, or the server/settings screens.

Two threads run through this cluster, and every section below sits on one of them.

**The SSH-target thread**: a ControlMaster socket is opened once per session → `config.ParseSSHTarget` turns `[user@]host[:port]` into an `SSHTarget` → its `PortArgs()` plus an optional `-i <key>` become `RemoteCompose.SSHExtraArgs` → every ssh argv in the repo splices that slice immediately before the host argument, through one helper. Break the thread anywhere and the process dials a different endpoint than the connection it was derived from.

**The color thread**: `Group.Color` (or `Server.Color` for an ungrouped server) → `config.ValidColors` gates what may be written → `Config.GroupColor()` resolves the group → `Model.resolveServerColor()` picks group-or-own → `serverBadge()` decides badge-or-plain-text → `serverBadgeStyle()` maps the name to a lipgloss background. Every hop has a defined empty case, and the empty case is a plain breadcrumb rather than an error.

## Remote SSH

`RemoteCompose` implements `runner.Composer` by wrapping every docker compose invocation in an ssh call over a ControlMaster persistent socket, so a deploy of six services costs one authentication rather than six. `NewRemote(host, projectDir)` derives the socket path deterministically: `/tmp/cdeploy-ctrl-{hex of the first 6 bytes of sha256(host)}-{pid}`. Both halves of that key are load-bearing — the host hash keeps two servers from sharing one master, and the PID scope keeps two concurrent `cdeploy` processes (or a crashed one that left a socket behind) from adopting each other's connection.

**Connect is split into a command and a runner because the TUI needs the terminal.** `ConnectCmd(ctx)` returns the `*exec.Cmd` (`ssh -fNM -S <socket> -- <host>`) WITHOUT running it, so the TUI can hand it to `tea.ExecProcess`, which suspends Bubble Tea and gives ssh the real terminal — a password, a passphrase or a 2FA prompt is unanswerable otherwise. `Connect(ctx)` runs the same command with `os.Stdin`/`Stdout`/`Stderr` attached, which is what the CLI needs. `Close()` sends `-O exit` under a 5-second `context.WithTimeout`: a stale socket must not hang process exit, and `Close` is on the deferred path of every CLI subcommand.

**`Detect` builds its own probe argv rather than going through `remoteCommand()`.** It runs `docker compose version`, then `docker-compose version`, each with `-o ControlMaster=no` over the existing socket. Going through `remoteCommand()` would prepend the `CURRENT_UID` assignment and the `cd <projectDir>` — neither is wanted for a version probe, and the `cd` would fail the probe on a host where the project directory does not exist yet. `Detect` no-ops once `detected` is set; `SetStandalone(bool)` inherits an already-known verdict into a new instance, which is how `remoteComposerFor` builds per-project composers without re-probing.

**Every argument that reaches the remote shell is escaped by `shellEscape()`** (wrap in single quotes, rewrite `'` as `'\''`). `buildRemoteCommand` assembles ONE shell string: `cd <projectDir> && CURRENT_UID=$(id -u):$(id -g) <composeBin> <flags><args>`. `CURRENT_UID` is evaluated ON THE REMOTE HOST via `$(id -u):$(id -g)` rather than stamped from the local process — the local uid/gid is the wrong owner for a bind-mounted volume on the server. The local `Compose` stamps `uid:gid` directly for the same variable, so the two transports agree on the variable and disagree on where it is computed, deliberately.

**Socket ownership is the TUI's, not the model's.** `tui.Run()` calls `disconnectFunc` on the FINAL model after `p.Run()` returns (alongside `ctxCancel()`), so a master connection never outlives the TUI process even on a panic-free early quit; the CLI resolve helpers hand back a cleanup the subcommand `defer`s. The TUI shows the server picker whenever servers are configured; the CLI selects one with `--server`/`-s`.

Pins: `TestConnectCmd_Args`, `TestClose_Args`, `TestRemoteDetect_SSHArgs`, `TestShellEscape`, `TestRemoteCommand_SpecialCharactersEscaped`, `TestRemoteConnect_ViaHook`, `TestRemoteConnect_Error`, `TestRemoteClose_ViaHook`.

## Ad-hoc SSH (`-S`/`--ssh`)

The `--ssh` persistent flag (registered in `cmd/root.go` immediately after `--server`) is the ad-hoc complement to config-based `--server`. It accepts `[user@]host[:port]` and lets CLI users — especially CI, which has no home directory worth persisting to — connect without a `~/.cdeploy/servers.yml` entry.

**Three rules, three enforcement sites, and the split is deliberate.**

1. `--server` and `--ssh` are MUTUALLY EXCLUSIVE, and `--identity` REQUIRES `--ssh`. Both live in `checkRemoteMutex(serverName, sshTarget, identityFile)` (`cmd/remote.go`), which every subcommand calls as the FIRST statement of its run function — before `os.Getwd()`, before `signal.NotifyContext`, and in `runOperationWithPrep` before the container-argument validation. Ordering is what makes the error deterministic: with the mutex check placed after argument validation, `cdeploy deploy -a --ssh h --server s` reports "specify container names" on one subcommand and the mutex error on another. Four call sites cover the whole surface: `runOperationWithPrep` (deploy/restart/stop/rollback), `runExec`, `runLogs`, `runList`. Pinned by `TestCheckRemoteMutex` and `TestRunOperation_MutexBeforeContainerValidation`, plus a per-subcommand mutex test each (`TestRunOperation_SSHAndServerMutex`, `TestRestartCmd_SSHAndServerMutex`, `TestStopCmd_SSHAndServerMutex`, `TestRollbackCmd_SSHAndServerMutex`, `TestRunExec_SSHAndServerMutex`, `TestRunLogs_SSHAndServerMutex`, `TestRunList_SSHAndServerMutex`).
2. `--ssh` REQUIRES `--project-dir`, enforced as the first check inside `resolveSSHRemote` rather than in the mutex helper (which is not given the directory). The directory is resolved ON THE REMOTE HOST — it becomes `cd <dir>` in the remote command string — so defaulting it to the local working directory would name a path that means nothing there. One consequence is documented at the call site in `cmd/list.go`: `--ssh` always implies a SINGLE project, so `cdeploy list --ssh …` never runs the host-wide multi-project discovery that the local and `--server` paths do. Pins: `TestResolveSSHRemote_EmptyProjectDir`, `TestRunOperation_SSHRequiresProjectDir`, `TestRunExec_SSHRequiresProjectDir`, `TestRunLogs_SSHRequiresProjectDir`, `TestRunList_SSHRequiresProjectDir`.
3. `--ssh` is CLI-ONLY. The root `RunE` rejects it (together with `--identity` and `--project-name`) rather than ignoring it, because `cdeploy --ssh user@host` reads as "open the TUI against that host" and would silently open a local one. `cmd/skill.go`'s `checkSkillNoRemoteFlags` rejects all four remote flags for the same reason: the skill verbs write local files only. Pins: `TestRootCmd_FlagRejectedInTUI`, `TestSkillRejectsRemoteFlags`.

**`resolveSSHRemote(ctx, sshTarget, projectDir, projectName, identityFile, newRemote)`** is the one body that builds an ad-hoc composer, in this order: project-directory check → `config.ParseSSHTarget` → `target.PortArgs()` → optional `config.ParseIdentity` appended as `-i <clean path>` → `newRemote(target.SSHHost(), projectDir)` → stamp `SSHExtraArgs` → stamp `ProjectName` → `Connect()` → `Detect()`. `newRemote` is a PARAMETER so each subcommand passes its own injectable factory variable (`opNewRemote`, `execNewRemote`, `logsNewRemote`, `listNewRemote`), preserving the test seams that predate the helper. `projectName` is a parameter for the reason the project-identity paragraph in `CLAUDE.md` gives: a directory does not identify a project, and a helper that read the package-level flag var would let a new subcommand forget it silently.

**The returned cleanup is ALWAYS non-nil**, so callers write `defer cleanup()` on the line after the call with no nil check — the error paths return the shared `noopCleanup`. On a `Detect` failure the helper calls `rc.Close()` itself before returning, because the ControlMaster is already up at that point and the caller is about to return an error rather than reach its defer; on a `Connect` failure there is nothing to tear down. Pins: `TestResolveSSHRemote_{HappyPath,HappyPathNoPort,ConnectFailure,DetectFailure,MalformedTarget}`.

Wiring is a branch ABOVE the existing `--server` block in `deploy`/`restart`/`stop`/`rollback`/`exec`/`logs`/`list`; the config-based path is untouched. `list` is the one subcommand that does not use `resolveServerRemote` for its `--server` branch — it inlines the equivalent (load config, `Validate()`, `FindServer()`, build the `RemoteCompose`, stamp `ProjectName`, `Connect()`, `defer Close()`, `Detect()`) because it must IGNORE `server.ProjectDir`: honouring it would silence host-wide discovery for every server that configures one. **Whichever of the three branches a new subcommand takes, the project name arrives as a PARAMETER and is stamped there** — `resolveSSHRemote` and `resolveServerRemote` take it in their signatures and `prepareLocalComposer` stamps the local composer, precisely so a new subcommand cannot silently address the DIRECTORY's default project instead of the one the user named (the identity rule itself is in `docs/architecture/compose-command-and-status.md`). Pins: `TestDeployCmd_SSHFlagInherited`, `TestExecCmd_SSHFlagInherited`, `TestLogsCmd_SSHFlagInherited`, `TestListCmd_SSHFlagInherited`, plus a `_SSHHappyPath` per subcommand.

**The parser is `internal/config/sshtarget.go`, and it fails closed.** `ParseSSHTarget` trims, then rejects, in order: an empty string (`ssh target is empty` — the one message that carries its own prefix, since it has no value to be quoted into the caller's wrapper); any internal whitespace; a `[`-prefixed value (bracketed IPv6); more than one `:` in the `host[:port]` tail, which catches bare IPv6 (`::1`, `fe80::1`) and malformed input (`host:22:30`) with one message rather than mis-parsing either; more than one `@`; an empty user; a `:` inside the user part (`user:pass@host` is not supported); **a user starting with `-`**; **a host starting with `-`**; a present-but-empty port; a non-numeric port; a port outside `1..65535`. The two `-` rejections are option-injection guards: without them `-oProxyCommand=…@host` or `-J jump@evil` lands in ssh's argv where an option is expected, and the connection string becomes arbitrary ssh configuration. Every other message is bare (`host is empty`, `port %q is not a number`) because the caller wraps with `invalid --ssh value %q: %w`. `SSHHost()` renders `user@host` or bare `host`; `PortArgs()` renders `["-p", "NNNN"]` or nil. Pins: `TestParseSSHTarget_Happy`, `TestParseSSHTarget_Errors`, `TestSSHTarget_SSHHost`, `TestSSHTarget_PortArgs`.

No TUI changes anywhere — `--ssh` is strictly a CLI feature.

## Ad-hoc SSH identity (`-i`/`--identity`)

The `--identity` persistent flag (registered in `cmd/root.go` immediately after `--ssh`) accepts a path to an SSH private key. It exists for CI and automation workflows that write a key out of a secret store at job start and have no `~/.ssh/config` entry to point at. It is deliberately STRICT-NARROW: valid only alongside `--ssh` (so mutually exclusive with `--server` by transitivity through the `--identity requires --ssh` rule), rejected by the TUI, rejected by `skill`.

**`config.ParseIdentity` (`internal/config/identity.go`) validates before ssh ever runs**, because ssh's own failure for a missing or unreadable key is late and obscure — it falls through to another auth method and reports a generic permission denial. It trims; rejects empty (`path is empty`); expands a `~/` prefix through `os.UserHomeDir()`; rejects bare `~` and the `~user` form (`only ~/ is supported (no ~user)`) — a home directory is not a key file, and `~user` would need a `getpwnam` lookup Go does not offer portably; `filepath.Clean`s; requires `os.Stat` to succeed (`not found: %s` / `cannot stat: %w`) and to report a REGULAR file (`not a regular file`, which is what catches a directory or a device); and requires `os.Open` to succeed (`not readable: %w`). The open is not redundant with the stat: mode bits miss ACLs and miss the case a CI runner actually produces, a key written by a different user in a shared workspace. **Permission checks (0600 and friends) are deliberately NOT done** — `ssh(1)` already enforces them at connect time, and duplicating the rule would put two different verdicts on one file. Relative paths pass through unchanged, matching `ssh -i`, which resolves them against the working directory. Symlinks are followed by the stat and accepted when the target is a regular file. Error wording is bare because the caller wraps with `invalid --identity value %q: %w`.

**`resolveSSHRemote` appends `["-i", cleanPath]` to `SSHExtraArgs` AFTER the port args**, producing `-p NNNN -i /path` in that order. Because the splice is centralised (next section), every SSH argv site absorbed `-i` with NO change to `internal/compose/remote.go` at all — that is the whole reason the identity rides `SSHExtraArgs` rather than becoming a field of its own.

Pins: `TestParseIdentity_{Empty,TildeExpansion,BareTilde,TildeUserRejected,NotFound,Directory,ValidFile,RelativePath,TrimsWhitespace,HomeUnsetError,StatPermissionError,Symlink_ToFile,Symlink_ToDir,Unreadable}`; `TestResolveSSHRemote_WithIdentity_{HappyPath,NoPort,InvalidPath,TildeExpansion}`; `TestRootCmd_IdentityFlagDetails`; `TestRootCmd_FlagRejectedInTUI`; `TestRunOperation_IdentityWithoutSSH`, `TestExec_IdentityWithoutSSH`, `TestLogs_IdentityWithoutSSH`, `TestList_IdentityWithoutSSH`; and a `_SSHHappyPathWithIdentity` per subcommand.

## The `SSHExtraArgs` splice — one helper, every argv site

**Rule: an ssh argv is built by `RemoteCompose.sshArgs(prefix []string, suffix ...string)` or it is wrong.** The helper returns `prefix + SSHExtraArgs + "--" + Host + suffix`, which encodes three things at once:

- **Extras go immediately before the host.** ssh takes its options before the destination; anything after the destination is the remote command. An extra spliced one position late becomes an argument to the remote shell, so `-p 2222` would be sent as text to the wrong port's default connection.
- **A literal `--` separates options from the destination.** Defence in depth over `ParseSSHTarget`'s two `-`-prefix rejections: even if a future caller supplies a host from somewhere the parser never saw, ssh reads it positionally.
- **nil `SSHExtraArgs` adds nothing.** That is the zero-behaviour-change default the flag shipped on, and it is pinned site by site: `TestSSHExtraArgs_NilArgvUnchanged_{Detect,DetectStandalone,ConnectCmd,Close,RemoteCommand,FindRemoteComposeFile,ConfigFile,EditCommand,ExecCommand}` compare full argv slices, `--` included.

The compose pipeline and the ordinary read methods reach the splice through `remoteCommand`/`remoteHostCommand` → `buildRemoteCommand`. **Everything else builds its own argv, and there are three separate reasons why** — knowing which one applies is how you decide whether a new site may reuse `remoteCommand`:

| Site | Why it builds its own argv |
| --- | --- |
| `Detect` (plugin + standalone probes) | must not carry `CURRENT_UID` or `cd <projectDir>` |
| `ConnectCmd`, `Close` | ssh control operations, not remote commands |
| `findRemoteComposeFile` | a `for f in …; do test -f …` shell loop, one round trip instead of four |
| `ConfigFile` | a plain `cat <file>` |
| `EditCommand` | needs `-t`, runs `${EDITOR:-vi}` |
| `ExecCommand` | needs `-t`, and assembles its own compose argv — so it must splice `composeFlags()` (`-f` pairs then `-p`) itself |
| `runRemoteDockerCmd`, `runRemoteDockerCmdStream`, `remoteDockerRunner.tty` | top-level `docker` commands (inspect, image inspect, buildx imagetools inspect, host ps/stats/logs/exec), not compose subcommands |
| `AllContainerStatsRemote` (`internal/compose/stats.go`) | `docker stats` is top-level; `remoteCommand` would emit `docker compose stats` |
| `writeRemoteFile`, `readRemoteSnapshot`, `PrepareRollback`'s cleanup `rm -f` | plain shell file I/O over the socket |

Every one of those calls `sshArgs`. A new site inherits the splice ONLY by doing the same.

**A composer derived from a live connection must COPY `SSHExtraArgs`.** `remoteComposerFor` (`cmd/root.go`) copies it onto each per-project `RemoteCompose` it builds, because the port and the key are what reach the host at all — a composer built without them dials a different endpoint than the connection it was derived from. `NewRemoteHostContainers(r)` keeps the `*RemoteCompose` pointer and so inherits the field rather than copying it.

Pins: `TestSSHExtraArgs_SplicedBeforeHost_AllSites` (a subtest per site, asserting `--` immediately before the host and the extras immediately before `--`), `TestRemoteEditCommand_SSHArgs`, `TestRemoteExecCommand_SSHArgs`, `TestRemoteInspect_SSHExtraArgsSplicedBeforeHost`, `TestAllContainerStatsRemote_extraArgsSplice`, `TestNewRemoteHostContainers_SplicesSSHExtraArgs`, `TestNewRemoteHostContainers_InspectSplicesSSHExtraArgs`, `TestHostContainers_GroupedRead_RemoteSplice`, `TestRemoteUpdateDetails_SplicesSSHExtraArgsBeforeHost`, `TestRemoteCheckUpdates_FallbackPath_ExtraArgsSpliced`, `TestRemoteWriteRemoteFile_SSHExtraArgs`, `TestRemoteComposerFor`.

## Config

`internal/config` loads `~/.cdeploy/servers.yml`, which defines remote servers and groups. `DefaultPath()` falls back to `./.cdeploy/servers.yml` when `os.UserHomeDir()` fails rather than returning an error, so a home-less environment still has a defined path to report.

`Config` holds `Groups []Group` and `Servers []Server`. `Group` has `Name` and `Color`. `Server` has `name`, `host`, optional `project_dir`, optional `group`, optional `color`.

**`Load()` returns an EMPTY config, not an error, when the file does not exist.** cdeploy has to run with no config at all — that is the local-only case, which is most users — so a missing file is a state, not a failure. Only a read error or a YAML parse error is fatal. Pins: `TestLoad_MissingFile`, `TestLoad_MalformedYAML`.

**`Load()` also runs `migrate()`, which is idempotent.** The old format put a color on each grouped server; the new format puts it on the `Group`. For every server carrying a `group`, migrate adopts the server's color into the group when the group has none — **first server wins** on a conflict — and then strips the per-server color. Auto-creating a missing `Group` entry happens ONLY for a legacy config, detected as `len(c.Groups) == 0`. Once a config declares any group at all, an unmatched `group:` reference is treated as a TYPO and left for `Validate()` to reject; auto-creating it would silently invent a group the user never wrote and mask the misspelling forever. Pins: `TestMigrate_OldFormatGroupedServers`, `TestMigrate_ConflictingColors_FirstWins`, `TestMigrate_NewFormatNoop`, `TestMigrate_UngroupedPreserved`, `TestMigrate_AutoCreateGroupWithoutColor`, `TestMigrate_NewFormatUnknownGroupNotCreated`.

**`Validate()` covers both halves.** Groups: name required, name unique, color in `ValidColors` when set. Servers: name required, host required, name unique, color in `ValidColors` when set, and `group` must name a declared group. It runs on the CLI resolve path (`resolveServerRemote`), at TUI startup, and inside the settings editor against a TEMPORARY config before anything is written. Pins: `TestValidate_{Valid,MissingName,MissingHost,DuplicateNames,InvalidColor,EmptyColor,DuplicateGroupNames,InvalidGroupColor,EmptyGroupColor,MissingGroup,ServerGroupExists,EmptyConfig}`.

**`Save(path)` is ATOMIC**: `MkdirAll(dir, 0o755)` → `os.CreateTemp(dir, ".servers-*.yml")` → write → close → `os.Rename`. The temp file is created in the DESTINATION directory so the rename is same-filesystem (a `/tmp` temp would make it a copy, which is not atomic); every failure path removes the temp. The settings editor is the only writer, and it writes on every keystroke-completed edit, so a half-written `servers.yml` after a crash or a full disk would take the user's whole server list with it. Pins: `TestSave_RoundTrip`, `TestSave_CreatesParentDir`, `TestSave_EmptyConfig`.

`FindServer(name)` is the lookup CLI `--server` uses; it returns `server %q not found in config`.

**SSH-specific options — keys, jump hosts, tunnels, port aliases, ciphers — belong in `~/.ssh/config`, with exactly ONE exception: `-i` for ad-hoc CI/automation use via `--ssh`.** `Server.Host` is handed to ssh verbatim, so a `servers.yml` entry can name an `~/.ssh/config` alias and inherit everything. Growing ssh knobs into `servers.yml` would fork the configuration surface and leave two places that disagree about how to reach one host.

## The color model — from `Group.Color` to the badge

`config.ValidColors` is an EXPORTED SLICE, in cycle order: red, green, yellow, blue, magenta, cyan, white, gray. It is the single source of truth for BOTH `Validate()` and the TUI cycle picker — `cycleColor(current, dir)` builds its list as `append([]string{""}, config.ValidColors...)`, so the empty (no color) option is position 0 and the wrap is modulo the whole list. Adding a color is therefore one edit.

**One edit there, and one more that nothing pins.** `serverBadgeStyle(color)` (`internal/tui/styles.go`) resolves the name through `colorMap`, a second list, and falls back to gray for a name it does not know. A color added to `ValidColors` alone validates, saves, round-trips and renders GRAY, silently. No test compares the two lists; add to both.

**Grouped servers carry no per-server color, enforced at three points**: `migrate()` strips `Server.Color` on load for any server with a group, the settings form assigns `srv.Color` only when the group field is empty, and `resolveServerColor` reads the group first. The group is therefore the ONLY home of a shared color, and recoloring a group recolors every member — which is the feature, not a side effect.

`Model.resolveServerColor(server)` returns `m.config.GroupColor(server.Group)` when the server has a group AND `m.config` is non-nil, otherwise `server.Color`. **The nil guard is load-bearing for tests**: many TUI tests build a Model without threading a config through, and an unguarded group lookup would panic on the server-selection path rather than in the test that forgot the config.

Every hop tolerates the empty string: `GroupColor` returns `""` for an unknown group, `resolveServerColor` passes `""` through, and `serverBadge()` reads `""` as "no badge" and renders the plain name.

Pins: `TestGroupColor_{Found,NotFound,EmptyColor,NoGroups}`, `TestResolveServerColor_{GroupedServer,UngroupedServer,NilConfig}`, `TestServerBadgeStyle_{KnownColor,UnknownAndEmpty}`, `TestCycleColor`.

## Settings editor

Two screens, `screenSettingsList` and `screenSettingsForm`, reached with `s` on the server select screen and **only when `m.config != nil`** — config and config path are threaded in through the `WithConfig(cfg)` / `WithConfigPath(path)` functional options, so `NewModel()` call sites that predate them (and every test that does not care) pass neither and get a Model that simply has no editor. The `s` key and the on-screen hint are both gated on the same nil check, so the screen never advertises a key it would ignore. Pins: `TestSettingsList_SKeyOpensSettings`, `TestSettingsList_SKeyIgnoredWithoutConfig`, `TestViewSelectServer_ShowsSettingsHint`, `TestViewSelectServer_NoSettingsHintWithoutConfig`, `TestSettingsReachable_EmptyServerList`.

**The list** renders every server in a Name/Host/Group/Color table. Color is resolved from the group for a grouped server and rendered with a trailing `(group)` marker so the user can see WHY the color is not editable per-server; an ungrouped server shows its own; no color shows `-`. `a` adds, `enter`/`e` edits, `d` arms an inline `y`/`n` delete prompt (`settingsDelete`). Empty list is a live state, not an error: `enter` and `d` on zero servers return without touching anything. Pins: `TestSettingsList_Navigation`, `TestSettingsList_ShowsGroupColorForGroupedServer`, `TestSettingsList_ShowsServerColorForUngroupedServer`, `TestSettingsList_EmptyState`, `TestSettingsList_DeleteOnEmptyList`, `TestSettingsList_EnterOnEmptyList`, `TestSettingsList_DeleteCancel`.

**The form** holds four `textinput.Model` instances (name, host, project_dir, group) plus a color cycle picker. `settingsField int` tracks focus: 0-3 are the text inputs, 4 is the picker. `tab`/`down` and `shift+tab`/`up` move modulo 5, blurring and focusing as they go. `left`/`right` cycle the color ONLY when `settingsField == 4`; on a text field they fall through to the input, where they are cursor movement. When the group field is non-empty the picker renders a `(group)` label instead of the `< value >` cycle chrome, and cycling then edits the GROUP's color — affecting every server in it. Editing a grouped server loads `settingsColor` from `GroupColor(srv.Group)` rather than from the server. Pins: `TestSettingsForm_{AKeyOpensBlankForm,EnterOpensPrefilledForm,TabCyclesFields,ShiftTabCyclesBackward,ColorCycling,ColorAccessibleWhenGrouped,GroupedServer_ColorGoesToGroup}`.

**Two shared dispatch predicates read these screens, and both are screen-SCOPED.** `typingInInput()` returns `settingsField < 4` for the form, which is what lets a server named `qa-prod` be typed (the `q`→`esc` rewrite skips the screen) and lets `?` reach the input instead of opening the overlay. `confirmPromptArmed()` returns `settingsDelete` for the list, so `?` cannot cover an armed delete prompt. A new input on either screen needs one case in `typingInInput()` and nothing else. Pins: `TestQTypedIntoSettingsFormInput`, `TestQBackNavigation_SettingsList`, `TestQBackNavigation_SettingsListCancelsDelete`, `TestQBackNavigation_SettingsFormColorPicker`, `TestHelpOverlay_QuestionReachesSettingsFormInput`, `TestHelpOverlay_SwallowedAtSettingsDeletePrompt`.

**SAVE FIRST, MUTATE ON SUCCESS — the order is the rule.** Both write paths (`enter` on the form, `y` on the delete prompt) build a TEMPORARY `config.Config` from cloned `Servers` and `Groups` slices, run `Validate()` on it (the form path; a delete cannot break an invariant that `cleanOrphanedGroups` does not already handle), call `tmpCfg.Save(m.configPath)`, and only THEN assign `m.config.Groups`, `m.config.Servers`, `m.servers` and `m.serverEntries`. Mutating the live config first and saving after inverts the failure: a full disk or a read-only home leaves the TUI showing a server list the file does not contain, and the next `Load()` — next session — silently reverts edits the user watched succeed. `settingsErr` carries `save failed: %v` and the screen stays put. Pins: `TestSettingsForm_SaveError`, `TestSettingsForm_ValidationError_EmptyName`, `TestSettingsForm_ValidationError_DuplicateName`.

**Groups are created and reaped automatically.** A form save whose group field names a group that does not exist appends a `Group{Name, Color}` entry; a group that already exists has its color overwritten with `settingsColor`. `cleanOrphanedGroups(groups, servers)` then drops every group no server references — run on BOTH the save and the delete path, so renaming the last member's group does not leave a dead entry behind. Pins: `TestSettingsForm_AutoCreateGroup`, `TestSettingsForm_OrphanedGroupCleanup`, `TestSettingsForm_OrphanedGroupCleanup_Delete`.

**After every successful write the derived state is rebuilt in one order**: `m.servers = m.config.Servers` → `m.serverEntries = buildServerEntries(m.servers)` → `m.fixServerCursor()`, plus a cursor clamp (an add parks `settingsCursor` on the new last row; a delete decrements it when it now points past the end). `buildServerEntries` is what makes grouped servers render together: Local first, then every ungrouped server, then each named group behind its own header row. Skipping the rebuild leaves the server picker listing a server the config no longer has. Pins: `TestSettingsList_ServerEntryRebuildAfterAdd`, `TestSettingsEdit_AddGroup_ClampsServerCursor`, `TestSettingsList_DeleteClampsServerCursor`, `TestSettingsList_DeleteLastServer_FixesCursor`, `TestBuildServerEntries_{NoGroups,WithGroups,MixedGroupedAndUngrouped,UngroupedAfterGrouped,Empty}`.

**Cleanup is small because the screens own nothing async.** `esc` from the list returns to the server picker; `esc` from the form returns to the list with no data changed; `settingsErr` is cleared on both transitions. There is no composer, no docker call, no session counter and no goroutine here — the stale-async-message discipline the rest of the TUI follows has nothing to guard on these two screens. Pins: `TestSettingsList_EscBackToServerSelect`, `TestSettingsForm_EscDiscardsBack`.

## Server badge

`breadcrumb()` joins `cdeploy`, the server badge (when `serverName != ""`) and `projName` with ` > `. `serverBadge()` reads `m.serverColor`: empty renders the BARE server name, so the breadcrumb falls back to the old plain form `cdeploy > prod-server > services`; non-empty renders `serverBadgeStyle(color).Render(" " + name + " ")` — bold black on the mapped background.

**The badge is inline, so no layout budget moves.** It occupies no extra line, which is why adding it needed no viewport height adjustment anywhere (`screenLogs`' `- 7`, `screenConfig`/`screenInspect`'s `- 6` are untouched). The style sets foreground and background only, so `ansi.StringWidth` still measures the breadcrumb correctly for any width clamp downstream.

**`serverHost` and `serverColor` are set and cleared alongside `serverName` at all five sites** — `entryServer` selection, `preselectedConnectMsg`, the `entryLocal` handler, the `connectResultMsg` ERROR path, and `backToServerScreen()`. Follow that discipline for any field added beside them. It matters more than a stale badge suggests: `serverName` is also a component of `projUpdatesCacheKey`, so a name left over from a failed connect reads ANOTHER server's update verdicts into this screen — which is exactly why the connect-failure path clears all three rather than only the one the breadcrumb draws.

Residual: `serverHost` is written at all five sites and read nowhere in production (the field comment says "for status bar"; no view renders it). It is kept because dropping it would break the set-and-clear symmetry that the cleanup rule above is stated in terms of.
