## Wait engine (`--wait` health gate)

`internal/runner/wait.go` holds ONE tested implementation of the health-wait rules, driven two ways. `EvaluateWait(prev WaitState, status map[string]ServiceStatus, opts WaitOptions, elapsed time.Duration) (WaitState, bool)` is a **pure reducer** — no clock reads, no IO; `elapsed` is an input, so it is table-testable without a fake clock and both drivers share identical semantics. `WaitState` is the accumulator (per-service `Verdicts`, plus unexported `everRunning`/`firstRunningAt`/`restartingCount`/`neverRunningCount` bookkeeping); it is copy-safe (the TUI holds it on its Model). Seed via `NewWaitState(services)` before the first call — a zero-value state has no target services and resolves as immediately-done. **Per-service precedence IS the spec, in this exact order** (documented above `EvaluateWait`): (1) `Uptime == "restarting"` bumps a counter, `restartingThreshold`=3 consecutive ⇒ `restarting` — checked FIRST because a restarting container reports `Running==false` AND `Uptime=="restarting"` simultaneously, so the exited rules would otherwise fire and the restart counter would never reach the threshold; (2) `Health=="unhealthy"` ⇒ `unhealthy`; (3) `Running==false` after `everRunning` ⇒ `exited`; (4) `Running==false`, never observed running, `neverRunningThreshold`=5 consecutive ⇒ `exited (never started)` (the ≥2-poll debounce absorbs the first-poll mid-transition race); (5) `Health!=""` ⇒ passes on `healthy`; (6) `Health==""` && `Running` ⇒ grace timer, passes after running continuously ≥ `Grace`. **Firm timeout boundary**: the PASS assignments in rules 5/6 are gated on `elapsed <= Timeout`, so a service that first becomes healthy STRICTLY AFTER the deadline is NOT allowed to flip a would-be-timeout into a success — it stays pending and is swept to `timed out (still starting)`. A pass observed at or before the deadline is terminal and kept; the fail-fast rules (1–4) are NOT gated (a genuine crash/restart at the deadline keeps its true verdict). Any service still pending once `elapsed >= Timeout` is swept to `timed out (still starting)`. The seven `WaitVerdict` strings (`VerdictHealthy`/`VerdictRunningNoHC`/`VerdictUnhealthy`/`VerdictExited`/`VerdictExitedNeverStart`/`VerdictRestarting`/`VerdictTimedOut`, plus `VerdictPending` = zero value) are load-bearing — both the CLI verdict table and the TUI progress screen render them literally; `WaitVerdict.OK()` (healthy or running-no-HC) defines a passing outcome. **Driver 1 (CLI)**: `WaitHealthy(ctx, c Composer, services, opts)` resolves an empty target set via `ListServices()` (the pipeline's "empty means all" convention), fires the first poll immediately then every `opts.Poll` — **capped at `min(Poll, Timeout-elapsed)`** so a poll lands at ~the deadline rather than up to a full `Poll` past it (the reducer's firm-boundary fix depends on the deadline poll landing at ~`Timeout`, not late) — feeds `ContainerStatus()` snapshots to `EvaluateWait`, and returns `(WaitReport, error)`. **The wait-scoped context is created FIRST — before ANY blocking call — and covers BOTH the empty-target-set `ListServices()` resolution AND the polls** (`context.WithDeadline(ctx, start+Timeout)`, a CHILD of the parent ctx), so a HUNG `ListServices` OR `ContainerStatus` (stuck daemon / dead SSH hop) is interrupted AT the deadline rather than blocking past `--wait-timeout`; the error-retry sleep is capped to the remaining budget the same way. **No status/list call in the wait phase can outlive `--wait-timeout`** — this is the invariant (regression pins: `TestWaitHealthy_HungPollInterruptedAtDeadline`, `TestWaitHealthy_HungListServicesInterruptedAtDeadline`). A `ListServices` resolution cut off by the deadline (derived-ctx `DeadlineExceeded`, parent NOT cancelled) returns a `resolve services: wait timeout … exceeded` operational error → exit 2; a parent-cancel during resolution returns `ctx.Err()` raw → exit 1 (classified by checking `ctx.Err()` first, then `waitCtx.Err()`, exactly as the poll loop does). In the poll loop a pure deadline expiry (derived-ctx `DeadlineExceeded`, parent NOT cancelled) sweeps still-pending verdicts to `timed out` via `reportTimedOut` (NOT a nil-status `EvaluateWait`, which would misread a running service as exited) and returns `(report, nil)` → the CLI wraps it → exit 2; a genuine PARENT cancellation (user Ctrl-C) returns `ctx.Err()` raw → exit 1 — the two are distinguished by an `ctx.Err()` check after the `select` (the `waitForHealth` `errors.Is(err, context.Canceled)` guard depends on this). The error is reserved for OPERATIONAL failures only (parent-ctx cancellation → partial report + `ctx.Err()`; `pollErrorThreshold`=3 consecutive `ContainerStatus` errors WHILE INSIDE the deadline → partial report + wrapped error; a non-deadline `ListServices` failure) — a completed wait with a failing verdict OR a pure deadline expiry returns `(report, nil)` with `report.OK==false`. A single transient poll error is skipped, state carried forward. **Driver 2 (TUI)**: `internal/tui/app.go` drives the same reducer from a `waitTickMsg` loop (the `refreshTickMsg` idiom), so the rules can never diverge between surfaces. Each TUI poll (`pollWaitStatus`) is likewise bounded — `context.WithDeadline(m.ctx, m.waitDeadline)`, the same wall clock the countdown uses — so a HUNG `ContainerStatus` still returns a `waitStatusMsg` (with a deadline error) instead of never delivering; without the bound the reducer's timeout sweep would never run and the progress screen would wait indefinitely (regression pin: `TestPollWaitStatus_BoundedByDeadline`). `WaitOptions{Timeout,Grace,Poll}` normalize non-positive fields to `DefaultWaitTimeout`=2m / `DefaultWaitGrace`=10s / `DefaultWaitPoll`=2s; only `--wait-timeout` is user-exposed (Grace/Poll are internal constants in v1). **Widening note: no `Composer` change** — the wait engine consumes the existing `ContainerStatus()`/`ListServices()` primitives, so the 4 mock sets are untouched.

## `WaitError` exit-2 contract

`cmd.WaitError{Report runner.WaitReport, Err error}` (exported, in `cmd/deploy.go`) signals that a post-operation `--wait` gate failed. `waitForHealth` wraps a non-OK OR errored report in it; `main.go` maps it via `errors.As(err, &waitErr)` → `os.Exit(2)`, letting CI distinguish "deployed but unhealthy" (2) from "pipeline step failed" (1). `Unwrap()` exposes the operational cause (ctx cancel / poll failures / resolution). `Error()` lists the failing services (or the wrapped cause). A **deploy** wait failure also prints the hint `run 'cdeploy rollback' to restore the previous images` (restart/rollback have no earlier snapshot to fall back to). `--wait`+`--wait-timeout` register on deploy, restart, and rollback via `addWaitFlags(cmd)`; `stop` never gets them, and `runOperationWithPrep` guards `op != runner.StopOnly` defensively so a leaked global can't make a stop wait. `formatWaitReport(report)` is a pure verdict-table renderer (sorted, aligned, colored via the shared styles) — golden-testable.

## Deploy snapshots & the state file

every `Deploy` records the image digest each *running container* actually uses, to a per-project state file **on the docker host**, BEFORE the pipeline stops anything, so `cdeploy rollback` can restore them. Schema and pure helpers live in `internal/compose/snapshot.go`; the capture + state-IO methods hang off `Compose`/`RemoteCompose`. **Ownership rules**: (1) **Deploy-only** — never Restart (a restart after a bad deploy must not overwrite the good snapshot) and never Rollback (rollback is idempotent — running it twice lands on the same state). (2) **Captured pre-Stop**, from the digest the running container is actually using — container ID → `docker inspect --format '{{.Image}}'` (batched) → `docker image inspect` → `RepoDigests` filtered against the compose-config image ref via `parseLocalDigest` — NOT the local tag's current digest (a pulled-but-not-deployed newer image must not poison the snapshot). (3) **Merge-not-replace** (`mergeSnapshot`, fresh entries win, older entries and their per-service `recorded_at` survive) so a partial `deploy web` never destroys the rest of the project's safety net. (4) State lives at `~/.cdeploy/state/<sha256(projectDir + "\x00" + projectName)[:12]>.json` on the host — local file for local, over SSH for remote — so a CI deploy and a laptop rollback share one authoritative history. The key hashes a NORMALIZED project dir (`localProjectDir` = `filepath.Abs`+`Clean`; `remoteProjectDir` = `path.Clean`), so `-C ./app` and its absolute spelling collapse to one key. **The PROJECT NAME is in the key, and the directory alone is not enough.** `docker compose -p blue` and `-p green` in `/srv/app` are two projects with two container sets, and `mergeSnapshot` merges by SERVICE name: on the directory alone, deploying green overwrote blue's `web` entry, and a later `R` (or `cdeploy rollback`) on blue passed every refusal check — blue DOES have a `web` entry and `web` IS live in blue — and pinned `image: <green's repo>@<green's digest>` with `pull_policy: never`. A wrong-image deployment with no warning (`TestSnapshotKeyNamedProjectsInOneDirStayDistinct`, `TestRemoteStatePath_NamedProjectsInOneDirStayDistinct`). NUL separates the halves because no filesystem path and no docker project name can contain it. **An EMPTY name keeps the historical DIR-ONLY hash, byte for byte** — every state file on every host was written under it, and a composer built from a bare directory (the local fast track, every CLI verb without `--project-name`) still addresses whatever project that directory resolves to (`TestSnapshotKeyEmptyNameIsTheLegacyDirOnlyHash`). **A NAMED project READS the dir-only file as a fallback** when its own file does not exist yet, in one SSH round trip on the remote side (`elif [ -f ]`), so the upgrade orphans nothing (`TestReadSnapshotFallsBackToTheLegacyDirOnlyFile`, `TestRemoteReadSnapshot_FallsBackToLegacyPathInOneRoundTrip`). **The fallback is a READ only.** `Snapshot.ProjectName` records the owner, `checkSnapshotProject` refuses a file that names a DIFFERENT project (`TestReadSnapshotRefusesAForeignProjectName`), and `WriteSnapshot` merges against `readPrimarySnapshot()` — the project's OWN file, no fallback — because the dir-only file belongs to whatever project the DIRECTORY resolves to and persisting its entries into a named project's history is the same wrong-image rollback in slow motion (`TestWriteSnapshotDoesNotMergeTheLegacyFile`, `TestRemoteWriteSnapshot_MergeReadHasNoFallback`). (5) **Warn-and-proceed**: a not-running service, a locally-built image with no registry digest, a capture error, and a write failure are ALL surfaced as warnings and never block the deploy (`cmd/deploy.go:recordSnapshot`, gated on `op == runner.Deploy` and a `snapshotter` type-assert). Schema is version 1; `parseSnapshot` returns the typed `errSnapshotSchema` for any other version so an older binary refuses rather than misreads. `SnapshotServices` returns `SnapshotResult{Snapshot, Warnings}`; `ReadSnapshot` returns `(nil, nil)` for a missing file (normal first deploy, distinguishable from a parse/schema error); `WriteSnapshot` ties read+merge+atomic-write (temp+rename, `config.Save` pattern). **Overwrite protection** (`existingForMerge`): only a MISSING file or a malformed-JSON file (`errSnapshotCorrupt`, wrapped by `parseSnapshot`) is treated as "no existing" and safely overwritten; a future-schema file (`errSnapshotSchema`) or a transient read/SSH failure ABORTS the write instead of clobbering it — otherwise an older binary would silently downgrade a newer-schema file, and one flaky read would wipe the merge history of every service not in the current deploy. The abort surfaces as a `WriteSnapshot` error, which the best-effort `recordSnapshot`/`recordDeploySnapshot` callers warn about and proceed past. **Concurrent-deploy locking**: the local `WriteSnapshot` wraps its read-modify-rename in an advisory `syscall.Flock` on a sidecar `<state>.lock` (`lockStateFile`, unix-only per the SSH/ControlMaster design; separate `os.OpenFile`s give independent open-file-descriptions so it contends even between goroutines of one process), so two concurrent local deploys of the same project can't both read the old file and clobber each other's merged entry. Best-effort: a lock failure proceeds unlocked (the prior single-deploy behavior). The REMOTE `WriteSnapshot` is deliberately NOT locked — a cross-SSH distributed lock is out of v1 scope (the read `cat` and the write are two SSH round-trips with a host-local merge between them), so concurrent same-project deploys to the same remote host from different machines can race; this is a documented v1 caveat (README) rather than a bug.

## Rollback pipeline & `PrepareRollback` prep

`cmd/rollback.go` (`newRollbackCmd`) reuses `runOperationWithPrep` with an op-specific pre-run hook (`rollbackPrep`) rather than forking `runOperation`. The hook: `ReadSnapshot` → `resolveRollbackTargets` refusal rules (nil snap = no state file; `-a` with an empty snapshot; a named service absent from the snapshot — the error names exactly which) → `filterLiveTargets` intersects the resolved targets with the CURRENT compose services (`c.ListServices()` = `config --services`) so rollback pins images only against the *current* compose file: a snapshot entry for a since-removed service is warned-and-skipped under `-a`, or a hard error naming it when explicitly named (a `ListServices` failure aborts prep — fail closed; an all-stale `-a` set errors "no snapshot services remain") — this prevents the generated override from resurrecting a removed service as a minimal image-only service → print the plan lines (`web  nginx@sha256:ab12… (recorded 2026-07-28 14:03)`) → `PrepareRollback`, whose returned cleanup `runOperationWithPrep` defers (function-scoped, so it runs after the wait phase but BEFORE the remote SSH teardown in LIFO order — a remote `rm -f` of the override still rides the live ControlMaster socket). `PrepareRollback(ctx, entries, services, w)` (on both composers): discovers the main compose file (fails fast if none), writes an advisory `already at snapshot` line for services whose running container already matches the snapshot digest (best-effort, proceeds — a recreate is still meaningful), ensures each target digest's blob is present locally (`docker image inspect <repo>@<digest>` presence check, else `docker pull <repo>@<digest>` streamed to `w` for live progress via the new `runDockerCmdStream`/`runRemoteDockerCmdStream` primitives — the existing `runDockerCmd` runners CAPTURE, these STREAM), then generates a minimal override YAML (`buildOverrideYAML`, `image: <repo>@<digest>` **plus `pull_policy: never`** per service, services emitted in SORTED order — never marshal a map) and sets `ExtraComposeFiles = [main, override]` (main FIRST — see the contract below). The `pull_policy: never` line is load-bearing for offline rollback (AC4): the rollback pipeline has NO Pull step, but its Create step is the shared `docker compose up --no-start`, whose pull is policy-driven — a MAIN-compose `pull_policy: always` would otherwise force a registry pull at Create and FAIL during a registry outage (the classic rollback trigger). As the SECOND `-f` file, the override's `never` wins the compose merge, so Create never pulls; safe because the presence-check/pull above already guarantees the pinned digest blob is on the host at Create time. A pull that fails (blob pruned AND registry down) aborts BEFORE any override file is written or `ExtraComposeFiles` is touched, so a failed prep never leaves the pipeline half-configured. Cleanup removes the temp override and resets `ExtraComposeFiles = nil`. Local delivery writes the override to `os.TempDir()` via `os.CreateTemp` (unique per process — no collision risk); remote pipes it over the ControlMaster socket to `/tmp/cdeploy-rollback-<pid>-<rand>.yml` via `writeRemoteFile` (`mkdir -p && cat > tmp && mv`) and cleans it up with `rm -f` over SSH. The remote path's random hex suffix (`remoteRollbackOverridePath`, `crypto/rand`) is generated ONCE per `PrepareRollback` and reused for both the write and the cleanup `rm -f`; it makes the path unique across CLIENTS (the local PID alone collides when two machines roll back the same project on the same docker host — one would overwrite the other's override, or a cleanup `rm -f` would delete a file the other's pipeline/wait still references in `ExtraComposeFiles`). `rollbackImageRef(entry)` (`stripTag(image)+"@"+digest`, exported as `compose.StripTag` and reused by `cmd/rollback.go`'s plan line so the advertised repo can't diverge from the pinned one) is the single source of truth for the presence check, the pull, and the override, so all three agree on the exact ref. `rollbackPrep` also returns the resolved (snapshot ∩ live-compose) service set, which `runOperationWithPrep` threads into BOTH the pipeline (`runner.Run`) AND the wait phase — for `-a` this is the intersected snapshot services, NOT the raw nil `containers` arg. Threading it into the pipeline is load-bearing: with nil, `runner.Run` would Stop/Remove/Create/Start EVERY compose service — including ones absent from the override — recreating them with their current UNPINNED image; and `WaitHealthy` would resolve every compose service via `ListServices()`, dragging build-only / run-to-completion services that were never rolled back into the `--wait` health gate. deploy/restart/stop pass a nil prep and keep operating on `containers` unchanged.

## `ExtraComposeFiles` contract

`ExtraComposeFiles []string` on both `Compose` and `RemoteCompose`. When non-nil, `command()`/`remoteCommand()` splice `-f <f0> -f <f1> …` immediately after `docker compose` / `docker-compose` (both plugin and standalone argv shapes), before the subcommand, shell-escaped on remote. `-f` disables compose's file auto-discovery, so the project's own files MUST come first, in load order, with the override LAST (`[...projectFiles, override]`). **Rollback stacks the WHOLE reported file set, not one discovered file**: `PrepareRollback` seeds from `ComposeFiles` (docker's `config_files` list, carried on `compose.Project.ConfigFiles`) and only falls back to `findComposeFile`/`findRemoteComposeFile` when the composer has none, because recreating a multi-file project from its first file alone drops the rest of its definition (`TestPrepareRollback_StacksTheWholeReportedFileSet`). **`ExtraComposeFiles` and `ComposeFiles` are not the same field and `composeFileList()` is the one arbiter**: `ExtraComposeFiles` wins when set, since it is the override stack that already contains the project's files. The local `PrepareRollback` absolutizes every file it stores (`filepath.Abs`), because `command()` sets `cmd.Dir = ProjectDir` and docker resolves `-f` relative to that cwd — a relative `-C ./app` would otherwise re-prefix `-f app/compose.yml` into `./app/app/compose.yml` and fail (the remote path uses a bare name + `cd`, so only the local side needs this). **Regression-pinned nil default**: a nil field produces byte-identical argv to the pre-feature behavior — `TestCommand_NilExtraComposeFiles_ByteIdentical` / `TestRemoteCommand_NilExtraComposeFiles_ByteIdentical` guard this; `cmd.Dir`/project-dir handling is unchanged so project-name derivation stays stable. Only rollback prep sets `ExtraComposeFiles`; a composer built from a discovered project instead carries `ComposeFiles`, which is nil for the local fast track and every CLI verb.

## TUI wait phase & `R` rollback (sessions + cleanup)

no new screens. The **progress screen** gains a `waiting` sub-state: when a Deploy/Restart/Rollback pipeline closes its events channel, it enters `waiting`, seeds `waitState = NewWaitState(targets)`, sets `waitDeadline`, and starts a singleton `waitTickMsg{session}` loop (one `ContainerStatus` tea.Cmd per tick → `EvaluateWait` → re-render → reschedule) gated on `m.screen == screenProgress && m.waiting && msg.session == m.waitSession`; StopOnly never waits. Each poll is deadline-bounded (`context.WithDeadline(m.ctx, m.waitDeadline)`) so a hung `ContainerStatus` returns a deadline error rather than stalling the loop; the `waitStatusMsg` error path then sweeps pending→timed-out once `elapsed >= Timeout` (`sweepWaitTimeout`), guaranteeing the wait resolves even if Docker/SSH never recovers. It renders a live per-service verdict line (reusing the `♥/●/✗/~` icons + `waitVerdictStyle`) with a countdown; footer shows `enter q esc skip` (and `enter skip wait • q esc stop` mid-sequence). `esc` while waiting calls `clearWaitState()` (bumps `waitSession` to invalidate in-flight ticks/polls, clears wait fields) and leaves the op "done" — and mid-sequence it STOPS the sequence instead, with `enter` carrying the release; see the per-batch section below. `clearWaitState` deliberately does NOT clear `opContainers`: that is the batch's resolved target set, which the grouped progress title reads, and clearing it re-titled an esc-skipped named-service operation "all services". `clearBatchSequence` owns it, at the progress departure. A resolved wait KEEPS `waitState` so the final verdicts stay visible; a failed **deploy** wait shows the hint `press R on the services screen to roll back`. The **`R` key** on the services screen type-asserts `m.composer.(RollbackPreparer)` (no-op if unsupported, like the `c`/`x` guards), guards empty list / empty selection (warn), then **captures the selected target set into `rollbackTargets`** at press time and bumps `rollbackFetchSession` and fires an async fetch that reads the snapshot AND the CURRENT compose service set in one goroutine. The capture is load-bearing (C11 fix): the fetch is async, so the live multi-select can change or CLEAR before `rollbackSnapshotMsg` lands; the captured `rollbackTargets` — NEVER the live `selectedContainers()` — drives the snapshot-presence + live-compose validation, the confirm prompt (`rollbackAgeSuffix`), `PrepareRollback`, and the pipeline target (`opContainers`), so a since-cleared selection can never become an unintended all-service rollback (empty `containers` == all services throughout the runner/composer). A somehow-empty captured set when the msg lands REFUSES (warns `warnNoSelection`) rather than falling through. `rollbackFetchSession` protects the captured set from a stale fetch; a fresh `R` press re-captures (`ReadSnapshot` + `ListServices`, `rollbackSnapshotMsg{snap, live, session}`, gated on screen + session; a `ListServices` failure fails closed via the shared `err`). The handler refuses with an inline warning (mirroring the CLI `filterLiveTargets`) when a selected service is absent from the snapshot OR has since been removed from the live compose file (`msg.live`) — a stale target must NOT resurrect a removed service as a minimal image-only override; an absent snapshot warns inline; a present-and-still-live snapshot enters the existing `confirming` flow with `pendingOp = runner.Rollback` (the confirm prompt shows the snapshot age via `rollbackAgeSuffix`). On confirm, prep runs inside the op tea.Cmd before `runner.Run` (prep failure → op failed); the cleanup is stored as `m.rollbackCleanup` and invoked (via `runRollbackCleanup`, which nils the field so it can't double-fire) when **LEAVING** `screenProgress` — NEVER goroutine-deferred, because `runner.Run`'s `defer close(events)` triggers the wait-tick loop whose `ContainerStatus` reads `ExtraComposeFiles` concurrently with a reset (`go test -race` would flag a goroutine-deferred cleanup). A **hard quit** during a rollback wait also runs `runRollbackCleanup` on the main goroutine so the override temp file isn't leaked (esp. the remote `/tmp` file, which has no reaper): local ctrl+c via `tryQuit()` before `tea.Quit`, remote ctrl+c via the `quitting` confirm's `y` branch (while the ControlMaster socket is still live — `Run`'s `disconnectFunc` only closes it after the tea loop exits). **New sessions**: `waitSession` (gates `waitTickMsg`) and `rollbackFetchSession` (gates `rollbackSnapshotMsg`); both are bumped at the same context-change sites as the other counters and cleared, along with `waiting`/`waitState`/`waitDeadline`/`rollbackSnapshot`/`rollbackTargets`/`rollbackCleanup`, at the documented departure sites (esc back-nav chain, `entryLocal`, `connectResultMsg` error path). `rollbackTargets` is cleared together with `rollbackSnapshot` at every one of those sites. The post-op update-cache invalidation on esc-from-progress now includes `runner.Rollback` alongside Deploy/Restart. `Snapshotter` (SnapshotServices + WriteSnapshot) and `RollbackPreparer` (ReadSnapshot + PrepareRollback) are optional interfaces defined in `tui` and type-asserted on the concrete composer, mirroring `ConfigProvider`/`ExecProvider` and the cmd package's `snapshotter`/`rollbackPreparer` seams; the TUI runs the deploy snapshot FIRST inside the Deploy op goroutine (warn-and-proceed).

## TUI wait phase — the gate is PER BATCH

a grouped operation runs one pipeline per project, in screen order, and **every batch runs its OWN `--wait` gate against its OWN composer** — which is what makes a two-project deploy stop at the project that came up broken instead of dragging the next one down with it. The row model, the partitioning and the sequencing live in `docs/architecture/tui-multi-project.md`; this section carries only what the gate owes.

**`pipelineDoneMsg` OPENS the gate; `batchDoneMsg` — not `pipelineDoneMsg` — RELEASES the next batch.** That split is the whole point of the second message: a batch's pipeline closing its channel no longer means the batch is over. Both messages carry `batchIdx` + `batchSession` captured at DISPATCH, and both handlers apply THREE gates — screen, session, index. The `batchDoneMsg` handler cancels the finished batch's context before the next batch takes over `m.cancel` (which `esc` reads), then calls `clearWaitState()` — **which also nils `opContainers`, so its order against `startBatch` re-setting it is load-bearing** — then advances `batchIdx` and starts the next batch. The test harness follows the split: `drainBatch` is now `resolveWaitPhase(drainPipeline(m), true)`, so every sequence test drives the gate as well as the pipeline, and a test that drives the gate by hand (an `esc` skip, an unhealthy verdict) starts from `drainPipeline` instead.

**A whole-project batch resolves its own target names.** The reducer seeds from the batch's service slice in BARE form (qualified `project/service` keys never reach it). An EMPTY slice is the runner's "all services", which the reducer cannot evaluate, so it is resolved per mode: drilled mode falls back to `m.services`, **grouped mode must NOT** — `m.services` is host-wide there, so seeding one project's composer with another project's services is a guaranteed timeout. Grouped mode asks the batch's composer through `ListServices` instead. **`waitTargetsMsg` is a SECOND message, not a widened `waitStatusMsg`**, because the reducer needs the names seeded BEFORE the first poll is evaluated; `m.waitState` stays empty (the header renders with no rows) for the one frame in between. **An unresolvable target set SKIPS the gate rather than failing it**: a `ListServices` error names no health verdict, so it is not a health failure — the gate closes and the sequence continues. In the TUI the wait is advisory for the same reason `esc` can skip it by hand.

**Each batch binds its own composer, and takes its own Deploy snapshot.** `startBatch` calls `bindProjComposer(b.proj)` for every op except `Rollback` — `R` bound it at press time (the snapshot fetch already needed one) and the prep validated the captured targets against it, so rebinding from the batch's project would swap it under a capture the selection has since drifted from. The snapshot is likewise per batch, taken inside the batch goroutine before `runner.Run` touches anything (pre-Stop ordering, best effort, `Snapshotter` type-asserted), so a two-project deploy records two state files — one per project key, exactly as two separate `cdeploy deploy` runs would.

**What a failing gate means depends on whether a batch is still to come.** `waitPhaseResolved()` decides: a passing gate releases the next batch; a failing one stops the sequence exactly as a failed pipeline step does (`m.failed` + `markBatchesSkipped(batchIdx+1)`), so the batches behind it read `(skipped)` rather than sitting at `○`; and **the LAST batch takes NEITHER branch** — today's single-project screen renders a failed wait as red verdicts plus the rollback hint over a `done` operation, not as a failed op, and that is preserved. `batchFinished()` is the shared release path for every no-gate case: `StopOnly`, an unresolvable target set, and the `esc` skip.

**`esc` on a MID-SEQUENCE gate STOPS the sequence; `enter` RELEASES the next batch.** The gate is where a multi-project deploy spends most of its wall clock (one `DefaultWaitTimeout` per batch), so it is where a user who wants to abort is sitting — and `esc` is the abort key everywhere else on the screen. Releasing the next batch from it meant the universal abort key launched a whole project's stop → rm → pull → create → start, under a footer and a `?` table that called it "skip health wait". So `esc` there spells the stop the same way a FAILING gate does (`m.failed`, `markBatchesSkipped(batchIdx+1)`, `batchSession++` to discard a `batchDoneMsg` already in flight) and `enter` carries the release. On the LAST batch there is nothing to release and both keys are the plain skip, which is what the single-row WAIT table says. A skip must not strand the sequence with no terminal state and no way out. `esc` on a RUNNING pipeline cancels the batch context, bumps `batchSession` (the cancelled batch is still going to close its channel, so its `pipelineDoneMsg` is already on the way), marks the rest skipped, and sets `m.failed` — the terminal state is what keeps the progress screen escapable rather than leaving a cancelled sequence with `done` and `failed` both false. `runRollbackCleanup` and the departure cleanup (`clearWaitState`, `waiting`, `waitDeadline`, `clearBatchSequence`) run when LEAVING `screenProgress`, on the main goroutine — never goroutine-deferred, per the rollback cleanup timing rule above.

**`R` covers ONE project.** A rollback restores one project's recorded digests from that project's own snapshot file, so in grouped mode `R` partitions the selection first and refuses a capture that spans projects outright — `warnRollbackCrossProject` ("Rollback covers one project at a time"), raised BEFORE any composer is bound, since there is no single project to bind. `d`/`r`/`s` may span projects; `R` may not. The batch's project is captured into `rollbackProj` at `R`-press time and the confirming `enter` builds the batch from it rather than from `m.currentProject()`, which is empty in grouped mode. All THREE probe failures after the bind — not a `RollbackPreparer`, an empty service list, an empty selection — call `unbindGroupedComposer()` before returning, or grouped mode keeps serving that project's composer to the next row's action key. **`rollbackPreppedMsg` carries `batchIdx` and `session`, captured in `startBatch` at DISPATCH time** — the same identity `stepEventMsg` and `pipelineDoneMsg` carry, captured the same way `waitForEvent` captures them. The screen alone is NOT identity: a prep the user cancelled with `esc` keeps running until `PrepareRollback` notices the cancelled context, and by then the user can be on `screenProgress` again with a different operation — ungated, its `err` marked THAT operation failed, its success overwrote the cleanup the new one owns, and the `waitForEvent` it starts put a SECOND consumer on the live event channel, two readers splitting one pipeline's events, losing steps and hanging the sequence. **Every stale branch still invokes `msg.cleanup`**, or the override file and `ExtraComposeFiles` leak (`TestRollbackPreppedMsg_CarriesBatchIdentity`, `TestPrepareRollbackCmd_StampsCurrentBatchIdentity`).
