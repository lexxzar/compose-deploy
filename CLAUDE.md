# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Test Commands

```bash
go build -o cdeploy .          # Build binary
go test ./...                   # Run all tests
go test ./internal/runner/ -v   # Run tests for a single package
go test ./... -count=1          # Run all tests uncached
go mod tidy                     # After adding/removing imports
```

The root command launches a Bubble Tea TUI requiring a TTY, so `cmd/root_test.go` tests flag registration and subcommand structure rather than executing the root command directly.

## Architecture

cdeploy is a dual-mode tool: interactive TUI (no args) or non-interactive CLI (`deploy`/`restart`/`stop`/`list`/`logs`/`exec` subcommands). Both modes share the same core through a three-layer architecture:

```
cmd/ (Cobra)  →  runner (pipeline orchestrator)  →  compose (docker CLI wrapper)
tui/ (Bubble Tea) ↗
```

Seven subsystems carry their full rationale, failure modes and test pins in `docs/architecture/`; the paragraphs below carry the rules only. **Read the matching file before you change one of them** — each rule there exists because it was violated once.

- `docs/architecture/tui-help-overlay.md` — the `?` overlay, the container footer, the `q` back key
- `docs/architecture/tui-logs-and-search.md` — container search, log streaming, formatting, filter and search
- `docs/architecture/tui-inspect-screen.md` — the `i` inspect screen and `internal/compose/inspect.go`
- `docs/architecture/wait-snapshots-rollback.md` — the `--wait` gate, deploy snapshots, the rollback pipeline
- `docs/architecture/update-detection.md` — the `⇧` glyph, digest comparison, failure cascades, the TUI cache
- `docs/architecture/unmanaged-containers.md` — `HostContainers`, the `(unmanaged)` group, the read-only UI contract
- `docs/architecture/tui-multi-project.md` — the grouped host view, `svcKey`, batch sequencing, grouped updates

**Key abstraction**: `runner.Composer` interface (defined in `internal/runner/runner.go`, implemented by `internal/compose/compose.go` for local, `internal/compose/remote.go` for SSH, and `internal/compose/hostcontainers.go` for the read-only unmanaged-container view). This is the seam between the orchestrator and Docker — the runner is testable with mock implementations. Methods: `Stop`, `Remove`, `Pull`, `Create`, `Start`, `ListServices`, `ContainerStatus`, `ContainerStats`, `CheckUpdates`, `Logs`. When widening this interface, every mock implementation must add a matching no-op — there are mocks in `internal/runner/`, `internal/tui/app_test.go` (`mockComposer`), `cmd/deploy_test.go` (`opMockComposer`), and `cmd/list_test.go` (`mockComposer`, `mockComposerStatusErr`); a fast `grep -rn "func.*Composer.*ListServices" ./...` enumerates them.

**Event system**: `runner.Run()` sends `StepEvent` structs through a channel. The CLI consumer (`cmd/deploy.go:runOperation`) prints colored status lines. The TUI consumer (`internal/tui/app.go`) drives a Bubble Tea model through `tea.Cmd` that reads from the channel.

**TUI state machine**: Eight screens: `screenSelectServer` → `screenSelectContainers` → `screenProgress` (for operations), `screenLogs` (for log viewing), `screenConfig` (for config viewing/editing), or `screenInspect` (for the read-only container inspect view), plus `screenSettingsList`/`screenSettingsForm`. **There is NO project-select screen** — the container screen's GROUPED mode replaced it (`m.grouped`; every compose project on the host is a foldable group plus the synthetic `(unmanaged)` one), and picking a project is a drill-in state change on the same screen rather than a screen transition — see the six `Multi-project host view — …` paragraphs below. The server screen is shown whenever servers are configured in `~/.cdeploy/servers.yml`; selecting "Local" fast-tracks to the DRILLED single-project container screen if a local compose file exists, and lands on the grouped host view otherwise. The model is a flat struct with a `screen` field determining which view/update logic runs. Operations are triggered via action keys on the container screen (`r` restart, `d` deploy, `s` stop) which enter a confirmation sub-state (`confirming` bool + `pendingOp`) before proceeding. The `x` key execs into a running container interactively (enters confirmation with `pendingExec = true`, then shells out via `tea.ExecProcess`; shows warning if container is not running). The `l` key opens the log viewer for the cursor service without confirmation (read-only operation). The `c` key opens the config screen without confirmation (read-only by default). The `i` key opens the inspect screen for the cursor service, also without confirmation, and is the one container action key that is NOT gated on `m.readOnly()` — see the "Inspect screen" paragraph below. Back-navigation (`esc`, also aliased to `q` on nested screens — see "Exit confirmation for remote connections" below) resets downstream state; during confirmation, `esc` cancels without navigating back. The grouped host view is skipped entirely when the current directory contains a compose file and no servers are configured (backward compatible). `Compose.ListProjects()` discovers projects via `docker compose ls -a --format json`; both `ProjectLoader` literals in `cmd/root.go` are plain `ListProjects` and append NOTHING — that loader feeds `loadGroups()` and supplies the grouped screen's row ORDER, while the synthetic `(unmanaged)` group comes from `buildSvcGroups`'s leftover path off the host-wide `docker ps` the same refresh already made; see the three `Unmanaged containers — …` paragraphs below.

**Exit confirmation for remote connections**: `ctrl+c` is the hard-exit shortcut from any screen. When a remote SSH connection is active (`disconnectFunc != nil`), pressing `ctrl+c` shows a confirmation prompt instead of quitting immediately. The `quitting bool` field on Model gates a global intercept at the top of `handleKey()`: `y` quits, `n`/`esc` cancels, all other keys are swallowed. `View()` checks `quitting` first and renders a standalone confirmation screen via `viewQuitConfirm()` (`"Disconnect from {serverName}? (y/n)"`). The `tryQuit()` helper replaces direct `return m, tea.Quit` calls on all screens except `screenSelectServer` (which always quits immediately since no remote connection exists there). `quitting` is reset to `false` in `esc` back-navigation handlers that clear `disconnectFunc` and in the `entryLocal` handler. Local sessions (`disconnectFunc == nil`) bypass the prompt entirely — `tryQuit()` returns `tea.Quit` directly.

**`?` key-reference overlay**: `?` opens a full-screen key list for the current screen. It is a flag (`helpOpen bool` on Model), **never a screen constant** (back-navigation, `clearSearch()`, the session counters). `View()` checks it right after `quitting`, returning `viewHelp()`. `helpGroupsFor(s, hc helpContext)` (`internal/tui/help.go`) covers all 8 screens; the context bits travel in a NAMED `helpContext{canGoBack, readOnly, grouped, phase}`, never adjacent same-typed parameters. **Group ORDER is load-bearing**: `splitHelpGroups` cuts sequentially, so LEAVE must stay 4th of 6 on `screenSelectContainers` and 3rd of 4 in `readOnlyContainerGroups` and on `screenLogs` — do not reorder for readability. LEAVE is conditional (`leaveGroup(canGoBack)` renders `q quit` instead of `q esc → back`; `esc` stays BOUND on a standalone screen but is not a way out, so the group must not name it), and `Model.canGoBack()` is the single predicate behind BOTH it and the footer's `back` label. `screenProgress` is conditional on a THREE-state phase, since `esc` changes meaning per phase (running: `esc` CANCELS the op — and marks it `failed`, so the screen is always escapable — while `q`/`ctrl+c` no-op; waiting: `q`/`esc` skip the health wait and `ctrl+c` quits, because a mid-sequence gate opens with `done` and `failed` BOTH false and the two guards read `m.waiting` as terminal-enough; finished: they go back), so `Model.progressPhase()` MUST resolve in the SAME order as `viewProgress()`'s footer switch (`waiting` FIRST — **not** "because it implies `done`", which stopped being true when the per-batch gate landed: a gate can be open with `done` set (the last batch), with `failed` set, or with neither (a mid-sequence batch), and only the waiting-first order names `esc` correctly in all three); never one static table. `helpGroup.actions bool` marks groups whose keys are advertised nowhere else; `singleColumnOrder()` emits them first in the single-column fallback, FIND stays split out of MOVE so `/` and `n N` keep that flag, and a new action row moves every truncation threshold. `layoutHelpColumns`/`budgetHelpRows` clamp row width and count (`m.height` minus chrome, floor 1). **`viewHelp()` must NOT end its string in a newline, and the height tests must NOT trim one**: bubbletea keeps the LAST `m.height` of the `\n`-split `View()`, so one costs the title (`viewSelectContainers()`/`viewLogs()` too). **Intercept order in `handleKey()` is load-bearing**: (1) the `quitting` intercept, (2) the `helpOpen` swallow, (3) the `?` open, (4) the `q`→`esc` rewrite — the swallow MUST precede the open. Close keys are `?`, `esc`, `q`; every other key is swallowed. **`ctrl+c` clears `helpOpen` and FALLS THROUGH** instead of returning, so each screen's own `ctrl+c` semantics apply unchanged — including the mid-progress no-op. The open block is gated on `!m.typingInInput() && !m.confirmPromptArmed()`; **`confirmPromptArmed()` is screen-SCOPED** (`screenSelectContainers` → `m.confirming`, `screenSettingsList` → `m.settingsDelete`, else false) and a flat `!m.confirming` is WRONG — `enterProgress()` never clears `confirming`. `connectResultMsg` clears `m.helpOpen` on BOTH branches and `rollbackSnapshotMsg` clears it beside its `m.confirming = true`: **any future handler that arms a confirmation must do the same**. `typingInInput()` (`m.searching`; `m.logFiltering || m.logSearching`; `m.settingsField < 4` — that form, not `!= 4`) gates BOTH the `?` open and the `q` rewrite, so **a new screen that opens a text input needs one case there and nothing else**. Extend the key set in `TestHelpGroups_NamesEveryBoundKey` (and its read-only twin) whenever you bind a key — it fails BOTH directions — and move `TestAllScreens_Complete`'s bound to `int(<new last screen>) + 1` per screen added, or table tests skip it. **A key bound only in a sub-state needs a description that NAMES it**: `enter  confirm the prompt`.

**Container footer and the one-line width guard**: `containerFooter()` renders it, `containerFooterLines()` counts its physical lines; `svcVisibleCount()` reserves `2 + containerFooterLines()` and `containerFooter()` **pads every state out to that same count**. Both read `containerHelpLines()`, the single home of the idle pair (`back` via `canGoBack()`, read-only AND grouped variants included — THREE pairs). **The footer must advertise only keys the current state binds**: a committed search replaces `line2` wholesale with `n/N cycle • esc clear`, which is why `back` and `? keys` must live in `line1`; a TYPING search binds only `enter`/`esc`/`ctrl+c`, so the whole footer becomes `enter jump • esc cancel`. **The line COUNT stays state-independent** — decided from the idle pair alone, BEFORE any substitution, with the shorter states padded back by a trailing `\n` (the typing footer, and the confirm prompt). The one-versus-two-line guard measures `m.width >= ansi.StringWidth(oneLine)+2`, NOT `len(oneLine)+2` — **do not reintroduce `len()`**. A substitution can be WIDER than the idle `line2`, so `containerFooter()` clamps every line with `clampToWidth` rather than widening the count. Six tokens on the drilled write path; the read-only pair carries four (`back`, `? keys`, `l logs`, `x exec`); the GROUPED pair carries six but swaps `space toggle` → `space fold/select` and `l logs` → `enter drill in`, because a group header is the row only grouped mode has. Every other container key — `a`, `/`, `n N`, `i`, `c`, `U`, `R`, `x`, and `l` in grouped mode — lives in the `?` overlay only.

**`q` as back key on nested screens**: the 4th `handleKey()` intercept rewrites `q` to `esc` on nested screens; the existing `esc` handlers do the cleanup — **do not add parallel `q` handlers**. `q` quits directly only on root screens: (1) `screenSelectServer` always; (2) `screenSelectContainers` when `!m.canGoBack() && !m.confirming` — which is the GROUPED screen with no servers and no config, or the DRILLED screen with `!m.drilledFromHost` (a standalone `cdeploy` launched in a directory holding a compose file). `drilledFromHost` is the renamed `showPicker` and carries that rule: no predicate derivable from the composer, the factory or the group list separates a drill-in from a standalone launch, so the entry sites record it. `screenProgress` while `!done && !failed` is a no-op for `q` (`ctrl+c` too) — an in-flight operation must not be cancelled. The rewrite is skipped when `m.typingInInput()` — `q` must reach an open input as a literal rune. `ctrl+c` is unchanged — `tryQuit()`, and the remote disconnect prompt. Full rationale and test pins: `docs/architecture/tui-help-overlay.md`.

**Backward-navigation state cleanup**: When navigating backward (`esc`) or handling errors (e.g. `connectResultMsg` failure), all mutable callbacks (`composerFactory`, `projectLoader`, `disconnectFunc`) must be explicitly cleared or restored to their local defaults (`localFactory`, `localComposer`, `localProjectLoader`). Bubble Tea's value-type model means stale closures silently persist across screen transitions. Every new callback field added to Model needs corresponding cleanup in: (1) `backToServerScreen()` (`esc` from the grouped host view), (2) `enterGroupedContainers()` (`esc` drill-out from the drilled screen, and every other landing site), (3) `entryLocal` handler, (4) `connectResultMsg` error path. `drillIntoGroup()` is the fifth site for anything the drilled screen owns.

**Stale async message guard**: Goroutines spawned by a screen (e.g., `readLogChunk` for `screenLogs`) may deliver messages after the user has navigated away. Message handlers for screen-specific async messages (`logChunkMsg`, `logDoneMsg`) must check `m.screen` and discard stale messages — otherwise they will read nil fields cleared by `esc` cleanup and panic. A monotonic `logsSession` counter provides additional stale-message rejection. This pattern applies to any future screen that spawns background goroutines.

**Service list scrolling**: The container select screen uses `svcOffset` to track the first visible ROW (`m.svcEntries`, so a group header consumes one exactly like a service does) when the list exceeds terminal height. `svcVisibleCount()` calculates available lines: `m.height - headerLines - footerLines` (min 1), returning `len(m.svcEntries)` when `m.height == 0` for backward compat. Line counts account for lipgloss margins: `titleStyle` has `MarginBottom(1)` (adds a space-padded line), `helpStyle` has `MarginTop(1)` (adds a space-padded line), so header=3 (or 4 with column captions) and footer=3+ (not 2). A conditional column captions row ("Created", "Uptime") is rendered above the service list when any service has non-empty `Created` or `Uptime` data; `hasStatusColumns()` checks this and `svcVisibleCount()` adds 1 to `headerLines` accordingly. The captions use `descStyle` and are left-padded to align with data columns (10 + maxName offset). `fixSvcOffset()` ensures cursor visibility after any state change that affects visible count — cursor movement, window resize, confirming/warning state change. Scroll indicators (`▲ N more` / `▼ N more`) replace existing blank-line content between breadcrumb/services and services/help, so they never change the total line count used by `svcVisibleCount()`; in grouped mode both indicators and the caption pad carry the service rows' 2-cell indent. `svcOffset` is reset to 0 alongside `svcCursor` in the DRILLED `servicesMsg` branch and at every landing/drill site — **never in the grouped `servicesMsg` branch**, which is also the 5s reload and must preserve cursor, selection, fold and search; it calls `clampSvcCursor()` + `fixSvcOffset()` instead (`fixSvcOffset` moves only the WINDOW, so a shrinking row count needs the separate clamp).

**Container search (search & jump)**: `/` is search-and-jump, **not a filter** — never narrow the rows, never touch `m.selected`; only `svcCursor` moves and matches highlight. A folded group DOES open for it: `unfoldSearchMatches(query)` runs before the indices are computed, because a folded group contributes no service ROW and a hidden row cannot be jumped to; the unfold is NOT undone when the search is cancelled. *Committed* is `searchQuery != "" && !searching`; highlighting and `n`/`N` key off `searchQuery != ""` alone. `computeMatches(m.svcEntries, query)` matches SERVICE entries only (never a group header) and returns **ascending** ENTRY indices (`nil` for an empty query) — `cycleMatch`'s wrap and off-match jumps rely on that ordering, and **every fold and every grouped reload must re-derive `searchMatches`** because the rebuild renumbers the rows those indices point at. **Ephemeral-on-departure invariant**: `m.clearSearch()` runs on **every** transition that leaves `screenSelectContainers` or reloads the rows — the 11 sites are `servicesMsg` (drilled branch), `connectResultMsg` error path, `entryLocal`, `enterProgress()`, `enterConfig()`, `enterInspect()`, `enterExec()`, `enterLogs()`, `enterGroupedContainers()` (drill-out + every landing), `drillIntoGroup()`, `backToServerScreen()`. **Two-stage `esc`**: the guard at the top of `case "esc"` clears a committed search plus `fixSvcOffset()` and stays on screen, a second `esc` back-navs, and `esc` while typing restores `svcCursor` to `searchReturn` and consumes the key. Reopening `/` over a committed search calls `clearSearch()` FIRST; `searchInput` is built by `textinput.New()` in the `/` handler — **not** in `NewModel` (`Model{}` test literals). The bar line is **always reserved** (blank when idle, blank while confirming) — `viewSelectContainers()` writes it in both the `confirming` early-return branch and the normal one, but it costs NO extra row in `svcVisibleCount()`: it merges with `helpStyle`'s MarginTop blank, so counting it separately over-reserves a row. **One-physical-line invariant**: `searchBarLine()` MUST render exactly one physical line — size the typing `textinput.Width` to the pane and clamp with `clampToWidth()` (no-op at `m.width <= 0`); style only the raw name so width math is unaffected. The `q`→`esc` rewrite is skipped while `m.searching`, via `typingInInput()`.

**Multi-project host view — grouped vs drilled, the entry model, and `svcKey`**: the container screen has TWO modes and ONE row model. GROUPED (`m.grouped`) is the host view — every compose project plus the synthetic `(unmanaged)` bucket, each a foldable group; DRILLED is the single-project screen, reached by `enter` on a group header or by the local fast track. **`m.grouped` is an explicit field, NEVER a `len(svcGroups) > 1` inference** (a host can run exactly one project; the drilled screen is always one group). `svcGroup{proj, services, folded}` is the source of truth and `svcEntry{kind, groupIdx, name}` is DERIVED by `rebuildSvcEntries` — `setSingleGroup`/`setGroups` are the only writers, `clearSvcGroups` the only wipe, and **a single group emits NO header**, which is what makes the drilled render byte-identical to pre-grouping. The header/indent predicate is `groupsHaveHeaders`/`hasGroupHeaders()` (`len(groups) > 1`), **not `m.grouped`** — one predicate feeds both the entry model and the renderer. **Folding hides ROWS, never services**: `svcRefs()` ignores fold state, so selection, counting and column widths read it rather than `svcEntries`. **Nothing may be keyed on a ROW INDEX across a rebuild** — a fold renumbers every row, which is why `m.selected` is `map[string]bool` keyed by `svcKey(proj, svc)` = `proj + "/" + svc` (`/` is safe: compose rejects it in both names). **Qualified keys live ONLY inside the tui Model** (`svcStatus`, `stats`, `selected`, the render caches); every message boundary converts — `qualifyMap(projName, src)` for a drilled bare-name payload, `flattenQualified(host)` for the grouped one — and **nothing qualified reaches `runner`/`compose`**: `selectedContainers()`, `opContainers`, `rollbackTargets` and the `NewWaitState` seed stay BARE (`TestQualifiedKeys_NeverCrossIntoRunner`). Row helpers live in `internal/tui/entries.go`, not `app.go`: `svcKeyAt` (the OWNING group decides the prefix), `cursorEntry`, `cursorService` (false on a header — every "service under the cursor" key reads it), `cursorGroup` (accepts a header; a header IS its group), `groupUnmanaged`, `selectableRefs` (`svcRefs` minus unmanaged), `clampSvcCursor` (`fixSvcOffset` moves only the WINDOW). **There is no flat `m.services` field** — `svcGroups` is the ONE representation, and its nil-versus-empty distinction carries the loading state: nil = still loading, empty non-nil = a real empty host.

**Multi-project host view — `HostGrouper`, the grouped loader, and the refresh dispatch**: `HostGrouper` is ONE method — `GroupedHost(ctx) (compose.GroupedHostSnapshot, error)`, whose snapshot carries a project → service status map, the same shape for stats, and the stats half's OWN error — declared in `tui` and type-asserted, reached through `composerFactory(compose.Project{Unmanaged: true})` — so **no existing signature changes**. **The two halves must stay in ONE call**: split across two methods each half listed the containers itself, so every 5s tick paid the same `docker ps` twice over the same SSH hop. A factory with no `HostGrouper` behind it is **not an error**: the loader's projects render with no status. The screen costs a CONSTANT number of calls regardless of project count — `docker compose ls -a` + one `hostPsArgs` `docker ps -a` (+ one `docker stats --no-stream`) — which is the whole point over an SSH hop. `GroupedHost` reads the `com.docker.compose.project=`/`.service=` label VALUES via `labelValue` (token-start match, value to the next comma — **safe for these two keys only**, both name-constrained); no-label containers form the `UnmanagedProjectName` bucket, a managed container missing the service label falls back to its container name, and replica aggregation mirrors `parseContainerStatus` exactly. **Accepted gap**: a never-created service has no container, so no grouped row — drill-in (`ListServices`) shows it, and a whole-group op does not inherit the gap (empty batch slice = ALL services). `loadGroups()` merges loader + `GroupedHost` through the pure `buildSvcGroups(projects, host, prev)` into a WIDENED `servicesMsg` carrying BOTH halves (`hostStats`, `statsErr`), so **`statsRefreshCmd()` is nil in grouped mode** and the grouped branch clears `refreshInFlight` BEFORE its screen check, exactly as `statsMsg` does; the `ProjectLoader` is plain `ListProjects` — `WithUnmanagedRow`/`CountUnmanaged`/`projectsWithUnmanaged` are DELETED, since counting unmanaged containers was a third `docker ps` for a fact the status map already carries, and `buildSvcGroups`'s leftover path is the sole producer of the `(unmanaged)` group; **`groupedPayload bool` discriminates**, never a nil check (an empty host is a legitimate grouped result). `buildSvcGroups` takes ORDER from the loader, keeps a loader-only project as an EMPTY group (a bare header), appends host-only projects after them (the two calls can disagree), and carries fold state forward by project NAME. **A host-only group carries NO `ConfigDir`, and every write path refuses it**: `operableProject(proj)` is false for a grouped non-unmanaged project with an empty dir, `bindProjComposer` is the single refusal point and names `warnNoComposeDir`, and `armOperation`/`drillIntoGroup` check it too — `compose.New("")` would otherwise run the pipeline in cdeploy's OWN working directory. It reuses `statusSession` — it is `loadServices`' grouped counterpart. **The grouped `servicesMsg` branch is BOTH the initial load and the 5s reload, so it PRESERVES cursor, selection, fold and search** (the landing sites clear them once) and re-derives `searchMatches`, prunes the selection, clamps the cursor and replays cached verdicts. Loader AND host-ps failures → `svcErr`; stats failure → `statsErr`. The mode-aware dispatch is `statusRefreshCmd()`/`statsRefreshCmd()` behind ONE fan-out helper, `containerFetchBatch(initial bool)`, and **every container-screen entry goes through it**.

**Multi-project host view — landing, drill-in/out, and action-time composer binding**: `NewModel`'s table is servers/config → server picker; no composer → GROUPED; else the drilled fast track. **`enterGroupedContainers()` is the ONE landing body** (connect success, `entryLocal` without a local composer, drill-OUT) and owns the whole one-time reset — composer nil, project identity, rows, selection, cursor, search, wait/rollback state, the four session counters, `refreshInFlight`/`updateInFlight`/`updatesErr`. **Grouped mode holds `m.composer == nil` deliberately**: every capability assert reads nil as "not available", which is the inert behaviour wanted until an action key binds one. Binding is action-time: `bindCursorComposer()` (the ROW decides), `bindProjComposer(proj)` (addressed — an op batch may sit in a group the cursor has left), `unbindGroupedComposer()`. Both binders are pass-throughs in drilled mode, so callers call them unconditionally. **EVERY path that binds and stays on / returns to the grouped screen must unbind** (`l`/`x`/`i`/`c` early returns, the config assert failure, the confirm `esc`, all three `R` probe failures, the progress departure). **`x` is the ONE key that keeps its binding across the prompt**, which is why grouped `readOnly()` reads the GROUP LIST (`allGroupsUnmanaged()`), never the composer — an exec prompt over an unmanaged row would otherwise flip the whole screen to the read-only variant; a host whose ONLY group is the unmanaged bucket DOES read as read-only, because there no write key can do anything and the footer must not advertise three no-ops (no checkboxes, 7-cell caption pad, a different footer pair and therefore a different `svcVisibleCount`) for the length of the prompt. `enter` drills in from a HEADER only: `drillIntoGroup` installs the group's composer, identity and existing rows first (no "Loading" frame), reloads via `loadServices` for full fidelity, and KEEPS `svcStatus`/`stats` (their keys are already qualified). `esc` drilled→grouped reuses `enterGroupedContainers()` whole; `esc` grouped→server goes through `backToServerScreen()`. **`drilledFromHost` is the renamed `showPicker`** and is the drilled screen's `canGoBack()` rule — no predicate over the composer, factory or group list separates a drill-in from a standalone launch. `screenSelectProject`, `projectsMsg`, `projectsSession`, `viewSelectProject`, `projects`/`projCursor`/`projErr`, `compose.Project.Desc` and `internal/compose/unmanagedrow.go` (`CountUnmanaged`/`WithUnmanagedRow`, plus `cmd/root.go`'s `projectsWithUnmanaged`) are all DELETED — `buildSvcGroups` derives the `(unmanaged)` group from the host-wide status map instead.

**Multi-project host view — fold, header aggregates, and grouped rendering**: `space` carries TWO meanings decided by the ROW — a header folds, a service selects, an unmanaged row is a no-op — and **each branch calls `fixSvcOffset()` first** (the dispatch clears `m.warning` above the switch, freeing a row). The fold branch rebuilds entries, re-derives `searchMatches`, clamps the cursor, fixes the offset. `groupHeaderLine` draws `▼ name   ● n up  ✗ n  ⇧ n` (`▶` folded); `✗`/`⇧` only when non-zero, and **an empty group renders a BARE header** ("0 up" for a project with nothing to run reads as a fault it is not). `groupCounts` reads `svcStatus` through the qualified key and counts a missing entry as none of the three. Service rows indent 2 cells off `hasGroupHeaders()`; the caption pad (10 writable / 7 read-only) and both scroll indicators add the same offset. **`svcVisibleCount` math is UNCHANGED** — a header is an ordinary row; column widths come from `svcRefs()` so folding never shifts an open group's columns. **Unmanaged rows draw NO checkbox but KEEP its 3 cells**; `a`/`allSelected()`/the title denominator read `selectableRefs()`. The footer's third idle pair and the `?` overlay's `selectGroup(grouped)` are covered in the two help paragraphs above; `enter drill into the project on a group header` belongs to SELECT, **not** a second OPERATE row (OPERATE already names `enter` as the confirm key), and `TestHelpGroups_GroupedNamesTheSameKeys` pins the grouped token set against the writable one in BOTH directions instead of adding a second hand-maintained list.

**Multi-project host view — batch partitioning and the sequential progress pipeline**: `opBatch{proj, services}` is one project's share of an operation, and **an EMPTY services slice means ALL services** (compose-resolved — the only way a batch reaches a never-created service). `partitionSelection()` walks `svcGroups` in SCREEN order, skips the unmanaged bucket, and falls back to ONE batch (the cursor's group, empty slice) when nothing is selected; a cursor on the unmanaged bucket yields NO batch. **That empty-selection rule is GROUPED-only** — `armOperation` keeps the drilled `warnNoSelection` guard, because reinterpreting an unselected `d` as "deploy everything" is a semantic change to a destructive key. **The composer binds at the confirming `enter`, not at the `d`/`r`/`s` press** (unlike `x`): the prompt swallows every key that could change the partition, so it RECOMPUTES rather than captures, which keeps `opBatch` off the Model. The prompt names the batches (`formatBatchTargets`: `web (nginx, api) → db (all)`) on ONE clamped line. `enterProgress(batches)` builds the steps for EVERY batch up front; **`stepState.label` is new and `name` still holds the RUNNER step name** a `StepEvent` matches, with the `"web: "` prefix on the label only when `len(batches) > 1`. **Each batch gets its OWN events channel** (`runner.Run` defer-closes the one it is given). **`handleStepEvent` resolves inside the CURRENT batch's step range** (`currentStepRange()`), never by a global name scan — the same five names repeat in every batch; `enterProgress` always sets `batchStepCount` to `len(runner.Steps(op))`, so there is no zero-count fallback and a hand-built fixture must set it too (`progressStep()` fills `name`+`label`). `markBatchesSkipped(from)` starts AT `from`, so a single-batch failure skips NOTHING (its own unreached steps stay `○`). `pipelineDoneMsg`/`batchDoneMsg` both carry `batchIdx` + `batchSession` captured at DISPATCH, gated on screen + session + index. **`batchSession` bumps at INVALIDATION sites only — never in `enterProgress`** (it starts at 0, so a zero-valued message still resolves against a fresh sequence): the `esc`-cancel and `clearBatchSequence()` at every progress departure. The Deploy snapshot is PER BATCH, pre-Stop, inside the batch goroutine; `startBatch` does NOT rebind for `Rollback` (`R` bound it at press time and the prep validated against it), and **`R` captures the batch's PROJECT into `m.rollbackProj` at press time** — `m.currentProject()` is the ZERO project in grouped mode, so the confirming `enter` must build its batch from the capture or the invalidation deletes the wrong key. Update-cache invalidation walks `projUpdatesCacheKey(b.proj)` for every batch that FINISHED (`m.batchIdx` counts only when `m.done`); keying it off `m.done` alone — which only the LAST batch sets — left an earlier successful batch's glyphs stale for the whole TTL. **`viewProgress` WINDOWS the step list** (`progressStepWindow`), keeping `currentStepRange()` on screen with `▲/▼ N more` markers: a five-project plan emits 25 rows and bubbletea keeps only the LAST `m.height` lines, so an unwindowed render dropped the title and the running batch.

**Multi-project host view — updates in grouped mode**: **no automatic scan fires here.** `autoUpdatesAllowed()` = `!readOnly() && !grouped`, and `maybeRefreshUpdatesCmd` ALSO early-returns on `m.grouped` before the cache lookup — grouped mode owns neither the single key that helper reads nor the single composer a detail refill would fetch through. The key is `projUpdatesCacheKey(proj)`, the SAME string `updatesCacheKey()` produces once drilled into that project, so one entry is shared between modes. **`reapplyUpdateVerdicts(results)` replaces the two clear-then-hydrate blocks**: the drilled rule ("the message is the whole truth") would blank every group a one-group scan did not cover, on the error path too. **Exec into container**: The `x` key on the container screen execs into a running container interactively. Uses an `ExecProvider` interface (defined in `internal/tui/app.go`) with method `ExecCommand(ctx, service, command) (*exec.Cmd, error)`. Both `Compose` and `RemoteCompose` implement it. The TUI type-asserts `composer.(ExecProvider)` when `x` is pressed — if the assertion fails (e.g., test mock), the key is ignored. If the service is not running, a warning is shown. Otherwise, confirmation is requested (`pendingExec = true`); on confirm, the TUI shells out via `tea.ExecProcess` which suspends Bubble Tea and gives full terminal to the exec process. On return, `execDoneMsg` resets `pendingExec` and calls `refreshStatus()`. Default shell command: `[]string{"/bin/sh", "-c", "command -v bash >/dev/null 2>&1 && exec bash || exec sh"}` (checks for bash first, falls back to sh for Alpine/minimal images; uses `command -v` instead of redirecting stderr on `exec` to avoid silencing bash's stderr for the entire session). Local: `docker compose exec <service> <command...>`. Remote: builds SSH command directly (like `EditCommand` pattern) with `-t` for TTY allocation — does NOT use `remoteCommand()`. CLI: `cdeploy exec <service> [-- command...]` with `--server`/`-s` support; follows `cmd/logs.go` pattern. `ExecCommand` returns `(*exec.Cmd, error)` (not executing it) so the caller controls execution. `DefaultExecCommand` is exported from `internal/compose/compose.go`.

**Docker Compose**: All docker interaction goes through `compose.Compose.command()` (local) or `compose.RemoteCompose.remoteCommand()` (SSH) which builds the correct command based on the `Standalone` field — `exec.CommandContext("docker", "compose", ...)` for plugin mode or `exec.CommandContext("docker-compose", ...)` for standalone mode. Both set `CURRENT_UID` env var (format `uid:gid` locally, `$(id -u):$(id -g)` on remote). Auto-detection via `Detect(ctx)` probes `docker compose version` first, then falls back to `docker-compose version`; the result is cached in the `Standalone` and `detected` fields. Detection is explicit — callers must call `Detect()` before first use; `command()`/`remoteCommand()` only read `Standalone`. `SetStandalone(bool)` allows inheriting the detection result into new instances. `SetTestHooks(run, output)` on both `Compose` and `RemoteCompose` injects test doubles. Exact subcommands: `stop`, `rm -f`, `pull`, `up --no-start`, `start`, `config --services`, `ps -a --format json`, `logs`, `exec`, `ls -a --format json`, plus top-level `stats --no-stream --format json` (NOT a compose subcommand — see below). Empty container slice means operate on all services. `parseContainerStatus()` handles both JSON array output (Docker Compose v2.21+) and NDJSON (older versions); it parses `CreatedAt` and `Status` fields from `psEntry` to populate `ServiceStatus.Created` and `ServiceStatus.Uptime`. `formatUptime()` in `internal/compose/uptime.go` converts Docker's Status string (e.g. `"Up 3 hours (healthy)"`) into compact form (`"3h"`): strips health suffixes, compacts time units (`hours` -> `h`, `days` -> `d`, etc.), handles special cases (`"About a minute"` -> `"~1m"`, `"Less than a second"` -> `"<1s"`), returns `"restarting"` for Restarting status, and empty string for non-Up statuses. `parseUptimeDuration()` converts compact uptime strings back to `time.Duration` for comparison (used to pick the longest-running replica among scaled services, which correctly handles restarts where CreatedAt is older but actual uptime is shorter). CLI subcommands reject `-a` combined with explicit container names.

**Remote SSH**: `RemoteCompose` wraps docker compose commands in SSH calls via a ControlMaster persistent socket (`/tmp/cdeploy-ctrl-{hash}-{pid}`). `ConnectCmd()` returns the SSH connect command for TUI's `tea.ExecProcess` (full terminal access for password prompts), `Connect()` runs it directly for CLI use, and `Close()` tears down the socket. All remote args are shell-escaped via `shellEscape()`. `CURRENT_UID` is evaluated on the remote host via `$(id -u):$(id -g)` to get the correct server-side UID/GID. The `Run()` function in `tui/app.go` calls `disconnectFunc` on exit to ensure socket cleanup. CLI uses `--server`/`-s` flag to select a server; TUI shows a server picker when servers are configured.

**Ad-hoc SSH (`-S`/`--ssh`)**: The `--ssh` persistent flag (registered in `cmd/root.go` alongside `--server`) is the ad-hoc complement to config-based `--server`. It accepts `[user@]host[:port]` and lets CLI users (especially CI) connect without a `~/.cdeploy/servers.yml` entry. Mutually exclusive with `--server`; requires `--project-dir`. Implemented via two helpers in `cmd/remote.go`: `checkRemoteMutex(serverName, sshTarget, identityFile)` enforces both the `--server`/`--ssh` mutex and the `--identity` requires `--ssh` rule at the top of each subcommand's `RunE`, and `resolveSSHRemote(ctx, sshTarget, projectDir, identityFile, newRemote)` parses the target via `config.ParseSSHTarget`, calls the injected factory (`opNewRemote`/`execNewRemote`/`logsNewRemote`/`newRemote` — preserving existing test seams), sets `RemoteCompose.SSHExtraArgs`, and runs `Connect()` + `Detect()`. On `Detect` failure the helper internally calls `Close()` before returning the error; on `Connect` failure cleanup is a no-op. The returned cleanup is always non-nil, so callers can `defer cleanup()` immediately after the call without nil-checking. Wired into `deploy`/`restart`/`stop`/`exec`/`logs`/`list` subcommands as a branch above the existing `--server` block — config-based path is unchanged. Parser lives in `internal/config/sshtarget.go`: rejects whitespace and IPv6 (`[`-prefixed); validates port `1..65535`; returns `SSHTarget{User, Host, Port}` with helpers `SSHHost()` (`user@host` or `host`) and `PortArgs()` (`["-p","NNNN"]` or nil). The `SSHExtraArgs []string` field on `RemoteCompose` is spliced **immediately before the host argument** in every SSH argv build site (Connect, Close, Detect plugin/standalone probes, `remoteCommand`, `findRemoteComposeFile`, `ConfigFile`, `EditCommand`, `ExecCommand`); nil = zero-behavior-change default. No TUI changes — `--ssh` is strictly a CLI feature.

**Ad-hoc SSH identity (`-i`/`--identity`)**: The `--identity` persistent flag (registered in `cmd/root.go` immediately after `--ssh`) accepts a path to an SSH private key, intended for CI/automation workflows that write a key from a secret and don't have a `~/.ssh/config` entry. Strict-narrow: only valid alongside `--ssh` (mutually exclusive with `--server` via the `--identity requires --ssh` rule); CLI-only (TUI mode rejects it). Path validation lives in `internal/config/identity.go` (`ParseIdentity`): trims input, rejects empty, expands `~/` paths via `os.UserHomeDir()`, rejects bare `~` and `~user` forms (only `~/...` is supported), requires `os.Stat` to succeed and report a regular file, requires `os.Open` to succeed (readability check beyond mode bits), and returns `filepath.Clean` of the resolved path. Relative paths pass through unchanged — `ssh(1)` resolves them against cwd. `resolveSSHRemote` appends `["-i", cleanPath]` to `SSHExtraArgs` after the port args, so every existing SSH argv splice site absorbs `-i` for free without any changes to `internal/compose/remote.go`.

**Config**: `internal/config` loads `~/.cdeploy/servers.yml` defining remote servers and groups. The `Config` struct has `Groups []Group` and `Servers []Server`. `Group` has `Name` and `Color` fields. `Server` has `name`, `host`, optional `project_dir`, optional `group`, and optional `color` fields. Color resolution: grouped servers inherit color from their `Group` via `Config.GroupColor()`; ungrouped servers use their own `color` field. `color` accepts ANSI color names listed in `config.ValidColors` (exported slice, single source of truth for both validation and the TUI cycle picker): red, green, yellow, blue, magenta, cyan, white, gray; invalid values are rejected by `Validate()`. `Validate()` also checks group name uniqueness, group color validity, and that servers reference existing groups. `Save(path string) error` writes config atomically (temp file + rename) with `MkdirAll` for parent dirs. When color is omitted (resolved or direct), the TUI keeps the old plain-text breadcrumb instead of rendering a badge. Servers with the same `group` are displayed together under a shared header in the TUI. `Load()` returns an empty config (not error) if the file doesn't exist; it also runs `migrate()` to auto-convert old-format configs (per-server colors on grouped servers) to the new format (colors on Group entries, first-server-wins for conflicts). SSH-specific options (keys, jump hosts, tunnels) belong in `~/.ssh/config` — except `-i` for ad-hoc CI/automation use via `--ssh`.

**Settings editor**: Two screens (`screenSettingsList` + `screenSettingsForm`) accessible via `s` key on the server select screen (only when `m.config != nil`). **Operations**: Four operations — `Restart` (stop → rm → create → start), `Deploy` (stop → rm → pull → create → start), `StopOnly` (stop), `Rollback` (stop → rm → create → start — Restart shape, **NO Pull**: registry outages are a classic rollback trigger, so offline rollback from local blobs must work). All share the same `runner.Run()` pipeline; the step list varies by operation type. `Steps()`/`buildSteps()` fold Rollback into the Restart branch (`default:` case, gated only by `op == Deploy` for the Pull step).

**Wait engine (`--wait` health gate)**: ONE implementation, `internal/runner/wait.go`, drives BOTH CLI and TUI. `EvaluateWait` is a **pure reducer** (no clock, no IO); seed `WaitState` via `NewWaitState(services)`. **Per-service precedence IS the spec, in this order**: (1) `Uptime=="restarting"` ×3, checked **FIRST** (it also reports `Running==false`); (2) unhealthy; (3) `Running==false` after `everRunning`; (4) never-ran ×5; (5) `Health!=""` ⇒ has a healthcheck, passes ONLY on `Health=="healthy"` (a "starting" service stays pending); (6) no healthcheck + running ⇒ after `Grace`. **Firm timeout boundary**: PASS in 5/6 is gated on `elapsed <= Timeout`, fail-fast 1-4 is NOT; anything pending at `elapsed >= Timeout` sweeps to timed-out. `WaitHealthy` resolves empty targets via `ListServices()`; **`context.WithDeadline(ctx, start+Timeout)` must be created FIRST, before ANY blocking call, covering that resolution AND the polls — no wait-phase call may outlive `--wait-timeout`**, each re-arm capped at `min(Poll, Timeout-elapsed)`. A deadline expiry sweeps via `state.reportTimedOut` (NOT nil-status `EvaluateWait`) → `(report, nil)` = exit 2; a PARENT cancel returns `ctx.Err()` raw → exit 1 — check `ctx.Err()` BEFORE `waitCtx.Err()`. Only OPERATIONAL failures error; a failing verdict is `(report, nil)`, `report.OK==false`.

**`WaitError` exit-2 contract**: `cmd.WaitError{Report, Err}` (`cmd/deploy.go`) wraps a non-OK **OR** errored `--wait` report; `main.go` `errors.As` → `os.Exit(2)`; `Unwrap()` must keep exposing the operational cause. `addWaitFlags` puts `--wait`/`--wait-timeout` on deploy, restart, rollback ONLY; `stop` never waits (`runOperationWithPrep` guards `op != runner.StopOnly`).

**Deploy snapshots & the state file**: every `Deploy` records each *running container*'s digest to `~/.cdeploy/state/<sha256(projectDir)[:12]>.json` **on the docker host**, BEFORE the pipeline stops anything. **Deploy-only** — never Restart, never Rollback; **captured pre-Stop** from the running container, NEVER the local tag; **merge-not-replace** (`mergeSnapshot`, fresh wins); the key hashes a NORMALIZED dir (`Abs`+`Clean` local, `path.Clean` remote); **warn-and-proceed** — capture and write failures never block. Schema version 1; any other returns typed `errSnapshotSchema`; `ReadSnapshot` returns `(nil, nil)` for a missing file. **Overwrite protection** (`existingForMerge`): ONLY a missing or `errSnapshotCorrupt` file may be overwritten; an `errSnapshotSchema` file or a transient read/SSH failure MUST abort the write. Local `WriteSnapshot` flocks `<state>.lock`; the REMOTE write is deliberately unlocked.

**Rollback pipeline & `PrepareRollback` prep / `ExtraComposeFiles` contract**: `cmd/rollback.go` reuses `runOperationWithPrep` with the `rollbackPrep` hook; never fork `runOperation`. Hook order: `ReadSnapshot` → `resolveRollbackTargets` refusals → `filterLiveTargets` against the CURRENT `ListServices()` (failure ABORTS prep — fail closed; a removed service is skipped under `-a`, errors when named) → `PrepareRollback`, which pulls absent blobs (a failed pull MUST abort BEFORE any override is written or the field set), writes `buildOverrideYAML` — `image: <repo>@<digest>` **plus `pull_policy: never`** per service, services in **SORTED order, never marshal a map** — and sets `ExtraComposeFiles = [main, override]`. Its cleanup (remove override, field to nil) MUST be deferred **function-scoped** — after the wait phase, BEFORE the remote SSH teardown, whose socket the `rm -f` still needs. `rollbackPrep` returns the resolved (snapshot ∩ live) set; `runOperationWithPrep` MUST thread it into **BOTH** `runner.Run` AND the wait phase — never the raw nil `containers`. Non-nil `ExtraComposeFiles` has `command()`/`remoteCommand()` splice `-f <f0> …` right after `docker compose`/`docker-compose`, BEFORE the subcommand, escaped on remote. `-f` disables auto-discovery, so the **main file MUST be first**, absolutized locally (`cmd.Dir = ProjectDir`). **A nil field must keep producing byte-identical argv.**

**TUI wait phase & `R` rollback (sessions + cleanup)**: `screenProgress`'s `waiting` sub-state drives a singleton `waitTickMsg` loop gated on screen+`waiting`+session; StopOnly never waits. **The gate is PER BATCH**: `pipelineDoneMsg` OPENS it and `batchDoneMsg` — never `pipelineDoneMsg` — RELEASES the next batch, so a batch's channel closing no longer means the batch is over. A whole-project batch (empty target set) resolves its names through `waitTargetsMsg`/`ListServices` — grouped mode must NOT fall back to the screen's rows, which are host-wide there (`drilledServices()` answers nil for anything but a single group) — and an unresolvable set SKIPS the gate (no health verdict was named, so it is not a health failure). A failing gate stops the sequence only when a batch is STILL TO COME; the last batch keeps today's `done`-with-red-verdicts rendering. `esc` on a mid-sequence gate RELEASES the next batch (`batchFinished()` is the shared release path for `StopOnly`, an unresolvable set and the skip) — see `docs/architecture/tui-multi-project.md`. Each poll MUST be `WithDeadline(m.ctx, m.waitDeadline)`-bounded and the `waitStatusMsg` error path MUST sweep pending→timed-out (`sweepWaitTimeout`) ONCE `elapsed >= Timeout` — before the deadline the failed poll is transient, state is carried forward and the loop keeps ticking; `esc` calls `clearWaitState()` (bumps `waitSession`). `R` **captures the selection into `rollbackTargets` at press time** (bumping `rollbackFetchSession`); that set — **NEVER live `selectedContainers()`** — drives validation, the prompt, `PrepareRollback` and `opContainers` (empty = ALL services), and an empty capture REFUSES. `rollbackSnapshotMsg` is screen+session gated, a `ListServices` failure fails closed, and a target absent from the snapshot or live compose is refused. The prep cleanup runs via `runRollbackCleanup` when **LEAVING `screenProgress` — NEVER goroutine-deferred**; a hard quit mid-wait must run it on the main goroutine too (both `ctrl+c` paths). `waitSession`/`rollbackFetchSession` bump at the same sites as the other counters; `waiting`/`waitState`/`waitDeadline`/`rollbackSnapshot`/`rollbackTargets`/`rollbackCleanup` clear at every departure site (esc chain, `entryLocal`, `connectResultMsg` error path); esc-from-progress must invalidate the update cache for `runner.Rollback` too. The TUI snapshots FIRST in the Deploy op goroutine; `Snapshotter`/`RollbackPreparer` are type-asserted. Rationale and test pins: `docs/architecture/wait-snapshots-rollback.md`.

**Health checks**: `ServiceStatus` has `Running bool`, `Health string` (values: `"healthy"`, `"unhealthy"`, `"starting"`, or `""` for no healthcheck), `Created string` (formatted creation time, e.g. `"2024-01-15 09:30"`), and `Uptime string` (compact uptime, e.g. `"3h"`, `"2d"`, or `""` if not running). For scaled services, `Running` uses OR (any running = running), `Health` uses worst-case priority (`unhealthy` > `starting` > `healthy`), `Created` uses the oldest replica, and `Uptime` uses the longest-running replica. The TUI shows health icons (♥/✗/~) next to status dots and Created/Uptime columns. The CLI `list` command shows the same icons and columns.

**Multi-project discovery**: The `list` subcommand auto-discovers all compose projects when no `-C` is specified (both local and remote). Services are grouped by project with headers. Per-project errors are non-fatal — a warning is printed to stderr and the project is skipped. When `-C` is specified, only that project's services are shown in a flat list. With `--stats`, CPU/Mem columns are populated by joining `docker stats --no-stream --format json` against each project's `ps` container IDs. The host-wide `docker stats` call is shared across every project: `runList` calls `compose.AllContainerStats`/`AllContainerStatsRemote` once before the project loop and passes the result map into `collectMultiProjectStats`. Each project's composer satisfies the `bulkStatsAggregator` interface (`ContainerStatsFromBulk`) and only runs `docker compose ps` per project, joining against the shared bulk map — one ~1.5s cost regardless of project count. Composers that don't implement the bulk interface (test mocks) fall back to per-project `ContainerStats()`; the fallback also runs if the host-wide fetch failed (`bulkStats == nil`), so stats degrade gracefully rather than disappearing.

**Resource stats**: `runner.ServiceStats` (`CPUPercent float64`, `MemoryUsed int64`, `MemoryLimit int64`) is populated from `docker stats --no-stream --format json` — host-wide NDJSON, one line per container, parsed by `parseStatsOutput()` in `internal/compose/stats.go` (tolerant of both NDJSON and JSON-array forms, mirroring `parseContainerStatus`). `ContainerStats()` is the **first method on `Compose`/`RemoteCompose` to bypass `command()`/`remoteCommand()`** because `docker stats` is a top-level Docker CLI command rather than a compose subcommand — calling `c.command(...)` would prepend `compose` and produce a malformed argv. `AllContainerStats()` builds `exec.CommandContext("docker", "stats", ...)` directly; `AllContainerStatsRemote()` builds the SSH argv directly, splicing `SSHExtraArgs` immediately before the host arg (same convention as `EditCommand`/`ExecCommand`, which also bypass `remoteCommand()`). Per-project `ContainerStats()` calls `docker compose ps --format json` for this project's container IDs, calls the bulk helper, joins by short container ID (first 12 chars), and sum-aggregates `CPUPercent`/`MemoryUsed`/`MemoryLimit` across replicas — a 3-replica service maxing each core shows ~300% CPU. Only running containers appear in the result map; stopped services are absent. Helpers `parseSize` (handles `B`/`KiB`/`MiB`/`GiB`/`TiB` binary and `kB`/`MB`/`GB`/`TB` decimal suffixes, case-insensitive), `parseCPUPercent` (strips `%`), and `FormatBytes` (exported; produces compact `124M`/`1.5G`) live in `internal/compose/stats.go` as the single source of truth — both `cmd/list.go` and `internal/tui/app.go` import `FormatBytes` from there. TUI fetches stats in parallel with status via `tea.Batch(refreshStatus(), refreshStats())` on every entry to `screenSelectContainers` and after every operation completes (return from progress / logs / exec). A periodic `refreshTickMsg` (every `statsRefreshInterval` = 5s, defined in `internal/tui/app.go`) keeps the data fresh while the user lingers on the screen: `Init()` kicks off a singleton `tea.Tick`, and the handler always reschedules itself so exactly one tick is in flight at any time regardless of how many transitions in/out of the screen happen. The handler gates fetches on `m.screen == screenSelectContainers && !m.confirming && m.composer != nil && !m.refreshInFlight` — anywhere else, the tick is a pure reschedule with no docker calls (off-screen / mid-confirmation / mid-disconnect / previous fetch still pending).

**Update detection — tri-state and Composer contract**: `runner.ServiceStatus.UpdateAvailable *bool` is a tri-state: `nil` = unknown / not checked / build-only / error, `true` = update available, `false` = current. `Composer.CheckUpdates(ctx, services)` returns ONLY checked services — an absent key must stay absent (that is the nil). **A non-nil error makes the map untrusted** — soft-failure consumers MUST discard it (`updates = nil`) and render all-blank-plus-warning. `compareImageDigestVia` returns `(updated, ok, err)`: **an empty digest is `ok == false`, never an error** (it would pollute the cascade counters).

**Update detection — digest comparison**: `parseLocalDigest` filters `RepoDigests` by repo (`stripTag`) and **falls back to the first non-empty digest when no repo matches**; `fetchRemoteDigestVia` tries `docker buildx imagetools inspect` FIRST and falls back to `docker manifest inspect --verbose` whenever imagetools yields no valid digest — a non-transport failure OR a successful call whose output the strict parser rejects; `errSSHTransport` short-circuits the fallback instead. — `errSSHTransport` propagates instead. **Do NOT add `--format '{{.Manifest.Digest}}'` back to `imagetoolsInspectArgs`** — silently ignored; `Name:` parses as the digest. `parseImagetoolsDigest` takes the top-level `Digest:` line and validates strict `sha256:<64 hex>`; do NOT add a "bare sha256 line" fallback. All three inspects **bypass `command()`/`remoteCommand()`** (top-level docker) — local `runDockerCmd`, remote `runRemoteDockerCmd` (`shellEscape`d image names, `SSHExtraArgs` before the host arg).

**Update detection — SSH transport classification (RemoteCompose only) / systemic-failure cascades**: `classifySSHError(err, stderr)` matches `sshTransportStderrPatterns` — SSH-ONLY signatures. **Do NOT add generic networking phrases** (`connection refused`, `no route to host`). A match wraps `errSSHTransport` and aborts `CheckUpdates`; anything else is a per-image failure → absent cell. Two post-scan cascades, both gated on `len(out) == 0`: **registry** when `networkFailures == remoteAttempts > 0` (`looksLikeNetworkErr`), **local-docker** when every local inspect failed AND every failure ALSO matches `looksLikeLocalDaemonErr` — that classifier gate is not optional. Partial failures never cascade; remote mirrors the registry cascade only. All three `CheckUpdates` share ONE loop, `scanImageUpdates`, memoized by image ref; **no cascade flag — the sentinel the comparer emits selects the cascade**: only `Compose` passes `wrapLocalImageInspectErr`, so only it emits `errLocalImageInspect`; `errSSHTransport` lives only on the remote runner.

**Update detection — TUI caching and refresh**: `updateCache` is keyed `projDir + "|" + serverName`; successes live `updatesCacheTTL` = 10m, failures `updatesErrorTTL` = 30s. **Errors ARE cached**, a new entry ALWAYS overwrites the prior one for that key (failure over stale success, success over failure), and **`errMsg` MUST be restored on every cache hit** (`maybeRefreshUpdatesCmd` and both replay paths). The `updatesMsg` handler applies its mutations (`updatesErr`, stale-glyph clears, hydration) **BEFORE the screen check**; only `fixSvcOffset` is screen-coupled. …deletes the current key's entry on a successful Deploy, Restart or Rollback, **before** the `m.done = false` reset; skipped on `m.failed` and on Stop. `U` bypasses the TTL but MUST keep its `if m.updateInFlight` guard, like `maybeRefreshUpdatesCmd`. Updates are **NOT** in the 5s `refreshTickMsg`. `projUpdatesCacheKey(proj)` is the sibling that composes the same string for a project the Model is not pointed at (a batch sequence, a grouped scan); `updatesMsg` carries `forKey` captured at DISPATCH and the handler **must never re-derive the key** — see the grouped-updates paragraph below.

**Update detection — sessions and in-flight discipline**: `updatesSession` gates `updatesMsg` and is bumped at the **same 7 sites** as `statsSession`/`statusSession` (`entryLocal`, `execDone`, return from progress, return from logs, `enterGroupedContainers`, `drillIntoGroup`, `backToServerScreen`) — **and the `connectResultMsg` SUCCESS path now reaches `enterGroupedContainers` too**, so it bumps all three; the old "NOT on success" rule died with the static project picker. Its ERROR path bumps `rollbackFetchSession` but NOT `statsSession`/`statusSession`/`updatesSession`. `updateInFlight` is cleared **BEFORE BOTH the session check AND the screen check, on EVERY arrival**, stale ones too. Every site that bumps `updatesSession` AND calls `maybeRefreshUpdatesCmd()` MUST reset `m.updateInFlight = false` first; the 2 leave-screen transitions reset it too. `connectResultMsg`'s error path clears `serverName`/`updatesErr`/`updateInFlight`; `entryLocal` clears `projDir`/`projName`/`updatesErr`.

**Update detection — rendering, CLI, and JSON**: `hydrateUpdates` (called from `servicesMsg`/`statusMsg`) writes verdicts into `m.svcStatus` and **MUST skip a verdict whose name is not already in `m.svcStatus`**. `updateGlyphStyle` appends `" ⇧"` (`compose.UpdateGlyph`); `maxName += 2` **unconditionally**, in the TUI and in `formatDots`/`formatDotsGrouped`, measured with `utf8.RuneCountInString`. Errors use the soft-warning slot prefixed `updates: `, priority `svcErr > statsErr > updatesErr`. `cmd/list.go` gates `CheckUpdates` behind `--updates` in BOTH single- and multi-project modes; a failure warns to stderr, SETS `updates = nil`, and never aborts the listing; JSON carries `update_available *bool` with `omitempty`. Full rationale and test pins: `docs/architecture/update-detection.md`.

**Update detection — inspect detail rows (`UpdateDetailer`)**: `UpdateDetails(ctx, services) (map[string]compose.UpdateDetail, error)` is declared in `tui` beside `Inspector` and type-asserted — **NOT a `Composer` change**, so the five mocks and `list --updates` stay untouched; keep the three `var _ UpdateDetailer = …` pins in `app_test.go`. Details ride the `refreshUpdates()` SCHEDULE but a SECOND message: `refreshUpdates` returns the moment `CheckUpdates` does, and its handler enqueues `updateDetailsCmd(entry, key)` AFTER the cache write (the WHOLE entry, so `results` and `fetchedAt` can never be paired from two different ones). **Do NOT fold the fetch back into `refreshUpdates`' goroutine** — one Cmd is one message, so the `⇧` verdicts would wait on up to three registry round-trips per updated image with `updateInFlight` pinned true (a dead `U`). The enqueue sits AFTER the session check, so a scan already superseded when its verdicts arrive spends no detail calls; one superseded LATER cannot be stopped, so **`m.detailsInFlight` bounds the phase to ONE batch GLOBALLY** — `updateDetailsCmd` returns nil while it is set, and the handler's unconditional clear on EVERY arrival (before the identity gates) is its ONLY clear. **No context-change site may reset it**: with at most one batch outstanding there is exactly one arrival per raise, which is what makes that clear exact — a reset lets two scans overlap and lets the refill dispatch a third onto an entry the second is already filling. **The arrival is guaranteed by `context.WithTimeout(m.ctx, updateDetailsTimeout)` inside `updateDetailsCmd`** — `m.ctx` has no deadline and no runner adds one, so without it ONE stalled registry call latches the flag for the rest of the session with no escape short of restarting cdeploy; an expiry degrades to a PARTIAL map, never an error. **Do NOT gate `U` on it and do NOT delay the `updateInFlight` clear** — either reinstates the dead-`U` window the split removed. **A refused or lost batch is not queued anywhere — it heals from the ENTRY**: `refillUpdateDetailsCmd` re-dispatches whenever the CURRENT entry is fresh, non-errored and has `details == nil`, called from exactly two sites — the tail of the `updateDetailsMsg` handler (**hoist it into its own statement**; `return m, m.refill…()` leaves the receiver mutation to an unspecified evaluation order, and losing it is an unbounded registry loop) and `maybeRefreshUpdatesCmd`'s fresh-SUCCESS branch. **NEITHER is behind `autoUpdatesAllowed()`** — a refill can only fire for an entry that ALREADY EXISTS under the current key, and on a read-only key only `U` can create one (the stale branch, the `statusMsg` self-heal and `Init()` all refuse), so a refill is the continuation of an authorised fetch, not a new automatic one; gating either site strands the rows `U` asked for for the whole 10m TTL. **`details == nil` vs an EMPTY map is load-bearing** — nil means no batch REPORTED, so the merge normalises a nil map to an empty one or a failed batch re-scans on every screen entry for the whole 10m TTL. Three review rounds each patched a different door that dropped a batch (a session gate, a merge-time key, a departure-site reset) and the bug walked through the next; **do not add a fourth guard — keep the retry keyed off the entry's own state**. **`updateDetailsMsg` carries NO session — it carries its OWN identity**, `forKey` + `forEntry`, both captured at DISPATCH time: the key is the context and `fetchedAt` names the exact verdict set. A session gate, and equally a key RE-DERIVED in the handler, DROPPED the rows for the entry's whole 10m TTL — ordinary navigation (esc from logs/progress, `execDone`, esc drilling out to the grouped host view) bumps the counter or changes the current key without touching the entry, and those sites enqueue no replacement. It only MERGES onto an existing non-errored entry, and `redrawInspectFromCache()` runs only when `forKey` IS the current key (it is a render path). One `updateEntry`, one key, so the `⇧` triggers, TTLs, invalidation and `autoUpdatesAllowed()` gate still apply by construction; `detailsInFlight` is the ONE new Model field, a transient guard with no departure-site cleanup at all, and `details` itself needs none either. **A detail failure is DISCARDED, never `updatesMsg.err`** — a 429 matches `looksLikeNetworkErr` and would trip the registry cascade and blank the whole `⇧` column. Pass **ONLY the `true` verdicts, SORTED**, and skip the call entirely when none is true or `CheckUpdates` errored — `filterServices` reads an empty slice as **ALL** services, so the guard is a rate-limit rule, not an optimisation. UP TO four round-trips per updated image (`localProbeArgs`, `manifestIndexArgs`, `rawManifestArgs`, `imageConfigArgs`), up to three of them registry — the single-manifest path skips step 3, so it costs two; all bypass `command()`/`remoteCommand()` through the `dockerRunner` seam. `scanUpdateDetails` memoizes by image ref (**failures too**), visits services SORTED, **OMITS a failed image and CONTINUES** (a partial map is a valid result — never turn that `continue` into a `return`), short-circuits on `errSSHTransport` with the partial map, and checks `ctx.Err()` per image; the first-failure early return belongs to `fetchUpdateDetail`'s four-step sequence, not to the scan. On the single-manifest path **step 3 is SKIPPED** — step 2's output IS the manifest, so `pinnedImageRef` returns `pinned bool` and `parseConfigDigest(indexOut)` supplies `NewID`, with the `--raw` call kept only as the fallback when that yields nothing. **`localProbeFormat` is `{{json .}}` and must NAME no field** — a template naming a field the CLI's struct lacks is a hard error, and the CLI's raw retry runs with `missingkey=error`, so an `omitempty` field with no value (`Variant` on most images) fails there too; the whole-document form degrades to an empty string instead, which is the same rule `hostPsArgs` carries. `parseLocalProbe` decodes `Created`/`Os`/`Architecture`/`Variant` out of it and ignores the rest. `parseIndexPlatformDigest` is THREE-state: `hasIndex=false` → use the ORIGINAL ref; `hasIndex=true, found=false` → **ABORT this image**; every doubt (malformed JSON, non-list `manifests`, empty os/arch, and an EMPTY document — `null` unmarshals into a nil map, so `len(doc) == 0` must abort rather than fall through) returns the ABORT state, and `unknown` os/arch entries are attestations that must never be selected. **The variant is MATCHED, not guessed, and BOTH sides are canonicalised first** through `normalizePlatformVariant` — containerd's `normalizeArch` rule, which docker and buildx inherit and the OCI image-spec leaves open: an unqualified `arm` IS `v7` (never a wildcard over 32-bit ARM), and `arm64` and `arm64/v8` are ONE platform. The entry whose NORMALISED variant equals the probe's normalised one wins; with no exact match a LONE entry whose normalised variant is EMPTY wins (it serves the whole arch — portainer and qdrant publish `linux/arm64` that way); everything else ABORTS — a KNOWN variant with no entry of its own draws nothing. `linux/arm` ships as v5+v7 or v6+v7, so index order drew another image's digest and build date, accepting a lone qualified entry regardless still handed an ARMv6 host a `v7`-only image, and treating an unqualified `arm` entry as architecture-wide handed the same image to an ARMv5/v6 host. **Do NOT re-add a lone-QUALIFIED-entry fallback for a probe that names no variant** — after normalisation such a probe is a concrete platform, so it would take an `arm64/v9` or `amd64/v3` entry (`TestParseIndexPlatformDigest_VariantMatching/a_lone_arm64...` fails under exactly that). **Do NOT "fail closed" on any qualified-only match either** — BOTH captures spell arm64 as `arm64/v8`, and the fold is what makes those hosts match exactly (`TestPinnedImageRef` fails under that mutation). `parseImageCreated(data)` reads the BARE OBJECT only — a platform-keyed map cannot reach step 4 (a multi-platform tag always has an index, so it is pinned or aborted first), and **do not re-add the map branch**; `validImagetoolsDigest` is a WHOLE-STRING check. **`Unix() <= 0` is a sentinel, not data** (reproducible builds) — `parseImageTimestamp` and `formatInspectTimeValue` both drop the row. `rebuildInspectSummary()` is the ONE cache-lookup site (`m.currentUpdateInfo()`, raw map read — NOT the TTL-checked lookup; `inspectUpdateInfo.detail` is a VALUE, only `verdict` is a pointer), and BOTH handlers MUST call `redrawInspectFromCache()` — rebuild when `m.screen == screenInspect`, **on the failure path too**, AFTER the cache write, and **skip the viewport write in raw mode** (`setInspectContent` resets `SetXOffset(0)`, which would snap a sideways scroll back). Raw mode stays byte-identical. Full rationale and test pins: `docs/architecture/update-detection.md`.

**Session filters for stale responses**: `statsMsg`, `statusMsg` AND `servicesMsg` all carry a `session uint64` captured at fetch time; their handlers reject messages where the session (and screen) don't match. Two counters live on Model:
- `statsSession` covers `refreshStats` (grouped stats ride `loadGroups`' `statusSession`) — bumped at every context change that swaps `m.composer` or the grouped host context: `entryLocal` fast track, `execDone`, `esc` from logs, `esc` from progress, plus the three navigation helpers `enterGroupedContainers()` (connect success, `entryLocal` grouped, drill-OUT), `drillIntoGroup()` (drill-IN) and `backToServerScreen()`.
- `statusSession` covers `refreshStatus`, `loadServices` AND `loadGroups` — bumped at the same 7 sites as `statsSession` (the lifecycle is identical: `loadServices`/`loadGroups` are the initial-load siblings of `refreshStatus`, fetching list + initial status in one shot). `loadGroups` deliberately reuses this counter rather than owning one: it is `loadServices`' grouped counterpart, same context changes, same staleness rule.
- `projectsSession` and `projectsMsg` are GONE with the project picker. The loader they guarded now feeds `loadGroups`, which is already gated on `statusSession` at the same swap sites.
- **The `connectResultMsg` SUCCESS path DOES bump all three counters** (via `enterGroupedContainers`) — the inverse of the rule that held while the next screen was the static picker. It now lands on LIVE data, and the site that starts fetching a resource is the site that must invalidate whatever a previous server left in flight.

Missing the session filter on any of them is the same class of bug — codex's adversarial review caught each one in successive rounds. When adding a NEW async msg type that's tied to a screen context, give it a session and gate the handler on `m.screen != <its-screen> || msg.session != m.<sessionField>`.

**`refreshInFlight` prevents fetch stacking**: the tick fan-out `tea.Batch(statusRefreshCmd(), statsRefreshCmd(), refreshTick)` — the mode-aware pair, `loadGroups` alone in grouped mode (it carries the stats half, so `statsRefreshCmd()` is nil there) and `refreshStatus`/`refreshStats` in drilled mode — schedules the next 5s tick *concurrently* with the current refresh — Bubble Tea batches execute concurrently, not sequentially. Without a guard, if `docker stats --no-stream` takes longer than 5s on a slow remote SSH hop, the next tick would stack another pair of fetches on top. The `m.refreshInFlight bool` is set true at every site that fires `refreshStats()` (the tick handler + the 5 transition handlers that fan out the fetch batch) and cleared in the `statsMsg` handler on any *current-session* arrival, *before* the screen check (success or error). Clearing has to happen before the screen check because if the user opens the config / logs / progress screen while a stats fetch is pending, the response arrives off-screen and would otherwise be discarded silently — leaving `refreshInFlight` stuck true and permanently silencing the periodic loop when the user returns to the container screen. The session-match condition makes the unconditional clear safe: stale responses (different session, indicating a context change has happened) don't touch the flag because the context-change handler already reset it. The flag is also explicitly reset to false in `backToServerScreen()` (the one transition that navigates away without firing a fetch batch) so the new context starts clean. When the next tick fires while the guard is set, it reschedules without fetching. **The tick's liveness check is `m.composer != nil` in drilled mode and `m.composerFactory != nil` in grouped mode** — grouped mode holds no composer by design, so a flat composer test would silence the periodic refresh on exactly the screen that most needs it.

**Test seam for the tick**: `Model.tickCmdOverride func() tea.Cmd` is nil in production; tests set it via `installFakeTick(&m)` (in `internal/tui/app_test.go`) to swap the real `tea.Tick` for a non-blocking Cmd that returns a `fakeTickMsg`. Without the override, every test exercising the gated paths (off-screen, in-flight, confirming) would leave a real 5s `tea.Tick` goroutine running until the program exits. With the override installed, tests assert directly on whether `cmd()` returns a `tea.BatchMsg` (positive path: fetch batch) or any other msg (gated path: just the rescheduling tick). NewModel sets `m.refreshInFlight = true` for the local fast-track because `Init()` will fire `refreshStats`; tests that exercise the unblocked tick path must explicitly clear it.

When adding a new screen that should NOT trigger periodic refreshes, no change is needed: the gate already excludes any screen != `screenSelectContainers`. When adding a new screen that DOES need its own periodic refresh, prefer a separate tick (different msg type) rather than overloading `refreshTickMsg`. When adding a new context-change handler (anything that swaps `m.composer`), bump BOTH `statsSession` AND `statusSession`, and set `refreshInFlight` (true if the handler fires a refresh batch, false if it just navigates away). `statsMsg` carries a `session uint64` captured at fetch time from `m.statsSession`; the handler rejects messages where `msg.session != m.statsSession` in addition to the screen check, mirroring the `logsSession`/`configSession` pattern. `statsSession` is bumped on every context change that swaps `m.composer` or the grouped host context (`drillIntoGroup`, `enterGroupedContainers`, `backToServerScreen`, `entryLocal`) so an in-flight fetch from project A cannot land in project B's view. Soft failure: on stats fetch error, both CLI (`cdeploy: stats unavailable: <err>` to stderr, exit 0, blank cells) and TUI (`statsErr` rendered as soft warning) keep status — the load-bearing primary view — intact; in the TUI, when both `svcErr` and `statsErr` are set, `svcErr` wins (the more important failure).

**Ports column**: `ServiceStatus.Ports []runner.Port` (with `Host`, `HostPort`, `ContainerPort`, `Protocol` fields) is populated by `parseContainerStatus()` from `docker compose ps --format json`. Primary data source is the `Publishers []` array (Compose v2); when absent or empty, `parsePortsString()` falls back to parsing the `Ports` text field (e.g. `0.0.0.0:8080->80/tcp, :::8080->80/tcp`). Publishers with `PublishedPort == 0` (i.e. `expose:`-only/internal) are skipped. Dedup is keyed on the full tuple `(Host, HostPort, ContainerPort, Protocol)` so distinct bind interfaces on the same port (e.g. `127.0.0.1:8080->80` and `192.168.1.10:8080->80`) both survive. A separate `collapseIPv6Mirrors()` pass collapses only the IPv4/IPv6 *wildcard* mirror pair — when both `0.0.0.0` (IPv4 unspecified) and `::` (IPv6 unspecified) appear on the same `(HostPort, ContainerPort, Protocol)` tuple, the `::` entry is dropped. All other host strings are distinct user-visible binds: IPv6 loopback `::1`, link-local `fe80::1`, or explicit IPv6 addresses like `2001:db8::1` survive intact, even alongside an IPv4 sibling. Multiple non-wildcard IPv6 entries on the same tuple do not collapse against each other (full-tuple dedup in `mergePort` already removes exact repeats). Bracketed IPv6 like `[::]:8080` is normalized (brackets stripped on input). Empty `URL` from Compose is normalized to `0.0.0.0`. Scaled-service ports go through the same dedup + collapse + sort pipeline (sorted ascending by `HostPort`, then `ContainerPort`, `Protocol`, `Host`). Render helpers live in `internal/compose/ports.go`: `FormatPort()` returns `host:hp→cp` for IPv4 and `[host]:hp→cp` for IPv6 (the arrow is U+2192, not `->`; IPv6 hosts — any host containing `:` — are wrapped in brackets to disambiguate the host:port boundary), with `/proto` suffix only when protocol is non-empty and not `tcp` (`/udp` and `/sctp` are shown). Wildcard hosts (`0.0.0.0` and `::`, both meaning "all interfaces") are omitted entirely so the common all-interfaces case renders as a bare `hp→cp`; non-wildcard binds (loopback, explicit address) keep their host so the LAN-vs-loopback distinction stays visible. The wildcard-hiding affects only display — JSON output (`cmd/list.go` serializes the `Port` struct directly) preserves the original `host` field. `FormatPorts()` comma-joins. Both the CLI `list` (`formatDots`/`formatDotsGrouped` width-track `maxPorts` and append the column after Uptime when any service has ports) and the TUI container-select screen (captions row gains `"Ports"` via `hasStatusColumns()`) render the column. Stopped containers and services without published ports show a blank cell (padded whitespace for alignment). CLI JSON output includes a `ports` array (`omitempty`) per service with `host`/`host_port`/`container_port`/`protocol` fields.

**Unmanaged containers — the `HostContainers` composer and the three-method `dockerRunner` seam**: a container with no `com.docker.compose.project` label gets `compose.HostContainers` (`internal/compose/hostcontainers.go`), a read-only `runner.Composer`: five writes `return errReadOnly`, five reads go through the unexported `dockerRunner` field. **The seam needs THREE methods, not one builder**: `run` captures and classifies — the remote form reuses `runRemoteDockerCmd`, so `errSSHTransport` classification comes free; `stream` must NOT allocate a TTY and MUST wire BOTH Stdout and Stderr to `w`; `tty` MUST splice `-t` remotely. All three remote forms go through `RemoteCompose.remoteDockerCmdString(args)` — one home for `docker` + `shellEscape`. `hostPsArgs` = `ps -a --size=false --format {{json .}}`: the **template** form, never the bare `json` keyword (CLI >= 23.0 only), and **never drop `--size=false`**. Never name fields individually instead: an unknown field is a hard template error (`.State` needs CLI >= 20.10). `isComposeManaged` matches the key **only at a token start** (`HasPrefix(labels, k) || Contains(labels, ","+k)`), **never** by splitting `Labels` into `k=v` pairs — a value may contain a comma; the const keeps its trailing `=`, excluding the sibling `…config_files`/`…working_dir` keys. `parseHealthFromStatus` reuses the end-anchored `healthSuffixRe` from `uptime.go` — extend it, never duplicate it. `Running` is `State == "running"` and **must keep the `HasPrefix(Status, "Up ")` fallback for an empty `State`**. `ContainerStats` uses the seam directly and **early-returns before the stats call when there are no unmanaged entries**; a container in `ps` but absent from `stats` is **skipped, not an error**; `ContainerStatus` has NO such guard and **must not grow one**. `hostStatsArgs` takes the same form; that equivalence is **per-command**. `CheckUpdates` maps name→image from the `Image` field `ps` already returned and calls `scanImageUpdates` with a **nil `localErrWrap`** (no local-daemon cascade); `hostImageMap` drops empty refs and bare image IDs.

**Unmanaged containers — the `(unmanaged)` group, the widened `ComposerFactory`, and the cache-key collision**: `compose.Project` gains `Unmanaged bool` — do NOT overload `Status`; `Desc` was deleted with the project picker that was its only reader. `CountUnmanaged`/`WithUnmanagedRow`/`projectsWithUnmanaged` were deleted with it too (`internal/compose/unmanagedrow.go` is gone); only `UnmanagedProjectName` survives, in `hostcontainers.go`. **`buildSvcGroups` (`internal/tui/entries.go`) is the SOLE producer of the row now** — its leftover path picks the bucket out of the host-wide status map the grouped fetch already returned and appends it LAST, so the group costs no second `docker ps`. It renders as the last GROUP on the container screen (read-only rows, no checkbox cell, never in an op batch). **Every branch `cmd/root.go` contributes to the composer side lives in a package-level helper, never in the `RunE` closure**: `localComposerFor`, `remoteComposerFor`. **`ComposerFactory` is `func(proj compose.Project) runner.Composer`** so it can branch on `proj.Unmanaged`. **`projUpdatesCacheKey(proj)` is the ONE key producer** and `updatesCacheKey()` is literally `projUpdatesCacheKey(m.currentProject())`, so a grouped scan and a drilled one cannot file the same project under two entries. The key is `ConfigDir + "|" + serverName` with an `"unmanaged|"` prefix taken from `proj.Unmanaged` (`currentProject()` supplies that from `m.readOnly()`, never a parallel `projUnmanaged bool` field) — an unmanaged row's empty `ConfigDir` otherwise collides with the local fast track's bare `"|"`. A NON-unmanaged project with an empty `ConfigDir` (a `buildSvcGroups` leftover group) falls back to `"name:" + proj.Name`, or two of them would share one slot and a `U` scan on one would paint the other's glyphs.

**Unmanaged containers — the read-only UI contract**: `ReadOnlyComposer` is declared in `tui` and type-asserted on the concrete composer; it needs a **named** `ReadOnlyComposer() bool` method — never a method-less marker; `Model.readOnly()` is nil-safe. `d`, `r`, `s`, `R`, `c`, `space` and `a` all early-return, **each calling `fixSvcOffset()` first**. `c` and `R` need an **explicit** gate anyway. **Nothing advertises a no-op**: `containerHelpLines()` returns a read-only idle pair (`line1` drops `space toggle`, `line2` = `l logs • x exec`) read by both `containerFooterLines()` and `containerFooter()`; the line count **must stay state-independent** and every rendered line is clamped with `clampToWidth`. `helpGroupsFor` returns `readOnlyContainerGroups(canGoBack)` when `helpContext.readOnly`: SELECT and OPERATE go whole and `c` leaves INSPECT, but **`enter` MOVES into INSPECT** (`confirm the exec prompt`). FIND/INSPECT come from shared `findGroup()`/`inspectGroup(readOnly bool)` — add a key once, not twice. Drift pins run **per variant, never a union** — extend `TestHelpGroups_NamesEveryBoundKey` and its `ReadOnly` twin. The title drops the `(n/m selected)` counter and rows the `[ ]`/`[x]` checkbox, so the caption pad must be **7**, not **10**. **The update check must NOT fire automatically here**: all THREE entry points — `maybeRefreshUpdatesCmd()`, the `statusMsg` self-heal and `Init()`'s fast path — consult `autoUpdatesAllowed()` (= `!m.readOnly() && !m.grouped`), leaving `U` the only trigger. `NewModel` sets `updateInFlight = m.autoUpdatesAllowed()`, never a flat `true`. Both gated paths also **clear `m.updatesErr` once the cache entry has expired** (the `statusMsg` clear sits BEFORE its `fixSvcOffset()`). Full rationale and failure modes: `docs/architecture/unmanaged-containers.md`.

## Adding New Operations

1. Add constant to `Operation` enum in `internal/runner/runner.go`
2. Update `String()`, `Steps()`, and `buildSteps()` in the same file
3. Add action key case in `screenSelectContainers` handleKey in `internal/tui/app.go`, AND name the key in the matching group in `helpGroupsFor()` (`internal/tui/help.go`) — the `?` overlay is the only place the full key table is advertised now that the footer carries 6 tokens
4. Gate the new key on `m.readOnly()` with an early return, and leave it OUT of `readOnlyContainerGroups()` (`internal/tui/help.go`). Every operation is a compose pipeline, and an unmanaged container has no compose file, so a new op is by definition inert on the read-only screen — a key the read-only table still named would advertise a no-op, which is the failure that whole variant exists to prevent
4b. **Route the key through the GROUPED path, or it writes a nil deref.** Grouped mode holds `m.composer == nil` BY DESIGN (see the multi-project paragraphs), so a new op key must not touch the composer at press time: arm through `armOperation` / `partitionSelection()`, bind with `bindProjComposer(batches[0].proj)` at the confirming `enter`, and call `unbindGroupedComposer()` on EVERY early return between the two. The grouped help table needs no second hand-maintained key list — `TestHelpGroups_GroupedNamesTheSameKeys` (`internal/tui/help_test.go`) compares the grouped token set against the writable one in BOTH directions and fails the moment they drift. Add the grouped dispatch test alongside the drilled one; a key that works drilled and panics grouped is the shape this step exists to prevent
5. Add CLI subcommand in `cmd/deploy.go` and register in `cmd/root.go`
6. Tests: runner sequence test, cmd subcommand/flag tests, TUI action key + confirmation tests, plus the expected-key set in `TestHelpGroups_NamesEveryBoundKey` (`internal/tui/help_test.go`), which fails in both directions when the help table drifts from the dispatch. If the operation is a WRITE, add the key to the table in `TestReadOnly_GatesWriteKeys` (`internal/tui/app_test.go`) so the read-only screen is pinned to refuse the gate step 4 added. The read-only help pin needs NO edit for a gated key — it stays out of `TestHelpGroups_ReadOnlyNamesEveryBoundKey`'s hand-maintained bound set, and that test's names-nothing-unbound direction is what catches a table that advertises it anyway.

If the new operation needs an op-specific pre-run step (like Rollback's snapshot read + digest-pin prep), don't fork `runOperation` — route through `runOperationWithPrep(ctx, op, all, containers, prep)`. The `prep func(context.Context, runner.Composer) (func(), error)` runs AFTER the composer is built and BEFORE the pipeline (so it can apply refusal rules and configure the composer, e.g. set `ExtraComposeFiles`); its returned cleanup is deferred function-scoped, so it runs after the wait phase but before the remote SSH teardown (LIFO). deploy/restart/stop pass a nil prep and keep the original path. Rollback lives in its own `cmd/rollback.go` (see "Adding New CLI Subcommands") but is a deliberate reuse of this deploy machinery, not a fresh subcommand skeleton.

## Adding New CLI Subcommands

See `cmd/list.go`, `cmd/logs.go`, and `cmd/exec.go` for the pattern. Each subcommand:
1. Creates a `*cobra.Command` in its own `new*Cmd()` function
2. At the top of the `Run*` function, calls `checkRemoteMutex(serverName, sshTarget, identityFile)` to enforce the `--server`/`--ssh` mutex and the `--identity requires --ssh` rule (it must run before `os.Getwd()` and `signal.NotifyContext` so spurious setup doesn't run when the flags conflict)
3. Branches in this order: `sshTarget != ""` → `resolveSSHRemote(ctx, sshTarget, projectDir, identityFile, <factoryVar>)` (passing the subcommand's own injectable factory); else `serverName != ""` → load config, `FindServer()`, create `RemoteCompose`, `Connect()`, defer `Close()`, `Detect()`; else fall back to local `compose.New(dir)`
4. Is registered in `cmd/root.go` via `rootCmd.AddCommand()`

`cmd/skill.go` (the `skill install|show|uninstall` subcommand, see "Agent Skill distribution" below) is a deliberate exception to this pattern — it operates on local files only and has no `--server`/`--ssh`/`--project-dir`/remote wiring.

`cmd/rollback.go` (the `rollback` subcommand) is a second deliberate exception: rather than reimplementing the composer-branch skeleton, it reuses the deploy machinery via `runOperationWithPrep(ctx, runner.Rollback, …, rollbackPrep(…))` — the shared `runOperationWithPrep` already does the `checkRemoteMutex` → ssh/server/local branching, and `rollbackPrep` is the op-specific pre-run hook (snapshot read + refusal rules + digest-pin prep). See "Adding New Operations" for the prep-hook recipe.

## Agent Skill distribution (`cdeploy skill`)

**`skills/` package**: the repo-root `skills/` directory is BOTH the external-installer convention directory (so `npx skills add lexxzar/compose-deploy` and `gh skill install lexxzar/compose-deploy` find `skills/cdeploy/SKILL.md` on the default branch) AND a Go package holding the `//go:embed cdeploy` directive. `skills.FS` exposes the embedded tree; `skills.CanonicalSkill()` returns the raw, unstamped SKILL.md bytes — the single source of truth for the CLI, external installers, and verification, version-locked to the binary via `go:embed` (panics on a missing embed, since that is a build/packaging fault, not a runtime error to thread).

**`cdeploy skill install|show|uninstall <claude|codex|all>`** (`cmd/skill.go`): installs the embedded skill into agent skill directories. Targets resolve via `skillTargetDirs()`: claude → `~/.claude/skills/cdeploy` (also read by Cursor/OpenCode); codex → `~/.agents/skills/cdeploy` AND `$CODEX_HOME/skills/cdeploy` (default `~/.codex`; an EMPTY `$CODEX_HOME` is treated as unset because `t.Setenv` can set but never unset an env var); all → the deduped union. Dedupe (`resolveDedupeKey`) resolves symlinks on the deepest EXISTING ancestor of each candidate (the target dir usually does not exist yet, and `filepath.EvalSymlinks` errors on missing paths), then re-appends the not-yet-existing suffix, so two candidates pointing at the same physical directory through a symlink collapse to one write. Multi-path install/uninstall aggregate per-path outcomes — one failed destination never aborts the others, and any failure yields a non-zero exit. Per-agent pickup notes are printed to stdout after a successful install. `show` writes the raw unstamped canonical via `cmd.OutOrStdout()` (NOT `os.Stdout` — testable with `cmd.SetOut(&buf)`); it also enables `cdeploy skill show > .claude/skills/cdeploy/SKILL.md` for project-level placement.

**Stamp/hash ownership model**: install never trusts a file it did not write. `renderSkill(canonical, version)` injects a metadata block — `metadata:` header + `cdeploy-version` + `cdeploy-content-hash: sha256(canonical)` — immediately before the frontmatter's CLOSING `---` (the second `---`, found via `frontmatterCloseOffset`; never a bare `---` in the markdown body), so the frontmatter stays the first bytes of the file (Gemini silently skips otherwise). `stripOwned()` removes exactly that block, giving the round-trip invariant `stripOwned(renderSkill(canonical, v)) == canonical` as literal byte-equality; the stamped hash is therefore simply `sha256(canonical)`, no self-reference. `verifySkillFile(onDisk)` answers ONLY "is this file consistent with its OWN stamp?" → `intact` / `modified` / `unstamped` (stripOwned → sha256 → compare to the recorded hash). The install decision needs a SECOND, distinct check — `bytes.Equal(stripOwned(onDisk), canonical)` against THIS binary's canonical bytes — to reach `unchanged` vs stamp-refresh vs updated; without both checks the `unchanged` state is unreachable. Modified or unstamped files (e.g. a copy dropped by `npx skills`) are refused by both install and uninstall without `--force`; uninstall removes only the stamped `SKILL.md`, then the `cdeploy/` dir only when it is empty (never a recursive delete). Dev builds stamp `cdeploy-version: dev` — freshness keys on the content hash, not the version string.

**SKILL.md content test pins** (`skills/skills_test.go`): future edits to `skills/cdeploy/SKILL.md` MUST keep these satisfied — frontmatter is the very first bytes (`---\n` fence with a closing `---`), `name: cdeploy` (matches the directory AND the `^[a-z0-9]+(-[a-z0-9]+)*$` regex), `description` non-empty and ≤1024 chars (and naming both ops and setup triggers: deploy/servers.yml/ssh), under 500 lines, and — load-bearing — NO `metadata:` key in the canonical frontmatter. That last pin is what keeps block insertion/removal trivial: the install-time renderer owns the `metadata:` block and `stripOwned` must round-trip back to exactly the canonical bytes, so a hand-authored `metadata:` key would break the byte-equality invariant.

## Package Coupling

The TUI package depends on `runner.Composer` (interface), not `compose.Compose` or `compose.RemoteCompose` (concrete). For operations that need to create a `Composer` at runtime (drilling into a group, or an action key binding the cursor row's project), use a `ComposerFactory` callback injected from `cmd/` — this keeps `tui` decoupled from `compose`. The factory takes the whole `compose.Project`, not a directory string, so it can branch on `proj.Unmanaged` and return the read-only `compose.HostContainers` for the synthetic `(unmanaged)` group. That same branch is how the grouped host view reaches its host-wide seam: `composerFactory(compose.Project{Unmanaged: true})` type-asserted to `HostGrouper`, so no signature had to widen. Similarly, `ProjectLoader` and `ConnectCallback` are injected by `cmd/` for remote server support. The `compose` package has the `HasComposeFile` package-level function for local compose file detection; project discovery (`ListProjects`) is a method on `Compose`/`RemoteCompose` requiring `Detect()` first. The `ConfigProvider` and `ExecProvider` interfaces are defined in `tui` (not `runner`) because they return `*exec.Cmd` and are TUI-only; the TUI type-asserts `composer.(ConfigProvider)` and `composer.(ExecProvider)` at runtime — no separate factory or wiring needed. `ReadOnlyComposer` is the same shape and the same reason: only `compose.HostContainers` implements it, and a composer that omits it renders the normal writable screen. `Inspector` is the same shape with the reach inverted — ALL THREE composers implement it, so the `i` key is live on every container screen and the type assert exists for test mocks rather than for a capability split. `UpdateDetailer` is `Inspector`'s twin: all three composers implement it, it is asserted the same way, and a composer that omits it simply renders no update rows. `HostGrouper` (one method, `GroupedHost`) is the same shape with the narrowest reach: only `compose.HostContainers` implements it, and a factory that cannot produce one yields a grouped screen with projects but no status — not an error.
