## `?` key-reference overlay

The `?` key opens a full-screen key list for the current screen. It is a flag (`helpOpen bool` on Model, beside `quitting`), not a screen constant of its own — a screen would drag the overlay into the back-navigation chain, the `clearSearch()` departure checklist, and the session-counter discipline. `View()` checks `helpOpen` immediately after the `quitting` check and returns `viewHelp()`, so the overlay replaces the whole screen exactly like `viewQuitConfirm()` and is invisible to `svcVisibleCount()` and the reserved-bar math. The renderer lives in its own file, `internal/tui/help.go`; the `helpOpen` field, the `View()` check, the two `handleKey()` intercepts, the `confirmPromptArmed()`/`typingInInput()` key-dispatch predicates that gate them, and the `connectResultMsg`/`rollbackSnapshotMsg` clears are in `app.go` (`canGoBack()` and the footer helpers live there too, beside `viewSelectContainers`): `helpGroupsFor(s screen, hc helpContext) []helpGroup` is near-pure data (the four context bits travel in a named `helpContext{canGoBack, readOnly, grouped, phase}` rather than as adjacent same-typed parameters, which a call site could transpose silently) — a `helpGroup` is a title plus `helpEntry{keys, desc}` rows — and covers all 8 screens (`screenSelectProject` went with the project picker; the grouped host view is a MODE on `screenSelectContainers`, not a screen of its own); `Model.helpGroups()` is the renderer's entry point and supplies the four context bits from `Model.canGoBack()`, `Model.readOnly()`, `m.grouped` and `Model.progressPhase()`. **Group ORDER in `helpGroupsFor` is load-bearing**: `splitHelpGroups` cuts the slice sequentially, so LEAVE sits 4th of 6 on `screenSelectContainers`, 3rd of 4 in `readOnlyContainerGroups` and 3rd of 4 on `screenLogs` purely to land it in the left column — reordering a group for readability changes the rendered layout. **The LEAVE group is conditional, not literal**: on `screenSelectContainers` `q` QUITS and `esc` is a no-op whenever `canGoBack()` is false — the GROUPED host view with no servers and no config file, or a DRILLED screen with `!drilledFromHost` (a standalone `cdeploy` launched in a directory holding a compose file) — so `leaveGroup(false)` renders `q quit` instead of `q esc → back`. `Model.canGoBack()` is the single predicate behind both that group AND the footer's `back` label, so the overlay can never contradict the footer rendered a moment earlier (pinned by `TestHelpGroups_LeaveGroupMatchesFooter`). **`screenProgress` is conditional for the same reason, on a THREE-state phase rather than a bool**: `esc` changes MEANING across the operation's life — while the pipeline runs it CANCELS the operation (`q` and `ctrl+c` are no-ops there), during the health gate `enter` skips the wait (and, mid-sequence, releases the next batch) while `q`/`esc` STOP the sequence, and once finished `q`/`esc` navigate back. `progressGroups(phase, midSequence)` renders one table per phase and `Model.progressPhase()` resolves it in the SAME order as `viewProgress()`'s footer switch — `waiting` FIRST. **The waiting-first ORDER is unchanged but its REASON is not "waiting implies done"**, which stopped being true when the per-batch health gate landed: a mid-sequence gate opens with `done` FALSE (only the last batch's pipeline sets it), the last batch's gate opens with `done` set, and a gate can also be open with `failed` set, so only the waiting-first order names `esc` correctly in all three (`internal/tui/help.go:51-56` carries the same wording). The WAIT table is truthful in every one of them: `q` and `ctrl+c` are no-ops only while a pipeline is RUNNING (`!done && !failed && !waiting`), so during a gate `ctrl+c  quit` does what it says, mid-sequence as well as on the last batch. **The WAIT group is the one table that also varies WITHIN a phase**, on `helpContext.midSequence` (= `Model.midSequence()` = `batchIdx+1 < len(batches)`): with a batch still to come the two keys have OPPOSITE consequences, so it renders TWO rows (`enter  skip health wait, start the next project` / `q esc  stop, skip the projects left`) rather than one under-describing `skip health wait` over a key that launched a whole project's pipeline. With nothing left to release both do the same thing and the table says so on one row (`enter q esc  skip health wait`), so `enter` is named in BOTH variants and the drift pin needs no midSequence union to see it. All three tables name the same three keys, so the drift pin holds whichever phase it samples; `helpKeyTokens(s, canGoBack, readOnly)` unions over `allProgressPhases` anyway, and `TestHelpGroups_ProgressPhases` (what the overlay SAYS) plus `TestProgressPhases_BehaviourMatchesLabels` (what the keys DO) pin the two halves against each other. A static progress table advertised `esc skip health wait` and `ctrl+c quit` mid-pipeline — wrong in the riskiest phase, and the finding an external review caught. `screenName(s screen)` labels the title (`cdeploy > keys > services`, the same `>` breadcrumb separator every other screen uses); `splitHelpGroups` balances the groups across two columns by rendered height (`helpGroupLines` = entries + title + separator), `helpColumnRows` aligns descriptions on the widest key, and `layoutHelpColumns(groups, width)` joins the two columns with `lipgloss.JoinHorizontal`, falls back to ONE column when the two-column render exceeds `width`, then clamps every row with `clampToWidth` — the same never-wrap guarantee as `searchBarLine()`/`logBarLine()`. **The overlay is budgeted against `m.height` too**: the single-column fallback stacks the container table to 24 rows, and bubbletea's renderer keeps only the LAST `height` lines, so without a budget the title and the first groups scroll off a 24-line terminal with no way back (the overlay swallows every scroll key). `budgetHelpRows(rows, budget, width)` truncates to `m.height` minus the title/hint chrome and spends the last row on a `▼ N more · resize for the rest` marker; a budget below 1 (a pane too short for the chrome alone) is clamped up to 1 rather than passed through, the same floor `svcVisibleCount()` applies, and the unknown-height case (`m.height == 0`, tests) is handled by `viewHelp()` skipping the helper entirely. Because of that floor the overlay bottoms out at FIVE physical lines (title 2 + one body row + hint 2), so a pane of height 1-4 still over-renders — accepted, and pinned by `TestViewHelp_MinimumHeightFloor` rather than left undefined: the renderer keeps the LAST lines, so what such a pane drops is the title while the close hint (the only way out) survives. **Truncation ORDER is the discoverability contract**: the footer carries six tokens — `space toggle`, the back key and `? keys` on line1, `d deploy`, `r restart` and `l logs` on line2, with the grouped host view swapping `space toggle` → `space fold/select` and `l logs` → `enter drill in`, which demotes `l` to the overlay there too — so every other key on the container screen exists NOWHERE else: `a all`, `/ search`, `n N`, `R rollback`, `c config`, `x exec`, `i inspect` and `U check updates`. `helpGroup.actions bool` marks the groups whose keys are advertised nowhere else — on the container screen that is FIND, SELECT, OPERATE and INSPECT, leaving only MOVE (arrows) and LEAVE unflagged — and `singleColumnOrder()` (applied ONLY in the single-column fallback, where the budget actually bites) emits the flagged groups first, so what falls off the bottom is the guessable navigation instead. FIND is split out of MOVE for exactly this reason: `/` and `n N` were riding along with the arrow keys in an unflagged group. The fallback also renders through `helpStackedRows()`, which drops the blank line BETWEEN groups (`helpColumnRows()` keeps it for the two-column layout): that takes the container table from 30 rows to 25, and 25 is what makes all 19 action rows fit the 20 a 24-line pane keeps. Truncation table at width < 65 (below the two-column threshold; re-measured when `i inspect` became the 19th action row, and identical at widths 30/40/50/59 and 64 — below the threshold the width does not change the row count): height >= 24 keeps everything, 23 loses `U check updates`, 22 loses `x exec` too, 21 loses `c config` too, 20 loses `i inspect` too, 19 loses `l logs` too. Every threshold moved up by exactly one when `i` landed, so a 20th action row moves them all again — re-measure rather than extrapolate. The read-only variant stacks to 16 rows and still fits every action row at every height >= 19, so it never truncates an action key. **That table is the DRILLED variant, and the GROUPED one is UNMEASURED and UNTESTED.** `selectGroup(grouped=true)` gives SELECT a third row (`enter  drill into the project on a group header`), and SELECT carries the `actions` flag — so the grouped table holds one action row more than the drilled table every threshold above was measured against, which by the sentence above moves all of them. Nothing pins it: both truncation tests build `drilledFromHost: true` models (`TestViewHelp_NarrowTerminalKeepsActionKeys` at height 24, `TestViewHelp_InspectSurvivesTheFirstTruncation` at 23), so the grouped variant has neither a measured threshold row nor a sacrifice-order pin. Measure it before quoting a number for grouped mode; do not extrapolate one from the drilled column. Pinned by `TestViewHelp_NarrowTerminalKeepsActionKeys` (widths 30/40/50/59 at height 24, want-list = the full nowhere-else set), by `TestViewHelp_InspectSurvivesTheFirstTruncation` (height 23, the FIRST notch where a key must go: `inspect` survives and `check updates` is the one sacrificed — height 24 fits everything, so the insert position of `{"i", "inspect"}` in `inspectGroup` is unguarded without a test that samples the notch) and by the ordering assertion in `TestLayoutHelpColumns_SingleColumnFallback`, which pins the CONTRACT against the RENDERED fallback (every `actions` group appears above every non-`actions` one, over whatever groups the screen declares) rather than a hard-coded group list. A short-AND-wide pane (e.g. 120x14) still truncates both columns' tails; the `▼ N more` marker names the remedy. **`viewHelp()` must NOT end its string in a newline, and the height test must NOT trim one.** bubbletea v1.3.10 hands `View()` straight to `standardRenderer.write()`, and `flush()` does a bare `strings.Split(r.buf.String(), "\n")` with NO `TrimSuffix` before keeping the last `r.height` elements — so a trailing newline is a whole extra element, the overlay renders at `m.height + 1`, and the renderer drops the title: the exact failure the budget exists to prevent. `viewSelectContainers()` and `viewLogs()` end without one for the same reason. `TestViewHelp_FitsShortTerminal` therefore splits the RAW `m.View()`, and `TestViewHelp_NoTrailingNewline` pins the invariant directly so a regression names the cause rather than the symptom. Deliberately NOT scrollable — the overlay is a flag over the current screen, not a screen with its own viewport state; widening past the two-column threshold or a taller pane brings the rest back. `helpGroupTitleStyle` and `helpKeyStyle` live in `styles.go`. No composer call and no goroutine, so the overlay needs no session counter and no stale-message guard. **Intercept order in `handleKey()` is load-bearing**: (1) the `quitting` intercept, (2) the `helpOpen` swallow block, (3) the `?` open block, (4) the `q`→`esc` rewrite. The swallow block MUST precede the open block — otherwise a `?` pressed while the overlay is open would re-open it and never close it. Close keys are `?`, `esc` and `q`; every other key is swallowed, so `d` cannot arm a deploy from behind the overlay. **`ctrl+c` clears `helpOpen` and FALLS THROUGH** instead of returning: the fall-through makes each screen's existing `ctrl+c` semantics apply unchanged — the plain local quit, the remote disconnect prompt, and the mid-progress no-op on `screenProgress` while `!done && !failed && !waiting` (the gate is escapable, the running pipeline is not). The rationale is NOT "`ctrl+c` is a hard exit from any screen"; that rule has the mid-progress exception, and the fall-through is what preserves it. The open block is additionally gated on `!m.confirmPromptArmed()`: `?` at an armed destructive prompt does nothing, because the overlay would hide the prompt and the single `esc` that closes the overlay would leave it armed underneath — a two-stage `esc` nobody expects (the `q` rewrite makes the same call). **`confirmPromptArmed()` is screen-SCOPED and that is load-bearing** (`screenSelectContainers` → `m.confirming`, `screenSettingsList` → `m.settingsDelete`, else false): `confirming` is armed on the container screen and `enterProgress()` does NOT clear it (only the `esc` back-nav out of `screenProgress` does), so a flat `!m.confirming` gate keeps the overlay shut for the ENTIRE life of the progress screen — hiding the phase table above, including the running phase's destructive `esc`. A `Model{screen: screenProgress}` literal cannot catch that regression; `TestHelpOverlay_OpensOnProgress` drives the real `d` → `enter` → `?` sequence instead. **Two message handlers clear `m.helpOpen` themselves.** `connectResultMsg` clears it for BOTH branches (above the `if msg.err != nil`): the SUCCESS branch is the one that reassigns `m.screen` (through `enterGroupedContainers()`, to the grouped host view), which an open overlay would ride into with a stale key table; the error branch clears alongside `quitting`/`clearSearch`/`clearWaitState` as uniform departure-site cleanup. Neither is reachable with the overlay open today (the connect runs through `tea.ExecProcess`, which suspends key input, and the overlay swallows the `enter` that starts a connect), so this is defence, not a live path. `rollbackSnapshotMsg` IS live: it is the one confirmation armed by a message rather than a key, so the `?` open gate never saw it — press `R`, press `?` while the async `ReadSnapshot`+`ListServices` fetch is in flight (seconds over SSH), and the rollback prompt would arm behind the overlay. It sets `m.helpOpen = false` next to `m.confirming = true`. Any future handler that arms a confirmation must do the same. **`typingInInput()` duplication rule**: the helper reports whether an open text input is capturing raw runes (`screenSelectContainers`: `m.searching`; `screenLogs`: `m.logFiltering || m.logSearching`; `screenSettingsForm`: `m.settingsField < 4` — fields 0-3 are textinputs, 4 is the color picker; the `< 4` form matches the surrounding code and is safe for out-of-range values, unlike `!= 4`). It is load-bearing because `?` is a regex metacharacter: with `ctrl+r` regex mode on, a user who types `(?:web|db)` into the log filter must get a filter, not a help overlay (pinned by `TestHelpOverlay_RegexFilterAcceptsQuestionMark`). The `q`→`esc` rewrite reads the SAME helper (`if key == "q" && !m.typingInInput()`), so **a new screen that opens a text input needs one case in `typingInInput()` and nothing else**. One exception the helper does NOT cover: the `helpOpen` swallow block runs BEFORE it, so while the overlay is up `q` closes the overlay even on a screen where `q` would otherwise be typed into an open input — the input is not visible behind the overlay. `TestHelpGroups_NamesEveryBoundKey` is the drift pin, and it runs BOTH directions: the help table must name every key that screen's `handleKey` case binds (against a hand-maintained expected set), and it must not name a key the screen does not bind — the likelier drift, where a binding is removed or renamed in `app.go` and the table keeps promising it. `TestAllScreens_Complete` pins the `allScreens` list against the contiguous `screen` iota so a new screen cannot silently skip every table test — but only because its bound now anchors to the LAST constant (`int(screenInspect) + 1`). **Recorded residual**: it used to read `int(screenSettingsForm) + 1`, which made that promise false. `screenInspect` was appended AFTER `screenSettingsForm`, so `want` stayed 8 and adding the constant without listing it in `allScreens` left the whole suite green, while the six tests that iterate the slice (`TestHelpGroups_EveryScreen`, `TestHelpGroups_NamesEveryBoundKey`, `TestViewHelp_FitsShortTerminal`, `TestViewHelp_MinimumHeightFloor`, `TestViewHelp_NoTrailingNewline`, `TestViewHelp_NeverExceedsWidth`) silently skipped the new screen. Move the bound to the new last constant with every screen added, or the hole reopens; the screen tax is developer discipline, not a failing test. A static help table that drifts from the dispatch is this feature's standard failure mode — extend the expected set whenever you bind a new key. It runs the standalone (`canGoBack == false`) variant in the names-nothing-unbound direction only: `esc` stays bound on a standalone container screen (it clears a committed search) but `leaveGroup(false)` must not advertise it as a way out. **A key bound only in a sub-state needs a description that NAMES that sub-state.** The pin forces every bound key into the table, but the overlay can only be opened from the idle state (the gate refuses at an armed prompt, and `?` types literally into an open input), so a bare label would advertise a no-op. `enter` on the container screen is bound only inside the `confirming` and `searching` blocks — it therefore reads `enter  confirm the prompt` under OPERATE, not `enter  confirm` under SELECT. Same shape as `enter  commit query` on `screenLogs` and `y n  confirm / cancel delete` on `screenSettingsList`.

## Container footer and the one-line width guard

two paired methods in `app.go`, beside `viewSelectContainers()`. `Model.containerFooter() string` renders the footer; `Model.containerFooterLines() int` reports how many physical lines it occupies. `viewSelectContainers()` writes the text and `svcVisibleCount()` reserves `2 + containerFooterLines()`, and `containerFooter()` pads every state out to that same count, so the render and the height math cannot drift — a divergence would miscount visible rows and let the list overflow the terminal. `containerHelpLines()` holds the two idle base strings (and the `back` label via `canGoBack()`); both methods read it, so the count is always measured against the footer that is actually drawn. It replaced the old `containerHelpLine2` const, which could no longer be a const once `back` had to be interpolated. `line1` is `space toggle • {back} • ? keys` (36 cells) and `line2` is `d deploy • r restart • l logs` (35 cells). A read-only composer gets a different idle pair — `{back} • ? keys` and `l logs • x exec`, 19 cells each and 41 joined — so both the render and the height math follow the variant through that one helper. **There are THREE pairs, not two**: the GROUPED host view gets `space fold/select • {back} • ? keys` (41 cells) and `enter drill in • d deploy • r restart` (43). `space` names both meanings because it has both there, and a group header is the row only grouped mode has, so `enter drill in` earns the slot `l logs` holds on the drilled screen — `l` keeps its home in the `?` overlay. The grouped pair joins to 87 cells, so unlike the other two it does NOT fit one line at 80 columns (the guard needs 89) and the grouped list reserves the second footer row there. `TestContainerFooterReservation`, `TestContainerFooter_AdvertisesOnlyWorkingKeys` and `TestContainerFooter_RendersOneLineAtEighty` all sweep the read-only dimension too, but only the read-only and `drilledFromHost` ones — the grouped row count is swept separately by `TestContainerFooterReservation_Grouped`. **The footer must advertise only keys the current state actually binds**, which splits the three search states two ways. *Committed* (`searchQuery != "" && !searching`): `line2` is replaced wholesale with `n/N cycle • esc clear`, but `q` and `?` still work — so `back` and `? keys` have to live in `line1` or they would vanish in exactly the state where the overlay matters most, `/ search` having already left the footer. *Typing* (`m.searching`): the search intercept binds ONLY `enter`, `esc` and `ctrl+c`; every other key, `space`, `q` and `?` included, lands in the query as a literal rune (see `docs/architecture/tui-logs-and-search.md`, "Container search"). Keeping `line1` there would name three dead keys, so `containerFooter()` swaps the whole footer for `enter jump • esc cancel` instead — `line1`'s always-visible role is scoped to the committed state, not to all three. **The line COUNT is state-independent**: `containerFooterLines()` decides it from the idle pair alone (the widest of the three on the WRITE path; the read-only variant inverts that, see the clamp below), before any substitution, and the shorter states are padded back out to it — a trailing `\n` for the typing footer, and a trailing `\n` on the confirm prompt in `viewSelectContainers`. Without that, a one-line typing footer under a wrapped two-line idle footer grew the service list by a row below ~76 columns and re-flowed it under the cursor, which is exactly what the reserved-bar design exists to prevent (`TestContainerFooterReservation` now compares the VISIBLE row count across idle/searching/committed/confirming at every width 40-180, not just the total physical height, which `svcVisibleCount` keeps constant by absorbing the delta). `TestContainerFooter_AdvertisesOnlyWorkingKeys` pins both directions (the tokens each state must show, and the ones the typing state must NOT). The full container key table lives in the `?` overlay — 19 action rows on the drilled screen, 20 in grouped mode (see the truncation note above). **`i inspect` is deliberately NOT a footer token, and that is a recorded residual, not an oversight**: a seventh token would re-open the 80-column guarantee and the width 40-180 sweep `TestContainerFooterReservation` runs, so `i` lives in the overlay only, exactly like `c`, `x`, `U` and `R` — the accepted cost is that inspect is discoverable through `?` alone. The one-line-versus-two guard measures `m.width >= ansi.StringWidth(oneLine)+2`, NOT `len(oneLine)+2`: each `•` is 3 bytes but ONE display cell, so the byte form over-counts by 2 per separator and split a footer that in fact fits (it split anywhere from 152 to 173 columns). Do not reintroduce `len()`. Because the count is decided from the idle pair, a substitution WIDER than the idle `line2` can overrun a width the idle pair fit — the read-only pair does exactly that (idle `line2` 19 cells against the committed `n/N cycle • esc clear` at 25, overrunning at widths 43-46), so `containerFooter()` clamps every rendered line with `clampToWidth` rather than widening the count, which would re-flow the list (`TestContainerFooter_NeverExceedsWidth`). The one-line footer measures 74 cells when idle, 64 with a committed search and 27 while a search is typing, so it fits an 80-column terminal in every state and the service list keeps the row the second line used to cost (pinned by `TestContainerFooter_RendersOneLineAtEighty` and `TestSvcVisibleCount_GainsRowVersusOldFooter`; `TestContainerFooterReservation` sweeps every width from 40 to 180 asserting rendered rows == `svcVisibleCount()`).

## `q` as back key on nested screens

A pre-dispatch block at the top of `handleKey()` (after the `quitting` intercept and the two `?`-overlay intercepts) rewrites `q` to `esc` on nested screens, so `q` behaves like a back-nav alias (lazygit/k9s convention). The existing `esc` handlers do the cleanup — no duplication. `q` quits directly only on root screens: (1) `screenSelectServer` always quits; (2) `screenSelectContainers` quits when `!m.canGoBack() && !m.confirming`. **`Model.canGoBack()` carries the whole of rule (2) and splits by MODE**: the GROUPED host view sits where the project picker used to, directly under the server picker, so it reads `len(m.servers) > 0 || m.config != nil` — truly standalone (no config file, no servers) makes it a root; the DRILLED screen reads `m.drilledFromHost`, the RENAMED `showPicker`. The rename is the point: no predicate derivable from the composer, the factory or the group list separates a drill-in (parent = the host view) from a standalone `cdeploy` launched in a directory holding a compose file (a ROOT, where `q` quits and `esc` does nothing), so the entry sites record it. Deriving it from `len(servers) > 0 || config != nil` breaks drill-in on a standalone host; making the root non-root turns `q` from "quit" into "drill out" on the primary local flow. The extra `!m.confirming` term has no `canGoBack` analogue: an armed prompt takes `q` as "cancel" (the `esc` handler clears it) even on a root screen. `screenProgress` is a no-op for `q` while `!done && !failed && !waiting` (must not cancel an in-flight operation; `ctrl+c` is a no-op in the same window). A health gate is NOT in that window — `q` there rewrites to `esc`, which STOPS the sequence mid-way (and is the plain skip on the last batch), and `ctrl+c` quits — which is what makes the overlay's WAIT table truthful on a mid-sequence batch as well as on the last one. The whole rewrite is skipped when `m.typingInInput()` — the container search bar, the log filter/search bars, and the settings-form text fields (`settingsField` 0–3) — so `q` reaches the open input as a literal character and server names like `qa-prod` stay typeable; with the settings-form color picker focused (`settingsField == 4`, no textinput active) the guard is false and `q` is rewritten to `esc`. That one guard replaced three per-screen carve-outs, so `screenLogs` and `screenSettingsForm` now fall into the `default: key = "esc"` case. `ctrl+c` is unchanged — it still goes through `tryQuit()` and triggers the disconnect prompt on remote sessions. Help footers on nested screens show `q back`; root screens show `q quit`. Because `q` is rewritten to `esc` before per-screen dispatch, the cleanup paths in the "Backward-navigation state cleanup" paragraph of `CLAUDE.md` cover both keys — do not add parallel `q` handlers.
