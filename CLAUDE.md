# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Test Commands

```bash
go build -o cdeploy .          # Build binary
go test ./...                   # Run all tests
go test ./internal/runner/ -v   # Run tests for a single package
go test ./... -count=1          # Run all tests uncached
go mod tidy                     # After adding/removing imports
```

The root command launches a Bubble Tea TUI requiring a TTY, so `cmd/root_test.go` tests flag registration and subcommand structure rather than executing the root command directly.

## Architecture

cdeploy is a dual-mode tool: interactive TUI (no args) or non-interactive CLI (`deploy`/`restart`/`stop`/`list`/`logs`/`exec` subcommands). Both modes share the same core through a three-layer architecture:

```
cmd/ (Cobra)  →  runner (pipeline orchestrator)  →  compose (docker CLI wrapper)
tui/ (Bubble Tea) ↗
```

Seven subsystems carry their full rationale, failure modes and test pins in `docs/architecture/`; the paragraphs below carry the rules only. **Read the matching file before you change one of them** — each rule there exists because it was violated once.

- `docs/architecture/tui-help-overlay.md` — the `?` overlay, the container footer, the `q` back key
- `docs/architecture/tui-logs-and-search.md` — container search, log streaming, formatting, filter and search
- `docs/architecture/tui-inspect-screen.md` — the `i` inspect screen and `internal/compose/inspect.go`
- `docs/architecture/wait-snapshots-rollback.md` — the `--wait` gate, deploy snapshots, the rollback pipeline
- `docs/architecture/update-detection.md` — the `⇧` glyph, digest comparison, failure cascades, the TUI cache
- `docs/architecture/unmanaged-containers.md` — `HostContainers`, the `(unmanaged)` group, the read-only UI contract
- `docs/architecture/tui-multi-project.md` — the grouped host view, `svcKey`, batch sequencing, grouped updates

**Key abstraction**: `runner.Composer` interface (defined in `internal/runner/runner.go`, implemented by `internal/compose/compose.go` for local, `internal/compose/remote.go` for SSH, and `internal/compose/hostcontainers.go` for the read-only unmanaged-container view). This is the seam between the orchestrator and Docker — the runner is testable with mock implementations. Methods: `Stop`, `Remove`, `Pull`, `Create`, `Start`, `ListServices`, `ContainerStatus`, `ContainerStats`, `CheckUpdates`, `Logs`. When widening this interface, every mock implementation must add a matching no-op — there are mocks in `internal/runner/`, `internal/tui/app_test.go` (`mockComposer`), `cmd/deploy_test.go` (`opMockComposer`), and `cmd/list_test.go` (`mockComposer`, `mockComposerStatusErr`); a fast `grep -rn "func.*Composer.*ListServices" ./...` enumerates them.

**Event system**: `runner.Run()` sends `StepEvent` structs through a channel. The CLI consumer (`cmd/deploy.go:runOperation`) prints colored status lines. The TUI consumer (`internal/tui/app.go`) drives a Bubble Tea model through `tea.Cmd` that reads from the channel.

**TUI state machine**: Eight screens: `screenSelectServer` → `screenSelectContainers` → `screenProgress` (for operations), `screenLogs` (for log viewing), `screenConfig` (for config viewing/editing), or `screenInspect` (for the read-only container inspect view), plus `screenSettingsList`/`screenSettingsForm`. **There is NO project-select screen** — the container screen's GROUPED mode replaced it (`m.grouped`; every compose project on the host is a foldable group plus the synthetic `(unmanaged)` one), and picking a project is a drill-in state change on the same screen rather than a screen transition — see the six `Multi-project host view — …` paragraphs below. The server screen is shown whenever servers are configured in `~/.cdeploy/servers.yml`; selecting "Local" fast-tracks to the DRILLED single-project container screen if a local compose file exists, and lands on the grouped host view otherwise. The model is a flat struct with a `screen` field determining which view/update logic runs. Operations are triggered via action keys on the container screen (`r` restart, `d` deploy, `s` stop) which enter a confirmation sub-state (`confirming` bool + `pendingOp`) before proceeding. The `x` key execs into a running container interactively (enters confirmation with `pendingExec = true`, then shells out via `tea.ExecProcess`; shows warning if container is not running). The `l` key opens the log viewer for the cursor service without confirmation (read-only operation). The `c` key opens the config screen without confirmation (read-only by default). The `i` key opens the inspect screen for the cursor service, also without confirmation, and is the one container action key that is NOT gated on `m.readOnly()` — see the "Inspect screen" paragraph below. Back-navigation (`esc`, also aliased to `q` on nested screens — see "Exit confirmation for remote connections" below) resets downstream state; during confirmation, `esc` cancels without navigating back. The grouped host view is skipped entirely when the current directory contains a compose file and no servers are configured (backward compatible). `Compose.ListProjects()` discovers projects via `docker compose ls -a --format json`; both `ProjectLoader` literals in `cmd/root.go` are plain `ListProjects` and append NOTHING — that loader feeds `loadGroups()` and supplies the grouped screen's row ORDER, while the synthetic `(unmanaged)` group comes from `buildSvcGroups`'s leftover path off the host-wide `docker ps` the same refresh already made; see the three `Unmanaged containers — …` paragraphs below.

**Exit confirmation for remote connections**: `ctrl+c` is the hard-exit shortcut from any screen. When a remote SSH connection is active (`disconnectFunc != nil`), pressing `ctrl+c` shows a confirmation prompt instead of quitting immediately. The `quitting bool` field on Model gates a global intercept at the top of `handleKey()`: `y` quits, `n`/`esc` cancels, all other keys are swallowed. `View()` checks `quitting` first and renders a standalone confirmation screen via `viewQuitConfirm()` (`"Disconnect from {serverName}? (y/n)"`). The `tryQuit()` helper replaces direct `return m, tea.Quit` calls on all screens except `screenSelectServer` (which always quits immediately since no remote connection exists there). `quitting` is reset to `false` in `esc` back-navigation handlers that clear `disconnectFunc` and in the `entryLocal` handler. Local sessions (`disconnectFunc == nil`) bypass the prompt entirely — `tryQuit()` returns `tea.Quit` directly.

**`?` key-reference overlay**: `?` opens the screen's key list; a flag (`helpOpen bool`), **never a screen constant**. `helpGroupsFor(s, hc helpContext)` builds it; **group ORDER is load-bearing** (`splitHelpGroups` cuts sequentially). **A key or row added moves that variant's width/height thresholds and needs its drift pin extended**; `layoutHelpColumns`/`budgetHelpRows` clamp; **`viewHelp()` must NOT end in a newline**. **Intercept order is load-bearing**: `quitting`, `helpOpen` swallow, `?` open, `q`→`esc`; swallow BEFORE open; `ctrl+c` clears it and FALLS THROUGH. Open gated on `!m.typingInInput() && !m.confirmPromptArmed()` (screen-SCOPED; flat `!m.confirming` is WRONG), and a handler arming a confirmation must clear `helpOpen`. Full rationale, failure modes and test pins: `docs/architecture/tui-help-overlay.md`.

**Container footer and the one-line width guard**: `containerFooter()` and `containerFooterLines()` read `containerHelpLines()`; `svcVisibleCount()` reserves `2 + containerFooterLines()`, and the footer pads every state to the reserved count, advertising ONLY keys the state binds while **the line COUNT stays state-independent**. Guard with `ansi.StringWidth`, **never `len()`**; clamp with `clampToWidth`, never grow the count. Full rationale, failure modes and test pins: `docs/architecture/tui-help-overlay.md`.

**`q` as back key on nested screens**: the 4th `handleKey()` intercept rewrites `q` to `esc` on nested screens — **never add parallel `q` handlers**. `q` quits only on roots: `screenSelectServer`, and containers when `!m.canGoBack() && !m.confirming` (drilled `canGoBack()` IS `m.drilledFromHost`, so `q` quits when it is FALSE). `screenProgress` no-ops `q`/`ctrl+c` while `!done && !failed && !m.waiting`; skipped under `m.typingInInput()`. Full rationale, failure modes and test pins: `docs/architecture/tui-help-overlay.md`.

**Backward-navigation state cleanup**: When navigating backward (`esc`) or handling errors (e.g. `connectResultMsg` failure), all mutable callbacks (`composerFactory`, `projectLoader`, `disconnectFunc`) must be explicitly cleared or restored to their local defaults (`localFactory`, `localComposer`, `localProjectLoader`). Bubble Tea's value-type model means stale closures silently persist across screen transitions. Every new callback field added to Model needs corresponding cleanup in: (1) `backToServerScreen()` (`esc` from the grouped host view), (2) `enterGroupedContainers()` (`esc` drill-out from the drilled screen, and every other landing site), (3) `entryLocal` handler, (4) `connectResultMsg` error path. `drillIntoGroup()` is the fifth site for anything the drilled screen owns.

**Stale async message guard**: Goroutines spawned by a screen (e.g., `readLogChunk` for `screenLogs`) may deliver messages after the user has navigated away. Message handlers for screen-specific async messages (`logChunkMsg`, `logDoneMsg`) must check `m.screen` and discard stale messages — otherwise they will read nil fields cleared by `esc` cleanup and panic. A monotonic `logsSession` counter provides additional stale-message rejection. This pattern applies to any future screen that spawns background goroutines.

**Service list scrolling**: The container select screen uses `svcOffset` to track the first visible ROW (`m.svcEntries`, so a group header consumes one exactly like a service does) when the list exceeds terminal height. `svcVisibleCount()` calculates available lines: `m.height - headerLines - footerLines` (min 1), returning `len(m.svcEntries)` when `m.height == 0` for backward compat. Line counts account for lipgloss margins: `titleStyle` has `MarginBottom(1)` (adds a space-padded line), `helpStyle` has `MarginTop(1)` (adds a space-padded line), so header=3 (or 4 with column captions) and footer=3+ (not 2). A conditional column captions row ("Created", "Uptime") is rendered above the service list when any service has non-empty `Created` or `Uptime` data; `hasStatusColumns()` checks this and `svcVisibleCount()` adds 1 to `headerLines` accordingly. The captions use `descStyle` and are left-padded to align with data columns (10 + maxName offset). `fixSvcOffset()` ensures cursor visibility after any state change that affects visible count — cursor movement, window resize, confirming/warning state change. **`svcVisibleCount()` is ALSO the `pgup`/`pgdown` step**, so the two keys overshoot by design: a `pgdown` from the top of the window lands one row past its bottom edge and `fixSvcOffset()` scrolls the window by one, which is what makes a page land on the row after the one the user just read. The step therefore needs `clampSvcCursor()` before `fixSvcOffset()` (the latter moves only the WINDOW), and it degenerates to end/home whenever the list fits the pane — including the unsized `m.height == 0` first frame, where `svcVisibleCount()` returns the whole row count. Scroll indicators (`▲ N more` / `▼ N more`) replace existing blank-line content between breadcrumb/services and services/help, so they never change the total line count used by `svcVisibleCount()`; in grouped mode both indicators and the caption pad carry the service rows' 2-cell indent. `svcOffset` is reset to 0 alongside `svcCursor` in the DRILLED `servicesMsg` branch and at every landing/drill site — **never in the grouped `servicesMsg` branch**, which is also the 5s reload and must preserve cursor, selection, fold and search; it calls `restoreCursorRow(cursorRowID())` + `fixSvcOffset()` instead (`fixSvcOffset` moves only the WINDOW, so a shrinking row count needs the separate clamp `restoreCursorRow` ends with). **The cursor survives by IDENTITY, not by index** — `svcRowID{proj, service, header}` captured BEFORE `setGroups` and looked up after, the same rule the fold state (project name) and the selection (`svcKey`) already use: the rows come from a live `docker ps`, so a container started or removed ANYWHERE on the host inserts or deletes a row and slides every index below it, re-aiming drill-in, `l`/`i`/`c`/`U` and — through the empty-selection rule — the whole-project `d`/`r`/`s`, every 5 seconds without a keystroke.

**Container search (search & jump)**: `/` jumps, **never filters**. **Every fold and reload MUST re-derive `searchMatches`** (`computeMatches`); **every departure from `screenSelectContainers` — and the DRILLED `servicesMsg` RELOAD — calls `clearSearch()`**. Two-stage `esc`: clear, then back-nav; typing-`esc` restores by `searchReturnID`. **`searchBarLine()` MUST be ONE physical line** (`clampToWidth`). Full rationale, failure modes and test pins: `docs/architecture/tui-logs-and-search.md`.

**Multi-project host view — grouped vs drilled, the entry model, and `svcKey`**: GROUPED (`m.grouped`, every project plus `(unmanaged)`) and DRILLED share ONE row model, `svcEntry` DERIVED from `svcGroup`. **`m.grouped` is explicit, never inferred from `len(svcGroups)`.** **Folding hides ROWS, never services — read `svcRefs()`.** **Never key state on a ROW INDEX across a rebuild**: selection by `svcKey(proj, svc)`, cursor by `svcRowID`, fold by NAME. **Qualified keys never leave the Model.** Full rationale, failure modes and test pins: `docs/architecture/tui-multi-project.md`.

**Multi-project host view — `HostGrouper`, the grouped loader, and the refresh dispatch**: `HostGrouper` = `GroupHostStatus` + `GroupHostStats`: **ONE listing, TWO calls**, joined by the STAMPED `HostEntries` handle. **Every `loadGroups` return carries `groupedPayload`, failures included**; `groupedStatsCmd` CHAINS off the arrival, seam and listing taken from IT at DISPATCH. **The arrival ENDING the cycle clears `refreshInFlight` UNCONDITIONALLY** before the screen check (never `if !chaining { clear }`); only the chaining branch re-arms. As the 5s reload it leaves cursor, selection, fold and search ALONE and DROPS payloads under `m.confirming`. **A host-only group has no `ConfigDir` — `bindProjComposer` refuses it.** Full rationale, failure modes and test pins: `docs/architecture/tui-multi-project.md`.

**Multi-project host view — landing, drill-in/out, and action-time composer binding**: **`enterGroupedContainers()` is the ONE landing body** and owns the reset. **Grouped mode holds `m.composer == nil`**; binding is action-time (`bindCursorComposer`/`bindProjComposer`) and **every binder must unbind before staying on or returning to the grouped screen**. **`x` alone keeps its binding across the prompt**, so grouped `readOnly()` reads `allGroupsUnmanaged()`. **The drill-out `esc` arms the third one-shot, `groupCursorPending`**: the visited project's HEADER, only when `projName != ""`, written AFTER `enterGroupedContainers()`; the next payload WITH ROWS spends it. Full rationale, failure modes and test pins: `docs/architecture/tui-multi-project.md`.

**Multi-project host view — fold, header aggregates, and grouped rendering**: **Every fold goes through `settleFold`: re-derive `searchMatches`, aim the cursor at the folded group's OWN header.** **`a` alone is FOLD-AWARE** (`eachUnfoldedSelectableRef()`); **every other selection read stays HOST-WIDE — that split IS the safety rule**. **Fold keys (`←`/`→`, `z`) are grouped-only, write-only, DIRECTIONAL; `Z` stays UNBOUND.** **The view LANDS FOLDED once, via the one-shot `groupFoldPending`**: armed in `enterGroupedContainers()` (after `clearContainerScreen()`) and `NewModel`'s grouped branch, spent by `applyPendingGroupFold()` before the re-derives. Full rationale, failure modes and test pins: `docs/architecture/tui-multi-project.md`.

**Multi-project host view — batch partitioning and the sequential progress pipeline**: `opBatch{proj, services}`: **an EMPTY slice means ALL services**. `partitionSelection()` walks SCREEN order, skips unmanaged, falls back to the cursor's group when nothing is selected — **GROUPED-only; drilled keeps `warnNoSelection`**. **Each batch owns its events channel**; `handleStepEvent` resolves inside `currentStepRange()`. **Every batch message carries `batchIdx` + `batchSession` captured at DISPATCH**; `batchSession` bumps at INVALIDATION sites only. Full rationale, failure modes and test pins: `docs/architecture/tui-multi-project.md`.

**Multi-project host view — updates in grouped mode**: **no automatic scan fires here**: `autoUpdatesAllowed()` = `!readOnly() && !grouped`, `maybeRefreshUpdatesCmd` returns before the cache lookup AND the in-flight guard. **`U` is the only trigger and scans the CURSOR row's group only.** **`updatesMsg` carries `forKey` captured at DISPATCH — never re-derive it.** **`reapplyUpdateVerdicts(results)` replaces the drilled clear-then-hydrate**: one group's scan blanks no other. Full rationale, failure modes and test pins: `docs/architecture/tui-multi-project.md`.

**Log streaming / Log follow-aware auto-scroll**: `screenLogs` pipes `Composer.Logs()` via `io.Pipe`. **ZERO new Model fields**: `YOffset` IS the pause state, following ≡ `AtBottom()`: capture BEFORE every content change, `GotoBottom()` only if it held (`logChunkMsg`, `fullReformat()`, `rederiveLogs()`). Full rationale, failure modes and test pins: `docs/architecture/tui-logs-and-search.md`.

**Log formatting**: `w` wrap/`p` pretty-print are independent; `applyLogFormat()` folds only the unscanned tail (`foldNewRawLines`) into `logsFormatted`; toggles/resizes call `fullReformat()`. Full rationale, failure modes and test pins: `docs/architecture/tui-logs-and-search.md`.

**Log search & filter**: `buildMatcher` builds both preds; `logFilterPred`/`logSearchPred` read the COMMITTED regex flag. `logsRawLines` unfiltered, `logsPartial` the tail, **`logsScanned` a RAW-line cursor, NOT a survivor count** — `foldNewRawLines` MUST advance to `len(raw)`. **`setLogViewportContent()` is the sole `SetContent` chokepoint.** **`esc` peels in order**: typing-search → typing-filter → committed-search → committed-filter → leave. `logBarLine()` is ONE clamped line; viewport height `- 7` at the **two log sites**, `- 6` at config — **no blind find/replace**. Full rationale, failure modes and test pins: `docs/architecture/tui-logs-and-search.md`.

**Status refresh**: When returning from the progress screen or logs screen, `refreshStatus()` re-fetches `ContainerStatus()` via a `statusMsg` to update the running/stopped dots on the container screen. `ContainerStatus()` errors are propagated through `statusMsg.err` and `servicesMsg.err` and displayed via `svcErr`; a successful refresh clears any prior error. Follow this pattern whenever an operation changes container state.

**Server badge**: When a remote server is selected, the breadcrumb renders the server name via `serverBadge()`. Color is resolved via `resolveServerColor()` which returns the group color for grouped servers or the server's own color for ungrouped ones (nil-guarded for tests without config). A colored inline badge is shown only when the resolved color is non-empty; otherwise the breadcrumb falls back to the old plain server name (`cdeploy > prod-server > services`). `serverBadgeStyle()` in `styles.go` maps color names to lipgloss background colors. `serverHost` and `serverColor` fields on Model are set/cleared alongside `serverName` — follow the same cleanup discipline. No extra line is consumed, so no viewport height adjustment is needed.

**Config screen**: The `screenConfig` screen lets users view and edit docker-compose configuration files. Accessible via `c` key on the container screen (no confirmation). Uses a `ConfigProvider` interface (defined in `internal/tui/app.go`) with methods: `ConfigFile`, `ConfigResolved`, `EditCommand`, `ValidateConfig`. Both `Compose` and `RemoteCompose` implement it. The TUI type-asserts `composer.(ConfigProvider)` when entering — if the assertion fails (e.g., test mock), the `c` key is ignored. Key `r` toggles between raw file content and resolved output (`docker compose config`); resolved content is lazy-fetched on first toggle and cached. Key `e` shells out to `$EDITOR` via `tea.ExecProcess`; on return, re-fetches content and validates. Uses `configSession` (monotonic counter) for stale message rejection, matching the `logsSession` pattern. `esc` clears all `config*` fields and returns to the container screen. Local `findComposeFile()` probes `composeFiles` candidates; remote `findRemoteComposeFile()` uses a single SSH command to avoid multiple round-trips.

**Inspect screen**: `Inspector` is `tui`-declared and type-asserted; **`i` is NOT gated on `m.readOnly()`**. **`docker inspect` is TOP-LEVEL**: bypass `command()`/`remoteCommand()`. **`buildInspectSummary` is pure; its ZERO VALUE draws no update row**; renders STATE/HEALTH/IMAGE/MOUNTS/ENV, empty omitted, HEALTH off POINTER `State.Health`/`Config.Healthcheck`. **Never truncate**: wrap via `inspectBuilder`/`wrapCells`, not `softWrapLine`. **`push` is the ONE sanitise chokepoint**; raw's `sanitizeInspectRaw` must NOT `ansi.Strip`. `inspectViewportSize()` = `m.height - 6` (NOT logs `- 7`); `setInspectContent()` is the ONE `SetContent` site + `SetXOffset(0)`; **`viewInspect()` must NOT end in a newline**. Full rationale, failure modes and test pins: `docs/architecture/tui-inspect-screen.md`.

**Exec into container**: The `x` key on the container screen execs into a running container interactively. Uses an `ExecProvider` interface (defined in `internal/tui/app.go`) with method `ExecCommand(ctx, service, command) (*exec.Cmd, error)`. Both `Compose` and `RemoteCompose` implement it. The TUI type-asserts `composer.(ExecProvider)` when `x` is pressed — if the assertion fails (e.g., test mock), the key is ignored. If the service is not running, a warning is shown. Otherwise, confirmation is requested (`pendingExec = true`); on confirm, the TUI shells out via `tea.ExecProcess` which suspends Bubble Tea and gives full terminal to the exec process. On return, `execDoneMsg` resets `pendingExec` and calls `refreshStatus()`. Default shell command: `[]string{"/bin/sh", "-c", "command -v bash >/dev/null 2>&1 && exec bash || exec sh"}` (checks for bash first, falls back to sh for Alpine/minimal images; uses `command -v` instead of redirecting stderr on `exec` to avoid silencing bash's stderr for the entire session). Local: `docker compose exec <service> <command...>`. Remote: builds SSH command directly (like `EditCommand` pattern) with `-t` for TTY allocation — does NOT use `remoteCommand()`. CLI: `cdeploy exec <service> [-- command...]` with `--server`/`-s` support; follows `cmd/logs.go` pattern. `ExecCommand` returns `(*exec.Cmd, error)` (not executing it) so the caller controls execution. `DefaultExecCommand` is exported from `internal/compose/compose.go`.

**Docker Compose**: All docker interaction goes through `compose.Compose.command()` (local) or `compose.RemoteCompose.remoteCommand()` (SSH) which builds the correct command based on the `Standalone` field — `exec.CommandContext("docker", "compose", ...)` for plugin mode or `exec.CommandContext("docker-compose", ...)` for standalone mode. Both set `CURRENT_UID` env var (format `uid:gid` locally, `$(id -u):$(id -g)` on remote). Auto-detection via `Detect(ctx)` probes `docker compose version` first, then falls back to `docker-compose version`; the result is cached in the `Standalone` and `detected` fields. Detection is explicit — callers must call `Detect()` before first use; `command()`/`remoteCommand()` only read `Standalone`. `SetStandalone(bool)` allows inheriting the detection result into new instances. `SetTestHooks(run, output)` on both `Compose` and `RemoteCompose` injects test doubles. Exact subcommands: `stop`, `rm -f`, `pull`, `up --no-start`, `start`, `config --services`, `ps -a --format json`, `logs`, `exec`, `ls -a --format json`, plus top-level `stats --no-stream --format json` (NOT a compose subcommand — see below). Empty container slice means operate on all services. `parseContainerStatus()` handles both JSON array output (Docker Compose v2.21+) and NDJSON (older versions); it parses `CreatedAt` and `Status` fields from `psEntry` to populate `ServiceStatus.Created` and `ServiceStatus.Uptime`. `formatUptime()` in `internal/compose/uptime.go` converts Docker's Status string (e.g. `"Up 3 hours (healthy)"`) into compact form (`"3h"`): strips health suffixes, compacts time units (`hours` -> `h`, `days` -> `d`, etc.), handles special cases (`"About a minute"` -> `"~1m"`, `"Less than a second"` -> `"<1s"`), returns `"restarting"` for Restarting status, and empty string for non-Up statuses. `parseUptimeDuration()` converts compact uptime strings back to `time.Duration` for comparison (used to pick the longest-running replica among scaled services, which correctly handles restarts where CreatedAt is older but actual uptime is shorter). CLI subcommands reject `-a` combined with explicit container names.

**Project identity — caller-supplied, never looked up**: a composer's identity is what its CALLER supplied — the `--project-name`/`-p` flag, or the `Name` on the picker row the TUI drilled into. It is **NEVER re-derived from `docker compose ls`**. That command enumerates projects by scanning CONTAINER LABELS, so a project whose containers are gone is not reported — and the deploy pipeline itself removes them (`stop → rm -f → pull → create → start`). A round that keyed the snapshot from that lookup made a failed deploy unrollbackable: `pull` fails after `rm -f`, `ls` reports nothing, and the rollback keys a different file. **THE STORAGE KEY MUST NOT DEPEND ON STATE THE OPERATION BEING SNAPSHOTTED CAN DESTROY.** Convergence instead comes from `canonicalStateName(dir, name)` (`internal/compose/projectidentity.go`), which needs no host state at all: an UNNAMED compose invocation is not identity-free — it addresses the project compose derives from the directory — so a composer naming that DEFAULT project and a composer naming nothing fold onto ONE key, the dir-only hash every release has written. `composeDefaultProjectName` reproduces compose-go's `NormalizeProjectName` on `path.Base(dir)` (lower-case, keep `[a-z0-9_-]`, trim leading `_-`); it is not a guess, it is the definition of the project compose would use. A project that is NOT the directory default (`-p blue`) keys its own file, so two `-p` projects sharing one directory never read each other's digests. **`Compose.stateName()`/`RemoteCompose.stateName()` are the ONE producer** of both the key and the `project_name` stamp, so `checkSnapshotProject` can never disagree with the file it guards. `COMPOSE_PROJECT_NAME`, a `name:` key and `.env` are deliberately NOT consulted — the environment is invisible over SSH (honoring it locally would split the local and remote key for one project) and the rest means replicating compose's interpolation; when one of them names a project the derivation does not predict, the two spellings key two files and a rollback says "no snapshot" — a safe failure for a `-p`-addressed project, which is the case this design targets. **It is NOT safe in one narrower shape**: two DIFFERENT projects sharing one directory and BOTH addressed with an EMPTY name (each selected by its own `name:` key, `.env` or `COMPOSE_PROJECT_NAME`) fold onto the same dir-only file, and `mergeSnapshot` merges by SERVICE name, so one can pin the other's digest. That is not a regression — before the name entered the key EVERY project in a directory shared one file — so the rule NARROWS the hazard rather than introducing it. `TestProjectIdentity_EveryPathKeysOneStateFile` (fast track + drill-in + `runOperation` ⇒ ONE state file) and `TestProjectIdentity_TwoNamedProjectsInOneDirStayApart` are the two halves of the contract; `TestRollbackFindsTheSnapshotAfterEveryContainerIsRemoved` and its remote twin pin it against an empty `ls`. **`ListProjects` must carry NO `-f` and NO `-p`** (`hostCommand`/`remoteHostCommand`): `ls` is host-wide discovery, neither flag selects anything there, and `-f` would point compose at a file it must parse — `cdeploy list` and the TUI project loader call it on a composer that may already carry both. **Documented limitation**: the CLI reproduces `docker compose -p <name>` run in `-C <dir>` exactly, so it auto-discovers compose files; a project whose files are not auto-discoverable there must be driven from the TUI, whose picker row carries the set.

**Remote SSH**: `RemoteCompose` wraps docker compose commands in SSH calls via a ControlMaster persistent socket (`/tmp/cdeploy-ctrl-{hash}-{pid}`). `ConnectCmd()` returns the SSH connect command for TUI's `tea.ExecProcess` (full terminal access for password prompts), `Connect()` runs it directly for CLI use, and `Close()` tears down the socket. All remote args are shell-escaped via `shellEscape()`. `CURRENT_UID` is evaluated on the remote host via `$(id -u):$(id -g)` to get the correct server-side UID/GID. The `Run()` function in `tui/app.go` calls `disconnectFunc` on exit to ensure socket cleanup. CLI uses `--server`/`-s` flag to select a server; TUI shows a server picker when servers are configured.

**Ad-hoc SSH (`-S`/`--ssh`)**: The `--ssh` persistent flag (registered in `cmd/root.go` alongside `--server`) is the ad-hoc complement to config-based `--server`. It accepts `[user@]host[:port]` and lets CLI users (especially CI) connect without a `~/.cdeploy/servers.yml` entry. Mutually exclusive with `--server`; requires `--project-dir`. Implemented via two helpers in `cmd/remote.go`: `checkRemoteMutex(serverName, sshTarget, identityFile)` enforces both the `--server`/`--ssh` mutex and the `--identity` requires `--ssh` rule at the top of each subcommand's `RunE`, and `resolveSSHRemote(ctx, sshTarget, projectDir, identityFile, newRemote)` parses the target via `config.ParseSSHTarget`, calls the injected factory (`opNewRemote`/`execNewRemote`/`logsNewRemote`/`newRemote` — preserving existing test seams), sets `RemoteCompose.SSHExtraArgs`, and runs `Connect()` + `Detect()`. On `Detect` failure the helper internally calls `Close()` before returning the error; on `Connect` failure cleanup is a no-op. The returned cleanup is always non-nil, so callers can `defer cleanup()` immediately after the call without nil-checking. Wired into `deploy`/`restart`/`stop`/`exec`/`logs`/`list` subcommands as a branch above the existing `--server` block — config-based path is unchanged. Parser lives in `internal/config/sshtarget.go`: rejects whitespace and IPv6 (`[`-prefixed); validates port `1..65535`; returns `SSHTarget{User, Host, Port}` with helpers `SSHHost()` (`user@host` or `host`) and `PortArgs()` (`["-p","NNNN"]` or nil). The `SSHExtraArgs []string` field on `RemoteCompose` is spliced **immediately before the host argument** in every SSH argv build site (Connect, Close, Detect plugin/standalone probes, `remoteCommand`, `findRemoteComposeFile`, `ConfigFile`, `EditCommand`, `ExecCommand`); nil = zero-behavior-change default. No TUI changes — `--ssh` is strictly a CLI feature.

**Ad-hoc SSH identity (`-i`/`--identity`)**: The `--identity` persistent flag (registered in `cmd/root.go` immediately after `--ssh`) accepts a path to an SSH private key, intended for CI/automation workflows that write a key from a secret and don't have a `~/.ssh/config` entry. Strict-narrow: only valid alongside `--ssh` (mutually exclusive with `--server` via the `--identity requires --ssh` rule); CLI-only (TUI mode rejects it). Path validation lives in `internal/config/identity.go` (`ParseIdentity`): trims input, rejects empty, expands `~/` paths via `os.UserHomeDir()`, rejects bare `~` and `~user` forms (only `~/...` is supported), requires `os.Stat` to succeed and report a regular file, requires `os.Open` to succeed (readability check beyond mode bits), and returns `filepath.Clean` of the resolved path. Relative paths pass through unchanged — `ssh(1)` resolves them against cwd. `resolveSSHRemote` appends `["-i", cleanPath]` to `SSHExtraArgs` after the port args, so every existing SSH argv splice site absorbs `-i` for free without any changes to `internal/compose/remote.go`.

**Config**: `internal/config` loads `~/.cdeploy/servers.yml` defining remote servers and groups. The `Config` struct has `Groups []Group` and `Servers []Server`. `Group` has `Name` and `Color` fields. `Server` has `name`, `host`, optional `project_dir`, optional `group`, and optional `color` fields. Color resolution: grouped servers inherit color from their `Group` via `Config.GroupColor()`; ungrouped servers use their own `color` field. `color` accepts ANSI color names listed in `config.ValidColors` (exported slice, single source of truth for both validation and the TUI cycle picker): red, green, yellow, blue, magenta, cyan, white, gray; invalid values are rejected by `Validate()`. `Validate()` also checks group name uniqueness, group color validity, and that servers reference existing groups. `Save(path string) error` writes config atomically (temp file + rename) with `MkdirAll` for parent dirs. When color is omitted (resolved or direct), the TUI keeps the old plain-text breadcrumb instead of rendering a badge. Servers with the same `group` are displayed together under a shared header in the TUI. `Load()` returns an empty config (not error) if the file doesn't exist; it also runs `migrate()` to auto-convert old-format configs (per-server colors on grouped servers) to the new format (colors on Group entries, first-server-wins for conflicts). SSH-specific options (keys, jump hosts, tunnels) belong in `~/.ssh/config` — except `-i` for ad-hoc CI/automation use via `--ssh`.

**Settings editor**: Two screens (`screenSettingsList` + `screenSettingsForm`) accessible via `s` key on the server select screen (only when `m.config != nil`). The settings list shows all servers in a table with Name/Host/Group/Color columns; color is resolved from the group for grouped servers (with a "(group)" indicator) or from the server directly. `a` adds, `enter`/`e` edits, `d` deletes (inline y/n confirmation). The form uses 4 `textinput.Model` instances (name, host, project_dir, group) and a cycle picker for color (left/right arrows cycle through `""` + `config.ValidColors`). `settingsField int` tracks focus (0-3 = text inputs, 4 = color picker). When a server has a group, the color picker shows a "(group)" label; cycling the color edits the group's color (affecting all servers in that group). Editing a grouped server loads `settingsColor` from the group; on save, `settingsColor` is applied to the group's color (not the server's). New group names auto-create `Group` entries; orphaned groups (no servers referencing them) are auto-cleaned on both save and delete. `resolveServerColor()` on Model returns group color when available, falling back to server color (nil-guarded for tests without config). Validation reuses `config.Validate()` on a temporary config (including `Groups`) before applying changes. On save: mutate `m.config.Groups` and `m.config.Servers`, call `m.config.Save(m.configPath)`, sync `m.servers = m.config.Servers`, rebuild `m.serverEntries` via `buildServerEntries()`. Config path and config are threaded into the TUI via `WithConfigPath(path)` and `WithConfig(cfg)` functional options — existing `NewModel()` call sites are not affected. State cleanup: `esc` from settings list returns to server select; `esc` from form returns to settings list with no data changes; `settingsErr` is cleared on transitions.

**Operations**: Four operations — `Restart` (stop → rm → create → start), `Deploy` (stop → rm → pull → create → start), `StopOnly` (stop), `Rollback` (stop → rm → create → start — Restart shape, **NO Pull**: registry outages are a classic rollback trigger, so offline rollback from local blobs must work). All share the same `runner.Run()` pipeline; the step list varies by operation type. `Steps()`/`buildSteps()` fold Rollback into the Restart branch (`default:` case, gated only by `op == Deploy` for the Pull step).

**Wait engine (`--wait` health gate)**: `EvaluateWait` is a **pure reducer** seeded by `NewWaitState`. **Precedence IS the spec**: (1) `Uptime=="restarting"` x3 **FIRST**; (2) unhealthy; (3) `Running==false` after `everRunning`; (4) never-ran x5; (5) `Health!=""` ⇒ ONLY `healthy`; (6) no healthcheck+running ⇒ after `Grace`. **Firm boundary**: 5/6 PASS needs `elapsed <= Timeout`, 1-4 do NOT; pending at `>= Timeout` ⇒ timed out. **`WaitHealthy`'s `WithDeadline(ctx, start+Timeout)` MUST precede ANY blocking call, `ListServices()` included.** Expiry = exit 2, parent cancel = exit 1 (`ctx.Err()` FIRST). Full rationale, failure modes and test pins: `docs/architecture/wait-snapshots-rollback.md`.

**`WaitError` exit-2 contract**: non-OK/errored ⇒ `errors.As` = **exit 2**; keep `Unwrap()`; `stop` never waits. Full rationale, failure modes and test pins: `docs/architecture/wait-snapshots-rollback.md`.

**Deploy snapshots & the state file**: **Deploy-only**, pre-Stop, from the RUNNING container; `mergeSnapshot`/`existingForMerge` guard writes. **The `canonicalStateName` key must never depend on state the operation destroys**; EMPTY name = dir-only hash. Full rationale, failure modes and test pins: `docs/architecture/wait-snapshots-rollback.md`.

**Rollback pipeline & `PrepareRollback` prep / `ExtraComposeFiles` contract**: `runOperationWithPrep`+`rollbackPrep`; a failed pull aborts BEFORE the override; `pull_policy: never`; `ExtraComposeFiles = [main, override]`, main FIRST, cleanup FUNCTION-scoped; **nil = byte-identical argv**. Full rationale, failure modes and test pins: `docs/architecture/wait-snapshots-rollback.md`.

**TUI wait phase & `R` rollback (sessions + cleanup)**: `screenProgress`'s wait is PER BATCH; **`clearWaitState` must NOT clear `opContainers`**; `runRollbackCleanup` on LEAVING, NEVER goroutine-deferred. Full rationale, failure modes and test pins: `docs/architecture/wait-snapshots-rollback.md`.

**Health checks**: `ServiceStatus` has `Running bool`, `Health string` (values: `"healthy"`, `"unhealthy"`, `"starting"`, or `""` for no healthcheck), `Created string` (formatted creation time, e.g. `"2024-01-15 09:30"`), and `Uptime string` (compact uptime, e.g. `"3h"`, `"2d"`, or `""` if not running). For scaled services, `Running` uses OR (any running = running), `Health` uses worst-case priority (`unhealthy` > `starting` > `healthy`), `Created` uses the oldest replica, and `Uptime` uses the longest-running replica. The TUI shows health icons (♥/✗/~) next to status dots and Created/Uptime columns. The CLI `list` command shows the same icons and columns.

**Multi-project discovery**: The `list` subcommand auto-discovers all compose projects when no `-C` is specified (both local and remote). Services are grouped by project with headers. Per-project errors are non-fatal — a warning is printed to stderr and the project is skipped. When `-C` is specified, only that project's services are shown in a flat list. With `--stats`, CPU/Mem columns are populated by joining `docker stats --no-stream --format json` against each project's `ps` container IDs. The host-wide `docker stats` call is shared across every project: `runList` calls `compose.AllContainerStats`/`AllContainerStatsRemote` once before the project loop and passes the result map into `collectMultiProjectStats`. Each project's composer satisfies the `bulkStatsAggregator` interface (`ContainerStatsFromBulk`) and only runs `docker compose ps` per project, joining against the shared bulk map — one ~1.5s cost regardless of project count. Composers that don't implement the bulk interface (test mocks) fall back to per-project `ContainerStats()`; the fallback also runs if the host-wide fetch failed (`bulkStats == nil`), so stats degrade gracefully rather than disappearing.

**Resource stats**: `runner.ServiceStats` (`CPUPercent float64`, `MemoryUsed int64`, `MemoryLimit int64`) is populated from `docker stats --no-stream --format json` — host-wide NDJSON, one line per container, parsed by `parseStatsOutput()` in `internal/compose/stats.go` (tolerant of both NDJSON and JSON-array forms, mirroring `parseContainerStatus`). `ContainerStats()` is the **first method on `Compose`/`RemoteCompose` to bypass `command()`/`remoteCommand()`** because `docker stats` is a top-level Docker CLI command rather than a compose subcommand — calling `c.command(...)` would prepend `compose` and produce a malformed argv. `AllContainerStats()` builds `exec.CommandContext("docker", "stats", ...)` directly; `AllContainerStatsRemote()` builds the SSH argv directly, splicing `SSHExtraArgs` immediately before the host arg (same convention as `EditCommand`/`ExecCommand`, which also bypass `remoteCommand()`). Per-project `ContainerStats()` calls `docker compose ps --format json` for this project's container IDs, calls the bulk helper, joins by short container ID (first 12 chars), and sum-aggregates `CPUPercent`/`MemoryUsed`/`MemoryLimit` across replicas — a 3-replica service maxing each core shows ~300% CPU. Only running containers appear in the result map; stopped services are absent. Helpers `parseSize` (handles `B`/`KiB`/`MiB`/`GiB`/`TiB` binary and `kB`/`MB`/`GB`/`TB` decimal suffixes, case-insensitive), `parseCPUPercent` (strips `%`), and `FormatBytes` (exported; produces compact `124M`/`1.5G`) live in `internal/compose/stats.go` as the single source of truth — both `cmd/list.go` and `internal/tui/app.go` import `FormatBytes` from there. In DRILLED mode the TUI fetches stats in parallel with status via `tea.Batch(refreshStatus(), refreshStats())` on every entry to `screenSelectContainers` and after every operation completes (return from progress / logs / exec). **In GROUPED mode the two halves are strictly SERIAL**: `statsRefreshCmd()` is nil there and `groupedStatsCmd` is CHAINED off the grouped `servicesMsg` arrival, because it consumes the listing that arrival carries — see the `HostGrouper` paragraph. A periodic `refreshTickMsg` (every `statsRefreshInterval` = 5s, defined in `internal/tui/app.go`) keeps the data fresh while the user lingers on the screen: `Init()` kicks off a singleton `tea.Tick`, and the handler always reschedules itself so exactly one tick is in flight at any time regardless of how many transitions in/out of the screen happen. The handler gates fetches on `m.screen == screenSelectContainers && !m.confirming && <live> && !m.refreshInFlight`, where `<live>` is `m.composer != nil` in drilled mode and `m.composerFactory != nil` in grouped mode (grouped holds no composer by design) — anywhere else, the tick is a pure reschedule with no docker calls (off-screen / mid-confirmation / mid-disconnect / previous fetch still pending).

**Session filters for stale responses**: `statsMsg`, `statusMsg` AND `servicesMsg` all carry a `session uint64` captured at fetch time; their handlers reject messages where the session (and screen) don't match. Two counters live on Model:
- `statsSession` covers `refreshStats` AND the chained grouped `groupedStatsCmd` (the two are the same fetch in the two modes) — bumped at every context change that swaps `m.composer` or the grouped host context: `entryLocal` fast track, `execDone`, `esc` from logs, `esc` from progress, plus the three navigation helpers `enterGroupedContainers()` (connect success, `entryLocal` grouped, drill-OUT), `drillIntoGroup()` (drill-IN) and `backToServerScreen()`. **All seven go through ONE helper, `bumpFetchSessions()`, which bumps `statsSession`/`statusSession`/`updatesSession`/`rollbackFetchSession` together — never four hand-written `++` lines at a new site.** The grouped cycle CROSSES the first two (the arrival passes its `statusSession` gate, then chains a stats fetch stamped `statsSession`), so a site bumping only one has the chained `statsMsg` dropped at a gate that does NOT clear `refreshInFlight` — the exact latch. The two LONE `rollbackFetchSession++` sites (the `R` keypress, the connect-failure path) are not context changes and keep their single bump.
- `statusSession` covers `refreshStatus`, `loadServices` AND `loadGroups` — bumped at the same 7 sites as `statsSession` (the lifecycle is identical: `loadServices`/`loadGroups` are the initial-load siblings of `refreshStatus`, fetching list + initial status in one shot). `loadGroups` deliberately reuses this counter rather than owning one: it is `loadServices`' grouped counterpart, same context changes, same staleness rule.
- `projectsSession` and `projectsMsg` are GONE with the project picker. The loader they guarded now feeds `loadGroups`, which is already gated on `statusSession` at the same swap sites.
- **The `connectResultMsg` SUCCESS path DOES bump all three counters** (via `enterGroupedContainers`) — the inverse of the rule that held while the next screen was the static picker. It now lands on LIVE data, and the site that starts fetching a resource is the site that must invalidate whatever a previous server left in flight.

Missing the session filter on any of them is the same class of bug — codex's adversarial review caught each one in successive rounds. When adding a NEW async msg type that's tied to a screen context, give it a session and gate the handler on `m.screen != <its-screen> || msg.session != m.<sessionField>`.

**`refreshInFlight` prevents fetch stacking**: the tick fan-out `tea.Batch(statusRefreshCmd(), statsRefreshCmd(), refreshTick)` — the mode-aware pair, `loadGroups` alone in grouped mode (`statsRefreshCmd()` is nil there because the stats half is chained off the arrival, not batched) and `refreshStatus`/`refreshStats` in drilled mode — schedules the next 5s tick *concurrently* with the current refresh — Bubble Tea batches execute concurrently, not sequentially. Without a guard, if `docker stats --no-stream` takes longer than 5s on a slow remote SSH hop, the next tick would stack another pair of fetches on top. The `m.refreshInFlight bool` is set true at every site that fires `refreshStats()` (the tick handler + the 5 transition handlers that fan out the fetch batch) plus the grouped `servicesMsg` branch that CHAINS the stats half, and cleared in the `statsMsg` handler on any *current-session* arrival, *before* the screen check (success or error). **The grouped `servicesMsg` branch clears it the same way — UNCONDITIONALLY, before its own screen check — and the ONE branch that accepts the payload and chains the stats half then RE-ARMS it beside the `tea.Cmd` whose `statsMsg` clears it again.** Never write `if !chaining { clear }`: that skips the clear on the stale-session, off-screen, `m.confirming` and `msg.err` paths, which is the exact latch this rule exists to prevent. Clearing has to happen before the screen check because if the user opens the config / logs / progress screen while a stats fetch is pending, the response arrives off-screen and would otherwise be discarded silently — leaving `refreshInFlight` stuck true and permanently silencing the periodic loop when the user returns to the container screen. The session-match condition makes the unconditional clear safe: stale responses (different session, indicating a context change has happened) don't touch the flag because the context-change handler already reset it. The flag is also explicitly reset to false in `backToServerScreen()` (the one transition that navigates away without firing a fetch batch) so the new context starts clean. When the next tick fires while the guard is set, it reschedules without fetching. **The tick's liveness check is `m.composer != nil` in drilled mode and `m.composerFactory != nil` in grouped mode** — grouped mode holds no composer by design, so a flat composer test would silence the periodic refresh on exactly the screen that most needs it.

**Test seam for the tick**: `Model.tickCmdOverride func() tea.Cmd` is nil in production; tests set it via `installFakeTick(&m)` (in `internal/tui/app_test.go`) to swap the real `tea.Tick` for a non-blocking Cmd that returns a `fakeTickMsg`. Without the override, every test exercising the gated paths (off-screen, in-flight, confirming) would leave a real 5s `tea.Tick` goroutine running until the program exits. With the override installed, tests assert directly on whether `cmd()` returns a `tea.BatchMsg` (positive path: fetch batch) or any other msg (gated path: just the rescheduling tick). NewModel sets `m.refreshInFlight = true` for the local fast-track because `Init()` will fire `refreshStats`; tests that exercise the unblocked tick path must explicitly clear it.

When adding a new screen that should NOT trigger periodic refreshes, no change is needed: the gate already excludes any screen != `screenSelectContainers`. When adding a new screen that DOES need its own periodic refresh, prefer a separate tick (different msg type) rather than overloading `refreshTickMsg`. When adding a new context-change handler (anything that swaps `m.composer`), bump BOTH `statsSession` AND `statusSession`, and set `refreshInFlight` (true if the handler fires a refresh batch, false if it just navigates away). `statsMsg` carries a `session uint64` captured at fetch time from `m.statsSession`; the handler rejects messages where `msg.session != m.statsSession` in addition to the screen check, mirroring the `logsSession`/`configSession` pattern. `statsSession` is bumped on every context change that swaps `m.composer` or the grouped host context (`drillIntoGroup`, `enterGroupedContainers`, `backToServerScreen`, `entryLocal`) so an in-flight fetch from project A cannot land in project B's view. Soft failure: on stats fetch error, both CLI (`cdeploy: stats unavailable: <err>` to stderr, exit 0, blank cells) and TUI (`statsErr` rendered as soft warning) keep status — the load-bearing primary view — intact; in the TUI, when both `svcErr` and `statsErr` are set, `svcErr` wins (the more important failure).

**Ports column**: `ServiceStatus.Ports []runner.Port` (with `Host`, `HostPort`, `ContainerPort`, `Protocol` fields) is populated by `parseContainerStatus()` from `docker compose ps --format json`. Primary data source is the `Publishers []` array (Compose v2); when absent or empty, `parsePortsString()` falls back to parsing the `Ports` text field (e.g. `0.0.0.0:8080->80/tcp, :::8080->80/tcp`). Publishers with `PublishedPort == 0` (i.e. `expose:`-only/internal) are skipped. Dedup is keyed on the full tuple `(Host, HostPort, ContainerPort, Protocol)` so distinct bind interfaces on the same port (e.g. `127.0.0.1:8080->80` and `192.168.1.10:8080->80`) both survive. A separate `collapseIPv6Mirrors()` pass collapses only the IPv4/IPv6 *wildcard* mirror pair — when both `0.0.0.0` (IPv4 unspecified) and `::` (IPv6 unspecified) appear on the same `(HostPort, ContainerPort, Protocol)` tuple, the `::` entry is dropped. All other host strings are distinct user-visible binds: IPv6 loopback `::1`, link-local `fe80::1`, or explicit IPv6 addresses like `2001:db8::1` survive intact, even alongside an IPv4 sibling. Multiple non-wildcard IPv6 entries on the same tuple do not collapse against each other (full-tuple dedup in `mergePort` already removes exact repeats). Bracketed IPv6 like `[::]:8080` is normalized (brackets stripped on input). Empty `URL` from Compose is normalized to `0.0.0.0`. Scaled-service ports go through the same dedup + collapse + sort pipeline (sorted ascending by `HostPort`, then `ContainerPort`, `Protocol`, `Host`). Render helpers live in `internal/compose/ports.go`: `FormatPort()` returns `host:hp→cp` for IPv4 and `[host]:hp→cp` for IPv6 (the arrow is U+2192, not `->`; IPv6 hosts — any host containing `:` — are wrapped in brackets to disambiguate the host:port boundary), with `/proto` suffix only when protocol is non-empty and not `tcp` (`/udp` and `/sctp` are shown). Wildcard hosts (`0.0.0.0` and `::`, both meaning "all interfaces") are omitted entirely so the common all-interfaces case renders as a bare `hp→cp`; non-wildcard binds (loopback, explicit address) keep their host so the LAN-vs-loopback distinction stays visible. The wildcard-hiding affects only display — JSON output (`cmd/list.go` serializes the `Port` struct directly) preserves the original `host` field. `FormatPorts()` comma-joins. Both the CLI `list` (`formatDots`/`formatDotsGrouped` width-track `maxPorts` and append the column after Uptime when any service has ports) and the TUI container-select screen (captions row gains `"Ports"` via `hasStatusColumns()`) render the column. Stopped containers and services without published ports show a blank cell (padded whitespace for alignment). CLI JSON output includes a `ports` array (`omitempty`) per service with `host`/`host_port`/`container_port`/`protocol` fields.

**Grouped host view — an `svcErr` makes every row key inert**: `viewSelectContainers` early-returns an error screen that hides the rows but KEEPS the groups and selection: **the dispatch swallows every key but `esc` and `ctrl+c` while `m.svcErr != nil`**. Full rationale, failure modes and test pins: `docs/architecture/tui-multi-project.md`.

**`rollbackPreppedMsg` carries batch identity**: `batchIdx`+`session` captured at DISPATCH; gate on screen+idx+session; stale branches MUST invoke `msg.cleanup`. Full rationale, failure modes and test pins: `docs/architecture/wait-snapshots-rollback.md`.

**`Compose.ProjectName` / `RemoteCompose.ProjectName` (`-p` splice)**: `docker compose ls` reports a project launched with `docker compose -p` or `COMPOSE_PROJECT_NAME` under its REAL name while several such projects share one `ConfigDir`, so a composer built from the directory alone addresses the directory's DEFAULT project — the picker showed one project and `d`/`r`/`s` stopped and removed another's containers. `projectNameArgs`/`RemoteCompose.projectFlag` splice `-p <name>` AFTER the `-f` pairs and before the subcommand (both are compose top-level flags; keeping `-f` first leaves the `ExtraComposeFiles` rule untouched), shell-escaped on remote, and `RemoteCompose.ExecCommand` must splice it too because it builds its own argv. **An empty name must keep producing byte-identical argv.** `localComposerFor`/`remoteComposerFor` (`cmd/root.go`) stamp it from the picker row and `prepareLocalComposer`/`resolveSSHRemote`/`resolveServerRemote` from the `-p` flag; **none of them looks the name up** — see the project-identity paragraph.


## Adding New Operations

1. Add constant to `Operation` enum in `internal/runner/runner.go`
2. Update `String()`, `Steps()`, and `buildSteps()` in the same file
3. Add action key case in `screenSelectContainers` handleKey in `internal/tui/app.go`, AND name the key in the matching group in `helpGroupsFor()` (`internal/tui/help.go`) — the `?` overlay is the only place the full key table is advertised now that the footer carries 6 tokens
4. Gate the new key on `m.readOnly()` with an early return, and leave it OUT of `readOnlyContainerGroups()` (`internal/tui/help.go`). Every operation is a compose pipeline, and an unmanaged container has no compose file, so a new op is by definition inert on the read-only screen — a key the read-only table still named would advertise a no-op, which is the failure that whole variant exists to prevent
4b. **Route the key through the GROUPED path, or it writes a nil deref.** Grouped mode holds `m.composer == nil` BY DESIGN (see the multi-project paragraphs), so a new op key must not touch the composer at press time: arm through `armOperation` / `partitionSelection()`, bind with `bindProjComposer(batches[0].proj)` at the confirming `enter`, and call `unbindGroupedComposer()` on EVERY early return between the two. A key bound in BOTH modes needs no second key list — `TestHelpGroups_GroupedNamesTheSameKeys` (`internal/tui/help_test.go`) checks `grouped == drilled ∪ groupedOnly` three ways and fails the moment they drift. **A GROUPED-ONLY key must be added to that test's hand-maintained `groupedOnly` list**, the last one left. Add the grouped dispatch test alongside the drilled one; a key that works drilled and panics grouped is the shape this step exists to prevent
5. Add CLI subcommand in `cmd/deploy.go` and register in `cmd/root.go`
6. Tests: runner sequence test, cmd subcommand/flag tests, TUI action key + confirmation tests, plus the expected-key set in `TestHelpGroups_NamesEveryBoundKey` (`internal/tui/help_test.go`), which fails in both directions when the help table drifts from the dispatch. If the operation is a WRITE, add the key to the table in `TestReadOnly_GatesWriteKeys` (`internal/tui/app_test.go`) so the read-only screen is pinned to refuse the gate step 4 added. The read-only help pin needs NO edit for a gated key — it stays out of `TestHelpGroups_ReadOnlyNamesEveryBoundKey`'s hand-maintained bound set, and that test's names-nothing-unbound direction is what catches a table that advertises it anyway.

If the new operation needs an op-specific pre-run step (like Rollback's snapshot read + digest-pin prep), don't fork `runOperation` — route through `runOperationWithPrep(ctx, op, all, containers, prep)`. The `prep func(context.Context, runner.Composer) (func(), error)` runs AFTER the composer is built and BEFORE the pipeline (so it can apply refusal rules and configure the composer, e.g. set `ExtraComposeFiles`); its returned cleanup is deferred function-scoped, so it runs after the wait phase but before the remote SSH teardown (LIFO). deploy/restart/stop pass a nil prep and keep the original path. Rollback lives in its own `cmd/rollback.go` (see "Adding New CLI Subcommands") but is a deliberate reuse of this deploy machinery, not a fresh subcommand skeleton.

## Adding a New TUI Screen

**No failing test forces any of this.** The bound in `TestAllScreens_Complete` anchors to the LAST screen constant, so it has to be moved by hand every time; until it is, a screen missing from `allScreens` silently skips all six tests that iterate it. Three more tables promise completeness in their names and iterate a literal list instead, so they stay silent too. `screenInspect` (the 8th and currently last screen, after `screenSelectProject` was deleted) is the worked example. **Do not add a screen for "a different view of the container list"** — the grouped host view is a MODE on `screenSelectContainers` (`m.grouped`), for the reasons in `docs/architecture/tui-multi-project.md`.

1. Append the constant to the `screen` iota in `internal/tui/app.go`.
2. Add it to `allScreens` (`internal/tui/help_test.go`) AND move `TestAllScreens_Complete`'s bound to `int(<newScreen>) + 1`.
3. Add the `screenName()` and `helpGroupsFor()` cases in `internal/tui/help.go`, and the `bound` row in `TestHelpGroups_NamesEveryBoundKey` — step 2 forces that row to exist (`screen %d has no expected key set`), and the pin then runs BOTH directions against the screen's `handleKey` case.
4. Add the `View()` case and, if the screen holds a viewport, a `WindowSizeMsg` branch — with the SAME width and height floors the `enter*` helper applies, or the two sizing sites disagree on a narrow pane.
5. Update the three hand-maintained tables that step 2 CANNOT reach — `TestCtrlCConfirmation_AllRemoteScreens` (`app_test.go`), `TestHelpOverlay_OpensFromEveryScreen` and `TestHelpOverlay_SwallowsEveryActionKey`'s `containerKeys` (`help_test.go`). Their names say "AllRemoteScreens" / "EveryScreen"; they iterate a literal list.
6. Add the entry key to the container dispatch, name it in the matching `helpGroupsFor` group, and call `m.clearSearch()` at the new `enter*` departure site (the ephemeral-on-departure site list lives in `docs/architecture/tui-logs-and-search.md`, and its count moves too).
7. Add a `typingInInput()` case ONLY if the screen opens a text input; that one case is all a new input needs, since the `q`→`esc` rewrite and the `?` open gate both read it.
8. If the screen fetches asynchronously, give it a session counter and gate its message handler on `m.screen != <its-screen> || msg.session != m.<its>Session` — see "Stale async message guard".

## Adding New CLI Subcommands

See `cmd/list.go`, `cmd/logs.go`, and `cmd/exec.go` for the pattern. Each subcommand:
1. Creates a `*cobra.Command` in its own `new*Cmd()` function
2. At the top of the `Run*` function, calls `checkRemoteMutex(serverName, sshTarget, identityFile)` to enforce the `--server`/`--ssh` mutex and the `--identity requires --ssh` rule (it must run before `os.Getwd()` and `signal.NotifyContext` so spurious setup doesn't run when the flags conflict)
3. Branches in this order: `sshTarget != ""` → `resolveSSHRemote(ctx, sshTarget, projectDir, projectName, identityFile, <factoryVar>)` (passing the subcommand's own injectable factory); else `serverName != ""` → `resolveServerRemote(ctx, serverName, projectDir, projectName, <factoryVar>)`, or the inline equivalent (load config, `FindServer()`, create `RemoteCompose`, `Connect()`, defer `Close()`, `Detect()`); else fall back to local `compose.New(dir)` handed to **`prepareLocalComposer(ctx, lc, projectName)`** (stamps the name, `Detect()`s — and looks NOTHING up) — the two remote helpers take the name as a parameter and stamp it themselves, precisely so a new subcommand cannot silently address the directory's default project instead
4. Is registered in `cmd/root.go` via `rootCmd.AddCommand()`

`cmd/skill.go` (the `skill install|show|uninstall` subcommand, see "Agent Skill distribution" below) is a deliberate exception to this pattern — it operates on local files only and has no `--server`/`--ssh`/`--project-dir`/remote wiring.

`cmd/rollback.go` (the `rollback` subcommand) is a second deliberate exception: rather than reimplementing the composer-branch skeleton, it reuses the deploy machinery via `runOperationWithPrep(ctx, runner.Rollback, …, rollbackPrep(…))` — the shared `runOperationWithPrep` already does the `checkRemoteMutex` → ssh/server/local branching, and `rollbackPrep` is the op-specific pre-run hook (snapshot read + refusal rules + digest-pin prep). See "Adding New Operations" for the prep-hook recipe.

## Agent Skill distribution (`cdeploy skill`)

**`skills/` package**: the repo-root `skills/` directory is BOTH the external-installer convention directory (so `npx skills add lexxzar/compose-deploy` and `gh skill install lexxzar/compose-deploy` find `skills/cdeploy/SKILL.md` on the default branch) AND a Go package holding the `//go:embed cdeploy` directive. `skills.FS` exposes the embedded tree; `skills.CanonicalSkill()` returns the raw, unstamped SKILL.md bytes — the single source of truth for the CLI, external installers, and verification, version-locked to the binary via `go:embed` (panics on a missing embed, since that is a build/packaging fault, not a runtime error to thread).

**`cdeploy skill install|show|uninstall <claude|codex|all>`** (`cmd/skill.go`): installs the embedded skill into agent skill directories. Targets resolve via `skillTargetDirs()`: claude → `~/.claude/skills/cdeploy` (also read by Cursor/OpenCode); codex → `~/.agents/skills/cdeploy` AND `$CODEX_HOME/skills/cdeploy` (default `~/.codex`; an EMPTY `$CODEX_HOME` is treated as unset because `t.Setenv` can set but never unset an env var); all → the deduped union. Dedupe (`resolveDedupeKey`) resolves symlinks on the deepest EXISTING ancestor of each candidate (the target dir usually does not exist yet, and `filepath.EvalSymlinks` errors on missing paths), then re-appends the not-yet-existing suffix, so two candidates pointing at the same physical directory through a symlink collapse to one write. Multi-path install/uninstall aggregate per-path outcomes — one failed destination never aborts the others, and any failure yields a non-zero exit. Per-agent pickup notes are printed to stdout after a successful install. `show` writes the raw unstamped canonical via `cmd.OutOrStdout()` (NOT `os.Stdout` — testable with `cmd.SetOut(&buf)`); it also enables `cdeploy skill show > .claude/skills/cdeploy/SKILL.md` for project-level placement.

**Stamp/hash ownership model**: install never trusts a file it did not write. `renderSkill(canonical, version)` injects a metadata block — `metadata:` header + `cdeploy-version` + `cdeploy-content-hash: sha256(canonical)` — immediately before the frontmatter's CLOSING `---` (the second `---`, found via `frontmatterCloseOffset`; never a bare `---` in the markdown body), so the frontmatter stays the first bytes of the file (Gemini silently skips otherwise). `stripOwned()` removes exactly that block, giving the round-trip invariant `stripOwned(renderSkill(canonical, v)) == canonical` as literal byte-equality; the stamped hash is therefore simply `sha256(canonical)`, no self-reference. `verifySkillFile(onDisk)` answers ONLY "is this file consistent with its OWN stamp?" → `intact` / `modified` / `unstamped` (stripOwned → sha256 → compare to the recorded hash). The install decision needs a SECOND, distinct check — `bytes.Equal(stripOwned(onDisk), canonical)` against THIS binary's canonical bytes — to reach `unchanged` vs stamp-refresh vs updated; without both checks the `unchanged` state is unreachable. Modified or unstamped files (e.g. a copy dropped by `npx skills`) are refused by both install and uninstall without `--force`; uninstall removes only the stamped `SKILL.md`, then the `cdeploy/` dir only when it is empty (never a recursive delete). Dev builds stamp `cdeploy-version: dev` — freshness keys on the content hash, not the version string.

**SKILL.md content test pins** (`skills/skills_test.go`): future edits to `skills/cdeploy/SKILL.md` MUST keep these satisfied — frontmatter is the very first bytes (`---\n` fence with a closing `---`), `name: cdeploy` (matches the directory AND the `^[a-z0-9]+(-[a-z0-9]+)*$` regex), `description` non-empty and ≤1024 chars (and naming both ops and setup triggers: deploy/servers.yml/ssh), under 500 lines, and — load-bearing — NO `metadata:` key in the canonical frontmatter. That last pin is what keeps block insertion/removal trivial: the install-time renderer owns the `metadata:` block and `stripOwned` must round-trip back to exactly the canonical bytes, so a hand-authored `metadata:` key would break the byte-equality invariant.

## Package Coupling

The TUI package depends on `runner.Composer` (interface), not `compose.Compose` or `compose.RemoteCompose` (concrete). For operations that need to create a `Composer` at runtime (drilling into a group, or an action key binding the cursor row's project), use a `ComposerFactory` callback injected from `cmd/` — this keeps `tui` decoupled from `compose`. The factory takes the whole `compose.Project`, not a directory string, so it can branch on `proj.Unmanaged` and return the read-only `compose.HostContainers` for the synthetic `(unmanaged)` group. That same branch is how the grouped host view reaches its host-wide seam: `composerFactory(compose.Project{Unmanaged: true})` type-asserted to `HostGrouper`, so no signature had to widen. Similarly, `ProjectLoader` and `ConnectCallback` are injected by `cmd/` for remote server support. The `compose` package has the `HasComposeFile` package-level function for local compose file detection; project discovery (`ListProjects`) is a method on `Compose`/`RemoteCompose` requiring `Detect()` first. The `ConfigProvider` and `ExecProvider` interfaces are defined in `tui` (not `runner`) because they return `*exec.Cmd` and are TUI-only; the TUI type-asserts `composer.(ConfigProvider)` and `composer.(ExecProvider)` at runtime — no separate factory or wiring needed. `ReadOnlyComposer` is the same shape and the same reason: only `compose.HostContainers` implements it, and a composer that omits it renders the normal writable screen. `Inspector` is the same shape with the reach inverted — ALL THREE composers implement it, so the `i` key is live on every container screen and the type assert exists for test mocks rather than for a capability split. `UpdateDetailer` is `Inspector`'s twin: all three composers implement it, it is asserted the same way, and a composer that omits it simply renders no update rows. `HostGrouper` (two methods over one listing, `GroupHostStatus`/`GroupHostStats`) is the same shape with the narrowest reach: only `compose.HostContainers` implements it, and a factory that cannot produce one yields a grouped screen with projects but no status — not an error.

## Testing Approach

Tests use stdlib `testing` only — no testify or other test frameworks.

- `internal/runner/`: Mock `Composer` interface to verify step sequences and failure behavior without Docker
- `internal/compose/`: Test command construction (args, env vars, flags) without executing commands; `parseProjects()`, `parseContainerStatus()`, `parseStatsOutput()`, `parseSize()`, `parseCPUPercent()`, and `FormatBytes()` extracted for testability; `RemoteCompose` tests verify SSH arg construction and shell escaping; `inspect_test.go` drives `pickInspectContainer`/`pickHostInspectContainer`, `parsePsEntries` and `ParseInspect` against three real `docker inspect` fixtures, and asserts the inspect argv carries no `compose`; `hostcontainers_test.go` drives `HostContainers` through a fake `dockerRunner` (the same seam production uses), so every read method is testable without Docker and the remote adapter's `SSHExtraArgs`-before-host splice is pinned directly; `updatedetails_test.go` drives the four-step detail fetch through that same seam, against real registry captures in `testdata/imagetools_*.json` plus a real `docker image inspect` document in `testdata/image_inspect_nginx.json` (the one thing a hand-authored fixture cannot pin is docker's KEY SPELLING) — **no test may hit a registry**, since a suite that did would reproduce the 429 in CI
- `internal/config/`: Test YAML parsing, validation, and lookup with temp files
- `internal/tui/`: Test model state transitions by calling `Update()` with `tea.KeyMsg` directly — no TTY needed; `entries_test.go` drives the pure row model (`rebuildSvcEntries`, `svcKey`, `buildSvcGroups`, `partitionSelection`, `groupCounts`, `groupSelected`, `eachSelectableRef`, `eachUnfoldedSelectableRef`, `cursorGroup`, `flattenQualified`) with no Model machinery at all. **There is no `services` field on Model at all** — rows come from `svcGroups` → `svcEntries`, so a test that wants a flat name list uses the `modelServices(m)` helper. The grouped host view has its own file, `grouped_test.go` (the row model over several projects, the grouped loader and reload, fold/select, the header line, drill-in/out, action-time binding, the grouped `U` scan), and the multi-batch progress sequence it feeds has `batch_test.go` — put a new test for either subsystem there rather than growing `app_test.go` again. Every container-screen test must go through the fixture helpers — `singleGroupModel(services)` (`app_test.go`) for the degenerate one-group (drilled) shape, `groupedModel(groups…)` + `svcGroupOf(name, services…)` (`grouped_test.go`) for the multi-group host view, `selectedIdx(m, i…)` to build a selection from ROW indices, `qStatus(m, status)` / `qStats(m, stats)` / `qk(m, service)` to qualify a bare-name map or name the way the message handlers do, and `progressStep(name, status)` to build a progress row (`enterProgress` always sets `label` AND `batchStepCount`, so a fixture must too); `format_test.go` tests `formatLogContent()`, `softWrapLine()`, and `prettyPrintLine()` as pure functions; `inspect_test.go` tests `buildInspectSummary()` the same way, against the compose package's fixtures; `help_test.go` pins the `?` overlay (the two-directional drift pin — run PER VARIANT, `TestHelpGroups_NamesEveryBoundKey` for the writable table and `TestHelpGroups_ReadOnlyNamesEveryBoundKey` for the read-only one, plus `TestHelpGroups_ReadOnlyDropsGatedKeys` — the `allScreens` completeness check, the typing/confirmation exceptions, and the never-exceeds-width/height clamps)
- `internal/logging/`: Use `t.TempDir()` for file creation tests
- `skills/`: Content pins on the embedded `cdeploy/SKILL.md` (frontmatter first, `name` matches dir + regex, description ≤1024 chars, <500 lines, no `metadata:` key) — see "Agent Skill distribution" above
- `cmd/`: Test flag registration, subcommand existence, and validation via `NewRootCmd()`; `cmd/skill_test.go` uses `t.Setenv` HOME/CODEX_HOME (never `t.Parallel`) for the path matrix, symlink dedupe, and the install/uninstall decision matrix in a temp HOME (render/verify round-trip is pure)
