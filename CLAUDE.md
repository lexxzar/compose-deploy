# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Test Commands

```bash
go build -o cdeploy .          # Build binary
go test ./...                   # Run all tests
go test ./internal/runner/ -v   # Run tests for a single package
go test ./... -count=1          # Run all tests uncached
go mod tidy                     # After adding/removing imports
```

The root command launches a Bubble Tea TUI requiring a TTY, so `cmd/root_test.go` tests flag registration and subcommand structure rather than executing the root command directly.

## Architecture

cdeploy is a dual-mode tool: interactive TUI (no args) or non-interactive CLI (`deploy`/`restart`/`stop`/`list`/`logs`/`exec` subcommands). Both modes share the same core through a three-layer architecture:

```
cmd/ (Cobra)  →  runner (pipeline orchestrator)  →  compose (docker CLI wrapper)
tui/ (Bubble Tea) ↗
```

Seven subsystems carry their full rationale, failure modes and test pins in `docs/architecture/`; the paragraphs below carry the rules only. **Read the matching file before you change one of them** — each rule there exists because it was violated once.

- `docs/architecture/tui-help-overlay.md` — the `?` overlay, the container footer, the `q` back key
- `docs/architecture/tui-logs-and-search.md` — container search, log streaming, formatting, filter and search
- `docs/architecture/tui-inspect-screen.md` — the `i` inspect screen and `internal/compose/inspect.go`
- `docs/architecture/wait-snapshots-rollback.md` — the `--wait` gate, deploy snapshots, the rollback pipeline
- `docs/architecture/update-detection.md` — the `⇧` glyph, digest comparison, failure cascades, the TUI cache
- `docs/architecture/unmanaged-containers.md` — `HostContainers`, the `(unmanaged)` group, the read-only UI contract
- `docs/architecture/tui-multi-project.md` — the grouped host view, `svcKey`, batch sequencing, grouped updates

**Key abstraction**: `runner.Composer` interface (defined in `internal/runner/runner.go`, implemented by `internal/compose/compose.go` for local, `internal/compose/remote.go` for SSH, and `internal/compose/hostcontainers.go` for the read-only unmanaged-container view). This is the seam between the orchestrator and Docker — the runner is testable with mock implementations. Methods: `Stop`, `Remove`, `Pull`, `Create`, `Start`, `ListServices`, `ContainerStatus`, `ContainerStats`, `CheckUpdates`, `Logs`. When widening this interface, every mock implementation must add a matching no-op — there are mocks in `internal/runner/`, `internal/tui/app_test.go` (`mockComposer`), `cmd/deploy_test.go` (`opMockComposer`), and `cmd/list_test.go` (`mockComposer`, `mockComposerStatusErr`); a fast `grep -rn "func.*Composer.*ListServices" ./...` enumerates them.

**Event system**: `runner.Run()` sends `StepEvent` structs through a channel. The CLI consumer (`cmd/deploy.go:runOperation`) prints colored status lines. The TUI consumer (`internal/tui/app.go`) drives a Bubble Tea model through `tea.Cmd` that reads from the channel.

**TUI state machine**: Eight screens: `screenSelectServer` → `screenSelectContainers` → `screenProgress` (for operations), `screenLogs` (for log viewing), `screenConfig` (for config viewing/editing), or `screenInspect` (for the read-only container inspect view), plus `screenSettingsList`/`screenSettingsForm`. **There is NO project-select screen** — the container screen's GROUPED mode replaced it (`m.grouped`; every compose project on the host is a foldable group plus the synthetic `(unmanaged)` one), and picking a project is a drill-in state change on the same screen rather than a screen transition — see the six `Multi-project host view — …` paragraphs below. The server screen is shown whenever servers are configured in `~/.cdeploy/servers.yml`; selecting "Local" fast-tracks to the DRILLED single-project container screen if a local compose file exists, and lands on the grouped host view otherwise. The model is a flat struct with a `screen` field determining which view/update logic runs. Operations are triggered via action keys on the container screen (`r` restart, `d` deploy, `s` stop) which enter a confirmation sub-state (`confirming` bool + `pendingOp`) before proceeding. The `x` key execs into a running container interactively (enters confirmation with `pendingExec = true`, then shells out via `tea.ExecProcess`; shows warning if container is not running). The `l` key opens the log viewer for the cursor service without confirmation (read-only operation). The `c` key opens the config screen without confirmation (read-only by default). The `i` key opens the inspect screen for the cursor service, also without confirmation, and is the one container action key that is NOT gated on `m.readOnly()` — see the "Inspect screen" paragraph below. Back-navigation (`esc`, also aliased to `q` on nested screens — see "Exit confirmation for remote connections" below) resets downstream state; during confirmation, `esc` cancels without navigating back. The grouped host view is skipped entirely when the current directory contains a compose file and no servers are configured (backward compatible). `Compose.ListProjects()` discovers projects via `docker compose ls -a --format json`; both `ProjectLoader` literals in `cmd/root.go` are plain `ListProjects` and append NOTHING — that loader feeds `loadGroups()` and supplies the grouped screen's row ORDER, while the synthetic `(unmanaged)` group comes from `buildSvcGroups`'s leftover path off the host-wide `docker ps` the same refresh already made; see the three `Unmanaged containers — …` paragraphs below.

**Exit confirmation for remote connections**: `ctrl+c` is the hard-exit shortcut from any screen. When a remote SSH connection is active (`disconnectFunc != nil`), pressing `ctrl+c` shows a confirmation prompt instead of quitting immediately. The `quitting bool` field on Model gates a global intercept at the top of `handleKey()`: `y` quits, `n`/`esc` cancels, all other keys are swallowed. `View()` checks `quitting` first and renders a standalone confirmation screen via `viewQuitConfirm()` (`"Disconnect from {serverName}? (y/n)"`). The `tryQuit()` helper replaces direct `return m, tea.Quit` calls on all screens except `screenSelectServer` (which always quits immediately since no remote connection exists there). `quitting` is reset to `false` in `esc` back-navigation handlers that clear `disconnectFunc` and in the `entryLocal` handler. Local sessions (`disconnectFunc == nil`) bypass the prompt entirely — `tryQuit()` returns `tea.Quit` directly.

**`?` key-reference overlay**: `?` opens a full-screen key list for the current screen. It is a flag (`helpOpen bool` on Model), **never a screen constant** (back-navigation, `clearSearch()`, the session counters). `View()` checks it right after `quitting`, returning `viewHelp()`. `helpGroupsFor(s, hc helpContext)` (`internal/tui/help.go`) covers all 8 screens; the context bits travel in a NAMED `helpContext{canGoBack, readOnly, grouped, phase, midSequence}`, never adjacent same-typed parameters. **Group ORDER is load-bearing**: `splitHelpGroups` cuts sequentially, so LEAVE must stay 4th of 6 on `screenSelectContainers` and 3rd of 4 in `readOnlyContainerGroups` and on `screenLogs` — do not reorder for readability. **The position is unchanged but the left-column guarantee it used to buy is now DRILLED-only**: the `pgup pgdown` row moved the grouped cut a group up, so grouped splits `MOVE FIND SELECT | LEAVE OPERATE INSPECT` (16/16) and renders LEAVE at the TOP of the RIGHT column, while drilled still cuts after LEAVE (17/13) and both read-only variants keep it left (13/6) — column membership is pinned by `TestSplitHelpGroups_Balances`, which runs BOTH container variants. LEAVE is conditional (`leaveGroup(canGoBack)` renders `q quit` instead of `q esc → back`; `esc` stays BOUND on a standalone screen but is not a way out, so the group must not name it), and `Model.canGoBack()` is the single predicate behind BOTH it and the footer's `back` label. `screenProgress` is conditional on a THREE-state phase, since `esc` changes meaning per phase (running: `esc` CANCELS the op — and marks it `failed`, so the screen is always escapable — while `q`/`ctrl+c` no-op; waiting: `q`/`esc` skip the health wait and `ctrl+c` quits, because a mid-sequence gate opens with `done` and `failed` BOTH false and the two guards read `m.waiting` as terminal-enough; finished: they go back), so `Model.progressPhase()` MUST resolve in the SAME order as `viewProgress()`'s footer switch (`waiting` FIRST — **not** "because it implies `done`", which stopped being true when the per-batch gate landed: a gate can be open with `done` set (the last batch), with `failed` set, or with neither (a mid-sequence batch), and only the waiting-first order names `esc` correctly in all three); never one static table. `helpGroup.actions bool` marks groups whose keys are advertised nowhere else; `singleColumnOrder()` emits them first in the single-column fallback, FIND stays split out of MOVE so `/` and `n N` keep that flag, and a new action row moves every truncation threshold **of the variant it lands in** — grouped `selectGroup` gained two rows (`← →`, `z`), taking that table to 33/28 rows and 21 action rows against the drilled 31/26/19, so every grouped HEIGHT threshold sits two notches higher (full fit 26 against 24) and `TestViewHelp_InspectSurvivesTheFirstTruncation` now measures BOTH; never extrapolate one column from the other. **A row in unflagged MOVE moves the row counts and every WIDTH threshold but no HEIGHT threshold** (the fallback already emits MOVE last, so the budget was cutting rows below it): `pgup pgdown` — 11 cells, the widest key label in all four container tables — took the two-column thresholds to 70 drilled / 87 grouped / 75 read-only drilled / 100 read-only grouped, pinned per variant by `TestViewHelp_TwoColumnThresholdPerVariant` because the older width pins sample the DRILLED table only. **Accepted regression**: in GROUPED mode at widths 77-86 and height 24 — 80x24 included — the overlay drops `x exec` and `U check updates`, whose only home it is; they return at width >= 87 or height >= 26. Do NOT shorten a label or a description to close it — that was weighed and refused, and the pin fails in both directions. Full rationale: `docs/architecture/tui-help-overlay.md`. `layoutHelpColumns`/`budgetHelpRows` clamp row width and count (`m.height` minus chrome, floor 1). **`viewHelp()` must NOT end its string in a newline, and the height tests must NOT trim one**: bubbletea keeps the LAST `m.height` of the `\n`-split `View()`, so one costs the title (`viewSelectContainers()`/`viewLogs()` too). **Intercept order in `handleKey()` is load-bearing**: (1) the `quitting` intercept, (2) the `helpOpen` swallow, (3) the `?` open, (4) the `q`→`esc` rewrite — the swallow MUST precede the open. Close keys are `?`, `esc`, `q`; every other key is swallowed. **`ctrl+c` clears `helpOpen` and FALLS THROUGH** instead of returning, so each screen's own `ctrl+c` semantics apply unchanged — including the mid-progress no-op. The open block is gated on `!m.typingInInput() && !m.confirmPromptArmed()`; **`confirmPromptArmed()` is screen-SCOPED** (`screenSelectContainers` → `m.confirming`, `screenSettingsList` → `m.settingsDelete`, else false) and a flat `!m.confirming` is WRONG — `enterProgress()` never clears `confirming`. `connectResultMsg` clears `m.helpOpen` on BOTH branches and `rollbackSnapshotMsg` clears it beside its `m.confirming = true`: **any future handler that arms a confirmation must do the same**. `typingInInput()` (`m.searching`; `m.logFiltering || m.logSearching`; `m.settingsField < 4` — that form, not `!= 4`) gates BOTH the `?` open and the `q` rewrite, so **a new screen that opens a text input needs one case there and nothing else**. Extend the key set in `TestHelpGroups_NamesEveryBoundKey` (and its read-only twin) whenever you bind a key — it fails BOTH directions — but **a GROUPED-ONLY key goes in a different pin**: that test names the DRILLED variant, so `←`/`→`/`z` are absent from its set and live in `TestHelpGroups_GroupedNamesTheSameKeys`'s `groupedOnly` list, which is no longer a plain two-way equality but `drilled ∪ {z, left, right}` checked three ways (grouped names everything drilled does, grouped names nothing outside that union, and drilled names none of the three) — and move `TestAllScreens_Complete`'s bound to `int(<new last screen>) + 1` per screen added, or table tests skip it. **A key bound only in a sub-state needs a description that NAMES it**: `enter  confirm the prompt`.

**Container footer and the one-line width guard**: `containerFooter()` renders it, `containerFooterLines()` counts its physical lines; `svcVisibleCount()` reserves `2 + containerFooterLines()` and `containerFooter()` **pads every state out to that same count**. Both read `containerHelpLines()`, the single home of the idle pair (`back` via `canGoBack()`, read-only AND grouped variants included — THREE pairs). **The footer must advertise only keys the current state binds**: a committed search replaces `line2` wholesale with `n/N cycle • esc clear`, which is why `back` and `? keys` must live in `line1`; a TYPING search binds only `enter`/`esc`/`ctrl+c`, so the whole footer becomes `enter jump • esc cancel`. **The line COUNT stays state-independent** — decided from the idle pair alone, BEFORE any substitution, with the shorter states padded back by a trailing `\n` (the typing footer, and the confirm prompt). The one-versus-two-line guard measures `m.width >= ansi.StringWidth(oneLine)+2`, NOT `len(oneLine)+2` — **do not reintroduce `len()`**. A substitution can be WIDER than the idle `line2`, so `containerFooter()` clamps every line with `clampToWidth` rather than widening the count. Six tokens on the drilled write path; the read-only pair carries four (`back`, `? keys`, `l logs`, `x exec`); the GROUPED pair carries six but swaps `space toggle` → `space fold/select` and `l logs` → `enter drill in`, because a group header is the row only grouped mode has. Every other container key — `a`, `/`, `n N`, `i`, `c`, `U`, `R`, `x`, `pgup pgdown`, `l` in grouped mode, and the three grouped-only fold keys `←`, `→` and `z` — lives in the `?` overlay only: the grouped pair is already at six tokens, so a fold key could only enter the footer by evicting one that has no other home.

**`q` as back key on nested screens**: the 4th `handleKey()` intercept rewrites `q` to `esc` on nested screens; the existing `esc` handlers do the cleanup — **do not add parallel `q` handlers**. `q` quits directly only on root screens: (1) `screenSelectServer` always; (2) `screenSelectContainers` when `!m.canGoBack() && !m.confirming` — which is the GROUPED screen with no servers and no config, or the DRILLED screen with `!m.drilledFromHost` (a standalone `cdeploy` launched in a directory holding a compose file). `drilledFromHost` is the renamed `showPicker` and carries that rule: no predicate derivable from the composer, the factory or the group list separates a drill-in from a standalone launch, so the entry sites record it. `screenProgress` while `!done && !failed && !m.waiting` is a no-op for `q` (`ctrl+c` too) — an in-flight operation must not be cancelled; an OPEN HEALTH GATE is not one, and a mid-sequence gate opens with `done` and `failed` BOTH false, so without the `!m.waiting` term `q` went dead for a whole wait timeout per batch while the overlay still advertised it. The rewrite is skipped when `m.typingInInput()` — `q` must reach an open input as a literal rune. `ctrl+c` is unchanged — `tryQuit()`, and the remote disconnect prompt. Full rationale and test pins: `docs/architecture/tui-help-overlay.md`.

**Backward-navigation state cleanup**: When navigating backward (`esc`) or handling errors (e.g. `connectResultMsg` failure), all mutable callbacks (`composerFactory`, `projectLoader`, `disconnectFunc`) must be explicitly cleared or restored to their local defaults (`localFactory`, `localComposer`, `localProjectLoader`). Bubble Tea's value-type model means stale closures silently persist across screen transitions. Every new callback field added to Model needs corresponding cleanup in: (1) `backToServerScreen()` (`esc` from the grouped host view), (2) `enterGroupedContainers()` (`esc` drill-out from the drilled screen, and every other landing site), (3) `entryLocal` handler, (4) `connectResultMsg` error path. `drillIntoGroup()` is the fifth site for anything the drilled screen owns.

**Stale async message guard**: Goroutines spawned by a screen (e.g., `readLogChunk` for `screenLogs`) may deliver messages after the user has navigated away. Message handlers for screen-specific async messages (`logChunkMsg`, `logDoneMsg`) must check `m.screen` and discard stale messages — otherwise they will read nil fields cleared by `esc` cleanup and panic. A monotonic `logsSession` counter provides additional stale-message rejection. This pattern applies to any future screen that spawns background goroutines.

**Service list scrolling**: The container select screen uses `svcOffset` to track the first visible ROW (`m.svcEntries`, so a group header consumes one exactly like a service does) when the list exceeds terminal height. `svcVisibleCount()` calculates available lines: `m.height - headerLines - footerLines` (min 1), returning `len(m.svcEntries)` when `m.height == 0` for backward compat. Line counts account for lipgloss margins: `titleStyle` has `MarginBottom(1)` (adds a space-padded line), `helpStyle` has `MarginTop(1)` (adds a space-padded line), so header=3 (or 4 with column captions) and footer=3+ (not 2). A conditional column captions row ("Created", "Uptime") is rendered above the service list when any service has non-empty `Created` or `Uptime` data; `hasStatusColumns()` checks this and `svcVisibleCount()` adds 1 to `headerLines` accordingly. The captions use `descStyle` and are left-padded to align with data columns (10 + maxName offset). `fixSvcOffset()` ensures cursor visibility after any state change that affects visible count — cursor movement, window resize, confirming/warning state change. **`svcVisibleCount()` is ALSO the `pgup`/`pgdown` step**, so the two keys overshoot by design: a `pgdown` from the top of the window lands one row past its bottom edge and `fixSvcOffset()` scrolls the window by one, which is what makes a page land on the row after the one the user just read. The step therefore needs `clampSvcCursor()` before `fixSvcOffset()` (the latter moves only the WINDOW), and it degenerates to end/home whenever the list fits the pane — including the unsized `m.height == 0` first frame, where `svcVisibleCount()` returns the whole row count. Scroll indicators (`▲ N more` / `▼ N more`) replace existing blank-line content between breadcrumb/services and services/help, so they never change the total line count used by `svcVisibleCount()`; in grouped mode both indicators and the caption pad carry the service rows' 2-cell indent. `svcOffset` is reset to 0 alongside `svcCursor` in the DRILLED `servicesMsg` branch and at every landing/drill site — **never in the grouped `servicesMsg` branch**, which is also the 5s reload and must preserve cursor, selection, fold and search; it calls `restoreCursorRow(cursorRowID())` + `fixSvcOffset()` instead (`fixSvcOffset` moves only the WINDOW, so a shrinking row count needs the separate clamp `restoreCursorRow` ends with). **The cursor survives by IDENTITY, not by index** — `svcRowID{proj, service, header}` captured BEFORE `setGroups` and looked up after, the same rule the fold state (project name) and the selection (`svcKey`) already use: the rows come from a live `docker ps`, so a container started or removed ANYWHERE on the host inserts or deletes a row and slides every index below it, re-aiming drill-in, `l`/`i`/`c`/`U` and — through the empty-selection rule — the whole-project `d`/`r`/`s`, every 5 seconds without a keystroke.

**Container search (search & jump)**: `/` is search-and-jump, **not a filter** — never narrow the rows, never touch `m.selected`; only `svcCursor` moves and matches highlight. A folded group DOES open for it: `unfoldSearchMatches(query)` runs before the indices are computed, because a folded group contributes no service ROW and a hidden row cannot be jumped to; the unfold is NOT undone when the search is cancelled. *Committed* is `searchQuery != "" && !searching`; highlighting and `n`/`N` key off `searchQuery != ""` alone. `computeMatches(m.svcEntries, query)` matches SERVICE entries only (never a group header) and returns **ascending** ENTRY indices (`nil` for an empty query) — `cycleMatch`'s wrap and off-match jumps rely on that ordering, and **every fold and every grouped reload must re-derive `searchMatches`** because the rebuild renumbers the rows those indices point at. **Ephemeral-on-departure invariant**: `m.clearSearch()` runs on **every** transition that leaves `screenSelectContainers` or reloads the rows — the 11 sites are `servicesMsg` (drilled branch), `connectResultMsg` error path, `entryLocal`, `enterProgress()`, `enterConfig()`, `enterInspect()`, `enterExec()`, `enterLogs()`, `enterGroupedContainers()` (drill-out + every landing), `drillIntoGroup()`, `backToServerScreen()`. **Two-stage `esc`**: the guard at the top of `case "esc"` clears a committed search plus `fixSvcOffset()` and stays on screen, a second `esc` back-navs, and `esc` while typing restores `svcCursor` to `searchReturn` and consumes the key — through `searchReturnID` (an `svcRowID`) FIRST, falling back to the raw index: typing UNFOLDS a group holding a match and the 5s grouped reload rebuilds the rows, so the index alone restored the cursor to a different row. Reopening `/` over a committed search calls `clearSearch()` FIRST; `searchInput` is built by `textinput.New()` in the `/` handler — **not** in `NewModel` (`Model{}` test literals). The bar line is **always reserved** (blank when idle, blank while confirming) — `viewSelectContainers()` writes it in both the `confirming` early-return branch and the normal one, but it costs NO extra row in `svcVisibleCount()`: it merges with `helpStyle`'s MarginTop blank, so counting it separately over-reserves a row. **One-physical-line invariant**: `searchBarLine()` MUST render exactly one physical line — size the typing `textinput.Width` to the pane and clamp with `clampToWidth()` (no-op at `m.width <= 0`); style only the raw name so width math is unaffected. The `q`→`esc` rewrite is skipped while `m.searching`, via `typingInInput()`.

**Multi-project host view — grouped vs drilled, the entry model, and `svcKey`**: the container screen has TWO modes and ONE row model. GROUPED (`m.grouped`) is the host view — every compose project plus the synthetic `(unmanaged)` bucket, each a foldable group; DRILLED is the single-project screen, reached by `enter` on ANY grouped row or by the local fast track. **`m.grouped` is an explicit field, NEVER a `len(svcGroups) > 1` inference** (a host can run exactly one project; the drilled screen is always one group). `svcGroup{proj, services, folded}` is the source of truth and `svcEntry{kind, groupIdx, name}` is DERIVED by `rebuildSvcEntries` — `setSingleGroup`/`setGroups` are the only writers, `clearSvcGroups` the only wipe, and **a single group emits NO header**, which is what makes the drilled render byte-identical to pre-grouping. The header/indent predicate is `groupsHaveHeaders(groups)` (`len(groups) > 1`), **not `m.grouped`** — one predicate feeds both the entry model and the renderer. **Folding hides ROWS, never services**: `svcRefs()` ignores fold state, so selection, counting and column widths read it rather than `svcEntries` — with ONE deliberate exception, the fold-aware `a` (see the fold paragraph). **Nothing may be keyed on a ROW INDEX across a rebuild** — a fold renumbers every row, which is why `m.selected` is `map[string]bool` keyed by `svcKey(proj, svc)` = `proj + "/" + svc` (`/` is safe: compose rejects it in both names). **Qualified keys live ONLY inside the tui Model** (`svcStatus`, `stats`, `selected`, the render caches); every message boundary converts — `qualifyMap(projName, src)` for a drilled bare-name payload, `flattenQualified(host)` for the grouped one — and **nothing qualified reaches `runner`/`compose`**: `selectedContainers()`, `opContainers`, `rollbackTargets` and the `NewWaitState` seed stay BARE (`TestQualifiedKeys_NeverCrossIntoRunner`). Row helpers live in `internal/tui/entries.go`, not `app.go`: `svcKeyAt` (the OWNING group decides the prefix), `cursorEntry`, `cursorService` (false on a header — every "service under the cursor" key reads it), `cursorGroup` (accepts a header; a header IS its group), `groupUnmanaged`, `eachSelectableRef` (`eachSvcRef` minus unmanaged), `eachUnfoldedSelectableRef` (that minus the rows a FOLD hides — **two callers only**, see the fold paragraph), `groupSelected` (the header's `[x] n/m`), `clampSvcCursor` (`fixSvcOffset` moves only the WINDOW). **There is no flat `m.services` field** — `svcGroups` is the ONE representation, and its nil-versus-empty distinction carries the loading state: nil = still loading, empty non-nil = a real empty host.

**Multi-project host view — `HostGrouper`, the grouped loader, and the refresh dispatch**: `HostGrouper` is TWO methods over ONE listing — `GroupHostStatus(ctx) (compose.GroupedHostSnapshot, error)`, whose snapshot carries a project → service status map plus the OPAQUE `compose.HostEntries` handle for the listing it was folded from, and `GroupHostStats(ctx, compose.HostEntries)`, which joins CPU/memory against that same handle — declared in `tui` and type-asserted, reached through `composerFactory(compose.Project{Unmanaged: true})` — so **no existing signature changes**. **The halves must stay ONE listing, and must NOT be ONE call**: the handle is what keeps the pair at a single `docker ps` (two self-listing methods paid it twice per 5s tick over the same SSH hop), while a merged call put `docker stats --no-stream` — 2.084s on a 7-container daemon, against 0.056s for `compose ls` and 0.033s for `docker ps` — in front of the FIRST PAINTED ROW and in front of every 5s reload, a 25x first-paint regression. `GroupHostStatus` must make NO stats call (`TestHostContainers_GroupHostStatus_MakesNoStatsCall`). **The handle is opaque AND STAMPED**: any package can write `compose.HostEntries{}`, so opacity alone guaranteed nothing — a zero handle joined against nothing and `GroupHostStats` answered it `(nil, nil)`, the SAME answer an empty host gives, so a dropped listing and a quiet host were one blank CPU/Mem column apart with nothing red anywhere. Only `GroupHostStatus` sets the unexported `listed` flag, `HostEntries.Listed()` exposes it, and `GroupHostStats` REFUSES an unstamped handle with `errUnlistedHostEntries` (`TestHostContainers_GroupHostStats_ZeroHandleIsRefused`); an empty HOST still gets a stamped handle and still reaches docker not at all (`TestHostContainers_GroupHostStats_EmptyStampedHandleMakesNoCall`). A factory with no `HostGrouper` behind it is **not an error**: the loader's projects render with no status. The screen costs a CONSTANT number of calls regardless of project count — `docker compose ls -a` + one `hostPsArgs` `docker ps -a` (+ one `docker stats --no-stream`) — which is the whole point over an SSH hop. `GroupHostStatus` reads the `com.docker.compose.project=`/`.service=` label VALUES via `labelValue` (token-start match, value to the next comma — **safe for these two keys only**, both name-constrained); no-label containers form the `UnmanagedProjectName` bucket, a managed container missing the service label falls back to its container name, and replica aggregation mirrors `parseContainerStatus` exactly. **Accepted gap**: a never-created service has no container, so no grouped row — drill-in (`ListServices`) shows it, and a whole-group op does not inherit the gap (empty batch slice = ALL services). `loadGroups()` merges loader + `GroupHostStatus` through the pure `buildSvcGroups(projects, host, prev)` into a `servicesMsg` carrying the ROWS plus the `hostEntries` handle — never the stats. **`statsRefreshCmd()` is STILL nil in grouped mode**, but for a new reason: the stats half needs a listing that does not exist until the status half returns, so it is CHAINED off the arrival (`groupedStatsCmd`, riding `statsSession`) rather than batched beside it. **The chain takes BOTH the seam and the listing from the ARRIVAL, captured at DISPATCH** — never a second `m.hostGrouper()` resolution in the handler, the same rule `updatesMsg.forKey` carries; `m.composerFactory` is mutable and the disagreeing direction handed a freshly built grouper the zero handle. `entries.Listed()` is the gate, so "the cycle ends here" is a property of the PAYLOAD (`TestGroupedStatsChain_UsesTheArrivalsSeam`, `TestGroupedStatsChain_RefusesAnUnstampedListing`). **`groupedStatsCmd` runs under `context.WithTimeout(m.ctx, groupedStatsTimeout)`** — the re-arm below rests on that message arriving, and `m.ctx` has no deadline and no `dockerRunner` adds one, so a wedged SSH ControlMaster that returns `docker ps` and then hangs on `docker stats` latched the guard and froze the host view for the rest of the session; an expiry degrades to an ordinary `statsErr` — soft warning, blank cells, guard cleared, loop alive (`TestGroupedStatsChain_IsDeadlineBounded`, `TestGroupedStatsChain_TimeoutClearsTheGuard`). Same bound and same reason as `updateDetailsTimeout` and `pollWaitStatus`. **The guard is settled in TWO steps and the rule is "the arrival that ENDS the cycle clears it"**: the grouped `servicesMsg` branch clears `refreshInFlight` unconditionally BEFORE its screen check, exactly as `statsMsg` does, and the ONE branch that accepts the payload and chains the stats half RE-ARMS it beside the `tea.Cmd` whose `statsMsg` clears it again. **Multi-project host view — fold, header aggregates, and grouped rendering**: `space` carries TWO meanings decided by the ROW — a header folds, a service selects, an unmanaged row is a no-op — and **each branch calls `fixSvcOffset()` first** (the dispatch clears `m.warning` above the switch, freeing a row). **Every fold goes through `settleFold`, and it is FIVE steps, not four**: rebuild entries, re-derive `searchMatches`, **aim the cursor at the folded group's OWN header**, clamp, fix the offset. The aim is what the `←`/`z` keys need — a fold from a service row deletes the row the cursor sat on, and aiming at the FIRST header instead jumps to the top of the host every time the user closes the second project (`TestGroupedFold_AimsAtTheCursorsOwnGroupHeader`); a miss is a real state (a lone unfolded group emits no header), so the clamp behind it settles the cursor. **A fold that changes nothing settles nothing** — `foldGroupAt` early-returns on an already-equal state, because the directional keys land on an already-folded (already-open) group routinely and re-aiming there moves the cursor for a keypress that changed no row. `groupHeaderLine` draws `▼ name   ● n up  ✗ n  ⇧ n  [x] n/m` (`▶` folded); `✗`/`⇧` only when non-zero, and **an empty group renders a BARE header** ("0 up" for a project with nothing to run reads as a fault it is not). `groupCounts` reads `svcStatus` through the qualified key and counts a missing entry as none of the three. **The `[x] n/m` cell is LAST and draws under THREE conditions** — only when `n > 0`, never on the unmanaged bucket, never on an empty group (the bare-header rule stands) — so a group with nothing ticked renders byte-identically to the pre-cell header and `space` never shifts the aggregates left of it. It comes from `groupSelected(g, selected)`, a SIBLING of `groupCounts` and not a fifth return value on it: the two read different things (live docker state off `svcStatus` versus the UI selection) and only this one needs the unmanaged gate. **Folding hides the ROWS, not the selection, so the header is the ONE place a folded group's selection can still be seen** — which is what makes the fold-aware `a` below readable rather than silent. Service rows indent 2 cells off `groupsHaveHeaders(m.svcGroups)`; the caption pad (10 writable / 7 read-only) and both scroll indicators add the same offset. **`svcVisibleCount` math is UNCHANGED** — a header is an ordinary row; column widths come from `svcRefs()` so folding never shifts an open group's columns. **Unmanaged rows draw NO checkbox but KEEP its 3 cells**, and no selection question may be answered over a row whose checkbox is not drawn — every one of them walks `eachSelectableRef()`. **`a` is FOLD-AWARE; every other selection read stays HOST-WIDE, and the split IS the safety rule**: `a` (via `toggleSelectAll()`) and `allVisibleSelected()` — the RENAMED `allSelected()`, and the toggle DIRECTION for that same key, so it must walk exactly what the key writes — go through `eachUnfoldedSelectableRef()`, while `selectedContainers()`, `selectedCount()`, `selectableCount()` and `partitionSelection()` do NOT. The grouped view LANDS folded, so a host-wide `a` ticked every service on the box while the only thing that moved on screen was one digit of the title counter. Scoping the READS as well would drop a service the user genuinely selected BEFORE folding its group, so the operation would touch fewer services than the confirmation prompt just named. **The title denominator therefore stays host-wide and `(2/6 selected)` after `a` on a partly-folded host is CORRECT** — the gap is the signal that a selection reaches past the fold, and the header's `[x] n/m` names where. **An `a` whose fold-aware walk writes NOTHING refuses**, with `warnAllSelectableFolded` ("No selectable service is visible — unfold a group to select one") and `fixSvcOffset()` first like every other gated container key; the refusal is gated on `selectableCount() > 0`, which keeps a still-loading or empty host silent (it has no fold to blame) and keeps the DRILLED screen byte-identical (`TestSelectContainers_SelectAllDrilledIgnoresTheFoldRule`, `TestGroupedSelectAll_ScopedToTheUnfoldedGroups`, `TestGroupedSelectAll_FoldedSelectionStillReachesTheRunner`, `TestGroupedSelectAll_EverySelectableFoldedWarns`, `TestGroupedSelectAll_NothingSelectableStaysSilent`). The word is SELECTABLE, not visible: an unfolded `(unmanaged)` bucket can be drawing rows while every compose group is shut, and those rows carry no checkbox. The footer's third idle pair and the `?` overlay's `selectGroup(grouped)` are covered in the two help paragraphs above; the grouped SELECT row for `a` reads `all visible` while the DRILLED one keeps the bare `all` (that screen has no fold, so the qualifier would name a distinction it cannot make) — a DESCRIPTION-only change, invisible to the TOKEN-set pin `TestHelpGroups_GroupedNamesTheSameKeys`, and it moved no two-column threshold and no truncation height in any of the four container variants (`all visible` is 11 cells against a left column already sized by `drill into the project · confirm the prompt`); `enter  drill into the project · confirm the prompt` is ONE row in SELECT and **OPERATE drops its own `enter` row while grouped** (one key must not occupy two rows of one table — the same fold `inspectGroup`'s read-only `enter` already carries), and the drill-in half answers on EVERY grouped row — header-only stranded the single-project host, which emits no header at all, and `TestHelpGroups_GroupedNamesTheSameKeys` pins the grouped token set against the writable one — **no longer a plain equality**, since `← →` and `z` are the first grouped-only keys on this screen: it is `drilled ∪ {z, left, right}`, and that three-name `groupedOnly` list is the only hand-maintained one left. **The fold keys are grouped-only and write-only** (`!m.readOnly() && m.grouped`, each refusal calling `fixSvcOffset()` first): `←` folds the cursor's group, `→` unfolds it, `z` folds every group while any is open and unfolds every group otherwise — the shape `a` already carries. The arrows act on the cursor's GROUP from a SERVICE row as well as from its header, which is the whole point: `space` folds only from the header, and twenty rows into a project that means scrolling back up to close it. **The arrows are DIRECTIONAL, never a toggle**, so a held key settles instead of oscillating (`TestGroupedFold_ArrowsAreDirectional`, `TestGroupedFold_LeftFoldsFromAServiceRow`, `TestGroupedFold_FoldAllTogglesEveryGroup`). **Fold-all is `z`, NOT `Z`** — uppercase on this screen marks a key with a lowercase sibling (`R`/`r`, `N`/`n`) or one that costs something (`U`, a registry round trip per image), and a fold is neither: free, local, and display-only — it touches no container. The rule is SCREEN-scoped and does not generalise: `screenLogs`' `G` is free and local too, and has no `g`. **Uppercase `Z` must stay UNBOUND** (`TestGroupedFold_UppercaseZIsNotBound` asserts both directions, and its unfold-direction fixture folds EVERY group first — against a partly-open host `foldAllGroups(anyGroupUnfolded())` reads one open group as "fold everything", so a still-bound `Z` folds, leaves the already-folded group folded, and passes). The dispatch's existing intercepts own the rest and each is pinned: inert drilled and read-only (`TestGroupedFold_KeysAreInertDrilledAndReadOnly`), literal while the search bar is open (`TestGroupedFold_KeysAreLiteralWhileSearching`), swallowed behind the `?` overlay (`TestHelpOverlay_SwallowsEveryActionKey`'s grouped case), inert behind an `svcErr` (`TestGroupedFold_KeysInertOnTheErrorScreen`) and inert while a confirmation is armed (`TestGroupedFold_KeysInertWhileAConfirmationIsArmed`) — a fold re-aims the cursor, and the armed prompt's `enter` re-resolves its batch from that cursor. Routing: `toggleGroupFold`/`foldGroupAt`/`foldAllGroups`/`setAllFolded`/`settleFold`/`aimCursorAtGroupHeader`/`anyGroupUnfolded`/`cursorGroupIdx` — `cursorGroupIdx` exists because the fold keys WRITE the group and `cursorGroup` hands back a copy. **The grouped host view LANDS FOLDED, once, through the one-shot `groupFoldPending`.** It is armed at exactly TWO sites and neither implies the other: `enterGroupedContainers()` (connect success, `entryLocal` without a local composer, drill-out) and **`NewModel`'s own grouped branch**, which sets `m.grouped` inline and runs no transition helper — without its own arm the bare `cdeploy` launch with no compose file and no `servers.yml`, the case the host view exists for, landed open. **`enterGroupedContainers()` calls `clearContainerScreen()` FIRST and arms AFTER**, because that helper drops the flag with the rows it names, so arming above the clear is a silent no-op; `drillIntoGroup()` is the one departure site that does not call the helper and disarms by hand (`TestGroupFoldPending_SettledAtEveryNavigationSite` covers all five sites). `applyPendingGroupFold()` spends it in the grouped `servicesMsg` branch, **between `setGroups` and every re-derive below it** — a fold renumbers every row and `searchMatches` holds ROW indices (`TestGroupedLanding_FoldsBeforeTheRowDerivedStateSettles`). **One-shot is the whole point**: that branch is also the 5s reload, so a flat fold-on-grouped-payload re-folds every group the user opened, every tick (`TestGroupedLanding_FoldFiresOnceNotOnEveryReload`). **`len == 0` and `len == 1` are DIFFERENT answers**: one group spends the flag WITHOUT folding (folding a lone group leaves a header and nothing else on screen) and a host that later gains a second project must not fold under an ordinary reload, while ZERO groups leaves the flag ARMED — `buildSvcGroups` always returns a non-nil slice, so an empty one is a real host, the user saw no rows, and the landing has not happened yet; **Multi-project host view — batch partitioning and the sequential progress pipeline**: `opBatch{proj, services}` is one project's share of an operation, and **an EMPTY services slice means ALL services** (compose-resolved — the only way a batch reaches a never-created service). `partitionSelection()` walks `svcGroups` in SCREEN order, skips the unmanaged bucket, and falls back to ONE batch (the cursor's group, empty slice) when nothing is selected; a cursor on the unmanaged bucket yields NO batch. **That empty-selection rule is GROUPED-only** — `armOperation` keeps the drilled `warnNoSelection` guard, because reinterpreting an unselected `d` as "deploy everything" is a semantic change to a destructive key. **The composer binds at the confirming `enter`, not at the `d`/`r`/`s` press** (unlike `x`): the prompt swallows every key that could change the partition, so it RECOMPUTES rather than captures, which keeps `opBatch` off the Model. The prompt names the batches (`formatBatchTargets`: `web (nginx, api) → db (all)`) on ONE clamped line. `enterProgress(batches)` builds the steps for EVERY batch up front; **`stepState.label` is new and `name` still holds the RUNNER step name** a `StepEvent` matches, with the `"web: "` prefix on the label only when `len(batches) > 1`. **Each batch gets its OWN events channel** (`runner.Run` defer-closes the one it is given). **`handleStepEvent` resolves inside the CURRENT batch's step range** (`currentStepRange()`), never by a global name scan — the same five names repeat in every batch; `enterProgress` always sets `batchStepCount` to `len(runner.Steps(op))`, so there is no zero-count fallback and a hand-built fixture must set it too (`progressStep()` fills `name`+`label`). `markBatchesSkipped(from)` starts AT `from`, so a single-batch failure skips NOTHING (its own unreached steps stay `○`). `stepEventMsg`, `pipelineDoneMsg` and `batchDoneMsg` ALL carry `batchIdx` + `batchSession` captured at DISPATCH (in `waitForEvent`), gated on screen + session + index. **`stepEventMsg` needs that gate as much as the other two**: the channel read blocks, an esc-cancel marks the screen terminal at once and the second `esc` leaves while the cancelled step's `StatusFailed` is still in flight — ungated it latched `m.failed` on the container screen and poisoned the NEXT operation, whose `pipelineDoneMsg` then returned early so no batch past the first ever ran. `enterProgress` resets `done`/`failed` as defence in depth. **`batchSession` bumps at INVALIDATION sites only — never in `enterProgress`** (it starts at 0, so a zero-valued message still resolves against a fresh sequence): the `esc`-cancel and `clearBatchSequence()` at every progress departure. The Deploy snapshot is PER BATCH, pre-Stop, inside the batch goroutine; `startBatch` does NOT rebind for `Rollback` (`R` bound it at press time and the prep validated against it) **unless the composer is nil** — `U` and every `l`/`x`/`i` refusal unbind it while the snapshot read is still in flight, and the batch's own project IS `m.rollbackProj`, so rebinding from it can drift nowhere while the alternative failed the prep with "rollback is not supported for this connection", and **`R` captures the batch's PROJECT into `m.rollbackProj` at press time** — `m.currentProject()` is the ZERO project in grouped mode, so the confirming `enter` must build its batch from the capture or the invalidation deletes the wrong key. Update-cache invalidation walks `projUpdatesCacheKey(b.proj)` for every batch that FINISHED; keying it off `m.done` alone — which only the LAST batch sets — left an earlier successful batch's glyphs stale for the whole TTL. **The CURRENT batch counts when its own PIPELINE ran to the end** (`currentBatchPipelineRan()`, every step of `currentStepRange()` at `StatusDone`), not when the operation succeeded: a mid-sequence batch whose health GATE failed pulled its images all the same, while one with an unreached or failed step keeps its cache. **`viewProgress` clamps its TITLE to `m.width`** — `formatBatchTargets` grows with every project and service, and the row budget counts `head`'s newlines, so a title the terminal wrapped added rows `strings.Count` cannot see. It also **WINDOWS the step list** (`progressStepWindow(total, rows, hi)`), keeping `currentStepRange()` on screen with `▲/▼ N more` markers. **The window anchors on `hi`, the running batch's LAST row, never on its first** — a batch taller than the row budget would otherwise show its head while the step actually running scrolled off the bottom: a five-project plan emits 25 rows and bubbletea keeps only the LAST `m.height` lines, so an unwindowed render dropped the title and the running batch.

**Multi-project host view — updates in grouped mode**: **no automatic scan fires here.** `autoUpdatesAllowed()` = `!readOnly() && !grouped`, and `maybeRefreshUpdatesCmd` ALSO early-returns on `m.grouped` before the cache lookup — and **before the `updateInFlight` guard**, since the grouped branch schedules nothing, so the guard has nothing to protect there while the one thing it does do (age out the soft warning) was skipped for the whole life of a `U` scan — grouped mode owns neither the single key that helper reads nor the single composer a detail refill would fetch through. All THREE auto entry points refuse and `NewModel` seeds `updateInFlight` from the same predicate. **`U` is the only trigger and scans the CURSOR row's group only**: the composer is bound, read and unbound in one keystroke, and the in-flight guard is checked BEFORE the bind so a refusal leaves the composer untouched. **`updatesMsg` carries `forKey`, captured at DISPATCH — never re-derive it in the handler**: the cursor may move (or fold) mid-scan, filing one project's verdicts under another's key. The key is `projUpdatesCacheKey(proj)`, the SAME string `updatesCacheKey()` produces once drilled into that project, so one entry is shared between modes. **`reapplyUpdateVerdicts(results)` replaces the two clear-then-hydrate blocks**: the drilled rule ("the message is the whole truth") would blank every group a one-group scan did not cover, on the error path too. **The soft warning follows the same rule**: on SUCCESS grouped mode re-derives `updatesErr` from `groupedUpdatesErr()` (the message of the first group whose cached entry is a still-unexpired failure) instead of clearing it flat, or a success on `web` erased a warning belonging to `db` that nothing would ever put back — `U` is the only trigger there. `syncGroupedUpdatesErr()` applies that same derivation on the periodic reload AND on the grouped landing, and it must be an unconditional ASSIGN, never an expire-only early return: the three landing sites (`enterGroupedContainers`, `drillIntoGroup`, `backToServerScreen`) all blank `updatesErr`, so an expire-only form left a failed `U`'s warning gone for good after an ordinary drill-in and `esc`, with that group's glyphs blank and nothing able to restore either for the full error TTL. Grouped hydration is `hydrateGroupedUpdates()` — **RAW cache reads, deliberately not the TTL-checked `updatesCacheLookup`**, because nothing here refetches and a TTL-gated replay would blank the glyphs 10 minutes after a scan with nothing queued to restore them; error entries are skipped. `groupCounts` returns the header's `⇧ n` as a THIRD value off the same tri-state the row glyph draws, so nothing on the header path can trigger a scan. **Grouped mode fetches NO inspect detail rows, and the gate is the MODE, not the nil composer** (`updateDetailsCmd` reads `m.composer`, which an armed `x` prompt may have left bound to a different project); the entry keeps `details == nil`, which `refillUpdateDetailsCmd` fills on drill-in. `inspectUpdateKey()` resolves the cursor row's group key at RENDER time — the cursor cannot move while the inspect screen is up, so it needs no Model field and no departure-site cleanup. **`redrawInspectFromCache()` is gated on `inspectUpdateKey()`, NOT `updatesCacheKey()`** — the latter is the degenerate `"\x00|<server>"` here and never matches a batch's key, so a detail batch landing on an open inspect screen repainted nothing. **`refillUpdateDetailsCmd` carries its OWN `m.grouped` refusal**, not one at its call sites: the `updateDetailsMsg` arrival tail runs on every screen and cannot check, and a refill on the degenerate key fetches one project's details into another's entry. **Log search & filter**: `f` filters, `/` searches within the survivors. Full rationale and test pins: `docs/architecture/tui-logs-and-search.md`.

**Status refresh**: When returning from the progress screen or logs screen, `refreshStatus()` re-fetches `ContainerStatus()` via a `statusMsg` to update the running/stopped dots on the container screen. `ContainerStatus()` errors are propagated through `statusMsg.err` and `servicesMsg.err` and displayed via `svcErr`; a successful refresh clears any prior error. Follow this pattern whenever an operation changes container state.

**Server badge**: When a remote server is selected, the breadcrumb renders the server name via `serverBadge()`. Color is resolved via `resolveServerColor()` which returns the group color for grouped servers or the server's own color for ungrouped ones (nil-guarded for tests without config). A colored inline badge is shown only when the resolved color is non-empty; otherwise the breadcrumb falls back to the old plain server name (`cdeploy > prod-server > services`). `serverBadgeStyle()` in `styles.go` maps color names to lipgloss background colors. `serverHost` and `serverColor` fields on Model are set/cleared alongside `serverName` — follow the same cleanup discipline. No extra line is consumed, so no viewport height adjustment is needed.

**Config screen**: The `screenConfig` screen lets users view and edit docker-compose configuration files. Accessible via `c` key on the container screen (no confirmation). Uses a `ConfigProvider` interface (defined in `internal/tui/app.go`) with methods: `ConfigFile`, `ConfigResolved`, `EditCommand`, `ValidateConfig`. Both `Compose` and `RemoteCompose` implement it. The TUI type-asserts `composer.(ConfigProvider)` when entering — if the assertion fails (e.g., test mock), the `c` key is ignored. Key `r` toggles between raw file content and resolved output (`docker compose config`); resolved content is lazy-fetched on first toggle and cached. Key `e` shells out to `$EDITOR` via `tea.ExecProcess`; on return, re-fetches content and validates. Uses `configSession` (monotonic counter) for stale message rejection, matching the `logsSession` pattern. `esc` clears all `config*` fields and returns to the container screen. Local `findComposeFile()` probes `composeFiles` candidates; remote `findRemoteComposeFile()` uses a single SSH command to avoid multiple round-trips.

**Inspect screen**: `Inspector` (`Inspect(ctx, service) ([]byte, error)`) is declared in `tui` and type-asserted on the concrete composer, so a composer without it makes `i` a silent no-op — **keep the three `var _ Inspector = …` compile-time assertions in `app_test.go`**, one per concrete composer. **All three composers implement it, so `i` is NOT gated on `m.readOnly()`** — it reaches BOTH help tables through ONE shared append in `inspectGroup(readOnly, grouped bool)`, whose position is load-bearing for the `?` overlay's truncation order. **`docker inspect` is a top-level docker command, not a compose subcommand**, so all three bypass `command()`/`remoteCommand()`: `runDockerCmd`, `runRemoteDockerCmd` and the `dockerRunner` seam's `run`. Sections render STATE, HEALTH, IMAGE, MOUNTS, ENV in that order; an empty one is omitted, STATE always renders, and HEALTH must build rows into a scratch `inspectBuilder` and write its header only when a row exists. IMAGE renders `image`, `image id` (NOT `digest` — it is the local image ID), `built`, `update`, `update id`, `update built`, `command`, `entrypoint`: the four update rows sit BETWEEN `image id` and `command` so the two ids and the two dates pair up, each keys off its OWN input, and **the section's presence gate is UNCHANGED** (a verdict alone never opens it). **Probe output soft-wraps and must NEVER truncate**: every line goes through `inspectBuilder`, which wraps with the cell-aware `wrapCells` (`ansi.Hardwrap(line, width, true)`) — do NOT use the rune-chunking `softWrapLine`, measure labels with `ansi.StringWidth`, and below `inspectMinValueWidth` stack the value under its label rather than shredding a rune per line. **Tabs are expanded BEFORE measurement, inside `wrapCells`** (`expandTabs`, 8-column stops) — expand-then-strip. **Every emitted line is sanitised at ONE chokepoint, `inspectBuilder.push`** (`sanitizeInspectLine` = `ansi.Strip`, then drop BEL, CR, DEL and the 8-bit C1 controls). A new section's content lines MUST go through `push`; only `section()`'s own styled title bypasses it (it carries a lipgloss escape sequence) — never route that title back through `push`. **Raw mode uses a narrower pass**: `setInspectContent()` writes `sanitizeInspectRaw(m.inspectRaw)`, which keeps newlines and must NOT run `ansi.Strip`; `m.inspectRaw` itself stays verbatim (filter at render only). ENV renders verbatim in both modes; masking, if added, must cover BOTH. **Mechanics**: `enterInspect()` bumps `inspectSession`, resets the seven `inspect*` fields, sizes through `inspectViewportSize()` (`m.height - 6` — NOT the logs `- 7` — 3-row floor; `m.width - 4`, `< 10 → 40` floor), calls `SetHorizontalStep(4)`, calls `m.clearSearch()` (one of the eleven sites the container-search paragraph lists) and returns `fetchInspect()`; **the `WindowSizeMsg` branch must call that same helper.** `inspectDataMsg` is gated on screen AND `msg.session != m.inspectSession`, and treats a fetch that SUCCEEDED with zero bytes as an error. `setInspectContent()` is the single `SetContent` chokepoint and must `SetXOffset(0)` on every buffer change; the `r` toggle adds `GotoTop()`. `rebuildInspectSummary()` sets `inspectErr`, empties the summary and KEEPS `inspectRaw`, but must NOT flip `inspectShowRaw` — only the `inspectDataMsg` handler switches, once. `clearInspect()` is the single departure cleanup and does NOT bump `inspectSession`; `esc` returns WITHOUT `refreshStatus()`. The `r` case and the footer must read ONE predicate, `inspectToggleAvailable()`, never `len(inspectRaw) == 0`. The footer and the one-line error slot (`strings.Fields` + `clampToWidth`) must never wrap, and **`viewInspect()` must NOT end in a newline**. TUI-only: no `Composer` change, no ID field on `runner.ServiceStatus`. Full rationale and test pins: `docs/architecture/tui-inspect-screen.md`.

**Exec into container**: The `x` key on the container screen execs into a running container interactively. Uses an `ExecProvider` interface (defined in `internal/tui/app.go`) with method `ExecCommand(ctx, service, command) (*exec.Cmd, error)`. Both `Compose` and `RemoteCompose` implement it. The TUI type-asserts `composer.(ExecProvider)` when `x` is pressed — if the assertion fails (e.g., test mock), the key is ignored. If the service is not running, a warning is shown. Otherwise, confirmation is requested (`pendingExec = true`); on confirm, the TUI shells out via `tea.ExecProcess` which suspends Bubble Tea and gives full terminal to the exec process. On return, `execDoneMsg` resets `pendingExec` and calls `refreshStatus()`. Default shell command: `[]string{"/bin/sh", "-c", "command -v bash >/dev/null 2>&1 && exec bash || exec sh"}` (checks for bash first, falls back to sh for Alpine/minimal images; uses `command -v` instead of redirecting stderr on `exec` to avoid silencing bash's stderr for the entire session). Local: `docker compose exec <service> <command...>`. Remote: builds SSH command directly (like `EditCommand` pattern) with `-t` for TTY allocation — does NOT use `remoteCommand()`. CLI: `cdeploy exec <service> [-- command...]` with `--server`/`-s` support; follows `cmd/logs.go` pattern. `ExecCommand` returns `(*exec.Cmd, error)` (not executing it) so the caller controls execution. `DefaultExecCommand` is exported from `internal/compose/compose.go`.

**Docker Compose**: All docker interaction goes through `compose.Compose.command()` (local) or `compose.RemoteCompose.remoteCommand()` (SSH) which builds the correct command based on the `Standalone` field — `exec.CommandContext("docker", "compose", ...)` for plugin mode or `exec.CommandContext("docker-compose", ...)` for standalone mode. Both set `CURRENT_UID` env var (format `uid:gid` locally, `$(id -u):$(id -g)` on remote). Auto-detection via `Detect(ctx)` probes `docker compose version` first, then falls back to `docker-compose version`; the result is cached in the `Standalone` and `detected` fields. Detection is explicit — callers must call `Detect()` before first use; `command()`/`remoteCommand()` only read `Standalone`. `SetStandalone(bool)` allows inheriting the detection result into new instances. `SetTestHooks(run, output)` on both `Compose` and `RemoteCompose` injects test doubles. Exact subcommands: `stop`, `rm -f`, `pull`, `up --no-start`, `start`, `config --services`, `ps -a --format json`, `logs`, `exec`, `ls -a --format json`, plus top-level `stats --no-stream --format json` (NOT a compose subcommand — see below). Empty container slice means operate on all services. `parseContainerStatus()` handles both JSON array output (Docker Compose v2.21+) and NDJSON (older versions); it parses `CreatedAt` and `Status` fields from `psEntry` to populate `ServiceStatus.Created` and `ServiceStatus.Uptime`. `formatUptime()` in `internal/compose/uptime.go` converts Docker's Status string (e.g. `"Up 3 hours (healthy)"`) into compact form (`"3h"`): strips health suffixes, compacts time units (`hours` -> `h`, `days` -> `d`, etc.), handles special cases (`"About a minute"` -> `"~1m"`, `"Less than a second"` -> `"<1s"`), returns `"restarting"` for Restarting status, and empty string for non-Up statuses. `parseUptimeDuration()` converts compact uptime strings back to `time.Duration` for comparison (used to pick the longest-running replica among scaled services, which correctly handles restarts where CreatedAt is older but actual uptime is shorter). CLI subcommands reject `-a` combined with explicit container names.

**Project identity — caller-supplied, never looked up**: a composer's identity is what its CALLER supplied — the `--project-name`/`-p` flag, or the `Name` on the picker row the TUI drilled into. It is **NEVER re-derived from `docker compose ls`**. That command enumerates projects by scanning CONTAINER LABELS, so a project whose containers are gone is not reported — and the deploy pipeline itself removes them (`stop → rm -f → pull → create → start`). A round that keyed the snapshot from that lookup made a failed deploy unrollbackable: `pull` fails after `rm -f`, `ls` reports nothing, and the rollback keys a different file. **THE STORAGE KEY MUST NOT DEPEND ON STATE THE OPERATION BEING SNAPSHOTTED CAN DESTROY.** Convergence instead comes from `canonicalStateName(dir, name)` (`internal/compose/projectidentity.go`), which needs no host state at all: an UNNAMED compose invocation is not identity-free — it addresses the project compose derives from the directory — so a composer naming that DEFAULT project and a composer naming nothing fold onto ONE key, the dir-only hash every release has written. `composeDefaultProjectName` reproduces compose-go's `NormalizeProjectName` on `path.Base(dir)` (lower-case, keep `[a-z0-9_-]`, trim leading `_-`); it is not a guess, it is the definition of the project compose would use. A project that is NOT the directory default (`-p blue`) keys its own file, so two `-p` projects sharing one directory never read each other's digests. **`Compose.stateName()`/`RemoteCompose.stateName()` are the ONE producer** of both the key and the `project_name` stamp, so `checkSnapshotProject` can never disagree with the file it guards. `COMPOSE_PROJECT_NAME`, a `name:` key and `.env` are deliberately NOT consulted — the environment is invisible over SSH (honoring it locally would split the local and remote key for one project) and the rest means replicating compose's interpolation; when one of them names a project the derivation does not predict, the two spellings key two files and a rollback says "no snapshot" — a safe failure for a `-p`-addressed project, which is the case this design targets. **It is NOT safe in one narrower shape**: two DIFFERENT projects sharing one directory and BOTH addressed with an EMPTY name (each selected by its own `name:` key, `.env` or `COMPOSE_PROJECT_NAME`) fold onto the same dir-only file, and `mergeSnapshot` merges by SERVICE name, so one can pin the other's digest. That is not a regression — before the name entered the key EVERY project in a directory shared one file — so the rule NARROWS the hazard rather than introducing it. `TestProjectIdentity_EveryPathKeysOneStateFile` (fast track + drill-in + `runOperation` ⇒ ONE state file) and `TestProjectIdentity_TwoNamedProjectsInOneDirStayApart` are the two halves of the contract; `TestRollbackFindsTheSnapshotAfterEveryContainerIsRemoved` and its remote twin pin it against an empty `ls`. **`ListProjects` must carry NO `-f` and NO `-p`** (`hostCommand`/`remoteHostCommand`): `ls` is host-wide discovery, neither flag selects anything there, and `-f` would point compose at a file it must parse — `cdeploy list` and the TUI project loader call it on a composer that may already carry both. **Documented limitation**: the CLI reproduces `docker compose -p <name>` run in `-C <dir>` exactly, so it auto-discovers compose files; a project whose files are not auto-discoverable there must be driven from the TUI, whose picker row carries the set.

**Remote SSH**: `RemoteCompose` wraps docker compose commands in SSH calls via a ControlMaster persistent socket (`/tmp/cdeploy-ctrl-{hash}-{pid}`). `ConnectCmd()` returns the SSH connect command for TUI's `tea.ExecProcess` (full terminal access for password prompts), `Connect()` runs it directly for CLI use, and `Close()` tears down the socket. All remote args are shell-escaped via `shellEscape()`. `CURRENT_UID` is evaluated on the remote host via `$(id -u):$(id -g)` to get the correct server-side UID/GID. The `Run()` function in `tui/app.go` calls `disconnectFunc` on exit to ensure socket cleanup. CLI uses `--server`/`-s` flag to select a server; TUI shows a server picker when servers are configured.

**Ad-hoc SSH (`-S`/`--ssh`)**: The `--ssh` persistent flag (registered in `cmd/root.go` alongside `--server`) is the ad-hoc complement to config-based `--server`. It accepts `[user@]host[:port]` and lets CLI users (especially CI) connect without a `~/.cdeploy/servers.yml` entry. Mutually exclusive with `--server`; requires `--project-dir`. Implemented via two helpers in `cmd/remote.go`: `checkRemoteMutex(serverName, sshTarget, identityFile)` enforces both the `--server`/`--ssh` mutex and the `--identity` requires `--ssh` rule at the top of each subcommand's `RunE`, and `resolveSSHRemote(ctx, sshTarget, projectDir, identityFile, newRemote)` parses the target via `config.ParseSSHTarget`, calls the injected factory (`opNewRemote`/`execNewRemote`/`logsNewRemote`/`newRemote` — preserving existing test seams), sets `RemoteCompose.SSHExtraArgs`, and runs `Connect()` + `Detect()`. On `Detect` failure the helper internally calls `Close()` before returning the error; on `Connect` failure cleanup is a no-op. The returned cleanup is always non-nil, so callers can `defer cleanup()` immediately after the call without nil-checking. Wired into `deploy`/`restart`/`stop`/`exec`/`logs`/`list` subcommands as a branch above the existing `--server` block — config-based path is unchanged. Parser lives in `internal/config/sshtarget.go`: rejects whitespace and IPv6 (`[`-prefixed); validates port `1..65535`; returns `SSHTarget{User, Host, Port}` with helpers `SSHHost()` (`user@host` or `host`) and `PortArgs()` (`["-p","NNNN"]` or nil). The `SSHExtraArgs []string` field on `RemoteCompose` is spliced **immediately before the host argument** in every SSH argv build site (Connect, Close, Detect plugin/standalone probes, `remoteCommand`, `findRemoteComposeFile`, `ConfigFile`, `EditCommand`, `ExecCommand`); nil = zero-behavior-change default. No TUI changes — `--ssh` is strictly a CLI feature.

**Ad-hoc SSH identity (`-i`/`--identity`)**: The `--identity` persistent flag (registered in `cmd/root.go` immediately after `--ssh`) accepts a path to an SSH private key, intended for CI/automation workflows that write a key from a secret and don't have a `~/.ssh/config` entry. Strict-narrow: only valid alongside `--ssh` (mutually exclusive with `--server` via the `--identity requires --ssh` rule); CLI-only (TUI mode rejects it). Path validation lives in `internal/config/identity.go` (`ParseIdentity`): trims input, rejects empty, expands `~/` paths via `os.UserHomeDir()`, rejects bare `~` and `~user` forms (only `~/...` is supported), requires `os.Stat` to succeed and report a regular file, requires `os.Open` to succeed (readability check beyond mode bits), and returns `filepath.Clean` of the resolved path. Relative paths pass through unchanged — `ssh(1)` resolves them against cwd. `resolveSSHRemote` appends `["-i", cleanPath]` to `SSHExtraArgs` after the port args, so every existing SSH argv splice site absorbs `-i` for free without any changes to `internal/compose/remote.go`.

**Config**: `internal/config` loads `~/.cdeploy/servers.yml` defining remote servers and groups. The `Config` struct has `Groups []Group` and `Servers []Server`. `Group` has `Name` and `Color` fields. `Server` has `name`, `host`, optional `project_dir`, optional `group`, and optional `color` fields. Color resolution: grouped servers inherit color from their `Group` via `Config.GroupColor()`; ungrouped servers use their own `color` field. `color` accepts ANSI color names listed in `config.ValidColors` (exported slice, single source of truth for both validation and the TUI cycle picker): red, green, yellow, blue, magenta, cyan, white, gray; invalid values are rejected by `Validate()`. `Validate()` also checks group name uniqueness, group color validity, and that servers reference existing groups. `Save(path string) error` writes config atomically (temp file + rename) with `MkdirAll` for parent dirs. When color is omitted (resolved or direct), the TUI keeps the old plain-text breadcrumb instead of rendering a badge. Servers with the same `group` are displayed together under a shared header in the TUI. `Load()` returns an empty config (not error) if the file doesn't exist; it also runs `migrate()` to auto-convert old-format configs (per-server colors on grouped servers) to the new format (colors on Group entries, first-server-wins for conflicts). SSH-specific options (keys, jump hosts, tunnels) belong in `~/.ssh/config` — except `-i` for ad-hoc CI/automation use via `--ssh`.

**Settings editor**: Two screens (`screenSettingsList` + `screenSettingsForm`) accessible via `s` key on the server select screen (only when `m.config != nil`). The settings list shows all servers in a table with Name/Host/Group/Color columns; color is resolved from the group for grouped servers (with a "(group)" indicator) or from the server directly. `a` adds, `enter`/`e` edits, `d` deletes (inline y/n confirmation). The form uses 4 `textinput.Model` instances (name, host, project_dir, group) and a cycle picker for color (left/right arrows cycle through `""` + `config.ValidColors`). `settingsField int` tracks focus (0-3 = text inputs, 4 = color picker). When a server has a group, the color picker shows a "(group)" label; cycling the color edits the group's color (affecting all servers in that group). Editing a grouped server loads `settingsColor` from the group; on save, `settingsColor` is applied to the group's color (not the server's). New group names auto-create `Group` entries; orphaned groups (no servers referencing them) are auto-cleaned on both save and delete. `resolveServerColor()` on Model returns group color when available, falling back to server color (nil-guarded for tests without config). Validation reuses `config.Validate()` on a temporary config (including `Groups`) before applying changes. On save: mutate `m.config.Groups` and `m.config.Servers`, call `m.config.Save(m.configPath)`, sync `m.servers = m.config.Servers`, rebuild `m.serverEntries` via `buildServerEntries()`. Config path and config are threaded into the TUI via `WithConfigPath(path)` and `WithConfig(cfg)` functional options — existing `NewModel()` call sites are not affected. State cleanup: `esc` from settings list returns to server select; `esc` from form returns to settings list with no data changes; `settingsErr` is cleared on transitions.

**Operations**: Four operations — `Restart` (stop → rm → create → start), `Deploy` (stop → rm → pull → create → start), `StopOnly` (stop), `Rollback` (stop → rm → create → start — Restart shape, **NO Pull**: registry outages are a classic rollback trigger, so offline rollback from local blobs must work). All share the same `runner.Run()` pipeline; the step list varies by operation type. `Steps()`/`buildSteps()` fold Rollback into the Restart branch (`default:` case, gated only by `op == Deploy` for the Pull step).

**Wait engine (`--wait` health gate)**: ONE implementation, `internal/runner/wait.go`, drives BOTH CLI and TUI. `EvaluateWait` is a **pure reducer** (no clock, no IO); seed `WaitState` via `NewWaitState(services)`. **Per-service precedence IS the spec, in this order**: (1) `Uptime=="restarting"` ×3, checked **FIRST** (it also reports `Running==false`); (2) unhealthy; (3) `Running==false` after `everRunning`; (4) never-ran ×5; (5) `Health!=""` ⇒ has a healthcheck, passes ONLY on `Health=="healthy"` (a "starting" service stays pending); (6) no healthcheck + running ⇒ after `Grace`. **Firm timeout boundary**: PASS in 5/6 is gated on `elapsed <= Timeout`, fail-fast 1-4 is NOT; anything pending at `elapsed >= Timeout` sweeps to timed-out. `WaitHealthy` resolves empty targets via `ListServices()`; **`context.WithDeadline(ctx, start+Timeout)` must be created FIRST, before ANY blocking call, covering that resolution AND the polls — no wait-phase call may outlive `--wait-timeout`**, each re-arm capped at `min(Poll, Timeout-elapsed)`. A deadline expiry sweeps via `state.reportTimedOut` (NOT nil-status `EvaluateWait`) → `(report, nil)` = exit 2; a PARENT cancel returns `ctx.Err()` raw → exit 1 — check `ctx.Err()` BEFORE `waitCtx.Err()`. Only OPERATIONAL failures error; a failing verdict is `(report, nil)`, `report.OK==false`.

**`WaitError` exit-2 contract**: `cmd.WaitError{Report, Err}` (`cmd/deploy.go`) wraps a non-OK **OR** errored `--wait` report; `main.go` `errors.As` → `os.Exit(2)`; `Unwrap()` must keep exposing the operational cause. `addWaitFlags` puts `--wait`/`--wait-timeout` on deploy, restart, rollback ONLY; `stop` never waits (`runOperationWithPrep` guards `op != runner.StopOnly`).

**Deploy snapshots & the state file**: every `Deploy` records each *running container*'s digest to `~/.cdeploy/state/<sha256(projectDir + "\x00" + canonicalStateName)[:12]>.json` **on the docker host**, BEFORE the pipeline stops anything. **Deploy-only** — never Restart, never Rollback; **captured pre-Stop** from the running container, NEVER the local tag; **merge-not-replace** (`mergeSnapshot`, fresh wins); the key hashes a NORMALIZED dir (`Abs`+`Clean` local, `path.Clean` remote); **warn-and-proceed** — capture and write failures never block. **The CANONICAL project name is in the key**: two `-p` projects share one `ConfigDir` and `mergeSnapshot` merges by SERVICE name, so on the directory alone deploying `green` overwrote `blue`'s `web` entry and a later rollback of `blue` pinned green's digest past every refusal check. **An EMPTY canonical name keeps the historical DIR-ONLY hash, byte for byte** (every existing state file) — and because `canonicalStateName` folds the directory's OWN project onto that empty name, an unnamed CLI verb, the TUI fast track and a drill-in row for that project all read it. **There is NO second path to try**: the earlier design keyed named projects apart from the dir-only file and needed a one-way `elif [ -f ]` fallback, which was one-way in exactly the direction a failed deploy needed; folding makes them the SAME file instead. `Snapshot.ProjectName` records the owner, re-derived from the composer at every write (never trusted from `fresh`), and `checkSnapshotProject` refuses a file naming a DIFFERENT project. Schema version 1; any other returns typed `errSnapshotSchema`; `ReadSnapshot` returns `(nil, nil)` for a missing file. **Overwrite protection** (`existingForMerge`): ONLY a missing or `errSnapshotCorrupt` file may be overwritten; an `errSnapshotSchema` file or a transient read/SSH failure MUST abort the write. Local `WriteSnapshot` flocks `<state>.lock`; the REMOTE write is deliberately unlocked.

**Rollback pipeline & `PrepareRollback` prep / `ExtraComposeFiles` contract**: `cmd/rollback.go` reuses `runOperationWithPrep` with the `rollbackPrep` hook; never fork `runOperation`. Hook order: `ReadSnapshot` → `resolveRollbackTargets` refusals → `filterLiveTargets` against the CURRENT `ListServices()` (failure ABORTS prep — fail closed; a removed service is skipped under `-a`, errors when named) → `PrepareRollback`, which pulls absent blobs (a failed pull MUST abort BEFORE any override is written or the field set), writes `buildOverrideYAML` — `image: <repo>@<digest>` **plus `pull_policy: never`** per service, services in **SORTED order, never marshal a map** — and sets `ExtraComposeFiles = [main, override]`. Its cleanup (remove override, field to nil) MUST be deferred **function-scoped** — after the wait phase, BEFORE the remote SSH teardown, whose socket the `rm -f` still needs. `rollbackPrep` returns the resolved (snapshot ∩ live) set; `runOperationWithPrep` MUST thread it into **BOTH** `runner.Run` AND the wait phase — never the raw nil `containers`. Non-nil `ExtraComposeFiles` has `command()`/`remoteCommand()` splice `-f <f0> …` right after `docker compose`/`docker-compose`, BEFORE the subcommand, escaped on remote. `-f` disables auto-discovery, so the **main file MUST be first**, absolutized locally (`cmd.Dir = ProjectDir`). **A nil field must keep producing byte-identical argv.**

**TUI wait phase & `R` rollback (sessions + cleanup)**: `screenProgress`'s `waiting` sub-state drives a singleton `waitTickMsg` loop gated on screen+`waiting`+session; StopOnly never waits. **The gate is PER BATCH**: `pipelineDoneMsg` OPENS it and `batchDoneMsg` — never `pipelineDoneMsg` — RELEASES the next batch, so a batch's channel closing no longer means the batch is over. A whole-project batch (empty target set) resolves its names through `waitTargetsMsg`/`ListServices` — grouped mode must NOT fall back to the screen's rows, which are host-wide there (`drilledServices()` answers nil for anything but a single group) — and an unresolvable set SKIPS the gate (no health verdict was named, so it is not a health failure). A failing gate stops the sequence only when a batch is STILL TO COME; the last batch keeps today's `done`-with-red-verdicts rendering. **`esc` on a mid-sequence gate STOPS the sequence** (`batchSession++` + `markBatchesSkipped(batchIdx+1)` + `m.failed`) and **`enter` RELEASES the next batch** (`batchFinished()` is the shared release path for `StopOnly`, an unresolvable set and the skip). The gate is where a multi-project deploy spends most of its wall clock (one `DefaultWaitTimeout` per batch) and `esc` is the abort key everywhere else on the screen, so releasing a whole project's stop → rm → pull → create → start from it made the universal abort key destructive. On the LAST batch nothing is left to release and BOTH keys are the plain skip; `midSequence()` is the ONE predicate behind the two-outcome footer (`enter skip wait • q esc stop`) and the `?` WAIT table — see `docs/architecture/tui-multi-project.md`. Each poll MUST be `WithDeadline(m.ctx, m.waitDeadline)`-bounded and the `waitStatusMsg` error path MUST sweep pending→timed-out (`sweepWaitTimeout`) ONCE `elapsed >= Timeout` — before the deadline the failed poll is transient, state is carried forward and the loop keeps ticking; `esc` calls `clearWaitState()` (bumps `waitSession`). **`clearWaitState` must NOT clear `opContainers`** — that is the BATCH's resolved target set, not wait state, and `viewProgress`'s grouped title reads it, so clearing it re-titled an esc-skipped named-service operation "all services"; `clearBatchSequence` owns it, at the progress departure (which also CANCELS the final batch's context — `batchDoneMsg` cancels each batch as the next takes over `m.cancel`, and the last one has no successor). `R` **captures the selection into `rollbackTargets` at press time** (bumping `rollbackFetchSession`); that set — **NEVER live `selectedContainers()`** — drives validation, the prompt, `PrepareRollback` and `opContainers` (empty = ALL services), and an empty capture REFUSES. `rollbackSnapshotMsg` is screen+session gated, a `ListServices` failure fails closed, and a target absent from the snapshot or live compose is refused. The prep cleanup runs via `runRollbackCleanup` when **LEAVING `screenProgress` — NEVER goroutine-deferred**; a hard quit mid-wait must run it on the main goroutine too (both `ctrl+c` paths). `waitSession`/`rollbackFetchSession` bump at the same sites as the other counters; `waiting`/`waitState`/`waitDeadline`/`rollbackSnapshot`/`rollbackTargets`/`rollbackCleanup` clear at every departure site (esc chain, `entryLocal`, `connectResultMsg` error path); esc-from-progress must invalidate the update cache for `runner.Rollback` too. The TUI snapshots FIRST in the Deploy op goroutine; `Snapshotter`/`RollbackPreparer` are type-asserted. Rationale and test pins: `docs/architecture/wait-snapshots-rollback.md`.

**Health checks**: `ServiceStatus` has `Running bool`, `Health string` (values: `"healthy"`, `"unhealthy"`, `"starting"`, or `""` for no healthcheck), `Created string` (formatted creation time, e.g. `"2024-01-15 09:30"`), and `Uptime string` (compact uptime, e.g. `"3h"`, `"2d"`, or `""` if not running). For scaled services, `Running` uses OR (any running = running), `Health` uses worst-case priority (`unhealthy` > `starting` > `healthy`), `Created` uses the oldest replica, and `Uptime` uses the longest-running replica. The TUI shows health icons (♥/✗/~) next to status dots and Created/Uptime columns. The CLI `list` command shows the same icons and columns.

**Multi-project discovery**: The `list` subcommand auto-discovers all compose projects when no `-C` is specified (both local and remote). Services are grouped by project with headers. Per-project errors are non-fatal — a warning is printed to stderr and the project is skipped. When `-C` is specified, only that project's services are shown in a flat list. With `--stats`, CPU/Mem columns are populated by joining `docker stats --no-stream --format json` against each project's `ps` container IDs. The host-wide `docker stats` call is shared across every project: `runList` calls `compose.AllContainerStats`/`AllContainerStatsRemote` once before the project loop and passes the result map into `collectMultiProjectStats`. Each project's composer satisfies the `bulkStatsAggregator` interface (`ContainerStatsFromBulk`) and only runs `docker compose ps` per project, joining against the shared bulk map — one ~1.5s cost regardless of project count. Composers that don't implement the bulk interface (test mocks) fall back to per-project `ContainerStats()`; the fallback also runs if the host-wide fetch failed (`bulkStats == nil`), so stats degrade gracefully rather than disappearing.

**Resource stats**: `runner.ServiceStats` (`CPUPercent float64`, `MemoryUsed int64`, `MemoryLimit int64`) is populated from `docker stats --no-stream --format json` — host-wide NDJSON, one line per container, parsed by `parseStatsOutput()` in `internal/compose/stats.go` (tolerant of both NDJSON and JSON-array forms, mirroring `parseContainerStatus`). `ContainerStats()` is the **first method on `Compose`/`RemoteCompose` to bypass `command()`/`remoteCommand()`** because `docker stats` is a top-level Docker CLI command rather than a compose subcommand — calling `c.command(...)` would prepend `compose` and produce a malformed argv. `AllContainerStats()` builds `exec.CommandContext("docker", "stats", ...)` directly; `AllContainerStatsRemote()` builds the SSH argv directly, splicing `SSHExtraArgs` immediately before the host arg (same convention as `EditCommand`/`ExecCommand`, which also bypass `remoteCommand()`). Per-project `ContainerStats()` calls `docker compose ps --format json` for this project's container IDs, calls the bulk helper, joins by short container ID (first 12 chars), and sum-aggregates `CPUPercent`/`MemoryUsed`/`MemoryLimit` across replicas — a 3-replica service maxing each core shows ~300% CPU. Only running containers appear in the result map; stopped services are absent. Helpers `parseSize` (handles `B`/`KiB`/`MiB`/`GiB`/`TiB` binary and `kB`/`MB`/`GB`/`TB` decimal suffixes, case-insensitive), `parseCPUPercent` (strips `%`), and `FormatBytes` (exported; produces compact `124M`/`1.5G`) live in `internal/compose/stats.go` as the single source of truth — both `cmd/list.go` and `internal/tui/app.go` import `FormatBytes` from there. In DRILLED mode the TUI fetches stats in parallel with status via `tea.Batch(refreshStatus(), refreshStats())` on every entry to `screenSelectContainers` and after every operation completes (return from progress / logs / exec). **In GROUPED mode the two halves are strictly SERIAL**: `statsRefreshCmd()` is nil there and `groupedStatsCmd` is CHAINED off the grouped `servicesMsg` arrival, because it consumes the listing that arrival carries — see the `HostGrouper` paragraph. A periodic `refreshTickMsg` (every `statsRefreshInterval` = 5s, defined in `internal/tui/app.go`) keeps the data fresh while the user lingers on the screen: `Init()` kicks off a singleton `tea.Tick`, and the handler always reschedules itself so exactly one tick is in flight at any time regardless of how many transitions in/out of the screen happen. The handler gates fetches on `m.screen == screenSelectContainers && !m.confirming && <live> && !m.refreshInFlight`, where `<live>` is `m.composer != nil` in drilled mode and `m.composerFactory != nil` in grouped mode (grouped holds no composer by design) — anywhere else, the tick is a pure reschedule with no docker calls (off-screen / mid-confirmation / mid-disconnect / previous fetch still pending).

**Update detection — tri-state and Composer contract**: `runner.ServiceStatus.UpdateAvailable *bool` is a tri-state: `nil` = unknown / not checked / build-only / error, `true` = update available, `false` = current. `Composer.CheckUpdates(ctx, services)` returns ONLY checked services — an absent key must stay absent (that is the nil). **A non-nil error makes the map untrusted** — soft-failure consumers MUST discard it (`updates = nil`) and render all-blank-plus-warning. `compareImageDigestVia` returns `(updated, ok, err)`: **an empty digest is `ok == false`, never an error** (it would pollute the cascade counters).

**Update detection — digest comparison**: `parseLocalDigest` filters `RepoDigests` by repo (`stripTag`) and **falls back to the first non-empty digest when no repo matches**; `fetchRemoteDigestVia` tries `docker buildx imagetools inspect` FIRST and falls back to `docker manifest inspect --verbose` whenever imagetools yields no valid digest — a non-transport failure OR a successful call whose output the strict parser rejects; `errSSHTransport` short-circuits the fallback instead. — `errSSHTransport` propagates instead. **Do NOT add `--format '{{.Manifest.Digest}}'` back to `imagetoolsInspectArgs`** — silently ignored; `Name:` parses as the digest. `parseImagetoolsDigest` takes the top-level `Digest:` line and validates strict `sha256:<64 hex>`; do NOT add a "bare sha256 line" fallback. All three inspects **bypass `command()`/`remoteCommand()`** (top-level docker) — local `runDockerCmd`, remote `runRemoteDockerCmd` (`shellEscape`d image names, `SSHExtraArgs` before the host arg).

**Update detection — SSH transport classification (RemoteCompose only) / systemic-failure cascades**: `classifySSHError(err, stderr)` matches `sshTransportStderrPatterns` — SSH-ONLY signatures. **Do NOT add generic networking phrases** (`connection refused`, `no route to host`). A match wraps `errSSHTransport` and aborts `CheckUpdates`; anything else is a per-image failure → absent cell. Two post-scan cascades, both gated on `len(out) == 0`: **registry** when `networkFailures == remoteAttempts > 0` (`looksLikeNetworkErr`), **local-docker** when every local inspect failed AND every failure ALSO matches `looksLikeLocalDaemonErr` — that classifier gate is not optional. Partial failures never cascade; remote mirrors the registry cascade only. All three `CheckUpdates` share ONE loop, `scanImageUpdates`, memoized by image ref; **no cascade flag — the sentinel the comparer emits selects the cascade**: only `Compose` passes `wrapLocalImageInspectErr`, so only it emits `errLocalImageInspect`; `errSSHTransport` lives only on the remote runner.

**Update detection — TUI caching and refresh**: `updateCache` is keyed `projDir + "\x00" + projName + "|" + serverName` (see `projUpdatesCacheKey`); successes live `updatesCacheTTL` = 10m, failures `updatesErrorTTL` = 30s. **Errors ARE cached**, a new entry ALWAYS overwrites the prior one for that key (failure over stale success, success over failure), and **`errMsg` MUST be restored on every cache hit** (`maybeRefreshUpdatesCmd` and both replay paths). The `updatesMsg` handler applies its mutations (`updatesErr`, stale-glyph clears, hydration) **BEFORE the screen check**; only `fixSvcOffset` is screen-coupled. …deletes the current key's entry on a successful Deploy, Restart or Rollback, **before** the `m.done = false` reset; skipped on `m.failed` and on Stop. `U` bypasses the TTL but MUST keep its `if m.updateInFlight` guard, like `maybeRefreshUpdatesCmd`. Updates are **NOT** in the 5s `refreshTickMsg`. `projUpdatesCacheKey(proj)` is the sibling that composes the same string for a project the Model is not pointed at (a batch sequence, a grouped scan); `updatesMsg` carries `forKey` captured at DISPATCH and the handler **must never re-derive the key** — see the grouped-updates paragraph below.

**Update detection — sessions and in-flight discipline**: `updatesSession` gates `updatesMsg` and is bumped at the **same 7 sites** as `statsSession`/`statusSession` (`entryLocal`, `execDone`, return from progress, return from logs, `enterGroupedContainers`, `drillIntoGroup`, `backToServerScreen`) — **and the `connectResultMsg` SUCCESS path now reaches `enterGroupedContainers` too**, so it bumps all three; the old "NOT on success" rule died with the static project picker. Its ERROR path bumps `rollbackFetchSession` but NOT `statsSession`/`statusSession`/`updatesSession`. `updateInFlight` is cleared **BEFORE BOTH the session check AND the screen check, on EVERY arrival**, stale ones too. Every site that bumps `updatesSession` AND calls `maybeRefreshUpdatesCmd()` MUST reset `m.updateInFlight = false` first; the 2 leave-screen transitions reset it too. `connectResultMsg`'s error path clears `serverName`/`updatesErr`/`updateInFlight`; `entryLocal` clears `projDir`/`projName`/`updatesErr`.

**Update detection — rendering, CLI, and JSON**: `hydrateUpdates` (called from `servicesMsg`/`statusMsg`) writes verdicts into `m.svcStatus` and **MUST skip a verdict whose name is not already in `m.svcStatus`**. `updateGlyphStyle` appends `" ⇧"` (`compose.UpdateGlyph`); `maxName += 2` **unconditionally**, in the TUI and in `formatDots`/`formatDotsGrouped`, measured with `utf8.RuneCountInString`. Errors use the soft-warning slot prefixed `updates: `, priority `svcErr > statsErr > updatesErr`. `cmd/list.go` gates `CheckUpdates` behind `--updates` in BOTH single- and multi-project modes; a failure warns to stderr, SETS `updates = nil`, and never aborts the listing; JSON carries `update_available *bool` with `omitempty`. Full rationale and test pins: `docs/architecture/update-detection.md`.

**Update detection — inspect detail rows (`UpdateDetailer`)**: `UpdateDetails(ctx, services) (map[string]compose.UpdateDetail, error)` is declared in `tui` beside `Inspector` and type-asserted — **NOT a `Composer` change**, so the five mocks and `list --updates` stay untouched; keep the three `var _ UpdateDetailer = …` pins in `app_test.go`. Details ride the `refreshUpdates()` SCHEDULE but a SECOND message: `refreshUpdates` returns the moment `CheckUpdates` does, and its handler enqueues `updateDetailsCmd(entry, key)` AFTER the cache write (the WHOLE entry, so `results` and `fetchedAt` can never be paired from two different ones). **Do NOT fold the fetch back into `refreshUpdates`' goroutine** — one Cmd is one message, so the `⇧` verdicts would wait on up to three registry round-trips per updated image with `updateInFlight` pinned true (a dead `U`). The enqueue sits AFTER the session check, so a scan already superseded when its verdicts arrive spends no detail calls; one superseded LATER cannot be stopped, so **`m.detailsInFlight` bounds the phase to ONE batch GLOBALLY** — `updateDetailsCmd` returns nil while it is set, and the handler's unconditional clear on EVERY arrival (before the identity gates) is its ONLY clear. **No context-change site may reset it**: with at most one batch outstanding there is exactly one arrival per raise, which is what makes that clear exact — a reset lets two scans overlap and lets the refill dispatch a third onto an entry the second is already filling. **The arrival is guaranteed by `context.WithTimeout(m.ctx, updateDetailsTimeout)` inside `updateDetailsCmd`** — `m.ctx` has no deadline and no runner adds one, so without it ONE stalled registry call latches the flag for the rest of the session with no escape short of restarting cdeploy; an expiry degrades to a PARTIAL map, never an error. **Do NOT gate `U` on it and do NOT delay the `updateInFlight` clear** — either reinstates the dead-`U` window the split removed. **A refused or lost batch is not queued anywhere — it heals from the ENTRY**: `refillUpdateDetailsCmd` re-dispatches whenever the CURRENT entry is fresh, non-errored and has `details == nil`, called from exactly two sites — the tail of the `updateDetailsMsg` handler (**hoist it into its own statement**; `return m, m.refill…()` leaves the receiver mutation to an unspecified evaluation order, and losing it is an unbounded registry loop) and `maybeRefreshUpdatesCmd`'s fresh-SUCCESS branch. **NEITHER is behind `autoUpdatesAllowed()`** — a refill can only fire for an entry that ALREADY EXISTS under the current key, and on a read-only key only `U` can create one (the stale branch, the `statusMsg` self-heal and `Init()` all refuse), so a refill is the continuation of an authorised fetch, not a new automatic one; gating either site strands the rows `U` asked for for the whole 10m TTL. **`details == nil` vs an EMPTY map is load-bearing** — nil means no batch REPORTED, so the merge normalises a nil map to an empty one or a failed batch re-scans on every screen entry for the whole 10m TTL. Three review rounds each patched a different door that dropped a batch (a session gate, a merge-time key, a departure-site reset) and the bug walked through the next; **do not add a fourth guard — keep the retry keyed off the entry's own state**. **`updateDetailsMsg` carries NO session — it carries its OWN identity**, `forKey` + `forEntry`, both captured at DISPATCH time: the key is the context and `fetchedAt` names the exact verdict set. A session gate, and equally a key RE-DERIVED in the handler, DROPPED the rows for the entry's whole 10m TTL — ordinary navigation (esc from logs/progress, `execDone`, esc drilling out to the grouped host view) bumps the counter or changes the current key without touching the entry, and those sites enqueue no replacement. It only MERGES onto an existing non-errored entry, and `redrawInspectFromCache()` runs only when `forKey` IS the current key (it is a render path). One `updateEntry`, one key, so the `⇧` triggers, TTLs, invalidation and `autoUpdatesAllowed()` gate still apply by construction; `detailsInFlight` is the ONE new Model field, a transient guard with no departure-site cleanup at all, and `details` itself needs none either. **A detail failure is DISCARDED, never `updatesMsg.err`** — a 429 matches `looksLikeNetworkErr` and would trip the registry cascade and blank the whole `⇧` column. Pass **ONLY the `true` verdicts, SORTED**, and skip the call entirely when none is true or `CheckUpdates` errored — `filterServices` reads an empty slice as **ALL** services, so the guard is a rate-limit rule, not an optimisation. UP TO four round-trips per updated image (`localProbeArgs`, `manifestIndexArgs`, `rawManifestArgs`, `imageConfigArgs`), up to three of them registry — the single-manifest path skips step 3, so it costs two; all bypass `command()`/`remoteCommand()` through the `dockerRunner` seam. `scanUpdateDetails` memoizes by image ref (**failures too**), visits services SORTED, **OMITS a failed image and CONTINUES** (a partial map is a valid result — never turn that `continue` into a `return`), short-circuits on `errSSHTransport` with the partial map, and checks `ctx.Err()` per image; the first-failure early return belongs to `fetchUpdateDetail`'s four-step sequence, not to the scan. On the single-manifest path **step 3 is SKIPPED** — step 2's output IS the manifest, so `pinnedImageRef` returns `pinned bool` and `parseConfigDigest(indexOut)` supplies `NewID`, with the `--raw` call kept only as the fallback when that yields nothing. **`localProbeFormat` is `{{json .}}` and must NAME no field** — a template naming a field the CLI's struct lacks is a hard error, and the CLI's raw retry runs with `missingkey=error`, so an `omitempty` field with no value (`Variant` on most images) fails there too; the whole-document form degrades to an empty string instead, which is the same rule `hostPsArgs` carries. `parseLocalProbe` decodes `Created`/`Os`/`Architecture`/`Variant` out of it and ignores the rest. `parseIndexPlatformDigest` is THREE-state: `hasIndex=false` → use the ORIGINAL ref; `hasIndex=true, found=false` → **ABORT this image**; every doubt (malformed JSON, non-list `manifests`, empty os/arch, and an EMPTY document — `null` unmarshals into a nil map, so `len(doc) == 0` must abort rather than fall through) returns the ABORT state, and `unknown` os/arch entries are attestations that must never be selected. **The variant is MATCHED, not guessed, and BOTH sides are canonicalised first** through `normalizePlatformVariant` — containerd's `normalizeArch` rule, which docker and buildx inherit and the OCI image-spec leaves open: an unqualified `arm` IS `v7` (never a wildcard over 32-bit ARM), and `arm64` and `arm64/v8` are ONE platform. The entry whose NORMALISED variant equals the probe's normalised one wins; with no exact match a LONE entry whose normalised variant is EMPTY wins (it serves the whole arch — portainer and qdrant publish `linux/arm64` that way); everything else ABORTS — a KNOWN variant with no entry of its own draws nothing. `linux/arm` ships as v5+v7 or v6+v7, so index order drew another image's digest and build date, accepting a lone qualified entry regardless still handed an ARMv6 host a `v7`-only image, and treating an unqualified `arm` entry as architecture-wide handed the same image to an ARMv5/v6 host. **Do NOT re-add a lone-QUALIFIED-entry fallback for a probe that names no variant** — after normalisation such a probe is a concrete platform, so it would take an `arm64/v9` or `amd64/v3` entry (`TestParseIndexPlatformDigest_VariantMatching/a_lone_arm64...` fails under exactly that). **Do NOT "fail closed" on any qualified-only match either** — BOTH captures spell arm64 as `arm64/v8`, and the fold is what makes those hosts match exactly (`TestPinnedImageRef` fails under that mutation). `parseImageCreated(data)` reads the BARE OBJECT only — a platform-keyed map cannot reach step 4 (a multi-platform tag always has an index, so it is pinned or aborted first), and **do not re-add the map branch**; `validImagetoolsDigest` is a WHOLE-STRING check. **`Unix() <= 0` is a sentinel, not data** (reproducible builds) — `parseImageTimestamp` and `formatInspectTimeValue` both drop the row. `rebuildInspectSummary()` is the ONE cache-lookup site (`m.currentUpdateInfo()`, raw map read — NOT the TTL-checked lookup; `inspectUpdateInfo.detail` is a VALUE, only `verdict` is a pointer), and BOTH handlers MUST call `redrawInspectFromCache()` — rebuild when `m.screen == screenInspect`, **on the failure path too**, AFTER the cache write, and **skip the viewport write in raw mode** (`setInspectContent` resets `SetXOffset(0)`, which would snap a sideways scroll back). Raw mode stays byte-identical. Full rationale and test pins: `docs/architecture/update-detection.md`.

**Session filters for stale responses**: `statsMsg`, `statusMsg` AND `servicesMsg` all carry a `session uint64` captured at fetch time; their handlers reject messages where the session (and screen) don't match. Two counters live on Model:
- `statsSession` covers `refreshStats` AND the chained grouped `groupedStatsCmd` (the two are the same fetch in the two modes) — bumped at every context change that swaps `m.composer` or the grouped host context: `entryLocal` fast track, `execDone`, `esc` from logs, `esc` from progress, plus the three navigation helpers `enterGroupedContainers()` (connect success, `entryLocal` grouped, drill-OUT), `drillIntoGroup()` (drill-IN) and `backToServerScreen()`. **All seven go through ONE helper, `bumpFetchSessions()`, which bumps `statsSession`/`statusSession`/`updatesSession`/`rollbackFetchSession` together — never four hand-written `++` lines at a new site.** The grouped cycle CROSSES the first two (the arrival passes its `statusSession` gate, then chains a stats fetch stamped `statsSession`), so a site bumping only one has the chained `statsMsg` dropped at a gate that does NOT clear `refreshInFlight` — the exact latch. The two LONE `rollbackFetchSession++` sites (the `R` keypress, the connect-failure path) are not context changes and keep their single bump.
- `statusSession` covers `refreshStatus`, `loadServices` AND `loadGroups` — bumped at the same 7 sites as `statsSession` (the lifecycle is identical: `loadServices`/`loadGroups` are the initial-load siblings of `refreshStatus`, fetching list + initial status in one shot). `loadGroups` deliberately reuses this counter rather than owning one: it is `loadServices`' grouped counterpart, same context changes, same staleness rule.
- `projectsSession` and `projectsMsg` are GONE with the project picker. The loader they guarded now feeds `loadGroups`, which is already gated on `statusSession` at the same swap sites.
- **The `connectResultMsg` SUCCESS path DOES bump all three counters** (via `enterGroupedContainers`) — the inverse of the rule that held while the next screen was the static picker. It now lands on LIVE data, and the site that starts fetching a resource is the site that must invalidate whatever a previous server left in flight.

Missing the session filter on any of them is the same class of bug — codex's adversarial review caught each one in successive rounds. When adding a NEW async msg type that's tied to a screen context, give it a session and gate the handler on `m.screen != <its-screen> || msg.session != m.<sessionField>`.

**`refreshInFlight` prevents fetch stacking**: the tick fan-out `tea.Batch(statusRefreshCmd(), statsRefreshCmd(), refreshTick)` — the mode-aware pair, `loadGroups` alone in grouped mode (`statsRefreshCmd()` is nil there because the stats half is chained off the arrival, not batched) and `refreshStatus`/`refreshStats` in drilled mode — schedules the next 5s tick *concurrently* with the current refresh — Bubble Tea batches execute concurrently, not sequentially. Without a guard, if `docker stats --no-stream` takes longer than 5s on a slow remote SSH hop, the next tick would stack another pair of fetches on top. The `m.refreshInFlight bool` is set true at every site that fires `refreshStats()` (the tick handler + the 5 transition handlers that fan out the fetch batch) plus the grouped `servicesMsg` branch that CHAINS the stats half, and cleared in the `statsMsg` handler on any *current-session* arrival, *before* the screen check (success or error). **The grouped `servicesMsg` branch clears it the same way — UNCONDITIONALLY, before its own screen check — and the ONE branch that accepts the payload and chains the stats half then RE-ARMS it beside the `tea.Cmd` whose `statsMsg` clears it again.** Never write `if !chaining { clear }`: that skips the clear on the stale-session, off-screen, `m.confirming` and `msg.err` paths, which is the exact latch this rule exists to prevent. Clearing has to happen before the screen check because if the user opens the config / logs / progress screen while a stats fetch is pending, the response arrives off-screen and would otherwise be discarded silently — leaving `refreshInFlight` stuck true and permanently silencing the periodic loop when the user returns to the container screen. The session-match condition makes the unconditional clear safe: stale responses (different session, indicating a context change has happened) don't touch the flag because the context-change handler already reset it. The flag is also explicitly reset to false in `backToServerScreen()` (the one transition that navigates away without firing a fetch batch) so the new context starts clean. When the next tick fires while the guard is set, it reschedules without fetching. **The tick's liveness check is `m.composer != nil` in drilled mode and `m.composerFactory != nil` in grouped mode** — grouped mode holds no composer by design, so a flat composer test would silence the periodic refresh on exactly the screen that most needs it.

**Test seam for the tick**: `Model.tickCmdOverride func() tea.Cmd` is nil in production; tests set it via `installFakeTick(&m)` (in `internal/tui/app_test.go`) to swap the real `tea.Tick` for a non-blocking Cmd that returns a `fakeTickMsg`. Without the override, every test exercising the gated paths (off-screen, in-flight, confirming) would leave a real 5s `tea.Tick` goroutine running until the program exits. With the override installed, tests assert directly on whether `cmd()` returns a `tea.BatchMsg` (positive path: fetch batch) or any other msg (gated path: just the rescheduling tick). NewModel sets `m.refreshInFlight = true` for the local fast-track because `Init()` will fire `refreshStats`; tests that exercise the unblocked tick path must explicitly clear it.

When adding a new screen that should NOT trigger periodic refreshes, no change is needed: the gate already excludes any screen != `screenSelectContainers`. When adding a new screen that DOES need its own periodic refresh, prefer a separate tick (different msg type) rather than overloading `refreshTickMsg`. When adding a new context-change handler (anything that swaps `m.composer`), bump BOTH `statsSession` AND `statusSession`, and set `refreshInFlight` (true if the handler fires a refresh batch, false if it just navigates away). `statsMsg` carries a `session uint64` captured at fetch time from `m.statsSession`; the handler rejects messages where `msg.session != m.statsSession` in addition to the screen check, mirroring the `logsSession`/`configSession` pattern. `statsSession` is bumped on every context change that swaps `m.composer` or the grouped host context (`drillIntoGroup`, `enterGroupedContainers`, `backToServerScreen`, `entryLocal`) so an in-flight fetch from project A cannot land in project B's view. Soft failure: on stats fetch error, both CLI (`cdeploy: stats unavailable: <err>` to stderr, exit 0, blank cells) and TUI (`statsErr` rendered as soft warning) keep status — the load-bearing primary view — intact; in the TUI, when both `svcErr` and `statsErr` are set, `svcErr` wins (the more important failure).

**Ports column**: `ServiceStatus.Ports []runner.Port` (with `Host`, `HostPort`, `ContainerPort`, `Protocol` fields) is populated by `parseContainerStatus()` from `docker compose ps --format json`. Primary data source is the `Publishers []` array (Compose v2); when absent or empty, `parsePortsString()` falls back to parsing the `Ports` text field (e.g. `0.0.0.0:8080->80/tcp, :::8080->80/tcp`). Publishers with `PublishedPort == 0` (i.e. `expose:`-only/internal) are skipped. Dedup is keyed on the full tuple `(Host, HostPort, ContainerPort, Protocol)` so distinct bind interfaces on the same port (e.g. `127.0.0.1:8080->80` and `192.168.1.10:8080->80`) both survive. A separate `collapseIPv6Mirrors()` pass collapses only the IPv4/IPv6 *wildcard* mirror pair — when both `0.0.0.0` (IPv4 unspecified) and `::` (IPv6 unspecified) appear on the same `(HostPort, ContainerPort, Protocol)` tuple, the `::` entry is dropped. All other host strings are distinct user-visible binds: IPv6 loopback `::1`, link-local `fe80::1`, or explicit IPv6 addresses like `2001:db8::1` survive intact, even alongside an IPv4 sibling. Multiple non-wildcard IPv6 entries on the same tuple do not collapse against each other (full-tuple dedup in `mergePort` already removes exact repeats). Bracketed IPv6 like `[::]:8080` is normalized (brackets stripped on input). Empty `URL` from Compose is normalized to `0.0.0.0`. Scaled-service ports go through the same dedup + collapse + sort pipeline (sorted ascending by `HostPort`, then `ContainerPort`, `Protocol`, `Host`). Render helpers live in `internal/compose/ports.go`: `FormatPort()` returns `host:hp→cp` for IPv4 and `[host]:hp→cp` for IPv6 (the arrow is U+2192, not `->`; IPv6 hosts — any host containing `:` — are wrapped in brackets to disambiguate the host:port boundary), with `/proto` suffix only when protocol is non-empty and not `tcp` (`/udp` and `/sctp` are shown). Wildcard hosts (`0.0.0.0` and `::`, both meaning "all interfaces") are omitted entirely so the common all-interfaces case renders as a bare `hp→cp`; non-wildcard binds (loopback, explicit address) keep their host so the LAN-vs-loopback distinction stays visible. The wildcard-hiding affects only display — JSON output (`cmd/list.go` serializes the `Port` struct directly) preserves the original `host` field. `FormatPorts()` comma-joins. Both the CLI `list` (`formatDots`/`formatDotsGrouped` width-track `maxPorts` and append the column after Uptime when any service has ports) and the TUI container-select screen (captions row gains `"Ports"` via `hasStatusColumns()`) render the column. Stopped containers and services without published ports show a blank cell (padded whitespace for alignment). CLI JSON output includes a `ports` array (`omitempty`) per service with `host`/`host_port`/`container_port`/`protocol` fields.

**Unmanaged containers — the `HostContainers` composer and the three-method `dockerRunner` seam**: a container with no `com.docker.compose.project` label gets `compose.HostContainers` (`internal/compose/hostcontainers.go`), a read-only `runner.Composer`: five writes `return errReadOnly`, five reads go through the unexported `dockerRunner` field. **The seam needs THREE methods, not one builder**: `run` captures and classifies — the remote form reuses `runRemoteDockerCmd`, so `errSSHTransport` classification comes free; `stream` must NOT allocate a TTY and MUST wire BOTH Stdout and Stderr to `w`; `tty` MUST splice `-t` remotely. All three remote forms go through `RemoteCompose.remoteDockerCmdString(args)` — one home for `docker` + `shellEscape`. `hostPsArgs` = `ps -a --size=false --format {{json .}}`: the **template** form, never the bare `json` keyword (CLI >= 23.0 only), and **never drop `--size=false`**. Never name fields individually instead: an unknown field is a hard template error (`.State` needs CLI >= 20.10). `isComposeManaged` matches the key **only at a token start** (`HasPrefix(labels, k) || Contains(labels, ","+k)`), **never** by splitting `Labels` into `k=v` pairs — a value may contain a comma; the const keeps its trailing `=`, excluding the sibling `…config_files`/`…working_dir` keys. `parseHealthFromStatus` reuses the end-anchored `healthSuffixRe` from `uptime.go` — extend it, never duplicate it. `Running` is `State == "running"` and **must keep the `HasPrefix(Status, "Up ")` fallback for an empty `State`**. `ContainerStats` uses the seam directly and **early-returns before the stats call when there are no unmanaged entries**; a container in `ps` but absent from `stats` is **skipped, not an error**; `ContainerStatus` has NO such guard and **must not grow one**. `hostStatsArgs` takes the same form; that equivalence is **per-command**. `CheckUpdates` maps name→image from the `Image` field `ps` already returned and calls `scanImageUpdates` with a **nil `localErrWrap`** (no local-daemon cascade); `hostImageMap` drops empty refs and bare image IDs.

**Unmanaged containers — the `(unmanaged)` group, the widened `ComposerFactory`, and the cache-key collision**: `compose.Project` gains `Unmanaged bool` — do NOT overload `Status`; `Desc` was deleted with the project picker that was its only reader. `CountUnmanaged`/`WithUnmanagedRow`/`projectsWithUnmanaged` were deleted with it too (`internal/compose/unmanagedrow.go` is gone); only `UnmanagedProjectName` survives, in `hostcontainers.go`. **`buildSvcGroups` (`internal/tui/entries.go`) is the SOLE producer of the row now** — its leftover path picks the bucket out of the host-wide status map the grouped fetch already returned and appends it LAST, so the group costs no second `docker ps`. It renders as the last GROUP on the container screen (read-only rows, no checkbox cell, never in an op batch). **Every branch `cmd/root.go` contributes to the composer side lives in a package-level helper, never in the `RunE` closure**: `localComposerFor(proj, detector, standalone, detected)`, `remoteComposerFor(proj, rc, standalone)` — both take the plugin/standalone VERDICT as a value and never read it off the composer, because **`detectGuard` (`cmd/root.go`) is what makes that verdict race-free**: the `ProjectLoader` runs `Detect()` inside a tea.Cmd goroutine while the `ComposerFactory` reads the verdict on the UI goroutine, and in grouped mode the loader runs on the 5-second tick, so the two are live together for the whole session. `resolve(probe, standalone)` probes once under a mutex and COPIES the answer out; a failed probe records nothing, so the next caller retries. **`ComposerFactory` is `func(proj compose.Project) runner.Composer`** so it can branch on `proj.Unmanaged` — and so it can carry `proj.Name` into `ProjectName` AND `proj.ConfigFiles` into `ComposeFiles`. **`-p` pins WHICH project; `ComposeFiles` pins WHAT it is made of**: a project created from `-f prod.yml -p prod` beside a sibling `docker-compose.yml` was stopped, removed and RECREATED from the sibling's definitions under the right label, and a `stack.yml`-only project reported "no compose file found" from `c` and from rollback prep. `compose.Project.ConfigFiles` is docker's full ordered `config_files` list (`ConfigDir` is only `filepath.Dir` of the first); the row's set goes through **`compose.PinComposeFilesLocal` locally and the pure `compose.PinComposeFiles` remotely**, both of which return nil (auto-discover) when compose's own discovery would reproduce the reported set — `-f` DISABLES auto-discovery and the `config_files` label was stamped at container-creation time, so pinning a default-named set froze out any `docker-compose.override.yml` added later, permanently (`up --no-start` re-stamps the same label). **Discovery is PRECEDENCE, not membership**: compose keeps the FIRST default name it finds (`compose.yaml` > `compose.yml` > `docker-compose.yml` > `docker-compose.yaml`, overrides likewise) and only warns about the rest, so a project created from an explicit `-f docker-compose.yml` in a directory that also holds `compose.yaml` carries a default name yet is NOT what discovery resolves — dropping its pin recreated it from `compose.yaml`'s definitions under the right `-p` label. `PinComposeFilesLocal` reads the directory and drops the pin only when discovery resolves the row's OWN main file; it still drops it when discovery finds an override the row lacks (that healing is the whole point) and when a reported file no longer exists (`-f` at a deleted file is a hard error). **`composeFiles`/`remoteComposeFiles` are stored in that precedence order and the order is load-bearing** — `findComposeFile`/`findRemoteComposeFile` probe them in order for the config screen and rollback prep. The REMOTE rows keep the name-only test on purpose: resolving precedence needs the project directory read, which is an SSH round trip per row on every 5-second grouped reload; the residual gap is exactly the lower-precedence `-f` case above, on a remote host. `composeFileList()` returns `ExtraComposeFiles` when set (the rollback override stack, which already contains these files) and `ComposeFiles` otherwise; `findComposeFile`/`findRemoteComposeFile` return `ComposeFiles[0]` instead of probing the four canonical names. `remoteComposerFor` must ALSO copy `SSHExtraArgs`. **`cmd/list.go`'s multi-project factory is `listComposerFactory func(compose.Project) runner.Composer` for the same reason** — keyed on the directory it printed the SAME containers under two headers, in text and in `--json`. The CLI addresses a project through the `--project-name`/`-p` persistent flag, threaded as an EXPLICIT parameter through `resolveSSHRemote`/`resolveServerRemote` so a new subcommand cannot forget it; TUI mode rejects it, and `list` refuses it without `-C` (host-wide discovery has no single composer to select). **`projUpdatesCacheKey(proj)` is the ONE key producer** and `updatesCacheKey()` is literally `projUpdatesCacheKey(m.currentProject())`, so a grouped scan and a drilled one cannot file the same project under two entries. The key is `ConfigDir + "\x00" + proj.Name + "|" + serverName` with an `"unmanaged|"` prefix taken from `proj.Unmanaged` (`currentProject()` supplies that from `m.readOnly()`, never a parallel `projUnmanaged bool` field) — an unmanaged row's empty `ConfigDir` otherwise collides with the local fast track's bare slot. **BOTH project halves are in the key and neither alone would do**: the directory does not identify a project (`docker compose -p blue` and `-p green` in one directory are two container sets, and on `ConfigDir` alone they shared one entry, so one project's verdicts were painted onto the other's rows and its own scan was suppressed for the whole 10m TTL), and the name does not either (a `buildSvcGroups` leftover group has no `ConfigDir` at all, and two hosts can run one project name from different trees). **NUL is the separator** because no path and no docker project name can contain it, so no `(dir, name)` pair can spell another pair's key.

**Unmanaged containers — the read-only UI contract**: `ReadOnlyComposer` is declared in `tui` and type-asserted on the concrete composer; it needs a **named** `ReadOnlyComposer() bool` method — never a method-less marker; `Model.readOnly()` is nil-safe. `d`, `r`, `s`, `R`, `c`, `space` and `a` all early-return, **each calling `fixSvcOffset()` first**. `c` and `R` need an **explicit** gate anyway. **Nothing advertises a no-op**: `containerHelpLines()` returns a read-only idle pair (`line1` drops `space toggle`, `line2` = `l logs • x exec`) read by both `containerFooterLines()` and `containerFooter()`; the line count **must stay state-independent** and every rendered line is clamped with `clampToWidth`. `helpGroupsFor` returns `readOnlyContainerGroups(canGoBack, grouped)` when `helpContext.readOnly`: SELECT and OPERATE go whole and `c` leaves INSPECT, but **`enter` MOVES into INSPECT** (`confirm the exec prompt`) — and in GROUPED read-only mode that row names TWO meanings on one line (`drill into the project · confirm the exec prompt`), because `enter` is not gated on `readOnly` and an unmanaged-only host still drills. The FOOTER keeps its four read-only tokens: it is a curated subset, and a lone group renders no header, so the drill shows the same rows. MOVE/FIND/INSPECT come from shared `moveGroup()`/`findGroup()`/`inspectGroup(readOnly, grouped bool)` — add a key once, not twice; the other screens' MOVE groups stay literals, since their contents differ. Drift pins run **per variant, never a union** — extend `TestHelpGroups_NamesEveryBoundKey` and its `ReadOnly` twin. The title drops the `(n/m selected)` counter and rows the `[ ]`/`[x]` checkbox, so the caption pad must be **7**, not **10**. **The update check must NOT fire automatically here**: all THREE entry points — `maybeRefreshUpdatesCmd()`, the `statusMsg` self-heal and `Init()`'s fast path — consult `autoUpdatesAllowed()` (= `!m.readOnly() && !m.grouped`), leaving `U` the only trigger. `NewModel` sets `updateInFlight = m.autoUpdatesAllowed()`, never a flat `true`. Both gated paths also **clear `m.updatesErr` once the cache entry has expired** (the `statusMsg` clear sits BEFORE its `fixSvcOffset()`). Full rationale and failure modes: `docs/architecture/unmanaged-containers.md`.

**Grouped host view — label-derived names are UNTRUSTED**: a project name comes from `com.docker.compose.project` and a service name from `com.docker.compose.service`, and any `docker run --label` sets both to arbitrary bytes; the grouped screen redraws itself every 5 seconds, so an OSC 52 clipboard write or a CSI sequence in a label is replayed with NO keystroke, and `ansi.StringWidth` counts an escape sequence as zero cells so every clamp and every column pad passes it through. `sanitizeName` (`internal/tui/entries.go`) is the ONE filter and it IS `sanitizeInspectLine` — never a second mechanism. It is applied at INGESTION, not at render: `buildSvcGroups` (which looks `host[raw]` up by the RAW name but stores, dedupes and fold-matches the SANITIZED one), `setSingleGroup`, and **`svcKey`, which sanitizes BOTH halves** so a map converted through `qualifyMap`/`flattenQualified` — whose keys arrive raw from the composer — still joins onto the sanitized rows. Sanitizing the NAME rather than the rendered line is what keeps the width math honest and covers every consumer at once (header, row, breadcrumb, confirm prompt, progress title, warnings, search bar); `m.projName`'s ONLY non-empty assignment is `drillIntoGroup` from an already-sanitized group. A real compose project is unaffected — compose rejects those bytes in both a project and a service name, which is exactly what makes the DEDUPE rule work: **on a collision the name that needed NO sanitizing wins** (`raw == sanitized`). Order comes from the loader, which sorts RAW names, so a forged label sanitizing onto a real project's name can sort BEFORE it — a plain first-wins dedupe dropped the real project and left the forged row, with its attacker-chosen `ConfigDir`, occupying the real name that `bindProjComposer`/`drillIntoGroup` hand to the factory. The leftover pass pre-filters nothing and lets `add()` apply the same rule, so a real project the loader missed still displaces a forged claim. Service names inside a group are deduped on the sanitized value too — the slice was sorted but never deduped, so one `svcKey` addressed two rows.

**Grouped host view — a lone group that draws no rows KEEPS its header**: `groupsHaveHeaders` is still "more than one group", plus the one exception `len(groups) == 1 && (folded || no services)`. Without it the screen renders ZERO rows, and a screen with no rows has no cursor — nothing to unfold, drill into, select or operate on, and no name saying which project is on screen. Both shapes are reachable: a sole project whose containers are all gone, and a folded group that outlived the other groups on the host (fold state survives the 5-second rebuild by project name).

**Grouped host view — an `svcErr` makes every row key inert**: `viewSelectContainers` early-returns an error screen that hides the rows, while the groups and the selection behind it are kept ON PURPOSE (a transient refresh failure must not discard fold state or a selection). The dispatch therefore swallows every key but `esc` and `ctrl+c` while `m.svcErr != nil`, right after the `m.warning = ""` line. Without it `d`/`r`/`s` armed a confirmation the error screen has no slot to draw, and the `enter` that followed ran the operation against an invisible stale selection.

**`rollbackPreppedMsg` carries batch identity**: `batchIdx` + `session`, captured in `prepareRollbackCmd` at DISPATCH exactly as `waitForEvent` captures them, and gated in the handler alongside `m.screen != screenProgress`. The screen alone is NOT identity now that a batch sequence makes a second operation reachable: a cancelled prep runs until `PrepareRollback` notices its context, and by then the user can be on `screenProgress` with a different op — its `err` failed THAT op, its success overwrote the cleanup the new one owns, and the `waitForEvent` it returns put a SECOND consumer on the live event channel. Every stale branch still invokes `msg.cleanup`, or the override file leaks.

**`Compose.ProjectName` / `RemoteCompose.ProjectName` (`-p` splice)**: `docker compose ls` reports a project launched with `docker compose -p` or `COMPOSE_PROJECT_NAME` under its REAL name while several such projects share one `ConfigDir`, so a composer built from the directory alone addresses the directory's DEFAULT project — the picker showed one project and `d`/`r`/`s` stopped and removed another's containers. `projectNameArgs`/`RemoteCompose.projectFlag` splice `-p <name>` AFTER the `-f` pairs and before the subcommand (both are compose top-level flags; keeping `-f` first leaves the `ExtraComposeFiles` rule untouched), shell-escaped on remote, and `RemoteCompose.ExecCommand` must splice it too because it builds its own argv. **An empty name must keep producing byte-identical argv.** `localComposerFor`/`remoteComposerFor` (`cmd/root.go`) stamp it from the picker row and `prepareLocalComposer`/`resolveSSHRemote`/`resolveServerRemote` from the `-p` flag; **none of them looks the name up** — see the project-identity paragraph.


## Adding New Operations

1. Add constant to `Operation` enum in `internal/runner/runner.go`
2. Update `String()`, `Steps()`, and `buildSteps()` in the same file
3. Add action key case in `screenSelectContainers` handleKey in `internal/tui/app.go`, AND name the key in the matching group in `helpGroupsFor()` (`internal/tui/help.go`) — the `?` overlay is the only place the full key table is advertised now that the footer carries 6 tokens
4. Gate the new key on `m.readOnly()` with an early return, and leave it OUT of `readOnlyContainerGroups()` (`internal/tui/help.go`). Every operation is a compose pipeline, and an unmanaged container has no compose file, so a new op is by definition inert on the read-only screen — a key the read-only table still named would advertise a no-op, which is the failure that whole variant exists to prevent
4b. **Route the key through the GROUPED path, or it writes a nil deref.** Grouped mode holds `m.composer == nil` BY DESIGN (see the multi-project paragraphs), so a new op key must not touch the composer at press time: arm through `armOperation` / `partitionSelection()`, bind with `bindProjComposer(batches[0].proj)` at the confirming `enter`, and call `unbindGroupedComposer()` on EVERY early return between the two. The grouped help table needs no second hand-maintained key list — `TestHelpGroups_GroupedNamesTheSameKeys` (`internal/tui/help_test.go`) compares the grouped token set against the writable one in BOTH directions and fails the moment they drift. Add the grouped dispatch test alongside the drilled one; a key that works drilled and panics grouped is the shape this step exists to prevent
5. Add CLI subcommand in `cmd/deploy.go` and register in `cmd/root.go`
6. Tests: runner sequence test, cmd subcommand/flag tests, TUI action key + confirmation tests, plus the expected-key set in `TestHelpGroups_NamesEveryBoundKey` (`internal/tui/help_test.go`), which fails in both directions when the help table drifts from the dispatch. If the operation is a WRITE, add the key to the table in `TestReadOnly_GatesWriteKeys` (`internal/tui/app_test.go`) so the read-only screen is pinned to refuse the gate step 4 added. The read-only help pin needs NO edit for a gated key — it stays out of `TestHelpGroups_ReadOnlyNamesEveryBoundKey`'s hand-maintained bound set, and that test's names-nothing-unbound direction is what catches a table that advertises it anyway.

If the new operation needs an op-specific pre-run step (like Rollback's snapshot read + digest-pin prep), don't fork `runOperation` — route through `runOperationWithPrep(ctx, op, all, containers, prep)`. The `prep func(context.Context, runner.Composer) (func(), error)` runs AFTER the composer is built and BEFORE the pipeline (so it can apply refusal rules and configure the composer, e.g. set `ExtraComposeFiles`); its returned cleanup is deferred function-scoped, so it runs after the wait phase but before the remote SSH teardown (LIFO). deploy/restart/stop pass a nil prep and keep the original path. Rollback lives in its own `cmd/rollback.go` (see "Adding New CLI Subcommands") but is a deliberate reuse of this deploy machinery, not a fresh subcommand skeleton.

## Adding New CLI Subcommands

See `cmd/list.go`, `cmd/logs.go`, and `cmd/exec.go` for the pattern. Each subcommand:
1. Creates a `*cobra.Command` in its own `new*Cmd()` function
2. At the top of the `Run*` function, calls `checkRemoteMutex(serverName, sshTarget, identityFile)` to enforce the `--server`/`--ssh` mutex and the `--identity requires --ssh` rule (it must run before `os.Getwd()` and `signal.NotifyContext` so spurious setup doesn't run when the flags conflict)
3. Branches in this order: `sshTarget != ""` → `resolveSSHRemote(ctx, sshTarget, projectDir, projectName, identityFile, <factoryVar>)` (passing the subcommand's own injectable factory); else `serverName != ""` → `resolveServerRemote(ctx, serverName, projectDir, projectName, <factoryVar>)`, or the inline equivalent (load config, `FindServer()`, create `RemoteCompose`, `Connect()`, defer `Close()`, `Detect()`); else fall back to local `compose.New(dir)` handed to **`prepareLocalComposer(ctx, lc, projectName)`** (stamps the name, `Detect()`s — and looks NOTHING up) — the two remote helpers take the name as a parameter and stamp it themselves, precisely so a new subcommand cannot silently address the directory's default project instead
4. Is registered in `cmd/root.go` via `rootCmd.AddCommand()`

`cmd/skill.go` (the `skill install|show|uninstall` subcommand, see "Agent Skill distribution" below) is a deliberate exception to this pattern — it operates on local files only and has no `--server`/`--ssh`/`--project-dir`/remote wiring.

`cmd/rollback.go` (the `rollback` subcommand) is a second deliberate exception: rather than reimplementing the composer-branch skeleton, it reuses the deploy machinery via `runOperationWithPrep(ctx, runner.Rollback, …, rollbackPrep(…))` — the shared `runOperationWithPrep` already does the `checkRemoteMutex` → ssh/server/local branching, and `rollbackPrep` is the op-specific pre-run hook (snapshot read + refusal rules + digest-pin prep). See "Adding New Operations" for the prep-hook recipe.

## Agent Skill distribution (`cdeploy skill`)

**`skills/` package**: the repo-root `skills/` directory is BOTH the external-installer convention directory (so `npx skills add lexxzar/compose-deploy` and `gh skill install lexxzar/compose-deploy` find `skills/cdeploy/SKILL.md` on the default branch) AND a Go package holding the `//go:embed cdeploy` directive. `skills.FS` exposes the embedded tree; `skills.CanonicalSkill()` returns the raw, unstamped SKILL.md bytes — the single source of truth for the CLI, external installers, and verification, version-locked to the binary via `go:embed` (panics on a missing embed, since that is a build/packaging fault, not a runtime error to thread).

**`cdeploy skill install|show|uninstall <claude|codex|all>`** (`cmd/skill.go`): installs the embedded skill into agent skill directories. Targets resolve via `skillTargetDirs()`: claude → `~/.claude/skills/cdeploy` (also read by Cursor/OpenCode); codex → `~/.agents/skills/cdeploy` AND `$CODEX_HOME/skills/cdeploy` (default `~/.codex`; an EMPTY `$CODEX_HOME` is treated as unset because `t.Setenv` can set but never unset an env var); all → the deduped union. Dedupe (`resolveDedupeKey`) resolves symlinks on the deepest EXISTING ancestor of each candidate (the target dir usually does not exist yet, and `filepath.EvalSymlinks` errors on missing paths), then re-appends the not-yet-existing suffix, so two candidates pointing at the same physical directory through a symlink collapse to one write. Multi-path install/uninstall aggregate per-path outcomes — one failed destination never aborts the others, and any failure yields a non-zero exit. Per-agent pickup notes are printed to stdout after a successful install. `show` writes the raw unstamped canonical via `cmd.OutOrStdout()` (NOT `os.Stdout` — testable with `cmd.SetOut(&buf)`); it also enables `cdeploy skill show > .claude/skills/cdeploy/SKILL.md` for project-level placement.

**Stamp/hash ownership model**: install never trusts a file it did not write. `renderSkill(canonical, version)` injects a metadata block — `metadata:` header + `cdeploy-version` + `cdeploy-content-hash: sha256(canonical)` — immediately before the frontmatter's CLOSING `---` (the second `---`, found via `frontmatterCloseOffset`; never a bare `---` in the markdown body), so the frontmatter stays the first bytes of the file (Gemini silently skips otherwise). `stripOwned()` removes exactly that block, giving the round-trip invariant `stripOwned(renderSkill(canonical, v)) == canonical` as literal byte-equality; the stamped hash is therefore simply `sha256(canonical)`, no self-reference. `verifySkillFile(onDisk)` answers ONLY "is this file consistent with its OWN stamp?" → `intact` / `modified` / `unstamped` (stripOwned → sha256 → compare to the recorded hash). The install decision needs a SECOND, distinct check — `bytes.Equal(stripOwned(onDisk), canonical)` against THIS binary's canonical bytes — to reach `unchanged` vs stamp-refresh vs updated; without both checks the `unchanged` state is unreachable. Modified or unstamped files (e.g. a copy dropped by `npx skills`) are refused by both install and uninstall without `--force`; uninstall removes only the stamped `SKILL.md`, then the `cdeploy/` dir only when it is empty (never a recursive delete). Dev builds stamp `cdeploy-version: dev` — freshness keys on the content hash, not the version string.

**SKILL.md content test pins** (`skills/skills_test.go`): future edits to `skills/cdeploy/SKILL.md` MUST keep these satisfied — frontmatter is the very first bytes (`---\n` fence with a closing `---`), `name: cdeploy` (matches the directory AND the `^[a-z0-9]+(-[a-z0-9]+)*$` regex), `description` non-empty and ≤1024 chars (and naming both ops and setup triggers: deploy/servers.yml/ssh), under 500 lines, and — load-bearing — NO `metadata:` key in the canonical frontmatter. That last pin is what keeps block insertion/removal trivial: the install-time renderer owns the `metadata:` block and `stripOwned` must round-trip back to exactly the canonical bytes, so a hand-authored `metadata:` key would break the byte-equality invariant.

## Package Coupling

The TUI package depends on `runner.Composer` (interface), not `compose.Compose` or `compose.RemoteCompose` (concrete). For operations that need to create a `Composer` at runtime (drilling into a group, or an action key binding the cursor row's project), use a `ComposerFactory` callback injected from `cmd/` — this keeps `tui` decoupled from `compose`. The factory takes the whole `compose.Project`, not a directory string, so it can branch on `proj.Unmanaged` and return the read-only `compose.HostContainers` for the synthetic `(unmanaged)` group. That same branch is how the grouped host view reaches its host-wide seam: `composerFactory(compose.Project{Unmanaged: true})` type-asserted to `HostGrouper`, so no signature had to widen. Similarly, `ProjectLoader` and `ConnectCallback` are injected by `cmd/` for remote server support. The `compose` package has the `HasComposeFile` package-level function for local compose file detection; project discovery (`ListProjects`) is a method on `Compose`/`RemoteCompose` requiring `Detect()` first. The `ConfigProvider` and `ExecProvider` interfaces are defined in `tui` (not `runner`) because they return `*exec.Cmd` and are TUI-only; the TUI type-asserts `composer.(ConfigProvider)` and `composer.(ExecProvider)` at runtime — no separate factory or wiring needed. `ReadOnlyComposer` is the same shape and the same reason: only `compose.HostContainers` implements it, and a composer that omits it renders the normal writable screen. `Inspector` is the same shape with the reach inverted — ALL THREE composers implement it, so the `i` key is live on every container screen and the type assert exists for test mocks rather than for a capability split. `UpdateDetailer` is `Inspector`'s twin: all three composers implement it, it is asserted the same way, and a composer that omits it simply renders no update rows. `HostGrouper` (two methods over one listing, `GroupHostStatus`/`GroupHostStats`) is the same shape with the narrowest reach: only `compose.HostContainers` implements it, and a factory that cannot produce one yields a grouped screen with projects but no status — not an error.

- `internal/compose/`: Test command construction (args, env vars, flags) without executing commands; `parseProjects()`, `parseContainerStatus()`, `parseStatsOutput()`, `parseSize()`, `parseCPUPercent()`, and `FormatBytes()` extracted for testability; `RemoteCompose` tests verify SSH arg construction and shell escaping; `inspect_test.go` drives `pickInspectContainer`/`pickHostInspectContainer`, `parsePsEntries` and `ParseInspect` against three real `docker inspect` fixtures, and asserts the inspect argv carries no `compose`; `hostcontainers_test.go` drives `HostContainers` through a fake `dockerRunner` (the same seam production uses), so every read method is testable without Docker and the remote adapter's `SSHExtraArgs`-before-host splice is pinned directly; `updatedetails_test.go` drives the four-step detail fetch through that same seam, against real registry captures in `testdata/imagetools_*.json` plus a real `docker image inspect` document in `testdata/image_inspect_nginx.json` (the one thing a hand-authored fixture cannot pin is docker's KEY SPELLING) — **no test may hit a registry**, since a suite that did would reproduce the 429 in CI
- `internal/config/`: Test YAML parsing, validation, and lookup with temp files
- `internal/tui/`: Test model state transitions by calling `Update()` with `tea.KeyMsg` directly — no TTY needed; `entries_test.go` drives the pure row model (`rebuildSvcEntries`, `svcKey`, `buildSvcGroups`, `partitionSelection`, `groupCounts`, `groupSelected`, `eachSelectableRef`, `eachUnfoldedSelectableRef`, `cursorGroup`, `flattenQualified`) with no Model machinery at all. **There is no `services` field on Model at all** — rows come from `svcGroups` → `svcEntries`, so a test that wants a flat name list uses the `modelServices(m)` helper. The grouped host view has its own file, `grouped_test.go` (the row model over several projects, the grouped loader and reload, fold/select, the header line, drill-in/out, action-time binding, the grouped `U` scan), and the multi-batch progress sequence it feeds has `batch_test.go` — put a new test for either subsystem there rather than growing `app_test.go` again. Every container-screen test must go through the fixture helpers — `singleGroupModel(services)` (`app_test.go`) for the degenerate one-group (drilled) shape, `groupedModel(groups…)` + `svcGroupOf(name, services…)` (`grouped_test.go`) for the multi-group host view, `selectedIdx(m, i…)` to build a selection from ROW indices, `qStatus(m, status)` / `qStats(m, stats)` / `qk(m, service)` to qualify a bare-name map or name the way the message handlers do, and `progressStep(name, status)` to build a progress row (`enterProgress` always sets `label` AND `batchStepCount`, so a fixture must too); `format_test.go` tests `formatLogContent()`, `softWrapLine()`, and `prettyPrintLine()` as pure functions; `inspect_test.go` tests `buildInspectSummary()` the same way, against the compose package's fixtures; `help_test.go` pins the `?` overlay (the two-directional drift pin — run PER VARIANT, `TestHelpGroups_NamesEveryBoundKey` for the writable table and `TestHelpGroups_ReadOnlyNamesEveryBoundKey` for the read-only one, plus `TestHelpGroups_ReadOnlyDropsGatedKeys` — the `allScreens` completeness check, the typing/confirmation exceptions, and the never-exceeds-width/height clamps)
- `internal/logging/`: Use `t.TempDir()` for file creation tests
- `skills/`: Content pins on the embedded `cdeploy/SKILL.md` (frontmatter first, `name` matches dir + regex, description ≤1024 chars, <500 lines, no `metadata:` key) — see "Agent Skill distribution" above
- `cmd/`: Test flag registration, subcommand existence, and validation via `NewRootCmd()`; `cmd/skill_test.go` uses `t.Setenv` HOME/CODEX_HOME (never `t.Parallel`) for the path matrix, symlink dedupe, and the install/uninstall decision matrix in a temp HOME (render/verify round-trip is pure)
