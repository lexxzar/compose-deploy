> Extracted verbatim from `CLAUDE.md`, which is auto-loaded and has a size limit.
> `CLAUDE.md` carries the rule digest; this file carries the full rationale, the

## Update detection — tri-state and Composer contract

`runner.ServiceStatus.UpdateAvailable *bool` is a tri-state: `nil` = unknown / not checked / build-only / error (blank cell), `*v == true` = a newer image exists in the registry (yellow `⇧` glyph, U+21E7), `*v == false` = current. `Composer.CheckUpdates(ctx, services) (map[string]bool, error)` returns only services that were *checked* — absent keys preserve the tri-state's nil for build-only services and per-image errors. When a non-nil error is returned, the accompanying map is *untrusted* — implementations may return a partial map (RemoteCompose does, with whichever services completed before the transport-fail abort), but partial verdicts may be inconsistent with unresolved services. Soft-failure consumers (CLI list, TUI) discard the map (`updates = nil`) and render all-blank-plus-warning rather than mixing partial verdicts with unresolved services. Local impl in `internal/compose/updates.go`; remote in `internal/compose/remote.go`; unmanaged-host impl in `internal/compose/hostcontainers.go` (which returns a partial map on a transport abort too, since its remote runner emits the same `errSSHTransport` sentinel). `compareImageDigest` returns `(updated, ok, err)` on both sides (3-tuple, kept symmetric) so empty-digest cases are distinguishable from positive verdicts without polluting the cascade counters with synthetic errors.

## Update detection — digest comparison

implementation always uses per-image digest comparison: `docker compose config --format json` for service→image mapping on the two compose paths (compose subcommand → goes through `command()`/`remoteCommand()`; `HostContainers` instead reads the `Image` field `docker ps` already returned, since there is no compose file), then `docker image inspect --format '{{range .RepoDigests}}{{println .}}{{end}}'` for the local digest and `docker buildx imagetools inspect` (preferred, default human format) or `docker manifest inspect --verbose` (fallback) for the remote digest. The buildx-first path is the **multi-arch fix**: `image inspect` returns the manifest-LIST digest for multi-arch images (because docker pulled via the list), and `imagetools inspect`'s top-level `Digest:` line is also the manifest-list digest — they match correctly. The legacy `manifest inspect --verbose` array form returns per-platform descriptor digests that never match a manifest-list digest (false positives on popular Docker Hub images like nginx/postgres/alpine/node/redis). `fetchRemoteDigestVia` (package-level, over the `dockerRunner` seam — the two per-composer `fetchRemoteDigest` methods it replaced no longer exist) tries imagetools first and falls back to manifest inspect only when imagetools fails for non-transport reasons (older Docker without the buildx plugin); SSH transport failures propagate immediately to abort the batch instead of retrying the same broken transport against a second endpoint. **IMPORTANT regression pin**: do NOT add `--format '{{.Manifest.Digest}}'` back to `imagetoolsInspectArgs` — empirically verified on Docker 29.1.3 / buildx v0.30.1-desktop.1 the template substitution silently falls through and the command prints the same default human-readable Name:/MediaType:/Digest:/Manifests: block as no format flag. A permissive "first non-empty line" parser would then return `Name:      docker.io/library/nginx:latest` as the "digest" → universal false-positive (every image flagged as updated). `parseImagetoolsDigest` extracts the top-level `Digest:` line (skipping indented per-platform digests under `Manifests:`) and validates against a strict `sha256:<64 hex>` regex (`imagetoolsDigestRE`); anything else returns empty so the manifest-inspect fallback engages. There is no defensive "bare sha256 line" fallback — aborting on the first non-matching line means any wrapper that prints a leading banner (e.g. a `motd`-injecting docker context) silently defeats it; every real buildx output we've observed exposes the digest on the primary `Digest:` line. Test fixture lives at `internal/compose/testdata/buildx_imagetools_default_output.txt` — a real `hello-world` capture exercised by `TestParseImagetoolsDigest_RealFixture` — and the parser's negative cases pin the `Name:` line, short non-hex, and wrong-length-hex rejections so the regression cannot be reintroduced. `parseLocalDigest(out, imageRef)` filters `RepoDigests` to the entry whose repo matches the compose-file image reference (stripping tags via `stripTag`); falls back to the first non-empty digest when no repo matches. `parseManifestDigest` extracts `Descriptor.digest`. All three (`docker image inspect`, `docker buildx imagetools inspect`, `docker manifest inspect`) **bypass `command()`/`remoteCommand()`** because they are top-level docker commands, not compose subcommands. Local Compose uses `runDockerCmd` (captures stderr explicitly via `strings.Builder`, mirroring the SSH path) and `RemoteCompose.runRemoteDockerCmd` builds the SSH argv directly and splices `SSHExtraArgs` immediately before the host arg (matching `AllContainerStatsRemote`/`EditCommand`/`ExecCommand`); image names are `shellEscape`d. The shared rune is `compose.UpdateGlyph` (alongside `FormatBytes`) so the TUI and CLI render the same character from a single source. The `docker compose pull --dry-run` path was explored and rejected: with `--policy=always` every non-build service reports "Pulling" regardless of currency; with `--policy=missing` the signal is "image present locally" rather than "image current in registry". The manifest-inspect/imagetools path is the single authoritative implementation.

## Update detection — SSH transport classification (RemoteCompose only)

`runRemoteDockerCmd` captures stderr explicitly (so test hooks producing non-`*exec.ExitError` errors still surface diagnostic context, and so classification works uniformly) and runs `classifySSHError(err, stderr)` which checks stderr against `sshTransportStderrPatterns` (case-insensitive substring match on SSH-only signatures: `ssh:`, `ssh_exchange_identification`, `could not resolve hostname`, `kex_exchange_identification`, `permission denied (publickey`, `control socket connect`, `port forwarding failed`, `lost connection`, plus ControlMaster failure modes `mux_client`/`client_loop`/`controlsocket`/`multiplex`/`session open refused`). Generic networking phrases like `connection refused`/`connection reset`/`broken pipe`/`no route to host` are deliberately NOT in this list — they ALSO appear in docker daemon stderr when docker fails to reach the registry, and classifying them as SSH transport would abort the entire CheckUpdates batch even though other images would have succeeded; the registry cascade below handles those instead. Transport matches are wrapped in the `errSSHTransport` sentinel; everything else is treated as a per-image docker failure and just gets the stderr appended for diagnostic context (mirroring `withStderr`). Tests can drive `classifySSHError` with explicit stderr via `RemoteCompose.SetOutputErrHook(func(*exec.Cmd) ([]byte, string, error))` — prefer this over `SetTestHooks` when the test cares about transport-vs-per-image classification; the legacy `outputCmd` path now passes empty stderr to the classifier (was: err.Error()-as-stderr) so production and test paths can't diverge. `CheckUpdates` then asymmetrically handles the two buckets: an `errSSHTransport` from ANY per-image call aborts the batch immediately with `"remote update check transport failure: <err>"` (return early — every subsequent call will fail the same way); a per-image docker failure (image not pulled, manifest auth required, registry 404) is absorbed into the tri-state "absent" cell, matching local Compose behaviour. Fresh-deploy single-service projects do not trigger a false cascade just because the image hasn't been pulled to the remote yet — `No such image` is a normal `docker image inspect` exit-1, not a transport failure.

## Update detection — systemic-failure cascades

`Compose.CheckUpdates` runs TWO parallel cascades so the soft-failure consumer sees a real diagnostic instead of an empty map. (1) **Registry cascade**: when `networkFailures == remoteAttempts > 0` AND `len(out) == 0`, returns `fmt.Errorf("registry unreachable: %w", firstNetErr)`. `looksLikeNetworkErr` matches `no such host` (canonical net.DNSError tail), `connection refused`, `dial tcp`, `x509:`, `too many requests`, `timeout exceeded`, etc. — patterns specific enough to avoid over-firing on per-image fragments. (2) **Local-docker cascade**: when EVERY local `docker image inspect` fails AND every failure ALSO matches `looksLikeLocalDaemonErr` (daemon not running, socket missing, docker CLI missing) AND `len(out) == 0`, returns `fmt.Errorf("local docker unavailable: %w", firstDaemonErr)`. The daemon-classifier gate prevents the common "fresh deploy with multiple un-pulled images" case (every image returns `No such image`) from misfiring as `local docker unavailable`. `compareImageDigest` wraps local failures in the `errLocalImageInspect` sentinel so CheckUpdates can dispatch via `errors.Is` into the right cascade. Partial failures (one image down, one up) do NOT cascade — the succeeded service gets a verdict, the failed one stays absent. **RemoteCompose mirrors the registry cascade**: when every non-transport failure matches `looksLikeNetworkErr` AND no service got a verdict, returns `"registry unreachable: <err>"`. This is critical because narrowing `sshTransportStderrPatterns` to SSH-only signatures means a Docker Hub outage seen from the remote host no longer trips the SSH-transport bucket — without this cascade, the remote case would silently blank every glyph with no diagnostic. The three classifiers (sshTransportStderrPatterns, looksLikeNetworkErr, looksLikeLocalDaemonErr) live next to their consumers — see the comment block above `looksLikeNetworkErr` in `internal/compose/updates.go` for the precedence overview. **All three `CheckUpdates` implementations share ONE loop**: `scanImageUpdates(ctx, wanted, compare)` in `updates.go`, with the per-image comparison behind `compareImageDigestVia(ctx, d dockerRunner, image, localErrWrap)`. **There is no per-caller cascade flag — the ERROR SHAPE the comparer emits is what selects the cascade**, and all three diagnostics run unconditionally. Only `Compose` passes `wrapLocalImageInspectErr` as `localErrWrap`, so only `Compose` can ever emit `errLocalImageInspect`, which is what routes a failed local `docker image inspect` to the daemon counters instead of the registry ones AND what keeps "local docker unavailable" off the SSH path, where it would name the wrong machine (`TestCompareImageDigest_SentinelBinding` pins the binding on all three composers, each direction independently mutation-sensitive). `errSSHTransport` likewise exists only on the remote runner, via `classifySSHError`. A flag would only re-state what the sentinel already decides — and `fetchRemoteDigestVia` already short-circuits on `errSSHTransport` with no flag one call level below. The transport abort is the one diagnostic that fires MID-scan rather than after it, because a dead SSH hop fails every remaining image the same way; the partial map still comes back with the error, matching the untrusted-partial-map half of the `Composer.CheckUpdates` contract. `scanImageUpdates` also **memoizes by image ref**, so a repeated image costs one comparison and contributes exactly one attempt to the cascade counters.

## Update detection — TUI caching and refresh

TUI caches results in `updateCache map[string]updateEntry` on Model, keyed `projectDir + "|" + serverName` (empty `serverName` = local; `projDir` is stored on Model because it's not otherwise retained after composer creation). `updateEntry{fetchedAt time.Time, results map[string]bool, err bool, errMsg string}` in `internal/tui/app.go`. **Two TTLs**: successes live for `updatesCacheTTL` = 10 minutes; failures live for `updatesErrorTTL` = 30 seconds. **Errors ARE cached** (with the short TTL): caching failures prevents the 5-second tight retry loop the `statusMsg` self-heal would otherwise produce on a persistent fault (empty cache → queue refresh → fail → empty cache → repeat; ~120 failed CheckUpdates per 10 minutes against a slow remote SSH hop or a Docker Hub outage). The cached failure entry has `results=nil`, `err=true`, and `errMsg` set to the original error text. **`errMsg` is restored on cache hit** in `maybeRefreshUpdatesCmd` and the `servicesMsg`/`statusMsg` cache-replay paths — without this, navigating away (which clears `m.updatesErr`) and re-entering within `updatesErrorTTL` would silently drop the soft warning even though the failure is still known-bad. A new error entry overwrites any prior successful entry for the same key (don't trust stale success once the latest refresh disagreed); a new success overwrites a cached failure. **Off-screen error handling**: the `updatesMsg` handler applies state mutations (set `updatesErr`, clear stale `UpdateAvailable` glyphs in `m.svcStatus`, hydrate fresh verdicts) BEFORE the screen check — `m.svcStatus` is the source of truth the next entry to `screenSelectContainers` renders from, so leaving stale glyphs in it during an off-screen window (e.g. the config screen, which is read-only and does NOT trigger `refreshStatus` on return) would let them resurface alongside no warning. Only `fixSvcOffset` stays screen-coupled (touches scroll offsets that are only meaningful while the container list is rendered). **Post-operation cache invalidation**: the `esc` handler that returns from `screenProgress` to `screenSelectContainers` deletes the cache entry for the current key on a successful Deploy or Restart, so the next `maybeRefreshUpdatesCmd` misses and enqueues a fresh CheckUpdates — without this, the "update available" glyph would persist for up to 10 minutes after a successful deploy, exactly when the user wants confirmation. Invalidation runs BEFORE the `m.done = false` reset (otherwise the check would see done==false and never fire). Skipped on `m.failed` (don't clear user-visible state on failure) and on Stop (stopping doesn't change image freshness). `refreshUpdates(session)` is fired on entry to `screenSelectContainers` only when the cache is missing or stale (`maybeRefreshUpdatesCmd` helper); the uppercase `U` key bypasses TTL for force-refresh AND guards against stacking via `if m.updateInFlight { return m, nil }`. Updates are **NOT** wired into the periodic 5s `refreshTickMsg` — cadence is TTL + explicit user action, because registry round-trips are expensive and the answer changes slowly.

## Update detection — sessions and in-flight discipline

`updatesMsg{results, err, session uint64}` carries a session captured at fetch time; `updatesSession` is bumped at the **same 7 sites** as `statsSession`/`statusSession` (project pick, esc container→proj, esc proj→server, entryLocal, execDone, return from progress, return from logs) but NOT at the `connectResultMsg` SUCCESS path (`m.composer` hasn't been swapped yet — the bump happens at the project-pick handler downstream; the success path carries a code comment documenting this asymmetry so future contributors don't add a redundant bump). The `connectResultMsg` ERROR path bumps `projectsSession` (the connect attempt swapped the projectLoader) but not the other three counters (composer/composerFactory weren't touched). The dedicated `updateInFlight bool` flag follows the same clear-before-screen-check pattern as `refreshInFlight`, with one strengthening: the flag is cleared BEFORE BOTH the session check AND the screen check, on EVERY `updatesMsg` arrival (current OR stale, on-screen OR off). The previous "stale leaves it alone, context-change handler resets it" semantics had a sticky-flag bug: after `U` (in-flight=true) → navigate away → come back, the original fetch arrived with an OLD session, and the in-flight guard inside `maybeRefreshUpdatesCmd` would silently swallow every subsequent fetch on cache hits. Clearing on stale arrivals as well is safe because the cache write below is still session-gated, so a stale result can't pollute the cache. Companion guard: `maybeRefreshUpdatesCmd` early-returns nil when `m.updateInFlight == true`, preventing fetch stacking — same rationale as `refreshTickMsg`'s `refreshInFlight` gate. Because of this guard, every context-change site that bumps `updatesSession` AND calls `maybeRefreshUpdatesCmd()` (project pick, execDone, esc back from progress/logs, entryLocal fast-track) MUST reset `m.updateInFlight = false` first; the session bump invalidates any in-flight fetch (its response will be discarded as stale), so the guard must not refuse to fire a fresh fetch for the new context. The 2 leave-screen transitions (esc container→proj, esc proj→server) also reset `updateInFlight = false`. The `connectResultMsg` error path also clears `serverName`/`updatesErr`/`updateInFlight` so a failed connect attempt doesn't leak transient state into a subsequent connection. The `entryLocal` handler explicitly clears `projDir`/`projName`/`updatesErr` to prevent stale cache-key components carrying over from a previous remote session.

## Update detection — rendering, CLI, and JSON

Cache results are re-hydrated onto `m.services` inside `servicesMsg` and `statusMsg` handlers via a `hydrateUpdates` helper, race-safe regardless of arrival ordering of status vs updates. **Phantom guard**: `hydrateUpdates` skips verdicts whose service name is NOT already in `m.svcStatus` — without this guard, a verdict for an unknown service (compose config and ContainerStatus may transiently disagree during a refresh, or a stale verdict may refer to a service that no longer exists after a project switch) would synthesise a zero-valued `ServiceStatus` entry that'd leak across context switches. The renderer iterates `m.services` (not the status map) so phantoms are invisible today, but the guard prevents a latent class of bugs in any future iterator. Rendering: yellow `updateGlyphStyle` in `internal/tui/styles.go` appends `" ⇧"` after the service name; `maxName += 2` unconditionally (always reserve the glyph slot so Created/Uptime/CPU/Mem/Ports don't shift when a verdict arrives or clears mid-poll); glyph is shown on stopped services too. The `U updates` token lives in the `?` overlay, not the footer. Errors render in the soft-warning slot prefixed `updates: `, priority `svcErr > statsErr > updatesErr`. CLI `cmd/list.go` gates `CheckUpdates` behind `--updates` in BOTH single-project (`-C`, `--ssh`) and multi-project modes (same opt-in shape as `--stats`) — each service costs one registry round-trip and 20+ services over SSH adds 10s+, so the default is off in both modes; soft failure prints `cdeploy: updates unavailable: <err>` (or `for "<project>": <err>` in multi-project) to stderr and leaves cells blank without aborting the listing — callers SET `updates = nil` on error in line with the `Composer.CheckUpdates` partial-untrusted contract above; JSON output gains `update_available *bool` with `omitempty` so the wire shape is unchanged when the flag is omitted. `formatDots`/`formatDotsGrouped` extend `maxName` by 2 cells the same way as the TUI — width is measured by `utf8.RuneCountInString` because the U+21E7 glyph is multi-byte but renders in one terminal cell, and styled rendering carries ANSI escapes that don't count toward display width. The glyph rune is owned by `compose.UpdateGlyph` so both surfaces stay in sync; bumping it changes both in one place.

## Update detection — the inspect screen's detail rows (`UpdateDetailer`)

Once the `⇧` verdict is `true` the glyph raises two questions it cannot answer: WHICH image is waiting, and WHEN each side was built. The inspect screen's IMAGE section answers both with four rows — `built`, `update`, `update id`, `update built` — drawn from `compose.UpdateDetail{LocalCreated, NewID, NewCreated}` (`internal/compose/updatedetails.go`), a three-field struct carrying exactly what a row draws and nothing more (`Platform` and `LocalID` were in an earlier draft and were dropped: `docs/architecture/tui-inspect-screen.md` states the rule directly — a parsed-but-unrendered field is a promise the screen does not keep). **`NewID` is the registry image's CONFIG digest, and that is the whole reason it is comparable with the `image id` row above it**: measured on Docker 29.1.3 / buildx v0.30.1-desktop.1, resolving the config digest at an image's own RepoDigest returned the same `sha256:7e7dbab8…` that `docker image inspect --format '{{.Id}}'` reports locally. The manifest-LIST digest `CheckUpdates` compares is a different thing entirely, which is why the same change relabelled the summary's `digest` row to `image id` — an `update id` row sitting beside a row labelled `digest` invites exactly the false comparison this feature must avoid.

**`UpdateDetailer` is a TUI-declared interface, not a `Composer` change.** It is declared in `internal/tui/app.go` beside `Inspector`/`ConfigProvider`/`ExecProvider` and type-asserted on the concrete composer, so `runner.Composer` and its five mock sets (`internal/runner/`, `internal/tui/app_test.go`, `cmd/deploy_test.go`, `cmd/list_test.go`) are untouched and `cdeploy list --updates` keeps its current cost — the CLI has no detail view, so it would pay three extra registry round-trips per updated image for data it cannot show. All three composers implement it (`Compose.UpdateDetails` over `localDockerRunner`, `RemoteCompose.UpdateDetails` over `remoteDockerRunner`, `HostContainers.UpdateDetails` over its own `dockerRunner` field), which is why **the three `var _ UpdateDetailer = …` compile-time pins sit beside the `Inspector` triple in `app_test.go`**, plus the runtime assertion in `TestHostContainers_CapabilityInterfaces`: the whole path runs through a runtime type assertion and every TUI test drives a double that satisfies it by construction, so without the pins a rename or a signature drift leaves all 7 packages green while the rows silently vanish. A composer that does NOT implement it produces verdicts with no detail rows — the same outcome a detail-fetch failure produces, which is the point.

**The fetch rides `refreshUpdates`, and that is the requirement rather than an optimisation.** The explicit requirement was that the detail rows follow the same rules and timings as the `⇧` glyph. Rather than satisfy that with a parallel schedule that could drift, `refreshUpdates()` — the single Cmd that already owns the glyph — calls `UpdateDetails` in the SAME goroutine, immediately after `CheckUpdates`, and the result rides the same `updatesMsg` into the same `updateEntry` under the same key, the same two TTLs, the same `updatesSession` gate and the same post-Deploy/Restart/Rollback invalidation. One Cmd, one message, one cache entry, one session counter: the "same timings" property holds by construction. It follows that no new Model field exists, so `clearInspect()`, the `esc` chain, `entryLocal` and the `connectResultMsg` error path need no cleanup — `details` lives only on the context-keyed cache entry and on the already-session-gated message. It also follows that the read-only unmanaged screen never fetches details on its own: `autoUpdatesAllowed()` gates the three entry points to `refreshUpdates` and `U` remains the only trigger there.

**A detail failure is discarded and must never reach `updatesMsg.err`.** `fetchUpdateDetails` (`app.go`) drops the error on the floor. That is load-bearing, not laziness: a Docker Hub rate limit reads as `429 Too Many Requests`, `looksLikeNetworkErr` matches `too many requests`, and a detail-phase failure promoted to `updatesMsg.err` would trip the registry cascade, blank the ENTIRE `⇧` column and shorten the cache entry to the 30-second error TTL — a rate limit hit while annotating the signal would degrade the signal it was annotating. The glyph is the load-bearing view and these rows are a bonus, the same asymmetry the `svcErr > statsErr > updatesErr` soft-warning priority already encodes. The detail phase is also **skipped entirely when `CheckUpdates` itself errored**: a non-nil error makes the whole verdict map untrusted per the `Composer` contract above, so no verdict is worth following up and the round-trips would be spent on a path that is already broken.

**The cost is real and was measured.** Each updated image costs FOUR round-trips (one local, three registry) on top of the one `CheckUpdates` already makes. During research ~15 anonymous manifest requests inside ten minutes was enough to earn `429 Too Many Requests` from `registry-1.docker.io` on a HEAD to `/v2/library/postgres/manifests/16-alpine`. Three mitigations are built in and **all three are load-bearing, not defence in depth**: (1) details are fetched ONLY for services whose verdict is `true`, usually a small minority — `servicesWithUpdate` filters, and the empty-slice guard in `fetchUpdateDetails` is required because `filterServices` reads an empty services slice as **ALL** services, so calling through with no true verdicts would spend four round-trips on every service in the project; (2) `scanUpdateDetails` memoises by image reference exactly as `scanImageUpdates` does, and memoises FAILURES alongside successes so a repeated unresolvable image costs one call set rather than one per service; (3) the `autoUpdatesAllowed()` inheritance above. The recommended operator-side mitigation is `docker login` on the docker host, which raises the anonymous quota.

**Considered and rejected — reusing the index `CheckUpdates` already fetched.** `fetchRemoteDigestVia` runs `imagetools inspect <ref>` moments earlier and its human output carries a `Manifests:` block with a `Name:` and `Platform:` per entry; harvesting per-platform digests from it would remove step 2 and cut the cost by a quarter. Rejected on two grounds: parsing per-platform digests out of that human block is exactly the fragile text parse that produced the `--format` regression this subsystem already carries a pin against, and plumbing the raw bytes out of `scanImageUpdates` would change a loop all three composers share. Revisit only if the quota proves binding in practice.

**The four-step sequence** (`fetchUpdateDetail`), per image, all four bypassing `command()`/`remoteCommand()` through the `dockerRunner` seam because every one of them is a top-level docker command:

| # | Command | Yields |
|---|---|---|
| 1 | `docker image inspect --format '{{.Created}}\|{{.Os}}\|{{.Architecture}}'` | `LocalCreated` + the platform pair. **Local only.** |
| 2 | `docker buildx imagetools inspect --format '{{json .Manifest}}'` | the index; select the entry matching the platform pair |
| 3 | `docker buildx imagetools inspect --raw <pinnedRef>` | `config.digest` → `NewID` |
| 4 | `docker buildx imagetools inspect --format '{{json .Image}}' <pinnedRef>` | `created` → `NewCreated` |

`<pinnedRef>` is `StripTag(ref) + "@" + platformDigest`, reusing the exported helper `rollbackImageRef` already uses rather than re-deriving the repo portion, so a registry port (`localhost:5000/foo:1`) survives the rewrite. Steps 2-4 are registry calls, so `fetchUpdateDetail` returns at the FIRST failure rather than pressing on — the caller omits the whole entry either way and a wasted round-trip is a step closer to the rate limit. **A step that SUCCEEDS but whose parser returns "absent" is NOT a failure**: only its own field stays zero and the rows the other steps filled still render. Going through the seam is what makes the remote path free: `remoteDockerRunner` already carries the `SSHExtraArgs`-before-host splice, `shellEscape`, and `classifySSHError`, so an `errSSHTransport` short-circuits `scanUpdateDetails` and returns the partial map alongside the error, matching the untrusted-partial-map contract. **Services are visited in SORTED order** for the same reason `servicesWithUpdate` sorts: each image costs three registry calls and a transport abort truncates the batch, so which images are reached must not depend on Go's map iteration order — otherwise the abort test is flaky and the quota cost is nondeterministic.

**`{{.Variant}}` is deliberately absent from step 1, and must stay absent.** A Go template referencing a field the docker struct lacks is a hard execution error, not an empty string — the same policy `hostPsArgs` documents for `{{json .}}`. On an older docker host, adding `.Variant` would fail step 1 for EVERY image and silently disable the whole feature. Variant is only ever a tie-breaker in the index match, so the local side treats it as always-empty. `.Id` is absent for the "only what a row draws" reason: the `image id` row already comes from the container's own inspect document.

**`parseIndexPlatformDigest` is three-state, and conflating two of the states is the silent failure mode.** `hasIndex=false` means there is no `manifests` key at all — a single-manifest ref, so steps 3 and 4 address the ORIGINAL ref. `hasIndex=true, found=false` means an index exists but the host's platform is absent from it, and the caller must **abort this image**. `hasIndex=true, found=true` pins and continues. A `(string, bool)` return would collapse the middle state onto the first, and then step 3 would run `--raw` against the index (which has no `config.digest`, so `NewID` comes back empty) while step 4 would return the platform-keyed map from which the code could pick a platform that is not the host's — a wrong `update id` and a wrong `update built`, drawn confidently. **Every doubt therefore returns the ABORT state**: malformed JSON, a `manifests` value that is not a list, and an empty os/arch argument all fail closed rather than being read as "single manifest". A real multi-arch index also interleaves **attestation manifests** carrying `platform.architecture == "unknown"` — 8 of nginx's 16 entries — whose digests address provenance/SBOM blobs rather than runnable images, so any entry with an `unknown` os or architecture is skipped. Variant is a tie-breaker with a determinism rule, since the signature carries no wanted variant: among the entries matching os+arch an entry with NO variant wins regardless of index order, and with only variant-qualified entries the first in index order wins.

**Step 4 must accept both shapes.** A pinned ref returns a bare OCI config object; a bare tag returns a platform-keyed map (and costs ~4.3 s against ~1.2 s, which is why callers pin whenever step 2 gave them a digest). Both are reachable because a single-arch ref arrives at step 4 unpinned. `pickImageConfig` discriminates on a top-level key CONTAINING `/` for the map form, falling back to a key from `imageConfigKeys` (`created`, `architecture`, `rootfs`, `config`, `history`) for the object form; a document that is neither returns "absent" rather than being read as one of them. **The bare object is trusted WITHOUT a platform cross-check** — it is only reached for a ref that resolves to exactly one manifest, so its config is the only one there is, and rejecting it on a platform mismatch would drop the row for every legitimate single-arch image. The map form applies the same variant tie-breaker with one extra rule: an unqualified `os/arch` key wins, and among variant-qualified keys the LEXICOGRAPHICALLY first wins, because Go map iteration order is not stable so "index order" does not exist here.

**`validImagetoolsDigest` is a WHOLE-STRING check, shared by steps 2 and 3.** It reuses `imagetoolsDigestRE` and normalises to lower case, and it is whole-string rather than a substring search for exactly the reason `parseImagetoolsDigest` is: the `--format` flag on `imagetools inspect` is only SELECTIVELY usable — `{{json .Manifest}}` and `{{json .Image}}` substitute correctly on buildx v0.30.1 while the documented `{{.Manifest.Digest}}` silently falls through and prints the human block — so a permissive parser would one day accept a fallen-through `Name:` line as a digest. Every parser here validates strictly and returns "absent" on doubt, so a future buildx regression drops rows rather than drawing wrong ones.

**The epoch sentinel.** `created` is `1970-01-01T00:00:00Z` for reproducible builds — verified on `gcr.io/distroless/static`, and true of ko, Bazel and nix images too. It is a placeholder, not data, so `parseImageTimestamp` treats any `Unix() <= 0` as the zero time and the TUI's `formatInspectTimeValue` applies the same guard on the render side; the `built` / `update built` row is then omitted. There is no upstream fix, so those images show no build date at all. An unparseable timestamp takes the same path rather than erroring: the platform pair beside it is still usable, so the scan continues and only the one row drops. A wrong field count or an EMPTY os/arch IS an error, though — without a platform pair the index match can only fail, so erroring in `parseLocalProbe` saves the three registry round-trips that would follow.

**Rendering: one lookup site, and the inspect screen never fetches.** `buildInspectSummary(doc, width, upd inspectUpdateInfo)` stays pure — the clock arrives inside `upd` rather than through a `time.Now()` call in the renderer — and **the zero value of `inspectUpdateInfo` draws no new row**, which is what made the signature widening mechanical and every pre-existing assertion hold. `rebuildInspectSummary()` is the SINGLE place the cache is read (via `m.inspectUpdateInfo()`), so the fetch path, the resize branch and the `updatesMsg` arrival cannot drift into three copies. That lookup deliberately reads the raw map rather than the TTL-checked `updatesCacheLookup`: the glyph itself is drawn from `m.svcStatus`, which keeps the last verdict until a refresh replaces it, so an entry aging past its TTL must not blank these rows either — the `(checked 3m ago)` suffix is what tells the user how old the answer is, and it is dropped rather than reported as "moments ago" when the entry carries no fetch time. An errored entry yields the zero value. **The `updatesMsg` handler carries a `screenInspect` branch** that rebuilds the summary and re-writes the viewport content: without it, pressing `i` while the first fetch is still in flight — a cold cache is exactly when that happens — would leave the rows permanently absent until the user backed out and re-entered. It sits directly after the cache write so it runs on the FAILURE path too: the entry that just landed carries no details, so a summary drawn from a previous one must stop showing them. It is the one screen-coupled mutation in that handler. Raw mode is untouched — `m.inspectRaw` never sees these values, so `r` stays byte-identical to `docker inspect`.
