## Container search (search & jump)

The `/` key on the container screen opens an incremental **search-and-jump** — it is **not a filter**. The row list is never narrowed and the multi-select map (`m.selected`) is never touched; only `svcCursor` moves and matching rows are highlighted, so multi-select/deploy/restart/stop semantics stay intact (regression-pinned by `TestSelectedContainersUnaffectedBySearch`). **`m.selected` is `map[string]bool` keyed by `svcKey(project, service)` = `project + "/" + service`, NOT a position-keyed map**: a fold renumbers every row below it, so nothing on the container screen may be keyed on a row index across a rebuild, and two projects on one host each owning a `db` need distinct keys anyway (see `docs/architecture/tui-multi-project.md`). It is fully synchronous — no goroutine, channel, or session counter (unlike stats/status/updates). Five Model fields (`internal/tui/app.go` ~537): `searching bool` (bar open, capturing text), `searchInput textinput.Model`, `searchQuery string`, `searchMatches []int` (indices into `m.svcEntries`, the ROW list — **never into `m.services`**, which is a flat name list with no rows behind it), `searchReturn int` (`svcCursor` to restore on esc-while-typing) and its identity twin `searchReturnID svcRowID`. **Two-mode model**: *typing* (`searching == true`) — the bottom bar is an open `textinput`, every keystroke routes to it and then recomputes matches and live-jumps `svcCursor` to `searchMatches[0]`; *committed* (`searchQuery != "" && !searching`) — bar closed, matching rows stay highlighted, `n`/`N` cycle, `j`/`k` move but keep the highlight. Highlighting and `n`/`N` are driven purely by `searchQuery != ""`. `computeMatches(entries []svcEntry, query string) []int` is a pure case-insensitive substring match on the service name, **skipping group HEADER rows** (a header names a project, not a service), preserving row order and returning `nil` for an empty query (table-tested). **Every fold toggle and every grouped reload must RE-DERIVE `searchMatches`**: both rebuild `svcEntries` wholesale, so the cached indices point at rows that have been renumbered — the fold handler re-derives, then clamps the cursor, then fixes the offset, in that order, and the grouped `servicesMsg` branch (which is also the 5-second periodic reload) does the same rather than clearing the search, because clearing it every 5 seconds would fight the user. **A search also UNFOLDS any folded group that holds a match**, so a match is never invisible: folding hides ROWS, `computeMatches` walks rows, and a jump to a row that is not drawn is a cursor the user cannot see — without it `/db` over a folded group reports `(no match)` for a service that is plainly on the host. `unfoldSearchMatches(query)` runs BEFORE the indices are computed and rebuilds `svcEntries` when any fold changed; the unfold is deliberately NOT undone when the search is cancelled, because re-hiding the row the user asked to see is the more surprising move. **Ephemeral-on-departure cleanup invariant**: `m.clearSearch()` (resets all five fields, `SetValue("")`/`Blur()` on the input) is called on **every** transition that *leaves* `screenSelectContainers` or *reloads* the rows — the 11 sites are `servicesMsg` (the DRILLED branch only), `connectResultMsg` error path, `entryLocal`, `enterProgress()`, `enterConfig()`, `enterInspect()`, `enterExec()`, `enterLogs()`, `enterGroupedContainers()` (drill-OUT and every other landing), `drillIntoGroup()` (drill-IN) and `backToServerScreen()`. **The grouped `servicesMsg` branch is the deliberate exception** and is why the drilled branch has to be named specifically: it is also the 5-second reload, so it preserves an active search (and the cursor, the selection and the fold state) and re-derives `searchMatches` instead — the landing sites clear that state once, on entry. Because departure always clears, the ~6 **return** paths into the screen (`esc` from logs/config/progress, `execDoneMsg`, init, pre-select) need **no** `clearSearch()` — a committed search never survives a nested-screen peek or an operation, and `searchMatches` can never carry stale indices into a rebuilt row list. A committed search does not survive; the user re-opens `/` if needed. **Cycle** (`cycleMatch(forward bool)`, no-op when `searchQuery == ""` or no matches): steps through `searchMatches` (kept ascending by `computeMatches`) with **wrap-around**; when the cursor sits *off* all matches after a manual `j`/`k`, `n` jumps to the first match strictly after the cursor and `N` to the first strictly before (wrapping at the ends). The bottom bar shows an `(i/N)` position counter (or `(no match)` while typing with no hits). **Two-stage `esc`** (committed mode): the first `esc` clears the search (guard at the top of `case "esc"`: `if m.searchQuery != "" { clearSearch(); fixSvcOffset(); return }`) and stays on the screen; a second `esc` (no active search) falls through to the normal back-nav. `esc` **while typing** is a separate branch inside the `if m.searching` intercept — it restores the cursor and consumes the key without back-nav. **That restore goes through `searchReturnID` FIRST (`indexOfRowID`), and falls back to the raw `searchReturn` index only when the row is gone**: typing UNFOLDS a group holding a match and the 5-second grouped reload rebuilds the rows underneath, and either renumbers `svcEntries`, so the index alone put the cursor on a *different* row. Both fields are captured BEFORE `clearSearch()` (which resets them) and the branch ends with `clampSvcCursor()` + `fixSvcOffset()`; the cursor-by-identity rule is the same one the grouped reload's `restoreCursorRow(cursorRowID())` follows (see `docs/architecture/tui-multi-project.md`). **Guards & seams**: `case "/"` early-returns when `len(m.services) == 0` (mirrors the `l`/`x` empty-list guards). `searchInput` is `(re)constructed via textinput.New()` inside the `/` handler — **not** in `NewModel` — because ~18 tests build `Model{}` literals directly, which would otherwise leave a zero-value input that doesn't echo runes (it is only ever rendered while `searching`, so a zero value is never displayed). The bottom-bar line is **always reserved** (blank when idle) so the list height never jumps between search-idle/searching/committed; `viewSelectContainers()` writes it in **both** the `confirming` early-return branch and the normal branch — search and `confirming` coexist (a committed search stays live when the user presses `d`), and the confirm prompt takes precedence over the bar on that shared reserved line. **The bar costs NO extra row in `svcVisibleCount()`**: it is emitted as `gap + searchBarLine()` with no newline of its own and merges with the full-width blank `helpStyle`'s `MarginTop(1)` already prepends, so the footer arithmetic (gap-or-indicator + MarginTop line + help lines) is unchanged. Counting the bar as its own row over-reserves one and the list silently loses a line at every height. The `q`→`esc` rewrite block is skipped entirely while `m.searching` (via the shared `typingInInput()` guard, which the `?` intercept also reads), so `q` lands in the `searchInput` as a literal character (`TestQTypedIntoSearchInput`) instead of hitting the `screenSelectContainers` sub-case's `!m.canGoBack() && !m.confirming` quit. Rendering: `searchMatchStyle` (yellow, same as `updateGlyphStyle`) wraps matching names and `searchCurrentStyle` (yellow + `Bold`) wraps the current match (`i == svcCursor`); styling wraps only the raw name so display-width math (`utf8.RuneCountInString`) is unaffected, same rationale as the update glyph/ports column. `/ search` lives in the `?` overlay, not the help footer; while the search input is OPEN the WHOLE footer becomes `enter jump · esc cancel` (`line1` included — `space`, `q` and `?` all type literal runes in that state), and once the search is COMMITTED only `line2` is replaced, by `n/N cycle · esc clear`. **One-physical-line invariant**: because `svcVisibleCount()` reserves exactly ONE row for the bar, `searchBarLine()` MUST always render as exactly one physical line — a long typed query, a long service name, or the committed-mode hint would otherwise wrap at narrow widths and push the footer past its reserved space (list overflows / cursor scrolls off). Two mechanisms enforce this: (1) the typing-mode `textinput.Width` is set to `m.width - len("  / ") - len(counter)` so a long query scrolls *within* the input, and (2) the final bar string (all non-idle modes) is clamped to `m.width` via `clampToWidth()` → `ansi.Truncate` (ANSI-aware: preserves/reset escape sequences, counts by display cell). `clampToWidth` no-ops when `m.width <= 0` (unknown terminal size in tests), mirroring `svcVisibleCount`'s `m.height == 0` fallback. Pinned by `TestSearchBarLineNeverWraps` (asserts `ansi.StringWidth(searchBarLine()) <= m.width` at widths 40/20 with long content). Reopening `/` over a *committed* search calls `clearSearch()` FIRST (before rebuilding the fresh input + setting `searching`/`searchReturn`) so the reopened bar starts empty with no stale highlights/counter and an immediate `enter` can't re-commit the old query (`TestSearchOpenOverCommittedResetsState`). TUI-only — no CLI/runner/compose changes.

## Log streaming

The `screenLogs` screen uses `io.Pipe` to bridge `Composer.Logs()` (blocking, writes to `io.Writer`) with Bubble Tea's message-driven architecture. A goroutine calls `composer.Logs(ctx, service, true, 50, pipeWriter)` and the `readLogChunk` tea.Cmd reads 4096-byte chunks from the pipe reader, sending `logChunkMsg` or `logDoneMsg`. The log context is derived from `m.ctx` so quitting the TUI cascades cancellation. Pressing `esc` cancels the log context, clears all `logs*` fields, and returns to the container screen.

## Log follow-aware auto-scroll

The tail is follow-aware — scrolling up auto-pauses it (read/scroll freely while the stream keeps flowing underneath), scrolling back to the bottom resumes it. **Headline invariant: ZERO new Model fields** — the viewport's `YOffset` *is* the pause state; "following" ≡ `m.logsViewport.AtBottom()`, recomputed wherever needed. The `logChunkMsg` handler captures `following := m.logsViewport.AtBottom()` BEFORE appending the chunk and only calls `GotoBottom()` when `following` (`SetContent` preserves `YOffset`, so a paused view holds while chunks keep landing). There is no new key: `G` (GotoBottom) doubles as "jump to live and resume follow". The three reformat sites — `w` wrap toggle, `p` pretty toggle, and the `WindowSizeMsg` `screenLogs` resize branch — each capture `following` before `fullReformat()` and re-`GotoBottom()` if following, so a live tail stays pinned across a reformat/resize (otherwise a changed line count would read as an accidental pause). The pure helper `logTailStatus(vp viewport.Model, done bool) (label string, below int)` drives a header indicator in `viewLogs()`: green `● following` when at bottom, yellow `⏸ paused ▲ N below` when scrolled up (`N = TotalLineCount − YOffset − Height`, clamped at 0 — the display-row distance to the live bottom, i.e. how far `G` will jump), and nothing (`""`) once the stream is done (`m.logsDone`) — there is nothing left to follow. Styles `logFollowStyle` (green `Color("2")`) / `logPauseStyle` (yellow `Color("3")`, same as `updateGlyphStyle`) live in `styles.go`. The `logDoneMsg` handler is unchanged — its force-`GotoBottom()` on error is deliberate (a terminal error should be pulled into view). TUI-only — no CLI/runner/compose changes.

## Log formatting

The log viewer has two independent toggles: `w` for soft-wrap (default: on) and `p` for JSON pretty-print (default: off). These are implemented via `formatLogContent()` and `formatLogLines()` in `internal/tui/format.go` — pure functions that process raw log content through optional pretty-print and soft-wrap stages. `applyLogFormat()` incrementally formats only the not-yet-scanned tail of the raw-line buffer (via `foldNewRawLines`, using `logsScanned` as a resume cursor into `logsRawLines`), appending to the cached `logsFormatted` — see the **Log search & filter** paragraph for the raw-line derivation pipeline that replaced the old flat `logsContent`/`logsRawOff` string. `fullReformat()` resets and reprocesses everything — called when toggles flip or the window resizes. When wrap is off, horizontal scrolling is enabled (`SetHorizontalStep(4)`). Docker compose log lines with format `<service> | <json>` have their JSON body indented with continuation lines padded to align under the body start.

## Log search & filter

Two coordinated navigation affordances on `screenLogs`, both synchronous/pure (no new goroutine or session counter — the existing `logsSession` + `m.screen == screenLogs` guards suffice). `f` opens a live **filter** (grep that hides non-matching lines while the stream keeps buffering underneath); `/` opens a **search** (highlight-and-jump *within* the possibly-filtered survivors, mirroring the container-screen search-and-jump). They coexist (lnav/less model): filter narrows, search highlights within. Both use `buildMatcher(query, isRegex, allowNegate) (pred, re, valid)` in `internal/tui/logfilter.go` — case-insensitive substring by default, `ctrl+r` toggles Go RE2 `regexp` (compiled **once**, reused per line); filter passes `allowNegate=true` so a leading `!` strips-and-inverts (RE2 has no negative lookahead — search has no `!`). `buildMatcher` returns `valid=false` (nil pred/re) on empty query, lone `!`, or bad regex; a **bad regex mid-type keeps the last-good predicate** (no thrash) and regex-ness is read from the committed `logFilterCommittedRegex`/`logSearchCommittedRegex` bool (NOT the live `IsRegex` flag) in `logFilterPred`/`logSearchPred`, so a `ctrl+r` into a *bad* regex holds the prior matcher instead of dropping the filter. **The `recomputeLogFilter`/`recomputeLogSearch` call sites still pass the LIVE `IsRegex` flag** — that is what makes `ctrl+r` take effect at all; the committed bool records the mode of the last query `buildMatcher` accepted and is read ONLY by the `logFilterPred`/`logSearchPred` re-derivations. Swapping the live flag for the committed one at the recompute sites makes `ctrl+r` a no-op. **Raw-line derivation pipeline** (replaces the old flat `logsContent`/`logsRawOff` string): the source of truth is `logsRawLines []string` (complete logical lines, always unfiltered) + `logsPartial` (trailing incomplete line, no newline yet) + `logsScanned` (a RAW-line scan cursor — count of raw lines already folded into `logsFormatted`, **not** a survivor count). `logChunkMsg` splits incoming bytes on `\n` into raw lines + partial; the filter runs at the **raw-line level before pretty-expansion** (`deriveFiltered(raw, pred)`, nil pred = pass-through), so a matched `svc | {json}` line pretty-prints as a whole block. `foldNewRawLines(raw, scanned, …)` folds only `raw[scanned:]` through the pred + formatter and **always advances the cursor to `len(raw)`** — advancing by survivor count would re-scan already-filtered lines and duplicate output (the survivor-cursor trap). `fullReformat()` resets `logsScanned=0`/`logsFormatted=""` and re-scans; `rederiveLogs()` wraps it with the follow-aware `AtBottom()`→`GotoBottom()` capture (the filter-change analogue of the `w`/`p` toggle). Because the raw buffer is never touched by the filter, **clearing the filter reveals lines that streamed in while it was active**. A terminal error (`logDoneMsg`) is stored in a dedicated **filter-exempt** `logsErrLine` slot appended outside the predicate path (always renders regardless of an active filter), not mixed into `logsRawLines`. **`setLogViewportContent()` is the single SetContent chokepoint**: it assembles `derivedLogContent()` (cached unstyled `logsFormatted` + unfiltered `logsPartial` + filter-exempt `logsErrLine`), and when a search is committed, splits it on `\n`, recomputes `logSearchMatches []int` (physical-line indices via `logComputeMatches`) and overlays `highlightMatches` as a **SetContent-time pass** — `logsFormatted` itself stays UNSTYLED. Routing every write (`applyLogFormat`, `rederiveLogs`, `w`/`p`/resize `fullReformat`) through this chokepoint means all of them pick up the highlight + fresh match set for free. Search runs over the filtered survivors (a filter-hidden line is absent from the derived content, so it can never be a match); a filter that hides everything renders a `(no lines match filter)` placeholder. `highlightMatches` wraps the WHOLE physical line (only indices are known, not a substring offset) with `logSearchMatchStyle`/`logSearchCurrentStyle` (yellow / yellow-bold, in `styles.go`); a foreground-only style adds zero-width ANSI so `ansi.StringWidth` is unaffected. `n`/`N` (`cycleLogMatch`) cycle the ascending `logSearchMatches` with wrap-around; typing live-jumps to the first match; `scrollLogMatchIntoView` pins an off-screen match (auto-pausing follow via the `AtBottom` heuristic — `G` resumes). **Per-physical-line match semantics**: an occurrence fully within a wrapped row highlights, but an occurrence split *across* a soft-wrap boundary is not matched (accepted, pinned). **Layered `esc` ladder** (peel inner → outer): (1) typing-search cancel, (2) typing-filter cancel, (3) committed-search clear-only (stay), (4) committed-filter clear-only (stay), (5) leave screen (cancel ctx, `clearLogFilter()`/`clearLogSearch()`, back to `screenSelectContainers`). Rungs 1–2 live in the two **typing intercepts** at the very top of `case screenLogs` — while `m.logFiltering || m.logSearching`, every keystroke routes to the open input and returns (else `w`/`p`/`G`/`f`/`q` would fire actions mid-query); rungs 3–5 in the main-switch `esc` (reached only when no input is open — filter and search bars are mutually exclusive). The `q`→`esc` rewrite block is skipped while an input is open (via the shared `typingInInput()` guard, which reads `m.logFiltering || m.logSearching`), so `q` types literally; with no input open `screenLogs` falls into the block's `default: key = "esc"` case. **Reserved one-line bar**: `logBarLine()` renders exactly ONE physical line below the viewport (blank when idle), precedence typing-search (`/ <q> [mode] (i/N)` / `(no match)`) → typing-filter (`f <q> [mode] · N/M shown` / `(bad regex)`) → committed summary (`filter: <q> [rx] · N/M · search: <q> (i/N)`, `logFilterCounts` counts RAW lines to match where the filter runs) → idle blank; the final `clampToWidth(line, m.width)` (ANSI-aware `ansi.Truncate`, no-op at width ≤ 0) enforces the never-wrap invariant (pinned by `TestLogBarLineNeverWraps`). To reserve that line, viewport height drops `- 6` → `- 7` at **exactly the two log sites** (`enterLogs` and the `WindowSizeMsg` `screenLogs` branch) — the two config sites are untouched, so a blind `- 6` find/replace is wrong. The follow indicator stays on the title line. Inputs are built lazily via `textinput.New()` inside the `f`/`/` open handlers (not `NewModel`) so `Model{}` test literals stay valid; `f` early-returns on an empty raw buffer, `/` on empty derived content. TUI-only — no CLI/runner/compose changes.
