## Unmanaged containers — the `HostContainers` composer and the three-method `dockerRunner` seam

a container with no `com.docker.compose.project` label — a hand-started `docker run` postgres, a watchtower, a monitoring agent — is invisible to every compose command, so it gets its own `runner.Composer`: `compose.HostContainers` (`internal/compose/hostcontainers.go`), read-only, built on host-level `docker ps`/`docker stats`/`docker logs`/`docker exec`. The differentiator is remote reach: the ControlMaster socket is already open, so the view inspects a production host with **nothing installed on that host**. **One type, one seam — not two parallel types.** The ten `runner.Composer` methods split into five writes that `return errReadOnly` and five reads that differ between local and remote only in how the `*exec.Cmd` is built, so the whole local/remote variation collapses into a single unexported `dockerRunner` field. **The seam needs THREE methods, not one `cmd(ctx, args...)` builder**, because the three call shapes are mutually exclusive: `run` CAPTURES and classifies (the remote adapter reuses `runRemoteDockerCmd`, so `classifySSHError`/`errSSHTransport` and explicit stderr capture come for free instead of being written a second time), `stream` writes to an `io.Writer` and must NOT allocate a TTY (a pty would let docker line-buffer and echo, corrupting the chunked reads the TUI log viewer makes) and wires BOTH Stdout and Stderr to `w` because `docker logs` sends the container's stderr to its own stderr, where most application logs land, and `tty` MUST splice `-t` on the remote side (matching `RemoteCompose.ExecCommand`). All three remote forms build the remote command string through one helper, `RemoteCompose.remoteDockerCmdString(args)` (`remote.go`, beside `sshArgs`), so the `docker` + `shellEscape` rule lives in one place instead of three. **Constructors are exported, the interface is not**: `cmd/root.go` has to build these and cannot name an unexported interface, so `NewLocalHostContainers(*Compose)` and `NewRemoteHostContainers(*RemoteCompose)` are exported while `dockerRunner` and both adapters stay package-private. Discovery is `hostPsArgs` = `ps -a --size=false --format {{json .}}` — the **template** form, not the bare `json` keyword, which only exists on Docker CLI >= 23.0 while this repo deliberately supports legacy standalone hosts via `Detect()`. **`--size=false` is load-bearing for latency and must not be dropped**: the CLI cannot tell which fields `{{json .}}` reads, so it conservatively requests container sizes, and `SizeRw`/`SizeRootFs` make the daemon walk every container's read-write layer — a `du`-style traversal per container that costs tens of seconds on a host with many or large containers (measured: `{{json .}}` alone returns `"Size":"0B (virtual 161MB)"`, the bare keyword and `--size=false` both return `"0B"`). `hostPsEntry` has no `Size` field, so that walk is computed, shipped over SSH and discarded. An explicit `false` wins over the format inference; naming the eight fields individually would avoid it too, but an unknown field is a **hard template error**, so `.State` (CLI >= 20.10) would break the legacy hosts this template form exists to serve. This regressed the project picker to ~30s on real hosts before it was caught; `parseHostContainers` reads NDJSON **only** — unlike the sibling `parseContainerStatus`/`parseStatsOutput`, which tolerate an array because the `--format json` flag they read changed shape across Docker versions; a per-container Go template emits one object per line by construction on every version, so there is no array form to tolerate. `isComposeManaged` matches the `com.docker.compose.project=` prefix **only at a token start** (`HasPrefix(labels, k) || Contains(labels, ","+k)`), **not by splitting into `k=v` pairs**: a label VALUE may legally contain a comma, so slicing the comma-joined `Labels` string into pairs can mis-slice — a false verdict would need a value containing the literal `,com.docker.compose.project=` (the trailing `=` is also what keeps the sibling `…project.config_files`/`…project.working_dir` keys from matching). Host-level `ps` has no Health field — it lives in the trailing `(...)` of `Status`, so `parseHealthFromStatus` captures it with `healthSuffixRe`, the SAME regex `formatUptime`/`stripHealthSuffix` uses (`uptime.go`), which grew a capture group rather than being duplicated — one grammar, one place, so the two consumers of the trailing annotation cannot drift. It is **anchored at the end**, which is what makes the reading trailing rather than first-match: without the anchor `Up 2 hours (healthy) (paused)` reports healthy (the `Exited (255) …` cases cannot catch that, since their first group is a numeric code the switch rejects anyway). `Running` reads `State == "running"` but **falls back to `HasPrefix(Status, "Up ")` when `State` is empty**: the `docker ps` JSON keys are reflected from the CLI's own formatter and `.State` only exists on Docker CLI >= 20.10 — exactly the legacy hosts `hostPsArgs` takes the template form for — so without the fallback every row on such a host renders a stopped dot beside a live `Uptime` and `x` exec refuses on a container that is plainly up (`hostContainerRunning`); `Created`, `Uptime` and `Ports` reuse the existing `parseCreatedAt`, `formatUptime` and `parsePortsString`, and there is no replica aggregation because a host container is its own row. `ContainerStats` goes through the seam directly rather than through `AllContainerStats`/`AllContainerStatsRemote`: those take a concrete `*Compose`/`*RemoteCompose`, which a seam-held `HostContainers` cannot supply without a type switch that would defeat the seam — only the two-line argv build is duplicated, `parseStatsOutput` and `aggregateStatsByService` are reused, and a container present in `ps` but absent from `stats` is skipped, not an error. It **early-returns before the stats call when there are no unmanaged entries** — the join would be empty by construction, and `docker stats --no-stream` is a ~1.5s host-wide call (a full SSH round-trip remotely) that the 5s refresh tick would otherwise pay forever. `ContainerStatus` has NO counterpart guard and must not grow one: its loop already yields an empty map for free, so the branch would buy nothing and imply a cost rationale it does not have. `hostStatsArgs` takes the SAME `{{json .}}` template form as `hostPsArgs`, for the same reason — the bare `json` keyword needs Docker CLI >= 23.0, and for `docker stats` the CLI rewrites that keyword to exactly this template, so the output is identical on a modern host and the two argv builders in this file no longer argue opposite positions on the same host-version question. **That equivalence is per-command and does NOT generalise**: it was verified for `stats`, which has no size concept, and assuming it also held for `ps` is what hid the `--size=false` regression above. Verify the two forms against the specific subcommand before reusing this argument a third time. `AllContainerStats` keeps the keyword; that is pre-existing and out of this file's scope. `CheckUpdates` sources the name→image map from the `Image` field `docker ps` already returned (no second call, and no `docker compose config` — there is no compose file to read) and delegates to the shared `scanImageUpdates`, passing a nil `localErrWrap` — which is what keeps the daemon cascade off this path; it could never fire anyway, because a dead local daemon fails the `docker ps` discovery call first, long before any image inspect runs. `hostImageMap` drops entries with no image ref AND entries whose `Image` is a **bare image ID** (`^[0-9a-f]{12}([0-9a-f]{52})?$` — what `docker ps` reports for an untagged image): no registry can be asked about a ref with no repository, so the verdict is the tri-state absent either way, and including it would only buy a wasted round-trip per hand-started container and skew the cascade ratios. The TUI never fires this check automatically — see the read-only UI contract below: `U` is the only trigger. `scanImageUpdates` **memoizes by image ref**, which matters far more here than on a compose project: distinct services usually have distinct images, but host containers repeat one image constantly (three MCP sidecars off one tag), and each comparison costs a local inspect plus up to two registry inspects — every one a separate SSH round-trip. The memo also keeps the cascade counters honest, since each distinct image contributes exactly one attempt. `ContainerStatsFromBulk` is deliberately NOT implemented — its only consumer is `cmd/list.go`'s `bulkStatsAggregator`, and list integration is deferred, so it would be dead code.

## Unmanaged containers — the `(unmanaged)` group, the widened `ComposerFactory`, and the cache-key collision

> **Superseded in part.** The project picker screen was deleted with the multi-project host view: the `(unmanaged)` row is now the last GROUP on the grouped container screen, not a picker entry. `compose.Project.Desc` went with `viewSelectProject`, its only reader, and `CountUnmanaged`/`WithUnmanagedRow` went with the picker they served — `internal/compose/unmanagedrow.go` is gone and only `UnmanagedProjectName` survives, in `hostcontainers.go`. **`buildSvcGroups` (`internal/tui/entries.go`) is the SOLE producer of the row now.** The `ComposerFactory` and cache-key rules below are unchanged and still load-bearing. See `docs/architecture/tui-multi-project.md`.

the view is one group at the end of the grouped container screen, not a new screen. `compose.Project` gains `Unmanaged bool` — `Status` is NOT reused for it, because `Status` means the `docker compose ls` lifecycle string and the group header never renders that, so overloading it would leave the field with two meanings and the rendered one bolted on. **The group is derived, not fetched separately.** The `ProjectLoader` is plain `ListProjects` on both paths and appends nothing; `buildSvcGroups` takes its project ORDER from that loader and then walks the host-wide status map for names the loader did not report, appending them after the loader's — name-ordered, with the `compose.UnmanagedProjectName` bucket LAST. That leftover path is where the `(unmanaged)` group comes from: the host-wide `docker ps` behind `GroupedHost` already reports every container with no project label under that name, so asking the host to COUNT them separately would be a second `docker ps` per refresh for an answer the first one already carries. Appending last is deliberate for the same reason the old picker row bypassed `sortProjects` — `(` sorts before every letter, so a name-sorted `(unmanaged)` would land first instead of last. **A group born on that leftover path carries an EMPTY `ConfigDir`**, because `docker ps` reports a project NAME and nothing else; operations, drill-in and rollback on such a group are refused with a warning rather than run against cdeploy's own working directory, and `projUpdatesCacheKey` substitutes `"name:" + proj.Name` for the empty `ConfigDir` so two of them cannot collide with each other — nor with the local fast track's own bare `"|"` — in the update cache. The `(unmanaged)` bucket is the common case of that shape and is read-only for its own reasons; a compose project the loader missed is the other. The name lives in the exported `compose.UnmanagedProjectName` const, which the grouped fold, the factory branch and the renderer tests all read, so it cannot be spelled two ways. A discovery failure is no longer swallowed into an invisible row: a host-ps failure lands in `svcErr`, because it leaves no usable screen. **Every branch `cmd/root.go` contributes to the COMPOSER side lives in a package-level helper, never in the `RunE` closure**, because `cmd/root_test.go` tests flag registration only — the root command needs a TTY and is never executed, so a closure body has no test seam and the whole feature could be deleted with CI green. The two helpers are `localComposerFor(proj, detector, detected)` and `remoteComposerFor(proj, rc)` (both `ComposerFactory` literals; `remoteComposerFor` reads the host off `rc.Host` rather than taking a parallel `host` parameter a caller could pass out of step); each is unit-tested in `cmd/root_test.go`. Add a helper, not an inline `if`, for anything new here. **`ComposerFactory` is widened to `func(proj compose.Project) runner.Composer`** — the unmanaged row has no config directory, and a sentinel directory string would be a magic value that deepens the cache-key problem below rather than avoiding it; `cmd/list.go` declares its own `func(dir string) runner.Composer` and is unaffected. **`updatesCacheKey()` gains an `"unmanaged|"` prefix from `m.readOnly()`, and this is the subtlest invariant of the feature.** The key is `projDir + "|" + serverName`, and the local fast track (the drilled screen `cdeploy` lands on in a directory holding a compose file, with no `projDir` recorded) keys a bare `"|"` — an unmanaged row's empty `ConfigDir` would key `"|"` too, a direct collision. Two failures follow: a fresh entry from either context suppresses the other's `CheckUpdates` for the full 10-minute TTL, and `hydrateUpdates` writes one context's verdicts onto any colliding service name (the phantom guard drops only *unknown* names, not colliding ones). The prefix is derived from the COMPOSER rather than from a parallel `projUnmanaged bool` field: the composer IS the context the cache describes, it is live at all three `updatesCacheKey()` call sites, and it is assigned or nil'd at exactly the sites such a field would have to be cleared at — so deriving it keeps four entries out of the back-navigation cleanup discipline CLAUDE.md calls the repo's most fragile invariant, where one forgotten site silently mis-keys the cache (pinned end-to-end by `TestUpdatesCacheKey_FollowsComposerAcrossNavigation`, which drives unmanaged-pick → `esc` → `esc` → local fast-track). **RESOLVED: the host view re-lists itself.** This section used to record a load-time snapshot in both directions — a picker row count cached across `esc`, and an unmanaged service list the 5s `refreshTickMsg` never re-fetched, so a container started by hand while the screen was open never appeared and a removed one kept a stopped-dot row. The grouped host view fixed both. `loadGroups()` is the grouped counterpart of `loadServices`, and the grouped `servicesMsg` branch is BOTH the initial load and the 5-second reload, so the project list and the container rows are re-derived every tick. The thing that made it "not a one-liner" is exactly what that branch owns: unlike the drilled branch it does NOT reset `svcCursor`/`svcOffset`/`selected` and does NOT call `clearSearch()` — it preserves the cursor, the selection, the fold state and an active search, prunes the selection, re-derives `searchMatches`, clamps the cursor and replays the cached update verdicts. The landing sites clear that state once, on entry, which is what lets the reload preserve it. **What remains status-only is the DRILLED single-project view**: it refreshes status and stats on the tick but does not re-run `ListServices`, so a service added to the compose file while it is open needs an `esc` and a fresh drill-in. Stated in the README rather than left to be discovered.

## Unmanaged containers — the read-only UI contract

`ReadOnlyComposer` is declared in `tui` beside `ConfigProvider`/`ExecProvider` and type-asserted on the concrete composer, with a **named** `ReadOnlyComposer() bool` method — a method-less marker would be `interface{}`, which every composer satisfies, so `m.readOnly()` would be true everywhere. `Model.readOnly()` is nil-safe, so a `Model{}` test literal reads as writable. **In GROUPED mode the predicate reads the GROUP LIST, not the composer**: it is true when EVERY group is the unmanaged bucket (`allGroupsUnmanaged()`), so an unmanaged-only host gets the read-only help table and the read-only footer pair instead of advertising `d`/`r`/`s` no-ops, while a host holding even one compose project stays writable. Reading the COMPOSER there would be wrong for the reason the short-circuit was written: grouped mode holds no composer between actions, an action key binds the cursor row's one and the return site drops it again, and `x` deliberately KEEPS its binding across the confirmation prompt — so a composer-derived predicate would flip the whole screen to the read-only variant (no checkboxes, a 7-cell caption pad instead of 10, a different footer pair and therefore a different `svcVisibleCount`) for the length of an exec prompt over an unmanaged row. The group list cannot change while a prompt is armed, so it carries the rationale intact. `d`, `r`, `s`, `R`, `c`, `space` and `a` all early-return, each calling `fixSvcOffset()` first: the container dispatch clears `m.warning` above the switch, and the freed warning line grows `svcVisibleCount()` by one, so a gated key that returned without re-clamping would leave a too-large `svcOffset` and a blank row under the last service of a scrolled list (`TestReadOnly_GatedKeyReclampsOffset`). `c` and `R` would gate themselves for free (`HostContainers` implements neither `ConfigProvider` nor `RollbackPreparer`) but get an **explicit** gate anyway: an inert key that a help table still names is the exact failure the `?` overlay exists to prevent, so the gate and the table have to move together. Because a read-only mock implements neither capability either, `TestReadOnly_GatesWriteKeys` alone would pass on the type assertion rather than on the gate — `TestReadOnly_GatesWriteKeys_WithCapableComposer` drives the same two keys through a double that DOES satisfy both, so the `m.readOnly()` early return is the only thing left standing between the key and its action. **Nothing advertises a no-op, and that extends past the keys to the widgets.** `containerHelpLines()` returns a different idle pair when read-only (`line1` drops `space toggle`, `line2` becomes `l logs • x exec`); because `containerFooterLines()` and `containerFooter()` both read that one helper, the height math and the render follow the variant by construction. **The read-only pair also inverts a width relationship the writable footer relied on.** `containerFooterLines()` is decided from the IDLE pair alone and must stay state-INDEPENDENT — `svcVisibleCount()` reserves rows from it, so reading the substituted footer would grow the list mid-search, the exact re-flow the reserved bar exists to prevent. On the write path the committed-search substitution (`n/N cycle • esc clear`, 25 cells) is SHORTER than the idle `line2` (35), so the one-line branch always held it; the read-only `line2` (`l logs • x exec`) is 19 cells, so at widths 43-46 the substitution overran the width by 1-4 cells of CONTENT. `containerFooter()` therefore clamps every rendered line with `clampToWidth`, the same never-wrap guarantee `searchBarLine()`/`logBarLine()` give — pinned by `TestContainerFooter_NeverExceedsWidth` and by the `readOnly` dimension of `TestContainerView_ExcessLineWidthIsPaddingOnly`. `helpGroupsFor` reads `helpContext.readOnly` (supplied by `Model.helpGroups()` from `m.readOnly()`) and returns `readOnlyContainerGroups(canGoBack)`: SELECT and OPERATE are gone whole and `c` leaves INSPECT, but **`enter` MOVES into INSPECT** as `{"enter", "confirm the exec prompt"}` — the `x` prompt still binds it and OPERATE was its only home, so deleting that group wholesale would break BOTH directions of `TestHelpGroups_NamesEveryBoundKey`. The two groups the variants SHARE come from shared constructors, `findGroup()` and `inspectGroup(readOnly bool)`, the same answer `leaveGroup(canGoBack)` already gives: FIND is byte-identical across variants and INSPECT differs only by `c` and `enter`, and both groups exist on no other screen — so a hand-copied pair would be new duplication a future key had to be added to twice, with no test comparing them. Group ORDER carries the same load as the writable table (LEAVE sits 3rd of 4 so `splitHelpGroups` leaves it in the left column) and the `actions` flags still drive `singleColumnOrder()`'s truncation order. The drift pin runs **per variant, never over a union**: `TestHelpGroups_NamesEveryBoundKey` reads `helpKeyTokens(s, canGoBack, false)` and `TestHelpGroups_ReadOnlyNamesEveryBoundKey` reads the `true` variant, both directions each. A union would weaken the writable half — a key deleted from the writable table but still named by the read-only one would go unnoticed. The selection affordances go too: the title loses its `(n/m selected)` counter and every row loses its `[ ]`/`[x]` checkbox, because multi-select exists only to feed `d`/`r`/`s`/`R` and a checkbox advertises a dead key as loudly as the counter does. That silently couples to the caption row — the left pad is `cursor(2) + checkbox(3) + space(1) + health(1) + space(1) + dot(1) + space(1) = 10`, so the read-only pad must be **7** in lockstep or every caption misaligns against its data column. **No new screen, no new `tea.Msg`, no new goroutine and no new session counter**: the screen runs the existing `loadServices`/`refreshStats`/`maybeRefreshUpdatesCmd` batch, which is already session-gated, so `clearSearch()` gains no departure site of its own (`enterInspect()` later added one of its own — see `docs/architecture/tui-inspect-screen.md`; the current list is ELEVEN sites, enumerated in `docs/architecture/tui-logs-and-search.md`), `hasStatusColumns()` is unchanged and `TestAllScreens_Complete` is unaffected. **The update check is the one member of that batch that does NOT fire here.** All THREE automatic entry points — `maybeRefreshUpdatesCmd()`, the `statusMsg` self-heal, and `Init()`'s local fast-track path — consult `autoUpdatesAllowed()` (= `!m.readOnly() && !m.grouped` — the grouped host view refuses for the same reason, squared across every project on the host) and skip the fetch, leaving `U` as the only trigger. The fast path is the one that does NOT route through `maybeRefreshUpdatesCmd()` (the cache is empty on launch, so it calls `refreshUpdates()` directly), which is why it needs its own gate; `NewModel` sets `updateInFlight = m.autoUpdatesAllowed()` rather than a flat `true`, so the flag tracks whether a fetch is actually queued — a `true` with no fetch behind it never clears, and `maybeRefreshUpdatesCmd`'s in-flight guard would then refuse every later fetch, including `U`'s. No production caller hands a `HostContainers` straight to `NewModel` today (the unmanaged view is reached through the grouped host view), but the gate is what keeps the invariant true for one that does. A compose project bounds `CheckUpdates` to one service list the user is actively managing; the unmanaged set comes from `docker ps -a`, so it grows with every container ever left on the host and each distinct image costs a REGISTRY manifest request. An automatic fan-out on screen entry, repeated by every 5s status tick, can exhaust the anonymous Docker Hub manifest quota — which then breaks a real `docker pull` from the same host. The CLI reaches the same conclusion for the same reason (`list --updates` is opt-in), and the `?` overlay already names `U check updates`. Gating only SOME of the three entry points leaves the rest firing (the self-heal is the worst — it repeats forever), so `TestReadOnly_NoAutomaticUpdateFetch` drives the first two and `TestReadOnly_InitFastPathHonoursOptIn` the third, each against a writable control, and `TestReadOnly_UpdateKeyStillFetches` pins the other half of the contract. **The two gated entry points also CLEAR `m.updatesErr` when the cache entry has expired.** A failed `U` caches a failure whose warning both self-heal paths restore while it is fresh; once the entry ages out, nothing here will ever refetch it, so leaving the warning up would keep one failed `U` on screen for the life of the view (`TestReadOnly_StaleUpdateWarningClears`; the `statusMsg` clear sits BEFORE that handler's `fixSvcOffset()` so the freed footer row is re-clamped). The success side has the matching consequence and it is deliberate: the `⇧` glyphs blank when the 10-minute entry expires and return on the next `U` — documented in the README.
